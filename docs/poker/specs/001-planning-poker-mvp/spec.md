## Clarifications

### Session 2026-07-16

- Q: 全員切断時にルームを即座に破棄するか、猶予期間を設けるか → A: 即時破棄（接続数が 0 になった瞬間にルームを消す）
- Q: 切断した参加者が同一人物として復帰する識別方法は → A: ブラウザに保持した参加者トークンで自動復帰（同じブラウザからの再接続は同一参加者として投票状態ごと復帰）
- Q: 投票受付中の途中参加者を「全員投票による自動公開」の判定に含めるか → A: 含める（自動公開の条件は常に「接続中の全参加者が投票済み」。待ちたくない場合はホストの手動公開で対応）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ルーム作成と招待リンクによる参加 (Priority: P1)

スクラムチームのファシリテーター（ホスト）が見積もりセッション用のルームを作成すると、
招待リンクが発行される。チームメンバーはそのリンクを開き、名前を入力するだけで
ルームに参加できる。参加者一覧は全員の画面にリアルタイムで反映される。

**Why this priority**: ルームが存在しなければ投票も結果表示も成立しない。
全機能の前提となる最小の土台であり、これ単体でも「誰が集まっているか」を
共有する価値を提供する。

**Independent Test**: ホストがルームを作成し、別のブラウザ（または端末）から
招待リンクで名前を入力して参加し、双方の画面に同じ参加者一覧が表示されることで
単独検証できる。

**Acceptance Scenarios**:

1. **Given** トップページを開いている, **When** ホストが名前を入力してルームを作成する, **Then** ルーム画面に遷移し、共有可能な招待リンクが表示される
2. **Given** 有効な招待リンクを受け取った, **When** 参加者がリンクを開いて名前を入力する, **Then** ルームに参加し、既存メンバー全員の画面に新しい参加者が表示される
3. **Given** 存在しない（または終了済みの）ルームのリンクを開いた, **When** 参加を試みる, **Then** ルームが存在しない旨のメッセージが表示され、参加できない

---

### User Story 2 - カードによる投票と一斉公開 (Priority: P1)

参加者はフィボナッチデッキ（0, 1, 2, 3, 5, 8, 13, 21, ?, ☕）からカードを1枚選んで
投票する。投票中は他の参加者からは「投票済みかどうか」だけが見え、選んだ値は
見えない。全員が投票し終えるか、ホストが公開操作を行うと、全員の票が一斉に
公開される。

**Why this priority**: プランニングポーカーの核心体験。「他人の票に影響されずに
見積もる」というアンカリング防止が本ツールの存在理由そのものであるため、
ルーム参加と同格の最優先とする。

**Independent Test**: 複数参加者でルームに入り、一部が投票した時点で他者から
値が見えないこと、全員投票（またはホスト公開操作）で全票が同時に表示されることで
単独検証できる。

**Acceptance Scenarios**:

1. **Given** ルームに複数の参加者がいる, **When** 参加者がカードを選択する, **Then** 本人には選択したカードが見え、他の参加者には「投票済み」状態のみが表示される
2. **Given** 一部の参加者が投票済み, **When** 残りの全員が投票を終える, **Then** 全員の画面で全参加者の票が一斉に公開される
3. **Given** まだ全員が投票していない, **When** ホストが公開操作を行う, **Then** その時点の票が全員の画面で一斉に公開される（未投票者は未投票として表示される）
4. **Given** 投票済みの参加者がいる（公開前）, **When** その参加者が別のカードを選び直す, **Then** 投票は上書きされ、他者には引き続き「投票済み」状態のみが見える

---

### User Story 3 - 結果表示と次ラウンドへの進行 (Priority: P2)

票の公開後、全参加者の画面に各自の票と集計値（平均・最頻値）が表示される。
ホストは「再投票」（同じ議題をもう一度見積もる）か「次のラウンド」（新しい議題に
進む）を選択でき、いずれの場合も全員の投票状態がリセットされて次の投票が始まる。

**Why this priority**: 集計と次ラウンド進行がなくても「せーの」で票を見せ合う
最低限の見積もりは成立するが、実際のセッション運用（意見が割れたら再投票、
合意したら次へ）にはこれが不可欠。

**Independent Test**: 票公開後の画面に平均・最頻値が正しく表示されること、
ホストの再投票／次ラウンド操作で全員の画面が投票前状態に戻ることで単独検証できる。

**Acceptance Scenarios**:

1. **Given** 全票が公開された, **When** 結果を表示する, **Then** 各参加者の票・数値票の平均・最頻値が全員の画面に表示される
2. **Given** 「?」や「☕」の票が含まれる, **When** 集計値を計算する, **Then** 数値以外の票は平均の計算から除外され、票としてはそのまま表示される
3. **Given** 結果が表示されている, **When** ホストが再投票または次ラウンドを開始する, **Then** 全参加者の投票状態がリセットされ、全員の画面が投票受付状態に戻る

---

### User Story 4 - 切断への耐性とホスト権限の繰上 (Priority: P3)

参加者が通信の切断などでルームから離脱しても、セッションは継続できる。
ホストが切断した場合は、残っている参加者のうち最も早く参加した人に
ホスト権限が自動的に引き継がれ、公開・ラウンド進行の操作が途切れない。

**Why this priority**: 快適な運用には必要だが、発生頻度は低く、最悪の場合
ルームを作り直せば回避できるため、コア体験より優先度を下げる。

**Independent Test**: ホストの接続を切断し、残った参加者の一人にホスト操作
（公開・次ラウンド）が可能になることで単独検証できる。

**Acceptance Scenarios**:

1. **Given** 投票中に参加者が切断した, **When** 残りの参加者が全員投票する, **Then** 切断した参加者を除いた全員投票として票が公開される
2. **Given** ホストが切断した, **When** ルームに他の参加者が残っている, **Then** 最先着の参加者にホスト権限が移り、その参加者がホスト操作を行える
3. **Given** 切断した参加者がいる, **When** 同じルームに再接続する, **Then** 進行中のラウンドに復帰できる

---

### Edge Cases

- 最後の1人が退室（切断）したルームはどうなるか → 接続数が 0 になった時点でルームは即時破棄され、以後そのリンクは無効となる（猶予期間なし。全員同時リロード等でルームが消えることを許容する）
- 参加者が1人（ホストのみ）でも投票・公開は成立するか → 成立する（動作確認用途）
- 同じ名前の参加者が複数参加した場合 → 参加は許可し、別々の参加者として区別して表示する
- 全員が「?」や「☕」に投票した場合 → 平均は算出不能として表示し、票はそのまま表示する
- 最頻値が複数ある場合 → 該当する値をすべて表示する
- ラウンド進行中（投票中・結果表示中）に新しい参加者が参加した場合 → 参加は許可し、未投票として自動公開の判定対象に含める（投票受付中なら投票できる。待たせたくない場合はホストが手動公開する。結果公開後の参加者は結果を閲覧できる）
- ホスト切断による権限繰上の後、元のホストが再接続した場合 → 一般参加者として復帰する（ホスト権限は自動では戻らない）
- 招待リンクの形式が不正な場合 → エラーメッセージを表示し、トップページへ誘導する

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ホストは名前を入力するだけでルームを作成できなければならない（アカウント登録・ログインは不要）
- **FR-002**: システムはルーム作成時に、参加用の一意な招待リンクを発行しなければならない
- **FR-003**: 参加者は招待リンクを開き、名前を入力するだけでルームに参加できなければならない
- **FR-004**: システムは参加者の入退室・投票状態の変化を、ルーム内の全参加者の画面にリアルタイム（体感的に即時）に反映しなければならない
- **FR-005**: システムはフィボナッチデッキ（0, 1, 2, 3, 5, 8, 13, 21, ?, ☕）の10種のカードによる投票を提供しなければならない
- **FR-006**: 票の公開前は、各参加者の選択値を本人以外に見せてはならない。他者には「投票済み／未投票」の状態のみを表示する
- **FR-007**: 参加者は票の公開前に限り、自分の票を変更できなければならない
- **FR-008**: システムは接続中の全参加者（途中参加者を含む）の投票完了時に票を自動で一斉公開しなければならない
- **FR-009**: ホストは全員の投票完了を待たずに、任意のタイミングで票を一斉公開できなければならない
- **FR-010**: システムは公開後の結果として、各参加者の票・数値票の平均・最頻値を表示しなければならない。「?」「☕」は平均の計算から除外する
- **FR-011**: ホストは結果表示後に再投票または次ラウンドを開始でき、いずれも全参加者の投票状態をリセットしなければならない
- **FR-012**: ホストが切断した場合、システムは残存参加者のうち最先着の者にホスト権限を自動で引き継がなければならない
- **FR-013**: 切断した参加者は、ルームに他の接続中の参加者が残っている間に限り、同じブラウザから再接続することで同一参加者として復帰できなければならない。復帰時は切断前の投票状態を引き継ぐ（本人識別はブラウザに保持する参加者トークンによる）
- **FR-014**: ルームの状態は揮発的であってよい。接続中の参加者が 0 になったルームは即時破棄され、サーバー再起動後にルームが失われることを許容する
- **FR-015**: 存在しないルームへの参加試行や不正な形式のリンクに対して、システムは分かりやすいエラーメッセージを表示しなければならない

### Key Entities

- **ルーム**: 見積もりセッションの単位。一意な識別子（招待リンクの元）、参加者の集合、現在のラウンドを持つ。全員退室で消滅する
- **参加者**: ルーム内の個人。名前・ホストか否か・接続状態を持つ。ホストはルーム内に常に1人。同一性はブラウザに保持する参加者トークンで識別する（名前は識別子ではない）
- **ラウンド**: 1回の見積もりの単位。状態（投票受付中／公開済み）と投票の集合を持つ。再投票・次ラウンドで新しいラウンドに置き換わる
- **投票**: 参加者とカード（デッキの1枚）の組。公開前は本人以外に値を秘匿する
- **デッキ**: 選択可能なカードの集合。MVP ではフィボナッチデッキ（0, 1, 2, 3, 5, 8, 13, 21, ?, ☕）に固定

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 参加者は招待リンクを開いてから 30 秒以内にルーム参加を完了できる（名前入力のみ）
- **SC-002**: 投票・公開・入退室などの状態変化は、ルーム内の他の参加者の画面に 1 秒以内に反映される
- **SC-003**: 10 人規模のチームが 1 つの議題の見積もり（投票開始〜結果確認）を 3 分以内に完了できる
- **SC-004**: 票の公開前に他の参加者の選択値が見える経路が存在しない（画面上・通信内容のいずれにも露出しない）
- **SC-005**: ホスト切断時、残存参加者が 5 秒以内にホスト操作（公開・次ラウンド）を引き継いで続行できる
- **SC-006**: 初見の参加者が説明なしで投票を完了できる（投票操作の成功率 100% を初回利用テストで確認）

## Assumptions

- 利用者は同一のオンラインミーティング等で会話しながら利用する少人数チーム（1〜20 人程度／ルーム）を想定する
- 認証・アカウント管理は行わない。名前は自己申告であり、なりすまし対策はスコープ外とする
- 見積もり結果の永続的な記録・履歴は不要（設計文書でスコープ外と明記）。ルーム状態の揮発を許容する
- お題（ストーリー）リストの管理、観戦者ロール、デッキの切替、AI 連携は初回リリースに含めない
- 利用環境はモダンブラウザ（PC・スマートフォン）とし、常時接続可能なネットワークを前提とする
- UI の表示言語は日本語とする
- 同時に存続するルーム数は小規模（数十程度）を想定し、大規模スケールは要件としない
