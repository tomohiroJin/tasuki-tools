## うまくいったこと

### 1. 決まりを文書ではなくコードで守らせた

設計正本 §2 の方針どおり、決めたことのうち機械で守れるものは同じ PR で検査にした。

- **scripts**: スクリプト同士の取り込みの許可表（`script-imports.test.mjs`）・ドメインの `throw` とトップレベル `let` の拒否・
  packages の相対 import の `.js` 必須（ESLint）
- **web**: `ConnectionStatus` と WS の URL の写しの拒否（`audit-web-sync-boundary.mjs`）・トークンと同じ値の直書きの拒否
  （`audit-ui-components.mjs`。値は `shape.css` から読む）
- **同期サーバー**: エラーの文言の出どころ・ルームの引き方・大域の時計と乱数・アダプタの取り込みを固定するテスト、正規化を飛ばす配線を
  型で落とすブランド型 `TimerCommandReceiver`
- **変異検査**: 宣言の表の置き場（ID の一意・機構に数える・汚れの検査の除外・除外した場所を書き換えるパッチの拒否）

どれも、移した後に壊して赤を見てから入れた。

### 2. 特性テストを先に書き、緑のまま形を変えた

移す前の振る舞いをテストで固定してから構造を変えた。特性テストを書いて初めて見えた食い違いが多い。

- timer の INTERNAL_ERROR だけ文言が違う（R2）→ #381
- 実 WS 越しの 32 件で、入口ごとの違いが 3 つ見えた（R6）。topic には名簿が届かない・timer は 2 度目の参加を拒まない・timer の文言が違う。
  どれも変えずに固定した
- 前例の `INVALID_SETTLE` に記録の抜けがある（R4）→ #382

### 3. 振る舞いの疑いは直さずに切り出した

#373〜#378 は着手前に、#381・#382 は作業中に起票した。構造の変更と振る舞いの変更を同じコミットに混ぜていない。
振る舞いに触れざるを得なかった 2 点は、利用者の判断を仰いだ。

- `Result` にすると消える `RangeError` のログを、ハンドラが同じ形で残す（R4）
- `member.shuffle` の乱数の出どころを `Math.random` から crypto へ。分布は同じ一様（R7）

### 4. 新しい変異の ID を 1 つも足さなかった

#94 PR 3 と宣言の表でぶつからないよう、各計画 §5 で「新しい ID は足さない」とした。触った所に当たるパッチは、ID と意味を変えずに
延べ 39 本当て直した（#379: 19・#386: 11・#388: 6・#398: 3）。宣言は終わりの時点で 155 件。

## 踏んだ罠（事実と再発条件）

### 1. Issue の前提の多くが、測り直すと成り立たなかった

**事実**: R1 の計画は「前提の半分は、測ると成り立たなかった」と書いた。その後の子でも同じことが続いた。

- R1: import の抽出 3 つは、わざと意味が違った
- R3: 手書きの型とスキーマは食い違っていなかった
- R7: 依存の袋は全項目が使われていた
- R9: `connectionNotice` は #94 PR 2 で寄せ終わっていた
- R12: 押せる大きさは「9 か所」ではなく 12 宣言だった
- R1b: 行数と 0 件ガードの位置がずれていた

設計正本 §5 の構造案も、R1・R2・R3・R6・R7・R8・R9 で追記して上書きした。

**再発条件**: Issue を書いた時点から main が動いたとき、また集計の方法を書き残していないとき。
**計画の §1 に「Issue 本文の前提との差」の表を置き、測ってから使う**（epic の「各子 Issue で必ず行うこと」の 1 番目）。
この表が、どの子でも計画の判断の土台になった。

### 2. 寄せるときに、片方だけが持つ宣言を落とした（R11）

**事実**: 3 つの隠し文字のクラスを部品層の `.ui-visually-hidden` に寄せたとき、topic だけが持っていた字の色 `--coal-soft` を
「隠れている間は見えない」として外した。e2e の AA コントラストの測定は隠した文字も測るので、象牙の地に象牙色の字（1.13:1）として
5 件落ちた。`/code-review` は既に指摘していたのに、外す判断を通してしまった。色は `.topic-reader-heading` で topic の側に持つ形に直した。

**再発条件**: 写しを 1 つに寄せるとき、宣言の「和」を取らずに「共通部分」だけを残すとき。
**片方だけが持つ宣言を落とすなら、それを見ている検査（e2e・a11y の測定）を先に探す。** レビューの指摘を退けるときは、退ける根拠を実測で示す。

### 3. 変異検査を流している間に作業ツリーを触った（R9）

**事実**: 変異検査は当てた変異を `git checkout --` で戻すので、走っている間の書き換えは消えるか、結果に混ざる。R9 で一度これを
起こし、検査を止めて書き換えを確かめ直した。以後、**流している間は作業ツリーに触らない**を決まりにした。走っている間に見える
未コミットの変更は検査が当てている変異で、コミットしてはいけない。

**再発条件**: 長く走る検査（全件で約 7 分半）の裏で編集を続けるとき。

### 4. この環境では Playwright を流せなかった

**事実**: このクラウドの環境では `@playwright/test` の版と導入済みの Chromium が合わず、e2e と #321 の `e2e/parity` を手元で
流せなかった。e2e は CI で確かめた（R11 の失敗も CI で見つかった）。R12 の見た目の比較は、利用者の承認のうえで、
**ビルドした CSS（`--minify false`）のトークンを値へ戻して基準と突き合わせる形**に代えた（5 アプリとも差 0。トークンの局所の
上書きが無いので、計算後の値も同じ）。言えるのは計算前の宣言の一致までで、画素は比べていない。

**再発条件**: 見た目を変えうる変更を、e2e を流せない環境で進めるとき。静的な比べ方で何が言えて何が言えないかを、計画の台帳に書く。

### 5. PR の積み方とブランチの制約

**事実**: 押せるブランチが 1 つだったので、R9 は計画の PR A・B を 1 本（#386）にした。R11〜R1b は、前の PR がマージされるまで手元の
ブランチに積み、マージ後に main の上へ cherry-pick で載せ直した。R1b の計画は、前の PR（#398）がマージされた直後に push したため
そちらに載らず、計画だけの PR（#399）から始めた。

**再発条件**: 1 本のブランチで続けて PR を出すとき。push の前に、前の PR がマージされていないかを確かめる。
