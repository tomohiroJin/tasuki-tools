# 振り返り: 検査が静かに効かなくなる経路を塞ぐ（#135）

**対象**: Issue #135（走査対象の健全性。#70 / #116 / #119 / #103 / #126 からの申し送り 6 経路＋本作業中に発見した 1 経路）
**ブランチ**: `feature/135-scan-target-integrity`（`main` への統合はまだ）
**期間**: 2026-08-16・merge-base `c2f2920` から 30 コミット（Task 1〜9 と最終レビュー 5 ラウンドの是正を含む）

## この Issue が扱ったもの

「検査が赤にならないまま、何も検証しなくなる」経路 **7 つ**（①②③④⑧⑪⑬）に手を入れ、
**5 経路を完全に塞いだ。①と⑪には既知の残余がある**（後述「塞げなかったこと」）。
経路の一覧・実測値・決定の正本は
[設計正本](../superpowers/specs/2026-08-16-scan-target-integrity-design.md)、
規範は [ADR-0014](../adr/0014-scan-target-integrity.md) にある。本文書には転記しない。

## 踏んだ罠（事実と再発条件）

### 1. 対策の側が、塞ごうとしている性質そのものを繰り返し持っていた

**この作業で最も価値のある発見はこれである。** 「宣言と実体がずれても誰も言わない」という
性質を塞ぐ作業の中で、**対策の記述・実装・規範・ガイドが同じ性質を 7 回持っていた**。

| # | どこで | 何が起きたか |
|---|---|---|
| 1 | 設計正本 §3.10 | 「git は `**` を解さず **0 件**を返す（実測）」と書いたが誤り。測定自体は正しかった（測定時点で `scripts/lib/` が存在せず、一致しうるファイルが 1 つも無かった）が、そこから引いた**一般化が誤り**だった。しかも**危険の向きが逆**で、実際は「0 件になって空振りが露見する」のではなく「**一部だけ一致して残りを静かに落とす**」。「0 件なら落とす」検査では救えない |
| 2 | CI の結線（経路④） | `node scripts/list-scan-targets.mjs shell \| xargs shellcheck` と書きかけた。GitHub Actions の既定シェルは `bash -e` で **`pipefail` を設定しない**ため、**対象生成が失敗しても後段が成功すればジョブは緑**になる。塞ごうとしている性質を、対策の実装で作るところだった |
| 3 | `scripts/list-scan-targets.mjs` | 「除外が 1 件も一致しなくなったら落とす」という中核ロジックに**自動テストが無かった**（`node --test` の網の外）。レビューで発覚 |
| 4 | `scripts/audit-structure.mjs` | SC-035 / SC-039 が `?? ""` のフォールバックを持ち、対象ファイル（`App.tsx` / `handlers.ts`）を失っても **0（PASS）を出す**。さらに実装者の「値が変わらない＝結線が無事」という検証論法が成立しない（**結線が切れても同じ値が出る**のだから、値の不変は結線の証明にならない） |
| 5 | 0 件ガードそのもの | 走査量を数える経路（`d.src !== null`）と実際に走査する経路（`d.src ? ... : new Map()` の真偽値）が**別々に導出**されていた。`test: ""` にすると**ガードは 166 件を「走査した」と数えて素通しし、実走査は 0 件・SC032 は 0/0 で PASS** になった。**自分で書いた規範（決定 8）を、自分の実装が満たしていなかった** |
| 6 | ADR-0014 の周辺 | 存在しない「ADR-0014 決定 10」への参照を 3 か所**新設した**（ADR-0014 の決定は 1〜8 のみ）。**宣言と実体のずれを塞ぐ作業が、宣言と実体のずれを作った** |
| 7 | [`docs/guides/development.md`](../guides/development.md) | 手元実行の例が、自己テスト 3 本の直書き（**経路⑬**）と shellcheck のグロブ直書き（**経路④**）のままだった。**規範で塞いだ経路を、同じリポジトリのガイドが手順として教えていた** |

**再発条件**: 「検査が空振りする」類の欠陥を扱うとき、**扱っている当人が同じ空振りを書く**。
機序はいずれも同じで、**対象を導出する経路と、対象を数える／宣言する経路が 2 本ある**とき、
2 本が食い違っても誰も言わない。1・5 は「同じ量を 2 か所から導いた」、2 は「失敗が伝わらない
配管を足した」、3・4 は「検査の中核に検査が無い」、6・7 は「規範を足した先に実体が無い／
実体が旧いまま」。**塞ごうとしている性質は、その作業自体の作業条件でもある。**

**対処**: 述語と導出を 1 本に固定した。走査対象かどうかの判定は `hasScanTarget` の 1 本だけを
使い、読み込みは `loadScanTargets` の 1 回だけにして、**ガードが数えた集合と指標を測る集合を
構造的に同一**にした（ADR-0014 決定 9）。CI の配管は `| xargs` をやめ、
`bash -c 'set -euo pipefail; targets="$(...)"; cmd $targets'` の形に統一した。
ガイド・CI のコメント・憲法も同じ導出を指すよう揃えた。

### 2. 「直したつもりが片側だけ」が 9 回起きた

同じ主張が複数の文書・複数の節に散在しており、1 か所を直しても他が旧いまま残った。

| # | 直した側 | 残った側 |
|---|---|---|

| 2 | ADR-0009 D2 の本文 | **但し書き**が旧い指標値のまま |
| 3 | [ADR-0006](../adr/0006-test-conventions.md) の決定 2 と影響に追記 | **背景**だけ現在形で取り残し |

| 5 | ADR-0014 決定 8 に規範を追記（ラウンド 5） | **実装**は `null` しか塞がず `""` を取りこぼした |

| 8 | 振り返り・ADR-0014・設計正本を「7 経路に手を入れた」へ更新 | **経路⑪の未閉部分**（ログ衛生の `${pkg}/src` 実在未確認）がどの記録にも現れず、「7 経路を塞いだ」と読める断定が残っていた（最終の全体レビューで検出） |

**再発条件**: これは単発の不注意ではなく、**「同じ主張が複数の文書・複数の節に散在する」という
媒体の性質**である。ADR は「背景／決定／影響」の 3 節が同じ事実を別の言葉で述べ、ガイドは
手順として、CI はコメントとして、憲法は原則として、それぞれ同じ主張を持つ。**主張を 1 つ直すと、
同じ主張の残り 4 か所が自動的に古くなる。** 同じ罠は #119 で 2 度、#103 で複数回起きており、
本 Issue が 3 度目の再演である（[`2026-08-14-issue-119-pr-granularity.md`](./2026-08-14-issue-119-pr-granularity.md) /
[`2026-08-15-issue-103-ip-rate-limit.md`](./2026-08-15-issue-103-ip-rate-limit.md)）。

**その結果**: Task 9（規範と文書）は**レビュー 5 ラウンド**を要し、
**ラウンド 1〜4 のすべてで「修正が新しい矛盾を作る」ことが起きた**。ラウンドごとの指摘の
中心は毎回「前回の修正が別の場所と食い違いを作った」であって、当初の欠陥ではなかった。

**対処**: 直したら、同じ主張の別の場所を grep する。**探索範囲を `docs/` に限らず
`.github/` / `scripts/` / `.specify/` / `AGENTS.md` / `README.md` へ広げ、言い回しも変えて
探す**（4 の見逃しは範囲と語の両方が足りなかった）。Task 9 の後半 2 ラウンドでは「探した語と
結果」の表を報告に付け、当たらなかった語も残した。

### 3. 一時ファイルの後始末で、既存の追跡下ディレクトリを消した

**事実**: 経路④の破壊検証で `deploy/timer/probe.sh` を 1 ファイルだけ作ったのに、後始末の
指示が `rm -rf deploy/timer` だった（**コントローラの指示ミス**）。`deploy/timer/` は
`app.env` / `caddy/`（3 ファイル）/ `env.example` / `NOTES.md` / `service.tmpl` を含む
**元からある追跡下ディレクトリ**だった。追跡下 7 ファイルは `git checkout -- deploy/timer/` で
復元したが、gitignore 対象の `deploy/timer/dist/` は復元できなかった（実害なし。
`deploy/deploy.sh` が毎回生成する中間物）。

**再発条件**: 一時ファイルを既存ディレクトリの中に作り、後始末をディレクトリ単位で書くとき。
「自分が作った」という記憶がディレクトリにまで拡張される。

**対処**: **一時ファイルの後始末は、作ったファイルだけを消す。** ディレクトリごと消す前に
`git ls-files <dir>` で元からあるかを確かめる。

### 4. `git checkout -- <file>` が未コミットの実装ごと消した

**事実**: 破壊検証の復旧に `git checkout -- <file>` を使ったところ、同じファイルに入っていた
未コミットの実装まで巻き戻した（既知の罠 24 の再演）。

**再発条件**: 実装直後（未コミット）に同じファイルを壊して検証するとき。復旧手段が
「HEAD に戻す」なので、HEAD に無いものは区別なく消える。

**対処**: **破壊検証は必ずコミットしてから行う。** Task 8 以降の全破壊検証は
「コミット → 作業ツリー clean を確認 → 壊す → 赤を見る → `git checkout -- <該当 1 ファイル>` →
`git status --porcelain` が空を確認」の順で実施した。

### 5. `mutation-check` は作業ツリーが clean であることを要求する

**事実**: 実装直後（dirty）に対照実行しようとしても `mutation-check` が走らない。
「壊す前に緑を見る」という対照実行が、実装した直後の状態では成立しない。

**再発条件**: 変異検査を対照に使いたい局面が、必ず「実装したばかりで未コミット」と重なるとき。

**対処**: 対照実行はコミット後に行う。`scripts/` 側の恒真化確認は変異検査では取れないため、
`diffTargets` を「常に空の差分を返す」実装へ差し替えて単体テストが赤くなることを手で確認した
（`# pass 12 / # fail 4`。詳細は [検証記録](../superpowers/plans/2026-08-16-scan-target-integrity-verification.md)）。

### 6. zsh の無引用展開は単語分割しない

**事実**: 経路④の破壊検証で `shellcheck ... $targets` を zsh でそのまま実行したところ、
改行区切りの出力が単語分割されず 1 個の巨大な引数として渡り、`openBinaryFile: does not exist`
という **SC2045 とは無関係の理由**で `exit=2` になった。危うく「検出できた」と誤認するところだった。

**再発条件**: bash の単語分割を前提にしたワンライナーを zsh で叩くとき。**終了コードだけを見ると、
別の理由の赤を「狙いどおりの赤」と読んでしまう。**

**対処**: `bash -c '...'` で包んでやり直した。「**赤の終了コードだけでなく本文まで確認する**」
という規則（憲法 原則 VII）が実際に効いた例である。ガイドの手元実行例も `bash -c` の形へ揃え、
zsh から実際に叩いて通ることを確認した。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

上の 1 の表のうち 3・4・5 は、**当時の全検査（typecheck・lint・全パッケージのテスト・
自己テスト・変異検査 13 件・監査 3 種）が緑のまま**成立していた。機序は 3 つとも違う。

### 除外の死活検知に自動テストが無かった（表 3）

**何が緑だったか**: `scripts/list-scan-targets.mjs` の「除外が 1 件も一致しなくなったら落とす」
という中核ロジックは、消しても自己テストが 1 件も落ちなかった。

**なぜ緑だったか**: `node --test` の対象列挙が **ci.yml に 4 本直書き**（ガイドの手元実行例は
3 本）で、`scripts/lib/` 配下も `list-scan-targets` 自身も列挙に無かった。**経路⑬（本作業中に
発見）そのものが、経路⑬を塞ぐコードの検査を殺していた。**

### 指標が依存するファイルピンが `?? ""` で消えていた（表 4）

**何が緑だったか**: `apps/timer-web/src/App.tsx` を改名すると SC-035 は「該当なし」＝ 0 を返し、
`apps/timer-sync/src/application/handlers.ts` を失うと SC-039 が同じく 0 を返す。**どちらも PASS。**

**なぜ緑だったか**: `web.srcFiles.get("App.tsx") ?? ""` は「ファイルが無い」と「違反が無い」を
同じ値へ潰す。加えて、実装者が使った検証論法（「値が変わらないから結線は無事」）は
**結線が切れても同じ値が出る**ため成立しない。**値の不変は結線の証明にならない。**

**塞ぎ方**: 式（`?? ""`）は変えず、`METRIC_FILE_PINS`（パスと理由の対）を宣言し、
`main()` で実在を確認する形にした。

### 0 件ガードが「宣言の行数」を数えていた（表 5）

**何が緑だったか**: 宣言の `src` / `test` を `null` にすると走査は 0 件になるが、**宣言の行数は
10 のまま**なので `SCANNED_PACKAGES.length` を見るガードは素通しした。さらに `""` にすると、
数える側（`!== null`）と走査する側（真偽値）で意味が割れ、**「166 件走査した」と出力しながら
実走査は 0 件・SC032 は 0/0 で PASS** という、より悪い状態になった。

**なぜ緑だったか**: **走査量を数える経路と実際に走査する経路が別々に導出されていた**ため。
`missingTargets`（null は `continue`）・エントリの実在確認（`d.src !== null` が条件）・
`METRIC_FILE_PINS`（走査集合への所属を見ない）・全単射照合（`pkg` 名だけを見る）の
どれも、この状態を検出できない。

**塞ぎ方**: ガードが見るものを、**実際に出力する走査量そのもの**へ差し替えた（ADR-0014 決定 8）。
述語を `hasScanTarget` 1 本に統一し、読み込みを `loadScanTargets` の 1 回へ寄せた（決定 9）。
宣言の値として正当なのは `null` か非空文字列だけであることも別に検査する
（**件数のガードは「1 件だけ対象を失った」状態を検知できない**ため）。

### 規範で塞いだ経路を、ガイドが手順として教えていた（表 7）

**何が緑だったか**: 検査そのものは正しく直っていたが、[`docs/guides/development.md`](../guides/development.md)
の手元実行の例が旧いままだったので、**人が手で経路④・⑬を再生産する**状態が残っていた。

**なぜ緑だったか**: ガイドの文面を検査する仕組みが無い。リンク検査はコードパスの実在を見るが、
「その手順が現行の規範と合っているか」は見ない。

## 成果

- **7 経路（①②③④⑧⑪⑬）に手を入れ、5 経路を完全に塞いだ。①と⑪には残余がある**（後述
  「塞げなかったこと」）。うち **⑬は本作業中に発見**した
  （`node --test` の対象列挙がハードコードで、新しいテストが黙って走らない）
- **構造監査の走査が 3 → 10 パッケージへ。** **SC031 が「0＝PASS」から 3 件の未達へ変わり、
  走査外に隠れていた違反が表に出た。** この値は #103 が実装前に別の方法（本物の `readFilesRecursive` と `splitIntoTestBodies` を
  import して走査外を測る）で予測した値と一致した
  （SC029 7→15・SC032 96.9%→84.2%・SC036 1466→1788 も動いた。数値の正本は
  [設計正本](../superpowers/specs/2026-08-16-scan-target-integrity-design.md) §3.9）
- **ログ衛生の走査が 52 → 120 ファイルへ**（違反は 0 件のまま。移行費用ゼロ）
- CI の自己テストが **4 本の直書き → 7 本の導出**へ。テスト件数は 178 件
- **CI で実証した。** `quality` ジョブの step 8〜11 が緑・step 12（shellcheck）だけ赤という
  状態を 1 回の run で作り、**「新しい配線が動く」と「新しい検出が効く」を同時に示した**
  （[run 31924201587](https://github.com/tomohiroJin/tasuki-tools/actions/runs/31924201587)）。
  同じファイルを旧グロブに掛けると `exit=0` で見逃すことも実測した
- **経路①は塞ぎきれない**（対応表の項目と patch を対で消せば全単射のまま通る）ことを、
  限界として [ADR-0014](../adr/0014-scan-target-integrity.md) に明記した

## 塞げなかったこと

| 項目 | 内容 |
|---|---|
| 経路①の残余 | 変異の対応表の項目と `scripts/mutations/*.patch` を**両方**消せば全単射は保たれ、検査は緑のまま通る。`MUTATIONS = []`（全消し）は 0 件ガードで落ちるので、残るのは「対で消す」経路だけ。patch の削除が diff に現れることをレビューの拠り所とする限界を ADR-0014 に書いた |
| 経路⑪の残余（ログ衛生） | `audit-log-hygiene.mjs` の走査先は宣言から `${pkg}/src` として導出するが、この派生ディレクトリの実在は検査していない。宣言したパッケージの `src/` が改名・消失しても全単射照合はパッケージ名しか見ないため素通りし、走査は静かに空になる（設計正本 §6.1 の E1 未達）。構造監査には同じ穴を塞ぐ実在確認があるが、ログ衛生には無い。**Issue #158**（#72 より前）。限界を ADR-0014 に書いた |
| `scripts/` を変異検査で守れない | `mutation-check` の `detectRunner` が対象パッケージの `package.json` から走者を決める。`scripts/` は `package.json` を持たないため、**共有モジュール自身を変異検査で守れない**。手動の破壊検証で代替した |
| 露出した未達の是正 | 走査拡大で表に出た SC029 15 件・SC031 3 件・SC032 84.2% の是正は範囲外（設計正本 D8）。構造監査の測定値は合否を持たないので CI は緑のまま |
