## 踏んだ罠

### 1. 自前の敵対的レビューを通した後でも、`/code-review` が実在の指摘を出し続けた

- **事実**: 第一陣（PR #605〜#611）の 7 本すべてと、第三陣（PR #623〜#628）の 6 本すべてで、自前の敵対的レビュー（Opus・別の作業ツリー）が「直す 0 件」で通した後の `/code-review` が、実在の指摘を出した。
  第三陣の例は次のとおり
  - PR #624: 純粋関数へ出したときに、エラーコード・接続状態・保存した名乗りの型が `string` や省略可能に広がり、境界の型の検査が効かなくなっていた
  - PR #627: かな漢字変換の確定の Enter で送信する、main からあったバグ
  - PR #626: packages/ui と landing に写しが残っていた
  - PR #628: マージ済みの PR だけのとき、フックが何も出さずに通っていた
- **原因**: 自前のレビューは「振る舞いを変えない」を主に、main と DOM・出来事の列を比べて確かめた。比べる軸に乗らない型の広がり・写しの取り残し・知らせの消失は、比べても差 0 件になる。`/code-review` は差分を読む側から当たるので、別の穴を拾う
- **再発条件**: 自前のレビューの「直す 0 件」を締めの合図にして、`/code-review` を後回しにするか省くとき

### 2. E2E の長い test を割るとき、準備を縮めて「その局面でしか拾えない主張」が消えた

- **事実**: PR #625 で、まとめの画面を見る test の準備を「要るものだけ」に縮めた（ゲスト 1 人・代理なし）。
  割る前は、まとめのドライバー別に区切りの無い 30 字の名前が並び、名前の切り詰め（`.summary-driver-name` の `overflow: hidden`）が外れると 320px で横に溢れる局面で測っていた。縮めた後は名前が短く、切り詰めが外れても緑になった
- **原因**: 主張（`expect`）の数は割る前と同じに保ったが、主張が測る局面は準備が作る。準備を縮めると、主張を残したまま局面が消える
- **再発条件**: テストを割る・準備を共通の補助に出すときに、`expect` の数だけを前後で突き合わせるとき
- **対処**: 差分のレビューが拾った。30 字の名前を戻し、切り詰めの CSS をわざと外して 2 本が「横に溢れる」で赤になることを確かめてから戻した

### 3. 変異の宣言の表を触る枝では、`check:fast` が毎回全件に倒れた

- **事実**: 第三陣の 6 本はすべて変異の宣言を足した。どの枝でも `check:fast` の変異の段が全件（1,155〜1,160 件・約 53 分）に倒れ、実装役は止めて `--id` に代えた。
  止めた後に `scripts/.wiring-*.mjs`（自己テストの一時ファイル。追跡外）が作業ツリーに残る枝があり、push の前に消した
- **原因**: 宣言の表は `--changed` の「変異検査の機構」に数える（`scripts/lib/mutation-declarations.mjs` の冒頭）。止め方によっては、自己テストの一時ファイルの後始末が走らない
- **再発条件**: 変異を足す枝で `check:fast` を最後まで流そうとするとき。並列の陣ではすべての枝がこれに当たる

### 4. マージのたびに、残る枝で宣言の表の末尾がぶつかった

- **事実**: 第三陣では 1 本マージするごとに、残る枝すべてで `mutation-declarations.mjs` の末尾（宣言の配列と `RESERVED_*` の定数）がぶつかり、延べ 8 回解いた
- **原因**: どの作業も表の末尾へ足す（`docs/guides/procedures/orchestration.md`「分ける前に」に書いてある既知の形）
- **再発条件**: 変異を足す PR を並列に 2 本以上開くとき
- **対処**: 両側が足しただけの衝突は、両側を残して並べる小さなスクリプトで毎回解けた。解いた後は、id の重複が 0 件・各帯の件数・全パッチの `git apply --check`・`mutation-check.test.mjs`・両側の帯の変異の `--id` を確かめた

## 検査の穴

### 1. 拡張の試算が、直したことを数えない

- **緑のまま壊れていたもの**: 「足すのが速くなったか」の判定。直した後の試算は増えた（上の表）
- **なぜ緑だったか**: 試算は「語を含むファイルの数」で、手で直す場所の数ではない。表を正本に寄せると表のファイルが、足し忘れを止める網羅のテスト・監査・変異を足すとそれらのファイルが、新しく数えに入る。調査の節 10 は「上限であり必ず触る場所ではない」と書いていたが、#482 の完了条件は直す前と後の比較を求めていた
- **対処**: 数を減らす直しはしていない。直したことの効き目は、PR ごとに「足し忘れがコンパイル・テスト・監査で落ちる」ことを壊して確かめた記録が持つ（PR #602・#610・#621）

### 2. 監査の許可リストの足し忘れが通る（A13）

- **緑のまま壊れていたもの**: 新しい道具を足したときの監査の対象。#482 の中では道具を足していないので、実害は出ていない
- **なぜ緑だったか**: 監査 7 本と `layer-direction.mjs` が道具のパッケージ名を手で並べていて、足し忘れたパッケージは「見ない」側に倒れるものがある
- **対処**: 直していない（上の「残したもの」）
