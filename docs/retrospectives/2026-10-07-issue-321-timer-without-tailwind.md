## 踏んだ罠（事実と再発条件）

### 1. 物差しを直すたびに全件の比較をやり直し、PR 2 に約 29 時間かかった

比較 1 本は約 27 分で、ポートが固定なので順にしか流せない。PR 2 では、網羅の確認（E8・規則の使用状況）が「当たらない規則」を出すたびに状態を足し、期待値を作り直し、全件を流し直した。見た目の移植よりも物差しの直しに時間を使った。

- **再発条件**: 網羅系の検査を最初から合否にする。全件の比較を「タスクの終わりの確認」に使う
- **扱い**: PR 3・4 は利用者の判断で検証を軽くした（設計正本 §7.1）。比較はタスクごとに対象の状態だけ、全件は PR の最後に 1 本。E8 は状態を足さず記録で受け入れた（§7.2）。PR 3 は機械の待ち約 2.4 時間、PR 4 は約 1 時間に収まった。**計画に検証の時間の見積もりを書く**ことを規範にした

### 2. 囲いを外すと、比較に描かれない要素で勝ち負けが逆転する

移行中は画面の CSS を `@layer timer` に入れ、レイヤーの外の規則（`base.css` の `:focus-visible` など）に必ず負けるように置いた。PR 4 で囲いを外すと、同じ詳細度なら後に読む画面の CSS が勝つ。改名欄の `outline-style: none` がこれで勝ち、キーボードで入ったときのフォーカスの輪郭が消えるところだった。改名中は比較の目録に無い状態で、比較は拾わない。

- **再発条件**: 「比較が最後の防壁」と書いた計画で、比較に描かれない要素がある。E8 を記録で受け入れた代償がここに出た
- **扱い**: PR 4 の計画を文脈を共有しない 3 人で検証し、2 人が別々にこれを見つけた（1 人は実際にビルドして確かめた）。宣言を消し、比較に描かれない要素の CSS をレイヤーの外の規則と目で突き合わせる手順を計画に足した

### 3. Tailwind が同名で生成していた規則が、外すと消える

`base.css` の `.sr-only` は `clip` だけを持ち、`clip-path: inset(50%)` は Tailwind が utilities 層に生成した同名の `.sr-only` が足していた。設計正本 D2 は「両版で勝っている宣言の和を残す」と決めていたが、検査の例外表（`KNOWN_COLLISIONS`）の理由文に約束として書かれたまま、実施されていなかった。

- **再発条件**: 決定を「例外の理由」にだけ書き、実施するタスクを持たせない。例外を消すと約束ごと消える
- **扱い**: PR 4 の計画の検証が見つけ、Tailwind を外すコミットで足した。比較の 1 回目が緑だったのはこれを先に直したから

### 4. 現況の記述の検索が、別の言い方で書かれた片側を拾わなかった

設計正本 D8 の検索は `tailwind|postcss|…` の語で引く。`packages/ui/src/index.css` と `components/index.css` の「timer は `main.tsx` から読む（#297 と同じ理由）」は Tailwind という語を含まず、README だけ直して注釈が古いまま残った。`/code-review` が拾った。

- **再発条件**: 仕組みを消したとき、その仕組みの名前（Tailwind）でだけ引き、仕組みが強いていた**回避策の名前**（`main.tsx` から JS で読む）で引かない
- **扱い**: 同じ PR で直した。移設や撤去では、消した仕組みの名前と、それが強いていた回避策の名前の両方で grep する

### 5. squash マージで、比較の仕組みを再現する SHA が main から消える

台帳は「`git checkout <SHA> -- e2e/parity` で再現できる」と書いていたが、PR 1〜3 の SHA はどれも枝のコミットで、main から辿れなかった。

- **再発条件**: squash マージのリポジトリで、枝の SHA を再現の手段として記録する
- **扱い**: `git fetch origin pull/<番号>/head` で取ってから `git restore --worktree` で戻す手順にした（`git checkout <SHA> -- path` は index も書き換え、次のコミットに撤去したものが戻る）。PR 1〜3 の行にも遡って注記した

### 6. 何も動かない空白

PR 3 で計約 20 時間、PR 4 でも比較の仕組みを撤去する実装役が、作業は数分なのに約 5.8 時間戻らなかった。原因は分かっていない。

- **扱い**: 止まる条件の実時間から除いた（利用者の判断）。各タスクの終わりに経過時間を見ると早く気づける

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 1. 比較に描かれない要素は、比較が緑でも守られていない

目録の状態に描かれない要素（改名中の入力欄・編集中の共有メモ・「ルーム」タブの中身など）は、比較が何を写し違えても緑になる。PR 3 ではレビューが元のクラスと 1 つずつ突き合わせ、PR 4 では勝ち負けの点検で目を通した。表は台帳の「E8 で当たらなかった規則」と「PR 3 で比較に掛からない要素」。**受容**（利用者の判断・設計正本 §7.2）。見直すきっかけは、これらの要素の見た目が崩れたという報告

### 2. Chromium の物差しに映らない差

前置詞と、古い Safari 向けの逃げ道（`color-mix()` の `@supports`・メディアクエリの範囲構文）の差は、Chromium で測る比較には出ない。PR 4 ではビルド出力の字面を直前の dist と比べて仕分け、Safari 16.4 未満だけに効く差を利用者が承認した
