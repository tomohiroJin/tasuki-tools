### 2. `pnpm update -r <pkg>@<version>` は直接依存まで巻き込む

**事実**: PR-2で`nanoid`の脆弱性（`postcss`経由の推移依存）を解消しようとした際、
`pnpm update -r nanoid@3.3.17`および`pnpm update -r nanoid --latest`を実行すると、
ワークスペース内の同名パッケージすべてが対象になり、`apps/timer-sync`が持つ
直接依存`nanoid`（宣言`^5.0.9`、実解決`5.1.16`）まで書き換えられた
（1回目は`^3.3.17`へダウングレード、2回目は`^6.0.1`へメジャーアップ）。
どちらもPR-2のスコープ外（メジャー更新は別Issue #113）で、2度とも
`git checkout`で復元した。

**原因**: pnpmの`update`コマンドは、パッケージ名が一致すればワークスペース内の
直接依存・推移依存を区別せず一括で対象にする。転移依存だけを狙い撃ちする
専用オプションは無い。

**再発条件**: 同名パッケージが「直接依存として宣言されたバージョン系列」と
「別パッケージ経由の推移依存としてのバージョン系列」の両方でワークスペースに
存在するとき（今回は`nanoid`の3.x系と5.x系）、明示バージョン指定つきの
`pnpm update -r <pkg>@<version>`または`--latest`は両系列を区別せず上書きする。

**対処**: `--latest`実行直後に対象パッケージの直接依存宣言（`package.json`）を
必ず確認し、意図しない書き換えがあれば個別に`git checkout`してから
`pnpm install --no-frozen-lockfile`で再解決する運用に切り替えた。
`docs/guides/development.md`への追記は行っていない（申し送りへ記載）。

### 3. `git checkout <file>` は未コミットの変更をまとめて消す

**事実**: PR-1の破壊検証（待機期間を一時的に無効化する演習）で
`git checkout pnpm-workspace.yaml package.json pnpm-lock.yaml`を実行したところ、
演習用の一時変更だけでなく、**その回のセッションでまだコミットしていなかった
`minimumReleaseAge`の本設定そのものも消えた**。演習の直前に本設定をコミットして
いなかったため、直近のコミット（本設定を含まない状態）まで巻き戻った。

**原因**: `git checkout <path>`はHEADコミット時点の内容へ戻す操作であり、
「今しがた加えた一時的な変更だけを戻す」動作ではない。実装計画の該当ステップ
（Task 1 Step 9）は「設定を戻し、作業ツリーを完全に元へ戻す」とだけ書いており、
本設定を先にコミットしておく前提が明示されていなかった。

**再発条件**: 「設定を入れる→演習で一時的に変える→`git checkout`で戻す」という
手順で、設定を入れた直後にコミットを挟まないと、演習のたびに本設定ごと消える。

**対処**: 即座に設定を書き直して復元し、以後は「本設定を入れたら演習の前に
必ずコミットする」運用に切り替えた（PR-1・PR-3のいずれもこの順序で実施し、
以後は再発しなかった）。

### 4. 構造監査の比較作業で `git checkout main -- .` によりコミット済み変更が一時的に消えた

**事実**: PR-4で構造監査の指標（SC029等）が退行かどうかを`main`と比較しようとして
`git checkout main -- .`を実行したところ、作業ブランチのコミット済み変更が
作業ツリー・インデックス上で一時的にmain相当へ巻き戻った（コミット履歴自体は
無傷）。`git reset --hard HEAD`で即座に復元した。

**原因**: 比較したいだけなら`git worktree add`で別ディレクトリにmainを展開すべき
ところ、同一ワークツリー内でファイルだけ差し替える操作を選んだ。

**再発条件**: 「他ブランチと比較したい」ときに`git checkout <ref> -- .`を
安易に使うと、作業ブランチの変更がステージされたまま置き換わる。

**対処**: 即座に`git reset --hard HEAD`で復元し、以後は`git worktree add`で
比較用ディレクトリを分離する方式に切り替えた（実際に効果を確認し、以後
発生しなかった）。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 1. `dompurify` は未使用の依存だったが、依存の更新プロセスはそれを検出しない

**何が壊れていたのに緑だったか**: PR-2で`dompurify`の脆弱性を解消する際、
`apps/timer-web/src`のどこからも`dompurify`がimportされていないことが判明した
（`grep -rn "dompurify\|DOMPurify"`で本文一致0件）。スペックは「apps/timer-web の
実行時依存」としていたが実態と食い違っていた。`pnpm audit`・`pnpm test`・
`pnpm build`のいずれも緑のまま、この未使用状態を検出しなかった。

**なぜ検出できなかったか**: `pnpm audit`は`package.json`の宣言を見るだけで
実際のimportの有無を見ない。ビルド（Vite/Rollup）はimportが無ければ単に
バンドルしないだけで、警告もエラーも出さない。「宣言されているが使われていない
依存」を検出する仕組みがリポジトリに存在しない。

**対処**: ビルド成果物（`dist/`）に`dompurify`のコードが含まれていないことを
`grep`で確認し、PR本文に記録した。未使用依存の削除自体は#69のスコープ外
（版の更新のみ）のため、#71（不要なディレクトリ・ファイルの整理）へ申し送った。
