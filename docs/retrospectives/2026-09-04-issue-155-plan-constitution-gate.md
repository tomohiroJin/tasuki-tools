# 振り返り: Constitution Check ゲートの空文化を検出する（#155）

- **Issue**: [#155](https://github.com/tomohiroJin/tasuki-tools/issues/155)
- **設計正本**: [`docs/superpowers/specs/2026-09-04-plan-constitution-gate-design.md`](../superpowers/specs/2026-09-04-plan-constitution-gate-design.md)
- **日付**: 2026-09-04

## この Issue が扱ったもの

憲法 Governance の MUST「すべての plan は Constitution Check ゲートを通過しなければ
ならない」に機械検査が無く、ゲートを持たない実装計画が増えても CI が緑のままだった
（#135 経路⑨）。#154 と違い、**先に規範の判断（どの集合に課すか）が要る**種類の作業だった。

## 踏んだ罠（事実と再発条件）

### 1. 走査の仕方で件数が 6 にも 3 にもなった

**事実**: 着手直後、「本文に `Constitution Check` を含むか」で数えて **6 件**という値を
得て、それを利用者へ報告しかけた。見出しで数え直すと **3 件**だった。

**原因**: 差の 3 件はいずれも**ゲートではなく言及**だった。

| ファイル | 出現箇所 |
|---|---|
| `2026-08-09-governance-and-docs.md`（#68） | Task 内の bash コメント 1 行 |
| `2026-08-16-repo-cleanup.md`（#71） | 憲法の変更内容を引用する散文 |
| `2026-08-16-scan-target-integrity.md`（#135） | 申し送り表の行「D-1 ゲートの空文化」 |

**皮肉なことに、この 3 件はいずれも「ゲートの空文化」を話題にした文書である。**
問題を語っている文書が、その語りによって「問題を解決している」側へ数えられていた。

**再発条件**: 文書の**構造**（節・見出し）で決まる性質を、**本文の字面**で数えたとき。
`grep -l` は「言及」と「実体」を区別しない。

**対処**: 検査は見出し（`^#{1,6}\s.*Constitution Check`）で判定する。設計正本 §3.1 に
6 件と 3 件の内訳を残した。

### 2. Issue 本文の「ゲートを持つ 4 件」が誤りで、同じ誤りが憲法にも入っていた

**事実**: Issue 本文が挙げる 4 件のうち `2026-08-09-governance-and-docs.md`（#68）に
ゲートは無い。さらに `docs/constitution.md` の 2.1.4 の Sync Impact Report が

> docs/superpowers/plans/ の 4 本が ## Constitution Check 節として体現しているため。

と書いており、**#155 の起票時の数え違いが、確かめられないまま憲法へ写っていた**。

**原因**: #71 の作業者が、#155 の本文を根拠に憲法の文言を決めた。上流（Issue）の誤りを
下流（規範文書）が承認した形である。これは #154 でも別の形で起きている
（既存の規範から類推して、確かめずに書いた記述が 2 件）。

**再発条件**: 他の文書が出した数値を、自分で数え直さずに規範文書へ書くとき。

**対処**: 憲法の記述は**残したまま**、日付つきの訂正注記を添えた（記録を消さずに、
誤りだったことを記録する）。原則にも決定にも影響しないため版は上げていない。

### 3. 検査を quality ジョブへ置きかけた —— それでは捕まえたい PR がちょうど外れる

**事実**: CI へ結線するとき、他の `audit-*` と並べて `quality` ジョブへ足した。
コミット前に気づいて `docs` ジョブへ移した。

**原因**: `quality` のステップは `steps.scope.outputs.code == 'true'` で絞り込まれ、
`ci-scope.mjs` の `code` は「`*.md` 以外の変更があるか」で決まる。
**実装計画は `*.md` である。** つまり「ゲートを持たない plan を足すだけの PR」は
`code=false` になり、**この検査がちょうどその PR で走らない**。

**これは対策が自分の塞ぐ欠陥を持つ型そのもの**（`docs/adr/0014` が #135 で 7 回踏んだ形）。
「検査を足した」という事実だけが残り、捕まえるはずのものを 1 件も捕まえない。

**再発条件**: 検査の対象が `*.md` で、置き場を「他の検査と同じところ」で決めたとき。
CI の絞り込みは**対象の種類ごとに違う**ので、並びの見た目で決めてはいけない。

**対処**: `docs` ジョブ（絞り込まない・`pnpm install` も要らない）へ置いた。
ci.yml のコメントと設計正本 §5.2 に「quality へ置いてはならない」理由を残した。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

**憲法の MUST そのものが、批准から 50 日間、機械検査を持たないまま空文化していた。**
批准（2026-07-16）以降の実装計画 28 件のうちゲートを持つのは 3 件で、CI は一度も
赤くなっていない。**#119 は自分の plan のゲートの中でこの空文化を指摘していた**が、
気づきを機械化する手段が無いまま 2 件増えた（#119 時点の 4 件 → 実測 3 件は §2 の誤り分）。

もう 1 つ、**この検査自身が空振りしうる経路**を実装中に見つけた。原則の一覧を憲法から
導出しているため、憲法の見出し形式が変われば導出は 0 件になる。そのとき
「原則 0 本を全部満たした」として**空のゲートが通る**。`docs/adr/0014` 決定 8 の
0 件ガードを原則の本数にも掛けて塞いだ（破壊検証 5 で確認）。

## レビューの指摘（`/code-review high`・7 件）

**7 件すべてが本物だった（5 連続）。** 中でも 2 件は、この検査が塞ごうとしている性質を
検査自身が持っていた形である。

### 1. ガイドに書いた様式サンプルが、そのまま抜け道だった

`docs/guides/plan-writing.md` は ```` ```markdown ```` で囲んだ見本を持つ。**その見本を
引用しただけの plan が、初版では問題 0 件で通った**（実測）。見出しも全原則の表も
逸脱の結論もそろっているように見えるが、その plan 自身は何も判定していない。

**様式の正本を作ったこと自体が、抜け道の供給元になっていた。** コードフェンスの中身を
読み飛ばすようにした。

### 2. 最初に一致した見出しをゲートとみなし、正しい plan を落としていた

`### Task 1: Constitution Check の節を足す` のような見出しがゲートより前にあると、
そのタスク節をゲートとみなす。実測では、正しい 11 原則の表と結論を持つ plan が
**「原則 I〜XI すべて欠落 ＋ 結論が無い」の 2 件で赤**になった。
**このゲートを扱う plan がいちばん踏みやすい形**である。

候補を全部見て、1 つでも満たせば通すようにした。落とすときは最も問題の少ない候補を報告する。

### 3〜7

- **逸脱の結論が判定表のセルで満たせた**（`| I. … | 通過 | 逸脱なし |` の 1 行で通る）。
  表の外の行で見るようにした
- **レベル 1 の見出しを拾えなかった**（設計正本 D3 が「レベルは問わない」と書いていたのに、
  実装は `#{2,6}` だった）
- **ADR 0003 とガイドが CI ジョブを `quality` と誤記していた。** `docs` へ移した後に
  ci.yml・設計正本・振り返りだけを直し、**規範側の 2 文書が取り残されていた**
  （「直したつもりが片側だけ」。しかも取り残されたのは、将来の作業者が最初に読む側）
- `docs/guides/development.md` の検査一覧に新しい検査を足し忘れていた
- 配線テストの正規表現 `/走査対象が 0 件です.*憲法の原則|憲法の原則/` が、選択の
  優先順位で実質 `/憲法の原則/` になっていた

**教訓**: 1 と 2 は「**検査が塞ごうとしている性質を、検査自身が持つ**」型で、
`docs/adr/0014` が #135 で 7 回踏んだのと同じ。5 は「置き場を変えた後、片側だけ直した」型。

## 敵対的レビューの指摘（2 巡目・4 件）

**1 巡目の 7 件を直した後、さらに 4 件出た。すべて本物で、うち 1 件は空のゲートが通る穴だった。**
**「直した」と言った後の状態を、もう一度敵対的に検証する意味がここにある。**

### 1. 文書の題（H1）に `Constitution Check` が入ると、文書全体が 1 つの節になる

節は「同位以上の見出しまで」で切るので、**H1 の下には H1 が無く、文書全体が節になる**。
候補のどれか 1 つが満たせば通す仕様（1 巡目の修正）と組み合わさると、
**本物の `## Constitution Check` が空でも、別の節に引用した判定表と本文中の「逸脱なし」を
拾って通った**（実測。problems 0 件）。

**この機能を扱う実装計画がまさにそう名乗る**（「Constitution Check ゲート検査の実装計画」）。
他の候補を丸ごと含む節は候補にしないようにした。

### 2. コードフェンスの長さを見ていなかった

`^\s*(```|~~~)` の**先頭 3 文字だけ**でトグルしていたため、CommonMark の
「開始フェンス以上の長さでしか閉じない」規則を満たしていなかった。
````` ````markdown ````` の内側の ```` ``` ```` を閉じと誤認し、**以降の本文が素通り**した。

**ガイドの様式サンプルは ```` ```markdown ```` の中にあるので、それを引用するには
4 バックティックを使うのが自然**である。1 巡目で塞いだはずの経路が、
**塞ぎ方の粗さのせいでそのまま開いていた**（実装計画 3 本が現に 4 バックティックを使っている）。

### 3・4. 表の行の定義が 2 箇所で食い違っていた

原則の突き合わせだけが行頭の空白を許さず（`^\|`）、すぐ下の結論判定は許していた（`^\s*\|`）。
字下げした判定表（GFM では 3 スペースまで表として描画される）が「全原則欠落」で偽陽性になり、
**GitHub 上では表に見えているのに CI だけが赤くなる**形だった。
ローマ数字の直後に空白を要求していた点も、ガイドの文言（「ローマ数字で始まる行」）より
厳しかったので緩めた。

**教訓**: 1 と 2 はどちらも**1 巡目の修正が作った/残した穴**である。
「指摘を直した」状態は、直す前と同じだけ敵対的に検証する必要がある。

### 破壊検証の fixture が、壊したい条件を作れていなかった

指摘 1 の破壊検証で、引用する判定表に `## Constitution Check` の見出しごと含めてしまい、
**その引用自体が完全なゲートになって緑になった**。「壊したのに緑」ではなく
「壊せていなかった」である。見出しを外した表だけを別の節へ置き直して赤を確認した。
**壊す前に「壊せたこと自体」を数える段が要る**（今回はゲート見出しの数を数えて気づいた）。

### パッチ生成で自分自身の差分を混入させた

変異 m22 のパッチを `git diff > scripts/mutations/m22-….patch` で作り直したところ、
**シェルがリダイレクト先を先に空にするため、`git diff` が「そのパッチファイルが消えた」
差分まで出力に含めた**。結果、`git apply` が「パッチファイル自身へのパッチ」として失敗した。
一時ファイル経由で作り直した。**追跡下のファイルへ `git diff` を直接リダイレクトしない。**
