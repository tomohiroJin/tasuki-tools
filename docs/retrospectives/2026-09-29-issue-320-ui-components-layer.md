## この Issue が扱ったもの

利用者は #319（プルダウンの白い一瞬の直しを 2 画面に写した）を見て、「共通する部品を画面ごとに作ってしまう。デザインシステムとして思わしくない」と言った。
`@tasuki/ui` に**部品層**（`.ui-` で始まるクラスだけを定義する層）を足し、画面ごとの写しを部品へ置き換えた。共有は既定、強制はしない（外すなら `ui-exempt:` を書く）。
部品ごとに見た目の変わる画面が違うので、5 本の PR に分けた（設計正本 §7）。

| 1（#322） | ADR 0022・部品層の骨組み・入力欄の系（`.ui-input` / `.ui-select`）・検査 `scripts/audit-ui-components.mjs` |
| 2（#323） | 接続の告知の帯（`.ui-banner`）と一言（`.ui-note`） |
| 3（#324） | パネルの面（`.ui-panel`）と、見出し・戻る導線（`.ui-page-header`） |
| 4（#327） | 招待リンクの表示（`.ui-invite`）・象牙の札（`.ui-sheet`）・Markdown の見た目（`.ui-md-*`） |
| 5（本ブランチ） | 画面の CSS の生の色を全部トークンへ仕分け、検査を画面の CSS へ広げた・ADR 0022 の実施状況・この振り返り |

## 踏んだ罠（事実と再発条件）

### 1. 部品へ移すたびに、別のファイルの注釈が古くなった

**事実**: PR 3 と PR 4 の最終レビュー（文脈を共有しないレビュー役）の Important は、どちらも**注釈**だった。
PR 3 は、地が `.ui-panel` へ移ったのに、poker の注釈 3 箇所が「`.topic` の地」を理由に挙げていた（`apps/poker-web/src/index.css`・`CurrentTopic.tsx`）。
PR 4 は、Markdown のリンクを札の色を継ぐ形（`color: inherit`）にしたのに、札の部品と poker の注釈が「札が無いとリンクが約 1.03:1」を札が要る理由に挙げていた。
いまの理由はコード・引用の枠（`--coal-soft`）で、リンクではない。

**原因**: 値を移した先の規則と注釈は直したが、**その値を理由として語る注釈が別のファイルにあった**。grep で探したのは消したクラス名で、理由の文は探していなかった。

**再発条件**: 規則を部品へ移すとき、移した値（地・色）を「なぜ」として書いた注釈が、移した規則とは別のファイルにあるとき。

**対処**: 両方とも最終レビューの修正で直した。PR 4 以降の計画に「消したクラスの名前を探す」課題（Task 5）を置いたが、理由の文までは拾えない。
移設の PR では、**値の持ち主の名前（`.topic`・`--coal` など）でも grep する**。

### 2. 計画の逐語コードが、設計正本の決定を落とした

**事実**: PR 1 の計画の検査のコードには、設計正本 D10 の 1 の「入れ子の `&` を解いてから判定する」が無かった（タスクのレビューで発覚）。
PR 4 の計画の `Markdown.tsx` の置き換えは、JSX として不正な位置に注釈を置いていた（実装の段で JS の注釈に直した）。
PR 5 の計画は、既存の自己テストが詰め物に `color: red` を使っていることと、トークン層のガードテストが `@supports` を落とすことを見込んでいなかった。

**原因**: 計画の逐語コードを、現物に当てて動かさずに書いた。

**再発条件**: 計画に逐語のコードを書き、そのコードを実装の前に一度も実行しないとき。

**対処**: 各 PR で、計画と違う形にしたところを実装の記録に残し、PR 本文に書いた。レビュー役には、逐語コードと一緒に設計正本の該当の D 番号を渡す。

### 3. PR 1〜3 は、部品をテストより先にコミットしていた

**事実**: PR 3 の `/code-review` が、部品の CSS のコミットが E2E のコミットより先にあることを、憲法 原則 I（テスト駆動開発）の違反として挙げた（確度の採点が PR へコメントする基準に届かず、PR には残っていない）。
PR 1〜3 は、部品を先に置いて「死んだ部品」の検査が赤になることを RED とみなしていた。その赤は部品の見た目を何も確かめていない。

**再発条件**: 部品を足して画面へ当てる PR で、画面の赤（E2E）より先に部品を書くとき。

**対処**: PR 4 と PR 5 は、E2E（と自己テスト）を先に書き、main のまま赤を見てから部品を書いた。PR 4 の `/code-review` はこの観点で 0 件だった。

### 4. main の CI が、1 つの PR をまたいで赤のままだった

**事実**: PR 2（#323）のマージの後、main の CI が `@tasuki/markdown` の速度テスト（10 万字の解析を 1 秒以内）で赤になった。
手元では同じテストが約 70ms で、CI は手元より 10 倍以上遅かった。PR 3 の CI で気づき、#325 で上限と長さを直した。
**最初に出した直し方（上限を 5 秒に広げる）は、実測していない推測（「O(N²) なら数十秒」）に立っていた。** 直す前に測ると、
O(N²) に戻す変異（m106）は 10 万字で約 6 秒で、5 秒では変異を取り逃がすところだった。長さを 20 万字にして両側に余裕を取った。

**再発条件**: 絶対時間の上限を持つテストを、CI の揺れに合わせて広げるとき。**線形の実装と変異の両方を測らずに**上限を決めるとき。

**対処**: #325 の PR 本文と、テストの注釈（`packages/markdown/tests/performance.test.ts`）に、両側の実測と余裕を書いた。
あわせて、`pnpm audit` の赤（`fast-uri`）も別の PR（#326）で直した。どちらも「ここでの問題はここで直す」の方針に従い、Issue は立てなかった。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 1. `<div>` の帯は、表示しても文字の走査に入っていなかった

PR 2 の前、poker とお題ツールの接続の帯は `<div>` だった。E2E の文字の走査（`e2e/support/a11y.ts` の `scanContrast`）は
`button, a, h1〜h3, label, p, span` だけを見るので、**帯を表示させても字は測られなかった**。そもそも帯を表示させるシナリオも無かった。
PR 2 で帯を `<p>` にし、`routeWebSocket` で帯を表示させて測った。main の poker の帯は、下を象牙の札が通ると字がほぼ読めなかった（撮影で確認）。

### 2. 「未投票」の字は AA を割っていたが、どのシナリオも未投票を出していなかった

poker の結果の「未投票」の印は象牙の α 0.4 で、票の行の上で 2.98:1 だった（PR 5 の E2E の実測）。
既存の E2E は 1 人のルームで投票し自動で公開するので、**未投票の人が居る結果の画面を一度も走査していなかった**。
PR 5 の生の色の仕分けで値を読んで見つけ、2 人のルームで 1 人だけ投票して公開するシナリオを足した。
最初に書いたシナリオは AA の判定だけで、**印を測ったことを固定していなかった**（印が `<div>` に変わると緑のまま測られなくなる。
穴 1 と同じ型を、この PR の最終レビューに指摘された）。印の色の組を測ったことも固定した。

### 3. 置き換える前から緑になる判定

PR 3 のパネルの面と PR 4 の札・Markdown は、写しと部品が同じ値を持っていたので、**E2E の判定は置き換える前の main でも緑だった**。
守っているのは「部品を当て忘れる」後退で、赤は破壊検証（部品のクラスを外す・部品の値を変える）でしか見えない。
各 PR の本文に破壊検証の結果を残した。部品の値を変える破壊は、各テストの最初のパネルで止まるので、2 枚目以降の写しの残りは grep で見た。

### 4. 文字の走査は h4〜h6・li・blockquote・code を見ない

PR 4 の `/code-review` が挙げた（確度の採点が PR へコメントする基準に届かず、PR には残っていない）。札の上の Markdown の見出し・リスト・引用・コードの字は `scanContrast` を通らない。
いまは札の字の色（`--coal`）を継いでいて、同じ組を段落とリンクで測っているので実害は無い。**Markdown の要素に色を直書きすると、その字は測られない**。

## 本番へ出すときの注意（この epic の分）

見た目が変わる画面は、各 PR の本文の「見た目の変化」にある（どれも利用者が撮影か Chrome で確認して受け入れた）。
配ると、timer の通知音と話者のプルダウンの字が 16px になって欄が高くなる・玄関のエラーが淡くなる・poker の帯が不透明になる・poker の招待リンクと
戻る導線の字が大きくなる・poker の未投票の字がはっきりする、などが一度に出る。配布は利用者の承認を得て行う。
