# 振り返り: IP 単位のレート制限を入れる（#103）

**対象**: Issue #103（IP 単位のレート制限）
**ブランチ**: `docs/103-ip-rate-limit-design`（`main` への統合はまだ）
**期間**: 2026-08-14〜2026-08-15・merge-base `e01f5b1` から 72 コミット
（このコミットを含む。最終レビュー是正・文書と規範の最終修正を含む）

## 踏んだ罠（事実と再発条件）

### 1. 設計正本の断定が実測で 4 回反証された

**事実**: 「1・2 を訂正して書いた文章が 3 を生み、3 を訂正した文章に 4 つ目（controller の
計測誤り由来）が入っていた」という経緯があった。最終レビューで見つかった主な反証:

- 「全走査は最悪でも `refillFullMs` に 1 回（MUST）」は公開 `sweep(now)` には成立しない
  （公開 `sweep` は閾値・間隔判定を経由せず、呼ばれた回数だけ無条件に全走査する。
  同じ文書が「定期バッチ・管理コマンドで `sweep(now)` を明示的に呼ぶことは妨げない」と
  自ら書いており、自己反証していた）
- 「`NODE_ENV` が効くのは 1 箇所のみ」は誤りで、実際は 3 箇所（`ALLOWED_ORIGINS` の
  fail-closed・`HOST` のループバック限定・`requireClientAddress`）＋ `server-env.ts` の
  未知値 throw。同じ数字が設計正本に「1」、`e2e/harness/sync.ts` のコメントに「2」と
  食い違って書かれていた
- 起動時 `throw` の列挙に M-1 ガード（`refillFullMs` が丸め誤差で吸収される規模のとき
  throw する）が抜けていた。「数値・閾値の正本はこの文書」と自ら宣言した文書での欠落だった
- 「`HOST` をループバック外へ変える変更はレート制限を丸ごと無効化する」は誤り。本番では
  起動時 fail-closed が起動そのものを拒否するため、気づける失敗になる。静かに無効化するのは
  fail-closed の検査自体を外す変更と、env から `NODE_ENV=production` が落ちる変更だった

**再発条件**: 訂正する側も、訂正前と同じだけ「断定を書いている」という自覚が抜け落ちる。
とくに量化の言葉（「1 つも無い」「唯一の」「必ず」「決して」「すべて」「常に」「1 箇所のみ」）
は反例が実装のどこかに 1 つあれば崩れる。訂正のたびに実装を読み直さず、前の断定を信じて
上書きすると連鎖が続く。

**対処**: 今回の訂正では、A の 5 件それぞれについて `node --experimental-strip-types` で
`packages/rate-limit/src/*.ts` を絶対パス import し、断定を壊す入力を実際に作ってから
文章を直した（例: 同一 `now` で `sweep(now)` を 100 回呼び `sweepRunCount()` が 100 に
なることを実行して確認）。**訂正を書く前に、それを壊す例を自分で作る**という手順を徹底した。

### 2. 「塞いだつもりで別の入口が空いている」が繰り返し起きた

**事実**: `NODE_ENV` の効く箇所を「1」→「2」→ 気づかず放置、`ADR 0012 D6` という架空の
根拠を 3 箇所（`timer-sync/config.ts`・`poker-sync/config.ts`・`client-key.ts`）に置いたまま、
`token-bucket.ts` の `shouldReject` 純粋性の一次記述を D4 と誤記したまま、といった具合に、
1 箇所を直しても他の箇所に同じ誤りが残っていた。

**再発条件**: 同じ事実を指す参照・数値を複数のファイル・複数の文書に**転記**すると、
1 箇所を直しても他が古いまま残る（`docs/adr/0002` が禁じる二重正本と同じ構造の問題が、
コードコメントとドキュメントの間でも起きる）。

**対処**: 修正時に `grep -rn` で同じ誤り（「ADR 0012 D6」「1 箇所のみ」「持続 1 回/秒・
バースト 60」等）の全出現箇所を洗い出してから直した。数値は可能な限り参照へ差し替え、
転記そのものを減らした（ADR 0011 決定4・S1・S7 行）。

## 検査の穴（緑のまま壊れていたものは何か）

### 防御を壊しても全検査が緑になる経路が 4 つ実証された（W-1〜W-4）

最終レビューがスクラッチのコピーに 4 通りの壊し方を適用し、当時の全検査
（typecheck・lint・566/132/117/70/17 のテスト・E2E 27・監査 3 種・変異 12 件）が
**緑のまま**通ることを確認した。うち 3 件（X-Real-IP を鍵の材料に使う・ループバック
許可リストへの誤った追記・ログ衛生が `packages/rate-limit/src` を走査していない）は
実 WS テスト・負のテストケース・走査対象への追加で塞ぎ、変異検査に 1 件登録した
（12 → 13 件）。**検査の厚さ（テスト件数・監査スクリプトの数）は正しさの証明にならない**
——同じ入口が 4 通りも見つかったのは、テストが「正しく動くこと」ばかりを固定し、
「特定の壊し方をしたら落ちること」を固定していなかったため。

### 既存検査が赤で教えていたのに走らせていなかった

`e2e/tests/spec-tags.test.ts` の 1 件が pre-existing で fail していた
（`e2e/specs/rate-limit.spec.ts` の 2 シナリオがタグをタイトルの**末尾**に付けており、
規約上は先頭のはずのタグ検査から「untagged」と誤分類されつつ、`--grep` には引っかかって
本番へ実際には流れる、という規約違反）。`turbo run test` の一部として実行されるが、
`corepack pnpm e2e`（実 Playwright 27 件）には含まれず、日常の確認経路では気づけない
構成になっていた。開始時点の HEAD でも同じ理由で fail することを確認し、本タスクの
回帰ではないと判断したが、**検査が指摘していたのに、指摘に気づく経路そのものが
日常運用から外れていた**という点は独立した欠陥として残る。

## 最終レビューで確定した文書と規範の誤り（本コミット群で対応）

上記の断定の反証に加えて、最終レビューは次も確定させた（本振り返りのコミット群で対応済み）:

- ADR 0012 の D3/D5/D6 と #103 設計正本の D3/D5/D6 は全部別物なのに、コード中の
  引用が「ADR 0012 D6」と誤って 3 箇所に置かれていた（実際に意図していたのは
  #103 設計正本 D6）
- 憲法 原則 XI が「秘密（トークン・鍵）は env のみに置く（MUST）」とする一方、
  HMAC ソルト（新しい保持）はどの分類にも載っておらず、「秘密」と分類すると
  ADR 0012 決定 D3 の「ソルトを env 化・永続化することは MUST NOT」と正面衝突する
  ——ソルトを「鍵導出材料」として独立に分類し、衝突を解消した
- ADR 0011 が自ら宣言した「数値を転記しない」に違反する箇所（バースト 60・容量 60・
  同時接続上限 200）が残っていた。決定4の判定に使う前提レート自体（除外対象）は残しつつ、
  それ以外を参照へ置き換えた
- ADR 0011 の「レート制限の設定値の正本」が、#103 が置き換えた旧仕様
  （`connId` 単位・10 秒 30 回）を記す古い設計正本を指したままだった
- `apps/timer-sync/src/adapters/ws-adapter.ts` の 3 箇所が、完了済みの Task 5・6 を
  「これから来る」前提で書いたままだった。しかも `gate.open()`/`gate.close()` の実際の
  呼び出しは `application/handlers.ts` 側にあり、ws-adapter.ts には来なかった
- 変異検査 m11 の note が「同義表記が同じ鍵になることを固定しているテスト」と書いていたが、
  パッチを実際に当てて確認したところ検出しているのは
  `client-key.test.ts` の「下位 64 ビットが違っても同じ鍵になる」だった
- 観測点（`size()`/`sweepRunCount()`）が「テストからも運用からも確かめられる」と
  書かれていたが、`RateLimitGate` は透過しておらず、`/status` にも出ておらず、
  製品コードからの呼び出しは 0 件だった。MUST の範囲を実装の到達範囲（テストからの
  観測のみ）に合わせて訂正し、運用面は既知のギャップとして明記した
- `docs/guides/architecture.md` の層対応表に `packages/rate-limit` が無かった。
  sync 専用の共有ユーティリティとして独立の行に追加した
