# 振り返り: 検査の CI 組み込みとジョブ絞り込み（#70）

**対象**: Issue #70（C: CI/CD 整備）・ **PR**: #129（設計書・実装計画）/ #130（PR-2）/
#131（PR-3）/ #132（PR-4）/ #133（PR-5）/ 本 PR（PR-6・振り返り）
**期間**: 2026-08-12（設計から PR-5 まで同日）・積み上げ 6 本、`main` への統合はまだ

## 踏んだ罠（事実と再発条件）

### 1. 設計段階で「直してはいけないもの」を直す計画になっていた

**事実**: 設計書の敵対的検証で 6 件を修正した（PR #129）。最大のものは、壊れリンクとして
「直す対象」に挙げた 10 件のうち 5 件が **直してはいけないもの** だったこと。
`docs/adr/0003` と `docs/adr/0008` が参照する `docs/BACKLOG.md` は、ADR 0003 の決定
「バックログは GitHub Issues に一本化する。`docs/BACKLOG.md` は廃止する」が実行された結果として
存在しない。不在は記録として正しく、リンクを直すと決定の実行結果を隠すことになる。

**再発条件**: 壊れリンクの実測値（「存在しない」）は正しかったが、**そこから「直すべき」への
飛躍が誤っていた**。ADR・過去決定を参照する文書では、リンク切れが「まだ直っていない」ではなく
「決定が実行された証拠」であるケースがある。

**対処**: `scripts/check-links.mjs` に例外表（`MISSING_PATH_EXCEPTIONS`）を新設し、
`docs/BACKLOG.md` を登録した。例外表は形骸化の入口なので、使われなくなったエントリを
落とす検査（Task 3）を併設した。**例外表は最終的に 2 件になっている**（もう 1 件は
`apps/timer-sync/.env`。経緯は「6. リンク検査の存在判定がファイルシステムを見ていた」を参照）。

### 2. 自作の slug 生成規則が GitHub の実際の出力と食い違っていた

**事実**: Markdown 見出しからアンカー slug を生成する自作規則（空白の連続を 1 個のハイフンへ
潰す）は、GitHub の実際のレンダリング結果と 18 見出し中 8 件で食い違っていた。GitHub の規則は
「空白 1 個 = ハイフン 1 個」であり、連続空白はハイフンも連続する。

**再発条件**: 外部システム（GitHub）の変換規則を、自分の理解で実装してから検証する順序。
仕様書やドキュメントを読んだだけの理解と、実際の出力は一致しない場合がある。

**対処**: GitHub の HTML レンダリング API（`Accept: application/vnd.github.html`）に
`docs/poker/specs/001-planning-poker-mvp/contracts/ws-protocol.md` の 18 見出しを実際に
生成させ、その結果と 18/18 一致する対応表をテストに持たせてから実装した。**規則を実装する前に、
その規則の正本に生成させて突き合わせる。**

### 3. 前提が調査で入れ替わった

**事実**: Issue #70 のコメントは「ランナー時間の 43% が無駄」を絞り込みの根拠にしていたが、
このリポジトリは **PUBLIC で GitHub Actions は無料** だった（`actions/runs/*/timing` の
`billable.UBUNTU.total_ms` が 0、実時間は 102 秒）。目的は費用削減ではなく **待ち時間の短縮**
へ置き換わった。

**再発条件**: Issue 本文・コメントに書かれた「無駄」「コスト」の主張を、実測せずに設計の
根拠として引き継ぐこと。過去の振り返り（#69・#84・#80・#79）でも同種の事実誤認を踏んでおり、
着手前に主張を 1 つずつ実測で叩く運用が今回も効いた。

### 4. 抑制だけが残って検査が無い（shellcheck）

**事実**: `deploy/deploy.sh:75` と `deploy/lib/common.sh:58` に shellcheck の抑制
ディレクティブが存在していたが、shellcheck 自体は CI にも手動運用にも組み込まれていなかった。
**抑制する対象の検査そのものが無かった。**

**再発条件**: 「検査が静かに効かなくなる」の一形態として、検査を弱める指示（抑制）だけが
コードに残り、検査本体が失われる／導入されないまま放置されるケース。

**対処**: shellcheck を `quality` ジョブへ導入し、`deploy/**` と `scripts/**` の対象 6 本
（`.specify/scripts/**` は vendor のため対象外）を CI で走らせるようにした（ADR 0009 D6）。

### 5. 自分たちの変更で既存文書が嘘になった

**事実**: `docs/guides/development.md:215` の記述「CI からは呼ばれない手動の検査です
（#70 で組み込み予定）」は、その #70 の実施（Task 13/14）によって事実と食い違う記述になった。
実装者が担当外の記述として気づき、同じ PR（コミット b11a410）で直した。

**再発条件**: #68 の振り返りが記録した **I-2**（「Task 12 以降、README はここへリンクするだけ
になります」という過渡期の説明が、Task 12 完了後も残っていた）と同型。**将来の完了を予告する
文が、その完了によって過去形にならず古いまま残る。**

### 6. リンク検査の存在判定がファイルシステムを見ていて、ローカルと CI で答えが違った

**事実**: `deploy/timer/NOTES.md:104` が参照する `apps/timer-sync/.env` は gitignore 対象で、
開発者の手元には実ファイルがあり、CI のフレッシュな checkout には無い。存在判定を
ファイルシステム基準で行っていたため、ローカルでは通り CI でだけ落ちた。PR-2 の初回 CI で
`docs` ジョブが落ちて発覚した。

**再発条件**: gitignore 対象のファイルを、案内目的でドキュメントが参照するケース。存在判定を
ファイルシステム基準にしていると、この非対称に気づけるのは CI 実行時（フレッシュな checkout）
だけになる。

**対処**: 走査対象と存在判定を `git ls-files` 基準へ変え、この 1 件を例外表
（`MISSING_PATH_EXCEPTIONS`）へ追加した。**文書の記述自体は正しく（実 env を各自で作る手順の
案内）、壊れリンクではない。** 例外表は `docs/BACKLOG.md` と合わせて最終的に 2 件になっている。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 1. 破壊検証の「壊し方」自体が検査に引っかからなかった 3 件

Task 7 Step 5 の破壊検証は 10 件すべて最終的に成立したが、そのうち **3 件は最初の壊し方では
検査に引っかからなかった**。

- **変異検査**: 1 度目は計画が消す対象を誤っていた（`driver-switch-equivalence.test.ts`。
  正しくは `evolve.test.ts`）。2 度目は正しい対象を消しても **quality が緑のまま** だった。
  原因は `mutation-check.mjs` 自身の構造的な穴（次項）。
- **shellcheck**: 計画が指定した `SC2086` は **info レベル** で、CI の
  `--severity=warning` に弾かれる。**破壊検証それ自体が空振りしていた。** `SC2046`
  （warning レベル）へ差し替えて成立させた。
- **fail-open**: 計画は `main()` の先頭に例外を挿す指定だったが、そこは `try` の外。
  実際に起きたのは fail-open ではなく **スクリプト自体の異常終了**（ジョブが赤くなる）
  だった。`changedFiles()` の中で存在しない base を見る形へ修正してやり直し、
  4 ジョブすべてのログに「判定できないため全ジョブを走らせます」が出ることを確認した。

**教訓**: 「わざと壊す」だけでは足りない。**その壊し方が本当に検査に引っかかるか**まで
確かめて初めて破壊検証が成立したと言える。今回は 3 件とも 1 回目は空振りし、指定を直して
2 回目でようやく成立した。

### 2. 変異検査そのものが空振りしていた

`scripts/mutation-check.mjs` は、vitest が「No test files found」（exit 1）を返した場合を
「変異を検出した」（`result.status !== 0`）と誤判定していた。対応表（`MUTATIONS`）が指す
テストファイルが消えると、変異検査は **全件「検出」と報告して緑になる**。守るべきはずの
「検査が静かに効かなくなる」を、**検査自身が起こしていた**。

対応表のテストファイルの実在を実行前に確かめる `assertMutationTestsExist()` を追加して塞いだ
（Task 7b・コミット 1b9f43e）。破壊検証（① 対応表を誤らせる、② 正しい対象を消す）の両方で
ローカルの赤を確認済み。

### 3. レビューが「実装を壊してもテストが落ちない」欠陥を摘出した（Task 2・3・6）

Task 2・3・6 で、レビュアーが実際に実装を壊して「テストが落ちないこと」を実証した。いずれも
**実装計画に書かれたテストの欠陥**で、実装者の逸脱ではない。

- **Task 2**: 「フェンス内のコマンド例は拾わない」規則を守る `if (mask[i]) return;` を
  無効化しても 27/27 が通った。フェンス内にバッククォート引用を含む fixture が無く、
  規則が **恒真**（常に true）になっていた。裁定は「Task 2 の修正ラウンドで今直す」→
  対照実験の 2 件へ置き換え。
- **Task 3**: `isLiveDoc` の完全一致条件を前方一致へ壊しても 35/35 が通った。「完全一致の
  エントリを前方一致で判定しない」ことを確かめる fixture が無かった。
- **Task 6**: 「値が文字列の指標も判定を出さない」規則から `typeof r.value === "number"`
  を落としても検出できなかった。fixture の目標がすべて文字列で、**判定条件のもう半分
  （値が数値かどうか）を検査する fixture が無かった**（レビュアーが 3 件全部を壊して実証）。

共通の形は「**条件式の片方だけで結果が決まる fixture**」だった。判定条件が `A && B` でも、
テストの入力が常に `B` 側だけで false になっていれば、`A` を落としても検出できない。

なお Task 1 の Important 指摘（`stripCodeRegions` がコードフェンスの長さを見ずに閉じていた
欠陥）は種類が異なる。これは恒真テストではなく、実際の文書
（`docs/superpowers/plans/2026-06-07-tasuki-vps-deployment.md:425/495/496`）を通した際に
初めて表面化した **未網羅のケース**（テストが無いことによる見落とし）だった。

## 実測した待ち時間の削減幅

| 変更の種類 | 実測 | 出典（run ID） |
|---|---|---|
| 通常の PR（コード変更あり） | ci 130〜133s / e2e 56〜69s / quality 22〜29s / audit 10〜13s / docs 4〜5s | 31549031840 / 31549998330 |
| fail-open 破壊検証（判定不能） | ci 121s / e2e 51s / quality 25s / **audit 19s**（本体を実行） / docs 8s | 31558407635 |
| 同上・revert 後（通常） | ci 123s / e2e 52s / quality 26s / **audit 7s**（早期成功） / docs 7s | 31559537335 |

基準（文書のみの PR で従来 128〜141 秒）に対し、実測は **20 秒**（見積り 25 秒より速い）。
`quality` ジョブ（22〜29 秒）は臨界経路の `ci`（121〜133 秒）に完全に隠れるため、コードを
変える PR でも体感の待ち時間は増えない。実測値の正本は設計書
`docs/superpowers/specs/2026-08-12-ci-checks-and-job-scoping-design.md` の
「実測値の正本」表（run ID つき）。
