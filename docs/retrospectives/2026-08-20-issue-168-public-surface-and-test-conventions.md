## 0. この Issue の戦略

## 1. 踏んだ罠（事実と再発条件）

### 1-1. 公開面を縮めたら、別の検査が「宣言が見つからない」で落ちた

**事実**: Task 1 で `packages/timer-core/src/errors.ts` の `Unauthorized` / `PhaseConflict` /
`InvalidIndex` / `InputLimitExceeded` の 4 interface から `export` を外した。この時点から
`node scripts/audit-domain-error-shape.mjs` が exit 1（4 件）になり、scripts 自己テストも
2 件 fail していた。**気づいたのは Task 4 の実装者であり、Task 1・2・3 の 3 タスク分
（コミット 4 本）気づかないまま進んでいた。**

**原因**: `findDeclarationSpan` の開始正規表現が `^\s*export\s+(type|interface)\s+NAME` で、
`export` を必須にしていた。加えて、各タスクの完了確認が `audit-structure.mjs` **1 本だけ**を
見る手順になっていた（計画の欠陥）。ADR-0016 決定 2 項目 3 の文言は
「ドメインエラーは判別子と機械可読な詳細のみを持つ」であり、**公開されているかどうかを
条件にしていない**。つまり検査の側が要求より狭かった。

**対処**: `findDeclarationSpan` を非公開の宣言にも当たるよう修正した（Task 4b）。
検査を弱める側（`DOMAIN_ERROR_TARGETS` から 4 型を落とす）は採らなかった。
自分たちの改修に合わせて検査を弱めるのは、SC032 の定義変更を却下したのと同じ形だからである。
あわせて各タスクの完了確認を**全検査 8 本 + scripts 自己テスト**へ広げた（裁定 R8）。

**再発条件**: 「公開範囲を変える」作業と「宣言を正規表現で探す検査」が同居していて、
かつ各タスクの完了確認が一部の検査しか見ていないとき。

### 1-2. 計画が指定した変異が弱く、実装者が 3 回訂正した

「テストが本当に効いているか」を確かめるための変異を計画が指定したが、**3 回とも
その変異では対象テストが赤くならなかった**。原因は 3 回とも別である。

| # | 指定した変異 | なぜ検出力が無かったか |
|---|---|---|
| Task 2 | `isManager` から `editor` を落とす | 唯一 editor が実在するテストで**その editor 自身が降格対象**になっており、`wouldKeepAtLeastOneManager` の `if (!isManager(target)) return true;` で**早期 return** するため `countManagers` に到達しない |
| Task 3 | `v.partial(SessionConfigSchema)` → `v.object({})` | valibot の `v.object({})` は**非 strict** で未知キーを黙って剥がす。`v.strictObject({})` なら 2 件とも赤くなる |
| Task 9 | `createRoom` への `sed` / `return ok(...)` の直後に追記 | `sed` が `joinRoom` にも**当たりすぎた**（行番号指定で解決）。`return` の直後の追記は**到達不能コード**なので何も変わらない（`return ok(...)` 行自体を `return err(...)` へ置換して解決） |

**原因**: 計画を書く側が、変異を**当てずに**「これで赤くなるはず」と書いていた。
実装を読めば分かる範囲（早期 return・非 strict）と、実行しないと分からない範囲
（`sed` の当たり幅）の両方がある。

**対処**: Task 3 の時点で裁定 R6 を出し、以降の dispatch には
「指定した変異が本当に検出力を持つかを疑え」を必ず書いた。3 回とも実装者が自力で
訂正し、対象テストが赤くなる別の変異を見つけている。

**再発条件**: 変異を「書いた」だけで「当てた」証拠が無いまま手順書に載せたとき。
このリポジトリの既存の教訓（`verify-the-break-itself`）が、計画を書く工程にも
そのまま当てはまることが示された。

### 1-3. 実装者が controller の裁定を覆した（deck.test.ts）

**事実**: SC032 の区切りを入れられないテストは全リポジトリで
`packages/poker-core/tests/deck.test.ts` の「フィボナッチ10種を順序どおりに含む」1 件だけだった。
controller は裁定 R13 で「既存の慣習を適用して区切りを入れる。例外機構は作らない」と決めた。
根拠は、Task 11 のレビューが承認した前例
`// Given（CONNECTION_CASES の各状態を入力に使う）`（下にコードが無く、モジュール定数を指す形）である。

**実装者はこれを実行せず、根拠つきで差し戻した。** 前例の `CONNECTION_CASES` は
モジュール定数が**関数への入力**であり、`// When` の下に `.map(...)` という**実体のある操作**が
あった。`FIBONACCI_DECK` のテストは定数そのものを 4 つの `expect` で直接見るだけで、
**手前に呼べる操作が一つも無い**。`// When` を足すと「もう存在する値を読む」行為に
操作の名札を貼ることになり、Task 10 で除去した「飾りの `// When`」と同種になる。

**原因**: **controller の裁定は「Given が実在するものを指すか」だけを見て、
「When 側に操作があるか」という肝心の違いを見落としていた。** 前例との類似を
一次元でしか測っていない。

**対処**: 差し戻しを受け入れ、裁定 R14 で SC032 に理由つき例外表を 1 件だけ持たせた
（Task 13b）。**除外は分母から行い、分子には足していない。**
その後のレビュアも独立に同じ結論に達している。

**再発条件**: 「承認済みの前例があるから同じ扱いでよい」と判断するとき。
前例と当該事例が**どの軸で似ていてどの軸で違うか**を書き出さないと、
似ている軸だけを見て決めてしまう。

### 1-4. コミットメッセージが到達していない達成を主張した

**事実**: コミット `b695492` のメッセージは「構造監査の測定値つき指標がすべて目標へ到達した」と
書いているが、そのコミット時点の SC032 は 99.9% であり **100% に到達していない**。

**原因**: **計画（controller が書いた実装計画の 1971 行目）に、その文言が
コミットメッセージの雛形としてあらかじめ書かれていた。** 実装者は雛形どおりに書いただけである。
つまり誤りの発生源は実装者ではなく、「まだ起きていない結果」を先回りして
書き込んだ計画の側にある。

**対処**: 裁定 R15 により**履歴は書き換えなかった**。`--amend` + force push は
未マージの専用ブランチなら技術的には可能だが、書き換えると「誤りがあり、
それを捕まえた」という事実自体が消える。追随コミット・PR 本文・この振り返りで訂正し、
計画の雛形も直した。

**再発条件**: 手順書に**結果を断定するコミットメッセージの雛形**を書いたとき。
雛形は「何をしたか」までにとどめ、「指標がどうなったか」は実行後に書く。

### 1-5. 測り方そのものが曖昧な結果を出した

**事実**: Task 13b で、検査の 4 経路のうち経路 4 の件数を数えるのに複数行の文字列を
`grep -cF` に渡したところ、9 と 8 で結果が揺れた。1 行の固定文字列で数え直して解決した。

**原因**: `grep -cF` は**行単位**で数える。複数行のパターンを渡すと、どの行がどう当たったかが
自明でなくなる。

**対処**: 数える対象を 1 行の固定文字列に限定した。

**再発条件**: 「壊れたことを先に確認する」ために `grep -c` を使うとき、
パターンが複数行にまたがっているとき。このリポジトリの既存の教訓
（`verify-the-break-itself` の「`grep -cF` で壊れたことを先に確認する」）は、
**パターンが 1 行であることを暗黙の前提にしていた**。

## 2. 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 2-1. 型検査は `index.ts` の列挙漏れを捕まえない（実測・本 PR の HEAD で再現）

`packages/poker-core/src/index.ts` から `export { computeStats } from './stats';` の 1 行を
削除して測ったところ、次のとおりだった。

| 検査 | 結果 |
|---|---|
| `pnpm typecheck --force` | **14/14 成功** |
| `node scripts/audit-public-surface.mjs` | **exit 0** |
| `node scripts/audit-structure.mjs` | **exit 0** |

**何一つ落ちない。** 理由は、`computeStats` を使っているのが `packages/poker-core` 内部の
`snapshot.ts` であり、**そちらは相対パスで直接 import している**ためである。
index 経由の利用者がゼロなので、index から落としても誰も壊れない。

`export *` を明示列挙へ置き換える作業は、この意味で**型検査を安全網にできない**。
本作業では 43 記号を機械生成して宣言と列挙を突合し（`LC_ALL=C` で並びを揃えて差分ゼロ）、
型検査を根拠にしなかった。ただし**これは一度きりの照合であり、以後この網羅性を継続的に
見る検査は存在しない**。

### 2-2. SC039③ の走査は `packages/timer-core` 1 パッケージだけを見ている

`buildSc039Sources` が組み立てる照合先は `packages/timer-core/src` の **14 ファイル**のみである
（実測）。`SCANNED_PACKAGES` には `packages/*` が 4 つ宣言されているが、
残る 3 つ（`poker-core` / `protocol` / `rate-limit`、計 15 ファイル）は**測られていない**。

指標は「公開記号 0 件」と表示するが、これは**timer-core についてのみ 0** という意味である。
#135 が他の指標について解消した「走査対象の狭さ」の残余であり、**#180 として切り出した**。

### 2-3. 理由つき例外表という「0」と「100%」の作り方

SC039③ の「0 件」と SC032 の「100.0%」は、どちらも**理由つき例外表を分母から外した値**である。
数字だけを見て「全件が規約を満たした」と読むのは誤りなので、両方の表に
`reason` を必須にし、腐り止めを付けた。

- SC039③: 例外 4 記号（`SYNC_ERROR_CODES` / `ServerMsgSchema` / `RoomSchema` /
  `DEFAULT_ERROR_MESSAGE`）。**3 経路**の腐り止め（宣言が消えた／製品から参照され始めた／理由が空）
- SC032: 例外 1 テスト（`packages/poker-core/tests/deck.test.ts`）。**4 経路**の腐り止め
  （ファイルが走査対象に無い／テスト名が無い／区切りを持った／理由が空）

**除外は分母からのみ行い、分子には足していない。** SC032 の分母は 1434 → 1433、
分子は 1433 のまま（独立に測って確認）。`n < d` のとき `(n-1)/(d-1) < n/d` なので、
この形の除外は比率を上げる向きには構造的に効かない。

**例外表の増加そのものを止める機構は無い。** 根本原因（SC032 の分母判定が
論理的な文ではなく物理行を数えること）は据え置いた。

### 2-4. 検査を 1 本足すと 4 箇所を触り、その突合を見る検査が無い

`scripts/audit-public-surface.mjs` を新設するために触った箇所は次の 4 つである。

1. `scripts/audit-public-surface.mjs`（検査本体）
2. `scripts/audit-public-surface.test.mjs`（自己テスト）
3. `.github/workflows/ci.yml` の `quality` ジョブ（実行される経路）
4. `docs/guides/development.md` の「検査系」節（人が見つけられる経路）

このうち**自己テストだけが git から導出**され、残り 3 箇所は手で書く。
**4 箇所が揃っているかを見る検査は存在しない**（実測で確認）。
1 箇所を書き忘れると、検査は存在するのに実経路では効かない（3 を忘れた場合）か、
存在するのに誰も知らない（4 を忘れた場合）状態になる。

#175 が機構へ倒したのは CI ジョブ**表**の `quality` 行であって、
`development.md` の「検査系」節の列挙ではない。この穴は本作業では塞いでいない。

### 2-5. SC032 の定義変更案を敵対的検証で却下した（検査を弱めかけた記録）

SC032 の分母判定を「物理行」から「トップレベルの文数え」へ変える案を出した。
賢い判定にすれば「本体が 2 行以下の自明なテストは対象外」という ADR-0006 決定 2 の
意図に近づく、という理屈だった。**実測したら壊れた。**

| 出した主張 | 実測 |
|---|---|
| 46 件が対象外になる | 不足は 275 → 199（76 減） |
| 分母 1432 → 1386 前後 | 分母 1432 → **1279**（153 減）。**分子も 77 減る** |

さらに副作用が 2 つあった。

- **`it.each` の 41 件中 35 件が分母から落ちる。** `it.each([...])(` の引数行が
  最小字下げになるため「文 = 0」と判定される
- 区切り済みなのに落ちる 77 件に、**34 行のテストが 2 件・26 行が 2 件**含まれる

これは「賢い検査ほど穴が増える」の実例であり、指標を良く見せるために検査を弱める形でもある。
**尺度は変えず、275 件すべてに区切りを入れる**方針へ戻した。
どうしても当てはまらない 1 件だけを、理由つき例外として名指しした（2-3）。

### 2-6. `ServerMsgSchema` は検査の土台だが、製品の実経路に配線されていない

例外表に載せた `ServerMsgSchema` の参照元を数えたところ、
`apps/timer-sync/src` と `apps/timer-web/src` からの参照は **0 件**だった（実測）。

- 送信側: `apps/timer-sync/src/adapters/ws-adapter.ts` の `send` / `broadcast` は
  `data: unknown` を受けて `JSON.stringify(data)` するだけで、スキーマ検証をしていない
- 受信側: `apps/timer-web/src/sync/dispatch.ts:35` は
  `JSON.parse(raw as string) as ServerMsg` という**型アサーションのみ**で、実行時検証が無い
- 一方、**受信方向（クライアント → サーバ）は検証されている**。
  `ws-adapter.ts:413` が `parseBoundaryMessage(CommandSchema, raw.toString())` を通している

つまり境界の検証が**片方向だけ**成立している。テストは実 WS のフレームを
`ServerMsgSchema` と突き合わせているので、契約自体は守られているが、
**製品コードは自分が送るものを検証していない**。**#181 として切り出した**。
