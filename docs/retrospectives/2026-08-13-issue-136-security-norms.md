# 振り返り: セキュリティの規範を定め、情報の露出を塞ぐ（#136）

**対象**: Issue #136（セキュリティの規範を定め、情報の露出を塞ぐ）
**ブランチ**: `docs/136-security-norms`（`main` への統合はまだ）
**期間**: 2026-08-13（設計から最終レビューまで同日）・merge-base `b4d249a` から 36 コミット

## 踏んだ罠（事実と再発条件）

### 1. 手書きの字句解析による検査が、直すたびに新しい検出漏れを持ち込んだ（Task 10）

**事実**: `scripts/audit-log-hygiene.mjs`（`console.*` 直接呼び出しやロガ迂回を禁じる検査）は、
最初の実装から 4 ラウンドかかった。

- round 1: `/* note */ console.log(x)` がすり抜ける（`isCommentLine` の穴）
- round 2: ブロックコメントの継続行を状態機械で追う実装に直したところ、正規表現リテラル内の
  エスケープされたスラッシュで行の残り全体が消える新しい検出漏れが生まれた
- round 3: 状態機械そのものを撤去し「行をまたぐ状態を一切持たない」設計（`trimStart()` が
  `//` か `*` で始まる行だけ飛ばし、それ以外は生テキストで照合）へ方針転換したが、
  `*/ code`（ブロックコメントを閉じた直後に実行されるコード）を塞ぎ切れていなかった
- round 4: 正規表現 1 本（`CLOSES_THEN_CODE`）を足して塞ぎ、状態は増やさずに解決

**再発条件**: 「賢い検査」（行をまたいで状態を追う・コメント/文字列/正規表現リテラルを正しく
判別する）を素朴な字句解析で書こうとすると、直すたびに別の穴が開く。JS を正しく解析するには
本物のレキサが要るのに、200 行規模の手書きスクリプトで済ませようとした設計判断そのものが
繰り返し裏目に出た。

**対処**: 「行をまたぐ状態を一切持たない」設計へ倒し、偽陽性（安全側）は許容し検出漏れは
原理的に起きない形にした。**賢い検査ほど穴が増える。単純で退屈な規則のほうが検査としては
強い。**

### 2. 変異検査自身が「テストを 1 件も実行せずに検出したと報告する」欠陥を持っていた（Task 11）

**事実**: `apps/timer-sync` に対する変異検査（`scripts/mutation-check.mjs`）は、`npx vitest`
が `vitest: not found` で exit 127 を返す状態でも「変異を検出した」と報告していた
（判定が `status !== 0` のみで、vitest が起動できないケースを弾いていない）。実際には
**変異を当てていない素のコードでも同じ exit 127 が出る**ことを対照実行で確認し、
Task 3/5/10 に対応する 3 件の「検出」がすべて偽陽性だったと判明した。

**再発条件**: exit code だけで合否を判定する自作の検査ランナーは、テストランナー自体が
起動に失敗するケース（依存未解決・パス誤り・ランタイム不一致など）を「検出」と誤判定しうる。
#70 で「No test files found」の文字列一致ガードを塞いだはずが、**ガードが見ていない別の
失敗モード**（起動失敗）には無力だった。

**対処**: 変異を当てる前に**対照実行**（素のコードでテストが実際に通ることを先に確かめる）
を必須にし、`apps/timer-sync` のランナーを `bun test` に正した。旧ガードは対照実行へ
一本化して削除。破壊検証で「対照そのものを壊すと検出扱いにならず停止する」ことも確認した。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 最終レビューだけが見つけた Critical: ロガの `event` 引数が生の `string`

`logger.info(\`reclaimed ${code}\`, { idleMs })` のような呼び出しが、**型検査・
460 件のテスト・ログ衛生の検査（当時の版）のすべてを通っていた**。これは設計書
8 節の受け入れ基準そのもの（「ルームコードをログ出力へ渡す変更を CI が検出すること」）の
反例であり、**タスク単位のレビューを 17 回重ねても見逃していた**。

**なぜ緑だったか**:
- 型検査: `Logger.info(event: string, ...)` のシグネチャで `event` を素の `string` として
  受けており、`LogSafe` 型の壁が `event` 引数にはかかっていなかった
- テスト: 460 件はいずれも「ロガが正しく動くか」を検証しており、「危険な呼び出し方をした
  ときに落ちるか」を検証する fixture が無かった
- ログ衛生の検査: `FORBIDDEN` の規則が `console.*` 直接呼び出しやロガ迂回は拾うが、
  ロガの `event` 引数の中身までは見ていなかった

**対処**: `audit-log-hygiene.mjs` へ**許可リスト方式**の規則（`event` はその場に書いた
素の文字列リテラルのみ許可し、テンプレートリテラル・連結・変数経由はすべて拒否）を追加。
失敗するテスト 11 件を先に足して 5 件の赤を確認してから実装し、修正後は型検査・464 件の
テスト・ログ衛生の検査がすべて緑になることを確認した（コミット `5325e36`）。

**教訓**: 仕様に忠実であること（各タスクの実装計画どおりに作る）と目的を達成していること
（受け入れ基準を満たす）は別である。タスク単位のレビューは「計画どおりか」は検証できても、
「計画自体が受け入れ基準を満たす設計になっているか」は見落としうる。最終レビューで通しの
受け入れ基準に立ち返ったことで初めて捕捉できた。

## 規範と実装の食い違いを直す作業が、食い違いを作りかけた

Issue #136 自体が「規範と実装の食い違いを塞ぐ」ことを目的としていたが、その作業の過程で
新しい食い違いが複数回生まれかけ、いずれもレビューで捕捉して直した。

- **ADR 0011 の S9**: 「現行が規範に一致し、変更なし」と書いた初稿が、実際には
  存在しないコマンド `break` を挙げ、`permissions.ts` の実体（`HOST_ONLY_BEFORE_START` ―
  開始前は host 限定・開始後は編集者以上）とも段階依存の扱いが食い違っていた。制御側が
  実測して「失敗した仕様レビュー」として扱い、修正させた
- **ADR 0012 D2 の数値転記**: 「4 文字」という数値を ADR 0011 決定 4 と ADR 0012 D2 の
  両方に書いてしまい、二重正本になっていた（ADR 0011 決定 4 が桁数変更を検討対象にしている
  ため、片方だけ直ると腐る構造）。最終レビューで Critical として指摘され、参照のみに直した
- **`log-safe.ts` のコメント**: 「生成経路は本ファイルの関数のみ」という記述が、
  `as LogSafe` の直接キャストという第 2 の経路の存在と食い違っていた
- **ADR が MUST と言い、ガイドが未着手と自認する状態**（I4）: ADR 0012 D1 が poker-sync
  にも MUST を宣言する一方、セキュリティガイドは自ら未着手と書いていた
- **CSP の「外す条件」**: 実装者が実測した「React の `style` prop は CSP の inline 判定に
  掛からない」という事実が、Caddy の設定コメントと ADR 0012 D7 の「外す条件」に反映され
  ていなかった。レビュアーが `cssText` / `setAttribute('style')` の使用がリポジトリ全体で
  0 件であることを独立に裏取りしたうえで指摘した

**再発条件**: 規範文書（憲法・ADR）と実装・ガイドを同じ作業内で並行して書き換えると、
片方を直した時点でもう片方が古いまま取り残される。「直している最中」であること自体が
一時的な不整合を作りやすい。

**対処**: 最終修正（コミット `433184f`）で憲法 2.1.1・ADR 0011 決定 4・ADR 0012 D1/D4/D5・
ガイドをまとめて是正した。
