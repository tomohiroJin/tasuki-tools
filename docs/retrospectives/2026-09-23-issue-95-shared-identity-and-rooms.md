## 踏んだ罠（事実と再発条件）

### 1. 段階の途中でだけ成り立たない性質があり、テストは旧入口だけを通っていた

**事実**: 各段は「その段をマージした時点で両ツールが使える」ことを目標にした。**実際には、
途中の状態でだけ壊れていた性質が 4 つあった。**

| 段 | 壊れていたもの | 見つけた手段 |
|---|---|---|
| S4a | timer のルームコードを poker の入口へ与えると、**合言葉なしで保護ルームの snapshot が読めた** | 実機での再現（静的なレビュー 5 人は「指摘なし」） |
| S5a | ハブの入口の表示名の判定が死んでいた。`normalizeDisplayName(raw) === null` は、`string` しか返さない関数に対しては常に偽 | S5b の着手時の実測 |
| S5b | **ハブで作ったルームでは timer の「セッションを開始」が永久に押せなかった**。お題の代表を `isCreator` で決めていたが、ハブ経由ではそのフラグが立たない | S5c で E2E を玄関経由へ移したとき |
| S5b | 輪に 1 人だけの timer 参加者が、poker にだけ人が残るルームから退出できない（`BelowMinMembers`） | S5b の実測（**この段で初めて到達できる状態**） |

**原因**: S5a〜S5c のあいだ、入口は意図して二重にしてあった（設計正本 §7）。**E2E も手元の
確認も、慣れた旧入口（`Setup`）からルームを作っていた。** 新しい入口を通る利用者は
まだ本番に居ないので、新しい入口でだけ壊れている性質は誰の目にも触れない。

**再発条件**: 入口や経路を二重にして段階的に移すとき、**テストの入口を新しい経路へ移すのを
最後の段まで待つ**とき。「両方が動く」の検証が、実際には片方しか通っていない。

**対処**: S5c で E2E の入口を玄関へ移し、`isCreator` を「輪の先頭」へ替えた（その後 #271 で
「輪の先頭が timer を離れた場合」も直した）。`BelowMinMembers` は #290 で
`participant.remove` 側だけ直った（下の申し送り表を参照）。

### 2. 撤去した画面が担っていた役割のうち、「外へ出る」と「待つ」が取り残された

**事実**: S5c は `Setup` / `Join` / `TopPage` / `NameForm` を消した。消す画面の**主な役割**
（作成・名乗り）は玄関へ移したが、**脇の役割**が漏れた。

- 戻る導線・完了後の行き先・端末の完了記録への入口 —— 利用者のフィードバックで S5c に足した
- 退出・追い出し・終了後の行き先 → **#290**
- 読み込み中に応答が来ないと無言で永久に待つ → **#292**
- 名乗る前にルームが消えていることを知らせる → **#274**

**再発条件**: 画面を撤去するとき、**その画面が担っていた役割を「主な用途」でしか数えない**とき。
「そこから外へ出る道」「そこで待っている間の受け皿」は用途の一覧に現れない。

### 3. 在席で絞った一覧と、絞らない輪が並び、その非対称から穴が 5 つ出た

**事実**: S5a で wire の `participants` を**在席で絞った**。一方、交代の輪（`rotation`）は
**絞らない**（離席しても席は残る）。画面は長いあいだ、絞った一覧から輪の名前を引いていた。

- S5c: 輪に**名前の無い空枠が 2 つ**出た（利用者の実画面フィードバック）。`rotation-names.ts` の
  docstring は「サーバーが退出時に rotation からも外すため通常は発生しない」と**現況について
  誤った説明をしていた**
- #276: 切断者に印が付かない／「次は誰か」をクライアントが素朴に計算してサーバーと食い違う／
  離席者どうしが同名だと呼び分けられない —— の 3 つ
- #294: 名前の投影として流用していた `config.members` を wire から落とした

**再発条件**: **同じ集合の 2 つの見え方**（絞った一覧と絞らない輪）を wire に並べ、どちらを
正本にするかを決めないまま画面が片方から他方を引くとき。

**対処**: #276 で `session.seats[]` に表示名と飛ばす理由を持たせ、画面は識別子で照合する形にした。

### 4. 計画と裁定の誤りは、実装の誤りより高くついた

**事実**: 私（計画を書く側）の誤りが下流へ写った例が、段ごとに出た。

- S3: 実装計画に誤りと欠落が 6 件（テスト名に Issue 番号を埋める例を示した・存在しない語「ホスト」を
  探すテストを示した。**書いたとおりなら初日から緑**になる偽の検証だった）
- S4a: 「UI は参加者の順序に依存しない」と裁定したが、`Lobby.tsx` は配列順に描画する
- S5a: 設計正本だけを読んで実装し、**ADR-0019 決定 2 の MUST（`vite.config.ts` を代理指標にする）**
  を落とした
- S5c: 「新しいセッション」の行き先を「同じルームの選択画面」と決めたのが Critical だった
  （`phase` が `celebration` のまま残り、抜けられない閉路になる）。**計画のテストは遷移先の文字列
  しか見ていなかった**
- #276: 設計に「配布は同期サーバーが先」と書いたが、`deploy/deploy.sh` は 1 コマンドの中で
  web → サーバーの順に配る。**実行不可能な指示を、実装者が 2 箇所のコード注釈へ忠実に写した**

**「新しいセッション」の行き先は 2 度決め直した。** S5c の裁定（2026-09-14）は
「`phase.set setup` を送ってから玄関へ」だった。#290 で「同じルームのロビーに留まる」へ
変わっている（2026-09-23 に実画面で確認）。**設計正本 §10.1 の 6 行目は S5c 時点の記録**として読む。

**再発条件**: 計画を書く側が、**参照する仕組み（`deploy.sh`・ADR・描画コード）を自分で開かずに**
記述を下ろすとき。下流の実装・テスト・レビューは上流の誤りに全部同じ側へ倒れる。

### 5. 決定を記録する段で、未来を完了形で書いた

**事実**: S0 の 1 つの PR で 3 回踏んだ（`docs/timer/adr/0007` に「廃止した」、`docs/adr/0011` の
「対策（現行）」の欄に「削除された」と書いたが、どちらも S3 で未着手だった）。

**再発条件**: 「未実施」「S○ で行う」と書いた文を、**実施した段が見に行かない**とき。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### 1. 合否の無い指標が、段ごとに後退していた

SC-032（本体 3 行以上のテストは前提と操作を区切る）の未達が、**S4a で 2 → 9、S4b で途中 2 → 15、
S5b の一括編集で 2 → 11** と後退した。S5c では SC-027 も 0 → 1 になった。
`audit-structure.mjs` はこれらを合否の無い「—」で出すので、**CI は毎回緑だった。**
タスク単位のレビューも全体レビューも拾わず、**main を worktree で流して並べたときだけ**見えた。

### 2. 変異パッチが当たらなくなり、以降の変異が検査されていなかった

実装を動かすと既存の変異パッチが当たらなくなる。S4b（m03）・S5c（m07・m13）・#276（m03・m25）で
起き、**`mutation-check.mjs` はそこで止まって、後ろの変異へ到達すらしなかった。**
`pnpm test` にも E2E にも出ない。S5c で `git apply --check` を全パッチへ流す検査を
`scripts/mutation-check.test.mjs` に足した。**ただし変異検査そのものは `pnpm test` に入っていない**
ので、回すことを忘れれば同じことが起きる。

### 3. 正しい実装と誤実装が同じ値を返す位置にアサーションがあった

#274 で 3 件・#276 で 3 件。例: 輪 `[A(現), B(不適格), C]` で交代を起こし、**交代後**に
`nextIndex` を見た。交代後は正しい実装も素朴な `(cur+1)%len` も 0 を返す。**交代の前**に見れば
2 と 1 で分岐する。出どころは独立レビュー 2 件・実装者の自己発見 1 件で、**書いた本人の巡回では
見つからなかった。**

### 4. 新旧比較のハーネスが「送った」と「通った」を区別していなかった

S4a の新旧比較は最初「111 ステップ・差 0」と報告した。**timer の受理コマンド 29 種のうち 10 種しか
送っていなかった。** 全種を送るよう直した 2 回目でも 4 経路が「送ったが弾かれていた」
（新旧とも同じエラーで終わるので「一致」と出る）。各ステップに期待（ok / err）を持たせてから、
同型がさらに 4 件出た。

### 5. 巡の回数は独立性の代わりにならなかった

S3 では私が 11 回レビューを回し、**その 11 巡すべてがすり抜けた欠陥を、文脈を共有しない
`/code-review` が拾った**（削除した権限を現在形で書いた docstring）。私は毎巡、消した記号名で
走査しており、**軸の外にある日本語の散文は 11 回とも同じように見えなかった。**
S5a でも、CI・E2E・変異検査・実画面をすべて通したあとに `/code-review` が 9 件を出した
（うち 1 件は実バグ: ルーム作成直後に WS が張り直され `room.join` を二重送信していた）。

### 6. 型検査が拾わないテスト造作と、cwd で効く `.env`

- S4b: wire から項目を落としても、`...host` スプレッドを含むリテラルと戻り値型の無いヘルパは
  余剰プロパティ検査に掛からず緑のまま通った。**実行時の `NOT_IN_ROOM` で初めて分かった**（5 ファイル）
- S2: poker のテストハーネスの cwd が `apps/tasuki-sync` へ移り、開発者が案内どおりに作った
  `.env` を Bun がテストの起動するサーバーへ流し込んだ（**53 件が落ちた**）
