## この Issue が扱ったもの

会の進行表（名前と長さを持つステップの並び）をルームの全員で同じ懐中時計の盤に映し、いまのステップの残りと、
会全体が予定より押しているか巻いているかを見せるツールを、玄関の 5 枚目の札として足した。「自動で次へ」の判断と期限は
サーバーが単調時計で持ち、画面へは送る時点で計った経過を配る。設計正本 §9 の 4 段を 1 本のブランチに積んだ
（利用者の「一気に実装を進める」の指示。PR の本文を段ごとの節に分ける）。

| 段 | 中身 |
|---|---|
| 1 | `packages/agenda-core`（シナリオの検証と展開・進行の遷移・見込み）・wire のスキーマ・ADR 0027・`docs/adr/0011` の分類 |
| 2 | 同期サーバーの経路（`?tool=agenda`・ストア・ハンドラ・専用の期限の予約・破棄・お題の配信先） |
| 3 | `apps/agenda-web`（組む画面・懐中時計の盤・進める画面・映す表示・終了の一覧・端末の保存・音） |
| 4 | 玄関の札・`deploy/agenda`・E2E・文書の残り |

実装で外したこと・決めたことは設計正本 §12 に書いた。ここでは繰り返さない。

## うまくいったこと

- **段ごとの境目で全件の検査を流した**。`pnpm test` / `typecheck` / `lint`・scripts の自己テスト・全 audit・全変異パッチの `git apply --check` を
  PR 1〜3 の終わりにまとめて流し、タスクごとの検査で漏れたものを段の中で拾えた（下の「2.」）
- **レビューが本物の欠陥を拾った**。どれもテストは緑だった:
  飛ばした区画の斜線が CSS の `stroke` に負けて描かれない・端末の保存が読めない版や項目を書き込みで消す・
  Standard Schema の Promise 分岐が fail-open になる・映す表示で見えない操作帯が押せる・一時停止を重ねた積算のテストが無い・
  アンマウント後の `visibilitychange` のテストが恒真・`AgendaError` をエラーの形の検査に登録していない
- **ドメインの不変条件を性質テストで固定した**（所要の合計 ＝ 実時間の経過）。一時停止を所要に含めるか否かは一時停止を挟んだ後でしか
  分かれないので、アサーションをそこに置いた。変異 m430〜m450 は帯を着手時に台帳で確かめ、別セッションの epic #360 と衝突しなかった
- **統括の撮影を段の中に挟んだ**。盤（6 局面）・組む画面・進める画面（375・1280）・映す表示（1920）・終了の画面を撮り、撮影で見つけた欠陥を
  その段の修正に含めた

## 踏んだ罠（事実と再発条件）

### 1. セッションの終了で Task 3.3 の実装役が中断した

**事実**: 盤（`Dial.tsx`・幾何・時打ちの判定）を 1 度に作らせていたところ、前のセッションの終了で実装役が成果物なしで止まった
（HEAD は c7f5b944 のまま、作業ツリーは空）。同じ実装役を再開し、「幾何と判定」「盤」「変異」の 3 段に分けてコミットさせた。
コミットが無いので失ったのは時間だけだった。

**再発条件**: 1 つのタスクに大きな差分（新しい部品・幾何・変異）を束ね、途中でコミットさせない。**大きいタスクは段ごとにコミットさせる。**

### 2. 依存の向きの許可表の漏れが、タスクごとの検査をすり抜けた

**事実**: `apps/tasuki-sync` が `@tasuki/agenda-core` を読み始めたのは Task 2.1 だが、`scripts/audit-dependency-direction.mjs` の許可表に
足していなかった。各タスクの実装役とレビューは触ったパッケージのテストだけを流しており、全 audit は流していなかった。
PR 2 の終わりの全 audit で初めて赤になり、11f0dd56 で直した。

**再発条件**: パッケージ間の新しい依存を足すタスクで、検査を「触ったパッケージのテスト」に絞る。**`package.json` の依存を足したタスクは
`node scripts/audit-dependency-direction.mjs` をその場で流す。**

### 3. 統括のディスパッチが計画と違うことを書いた（m439）

**事実**: 計画 §6 は変異 m439（破棄が agenda を残す）を Task 2.2 で足すとしていたが、統括のディスパッチに「後で足す」と書いた。
実装役はディスパッチに従って足さず、レビューが「m439 が無い」を Important で拾った。計画を正本として同じタスクの修正で足した。

**再発条件**: 統括が計画をディスパッチへ要約するとき、要約の誤りは実装役には見分けられない。**ディスパッチには計画の該当行をそのまま引く。**

### 4. 盤が広い幅で潰れる欠陥は、撮影でしか見つからなかった

**事実**: 単体テスト・a11y の検査・書体の検査はすべて緑のまま、広い幅の進める画面と映す表示で盤が約 180px に潰れ、
終了の画面では盤の SVG が消えて中央の文字が小箱で「KPT のふり…」と切れていた。中央揃えの器の中で `figure` が一行の幅まで縮んだため。
375px では正しく見え、テストは寸法を見ていなかった。針が中央の数字を横切って読めない欠陥も、撮影で見つけた。

**再発条件**: SVG の盤のように中身の幅を持たない部品を、中央揃えの器に置く。**大きさが要の部品は、段組みの全幅（375・1280・1920）と
全局面（開始前・進行・オーバー・一時停止・終了）を撮ってから完了にする。**

### 5. 同時の「次へ」の E2E が、製品の欠陥のように見えて実はテストの競合だった

**事実**: 2 つのページでほぼ同時に「次へ」を押す E2E が「Try の議論」まで 2 段進んで赤になった。送信フレームを見ると、2 つ目のページは
1 つ目の更新を受けてから**新しい `stepId` で**押していた —— Playwright の 2 ページのクリックは同時ではなく、これは正しい操作である。
同じページの 2 連打（同じ `stepId`）で重複を確実に起こし、2 ページの押下は送った `stepId` の種類数で判定する形にした。

**再発条件**: 「同時」を 2 つのクライアントの逐次の操作で作る。**同時性の検査は、送ったものを観測して重複が本当に起きたかを先に確かめる。**

## リリース前の実機確認

テストは手元の時計を止めて局面をフレームで作るので、片道の遅れ・音の解錠・ブラウザの自動再生の制限は見ていない。配る前に実機で見る。

- [ ] **自動で次へ（I-1）**: 1 分の「自動で次へ」の区切りを含むシナリオを 2 つのブラウザで開き、音ありにして放置する。0 で**両方が次へ移り、両方で時打ちが鳴って縁が光る**。最後の区切りを「自動で次へ」にして、終了へ移るときも両方で鳴る。動きを減らす設定の端末でも音が鳴る
- [ ] **音の設定の再読み込み（I-2）**: 音ありにしてから再読み込みする。ボタンが「音を有効に」と出る。1 回押すと「音あり」になり、次の 0 で鳴る。押さずに画面のどこかに触れても「音あり」に変わる

## 教訓

- **段の終わりの全件の検査は、タスクごとの検査の代わりにならないが、その漏れを拾う網になる。** 新しい依存のように「触ったパッケージの外」に
  効く変更は、タスクの中で全 audit を流す
- **見た目の欠陥は撮らないと見えない。** 寸法・重なり・消失は、どのテストも見ていなかった。撮影を段の中に置いたことで、配る前に直せた
- **レビューは「テストが緑」の外を見る役である。** 拾った欠陥のほとんどは、テストが恒真だったか、テストが見ていない経路（CSS の勝ち負け・
  書き込みの側・見えない部品）にあった
- **統括の要約は計画の写しではない。** ディスパッチの誤りは実装役もそのまま実装する。計画の行を引く
