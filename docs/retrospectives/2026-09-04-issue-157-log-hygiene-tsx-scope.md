# 振り返り: ログ衛生の射程に `.tsx` を含める（#157）

- **Issue**: [#157](https://github.com/tomohiroJin/tasuki-tools/issues/157)
- **設計正本**: [`docs/superpowers/specs/2026-09-04-log-hygiene-tsx-scope-design.md`](../superpowers/specs/2026-09-04-log-hygiene-tsx-scope-design.md)
- **日付**: 2026-09-04

## この Issue が扱ったもの

#135 の設計 D7 が「規範の判断」として範囲外にした申し送り（D-3）。**#135 の切り出し 4 本の最後**である。
#135 はログ衛生の走査を 3 → 9 パッケージへ広げたが拡張子は `.ts` に据え置き、代わりに
「走査していない `.tsx` の件数」を出力する E7 を実装した。本 Issue はその出力に決着をつけた。

## 踏んだ罠（事実と再発条件）

### 1. Issue が「決めること」に挙げた規範の判断は、起票の 3 日前に決着していた

**事実**: Issue の「決めること 1」は「ADR 0012 D1 はブラウザの `console` に及ぶか」だった。
ところが ADR 0012 の**初版**（コミット `1b4c8ef`・**2026-08-13**・#136）に、既にこの一文がある。

> ブラウザの `console` は本決定の対象外とする。journal は運用者とサーバーへ侵入した者の
> 双方が読みうるが、ブラウザの `console` は利用者本人しか見ない。脅威が異なるため規律を分ける。

#157 の起票は **2026-08-16**。**完了条件 E1 は起票時点で満たされていた。**

**原因**: #135 の設計（2026-08-16）が「ADR 0012 D1 の解釈は未決」と書き、Issue がそれを
そのまま写した。#135 の側から見れば「自分の Issue では判断しない」であって
「まだ決まっていない」ではなかったが、切り出された Issue では未決として立ち上がった。

**再発条件**: 「別 Issue で判断する」と書いて切り出すとき、**その時点で既に決まっていないかを
確かめない**とき。切り出しは判断の所在を移すのであって、判断が無いことを意味しない。

**対処**: 検査の出力にも同じ揺れがあった（「決定済み。ただし本検査が `.tsx` を走査しない
こと自体の妥当性は別 Issue で判断する」）。**残っていた未決は後半だけ**であり、そこだけを決めた。

### 2. 違反件数が 6 件から 2 件へ減っていた

Issue が挙げた `App.tsx` の 4 件は**現存しない**（#167「web の三層責務」の整理で消えた）。
残っていたのは `History.tsx` の 2 行だけで、**射程を広げる費用は本文の 3 分の 1** だった。

**再発条件**: 「移行費用」を根拠に判断を先送りした Issue が、費用の実測を更新しないまま
時間を置いたとき。**費用は勝手に変わる。**

### 3. 引数を逆に渡した計測が、静かに「違反 0 件」を返した

**事実**: `.tsx` 48 件へ本物の判定を当てる probe を書き、最初に**違反 0 件**を得た。
`grep` では 2 件見えたので食い違いに気づいた。

**原因**: `findViolations(relPath, source)` の引数を逆に渡していた。逆でも例外にならない ——
`relPath` として渡ったファイル本文は `ALLOWED_FILES.includes()` に一致せず、`source` として
渡ったパス文字列には禁止構文が無いので、**静かに 0 件**になる。

**再発条件**: 同じ型（`string`）の引数を 2 つ取る関数を、宣言を見ずに呼ぶとき。
**「0 件」は最も疑うべき結果である。**

**対処**: 別の手段（`grep`）と突き合わせて食い違いに気づいた。数え直した値が 2 件である。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

**拡張子が「サーバか画面か」の代理として働いていなかった。**

| ファイル | ブラウザの `console` | 旧: 検査の扱い |
|---|---|---|
| `apps/timer-web/src/sync/use-timer-sync.ts` | あり | マーカー必須 |
| `apps/timer-web/src/ui/History.tsx` | あり | **自由**（走査対象外） |

**スクリプト自身のコメントが「`.ts` か `.tsx` かは『サーバか画面か』の代理にならない」と
書いているのに、射程は拡張子で決まっていた。** 配線を `.tsx` と `.ts` の間で移すだけで、
検査の対象に入ったり出たりする。

もう 1 つ、**射程を狭める変更を自己テストが止められなかった**。拡張子の判定が収集関数の中に
埋まっていたため、`.ts` だけに戻しても単体テストは全件緑のままだった。宣言
（`SCANNED_EXTENSIONS`）と純粋関数（`isScannedFile`）へ切り出し、**規範の写しをテスト側が
リテラルで持つ**形にして塞いだ。

## 敵対的レビューの指摘（4 件・うち 1 件は再現せず）

**機能上のバグは 0 件**で、4 件はいずれも規範・文書と実装の食い違いだった。
**そのうち 1 件は実測で再現しなかった** —— この作業の連続では初めてである
（直前の 3 巡は 4 / 7 / 4 件がすべて本物だった）。

### 1. 違反メッセージが、自分と反対のことを書いた ADR を根拠に名指ししていた（本物）

`直接の console は使えません（ADR 0012 D1）` は据え置きだったが、射程が `.tsx` へ広がって
**ブラウザ側のコードにもこの赤が出る**ようになった。**ADR 0012 D1 の本文は「ブラウザの
`console` は本決定の対象外とする」と書いている**ので、その根拠だけを指すと
「検査の誤検知だ」と読める。一段厳しくしているのは 2026-09-04 の追記なので、
**直し方（`docs/guides/security.md`）と追記**を出力に足した。

### 2. 「`.mts` / `.cts` は既に走査対象」— **再現しなかった**

指摘は「`isScannedFile` が `endsWith` で判定するので `"foo.mts".endsWith(".ts") === true`
となり `.mts` は既に走査されている」というものだった。実測すると **false** である。
`"foo.mts"` の末尾 3 文字は `mts` であって `.ts` ではない。docstring と ADR の
「足していない」は事実どおりだった。

**指摘が具体的で機序まで書かれていても、前提の算術が違うことがある。**
`node -e` で 1 行流すだけで決着した。

### 3. 生きている EARS を片側だけ直していた（本物）

#135 の設計正本に **E7「走査していない `.tsx` の件数を出力する」** が残ったままだった。
本 Issue はその出力を削除したのに、更新したのは ADR と新しい設計正本だけで、
E7 を持つ文書に超越の印が無かった。**EARS と検査の対応表を突き合わせる次の作業で、
E7 が「未達」として復活する**形である。§3・§4 D7・申し送り表・E7 の 4 箇所へ
日付つきの超越注記を入れた。

### 4. 新しい MUST に対応する手順書が無かった（本物）

ADR 0012 の追記が「ブラウザの `console` は `ALLOWED_FILES` ＋ 行マーカーで通す」を MUST に
したのに、`docs/guides/security.md` は「ロガ経路の対象は `apps/timer-sync` だけです」の
ままだった。**指摘 1 と合わせると、赤を踏んだ開発者が正しい直し方に辿り着けない。**
ガイドへ「画面側に `console` を足すとき」を新設した。

**教訓**: 1・3・4 はすべて「**射程を広げた影響が、実装の外側へ波及していた**」型である。
検査本体は正しく動いていたが、**その赤を読む人が辿る経路**（メッセージ → ADR → ガイド）が
古いままだった。射程を変えたら、赤を読む人の経路を最後まで歩く。

## 敵対的レビュー 2 巡目（4 件・すべて本物）

**1 巡目で入れた案内が、そのまま新しい穴になっていた。**

### 1. 「直し方」の案内が、サーバ側の本物の違反に「許可へ足せ」と誘導していた

1 巡目の指摘 1 を受けて足した 2 行は、**違反の種別を見ずに全部の赤へ出ていた**。
`apps/timer-sync` の本物の違反（ルームコードが journal へ漏れる類）にも
「`ALLOWED_FILES` へ足してマーカーを付ければ通る」と読める案内が出る。

**ADR 0012 が防ごうとしているものを、検査自身が最短の抜け道として提示していた。**
[[countermeasures-carry-the-flaw-they-fix]] の、**対策を直した対策**での再演である。

直し方はサーバ側と画面側で正反対なので、**分類はせず両方を書いた**
（パッケージの分類表を持つとそれ自体が腐る）。あわせて、違反が 1 件も無いとき
（陳腐化した許可・必須ファイルの消失だけのとき）は案内を出さないようにした ——
そちらの直し方は「許可を消す」「走査対象を戻す」であって、どちらの枝でもない。

### 2. 同じガイドの中で、レビュー観点が新しい手順と正面から矛盾していた

`docs/guides/security.md` に「画面側に `console` を足すとき」を新設したのに、
同じファイルのレビュー観点 3 は「`console-log-sink.ts` 以外に `console.*` が
追加されていないか」のままだった。**この観点に従うレビュアーは、本 PR が入れた
`History.tsx` の 2 行をそのまま却下する**（既に許可済みの 3 ファイルも同様）。
**「直したつもりが片側だけ」が 1 ファイルの中で起きていた。**

### 3. ADR 0014 の「影響」節が、削除した出力を現在形で記録したままだった

#135 の設計正本には 4 箇所へ超越注記を入れたのに、ADR 0014 は取り残していた。
**1 巡目で「片側だけ直した」と指摘された修正が、まだ片側だった。**

### 4. 案内した見出しの文字列が、実在の見出しと一致せず grep で辿れなかった

出力は `「画面側に console を足すとき」`、実際の見出しは
`### 画面側に \`console\` を足すとき（#157）`。バッククォートの有無で
`grep` が 0 件になる。**案内どおりに検索した人が辿り着けない。**
出力側を見出しの逐語（バッククォート込み）へ揃えた。

**教訓**: 4 件とも 1 巡目の修正が作った/残したものだった。**「赤を読む人の経路を歩く」と
書いた直後に、その経路の途中で誤誘導していた。** 案内を足すときは、
**その案内が誤って当てはまる場合**を先に探す。

## 塞げなかったこと

- **検査が規範より厳しい。** ブラウザの `console` は ADR 0012 D1 上は自由で、
  マーカーの要求は検査側の判断である
- **許可は増え続ける。** 画面に `console` を足すたびに `ALLOWED_FILES` が伸びる。
  伸びること自体が可視化だが、増えすぎたら決定を見直す
- **`.mts` / `.cts` / `.jsx` は足していない。** 現在 0 件で実需が無い
