# 振り返り: pnpm 供給網設定の退化を検出する（#154）

- **Issue**: [#154](https://github.com/tomohiroJin/tasuki-tools/issues/154)
- **設計正本**: [`docs/superpowers/specs/2026-09-03-supply-chain-config-integrity-design.md`](../superpowers/specs/2026-09-03-supply-chain-config-integrity-design.md)
- **日付**: 2026-09-03

## この Issue が扱ったもの

#135 が「機序も直し方も違う」として範囲外にした 4 経路（⑤版指定の退化・⑥死んだ除外行・
⑦キーと値の綴り誤り・⑫検証の短絡）。#135 の 7 経路が「宣言と実体のずれ」という単一の
機序だったのに対し、こちらは **pnpm の設定の書式と、pnpm の実行そのもの**を見る。

## Issue 本文の前提が 3 点崩れた

**着手前に本文の主張を 1 つずつ実測で叩いた。3 点が現在と食い違っていた。**
本文の実測表は 2026-08-16 のもので、その後 2 つの Issue が現物を動かしていた。

### 1. `overrides` は 1 件ではなく 0 件だった

本文は「`overrides` 1 件（`"nanoid@3": "^3.3.18"`）。⑤ と同型の退化面が 1 つ増えている」と
書いていたが、#199（2026-08-30）が**キーごと削除**していた。E1 の `overrides` 半分は、
現時点で**対象が空の検査**になる。

**入れる判断は変えなかった。** 「起きてから気づく手段が無い」から入れる、という Issue の
判断は対象が空でも成り立つ。ただし PR がその事実を隠さないよう、設計正本と本振り返りの
両方に「守る対象がまだ無い」と明記した。

### 2. ⑫ の機序が違った。短絡は 2 段あり、本文が名指ししたのは 2 段目だった

本文は「`~/.cache/pnpm/lockfile-verified.jsonl` が鍵にしているため飛ぶ」と書き、
リポジトリの記録も「強制するにはキャッシュを消す」としていた。**実測ではキャッシュを
消しても走らなかった**（キャッシュファイルが再生成すらされない＝検証段へ到達していない）。

真犯人は 1 段目の `optimisticRepeatInstall`（既定で有効）で、`Already up to date` を出して
**検証器を作るより手前で return** する。キャッシュはその後ろにある。

| 実行 | `✓ Lockfile passes supply-chain policies` |
|---|---|
| `pnpm install --frozen-lockfile` | 出ない |
| 検証キャッシュ**だけ**消してから同じ実行 | **出ない** |
| `--config.optimistic-repeat-install=false` を付ける | 出る（445 entries） |
| 同じものをもう一度 | 出ない（ここで初めてキャッシュ） |

**「キャッシュを消しても直らなかった」で止めず、pnpm の実装まで降りたのが分かれ目だった。**
`installDeps` の先頭に早期 return があり、そこがストア生成より手前だと読めて初めて、
「消しても再生成されない」という観測と辻褄が合った。

### 3. 本文に無い穴が 1 つあった。CI は検証しているが、誰も確かめていない

本文は CI 側に触れていない。main の CI ログを実際に読むと、
`✓ Lockfile passes supply-chain policies (445 entries in …)` が ci / quality / e2e の
3 ジョブで出ていた（新規チェックアウトでは 1 段目が成立しないため）。

**問題は、その行が出たことを検査している主体がいないことだった。** `node_modules` を
CI キャッシュへ載せる・`--trust-lockfile` が紛れ込む（ADR 0008 の MUST NOT だが機械検査は
無かった）・pnpm の既定が変わる、のいずれでも CI は緑のまま検証をやめる。

## 設計で効いた判断

### 規範が先に道を塞いでいた（自作解析の禁止）

キーの集合をどう取るかで、最初に思いついたのは `pnpm-workspace.yaml` の列 0 を読む
小さなリーダーだった。**ADR-0014 D2 が「`pnpm-workspace.yaml` を手で解析してはならない
（MUST NOT）」と既に決めていた**（手書きの字句解析が 3 回続けて検出漏れを作った前科による）。

そこで `pnpm config list --json` を 2 か所（リポジトリ直下と、同じ `packageManager` を
書いた素のディレクトリ）で走らせ、差分を取る形にした。実測でちょうど 5 件
（`allowBuilds` / `minimumReleaseAge` / `packages` / `trustPolicy` / `trustPolicyExclude`）が
得られ、`pnpm-workspace.yaml` の中身と一致した。

**規範に従った結果、検査が強くなった。** この形は `.npmrc` など別の場所から供給網設定が
入る経路も「未知のキー」として捉える。ADR 0008 の「設定の置き場は `pnpm-workspace.yaml` の
1 箇所のみ」という MUST に、初めて機械検査が付いた。自作リーダーではこれは見えなかった。

### 全単射に倒しきらなかった

#135 の道具（`diffTargets`）は「宣言と実体の全単射」だが、**除外リストは空・不在が正しい
状態でありうる**。`trustPolicyExclude` を必須にすると、最後の 1 件が不要になって行ごと
消したときに赤くなる。#126 は `minimumReleaseAgeExclude` で、#199 は `overrides` で、
実際にその道を通っている。

presence を required / optional / forbidden の 3 段にした。**0 件ガードも設定キーだけに
掛け、除外と overrides には掛けない。** この判断が後から緩まないよう、
「除外が 0 件でも緑になる」ことを配線テストで固定した。

### 実経路を判定する（合成した経路を判定しない）

⑫ の検査には 2 案あった。(a) 検査スクリプトが自前で
`--config.optimistic-repeat-install=false` 付きの install を走らせる、(b) CI が実際に走らせる
install を包む。**(b) を採った。** (a) が確かめるのは合成した経路であり、`node_modules` を
CI キャッシュへ載せた瞬間に「合成側は緑・実経路は無検証」になる。

その代償として、ラッパを手元で叩くと `node_modules` が温まっている限り落ちる。
これは欠陥ではなく「このインストールでは検証が走らなかった」という正しい報告なので、
そう読めるメッセージ（2 段の短絡と、それぞれの外し方）を出すようにした。

## 踏んだ罠

### 「壊れたこと自体」の判定が、関数定義まで数えていた

配線テストで `checkExclusionFormat(key, entries)` の出現数が 0 になることを確かめようと
したが、**同じ字面が `export function` の側にもある**ため、呼び出しを壊しても 1 件残って
「呼び出しを壊せていません」で落ちた。呼び出しの行ごと
（`problems.push(...checkExclusionFormat(key, entries));`）数える形へ直した。

**破壊検証は、壊し方自体を確かめる段があったから止まった。** その段が無ければ
「壊したつもりで壊れていない緑」をそのまま通していた。

### zsh の無引用展開で自己テストが 1 件も走らなかった

`node --test $targets` を既定シェル（zsh）で叩いて `Could not find '…改行を含む 1 つの名前…'`
になった。ガイドが `bash -c` で包めと書いている理由そのもので、**既知の罠を書いてある
とおりに踏んだ**。

## レビューの指摘（`/code-review high`・4 件＋注 1 件）

**4 件すべてが本物だった。** ただし 1 件は「機序は実在するが、示された具体シナリオは
到達しない」ものだったので、そこは実測して切り分けた。

### 1. 名前パターン付きの除外が、直し方の食い違う 2 行を出した

`main()` は実在確認に渡す名前から `*` 付きを外していたが、`findDeadExclusions` へは
**フィルタしていない `entries` をそのまま**渡していた。`"semver-*@6.3.1"` で実測すると
「名前@版 で書いてください」と「行を消してください」が並ぶ。**自分のコメントが
「二重に責めない」と書いている真下で二重に責めていた。** 判定を純粋関数の側へ寄せた。

### 2. `process.exit()` が、このラッパが出す説明を切り落としうる

子プロセスの出力を `process.stdout.write` で流した直後に `process.exit` を呼んでいた。
stdout がパイプのとき（＝CI）その書き込みは非同期で、`process.exit` は残りを捨てる。
**捨てられるのは「検証が走らなかった」という 14 行の説明そのもの**で、
このラッパが防ぐはずの失敗と同じ形になる。`process.exitCode` へ変えた。

### 3. 必須キーの判定が、在るものを「ありません」と言いうる

`deriveOwnKeys` は素の環境と値が同じ鍵を落とすので、必須キーの値がたまたま環境側と
一致すると差分から消え、「必須の設定キーがありません」と**事実に反する**ことを言う。

**指摘された具体シナリオ（利用者の `~/.npmrc`）は再現しなかった。** 偽の HOME を作って
実測したところ、pnpm 11.5.0 は `.npmrc` も `npm_config_*` もこれらの設定に使わない
（ADR 0008 が「`.npmrc` には書かない（実測で無視される）」と書いているとおりだった）。
**それでも直した。** 機序はコードに実在し、直すと検査が事実を言うようになるため。
未知は「持ち込んだ鍵」、必須の欠落と禁止は「実効設定」で見る形へ分けた。

### 4. `pnpm why` の失敗を空配列へ丸めていた

`catch` で `error.stdout ?? ""` → `[]` としていた。pnpm は「依存木に無い」を
**exit 0 ＋ `[]`** で表す（実測）ので、非ゼロは本当の失敗である。それを空配列へ丸めると
**すべての除外が「依存木に無い」と判定され、「行を消してください」という誤った指示を出す**。
消せば `pnpm install` が全員分壊れる。解釈できない出力は例外にした。

### 注: 「`pnpm install` 済みを要求する」は言い過ぎだった

`node_modules` の無い新規 worktree で `pnpm config list --json` も `pnpm why -r --json` も
exit 0 で動き、後者は `semver@6.3.1` を返した。**`pnpm-lock.yaml` があれば足りる。**
ADR-0014 D2 が `check-links` に課した制約（`pnpm -r list` は install 済みを要求する）を、
確かめずに隣の道具へ広げていた。規範文書 4 箇所を訂正した。

**教訓**: 3 と注はどちらも「**既存の規範から類推して、確かめずに書いた**」ものだった。
1 と 2 は「自分で書いたコメントの主張を、実装が満たしていなかった」型である。

**破壊検証は 7 種の設定破壊 ＋ 実経路 3 通りで実施した。** 対照実行（壊さずに緑になること）を
先に取り、すべて期待どおり非ゼロで終了して当該エントリを名指しした。実経路は
「素のまま＝赤（1 段目）」「1 段目だけ切る＝赤（2 段目）」「2 段とも切る＝緑（445 entries）」の
3 通りで、短絡が 2 段あることを検査の側からも再現した。

変異検査は 21 件すべて検出（新規 2 件を含む）。

## 塞げなかったこと

- **`"*"` 単独の除外は「版を持たない形」として落ちるが、名前パターン全般を禁じてはいない。**
  pnpm の `createMatcher` が受ける表記を網羅的に判定してはいない
- **目撃者は `quality` ジョブ 1 つだけ。** そのジョブを消せば E4 の判定も消える。
  ジョブの存在自体は検査していない
- **`overrides` と `minimumReleaseAgeExclude` は現在空。** 書式検査は走るが守る対象がまだ無い
- **pnpm の出力文言に依存している。** `passes supply-chain policies` の文言が変われば
  E4 は赤くなる（偽陰性ではなく偽陽性の側へ倒れるので、安全側ではある）
