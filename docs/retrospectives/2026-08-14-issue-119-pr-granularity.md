# 振り返り: PR の粒度を定める（#119）

**対象**: Issue #119（PR の粒度を定める）
**ブランチ**: `docs/119-pr-granularity`（PR #140・`main` への統合はまだ）
**期間**: 2026-08-14（設計から実装まで同日）・merge-base `e01f5b1` から 10 コミット（本振り返りのコミットを含まない時点）

## 踏んだ罠（事実と再発条件）

### 1. Issue 本文の前提のうち 3 点が着手時に成り立たなくなっていた

**事実**: Issue #119 は 2026-08-11 に起票されたが、着手（2026-08-14）までの 3 日間に
#70 / #116 / #136 が先に動き、本文の主張のうち 3 点が古くなっていた。

1. 「CI 3 ジョブの完了を待つ（実測 3〜3.5 分）」— #70（2026-08-12 完了）で CI が
   3 → 5 ジョブに再編され、文書のみの PR は 20 秒になった
2. 「DoD 8 項目のうち多くが『該当なし』だが、毎回書く手間がある」—
   `docs/guides/definition-of-done.md` と `.github/pull_request_template.md` の両方に
   「該当しない項目は『該当なし』と明記してよい」が既に書かれていた
3. 完了条件「#113 の実装計画を粒度に合わせて改訂したか」— #113 は 2026-08-11 に
   完了・クローズ済みで、改訂対象の計画は既に実行し終えていた

**測り方を誤って誤った反証を立てかけた**: 前提 1 を検証する過程で、いったん
「CI はまだ 122 秒かかっている」という反証を立てた。これは `gh run list` の
`startedAt`（キュー待ちを含む）を使った誤測定によるもので、`createdAt` → `updatedAt`
で測り直すと実際は 20 秒だった（run `31562015113`）。この疑いはコミット `8e1c3fa` で
取り下げた。

**再発条件**: Issue の起票から着手までに日数が空くと、その間に運用が先に動いて本文の
前提が古くなる。着手前に本文の主張を 1 つずつ実測で叩き直さないと、既に解消済みの問題を
解決しようとして無駄な設計をする。CI の所要時間は `startedAt`（キュー待ちを含む）ではなく
`createdAt` → `updatedAt` で測らないと、待ち時間を過大に見積もる。

**対処**: 設計書 §1.1 に「いま成り立たないもの」として 3 点を明記し、Issue 側の完了条件は
「改訂不要」の理由つきで閉じた。CI 所要の測り方は `createdAt` → `updatedAt` に統一した。

### 2. 設計の self-review が片側しか直せていなかった（F3）

**事実**: 自分で書いた spec を敵対的に検証したところ（コミット `8e1c3fa`）、ADR 決定 2
「『1 つの論理的変更』は Issue 1 件を指す（MUST）」が、憲法 原則 IX ①「1 PR は 1 つの
論理的変更に**留める**」という**上限規定**と噛み合っていないことが判明した。決定 2 を
**等号**で書くと、1 つの Issue を複数 PR に分割した場合、分割後の各 PR は「Issue 1 件」
ぴったりではなくなり MUST 違反と読めてしまう。

最初の self-review では**憲法側だけ**を「留める」＝上限規定と読み直し、ADR 決定 2 の
等号はそのまま残していた。敵対的検証（F3）で再検出し、決定 2 も「1 本の PR に複数の
Issue を混ぜない（MUST）」という上限の形に書き換えて解決した。

**再発条件**: 憲法・ADR・ガイドのように相互参照する複数文書を同時に改版するとき、
矛盾を 1 か所直しただけで安心すると、参照先の別文書に残っている食い違いを見落とす。
「規定の形（上限か等号か）を揃える」という視点を持たずに文言だけ直すと再発する。

**対処**: ADR 0013 決定 2 を上限形に書き換え、「決定 1（SHOULD）と決定 2（MUST）が
衝突しない理由」を ADR 本文に節として明記した。

### 3. 修正の再検証で、自分の修正が新しい矛盾を作っていた

**事実**: 罠 2（F2）の修正として「ADR とガイドに同じ数値表を持たない」ため実例表の
正本をガイドに定めた。ところがこの修正が、spec §2「本節が数値の正本であり、実装計画・
タスク・ADR・ガイドは本節から引用し数値そのものを転記しない」という既存の記述と衝突する
矛盾を新しく作り込んでいた。再検証で気づき、コミット `8e1c3fa` で
「作業文書（spec）の正本は §2」「成果物（ガイド）の正本は §3.4」と役割を分けて整理した。

**再発条件**: 「二重正本を作らない」ために片方を正本と定め直す修正は、その文書自体の
別節に既にある「正本はここ」という別の宣言と衝突しうる。修正した節だけを見て安心すると、
同じ文書の他の節との整合を見落とす。

**対処**: 修正後に文書全体をもう一度通しで読み、役割（作業時点の記録 vs 今後参照され
続ける成果物）で正本を使い分ける形に整理した。**直したあとに必ずもう一度読む。**

### 4. 憲法 Governance の Constitution Check ゲートが実運用で空文化していた

**事実**: 憲法 Governance は「すべての plan は Constitution Check ゲートを通過しなければ
ならない（MUST）」と定めるが、`docs/superpowers/plans/` の全 36 件中、実際にこのゲートを
持つのは 4 件のみ（`2026-08-09-governance-and-docs.md` /
`2026-08-10-dependency-supply-chain.md` / `2026-08-11-major-dependency-updates.md` /
`2026-08-14-pr-granularity.md`）。最新かつ最大規模の
`2026-08-13-security-norms.md`（#136・11 タスク）にすら無い。

**再発条件**: MUST を検査する仕組みが無いと、規範と実装の乖離は誰も気づかないまま蓄積する。
plan テンプレートに任意の節としてゲートが存在するだけでは、書く側が省略しても検出されない。

**対処**: 本作業の実装計画（`docs/superpowers/plans/2026-08-14-pr-granularity.md`）には
Constitution Check ゲートを実際に設けた。全体の空文化そのものは未解決のため #135 へ申し送る
（後述）。

### 5. `AGENTS.md:36` が #136 の時点で既に古かった

**事実**: `AGENTS.md` の文書地図は「ガイド: 今日どう書くか（DoD・EARS・振り返り・
アーキテクチャ・開発手順）」と 5 本を列挙していたが、`docs/guides/security.md` は
#136（2026-08-13）で新設済みだった。`docs/README.md:24` 側は 6 本（security を含む）で
正しく、`AGENTS.md` だけが取り残されていた。**リンク切れではないので `check-links` は
検出しない種類の腐りで、本作業が粒度ガイドを 7 本目として足すまで誰も気づかなかった。**

**再発条件**: ガイドの本数を文書内に名前で列挙する箇所が複数あると、1 か所を更新しても
他が追随せず、数え上げが箇所ごとに腐る（`count-in-prose-goes-stale.md` と同型）。

**対処**: 本作業で `AGENTS.md` の列挙を 7 本（security・PR の粒度を含む）に是正した
（コミット `3560c56`）。#136 の積み残しの回収でもある。

### 6. 壊し方が効いていないのに緑を見て安心する空振りを、計画作成中に 2 度踏んだ

**事実**: 破壊検証（わざと壊して赤を確認する手順）を設計する過程で、以下の 2 回、
壊したつもりが実際には差分に反映されていない空振りを踏んだ。

1. ガイドの拡張子なしパス表記を壊そうとしたが、置換対象の文字列が存在せず sed が
   何も変えていなかった
2. 憲法に存在しないパス名を sed で置換しようとしたが、同様に対象が無く空振りした

**再発条件**: `sed` によるテキスト置換は、対象文字列が存在しなくてもエラーを出さずに
終了する。置換後に検査だけ実行すると、「検査が通った」のか「そもそも壊れていない」のかを
区別できない。

**対処**: 以後、全タスクの破壊検証手順に `grep -c` で置換が実際に効いたこと（件数が
1 以上）を先に確認する手順を入れた（Task 1 Step 4・Task 3 Step 7 で実施）。

### 7. 自己参照の測定問題（ADR の実測記録）

**事実**: ADR 0013 に「本決定を適用した最初の PR（#140 自身）の実測」を記録しようとした
際、実測値を記録するコミット自体が PR の差分・コミット数を増やすため、**記録した瞬間に
その値が古くなる**という自己参照の問題が生じた。実際、実測表を追記した直前のスナップショット
（8 コミット・差分 1,160 行）と、追記コミットを含む最終値（9 コミット・差分 1,175 行）が
食い違った。Task 5 のレビューで Important として指摘され、表の直後に「この表は追記直前の
実測であり、追記コミット自体の差分は含まない」という注記を足すことで解決した
（コミット `3d051ac`）。

**再発条件**: 「この PR 自身を実測台にする」という自己適用の設計は、記録行為そのものが
測定対象を変化させる。計画のテンプレートに、この種の自己参照が起きうる作業への注記スロットが
無いと、実装者は気づかないまま矛盾した数値を記録する。

**対処**: 実測表の直後に自己参照の注記を追加した。以後、成果物が自身の差分を含む形で
実測を記録する作業では、注記の要否を計画段階で検討する。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

### `check-links` は git 追跡下のファイルしか走査しない

**何が緑だったか**: `scripts/check-links.mjs` は走査対象・存在判定のいずれも
`git ls-files`（`trackedPaths()`、238〜243 行目・`main()` 内 250 行目の
`gitList(["ls-files", "*.md"])`）に基づく。**この設計自体は意図的**で、
217〜223 行目のコメントに理由が明記されている（gitignore 対象のファイルが手元には
あって CI のフレッシュな checkout には無いため、ファイルシステムを見ると
ローカルと CI で結果が食い違う。PR-2 の初回 CI で実際に踏んだ）。

**なぜ検査の穴になるか**: 設計意図は正しいが、副作用として **`git add` する前の新規文書は
走査対象にも存在判定対象にも入らない**。新しく書いた未追跡の Markdown にリンク切れや
壊れたパス表記があっても、`node scripts/check-links.mjs` をローカルで実行すると何も検出せず
緑になる。ステージしてようやく検査対象になる。

**対処**: 本作業では影響しなかった（各コミットで都度 `git add` してから検査した）。
仕組みそのものの改善は行っていない。#135 へ申し送る。

### `check-links` のコードパス検査は拡張子つきの表記しか見ない

**何が緑だったか**: `isRepoPathLike()`（`scripts/check-links.mjs:107-113`）は
バッククォート内のテキストが拡張子つき（`/\.[a-z0-9]+(:\d+(-\d+)?)?$/i`）でなければ
「参照記法（ADR 番号の接頭辞など）」とみなし、検査対象から除外する。憲法
（`.specify/memory/constitution.md`）には `` `docs/adr/0002` `` `` `docs/adr/0011` ``
のような拡張子なし表記が実測で **8 箇所**ある（先行コミット `3900654` のメッセージは
「6 箇所」と記載していたが、同コミット時点の内容を再カウントすると既に 8 箇所だった。
記録時点の数え間違いと判明したため、本振り返りでは実測値 8 箇所を正とする）。

**なぜ検査の穴になるか**: 拡張子なし表記は現時点ではすべて実在する ADR を指しており
無害だが、`isRepoPathLike` の除外条件に該当するため**存在判定そのものが行われない**。
ADR がリネーム・統合されて番号が変わっても、この検査は気づかない。

**対処**: 本作業では影響しなかった（新設した ADR 0013 は拡張子つき表記で参照した）。
仕組みそのものの改善は行っていない。#135 へ申し送る。
