# #574: E2E の時刻採取・演出待ち・休憩の最初の描画

Issue: [#574](https://github.com/tomohiroJin/tasuki-tools/issues/574) / PR: [#581](https://github.com/tomohiroJin/tasuki-tools/pull/581)

## 初回対応で変えたこと

- 休憩テストはクリックを送る前と、両画面を確認した後に Playwright から残りを読んでいた。検査の往復の間にも時計が進み、その時間まで休憩中の消費として比較していた。クリックの capture リスナーと、時計が消えた後に戻る最初の描画の MutationObserver で、ブラウザ内で値を採る形にした。元の下限 `>= -1`、実時間3秒の休憩、両文脈の覆いと時計の検査は維持した。
- レイアウトの検査は、走っている有限演出を `Animation.finish()` で終端へ送り、finish イベントと画面更新のため2フレーム待ってから測る。無限・一時停止・非表示の演出は対象にしない。製品の演出、判定値、retry、skip、既存の制限時間は変更していない。
- Issue に併記された320pxの長い名前の休憩表示も全件で再現した。上端の帯の下端の測定を `useLayoutEffect` へ移し、覆いの最初の描画前に余白へ反映する。これは実画面の初回配置の修正である。

## 原因を確かめたこと

- 検査側が遅れる場合を作るため、クリック前と結果を読む前にそれぞれ1.2秒待った。修正前の休憩テストは差 -2 で赤、修正後は単独3回成功した。
- 修正前のタイマー画面テストは単独40.4秒、全件内47.9秒だった（開始時のチェックアウト89f100f1）。
- 最新 main 8d5c0f46 の演出補助を独立作業ツリーで計測した。60秒でまとめの表示待ちに到達して落ちた時点で、演出待ちは36回、合計32,976ms、最長3,349ms。今回観測した失敗は、1本が永久に止まったのではなく、有限の待ちの累計が全体の制限を圧迫するものだった。型検査等も動いていた測定なので、速度の定量比較には用いない。
- 閉じた details の中では、100msの遷移の playState が finished になっても finished Promise が500ms後に未解決であることも、指定版Chromiumの単体プローブで確認した。今回の全件の失敗原因として観測したものとは分ける。
- 最初の既定設定の全件は281件成功、320pxの長い名前の休憩表示1件失敗だった。見出しの中心に当たった要素は、通常の「休憩を始めました」の知らせ（app-banner-warn）。単なる負荷の警告ではなかった。上端の帯の測定が描画後になる経路に、描画前の契約テストを足すと赤になった。
- 描画前の契約は、休憩無効から有効へ変えたときの layout effect でCSS変数を読む。修正前は期待 `['', '200px']` に対し `['', '']`。修正後は対象単体11件と、短い名前・長い名前の320px E2E各5回、計10件が成功した。

## 変異と独立レビュー

実装とは別のエージェント review_574 に、Issue・ブランチ・基準を渡した。独立作業ツリーで最初の変更と描画前測定の追加差分をレビューし、再現できた欠陥は0件。

- 有限演出の終端は幅100px。無限はrunning、一時停止はpausedを維持した。finishを無効にする手動変異では幅が約50pxとなり、状態と寸法の検査が検出した。
- evolveBreakEnded で再開時の secondsLeftAtAnchor だけ2秒減らす手動変異は、通常の3秒の休憩で4回、休憩を3500msにした試行で3回、すべて差 -2 で検出した。通常の別の1回は Given の表示待ちで落ちたので検出回には数えない。
- 再開の最初の描画が古い now を使うため不正消費を隠す懸念は、上記試行では再現しなかった（記録のみ）。
- 変異1440は描画前の測定を通常のeffectに戻す。新規契約1件だけが赤、既存10件は成功。実装側とレビュー側で独立に検出した。初回の番号1435は別作業の予約帯だったため1440へ付け替え、付け替え後にも検出を確認した。

E2Eのspecは既存の変異ランナーの対象（vitestのtests/）に載らないため、最初の2種類は実ブラウザで手動変異を行った。製品フックの変異1440は宣言とパッチを残した。変異は検査後に戻した。

## 2026-11-11: PRレビューへの対応

[外部の敵対的レビュー](https://github.com/tomohiroJin/tasuki-tools/pull/581#issuecomment-6772482400)で、休憩明けの古い時刻が2秒の不正消費を隠す条件が報告された。上の「再現しなかった」は少数回の実ブラウザ試行の記録であり、位相に依存する検出力の証明にはならなかった。初回の全件5回成功だけでは、この穴を検出できていなかった。

1. 実物の `useNowTick`・`secondsLeft`・表示用の丸めと整形を使い、休憩3000・3100・3500・3900ms、消費0・2秒、秒内10ms刻み100通りの計800条件を恒久テストにした。修正前は3100msで10/100、3500msで50/100、3900msで90/100の2秒消費が差 -1 となり、E2Eの下限を通った。消費0でも同じ割合で表示が1秒増えた。再開する描画の前に現在時刻を取り直すようにし、全位相で0秒は増減なし、2秒消費は差 -2 となることを確認した。
2. 休憩中に知らせを別の描画で追加する単体を足すと、期待する帯の下端200pxに対し古い95pxが残って赤になった。DOM更新ごとにlayout effectで測り、継続的な観測は張り直さない形にした。実ブラウザでも、実サーバーの休憩開始の知らせだけを一時保留し、snapshotで覆いが出た後に渡す条件を作った。知らせの最初のDOM更新をMutationObserverで採り、ResizeObserver待ちの前にも余白と見出しの当たりを確かめる。
3. 非表示でも `document.getAnimations()` に含まれる演出を作り、その前提を確かめた上で終端へ送られないことを検査する。非表示の演出が収集されず空振りする場合は前提の失敗として止める。
4. 恒久的な1.2秒の待ちを前後とも削除した。秒境界に揃う3000msだけに依存しないよう、実時間の休憩は3500msにした。元の下限 `>= -1`、両文脈の検査、retry・skip・既存の制限時間は維持する。

追加修正の検証状況:

- 実ブラウザの対照実行は4件すべて成功。非表示の選別を削る変異はhiddenの状態がrunningからfinishedになり検出した。別コミットで測り直す処理を戻す変異は、知らせの最初のDOM更新で余白が足りず検出した。
- 実サーバーで休憩明けの残りを2秒減らす変異は5回すべて、期待 `>= -1` に対し差 -2 で検出した。Givenの失敗はなく、5回とも時間比較で赤になった。変異は独立作業ツリーだけで行い、終わりに戻した。
