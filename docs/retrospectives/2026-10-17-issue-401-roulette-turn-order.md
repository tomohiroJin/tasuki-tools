## この作業が扱ったもの

回すたびにまだの人から 1 人の番が決まり、選ばれた人は円盤から抜けていく決め方（順番に回す）を足した。最後の 1 人は回さずに出し、
円盤を空にして回を終える（案 A）。あわせて脇を「決め方」「ルーレットに入る人」「仲間を招く」の 3 つの面に整理した。
利用者の方針は「いったん実装してから考える」。細部（設計正本 §7）は触ってから決める。

## 踏んだ罠（事実と再発条件）

### 1. 「だんだん減っていく」を「最後に残った人が当たり」と読んだ

**事実**: 初版の設計とモックは、抜けていって最後に残った人を「次の進行役」にする形だった。利用者の意図は「発表者がルーレットで決まり、
発表した人は抜けていく」で、選ばれた順そのものが結果だった。設計をやり直した。

**再発条件**: 提案の言葉（「1 人ずつ抜けていく緊張感」）が、既存の画面の結果（次の進行役 1 人）に寄せて読める。使う場面
（何のために回すか）を利用者に確かめる前に、既存の結果の形へ当てはめる。

### 2. 選ぶ人数の切り替えで、選んでいるボタンが見分けられなかった（#415 の見落とし）

**事実**: #415 は「選んだ状態の色と枠は部品（副のボタン ＋ `aria-pressed`）が持つ」としていたが、部品は `aria-pressed` を飾らない。
モック 3 版で決め方のボタンを並べて気づき、topic-web と同じ金の敷きと内側の線を画面の CSS で当てた。

**再発条件**: 部品の振る舞いを確かめずに「部品が持つ」と書き、テストは `aria-pressed` の属性だけを見る（見た目は見ない）。

### 3. 2 列にしたはずの決め方のボタンが、4 列の器で丸く潰れた

**事実**: 決め方のボタンは選ぶ人数の並び（`.roulette-pick-options`・4 等分）を借り、`.roulette-mode-options` で 2 等分にした。
CSS の中で 2 等分の規則が 4 等分より前に書かれ、同じ詳しさなので後ろの 4 等分が勝った。モックは別の CSS を後から読んでいたので出なかった。
実画面を撮って気づき、2 つのクラスを重ねて詳しさで勝たせた。

**再発条件**: モックで足した CSS を本物の CSS の別の位置へ移す。読み込みの順が変わる。

### 4. 変更した行の近くにある、以前の変異のパッチが当たらなくなった

**事実**: 変異の検査で 7 本（153・173・181・184・202・305・309）が `git apply` に失敗した。同じ変異を今のファイルに当て直してパッチを作り直した。

**再発条件**: 変異が当たる関数のすぐ近くを書き換える（パッチの前後の行が変わる）。

## 検査の穴

- **選んだ状態の見た目は単体テストでは見ていない**（jsdom は CSS を当てない）。実画面の撮影で見た。変異も置いていない
- **E2E はこの作業環境で流せなかった**（Caddy が無い）。同じルームの通しに足した順番に回す場面は CI の `e2e` に任せた
- 「1 回で決める」の舞台は、変更の前後を 320・768・1440 の 5 場面で撮り、画素まで一致を確かめた
