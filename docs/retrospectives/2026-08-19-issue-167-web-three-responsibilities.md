# 振り返り: web 層を「純粋関数・同期フック・画面」の 3 責務へ再編する（#167）

- 対象: Issue #167（#72 の E4）
- 期間: 2026-08-19
- 成果: `apps/timer-web/src/App.tsx` の WS 配線・状態・判断ロジックを
  `src/sync/use-timer-sync.ts`（同期フック）・`decideSnapshotIntents`（純粋関数）・
  `createCommands`（純粋ファクトリ）・`useBanner` / `problem-text.ts` へ分離。
  機械検査 `scripts/audit-web-sync-boundary.mjs` を新設。

## 0. この Issue の戦略

E4 は `App.tsx`（849 行）から WS 配線を丸ごと 1 本のフックへ移す、この Issue の中で
最も危険度の高い移動だった。着手前に実測すると、既存テストが観測していた送信コマンドは
`problem.request` の**1 種だけ**で、接続状態表示（EARS 2）は `StatusStrip` などの部品単体は
緑でも `App.tsx` からの配線を守るテストが無かった（配線が死んでいても検査は緑になる状態）。

このため計画は「大移動の前に安全網を張る」順序を取った。Task 1・2 で送信配線と接続状態表示を
先に固定する特性テストを足し、Task 3〜7 の各移動でその網が緑を保つことを条件にした。
Task 6（本体の大移動）は既存テストを 1 行も書き換えずに通過し、これが「振る舞いが変わって
いない」ことの直接の証拠になった。

## 1. 対照実行が繰り返し穴を暴いたこと

このリポジトリの方針どおり、破壊検証は「壊す前」と「壊した後」の両方を確かめる形で
繰り返し実施した。3 件が実際に穴を見つけている。

- **Task 4**: 切断バナーの自動消去（`autoDismiss`）を無効化する変異を入れても、
  当時の `App.connection.test.tsx` は実時間を進めない作りのため検出できなかった。
  切断バナーが 4 秒で消えるようになっても誰も気づかない実在の穴で、修正ラウンドで
  偽タイマー（fake timers）を使う検証を新規ファイルとして足した。
- **Task 5**: `decideSnapshotIntents` が返す意図 8 種のうち、App 配線レベルで守られて
  いたのは 4 種（save-resume / join-rotation / clear-generating / set-screen）だけだった。
  残り 4 種（consume-driver-join / request-problem / regenerate-problem /
  persist-completion）は適用を握り潰しても既存テストが 1 件も落ちない、変更前から
  無防備な状態だった。App レベルの肯定テストを新規ファイルとして足し、8/8 検出まで引き上げた。
- **Task 9**: 完了条件 4（変異検査で既存テストが恒真化していない）の実測で、
  用意した 13 種の変異すべてを検出した。対照実行（変異前は緑であること）も 13 件全数
  確認した上での結果であり、「テストを 1 件も走らせず全件『検出』」という過去の事故
  （`checks-need-a-control-run`）と同型の誤りではないことを確かめている。

## 2. 検査の無力化の最短経路（実測）

新設した `scripts/audit-web-sync-boundary.mjs` に対して、Task 9 で無力化の最短経路を
実際に試した。`App.tsx` へ `SyncClient` の直接 import を 1 行挿入すると検査は NG
（赤）になるが、検査本体の `allowedImporters`（許可リスト）へ `"src/App.tsx"` を
1 行足すだけで、本体の判定は**無傷で NG → OK へ素通りした**。

ここで想定と食い違う実測結果が出た。検査スクリプトの docstring は「自己テストも
素通りする」と書いていたが、実際に `node --test scripts/audit-web-sync-boundary.test.mjs`
を走らせると、`allowedImporters` の中身をちょうど 2 要素の配列として `deepEqual` で
固定するテストが `not ok` になった。**docstring は防御を実際より弱く書いていた。**
無力化の最短経路は「検査本体だけなら 1 行で素通りするが、自己テストまで含めると
CI 上は赤のまま残る」という、想定より少しだけ強い防御線だったことになる。

## 3. 依頼者（私）が設計・計画に作り込んだ欠陥は、同じ型の誤りだった

この Issue の設計・計画段階で、私は量を含む主張を 3 回書き、3 回とも実装や実測の段階で
訂正が入った。

| 主張 | 私が書いた値 | 実測値 | 原因 |
|---|---|---|---|
| 送信箇所の数 | 32 箇所 | **35 箇所** | grep パターンが `c.send` の形に当たらなかった |
| snapshot 受信時の意図の種類 | 7 種 | **8 種** | 設計正本の意図名が実装名からドリフトしていた（`consume-driver-join` が抜けていた） |
| `Date.now()` の用途 | 「全量で見て 4 用途のみ」 | **実際は 6 用途**（clockOffset 推定・未使用の `get now()` を含む） | 測定時に `client.ts` を `grep -v` で明示的に除外していたにもかかわらず、結果を「全量」と断定した |

3 件はいずれも独立した現象に見えるが、共通点は同じである。**量化を含む主張を、測り方
そのものを確かめずに書いた。** grep のパターンが実物の字面と一致するか、設計文書の
用語が実装と同期しているか、集計対象から除外したファイルがあるかを検証せずに、
出てきた数をそのまま断定に使っている。3 番目（Date.now）は特に、除外の事実を自分で
コマンドに書きながら結果の記述からは消えており、最も再発しやすい形だった。

この教訓を踏まえ、Task 10 では ADR-0003 への追記を「4 用途のみ」という量化から、
「状態を進めるものが無い」という**性質**を主張する書き方へ直した（列挙は腐る。
`enumerations-rot-name-the-mechanism` と同型）。

## 4. 新設した検査が、自分が塞ぐ欠陥と同じ欠陥を持っていたこと

`audit-web-sync-boundary.mjs` の初版レビューで、ADR-0014 決定 1 が求める全単射照合
（走査対象と宣言済みアプリの一致確認）が抜けていることが分かり、修正ラウンドで足した。
ところがその**修正自身**に、それを守る配線テストが無かった。

Task 8 の 2 回目の修正ラウンドで検証したところ、全単射照合のコードを変異（削除）
させても、自己テスト・配線テストのどちらも全緑のままだった（グリーンのまま壊れている
状態）。これは C1・C2 のレビューで確立したばかりの規範——「判定ループと実在確認の
配線を守るテストを持つ」——から、その規範を実装するための修正自身が外れていたことを
意味する。このリポジトリが繰り返し記録している「対策は自分が塞ぐ欠陥を持つ」
（`countermeasures-carry-the-flaw-they-fix`）と同型の事例であり、変異テストを追加して
解消した。

## 5. 移設が既存の検査を 1 つ赤にしたこと

Task 6 で WS 配線を `App.tsx`（`.tsx`）から `use-timer-sync.ts`（`.ts`）へ移した直後、
`scripts/audit-log-hygiene.mjs` が赤になった。原因は単純な移動ではなく、この検査の
走査対象の決め方そのものにあった。

`audit-log-hygiene.mjs` は各パッケージの `src/` 配下の**`.ts` のみ**を走査し、`.tsx` は
「ブラウザの console は ADR-0012 D1 で対象外」という理由で意図的に除外している。
`App.tsx` にあった `console.error` 4 行は、拡張子が `.tsx` である間は検査の外にあった。
ところが同期フックへ移した先は JSX を持たないため必ず `.ts` になり、**中身も用途も
変わっていないのに、拡張子が変わっただけで走査対象に入った。**

ここでの発見は、この検査にとって**拡張子が「サーバ側コードか画面コードか」の代理変数に
なっていない**という構造的な事実である。ADR-0015 の MUST 2 が求める同期フックは
定義上 JSX を持たない `.ts` ファイルであり、配線を集約するという設計そのものが、
この検査の除外条件をすり抜けさせる。

対処は「web アプリの `src` 全体を除外する」という広い免除ではなく、`ALLOWED_FILES` へ
理由つきで 1 ファイルずつ追加する形にした。対象行には
`// log-hygiene:allow ブラウザの devtools 向け` を付け、`ALLOWED_FILES` の docstring の
類型リストにも「ブラウザ側の `console`」を追記した。広い除外にしなかった理由は、
将来 web アプリ側に増える `.ts` ファイルを黙って免除しないようにするためである。
