# 振り返り: trustPolicy による信頼証跡の降格拒否（#116）

**対象**: Issue #116（親エピック #67 段階 B）・**PR**: #137（設定 / ADR 0010 / 開発ガイド /
スペックの CI 実測、積み上げ 4 コミット）
**期間**: 2026-08-12（設計から PR まで同日）

## 踏んだ罠（事実と再発条件）

### 1. `trustPolicyIgnoreAfter` が待機期間と組み合わさると検査を完全に無力化する

**事実**: `trustPolicyIgnoreAfter: 10080`（分。7 日）を仮に設定して実測したところ、
`semver@6.3.1` の降格違反が消え、終了コード 0 になった。検証自体は走っており 8 秒かけている
（数値の正本は
[スペック](../superpowers/specs/2026-08-12-trust-policy-design.md)の「罠:
`trustPolicyIgnoreAfter` は検査を無力化する」節）。**コストを払ったまま 1 件も判定しない
状態**になっていた。

**原因**: `trustPolicyIgnoreAfter` は「公開から N 分より古い版は検査しない」設定であり、
`minimumReleaseAge`（7 日）は「公開から 7 日未満の版は install できない」設定である。
前者を 7 日以下にすると、install されうる版（=公開から 7 日以上経った版）の集合と
検査対象外になる版（=公開から N 分以上経った版）の集合がほぼ完全に重なり、検査対象が
空集合に近づく。2 つの設定は別々の意図（「検査対象を絞る」「入力そのものを絞る」）で
入れられているため、単体で読むと副作用が見えない。

**再発条件**: 「検査対象を絞る設定」と「入力そのものを絞る設定」が併存し、後者の範囲が
前者を覆うとき。この 2 つの設定は同じ機能（`trustPolicy`）の中にすら現れず、片方
（`minimumReleaseAge`）は ADR 0008・もう片方（`trustPolicyIgnoreAfter`）は本 Issue と、
導入されたタイミングも文書も別だった。

**対処**: `trustPolicyIgnoreAfter` を使わない決定を ADR 0010 に MUST NOT として明記した
（D2）。設定ファイルのコメントにも理由を書いた。

### 2. 自分のスペックが #70 で入れた CI の絞り込みを無視していた

**事実**: 実装計画の初期見積りは「CI の 4 ジョブが各 +6 秒」と書いていた。実際には
`pnpm install` は `ci` / `e2e` / `quality` / `audit` すべてで条件付きステップ
（`.github/workflows/ci.yml` の `if: steps.scope.outputs.code == 'true'` /
`...deps == 'true'`）であり、**文書のみの PR では 1 回も走らない**。

**原因**: #70（同日に完了・クローズ済み）でジョブ絞り込みを自分自身が実装していたにも
かかわらず、#116 の見積りを書く段でその仕組みを踏まえていなかった。「4 ジョブ全部が
常に払う」という #70 以前の古いメンタルモデルのまま数を積んだ。

**再発条件**: 直前の Issue で入れた仕組みを、次の Issue の見積りで数に入れ忘れるとき。
とくに同日に連続して完了した Issue 間では、直前の変更を「まだ入っていない前提」で
見積もりがちになる。

**対処**: Task 4 で CI を実際に走らせ、スペックの「CI が実際に払うコスト」節を実測値
（4 ジョブとも 7.8〜7.9 秒）と、絞り込みの効果（文書のみの PR では増分 0）の両方で
書き直した。数値の正本はスペックの 1 か所に統一した。

### 3. 憲法の原則を読まずに引用した

**事実**: D9（1 PR にまとめる判断）の根拠として「原則 IX は PR の本数を規定していない」と
書いたが、この結論を書いた時点では `.specify/memory/constitution.md` の原則 IX 本文を
確認していなかった。後で読み直すと、原則 IX の本文は「1 PR は 1 つの論理的変更に留める
（MUST）」であり、本数の規定が無いという結論自体は正しかった。

**原因**: 「原則 IX ＝ 小さく回す ＝ 1 コミット 1 論理変更」という要約を記憶から引用し、
一次情報（憲法本文）を開かずに結論を書いた。要約と原文が一致していたのは結果論で、
確認の手順自体が欠けていた。

**再発条件**: 引用元が記憶にあると思ったとき。過去に何度も読んだ文書ほど、
「知っているはずだから確認は不要」という判断が働きやすい。

**対処**: 引用箇所を憲法本文で確認してからスペックの D9 に反映した
（[スペック](../superpowers/specs/2026-08-12-trust-policy-design.md) D9 節）。以後、
憲法・ADR を根拠として引用する際は原文を開いてから書く。

### 4. overlay に成果物を置いて場所を伝えず、利用者が確認できなかった

**事実**: 作業は `/home/vscode/tasuki-work`（overlay）で行うが、利用者が閲覧するクローンは
`/workspaces/claym/local/Tasuki` であり、両者は別物である。Task 4 で成果物
（スペック・ADR 0010）を overlay に作った直後は、利用者側クローンへのコピーとフルパスの
案内が抜けていた。

**原因**: 作業クローンと閲覧クローンが分かれている構成そのものが、パスを明示しない限り
利用者から成果物を見えなくする。

**再発条件**: 作業クローンと利用者のクローンが分かれているとき。フルパスを書けば足りるが、
書かなければ利用者は成果物の存在を知りようがない。

**対処**: Task 4 Step 6 で `/workspaces/claym/local/Tasuki/docs/superpowers/specs/` と
`/workspaces/claym/local/Tasuki/docs/adr/` へコピーし、フルパスを報告に明記した。

### 5. `node_modules` を消しても検証キャッシュは消えない

**事実**: `~/.cache/pnpm/lockfile-verified.jsonl` は「lockfile のハッシュ＋ポリシー」を
鍵に検証結果を保持する。管理者が Task 1 の結果を独立確認しようとした最初の試行は、
`node_modules` だけを削除して `pnpm install --frozen-lockfile` を実行するものだったが、
検証が走らず 1.4 秒で終了コード 0 になった。**検査していないのに緑を見た。**
キャッシュを消してから測り直して初めて、447 エントリの検証（`main = 1bbde74` の実測で
6.9 秒。数値の正本は
[スペック](../superpowers/specs/2026-08-12-trust-policy-design.md)「適用コスト」節）が
走っていることを確認できた。

**原因**: pnpm は「lockfile もポリシーも変わっていなければ、以前の検証結果を再利用できる」
という最適化を持つ。`node_modules` の削除は install の短絡（「Already up to date」）だけを
解除し、検証キャッシュの鍵（lockfile ハッシュ＋ポリシー）には触れない。既存の開発ガイドは
`node_modules` の削除しか案内しておらず、この経路を取り逃がしていた。

**再発条件**: 検査結果にキャッシュがあり、そのキャッシュの鍵が「確認したい対象」を
含まないとき。今回は「ポリシー（`pnpm-workspace.yaml`）を変えずに検証だけを再実行したい」
という確認方法が、キャッシュの鍵の外側にあった。

**対処**: Task 3 で `docs/guides/development.md` の「ローカル確認時の注意」に
`rm -f ~/.cache/pnpm/lockfile-verified.jsonl` の手順と、検証が実際に走ったかを
`Verifying lockfile against supply-chain policies` の行の有無で判断する旨を追加した
（コミット a528af8）。CI は毎回フレッシュな checkout のためこの罠にはかからない。

## 検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）

`trustPolicy` 自体は破壊検証済み（設定を消す・除外を差し替える、いずれも期待通り赤くなる
ことを確認済み。詳細は
[スペック](../superpowers/specs/2026-08-12-trust-policy-design.md)「検証」節）。
一方で、今回新設した `trustPolicyExclude` という**除外リスト**には、静かに効かなくなる
経路が 2 つあり、**どちらも現時点で機械的な検査が無い**。CI は緑のまま、除外が意図と
違う範囲まで免除を与えてしまう。

### 1. 版指定の退化

`trustPolicyExclude` の行が `"名前@版"`（例: `"semver@6.3.1"`）ではなく `"名前"`
（例: `"semver"`）だけになると、以後そのパッケージの**全版**が降格検査の対象外になる。
乗っ取りが起きた新しい版が publish されても、この除外が黙って通してしまう。

**なぜ緑のままか**: pnpm は `trustPolicyExclude` を「文字列（名前のみ）」と
「配列（`名前@版` のリスト）」の両方の形式で受け付ける
（`failIfTrustDowngraded` の `excludeResult === true` と
`Array.isArray(excludeResult) && excludeResult.includes(version)` の 2 経路）。
形式の退化はエラーにならず、pnpm から見れば単に「より広い除外」として正常に動作する。
書式の逸脱を弾く検査が無い。

### 2. 死んだ除外行の残留

除外した版が依存木から消えても行はそのまま残る。将来その版が（別の依存元経由などで）
再び依存木に現れたとき、期限も検査も無いため、除外行はそのまま黙って免除を与える。

**なぜ緑のままか**: lockfile に存在しないパッケージ・版に対する除外エントリがあっても、
pnpm はそれを無効エントリとして警告も失敗もしない。除外リストは「一度書いたら誰も
見返さない」構造になりやすく、対象が変わったことに気づく契機がゼロ。

いずれも設計上の対処（版指定を書式として強制する、除外の対象が依存木に存在するかを
機械的に検査する）は Issue #135 が扱う「検査が静かに効かなくなる経路」の一群に含まれる
性質であり、本 Issue の範囲では未対応（ADR 0010 決定 D7）。

同じ性質の穴は `minimumReleaseAgeExclude`（#69 で導入した待機期間の除外リスト）にも
ある。現状は「解除予定日をコメントに書く」という運用のみで支えられており、期限切れの
検査・死んだエントリの検査のどちらも機械的には存在しない。
