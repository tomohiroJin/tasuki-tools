# 機能仕様: 再接続時の自動リジューム配線（Issue #24）
**ブランチ/ディレクトリ:** `fix/issue-24-resume-wiring` / `docs/plans/resume-token-wiring` ・ **ステータス:** Draft ・ **フロー:** 要件優先

## 概要
WebSocket が一時的な切断から自動再接続したあと、web クライアントは `room.join` を再送しないため、
サーバー側に実装済みのリジューム処理（`resumeToken` による参加者復帰）が一度も実行されない。
利用者は `NOT_IN_ROOM` エラーに遭遇し、手動で入り直すしかない。手動での入り直しは新規参加として
扱われるため、同じ表示名の参加者が二重に登録され、片方が `presence: "offline"` のまま一覧に残り続ける。

本機能は、web クライアントが自分の `resumeToken` を保持し、WS 再接続の完了時に自動で
`room.join`（resumeToken 付き）を再送することで、利用者の操作なしに元の参加者として復帰させる。

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 一時的な切断からの自動復帰（優先度: P1）
モブプロのセッション参加者として、ネットワークが一時的に切れて WS が自動再接続したときに、
何も操作しなくても元の参加者として復帰したい。なぜなら、手動で入り直すと二重参加になり、
ローテーションや残り時間の表示が崩れるから。

**受け入れ基準（EARS）:**
1. 参加者が `room.create` または `room.join` に成功したとき、システムはその参加者の
   `resumeToken` / `participantId` / ルームコード / 表示名を同一タブ内で保持しなければならない。
   **【改定 2026-09-06・#95】** 保持先は同一タブ内ではなく、ルームコード別の
   `localStorage` とする（FR-006 の注記を参照）。
2. WS が切断後に自動再接続したとき、保持済みの識別情報があれば、システムは
   `resumeToken` を含む `room.join` を利用者の操作なしに再送しなければならない。
3. サーバーが `resumeToken` を有効なものとして受理したとき、システムは
   参加者一覧の重複を発生させてはならない（既存参加者の `presence` が `online` に戻るのみ）。
4. 参加者がルームから明示的に退出した、またはセッションが喪失（`session-lost`）と判定されたとき、
   システムは保持していた識別情報を破棄しなければならない（次回接続で誤って古いルームへ
   復帰しようとしないため）。

### ユーザーストーリー2 — サーバー再起動によるトークン失効時の縮退（優先度: P2）
参加者として、サーバー再起動などでリジュームができなくなった場合でも、エラーが分かりやすく
表示され、混乱なく次の行動（入り直す/様子を見る）を選べるようにしたい。

**受け入れ基準（EARS）:**
1. 保持していた `resumeToken` でルーム自体が消失している（`ROOM_NOT_FOUND` 相当）とき、
   システムは既存の「セッション喪失」表示（`session-lost` 経路）を用いて状況を説明し、
   保持していた識別情報を破棄しなければならない。
2. システムは、リジューム失敗時に自動でリトライを繰り返し利用者を待たせ続けてはならない
   （既存のバックオフ付き再接続ループ以上の追加リトライは行わない）。

## 機能要件 *(必須)*
- **FR-001**: システムは `room.created` / `room.joined` 受信時に、`resumeToken` と
  `participantId`、ルームコード、表示名の組を同一タブ内のストレージへ保存しなければならない。
- **FR-002**: システムは WS の初回接続と再接続を区別し、再接続の完了時にのみ、保存済みの
  識別情報を使って `room.join`（resumeToken 付き）を自動送信しなければならない。
- **FR-003**: システムは初回接続時（新規の `room.create` / `room.join` 操作）には、
  この自動再送を行ってはならない（利用者の明示操作による送信と重複させないため）。
- **FR-004**: システムは明示的な退出（`leave-room` エラー経路）成立時に保存済み識別情報を
  破棄しなければならない。
- **FR-005**: システムは `session-lost` 判定時に保存済み識別情報を破棄しなければならない。
- **FR-006**: システムは保存する `resumeToken` を `sessionStorage` に保持しなければならない
  （`localStorage` は用いない）。
  **【撤廃 2026-09-06・#95】** 復帰の組は `localStorage` にルームコード別で保存する。
  理由は 2 つある。(1) 参加者は明示的な退出でしか名簿から消えないため、`sessionStorage` だと
  タブを開き直すたびに別人として join し、前の自分が名簿へ残る（幽霊が溜まる）。
  (2) 本要件の非機能要件が根拠に挙げた `.claude/rules/security.md` は、`localStorage` と
  `sessionStorage` を同列に禁じており、2 つを区別する根拠にならない。
  詳細は[設計正本](../../superpowers/specs/2026-09-06-shared-identity-and-rooms-design.md) D12。
  **実装は S4b（[#246](https://github.com/tomohiroJin/tasuki-tools/issues/246)）で行う。**
  それまで `apps/timer-web/src/sync/resume-identity.ts` は `sessionStorage` のままである。

## 非機能要件
- **セキュリティ**: `resumeToken` はルーム限定・短命（サーバーメモリ上のみで保持され、
  サーバー再起動で失効する）ため `sessionStorage` に保存する。`.claude/rules/security.md` は
  localStorage への機密情報保存を禁じているが、本トークンは以下の理由で sessionStorage が
  要件に合致すると判断する: (1) 再接続は同一タブ内で起きる事象であり、タブをまたいだ
  永続化は本来不要（かえって「別タブで開いた同名参加者が誤って乗っ取る」リスクを生む）、
  (2) タブを閉じれば自動的に消え、長期間の残留がない、(3) サーバー側も再起動で失効するため
  クライアント側だけが長寿命に保持する意味がない。
  **【撤廃 2026-09-06・#95】** ここに書いた判断は FR-006 とともに撤廃された。復帰の組は
  `localStorage` にルームコード別で保存する。理由は FR-006 の注記を参照。
- **可観測性**: 自動リジューム再送は既存の `console.error` 相当のログ方針に合わせ、
  過剰なログを追加しない（個人情報・トークン文字列そのものはログに出さない）。

## 主要エンティティ
- **ResumeIdentity** — `code`（ルームコード）, `participantId`, `resumeToken`, `displayName` の組。
  同一タブの `sessionStorage` に単一の現在ルーム分だけ保持される（複数ルーム同時参加は非対応）。
  **【改定 2026-09-06・#95】** `localStorage` にルームコード別で保持する。ルームごとに
  1 組を持つため「単一の現在ルーム分だけ」という制限も撤廃する（FR-006 の注記を参照）。

## 成功基準 *(必須・技術非依存)*
- **SC-001**: WS が一時切断ののち自動再接続した場合、参加者一覧に重複した参加者が現れない。
- **SC-002**: 再接続後、利用者が何も操作しなくても、参加者は自分の元の参加者行として
  `online` 表示に戻る。
- **SC-003**: サーバー再起動でルームごと消失した場合は、二重参加ではなく既存の
  「セッションが見つかりません」表示に帰着する。

## スコープ外 / 非目標 *(必須)*
- ブラウザタブの再読み込み（フルリロード）やタブを跨いだ復帰の自動化は対象外。
  本機能は同一タブ内で React アプリが生存し続けたまま WS だけが再接続するケースに限定する
  （sessionStorage への保存自体はリロード後も残るが、リロード時に自動でルームへ入る画面遷移は
  実装しない。理由: App.tsx はこの直後に Issue #41 で全面リファクタされる予定であり、
  マウント時の自動遷移まで実装すると変更範囲が state 初期化ロジックへ広がり「最小限・局所的」
  の制約に反するため）。
- サーバー側のリジューム処理・`resumeTokens` ストアの実装変更は対象外（`apps/sync` は
  担当領域外であり、既存実装をそのまま前提とする）。
- 「ルームは存在するが特定の resumeToken だけ失効している」エッジケース
  （新規参加へ静かにフォールバックし、結果として二重参加になりうる）の是正は対象外。
  これは Issue #24 の「検討事項」に記載された既知の残存リスクであり、サーバー側で
  「リジューム試行が失敗した」ことをクライアントへ区別して伝える仕組みが要る。
  担当領域外（`apps/sync`）のため、親タスクへの報告事項として扱う。

## 前提
- [前提1] `apps/sync/src/application/command-handlers/room-join.ts` のリジューム処理
  （`resumeToken` 一致時に既存参加者の `connId`/`presence` を更新して復帰させる）は
  現状のまま変更せず利用できる、という Issue の前提を実測で確認済み（2026-08-01 時点）。
- [前提2] `room.joined` サーバーメッセージにはルームコードが含まれない
  （`packages/core/src/schemas.ts` の `RoomJoinedMsg`）ため、参加時の `code` は
  クライアント側の呼び出し元スコープ（`handleJoinRoom` の引数）から補う。
