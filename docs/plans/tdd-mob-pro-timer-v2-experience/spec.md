# 機能仕様: TDD Mob Pro Timer v2 — 体験・導線の作り直し

**ブランチ/ディレクトリ:** `docs/plans/tdd-mob-pro-timer-v2-experience` ・ **ステータス:** Implemented（v2.10.0 本番デプロイ済み 2026-06-26） ・ **フロー:** 要件優先（v1 実装とフィードバックから導出）

> 本仕様は技術非依存（何を・なぜ）に徹する。フレームワーク・同期方式・API 名などの「どう作るか」は承認後に `plan.md` で扱う。
> v1（M0〜M3）で「モブタイマーは動く」状態に到達済み。本 v2 は**動くコアはそのままに、体験（見た目・導線・お題の質・離脱フロー・新規参加）を作り直す**ことを目的とする。

## 概要

v1 のフィードバックは「タイマーは動くが、アプリとして考え抜かれておらずチープ」という一点に集約される。
具体的には ①画面の見た目・UX が良くない ②生成されるお題が一言すぎて実用に耐えない ③新しく参加する人の
ための導線（ルーム作成→共有→参加）が整っていない ④完成以外の「途中でやめる」フローとボタン表現への配慮がない
⑤AI 機能が本当に効いているか不明、である。

本機能は、解決する課題を「**初めて触る人でも、迷わず・気持ちよく・実用的なお題でモブプロを始め、必要なら
途中でも自然に切り上げられる**」体験へと引き上げることに定める。新しい画面を作ることが目的ではなく、
**最初の60秒で価値が伝わり、チームを招き入れられる**ことを目的とする。

---

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 初見の人が迷わず開始できる（優先度: P1）

モブプロを初めて主催する人として、説明書を読まなくても、開いてから数十秒で最初のセッションを始めたい。
なぜなら、ツールの学習に時間を取られず、本題（コーディング）に入りたいからだ。

**受け入れ基準（EARS）:**
1. 利用者が初めて画面を開いたとき、システムは「何をするツールか」と「次に押すべき主要アクション」を一目で理解できる形で提示しなければならない。
2. 利用者が初期状態のまま開始操作を行ったとき、システムは追加入力を必須とせず、妥当な既定（メンバー・言語・難易度・交代間隔）でセッションを開始できなければならない。
3. もし開始に必要な条件が満たされていない（例: メンバー名が空・重複）なら、システムはどこをどう直せばよいかを、該当箇所の近くで具体的に提示しなければならない。
4. 主要な操作（開始・参加・共有）に至るまでの段階数は、初期状態から最短で把握できる範囲に収めなければならない。

### ユーザーストーリー2 — チームを招き入れる（ルーム作成→共有→参加）（優先度: P1）

主催者として、作ったセッションのルームを仲間に共有し、別々の端末から同じセッションに合流してほしい。
なぜなら、リモート/分散したチームで同じ画面・同じタイマーを見たいからだ。

**受け入れ基準（EARS）:**
1. 利用者がルーム作成を行ったとき、システムは共有可能な招待手段（コピー可能な参加用リンクとルームコード、および読み取り用コード）を、見つけやすい位置に提示しなければならない。
2. 招待を受け取った利用者が参加用リンクを開いたとき、システムは追加の探索操作なしに、当該ルームへ参加する導線を提示しなければならない。
3. 参加者がルームに合流したとき、システムは参加者一覧・現在のフェーズ・現/次ドライバー・残り時間を、合流時点の最新状態として提示しなければならない。
4. ルームの状態が変化したとき、システムは在室する全参加者の画面に、その変化を反映しなければならない。
5. もし無効・期限切れのルームへ参加しようとしたなら、システムは参加できない理由と次にとるべき行動（新規作成など）を提示しなければならない。
6. 待機中（ロビー）の主催者に対して、システムは「誰が来ているか」と「開始できる状態か」を提示しなければならない。

### ユーザーストーリー3 — お題を「自分たちのもの」にして始める（優先度: P1）

参加者として、そのまま TDD を始められる十分な情報量のお題がほしいだけでなく、気に入らなければやり直し、
AI を使わず手持ちの題材から選び、少し編集し、言語や難易度を変え、用意済みのお題を持ち込んで始めたい。
なぜなら、お題はチームのその日のコンディションに合わせて調整するものであり、押し付けられた一品では空転するからだ。

**受け入れ基準（EARS）:**
1. 利用者がお題を受け取ったとき、システムは「タイトル・解くべき課題の説明・テスト可能な要件の一覧・最低1つの例示テスト・着手のためのヒント」を、そのまま着手できる粒度で提示しなければならない。
2. お題の各要件は、テストで合否を判定できる粒度でなければならない（曖昧な一語で済ませない）。
3. もし生成元（AI 等）が利用できない・失敗した・不正な形式であったなら、システムは実用的な定型お題へ縮退し、画面を壊してはならず、出所（AI 生成 / 定型）を利用者に明示しなければならない。
4. 利用者がお題の再生成（やり直し）を要求したとき、システムは直近のお題と重複しにくい新しいお題を提示しなければならない。
5. 利用者が AI を使わずに出題することを選んだとき、システムは定型お題のバンクから（選択言語・難易度に沿って）お題を提示しなければならない。
6. 利用者がお題の内容（タイトル・説明・要件・例示テスト・ヒント）を編集したとき、システムは編集後の内容をそのセッションのお題として扱わなければならない。
7. 利用者が言語または難易度を変更したとき、システムは変更後の条件に沿って、お題を出題し直す手段を提示しなければならない。
8. 利用者が自前のお題を持ち込んだ（貼り付け/入力した）とき、システムはそれをそのセッションのお題として受け入れ、開始可能な状態にしなければならない。
9. 利用者がお題のコピーを要求したとき、システムはお題を可搬な形式で取得できる形（クリップボード等）で提供しなければならない。
10. 共有ルームでお題が確定・変更されたとき、システムは在室する全参加者へ同一のお題を反映しなければならない。

### ユーザーストーリー4 — AI のオン/オフが一目で分かり、自分で選べる（優先度: P1）

利用者として、AI によるお題生成が今オンなのかオフ（定型）なのかを一目で把握でき、かつ自分の判断で
切り替えたい。なぜなら、v1 では AI が効いているか分からず価値が伝わらなかったし、トークン残量が心もとない日や
オフラインの場面では「今日は AI を使わない」と自分で決めたいからだ。

**受け入れ基準（EARS）:**
1. システムは現在の出題モード（AI 生成 / 定型）を、画面上で常に一目で判別できる形で提示しなければならない。
2. AI 生成を使うために利用者の設定（鍵など）が必要な場合、システムは未設定であることと、設定への導線を、利用者が気づける形で提示しなければならない。
3. 利用者が出題モードを切り替えたとき（AI を使う / 使わない）、システムは以降の出題を選択したモードで行わなければならない。
4. AI 設定が有効な状態で AI モードのお題を生成したとき、システムは結果が AI 由来であることを明示しなければならない。
5. AI 設定が無効・未設定、または利用者が AI オフを選んだ状態では、システムは定型お題で動作し続け、かつ「定型である」ことと「AI を有効化する方法」を提示しなければならない。
6. AI 生成中の間、システムは生成中であること（待機状態）を利用者に提示しなければならない。
7. もし利用者の鍵を扱うなら、システムはそれを同期基盤へ送らず、本人の端末内に留め、記録・ログに残してはならない。

### ユーザーストーリー5 — セッションの終え方を、画面全体で自然に扱う（優先度: P1）

参加者として、最後までやり切る場合だけでなく、時間切れ・中断・中止・やり直しといった様々な終え方を、
戸惑わずに、操作の言葉と画面の流れに沿って扱いたい。なぜなら、実際のモブプロは必ずしも「完成」で終わらず、
「完成」一辺倒の画面とボタンは実態に合わず誤操作と気まずさを生むからだ。

**受け入れ基準（EARS）:**
1. セッション進行中の間、システムは終え方（やり切って終える=完成 / 途中で切り上げる=中断 / 初期状態へ戻す=リセット）を、別個の・意味が取り違えられない表現の操作として提供しなければならない。
2. 利用者が破壊的・不可逆になりうる終了操作（中断・リセット等）を行おうとしたとき、システムは結果（記録の扱い・初期化の有無・共有ルームでは他参加者への影響）を提示し、確認を経てから実行しなければならない。
3. 完成で終えたとき、システムは達成を記録し、達成にふさわしい締めくくりを提示しなければならない。
4. 途中で終えたとき、システムは「完成」とは区別した形（終了種別=中断）で結果を扱い、誤って達成として記録してはならない。
5. システムは、終え方に応じてその後の画面（締めくくり/振り返り/設定復帰）を自然につなげ、各フェーズの語彙（見出し・ボタン）を実態と一致させなければならない。
6. 共有ルームで終了が確定したとき、システムは在室する全参加者に対し、終え方（完成 / 中断）と次の状態を一貫して反映しなければならない。
7. いずれの終了後も、システムは利用者を、次の行動（新規セッション・設定変更・退出）へ明確に導かなければならない。

### ユーザーストーリー6 — 情報設計とレスポンシブ（どの画面サイズでも破綻しない）（優先度: P2）

利用者として、画面の大小に関わらず、今いちばん大事な情報が一目で分かり、主要な操作に手が届いてほしい。
なぜなら、モバイルや小さなウィンドウで情報が溢れたり操作が押せなかったりすると、ツールとして使えないからだ。
（ビジュアルの方向性・一貫性・演出は US7 が定める。本 US6 は方向性に依らず満たすべき情報の優先順位と
レスポンシブの最低品質に絞る。）

**受け入れ基準（EARS）:**
1. 利用者が画面を見たとき、システムは情報の優先順位（今・誰が・あと何分・次は誰）が視線の流れで把握できる順序・配置で提示しなければならない。
2. 画面サイズが小さい（モバイル相当）とき、システムは主要情報（残り時間・現/次ドライバー）と主要操作（開始・一時停止/再開・スキップ・終了系）を、破綻なく操作可能な形で提示しなければならない。
3. 画面サイズが変化したとき、システムは情報の優先順位を保ったままレイアウトを再構成しなければならない（重要要素が画面外に隠れない）。

### ユーザーストーリー7 — 「セッション没入装置」としてのビジュアルアイデンティティ（優先度: P1）

利用者として、開いた瞬間に「これはモブプロのための集中装置だ」と感じる、一貫した世界観の画面がほしい。
なぜなら、見た目がプロダクトの価値の核であり、第一印象でチームに勧められるかどうかが決まるからだ。
（方向性: **集中・ステージ型** — ダークな舞台に「今・誰・あと何分」が主役として浮かび、周辺情報は控えめ。
交代のような節目だけ強い演出。）

**受け入れ基準（EARS）:**
1. 利用者が画面を見たとき、システムは暗い基調の舞台の上に、当該フェーズで最も重要な要素（セッション中は残り時間と現ドライバー）を、画面内で最も大きく・最も明るい焦点として提示しなければならない。
2. システムは全フェーズ（開始前・ロビー・セッション・終了）を通じて、一貫した視覚言語（基調色・焦点の作り方・余白・操作要素の見え方・字面）を用いなければならない。
3. 周辺情報（メンバー一覧・統計・補助操作）について、システムは焦点を妨げない明度・サイズ・配置で、必要なときに参照できる形で提示しなければならない。
4. 節目の状態変化（交代・残りわずか）について、システムは普段は静かで、その瞬間にのみ強まる演出で変化を伝えなければならない（常時の派手な演出を避ける）。
5. モーション軽減が望まれる場合、システムは強い演出を控えめ版へ置き換えつつ、焦点と状態は同等に伝えなければならない。
6. システムは舞台上の主要要素（焦点・操作・状態）について、WCAG AA を満たすコントラストを保ち、色のみに依存しない表現（テキスト/アイコン併記）を用いなければならない。

### ユーザーストーリー8 — 使いやすさの核（招待が一瞬・誤操作させない・迷子にしない）（優先度: P1）

利用者として、招待も参加も一瞬で済み、危険な操作は取り違えず、自分が今どこにいて何が起きているかが常に分かる、
という「使い心地」がほしい。なぜなら、見た目の良さは、この操作の質が伴って初めてプロダクトの価値になるからだ。

**受け入れ基準（EARS）:**
1. ルームが存在する間、システムは「招待を渡す」操作を、最小の操作数（目安: ワンアクション）で完了できる形（リンク/コードのコピー）で提示しなければならない。
2. 招待を受け取った利用者が参加用リンクを開いたとき、システムはコード入力やページ探索を求めず、最小の操作数で合流できる導線を提示しなければならない。
3. 破壊的・不可逆になりうる操作（途中終了・リセット）について、システムは意味が取り違えられない表現を用い、結果を提示し、確認を経てから実行しなければならない。
4. 利用者が操作を行ったとき、システムは結果（状態がどう変わったか）を即時かつ明確なフィードバックで伝えなければならない。
5. システムは利用者に対し、現在のフェーズ・自分の役割・接続状態・（共有時は）在室者を、各フェーズで常に把握できる形で提示しなければならない。
6. もし接続が切れた・エラーが起きたなら、システムはその事実と回復状況（再接続中など）を、利用者が気づける形で提示しなければならない。

### ユーザーストーリー9 — 在席を現場に合わせて柔軟に扱う（優先度: P1）

参加者・主催者として、Web に繋げない人を代理で加え、自分の表示名を決め・後から変え、回線が切れたら復帰でき、
都合の悪いターンは一時的に抜けたい。なぜなら、実際のモブは固定メンバーが常時オンラインとは限らず、
出入り・改名・離脱・復帰が日常的に起きるからだ。

**受け入れ基準（EARS）:**
1. 利用者がルームに参加するとき、システムはその利用者が自分の表示名を決められるようにしなければならない。
2. 主催者が、Web に接続できない人をローテーションに代理で加えたいとき、システムは接続を伴わない参加者（名前のみのプレースホルダ）を追加し、ローテーションに含められるようにしなければならない。
3. 参加者が自分の表示名を変更したとき、システムは在室する全参加者の表示に変更を反映しなければならない。
4. もし参加者の接続が切れたなら、システムは自動再接続を試み、復帰時に同一参加者・同一役割として扱わなければならない。
5. もし参加者が長く不在になったなら、システムは他の参加者に在席状況（オンライン/離席/オフライン）を提示し、進行を妨げないようにしなければならない。
6. 参加者が自分のターンを一時的に飛ばしたい（離脱したい）とき、システムはその参加者をローテーションのドライバー対象から外し、復帰時に戻せるようにしなければならない。
7. 観覧のみで参加する利用者がいる間、システムはその利用者にセッションの閲覧を許可しつつ、ドライバー対象に含めず、状態を変える操作を行わせてはならない。
8. システムは在室する全参加者と各人の在席状況・現/次ドライバーを、常時一覧で提示しなければならない。

### ユーザーストーリー10 — 続きから・自分らしく・主催者が舵を握る（優先度: P2）

利用者として、一度入れた設定を保存し、再訪時に名前や交代間隔などの既定が自動で埋まっていてほしい。また、
主催者には進行や設定変更の舵を握っていてほしく、自分が何らかの理由で落ちても元の状態へ復帰したい。
なぜなら、毎回ゼロから設定し直すのは煩わしく、誰でも全部いじれると混乱し、不慮の離脱で進行が止まると困るからだ。

**受け入れ基準（EARS）:**
1. 利用者が設定（表示名・言語・難易度・メンバー・交代間隔など）を入力したとき、システムはその端末にそれを保存しなければならない。
2. 利用者が再訪したとき、システムは前回保存した値を既定として自動的に提示しなければならない。
3. システムは役割（主催者・編集者・観覧者）に応じて操作可否を定め、進行・設定・終了に関わる重要操作を主催者（および許可された役割）に限定し、コマンドごとに権限を検証しなければならない。
4. 主催者が参加者の役割を変更したとき、システムはその役割に応じて操作可否を更新しなければならない。
5. もし主催者が一定時間を超えて不在になったなら、システムは進行を止めないよう、在室する適切な参加者へ主催権限を引き継がせなければならない。
6. もし利用者が不慮に離脱したなら、システムは復帰時に、離脱前と同一の参加者・役割・最新のセッション状態へ復帰させなければならない。
7. もしサーバー側のセッションが失われたなら、システムは利用者へその旨を明示し、各端末のローカル記録（完成履歴など）は保持しなければならない。

### ユーザーストーリー11 — 開発の証跡がユーザーの邪魔をしない（優先度: P3）

利用者として、開発・テストのための表示が本番の体験に混ざってほしくない。
なぜなら、v1 では自己テスト結果のトーストなど開発用の表示が画面に出ており、製品としての完成度を損ねていたからだ。

**受け入れ基準（EARS）:**
1. 通常の利用時、システムは開発・テスト専用の表示（自己テスト結果など）を利用者向け画面に出してはならない。
2. もし利用者が診断情報を明示的に求めたなら、システムは診断情報を提示してよい（既定では出さない）。

## 機能要件 *(必須)*

**オンボーディング・導線（US1）**
- **FR-001**: システムは初回表示で、ツールの目的と主要アクション（開始 / ルーム作成 / 参加）を、説明文を読まずに識別できる形で提示しなければならない。
- **FR-002**: システムは既定値（メンバー・言語・難易度・交代間隔）でセッションを開始可能にし、入力を必須化してはならない。
- **FR-003**: システムは入力不備（空名・重複名・人数範囲外）を、該当箇所の近くで具体的かつ修正可能な形で提示しなければならない。

**ルーム作成・共有・参加（US2）**
- **FR-004**: システムはルームに対し、参加用リンク（コピー可能）・ルームコード・読み取り用コードを提供しなければならない。
- **FR-005**: システムは参加用リンクからの来訪者に、当該ルームへ参加する導線を直接提示しなければならない。
- **FR-006**: システムは合流した参加者に、合流時点の最新状態（参加者一覧・フェーズ・現/次ドライバー・残り時間）を提示しなければならない。
- **FR-007**: システムは無効・期限切れのルームへの参加要求を、理由と代替行動つきで拒否しなければならない。
- **FR-008**: システムは待機（ロビー）状態で、在室者と開始可否を主催者に提示しなければならない。

**お題を自分たちのものにする（US3）**
- **FR-009**: システムはお題を「タイトル・説明・テスト可能な要件一覧・例示テスト・ヒント」の構造で、そのまま着手できる粒度で提示しなければならない。
- **FR-010**: システムは各要件を、テストで合否判定できる粒度で表現しなければならない。
- **FR-011**: システムは生成失敗・不正形式時に実用的な定型お題へ縮退し、出所（AI / 定型）を明示しなければならない。
- **FR-012**: システムはお題の再生成（やり直し）で、直近のお題と重複しにくい結果を返さなければならない。
- **FR-013**: システムはお題を可搬な形式で取得（コピー等）できるようにしなければならない。
- **FR-037**: システムは AI を使わない出題（定型バンクからの選択・言語/難易度に整合）を提供しなければならない。
- **FR-038**: システムはお題の各フィールド（タイトル・説明・要件・例示テスト・ヒント）を利用者が編集でき、編集後の内容をそのセッションのお題として扱わなければならない。
- **FR-039**: システムは言語・難易度の変更に応じて、お題を出題し直せなければならない。
- **FR-040**: システムは利用者が自前のお題を持ち込む（貼り付け/入力）ことを受け入れ、それでセッションを開始できなければならない。
- **FR-041**: システムは共有ルームでお題が確定・変更されたとき、在室する全参加者へ同一のお題を反映しなければならない。

**AI のオン/オフと可視性（US4）**
- **FR-014**: システムは AI 生成に必要な利用者設定（鍵など）の有無を判定し、未設定時は設定導線を提示しなければならない。
- **FR-015**: システムはお題ごとに出所（AI 由来 / 定型）を明示しなければならない。
- **FR-016**: システムは AI 生成中の待機状態を提示しなければならない。
- **FR-017**: システムは利用者の鍵を同期基盤へ送らず、本人端末に留め、記録・ログに残してはならない。
- **FR-042**: システムは現在の出題モード（AI 生成 / 定型）を常に一目で判別できる形で提示しなければならない。
- **FR-043**: システムは利用者が出題モード（AI を使う / 使わない）を切り替えられるようにし、以降の出題を選択モードで行わなければならない。

**セッションの終え方を自然に扱う（US5）**
- **FR-018**: システムは「完成」と「途中で終える（中断）」と「リセット」を、意味が取り違えられない別個の操作として提供しなければならない。
- **FR-019**: システムは破壊的な終了操作を、結果提示と確認を経てから実行しなければならない（共有時は他参加者への影響も提示）。
- **FR-020**: システムは完成記録と途中終了を区別して扱い（終了種別を保持）、途中終了を達成として記録してはならない。
- **FR-021**: システムは終了後に、次の行動（新規・設定変更・退出）への導線を提示しなければならない。
- **FR-044**: システムは終え方に応じて後続画面と各フェーズの語彙（見出し・ボタン）を実態と一致させ、自然につなげなければならない。
- **FR-045**: システムは共有ルームで終了が確定したとき、在室する全参加者へ終え方（完成 / 中断）と次の状態を一貫して反映しなければならない。

**在席の柔軟な管理（US9）**
- **FR-046**: システムは参加者が参加時に自分の表示名を決められるようにしなければならない。
- **FR-047**: システムは Web に接続できない人を、接続を伴わないプレースホルダ参加者として主催者が代理追加でき、ローテーションに含められるようにしなければならない。
- **FR-048**: システムは参加者の表示名変更を、在室する全参加者の表示に反映しなければならない。
- **FR-049**: システムは接続切断時に自動再接続を試み、復帰時に同一参加者・同一役割として扱わなければならない。
- **FR-050**: システムは各参加者の在席状況（オンライン/離席/オフライン）を提示し、不在が進行を妨げないようにしなければならない。
- **FR-051**: システムは参加者が自分のターンを一時的に飛ばす（ドライバー対象から外れる/戻る）ことをできるようにしなければならない。
- **FR-052**: システムは在室する全参加者と各人の在席状況・現/次ドライバーを常時一覧で提示しなければならない。
- **FR-061**: システムは観覧のみの利用者を、ドライバー対象に含めず、状態を変える操作を拒否しつつ、閲覧を許可しなければならない。

**継続性・権限・復帰（US10）**
- **FR-053**: システムは設定（表示名・言語・難易度・メンバー・交代間隔など）を端末に保存しなければならない。
- **FR-054**: システムは再訪時に、前回保存した値を既定として自動提示しなければならない。
- **FR-055**: システムは役割（主催者・編集者・観覧者）に応じて操作可否を定め、重要操作を主催者（および許可された役割）に限定し、コマンドごとに権限を検証しなければならない。
- **FR-056**: システムは主催者による役割変更に応じて操作可否を更新しなければならない。
- **FR-057**: システムは主催者が一定時間を超えて不在のとき、在室する適切な参加者へ主催権限を引き継がせなければならない。
- **FR-058**: システムは不慮の離脱からの復帰時に、離脱前と同一の参加者・役割・最新のセッション状態へ復帰させなければならない。
- **FR-059**: システムはサーバー側セッション喪失時に利用者へその旨を明示し、各端末のローカル記録を保持しなければならない。

**情報設計とレスポンシブ（US6）**
- **FR-022**: システムは情報の優先順位（現ドライバー・残り時間・次ドライバー）を視線誘導で把握できる順序・配置で提示しなければならない。
- **FR-026**: システムは小さい画面でも主要情報・主要操作を破綻なく操作可能な形で提示しなければならない。
- **FR-060**: システムは画面サイズの変化に対し、情報の優先順位を保ったままレイアウトを再構成しなければならない（重要要素が画面外に隠れない）。

**ビジュアルアイデンティティ（US7・集中ステージ型）**
- **FR-028**: システムは暗い基調の舞台上に、各フェーズで最重要の要素を、画面内で最大かつ最も明るい焦点として提示しなければならない（セッション中は残り時間と現ドライバー）。
- **FR-029**: システムは全フェーズで一貫した視覚言語（基調色・焦点の作り方・余白・操作要素・字面・デザイントークン）を用いなければならない。
- **FR-030**: システムは周辺情報を、焦点を妨げない明度・サイズ・配置で提示しなければならない。
- **FR-031**: システムは節目の状態変化（交代・残りわずか）に限って強まる演出を用い、常時の派手な演出を避けなければならない（フィードバックを過剰でない範囲に保つ）。
- **FR-025**: システムはモーション軽減設定を尊重し、演出を控えめ版へ切り替えつつ、焦点と状態は同等に伝えなければならない。
- **FR-032**: システムは舞台上の主要要素について WCAG AA のコントラストを満たし、色のみに依存しない表現（テキスト/アイコン併記）を用いなければならない。

**UX の核（US8）**
- **FR-033**: システムは招待の受け渡し（リンク/コードのコピー）を、1操作（コピー1回）で完了できる形で提示しなければならない。
- **FR-034**: システムは参加用リンクからの来訪者を、コード入力やページ探索なしに1操作で合流させなければならない。
- **FR-035**: システムは操作の結果（状態変化）を、即時かつ明確なフィードバックで伝えなければならない。
- **FR-036**: システムは現在のフェーズ・自分の役割・接続状態・（共有時は）在室者を、各フェーズで常に把握できる形で提示しなければならない。

**開発証跡の分離（US11）**
- **FR-027**: システムは通常利用時に、開発・テスト専用表示を利用者向け画面へ出してはならない。

## 非機能要件

- **アクセシビリティ**: 主要操作はキーボードのみで完結できる。色のみに依存せずテキスト/アイコンを併記する。テキストのコントラストは WCAG AA を満たす。状態変化（交代・残りわずか・一時停止・終了）は支援技術へ通知可能とする。モーダルはフォーカストラップと Esc を備える。
- **性能・同期**: 状態変化は在室参加者へほぼ即時に反映される。初回表示は素早く、主要操作の反応は即時に感じられること（具体的なしきい値は `plan.md` の非機能で定める）。
- **プライバシー・セキュリティ**: 既定で外部送信なし。AI 利用は本人の鍵による本人端末からの通信に限る。同期基盤に保持する個人データは表示名のみ・揮発。ユーザー/AI 由来テキストの描画でスクリプト実行を許さない。
- **互換性**: v1 のドメイン（交代・一時停止・経過時間・不変条件）と整合し、既存の正しい振る舞いを壊さないこと。

## 主要エンティティ

- **ルーム（Room）** — ルームコード、招待手段、主催者、設定、現在のお題、出題モード、フェーズ、参加者一覧、セッション状態、タイマー状態。
- **参加者（Participant）** — 安定 ID、表示名（変更可）、役割（主催者/編集者/観覧者）、在室状況（オンライン/離席/オフライン）、ドライバー対象か（一時離脱フラグ）、接続の有無（プレースホルダか実接続か）、AI 鍵保有の自己申告。
- **お題（Problem）** — タイトル、説明、テスト可能な要件一覧、例示テスト、ヒント、出所（AI / 定型 / 持ち込み）、編集済みか。
- **セッション設定（SessionConfig）** — 言語、難易度、メンバー、交代間隔。
- **出題モード（ProblemMode）** — AI 生成 / 定型（利用者が切替可能。鍵未設定時は定型固定）。
- **完成記録（CompletionRecord）** — お題タイトル、言語、難易度、所要時間、メンバー、交代回数、終了日時、**終了種別（完成 / 中断）**。
- **AI 設定（AiSettings）** — 鍵の有無（本人端末内）。
- **保存済み設定（SavedPreferences）** — 端末ローカルの既定値（表示名・言語・難易度・メンバー・交代間隔など）。

## 成功基準 *(必須・技術非依存)*

- **SC-001**: 初見の利用者が、手順説明なしに、開いてから最初のセッション開始までを短時間（目安: 1分以内）で完了できる。
- **SC-002**: 招待リンクを受け取った人が、リンクを開いてから当該ルームに合流するまでを、コード入力や追加ページ遷移なしの導線（最短1操作）で完了できる。合流時に最新状態（参加者一覧・フェーズ・現/次ドライバー・残り時間）が提示される。
- **SC-003**: 提示されたお題だけで、追加の口頭説明なしに TDD に着手できる（要件がテスト可能で、例示テストが付く）。
- **SC-004**: 利用者が、お題の出所（AI / 定型）と、AI を有効化する方法を、画面から判別できる。
- **SC-005**: 利用者が「完成」と「途中で終える」を取り違えず操作でき、途中終了が達成として誤記録されない。
- **SC-006**: 全フェーズ（開始前・ロビー・セッション・終了）で、暗い基調・一貫した視覚言語・「最重要要素が最大かつ最明の焦点」という構図が満たされている（v1 で見られた多色グラデーション/常時アニメーション/開発用トースト等のチープさの要因が画面から除かれている）。
- **SC-007**: 通常利用画面に開発・テスト専用の表示が出ない。
- **SC-008**: セッション中、利用者は画面を見た瞬間（目安: 1秒以内）に「残り時間」と「現ドライバー」を、他の要素より先に視認できる（焦点が成立している）。
- **SC-009**: 全フェーズで視覚言語が一貫しており、利用者が「同じツールの別画面」だと認識できる（基調色・操作要素・字面の不一致がない）。
- **SC-010**: 主要要素のコントラストが WCAG AA を満たし、状態が色のみに依存せず（テキスト/アイコン併記で）判別できる。
- **SC-011**: 招待の受け渡し（リンク/コードのコピー）と、リンクからの合流が、それぞれ1操作で完了できる（招待: コピー1回。合流: リンクを開いた先で参加1操作。コード入力や追加ページ遷移を要さない）。
- **SC-012**: 利用者は、AI を使わずに出題する／お題を編集する／言語・難易度を変えて出し直す／自前のお題を持ち込む、のいずれも、別ツールに移らず画面内で完了できる。
- **SC-013**: 利用者は、現在の出題モード（AI / 定型）を画面から判別でき、自分の操作でモードを切り替えられる。
- **SC-014**: 主催者は Web 非接続のメンバーを代理で加えられ、参加者は自分の名前を決め・変更でき、切断しても同一参加者として復帰できる（在席の出入りで進行が止まらない）。
- **SC-015**: 利用者は再訪時に前回の設定（名前・交代間隔など）が既定として埋まった状態で始められ、主催者は重要操作の権限を保持し、主催者不在でも進行が継続する。

## スコープ外 / 非目標 *(必須)*

- **ドメインロジックの作り直しはしない**: 交代・一時停止・経過時間積算・不変条件など v1 の正しいコア計算は再設計しない（壊さないことが要件）。
- **コードエディタ・実コード実行・テスト実行環境は提供しない**（お題提示まで。実装はチームの実環境で行う）。
- **アカウント登録・ログイン・恒久ユーザー管理は行わない**（参加は表示名と揮発トークンのみ）。
- **AI 生成の代理（運営鍵による managed / サブスク）は行わない**（BYOK = 本人鍵のみ）。
- **永続的なサーバー側状態・チーム横断の恒久記録ストアは持たない**（記録は各端末ローカル）。
- **ネイティブアプリ化・PWA・オフライン高度化**は本 v2 のスコープ外（将来枠）。
- **デザインの全面的ブランド刷新（ロゴ・命名・トーン策定）**は行わない。本 v2 のビジュアル方向性は「集中・ステージ型（ダーク基調）」に確定済みで、これを既存のデザイントークン基盤の上で具現化する。配色・余白・タイポの具体値は plan.md で確定する。
- **ライトモードを主体験にはしない**: 集中・ステージ型はダーク基調を主とする。ライトテーマの提供可否・優先度は plan.md で判断する（v1 のダーク/ライト両対応資産は活かしうるが、本 v2 の主役はダーク）。
- **AI のトークン/クレジット残量の表示はしない**: 利用者の本質ニーズ「今日は AI を使わないと自分で決める」は出題モードのオン/オフ（US4）で満たす。クレジット残量そのものの数値表示・残量に応じた自動制御は行わない（後述の前提に技術的理由を記載）。
- **恒久的なユーザーアカウント・サーバー側プロフィールは持たない**: 表示名やデフォルト値の保存は各端末ローカルに限る（US10 の「保存」は端末ローカル）。複数端末間でのプロフィール同期は将来枠。
- **任意フィールドの自由編集に対するリッチエディタ・書式（Markdown プレビュー編集 UI 等）は最小限**: お題編集（US3）は内容を差し替えられれば足り、高度なエディタ体験は本 v2 のスコープ外。

## 前提

- v1 実装（pnpm モノレポ: 純粋ドメイン / 同期サーバー / フロント）が稼働しており、本 v2 はその上に体験を再構築する。
- 「AI 機能は本当についている？」への現状回答: v1 はコード上 BYOK プロバイダを持つが、**鍵を設定する UI 導線が無く、既定では定型お題に縮退する**ため、利用者からは AI が「効いていない」ように見える。本 v2 はこの可視化（US4）を要件に含める。
- 元になった単一ファイル版（アーティファクト）は、API キーなしで Anthropic API を直接叩いており、実質的に常に定型へ縮退していた。これも「AI が効いていない」の一因であり、v2 では出所明示と設定導線で解消する。
- 交代間隔の既定は 5 分、選択肢は 3/5/7/10/15 分。メンバーは 2〜10 人。言語 10 種・難易度 3 種（v1 準拠）。
- ビジュアル方向性は「集中・ステージ型（ダーク基調・タイマー主役・現ドライバーをスポットライト・交代の瞬間のみ強い演出）」に確定。セッション主役は「今・誰・あと何分」。UX の核は「招待/参加が一瞬・誤操作させない・状態が常に分かる」。
- **AI トークン残量について（US4 の技術的背景）**: 利用者が使う AI（本人鍵での生成）は各応答で消費トークン（usage）を返すが、**アカウントのクレジット残量は API から取得できない**（管理コンソールでのみ確認可能）。そのため「残量メーター」は実現困難であり、利用者の本質ニーズ「今日は使わないと自分で決める」は出題モードのオン/オフ（FR-042/043）で満たす。任意で「直近の生成にかかった概算トークン」を参考表示する余地はあるが、残量制御は行わない（plan.md で要否を判断）。
- **US9/US10 は v1 の既存能力の再利用が多い**: 表示名・役割・在席状況・復帰トークン・ホスト委譲・full snapshot 同期は v1 同期サーバーに実装済みの能力であり、v2 では主にこれらを「体験として表に出す（UI 導線・可視化・操作）」ことが中心になる。代理追加（プレースホルダ参加者）・一時離脱・お題編集/持ち込みの同期は新規能力で、plan.md でドメイン/契約への影響を確定する。
- **お題編集・持ち込みの同期範囲**: 共有ルームでは編集/持ち込み後のお題も全参加者へ同一反映する（FR-041）。誰が編集できるか（役割）は権限（FR-055）に従い、plan.md で確定する。
- 具体的な性能しきい値・同期遅延の数値・デザイントークンの値（色・余白・タイポ・焦点サイズ）・招待リンクの形式・各画面のレイアウト（ワイヤー）は `plan.md` で確定する。
