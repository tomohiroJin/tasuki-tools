# Example Map: 役割・権限と観覧

> 対象ユーザーストーリー: US5（役割・権限と遅延参加/観覧）

## 🟨 ストーリー（黄）

主催者として、参加者の役割（主催者・編集者・観覧者）を管理し、見学だけの参加も許したい。
なぜなら、見知らぬ第三者の操作を防ぎつつ、観覧者も巻き込みたいからだ。

## 🟦 ルール（青）

- ルールA: 新規参加者の既定の役割は観覧者である（FR-016, US5-AC1）
- ルールB: 観覧者は状態を変える操作を行えず、閲覧のみ許される（US5-AC3, FR-017）
- ルールC: 主催者限定の操作（完成・リセット・役割変更・フェーズ変更・休憩）は、主催者以外には拒否される（FR-017）
- ルールD: 主催者が参加者の役割を変更すると、その役割に応じて操作可否が更新される（US5-AC4, FR-016）
- ルールE: 権限はコマンドごとに検証される（FR-017）

## 🟩 具体例（緑）

### ルールA: 既定は観覧者

- **正例**: 利用者が有効なコードでルームに参加すると、その参加者の役割は観覧者として登録される — _根拠: spec §FR-016, §US5-AC1_

### ルールB / C: 観覧者・非主催者の操作拒否

- **負例**: 観覧者がセッション操作（開始・スキップ等）を要求すると、その操作は拒否される — _根拠: spec §US5-AC3, §FR-017_
- **負例**: 観覧者がリセットを要求すると拒否される — _根拠: spec §FR-017_
- **負例**: 観覧者がフェーズ変更を要求すると拒否される — _根拠: spec §FR-017_

### ルールD: 役割変更による操作可否の更新

- **正例**: 主催者が観覧者を編集者へ昇格させると、その参加者はセッション操作を行えるようになる — _根拠: spec §US5-AC4, §FR-016_
- **負例**: 観覧者が他の参加者の役割変更を要求すると拒否される（役割変更は主催者限定） — _根拠: spec §FR-017_

### ルールE: コマンドごとの検証

- **負例**: 主催者の役割そのものを役割変更操作で剥奪しようとしても、主催者の役割は変更できない — _根拠: spec §FR-018（委譲は別経路）／実装の保護。spec に直接の明記がないため下の赤に再掲_

## 🟥 オープン質問（赤）
