# Example Map: ルーム作成・参加・共有タイマーで交代

> Example Mapping（Matt Wynne）の4要素。赤（オープン質問）が残るうちは次段階に進まない。
> 対象ユーザーストーリー: US1（共有タイマーでドライバーを回す）/ US2（ルームを作って仲間と参加する）

## 🟨 ストーリー（黄）

モブプロのファシリテーターとして、ルームを作成して仲間を招き、設定した間隔でドライバーが
自動交代する共有タイマーを使いたい。なぜなら、別々の端末にいる全員が同じ残り時間と次の担当を
見て、滞りなく交代できるからだ。

## 🟦 ルール（青）

- ルールA: ルーム作成時、推測困難な一意のルームコードが発行され、作成者は主催者になる（FR-011, FR-016）
- ルールB: 有効なコードで参加すると、参加者は加入時点の最新状態を受け取る（US2-AC2, FR-013）
- ルールC: 無効・存在しないコードでの参加は、理由を添えて拒否される（US2-AC3）
- ルールD: 交代間隔に達すると、ドライバーは次の参加者へ自動的に進み、全員に反映される（FR-003, SC-002）
- ルールE: 手動スキップは残り時間を待たずに次のドライバーへ進める（FR-004）
- ルールF: 状態が変化すると、在室する全参加者が同一の現/次ドライバー・残り時間に追従する（FR-007, SC-001）

## 🟩 具体例（緑）

### ルールA: 一意コード発行と主催者登録

- **正例**: 利用者がルーム作成を要求すると、一意のルームコードが発行され、その利用者は主催者として登録される — _根拠: spec §FR-011, §FR-016, §US2-AC1_
- **負例**: （コード発行は内部生成のため利用者起因の負例なし。推測困難性は NFR セキュリティ S1 で別途担保）— _根拠: spec §NFRセキュリティ_

### ルールB: 加入時の最新状態提示

- **正例**: 主催者がメンバー構成を変更した後に別の利用者が有効なコードで参加すると、その参加者は変更後の最新メンバー構成を見る — _根拠: spec §US2-AC2, §FR-013_

### ルールC: 無効コードの拒否

- **負例**: 利用者が存在しないルームコードで参加を要求すると、参加は拒否され、ルームが見つからない旨が提示される — _根拠: spec §US2-AC3_

### ルールD: 自動交代

- **正例**: 3人のセッションが進行中、交代間隔が経過すると、現ドライバーが次の参加者へ自動で進み、全参加者の表示が新しい現/次ドライバーで一致する — _根拠: spec §FR-003, §SC-002_
- **境界（緑）**: 末尾の参加者がドライバーのとき交代すると、先頭の参加者へ折り返す — _根拠: spec §FR-003（ローテーション）, §FR-008（currentIndex 有効範囲）_

### ルールE: 手動スキップ

- **正例**: 残り時間が十分ある状態で参加者がスキップを要求すると、残り時間を待たずに次のドライバーへ進む — _根拠: spec §FR-004, §US1-AC3_

### ルールF: 全参加者の追従

- **正例**: ある参加者が交代を起こすと、在室する全参加者が同一の現ドライバー・次ドライバーを見る — _根拠: spec §FR-007, §SC-001_
- **正例（遅延参加）**: セッション進行中に後から参加した利用者は、現在の正しい現ドライバーと残り時間に追従する — _根拠: spec §US1-AC4_
