# 機能仕様: TDD Mob Pro Timer

**ブランチ/ディレクトリ:** `docs/plans/tdd-mob-pro-timer` ・ **ステータス:** Draft ・ **フロー:** 設計優先（v3.0 設計書から実現可能な要件を導出）

> 本仕様は技術非依存（何を・なぜ）に徹する。アーキテクチャ・ランタイム・ライブラリ・同期方式・API 名などの「どう作るか」は、承認後に `plan.md` で扱う。出典は `tdd-mob-pro-timer-spec-v3.0-final.md`。

## 概要

モブプログラミングを TDD で実践するチームのための、**交代タイマー兼お題出題ツール**。2〜10 人のチームが、設定した間隔で「ドライバー（キーボードを打つ人）」を自動的に回し、全員が同一のカウントダウンと同一のセッション状態をほぼ即時に共有する。お題（プログラミング課題）は自動生成または定型バンクから出題され、セッション完了時には所要時間・交代回数などの記録が残る。一人での練習にも対応する。

解決する課題: リモート/対面のモブプロでは「いま誰がドライバーか」「あと何分か」「次は誰か」がずれやすく、交代の合図・休憩・引き継ぎの文脈共有が属人化しがち。これらをチーム全員に対して一元化・可視化し、TDD のリズム（小さく回す）を支える。

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 共有タイマーでドライバーを回す（優先度: P1）

モブプロのファシリテーターとして、設定した間隔でドライバーが自動交代する共有タイマーがほしい。なぜなら、全員が同じ残り時間と次の担当を見て、滞りなく交代できるからだ。

**受け入れ基準（EARS）:**
1. セッションが進行中の間、システムは全参加者に対して**同一の残り時間**（端末間の表示差は非機能要件で定める ±1 秒以内）と現ドライバー・次ドライバーを表示しなければならない。
2. 交代間隔に達したとき、システムはドライバーを次の参加者へ自動的に進め、全参加者に交代を通知しなければならない。
3. 参加者が手動スキップ（次へ）を要求したとき、システムは残り時間を待たずに次のドライバーへ進めなければならない。
4. もし参加者が後から（遅れて）状態を受信したなら、システムはその参加者を**現在の正しい状態**（誰がドライバーか・残り時間）に追従させなければならない。
5. セッション進行中の間、システムは現ドライバーの累計担当回数・総交代回数・経過時間（停止中を除外）を保持・表示しなければならない。

### ユーザーストーリー2 — ルームを作って仲間と参加する（優先度: P1）

チームのメンバーとして、ルームを作成し共有 URL から仲間を招き入れたい。なぜなら、別々の端末から同じセッションに集まりたいからだ。

**受け入れ基準（EARS）:**
1. 利用者がルーム作成を要求したとき、システムは推測困難な一意のルームコードを発行し、作成者を主催者として登録しなければならない。
2. 利用者が有効なルームコードで参加を要求したとき、システムはその利用者をルームに加え、加入時点の最新状態を提示しなければならない。
3. もし利用者が無効・存在しないルームコードで参加を要求したなら、システムは参加を拒否し理由を提示しなければならない。
4. ルームの状態（メンバー・設定・フェーズ・タイマー・在室状況）が変化したとき、システムは在室する全参加者へ更新後の状態を反映しなければならない。

### ユーザーストーリー3 — TDD のお題を出題する（優先度: P1）

モブの参加者として、言語・難易度に応じた TDD のお題（要件と例示テストつき）を出題してほしい。なぜなら、毎回お題を考える手間なくセッションを始めたいからだ。

**受け入れ基準（EARS）:**
1. 利用者がお題を要求したとき、システムは選択された言語・難易度に沿ったお題（タイトル・説明・要件一覧・例示テスト・ヒント）を提示しなければならない。
2. AI 生成が利用できる場合、システムは AI 生成のお題を提示し、その出所が AI 生成であることを示さなければならない。
3. もし AI 生成が利用不可・失敗・不正な形式であったなら、システムは定型お題バンクへ縮退し、その出所が定型であることを示し、**画面を壊してはならない**。
4. 共有ルームでお題が確定したとき、システムは全参加者へ同一のお題を提示しなければならない。
5. お題の生成中の間、システムは全参加者へ「生成中」であることを表示しなければならない。

### ユーザーストーリー4 — 一時停止・完成・リセット（優先度: P1）

参加者として、セッションを一時停止/再開し、完成時に記録を残し、必要ならリセットしたい。なぜなら、中断や達成を正しく扱い、所要時間を正確に測りたいからだ。

**受け入れ基準（EARS）:**
1. 利用者が一時停止を要求したとき、システムはカウントダウンを停止し、経過時間の積算を止めなければならない。
2. 利用者が再開を要求したとき、システムは停止時点の残り時間からカウントダウンを再開しなければならない。
3. セッションが完成として確定されたとき、システムは完成記録（お題・言語・難易度・所要時間・メンバー・総交代回数・完成日時）を生成しなければならない。
4. 利用者がリセットを要求したとき、システムは破壊的操作である旨を扱った上でセッションを初期（設定）状態へ戻さなければならない。

### ユーザーストーリー5 — 役割・権限と遅延参加/観覧（優先度: P2）

主催者として、参加者の役割（主催者・編集者・観覧者）を管理し、途中参加や見学だけの参加も許したい。なぜなら、見知らぬ第三者の操作を防ぎつつ、観覧者も巻き込みたいからだ。

**受け入れ基準（EARS）:**
1. 新規参加者が加わったとき、システムは既定の役割を**観覧者**として登録しなければならない。
2. 操作（設定変更・フェーズ変更・完成・リセット・役割変更・休憩）が要求されたとき、システムはその操作に必要な役割を**コマンドごとに**検証し、権限がなければ拒否しなければならない。
3. 観覧者である間、システムはセッションの閲覧を許可しつつ、状態を変更する操作を拒否しなければならない。
4. 主催者が参加者の役割を変更したとき、システムはその役割に応じて操作可否を更新しなければならない。
5. ルームに参加者がいる間、システムは在室する全参加者と各人の在室状況（オンライン/離席/オフライン）・現/次ドライバーを常時一覧表示しなければならない。

### ユーザーストーリー6 — 再接続・復帰とホスト不在耐性（優先度: P2）

リモート参加者として、回線切断後に自動で復帰し、主催者が落ちてもセッションが続いてほしい。なぜなら、不安定な環境でもモブを止めたくないからだ。

**受け入れ基準（EARS）:**
1. 接続が切れたとき、システムは自動再接続を試み、復帰時に**同一参加者・同一役割**として扱わなければならない。
2. 再接続が成功したとき、システムは最初に受信する状態で完全に同期しなければならない。
3. もし主催者が猶予時間を超えて不在になったなら、システムは在室する最古の編集者へ主催者権限を自動委譲しなければならない。
4. もしサーバー側のセッションが失われた（例: 再起動）なら、システムは「セッション終了」を参加者へ明示し、各端末のローカル記録は保持しなければならない。

### ユーザーストーリー7 — モブ実践支援（ナビゲーター・休憩・強い通知・引き継ぎ）（優先度: P2）

モブの実践者として、ナビゲーター役の明示・休憩・目立つ交代通知・引き継ぎメモを使いたい。なぜなら、これらが進行と遠隔での文脈共有を保つからだ。

**受け入れ基準（EARS）:**
1. ナビゲーター明示が有効な場合、システムは現ドライバーに加えてナビゲーター役を UI 上で明確に示さなければならない。
2. 強い交代通知が有効な場合、交代の瞬間に、システムは目立つ全画面の割り込み（＋音）で交代を提示しなければならない。
3. 主催者が休憩開始を要求したとき、システムは全参加者のタイマーを止め、休憩中であることを表示しなければならない。
4. 休憩設定された巡回数に達したとき、システムは休憩を提案しなければならない。
5. 引き継ぎメモが更新されたとき、システムは次の交代時に次ドライバーへそのメモを目立つ形で提示しなければならない。

### ユーザーストーリー8 — 共有 URL/QR と記録の入出力（優先度: P2）

参加者として、ルームを QR や URL で手早く共有し、完成記録を端末に残して持ち運びたい。なぜなら、招待を簡単にし、過去の成果を蓄積したいからだ。

**受け入れ基準（EARS）:**
1. ルームが存在する間、システムは参加用 URL とルームコードのワンタップコピーおよび QR 表示を提供しなければならない。
2. セッションが完成したとき、システムは完成記録を**各端末のローカル**に永続化しなければならない。
3. 利用者が記録の書き出しを要求したとき、システムは記録を持ち運び可能な形式で出力しなければならない。
4. 利用者が記録の読み込みを要求したとき、システムは出力した形式の記録を取り込まなければならない。

### ユーザーストーリー9 — 一人で練習（ソロモード）（優先度: P3）

一人の学習者として、仲間なしでも同じタイマーとお題でモブの所作を練習したい。なぜなら、サーバーや共有なしで手早く始めたいからだ。

**受け入れ基準（EARS）:**
1. 利用者がソロ練習を選んだとき、システムは**共有経路を通らず完全にローカル**でセッションを完結させなければならない。
2. ソロモードの間、システムは共有セッションと同一の交代・一時停止・経過時間の振る舞いを再現しなければならない。
3. ソロモードの間、システムは外部への通信なしでお題（定型、または利用者の鍵がある場合は AI）を提供しなければならない。

### ユーザーストーリー10 — 通知・スリープ防止・アクセシビリティ（優先度: P3）

参加者として、自分の番が来たら気づけて、画面が消えず、支援技術でも使えるようにしたい。なぜなら、見落としや操作不能を避けたいからだ。

**受け入れ基準（EARS）:**
1. セッション進行中の間、システムは画面のスリープを抑止し、可視状態へ復帰したとき抑止を再取得しなければならない。
2. 自分がドライバーになったとき、画面が非アクティブなら、システムは（許可がある場合）通知し、モバイルでは振動を併用しなければならない。
3. モーション軽減設定が有効な場合、システムは紙吹雪・回転などの過度な演出を抑え、強い全画面通知も控えめ版へ切り替えなければならない。
4. 交代・残り 10 秒・一時停止・休憩が起きたとき、システムは支援技術向けにそれらを読み上げ可能な形で通知しなければならない。

### ユーザーストーリー11 — 国際化（優先度: P3）

日本語話者の利用者として、UI とお題・エラー文言を日本語で読みたい（英語にも切替可）。なぜなら、母語で迷わず使いたいからだ。

**受け入れ基準（EARS）:**
1. 表示言語が日本語の間、システムは UI 文字列・定型お題・エラー文言を日本語で表示しなければならない。
2. 利用者が表示言語を英語へ切り替えたとき、システムは対象文字列を英語で表示しなければならない。

## 機能要件 *(必須)*

**セッション / タイマー（コア）**
- **FR-001**: システムはセッションのフェーズを `setup → ready → session → celebration` の順で管理し、完成後は `setup` へ戻せなければならない。
- **FR-002**: システムは交代間隔を 3 / 5 / 7 / 10 / 15 分から選べ、既定を 5 分としなければならない。
- **FR-003**: システムは交代間隔に達した時点でドライバーを次の参加者へ自動的に進めなければならない。
- **FR-004**: システムは手動スキップ要求により残り時間を待たずに次ドライバーへ進めなければならない。
- **FR-005**: システムは一時停止でカウントダウンと経過時間積算を止め、再開で残り時間から続行しなければならない。
- **FR-006**: システムは経過時間を**稼働区間のみ積算**し、停止中の時間を含めてはならない。
- **FR-007**: システムは全参加者へ同一の残り時間・現ドライバー・次ドライバー・在室状況を提示しなければならない。
- **FR-008**: システムは不変条件「ローテーション人数と各人の担当回数配列の長さが一致」「現ドライバー指標が有効範囲内」を、あらゆる操作後に保たなければならない。
- **FR-009**: システムはメンバーの追加・削除・並べ替えを許し、人数は 2〜10 人の範囲に制限しなければならない。
- **FR-010**: もしメンバー名が重複・空、または人数上限超過・最小人数割れなら、システムはその操作を拒否し理由を返さなければならない。

**ルーム / 参加 / 同期**
- **FR-011**: システムは推測困難な一意ルームコードを発行し、URL への埋め込み・コピー・QR 表示を提供しなければならない。
- **FR-012**: システムは参加者の接続識別子と安定した参加者識別子を分離し、再接続後も同一参加者として扱えなければならない。
- **FR-013**: システムは状態変化のたびに在室全参加者へ**完結した最新状態**を配信し、受信側はそれで状態を置き換えられなければならない。
- **FR-014**: システムは在室状況（オンライン/離席/オフライン）を状態に含め、単なる生存確認では配信を間引き、遷移・入退室時に配信しなければならない（snapshot 配信を促す「状態変化」に単なる生存通知は含まない）。
- **FR-015**: システムは自分の離散操作（メンバー編集・設定・フェーズ）を即時に画面へ反映し、最終的にサーバーの最新状態へ収束しなければならない。

**役割 / 権限 / ライフサイクル**
- **FR-016**: システムは役割を主催者・編集者・観覧者の三段で管理し、新規参加者の既定を観覧者としなければならない。
- **FR-017**: システムは完成・リセット・役割変更・フェーズ変更・休憩を主催者限定とし、設定変更・お題操作・セッション操作・引き継ぎメモを編集者以上に限定し、**コマンドごとに**権限を検証しなければならない。
- **FR-018**: システムは主催者が猶予時間を超えて不在のとき、最古のオンライン編集者へ主催者権限を自動委譲しなければならない。
- **FR-019**: システムは再接続の自動試行と、復帰用トークンによる同一参加者・同一役割での復帰を提供しなければならない。
- **FR-020**: システムはサーバー側セッション喪失時に参加者へ「セッション終了」を明示し、ローカル記録を保持しなければならない。

**お題**
- **FR-021**: システムはお題を `タイトル・説明・要件一覧・例示テスト・ヒント` の構造で提示しなければならない。
- **FR-022**: システムは言語 10 種・難易度 3 種の選択に応じてお題を出題しなければならない。
- **FR-023**: システムは AI 由来のテキストを**信頼しないデータ**として扱い、お題の構造へ検証してから使用しなければならない。
- **FR-024**: システムは AI 生成失敗時に定型バンクへ縮退し、出所（AI 生成 / 定型）をバッジ表示しなければならない。
- **FR-025**: システムは共有ルームでは代表となる参加者がお題を生成・投入し、確定後に全員へ同一のお題を反映しなければならない。
- **FR-026**: もし代表候補が期限内に投入できなかった/離脱した/失敗したなら、システムは次候補へ再委譲し、全候補が失敗したら定型で確定しなければならない。
- **FR-027**: システムはお題再生成（リロール）で旧依頼をキャンセルしなければならない。

**記録**
- **FR-028**: システムは完成記録（お題・言語・難易度・所要時間・メンバー・総交代回数・完成日時）を各端末のローカルに永続化しなければならない。
- **FR-029**: システムは完成記録の書き出し・読み込み（持ち運び可能形式）と、お題の書式付きコピーを提供しなければならない。

**モブ実践支援**
- **FR-030**: システムはナビゲーター役の明示・強い交代通知・引き継ぎメモ・休憩（手動開始/終了および巡回数による提案）を、それぞれ設定で切り替え可能にしなければならない。

**ソロモード**
- **FR-031**: システムはソロ練習を共有経路を通さず完全ローカルで提供し、共有セッションと同一の交代・一時停止・経過時間ロジックを用いなければならない。

**ユーザビリティ / アクセシビリティ / i18n**
- **FR-032**: システムはセッション中の画面スリープ抑止と、可視復帰時の再取得を行わなければならない。
- **FR-033**: システムは自分の番の通知（許可制）とモバイルの振動併用を提供しなければならない。
- **FR-034**: システムはモーション軽減設定を尊重し、過度な演出と強い全画面通知を控えめ版へ切り替えなければならない。
- **FR-035**: システムは交代・残り 10 秒・一時停止・休憩を支援技術向けに読み上げ可能な形で通知しなければならない。
- **FR-036**: システムは UI 文字列・定型お題・エラー文言を外部化し、日本語を主・英語を追加として切替可能にしなければならない。

## 非機能要件

- **性能 / 同期遅延**: 状態変化は在室参加者へほぼ即時に反映されること。基準値: **同一ネットワーク条件下で、状態変化の発生から在室参加者への反映完了までの遅延が P95 で 300ms 以内**、**参加者間の残り時間表示差が ±1 秒以内**、**操作（コマンド送信）から自端末への即時反映までが 100ms 以内**。これらは自動・準自動で計測可能な目標値とする。
- **セキュリティ**: 同期基盤は秘密情報を保持せず、状態は揮発とする。利用者の AI 鍵は同期基盤へ一切送らない。許可ドメインからの接続のみ受け付ける。境界で受信メッセージを一度だけ検証し、未知・過大・不正な入力を即時拒否する。ユーザー/AI 由来テキストの描画でスクリプト実行を許さない。詳細な脅威・対策は v3.0 §7 を `plan.md` に引き継ぐ。
- **可用性 / 運用**: サーバー再起動は「進行中セッションの終了」を意味するのみで、復旧手順を要しない（状態揮発・再起動安全）。
- **資源上限**: 同時接続・ルーム数・ルーム参加者数（最大 10）に上限を設け、アイドルなルームは時間経過で回収する。
- **アクセシビリティ**: キーボードのみで全操作可能。色のみに依存せずアイコン＋テキスト併記。コントラストを確保。モーダルはフォーカストラップ＋Esc。
- **プライバシー**: 既定で外部送信なし（AI 利用は本人の鍵による本人ブラウザからの通信のみ）。サーバーに保持・記録する個人データは表示名のみ・揮発。鍵・プロンプトを記録に残さない。

## 主要エンティティ

- **ルーム（Room）** — ルームコード、主催者、設定、現在のお題、セッション状態、タイマー状態、フェーズ、参加者一覧、揮発の表示用記録、引き継ぎメモ、休憩中フラグ。
- **参加者（Participant）** — 安定 ID と接続 ID（分離）、表示名、役割（主催者/編集者/観覧者）、在室状況、AI 鍵保有の自己申告、参加時刻。
- **セッション状態（SessionState）** — ローテーション（順序）、現ドライバー指標、一時停止フラグ、各人の担当回数、総交代回数。**時間系を含まない**。
- **タイマー状態（Timer/Clock）** — 稼働中フラグ、交代間隔、各種アンカー時刻と残り秒、稼働積算時間。**時間系の唯一の真実**。
- **お題（Problem）** — タイトル、説明、要件一覧、例示テスト、ヒント。
- **セッション設定（SessionConfig）** — 言語、難易度、メンバー、交代間隔、（任意）ナビゲーター有効・休憩巡回数・強い交代通知。
- **完成記録（CompletionRecord）** — ID、（任意）ルーム ID、お題タイトル、言語、難易度、所要時間、メンバー、総交代回数、完成日時。

## 成功基準 *(必須・技術非依存)*

- **SC-001**: 2〜10 人が別端末から同一ルームに参加し、交代・一時停止・再開・スキップの全操作で**全員の表示が食い違わない**（残り時間の端末間差が非機能要件で定める ±1 秒以内）。
- **SC-002**: 交代間隔の経過で**自動交代が起き、現/次ドライバーが全員一致**して更新される。
- **SC-003**: AI 生成が失敗・無効でも、利用者は**毎回お題を受け取れ、画面が壊れない**（定型へ確実に縮退）。
- **SC-004**: 一時停止を挟んでも、完成記録の所要時間は**停止時間を除いた稼働時間**と一致する。
- **SC-005**: 回線切断後、参加者は**自動で同一参加者・同一役割に復帰**し、最初の状態受信で完全同期する。
- **SC-006**: 主催者が不在になっても、猶予後に**別の編集者へ権限が委譲され**セッションが継続する。
- **SC-007**: 観覧者は閲覧でき、かつ**状態を変える操作が一切できない**。
- **SC-008**: 完成記録を一方の端末から書き出し、別の取り込みで**欠落なく復元**できる。
- **SC-009**: 一人でのソロ練習が、**共有・通信なしで**交代・一時停止・お題出題まで完結する。
- **SC-010**: ドメインの状態遷移（交代・一時停止・再開・メンバー編集）について、任意の操作列で不変条件（FR-008）が**常に保たれる**ことを自動テストで確認できる。

## スコープ外 / 非目標 *(必須)*

- **永続的なサーバー側状態**を持たない（ルームはサーバー再起動で失われてよい。チーム横断の恒久記録ストアは将来枠）。
- **差分同期（patch/revision）・ギャップ検知・部分ロールバック**は行わない（完結した状態の置き換えのみ）。
- **同期基盤が AI 鍵や AI 生成を代行しない**（運営鍵による代理 = managed、サブスク経由 = subscription は v1 スコープ外）。
- **time 系の楽観更新**（カウントダウン・交代のローカル先行）は行わない。
- **アカウント登録・ログイン・恒久ユーザー管理**は行わない（参加は表示名と揮発トークンのみ）。
- **コードエディタ・実コード実行・テスト実行環境**は提供しない（お題提示まで。実装はチームの実環境で行う）。
- ロビーの投票機能、ドライバー別の長期統計（XP 等）、テーマ切替、PWA は将来枠（あると良い）。

## 前提

- 想定規模は 2〜10 人・共有状態は数百バイト程度（v3.0 §0）。
- 言語は 10 種、難易度は 3 種（具体的な内訳は現行プロトタイプ準拠）。
- 主催者不在の自動委譲の猶予は既定 30 秒（v3.0 §4）。
- 復帰用トークンの保持は既定で**セッション内のみ**（端末を閉じると失効しうる）。永続保持はオプトイン＋露出注意。
- 完成記録の恒久保存先は各端末のローカル（クライアント側）。サーバーが持つ記録は表示用の揮発コピー。
- 失敗参加・コマンドのレート制限、アイドル回収の具体閾値は運用設定値として `plan.md` で定める。
