# 機能仕様: ADR を #28 後の実態に合わせる

**Issue:** [#33](https://github.com/tomohiroJin/tasuki-tools/issues/33) ・ **ディレクトリ:** `docs/plans/adr-alignment-post-refactor` ・ **ステータス:** Draft（要件レビュー中） ・ **フロー:** 要件優先（Issue 分析から導出）

> 本仕様は技術非依存（何を・なぜ）に徹する。ADR のどの行をどう書き換える／追記するかという
> 「どう作るか」は承認後に `plan.md` で扱う。

## 概要

Issue #28（コードベースの構造是正）で **ソロモードの撤去**・**契約の型付け**・**テスト規約の移行完了**が
実施された。その結果、`tdd-mob-pro-timer/docs/adr/` 配下の一部の ADR が実態と食い違っている。

ADR（Architecture Decision Record）は「なぜその設計判断をしたか」の記録であり、**過去の判断そのものを
書き換えてはならない**。しかし今回のズレは一様ではなく、性質が異なる 2 種類が混在している。

1. **単に事実として偽になっている記述** — 決定にも根拠にも関係なく、単純に更新を怠った結果、
   本文とインデックスが矛盾している（ADR-0009 のステータス）。あるいは、決定は今も有効だが、
   決定を支える説明の一部が現存しない機能に言及しており、そのままでは読み手を誤らせる
   （ADR-0002 の「利点」）。これらは**本文を実態に合わせて直す**。
2. **今も有効な決定の、失われた根拠を記録する必要がある記述** — 決定（core を共有パッケージに
   切り出す）自体は今も有効だが、決定当時の根拠（「ソロと共有の一致」）を成立させていた前提
   （ソロモード）が消えた（ADR-0001）。この場合は**本文を書き換えず、追記で経緯を残す**。

**この 2 つを区別して手当てすることが、本仕様の核心である。** 区別を誤ると、本来「追記で経緯を
残すべき」判断の記録（0001）を書き換えてしまい、ADR が本来持つべき「決定当時の思考の記録」という
性質を壊す。逆に、単なる事実の誤りをいつまでも「追記待ち」にすると、本文とインデックスの矛盾
（0009）を読み手が延々と見せられ続ける。

### 対象範囲（Issue #33 の論点 1〜3 のみ）

| # | 対象 ADR | ズレの性質 | 手当ての方針 |
|---|---|---|---|
| 1 | ADR-0009（テスト規約） | 本文のステータス行がインデックス（`README.md`）と食い違っている。移行は #28 の T084 で 148 ファイル全件完了済み | 本文を実態（移行完了）に合わせて修正する |
| 2 | ADR-0002（Decider パターン） | 「利点」に、撤去済みのソロモードへの言及（「サーバーとソロが同じ `decide`/`evolve` を呼ぶため挙動が一致する」）が残っている | 決定（Decider パターン採用）は維持したまま、利点の記述を実態（`apps/sync` と `apps/web` が core を共有する構図）に合わせる |
| 3 | ADR-0001（モノレポ + 共有 core） | 「共有」の存在理由が「ソロと共有の一致」に依拠しているが、ソロモードは #28 で撤去済み。決定（core を共有パッケージにする）自体は今も有効（`apps/sync` と `apps/web` が共有） | 既存の本文（背景・決定・影響）は書き換えず、更新の経緯を記した追記セクションを末尾に加える |

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — ADR を読む開発者が、どちらが正しいか判断せずに済む（優先度: P1）

ADR を読む開発者として、ADR 本体とインデックス（`README.md`）の記述に矛盾があるとき、
**どちらが正しいか自分で判断せずに済む**ようにしたい。なぜなら、矛盾したまま放置されると、
移行状況を確認するたびに両方のファイルを突き合わせる手間が発生し、しかもその突き合わせ自体が
毎回同じ結論（インデックスが正しい）に達するだけの無駄な作業になるからだ。

**受け入れ基準（EARS）:**

1. ADR-0009 の本体ステータス行を読んだとき、システム（ドキュメント一式）は
   `README.md` の該当行と矛盾しない状態を示さなければならない。
2. ADR-0009 の移行状況を確認する開発者は、本体だけを読んでも `README.md` だけを読んでも
   同じ結論（移行完了・148 ファイル全件）に達しなければならない。

### ユーザーストーリー2 — ADR を読む開発者が、現存しない機能を根拠にした説明を信じてしまわない（優先度: P1）

ADR-0002 を読む開発者として、「利点」に書かれた説明が**現存する構成要素だけを根拠にしている**
ことを期待したい。なぜなら、撤去済みのソロモードを根拠にした説明を信じたまま作業すると、
「ソロと共有で挙動が一致することを検証するテストがどこかにあるはずだ」のような誤った期待を
持ったままコードを探し、存在しないものを探して時間を失うからだ。

**受け入れ基準（EARS）:**

1. ADR-0002 の「利点」を読んだとき、システムはソロモードへの言及を含まない説明を
   示さなければならない。
2. ADR-0002 の「利点」を読んだとき、システムは `apps/sync` と `apps/web` が
   core の `decide`/`evolve` を共有するという、現存する構図を根拠として示さなければならない。
3. ADR-0002 の「決定」（Decider パターンの採用）は、利点の記述修正の前後で
   変更されていてはならない。

### ユーザーストーリー3 — ADR を読む開発者が、決定は生きているが根拠は変わったことを正しく理解する（優先度: P1）

ADR-0001 を読む開発者として、「core を共有パッケージにする」という決定が**今も有効であること**と、
「その決定を下した当時の根拠（ソロと共有の一致）はもう成立しないこと」の**両方**を、
本文の書き換えではなく読み取れるようにしたい。なぜなら、決定当時の思考をそのまま消してしまうと、
「なぜ当時ソロモードのために共有化したのか」という設計判断の履歴が失われ、後から
「もう根拠が無いなら共有化自体をやめてよいのでは」という誤った再検討を招きかねないからだ。

**受け入れ基準（EARS）:**

1. ADR-0001 を読んだとき、システムは背景・決定・影響の既存の記述（ソロモードへの言及を
   含む）をそのまま示さなければならない（削除・書き換えをしてはならない）。
2. ADR-0001 を読んだとき、システムは既存の記述に加えて、更新日付を持つ追記セクションを
   示さなければならない。
3. 追記セクションを読んだとき、開発者は「決定（core を共有パッケージにする）は今も有効である」
   ことを読み取れなければならない。
4. 追記セクションを読んだとき、開発者は「根拠がソロと共有の一致からサーバーと共有フロントの
   一致に変わった」ことを読み取れなければならない。
5. ADR-0001 と ADR-0002 の両方でソロモードへの言及が扱われる文書を横断して読んだとき、
   開発者は「ADR-0001 は追記のみ・ADR-0002 は本文修正」という非対称な扱いの理由
   （構成的か付随的かの判定、FR-147）を、いずれかの文書の記述から読み取れなければ
   ならない。

### ユーザーストーリー4 — 機械的検証で手当ての漏れ・過剰修正を検出できる（優先度: P2）

このドキュメント変更をレビューする開発者として、**目視だけに頼らず**、ステータス文字列の一致・
ソロ語の残存・相対リンクの解決可否を機械的に確認したい。なぜなら、ドキュメント変更は
テストスイートで検証できないため、レビューが見落とすと矛盾がそのまま残ってしまうからだ。

**受け入れ基準（EARS）:**

1. 検証を実行したとき、システムは ADR-0009 本体と `README.md` のステータス文言が
   矛盾していないことを確認しなければならない。
2. 検証を実行したとき、システムは ADR-0002 の本文に「ソロ」という語が
   残っていないことを確認しなければならない。
3. 検証を実行したとき、システムは ADR-0001 の既存本文が変更されておらず、
   追記セクションのみが増えていることを確認しなければならない。
4. 検証を実行したとき、システムは `tdd-mob-pro-timer/docs/adr/` 配下の相対リンクが
   すべて解決可能であることを確認しなければならない。

## 機能要件 *(必須)*

- **FR-139**: システムは、ADR-0009 本体のステータス行を、`README.md` の該当行と
  意味的に矛盾しない文言（移行完了・148 ファイル全件）に修正しなければならない。
- **FR-140**: システムは、ADR-0002 の「利点」からソロモードへの言及を
  除去しなければならない。
- **FR-141**: システムは、ADR-0002 の「利点」を、`apps/sync` と `apps/web` が
  core の `decide`/`evolve` を共有するという現存の構図を根拠にした記述に
  置き換えなければならない。
- **FR-142**: システムは、ADR-0002 の「決定」節（Decider パターンの採用そのもの）を
  変更してはならない。
- **FR-143**: システムは、ADR-0001 の既存の本文（背景・決定・影響。ソロモードへの
  既存の言及を含む）を書き換えてはならない。
- **FR-144**: システムは、ADR-0001 に、更新日付を持つ追記セクション（例:
  `## 更新 (YYYY-MM-DD)`）を末尾に追加しなければならない。
- **FR-145**: 追記セクションは、決定（core を共有パッケージにする）が
  依然有効であることを明記しなければならない。
- **FR-146**: 追記セクションは、決定の根拠が「ソロと共有の一致」から
  「サーバー（`apps/sync`）と共有フロント（`apps/web`）の一致」に変わったことを
  明記しなければならない。
- **FR-147**: システムは、事実として偽になっている記述（0009 のステータス、0002 の利点）と、
  決定は有効だが根拠が変わった記述（0001）を区別し、前者には本文修正、後者には追記という
  異なる手当てを適用しなければならない。同一の手当てで両者を扱ってはならない。
  この区別は次の判定規則によらなければならない：
  - ある ADR の「影響」節等に含まれるソロモードへの言及が、その ADR の**決定にとって
    構成的か付随的か**を判定する。
  - **付随的**（決定の論理がソロの存在に依存しない。ソロへの言及が利点の一例示に
    すぎず、他の具体例に置き換えても決定の論理が変わらない）場合 → **本文修正**を適用する。
  - **構成的**（決定の存在理由そのものがソロに依拠しており、背景・関連要件の全体が
    ソロ vs 共有の二重実装回避で構成されている）場合 → **本文は保存し、追記で経緯を
    残す**。この場合、影響節の一文だけを書き換えると背景・関連要件がソロ前提のまま
    残り、文書が内部で矛盾するため、部分的な書き換えを行ってはならない。
  - ADR-0002（Decider パターン）はソロと無関係に成立する決定であるため付随的、
    ADR-0001（モノレポ+共有 core）は関連要件 FR-031「ソロと共有で同一ロジック」に
    直接依拠するため構成的と判定する。この判定の結果が、この 2 つの ADR で
    扱いが分かれる理由である。
- **FR-148**: システムは、ADR-0002 の「Decider パターンの適用がハンドラ経路で破れている」
  という論点（Issue #33 の論点4）について、本変更で ADR 本体を変更してはならない
  （Issue #26 側の対応とする）。
- **FR-149**: システムは、`tdd-mob-pro-timer/docs/adr/` 配下のコード（`tdd-mob-pro-timer/apps/`,
  `tdd-mob-pro-timer/packages/`）を変更してはならない。変更はドキュメントに限る。

## 非機能要件

- **検証可能性**: すべての変更は、テストスイートの実行ではなく機械的な文字列検証
  （grep・diff・相対リンク解決チェック）で合否判定できること。
- **不変性の尊重**: ADR-0001・ADR-0002 の「決定」節の文言は、本作業のいかなる手当てでも
  一切変更されないこと。
- **可読性**: 追記セクションは既存の Michael Nygard 形式（背景/決定/影響）の直後に、
  見出しとして明確に区切って追加され、既存の節と混同されないこと。
- **保守性**: 今後同種のズレ（決定は有効だが根拠が変わる／単純に事実が古くなる）が
  発生したときに、どちらの手当て方針を取るべきかが本仕様の区別（FR-147）から
  判断できること。

## 主要エンティティ

| エンティティ | 説明 |
|---|---|
| ADR 本体 | `tdd-mob-pro-timer/docs/adr/000N-*.md`。背景・決定・影響・ステータスを持つ個別ファイル |
| ADR インデックス | `tdd-mob-pro-timer/docs/adr/README.md`。全 ADR の一覧とステータスの要約表 |
| 追記セクション | ADR 本体の末尾に加える、更新日付見出しを持つ節。既存の背景/決定/影響を書き換えずに経緯を残す |
| 事実ズレ | ADR の記述が現在のコード・状態と矛盾している箇所。性質により「本文修正対象」と「追記対象」に分類される |

## 成功基準 *(必須・技術非依存)*

  **1 件 → 0 件**になる。
- **SC-049**: ADR-0002 本文に含まれる「ソロ」という語の出現が **1 件 → 0 件**になる。
- **SC-050**: ADR-0001 の既存本文（追記セクション追加前の全行）が、追記セクション追加の

- **SC-051**: `tdd-mob-pro-timer/docs/adr/` 配下の相対リンクのうち、解決できないものが
  **0 件**である。

## スコープ外 / 非目標 *(必須)*

- **論点4（Decider パターンの破れを ADR-0002 に記録するか）** — Issue #33 が挙げる4つの論点の
  うち最も重要だが検討中の論点。`session.act SWITCH` 経路で `decide`/`evolve` の構図が
  破れている事実は `packages/core/test/driver-switch-equivalence.test.ts` に検証結果として
  残っているが、**「どちらの回数が正しいか」という振る舞いの設計判断は Issue #26（二重ルート統合）
  の担当範囲であり、ユーザーの判断により Issue #26 の PR に含める**。本仕様・本変更では
  ADR-0002 に既知の例外としての記録を追加しない。
- **ADR-0005（BYOK）への追記** — 既に `Superseded by 0008` であり、#28 でコードも撤去された。
  Superseded な ADR の実装が消えるのは自然な帰結であり、追記は不要と判断済み。
- **ADR-0006（Result 型・境界検証）への追記** — #28 で `ErrorCode` 列挙の導入により決定が
  強化される方向であり矛盾しない。「ハンドラの戻り値が本番で使われていない」という事実は
  0006 の射程外の新情報であり、本仕様では扱わない。
- **ADR-0003（サーバー権威時刻）・ADR-0004（full snapshot 同期）・ADR-0007（揮発インメモリ状態）** —
  #28 はこれらの決定に触れていない。対応不要と判断済み。
- **ADR-0010（設計文書の正本）** — #28 で新設された ADR であり、実態と一致している。
  対応不要と判断済み。
- **コードの変更** — `tdd-mob-pro-timer/apps/`, `tdd-mob-pro-timer/packages/` は一切変更しない。
- **テストスイートの実行・追加** — ドキュメントのみの変更であり、実行可能なテストコードの
  追加・変更は行わない（機械的検証はテストスイートではなくコマンドで行う。詳細は `plan.md`）。

## 前提

- Issue #28 の完了により、ソロモード（`apps/web/src/solo/`）はコードから完全に撤去済みである
  （本仕様の作成にあたり `tdd-mob-pro-timer/apps/web/src/solo` の不在と、
  `apps/web` 配下に "solo" という語を含む実装コードが残っていないことを確認済み。
  `Session.tsx` 等に残る `room.code !== "SOLO"` はルームコードの特殊値であり、
  撤去対象の「ソロモード機能」とは別概念のため対象外とする）。
- ADR-0009 の移行完了（148 ファイル全件）は `README.md` に既に反映済みであり、
  本仕様は ADR 本体側を追随させるだけで足りる（移行作業自体の再確認は不要）。
- ADR は Michael Nygard 形式（背景/決定/影響）に従う不変の記録という、
  `tdd-mob-pro-timer/docs/adr/README.md` 冒頭の原則を前提とする。
