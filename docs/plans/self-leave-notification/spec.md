# 機能仕様: 自己退出した本人に退出を伝え、入口へ戻す

**Issue:** [#32](https://github.com/tomohiroJin/tasuki-tools/issues/32) ・ **ディレクトリ:** `docs/plans/self-leave-notification` ・ **ステータス:** Draft（要件レビュー中） ・ **フロー:** 要件優先（実機フィードバックから導出）

> 本仕様は技術非依存（何を・なぜ）に徹する。通知の運び方・画面の遷移方式・部品の分割などの
> 「どう作るか」は承認後に `plan.md` で扱う。

## 概要

自分で「ルームから抜ける」を押した本人だけが、**抜けたことを知らされない**。
画面は退出前のまま残り、そこに映っている参加者一覧には自分がまだ居るように見える。
しかしサーバー側では既に退出が成立しているため、その画面から行うどの操作も拒否される。
利用者からは「抜けたのに抜けていない」「壊れた」と見える。

原因は、**自己退出だけが本人へ状態変化を伝える経路を持っていない**ことである。
他者に退出させられた場合は本人へ専用の通知が届き、それを受けて画面が入口側へ戻る。
自己退出ではその通知が意図的に抑止されている。抑止の意図（自分で押した操作を
「外されました」と伝えない）は妥当だが、**代わりの通知が用意されていない**。

さらに、退出が成立すると本人は在室者ではなくなるため、**残ったメンバーへ配信される
新しい参加者一覧が本人には届かない**。届く通知も無く、届く一覧も無い。
これが二重の取り残しになっている。

### この仕様が解く問題と、解かない問題

| | 扱い |
|---|---|
| 抜けた本人が抜けたと分からない | **本仕様で解く** |
| 抜けた本人の画面がどこへ向かうかが未定義 | **本仕様で決める** |
| 抜ける操作そのものが拒否される場合の見せ方 | **既存の担保を維持する**（下記「前提」） |
| 他者に退出させられた場合の挙動 | 変更しない（既に正しく動作している） |
| 残ったメンバーへの「◯◯さんが退出しました」通知 | 変更しない（既に正しく動作している） |

### 遷移先の決定 — 入口画面へ戻す

抜けた本人をどこへ運ぶかは、次の 2 つのどちらかである。

1. **参加画面**（直前のルームへ戻る手がかりを保持し、名前を入れ直せば戻れる）
2. **入口画面**（ルームへ戻る手がかりを持たず、新しいルームを作るところから始まる）

**本仕様は 2（入口画面）を採る。**

自分で抜ける操作は、他者に外される操作と**意図の方向が逆**である。外された人は多くの場合まだ
参加したいのであり、戻る手がかりを残すことが親切になる。自分で抜けた人は「もうこのルームでの
作業を終える」と判断して押している。そこへ「戻るには名前を入力してください」と促す画面を
出すのは、利用者が下したばかりの判断を押し返すことになる。

戻りたくなった場合の回復手段は失われない。ルームへの入り方は元々**招待の共有**であり、
招待を受け取った経路（チャット・共有リンク）はルームを抜けても消えない。
つまり「戻る手がかりを画面が保持していること」は復帰の必要条件ではない。

> **誤操作の危険との釣り合い。** 押し間違いで抜けてしまうと、招待を再度開くまで戻れない。
> ただしこの操作は**本人にしか押せず**、対象も自分自身に限られ、押した結果は
> 「自分がこのルームから離れる」ことだけである。他者の作業を壊さないので、確認を課すほどの
> 破壊力はない（この判断は既存の設計に従う）。回復コストは招待を開き直す 1 手であり、
> 誤操作の頻度と釣り合っている。

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 抜けたら抜けたと分かる（優先度: P1）

モブに参加している者として、「ルームから抜ける」を押したら**抜けたことがその場で分かり、
操作できない画面に取り残されたくない**。なぜなら、見えている画面と実際の状態が食い違うと、
操作が効かない理由が分からず、アプリが壊れたと受け取るからだ。

**受け入れ基準（EARS）:**

1. 参加者が自分自身の退出を要求し、それが受理されたとき、システムは**その参加者本人へ
   退出が成立したことを伝えなければならない**。
2. 参加者が自分自身の退出を要求し、それが受理されたとき、システムは本人の画面を
   **セッションの画面に留めてはならない**。
3. 本人へ退出の成立を伝えるとき、システムは**その退出が本人自身の操作によるものとして
   自然な説明**を示さなければならない。他者の操作によって退出させられたという説明を
   示してはならない。
4. 参加者が自分自身の退出を要求し、それが**拒否された**とき、システムは本人の画面を
   セッションの画面から離してはならない。

### ユーザーストーリー2 — 抜けた先が行き止まりでない（優先度: P1）

抜けた者として、**退出後の画面から次の行動が取れる**ようにしたい。
なぜなら、抜けた直後の画面が何もできない終端だと、ブラウザを閉じるしか選択肢がなくなるからだ。

**受け入れ基準（EARS）:**

1. 本人の退出が成立したとき、システムは**入口の画面**を示さなければならない。
2. 入口の画面を示すとき、システムは**直前のルームへ復帰するための手がかりを保持しては
   ならない**（退出は本人の意思であり、復帰は招待からやり直す）。
3. 本人の退出が成立したとき、システムは**そのルームに属していた画面上の状態
   （参加者一覧・持ち時間・お題・共有メモ・自分の識別）を保持してはならない**。

### ユーザーストーリー3 — 抜けたことが他の人にも伝わる（優先度: P3・既存の担保）

同じルームに残る者として、誰が抜けたのかを知りたい。

**受け入れ基準（EARS）:**

1. 参加者の退出が成立したとき、システムは残る在室者へ**誰が退出したか**を伝えなければならない。

> このストーリーは**既に満たされている**。自己退出の場合に「◯◯さんがルームから退出しました。」
> と伝える分岐も実装済みである。本仕様では**退行させないことだけを確認**する。

## 機能要件 *(必須)*

- **FR-124**: システムは、参加者が自分自身を対象として退出を要求し受理されたとき、
  本人へ「退出が成立した」ことを伝える通知を送らなければならない。
- **FR-125**: 本人へ送る退出の通知は、他者による退出（外された）と**区別できる種類**で
  なければならない。両者を同じ種類で伝えてはならない。
- **FR-126**: 本人へ示す退出の文言は、**本人自身の操作の結果として自然な表現**で
  なければならない。
- **FR-127**: システムは、本人の退出が成立したことを認識したとき、画面を**入口の画面**へ
  移し、直前のルームへ復帰するための手がかりを保持してはならない。
- **FR-128**: システムは、本人の退出が成立したことを認識したとき、そのルームに由来する
  画面上の状態（ルームの内容・自分の識別・接続・記録の途中状態）を**破棄**しなければならない。
- **FR-129**: システムは、退出の要求が**拒否された**場合には画面を移してはならない。
  拒否の理由は一時的な通知として示す。
- **FR-130**: 退出の通知の種類を新たに増やすとき、その種類について**利用者に何が見えるか**が
  定義されていなければならない。定義されていない種類を増やしてはならない。

## 非機能要件

- **可観測性**: 本人への通知が送られたかどうかは、サーバー側の振る舞いとして検証可能でなければならない。
- **アクセシビリティ**: 退出の通知は、既存の通知領域と同じ方式で提示し、読み上げに乗ること。
- **後方互換**: 配備の前から開いたままの画面が旧サーバーの応答を受け取り得るため、
  **既存の退出通知の種類を受け付けなくしてはならない**。
- **性能**: 退出から本人の画面が移るまでに、追加の往復通信を要さないこと。

## 主要エンティティ

| エンティティ | 説明 |
|---|---|
| 参加者 | ルームに属する人。自分自身を対象とした退出を要求できる |
| 退出の通知 | 退出が成立したことを本人へ伝える知らせ。**誰の操作によるか**で種類が分かれる |
| 画面の段階 | 入口 / 参加 / 待機 / セッション / 記録。退出の成立で入口へ移る |

## 成功基準 *(必須)*

- **SC-040**: 自分で退出した本人の画面が、セッションの画面に留まる事象が **0 件**になる。
- **SC-041**: 自分で退出した本人に示される文言に、他者の操作を示す表現（「〜させられました」等）が
  **含まれない**。
- **SC-042**: 退出後の画面から、直前のルームへ復帰する手がかりが**提示されない**。
- **SC-043**: 退出の要求が拒否されたとき、画面の段階が**変わらない**。

## スコープ外 / 非目標 *(必須)*

- **他者による退出の挙動の変更** — 現在の通知・遷移・文言をそのまま維持する。
- **退出の確認ダイアログの追加** — 自分の操作には確認を課さないという既存の判断に従う。
- **退出が拒否される条件そのものの見直し** — 「進行できる人が 1 名以上残る」制約や
  「最後のドライバーは外れられない」制約は変更しない。
- **拒否時の文言の作り直し** — 文言の具体性は Issue #29 の担当であり、本仕様では触らない。
- **退出の取り消し（元に戻す）機能**。
- **退出後にルームへ自動で復帰する仕組み**。
- **既定文言のまま表示されている他の通知種類の文言整備** — Issue #29 の担当。

## 前提

- 退出の要求が**拒否される**場合（進行できる人がいなくなる／最後のドライバー）については、
  **押せない状態にして理由を添える担保が既に存在する**。本仕様は拒否時に画面を移さないことだけを
  要件に持ち、拒否の見せ方は現状を維持する。
- 退出を要求できるのが誰かという権限判定は既に正しく、本仕様では変更しない。
- クライアントを持たない参加者（対面在席を表す代理）は通知の宛先にならない。
- 残る在室者への「誰が退出したか」の通知は、自己退出の場合の分岐も含めて既に実装済みである。
