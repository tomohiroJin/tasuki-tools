# 機能仕様: サーバー側の死活監視（WS ping/pong ヘルスチェック）

**ブランチ/ディレクトリ:** `fix/issue-25-server-heartbeat` ・ **ステータス:** Draft ・ **フロー:** 設計優先（Issue #25 に対応方針案が既に示されているため）

## 概要

参加者の在室状況（`presence`）が `offline` になる経路が、現状は WebSocket の `close` イベントのみである。サーバー側に死活監視（ハートビート）が存在しないため、回線断・端末スリープ・モバイルの背面化などで接続が「半開き」のまま残ると、その参加者は実際には応答不能であるにもかかわらず永久に `online` 扱いのままになる。

本機能は、サーバーが WebSocket の標準 ping/pong を用いて能動的に生存確認を行い、応答のない接続を所定時間内に検出して切断（`terminate`）することで、既存の `close` 経路に乗せて `presence` を正しく `offline` に収束させる。

## ユーザーシナリオとテスト

### ユーザーストーリー1 — 回線断で放置された参加者が offline になる（優先度: P1）

参加者として、自分の回線が突然切れた（Wi-Fi 切断・端末スリープ・電波不良等）とき、サーバーが自分の不在を自動的に検出してくれてほしい。なぜなら、そうでないと自分がドライバーやホストのまま部屋に「亡霊」として残り、他の参加者の進行（不在ドライバーの繰り上げ・ホスト委譲）を妨げるから。

**受け入れ基準（EARS）:**
1. 接続がサーバーの ping に対して連続して規定回数の pong を返さないとき、システムはその接続を切断し、既存の切断処理（`presence` を `offline` に更新するなど）を発火させなければならない。
2. 接続が pong を返している間、システムはその接続の `presence` を `offline` にしてはならない。

### ユーザーストーリー2 — 一時的な通信の揺れで誤って offline にされない（優先度: P1）

参加者として、瞬間的なネットワークの遅延やジッターが起きても、実際に在室しているのに `offline` 扱いにされたくない。なぜなら、誤検出はドライバー交代やホスト委譲を不必要に発火させ、セッション進行を乱すから。

**受け入れ基準（EARS）:**
1. 1回分の ping 応答が遅延・欠落しただけでは、システムは接続を切断してはならない（猶予として複数回の連続失敗を要求する）。
2. 直前まで応答が途切れていた接続が pong で復帰した場合、システムは失敗カウントをリセットしなければならない。

### ユーザーストーリー3 — 運用者が検出間隔・閾値を調整できる（優先度: P2）

運用者として、検出間隔と許容ミス回数を環境変数で調整したい。なぜなら、本番環境のネットワーク事情（プロキシのタイムアウト等）に応じてチューニングする必要があるから。

**受け入れ基準（EARS）:**
1. 環境変数が設定されているとき、システムはその値を検出間隔・許容ミス回数として使用しなければならない。
2. 環境変数が未設定または不正な値のとき、システムは既定値にフォールバックしなければならない。

## 機能要件

- **FR-001**: システムは、確立済みの各 WebSocket 接続に対して、一定間隔でサーバー主導の ping を送信しなければならない。
- **FR-002**: システムは、接続ごとに直近の pong 受信状況を追跡しなければならない。
- **FR-003**: システムは、連続して規定回数（既定2回）分の pong 応答が確認できない接続を切断（`terminate`）しなければならない。
- **FR-004**: 接続が切断されたとき、システムは既存の `close` イベント経路（`presenceManager.handleDisconnect` 等）をそのまま発火させ、`presence` の `offline` 化・ホスト不在委譲・ドライバー不在繰り上げの各既存ロジックを重複実装してはならない（DRY）。
- **FR-005**: システムは、検出間隔（既定15000ms）と許容ミス回数（既定2回）を環境変数で上書き可能にしなければならない。環境変数が不正・未設定の場合は既定値を用いなければならない。
- **FR-006**: システムは、サーバーのグレースフルシャットダウン（`WsAdapter.close()`）時に、ハートビート用の定期タイマーを確実に停止しなければならない（プロセス終了を妨げてはならない）。
- **FR-007**: システムは、1接続あたり1間隔につき ping 送信を高々1回のみ行い、参加者数（接続数）の増加に対して通信量が線形を超えて増加してはならない。

## 非機能要件

- **性能**: ハートビートによる追加通信は、接続数 N に対して O(N) の ping 送信/interval に収まること。ペイロードは ws 標準の ping/pong フレーム（アプリケーションデータなし）を用い、追加のシリアライズコストをかけない。
- **可観測性**: 既存のログ形態（`console.log`/`console.error`）に倣い、新規のログ出力を必須要件とはしない（運用ログは既存の `close`/`reclaimed` ログで代替可能なため、本機能ではハートビート専用ログを追加しない）。
- **後方互換性**: 既存の WS プロトコル（`CommandSchema`）・既存テスト（`driver-absence.test.ts`、`room-reclaimer.test.ts`）を変更・破壊しないこと。

## 主要エンティティ

- **接続ハートビート状態** — 接続ID（`connId`）ごとに保持する「直近 ping 送信からの pong 未受信回数（missedPongs）」。WebSocket 接続のライフサイクル（接続確立〜切断）と同じ寿命を持つ。永続化はしない（プロセス内メモリのみ）。

## 成功基準

- **SC-001**: 参加者の接続を強制的に無応答にした場合、既定設定（15000ms × 2回）で 45 秒以内に当該参加者の `presence` が `offline` に遷移する。
- **SC-002**: 通常運用下（pong が都度返る）で、既存の `driver-absence.test.ts` / `room-reclaimer.test.ts` が変更なしでパスし続ける。
- **SC-003**: 1回だけ pong が遅延したケースでは `presence` が `offline` に遷移しない（誤検出ゼロ）。

## スコープ外 / 非目標

- クライアント（`apps/web`）側の実装（Issue の案2、`presence.ping` の定期送信）は行わない。担当トラックの競合を避けるため、本機能はサーバー主導の ping/pong（案1）のみに限定する。
- `presence` の `idle` 値への遷移ロジックは実装しない。**理由**: 本機能のスコープは「応答不能な接続を検出して `offline` にする」という二値の死活監視であり、`idle`（離席中だが接続は生きている、を表すと想定される中間状態）の意味付け・遷移条件・UI 表示は死活監視とは独立した別要件（離席検出）である。混在させると `offline` 検出のタイミングが曖昧になり本 Issue の解決目的がぼやけるため、今回は `idle` を既存のまま未使用で残し、将来必要になった時点で別途仕様化する。
- `packages/core` のスキーマ変更は行わない（`presence` の型定義・`CommandSchema` は変更不要）。
- ルーム回収（`room-reclaimer.ts`）・プレゼンス遷移ロジック（`presence.ts`）自体の変更は行わない。両者は既に `store` 経由の疎結合であり、`ws-adapter.ts` が `presence` を正しく更新する既存経路（`close` イベント）を確実に発火させることだけで要件を満たせる。

## 前提

- [前提1] ハートビートの既定値（間隔15000ms・許容ミス2回・検出まで最大45秒）は、既存の `HOST_ABSENCE_GRACE_MS` / `DRIVER_ABSENCE_GRACE_MS`（いずれも30秒）と同程度のオーダーの猶予を持たせる値として設計時に決定した仮定である。Issue に具体的な数値指定はないため、運用開始後に実測値を見て env で調整する前提を置く。
- [前提2] `ws` パッケージ（`ws.ping()` / `pong` イベント）は Node.js の `ws` ライブラリの標準機能であり、追加の依存追加は不要という前提を置く（既に `package.json` に `ws` が存在する前提。実装フェーズで確認する）。
