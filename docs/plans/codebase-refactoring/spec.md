# 機能仕様: コードベースの構造是正 — 原則違反の棚卸しと解消

**Issue:** [#28](https://github.com/tomohiroJin/tasuki-tools/issues/28) ・ **ディレクトリ:** `docs/plans/codebase-refactoring` ・ **ステータス:** Draft（要件レビュー中） ・ **フロー:** 要件優先

> 本仕様は技術非依存（何を・なぜ）に徹する。どのモジュールをどう分割するか、どの型を導入するかといった
> 「どう作るか」は承認後に `plan.md` で扱う。
>
> **本仕様の利用者は「このコードベースを保守する人」である。** 外部利用者から見た振る舞いは一切変わらない。
> したがって受け入れ基準は「画面でこう見える」ではなく「コードベースがこの性質を満たす」で書く。

## 概要

v2.0 以降、実機フィードバックを起点に機能を積層してきた。個々の変更は妥当だったが、**変更しやすさを保つ
作業が伴走しなかった**結果、原則に反する構造がコードベース全域に堆積している。

この堆積は、すでに**欠陥という形で二度以上表面化している**。

- Issue #22 の設計中、権限の集合表に登録されているのに到達しない**デッドコードが 6 件**見つかった。
  集合表を書き換えても効かない状態が、誰にも気づかれずに存在していた（→ #26）
- 同じ Issue #22 で、同名参加者を区別する規則を 1 箇所に作ったにもかかわらず、**呼び出し側が 2 系統
  あったために片方へ行き渡らず**、見分けのつかない状態のまま出荷しかけた
- v2.7〜v2.10 の「自動交代と手動交代で挙動が違う」バグ群は、**同じ決定が 2 箇所に別実装で存在した**ことに
  起因する。当時は片側を揃えて収束させたが、分裂そのものは残っている

いずれも「うっかり」ではなく、**構造が見落としを誘発している**。本仕様はその構造を対象とする。

### なぜ今か

未デプロイのコミットが 65 溜まっており、次のリリース後は比較的静かな時期に入る。**機能追加と競合しない
時期にしか、この種の作業はまとまって行えない。**

加えて、**構造変更の予定が 2 つ控えている**。Issue #26（コマンド処理の二重ルート統合）と、
monorepo 統合（#15〜#20）である。どちらも「既存の構造を大きく動かす」作業であり、
**動かす前に整えておくほど安全**になる。荒れたまま運べば荒れたまま固定される。

本仕様はこの 2 つの**前**に置く。**Tidy First** — 難しい変更を難しくしている原因を先に片付け、
そのうえで本来やりたかった設計変更（#26）に取りかかる、という順序である。

### 判断の基準

本仕様で「直すか、残すか」を判断するとき、一貫して次の基準を用いる。

> **その構造が、過去に欠陥を生んだか、または「片方を忘れる」種類の変更を今後強いるか。**

美しさや流儀の統一は理由にしない。**同じ規則が 2 箇所にあること、決めた規則が使われない経路が
残っていること、読む対象が実在しないこと**——これらは実際に人が間違える構造なので直す。

逆に、行数が多いだけで分岐も重複も無いもの（お題データなど）は、この基準では優先度が下がる。

### 優先度の付け方（判断の基準とは別の軸である）

上の「判断の基準」は **何を直すか（対象の選別）** を決めるものであり、
**どの順で直すか（優先度）** を決めるものではない。この 2 つを混同すると、
「過去に欠陥を生んだものから着手する」という一見もっともな順序になるが、それは誤りである。

> **優先度は Tidy First の原則に従い、「安全な順」で付ける。**
> すなわち **①挙動を変える危険が小さいもの ②他の作業の安全ネットになるもの** を先に置く。

この結果、次のようになっている。

| 順 | ストーリー | なぜこの位置か |
|---|---|---|
| P1 | US1（撤去） | **削除のみで挙動を変えようがない。** 最も安全。かつ後続の書き換え対象を減らす |
| P1 | US2（テスト） | **後続すべての安全ネットになる。** 製品コードを触らないため、それ自体は挙動を変えない |
| P2 | US3（契約）・US4（規則の一元化） | **製品コードを触る。** 安全ネットが整った後でなければ危険 |
| P2 | US5（構造） | **列挙・移動・削除が中心で、判定ロジックを変えない。**US3・US4 より安全なので、製品コードに触る段階の先頭に置く |

> **US5 は当初 P3 とし、その根拠を「移動が中心で価値が出るのが遅い」としていた。これは誤りだった。**
> それは**価値の議論**であり、本節が宣言した「優先度は安全な順で付ける」という基準と噛み合っていない。
> 安全性で見れば、US5（公開記号の列挙・データの移動・空ディレクトリの削除）は
> US3（型の変更）や US4（判定規則の統合）より明らかに安全である。
> **基準を自分に適用し直して P2 に上げた。**
> P2 の内部順序は plan が定める（US5 → US4 → US3 の順。安全な順である）。

**過去に実際の欠陥を生んだのは US3（交代の 2 実装）と US4（規則が行き渡らない）であり、
これらは P2 に置かれている。** 動機として最も強い項目を後回しにすることになるが、
それは意図的である。**「危険な変更を、安全ネットが弱いうちに、動機が強いという理由で先に行う」
のは Tidy First が最も避けようとする順序**だからである。

（残る 1 件、権限集合表のデッドコードは Issue #26 が扱う。本仕様のスコープ外である）

### 本仕様で目指す状態

| 観点 | 現在 | 目指す状態 |
|---|---|---|
| 読む対象 | 使われないコードが約 1,400 行、テストごと保守されている | **live tree から参照されるコードだけが存在する** |
| 型と契約 | 戻り値型が実態を語らず、ダミー値で埋められる | **型を読めばその関数が何を返すか分かる** |
| 規則の所在 | 同じ規則が複数箇所にあり、片方だけ直る事故が起きている | **規則は 1 箇所にあり、呼び出し側が全てそこを通る** |
| テスト | 件数は十分だが、仕様書として読めない | **テスト名と構造から、何が保証されているか読み取れる** |

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 読む対象が実在するコードだけになる（優先度: P1）

このコードベースを保守する者として、目の前のモジュールが**実際に動いているのかどうかを調べずに済ませたい**。
なぜなら、使われていないコードを「使われているかもしれない」と仮定して読むのは純粋な浪費であり、
そのうえ撤去できないという誤った制約を自分に課してしまうからだ。

**受け入れ基準（EARS）:**

1. コードベースは、`src` 配下のモジュールのうち、テストからのみ参照され製品コードからは到達しないものを
   含んではならない。
2. 撤去の対象を判断するとき、判断者は参照の有無を機械的な走査によって確認できなければならない。
3. コードベースは、到達しないモジュールを**いかなる理由によっても保持してはならない**。
   「将来の再有効化に備えて」「テスト維持のため」といった記録は、保持を正当化する根拠にならない。
4. 生きたモジュールの内部に到達不能な分岐が存在する場合、コードベースはその分岐を撤去しなければならない。
   ただし撤去がそのモジュール単体の振る舞いを変える場合、その撤去は挙動を変える変更として扱われる。
5. もし撤去対象が外部との取り決め（通信プロトコルの受理可能な形式など）に関わるならば、
   コードベースは受理側の後方互換を維持したまま、内部の到達不能コードのみを撤去しなければならない。

> **なぜ例外を設けないか（この基準は当初「根拠を記録すれば残してよい」と書かれていた）。**
> 実際に `apps/web/src/ai/key-storage.ts` には「**テスト維持のため残置**」という根拠と、
> 再有効化時の条件が既に記録されている。例外条項を設けると、**この記録がそのまま撤去回避の根拠として
> 成立してしまう**。しかもその根拠は「テストがあるからコードを残し、コードがあるからテストを保守する」
> という循環であり、本仕様が解こうとしている問題そのものである。
> **コメントを 1 行書けば回避できる要件は、要件として機能しない。**

### ユーザーストーリー2 — テストが振る舞いの仕様として読める（優先度: P1）

このコードベースを保守する者として、**テストを読めば何が保証されているのかが分かる**状態にしたい。
なぜなら、リファクタリングの安全ネットはテストであり、読めないテストは安全ネットとして機能しないからだ。
また、テストが落ちたときに「何の振る舞いが壊れたか」が名前から分からなければ、原因追跡は毎回ゼロから始まる。

**受け入れ基準（EARS）:**

1. テストスイートは、各テストについて**前提・操作・検証の境界が識別できる**形式で記述されなければならない。
2. テストの名前は、**観測可能な振る舞い**を述べなければならない。内部の関数名・呼び出しの有無・
   仕様の識別番号を主語にしてはならない。
3. 仕様への追跡情報（要件番号）を保持する場合、テストスイートはそれをテスト名以外の場所に記録しなければならない。
4. 1 つのテストは 1 つの振る舞いのみを検証しなければならない。複数の振る舞いを検証する必要がある場合、
   テストスイートは前提を共有したうえでテストを分割しなければならない。
5. テストが前提の構築に失敗したとき、テストスイートは**その失敗を検証の失敗と区別できる形で**報告しなければならない。
6. テストスイートは、同一のテスト用代替実装（フェイク・スパイ）を複数のファイルで重複して定義してはならない。
7. テストは、検証対象の**順序や位置**が仕様である場合を除き、順序や位置に依存して対象を取り出してはならない。

### ユーザーストーリー3 — 型を読めば契約が分かる（優先度: P2）

このコードベースを保守する者として、**関数の型からその関数が何を約束しているのかを読み取りたい**。
なぜなら、型が実態と食い違っていると、型検査が通ることが安全の証拠にならず、
「型は変わらないが意味が変わる」変更を人力で追う羽目になるからだ（Issue #22 で実際に退行を 2 件出した）。

**受け入れ基準（EARS）:**

1. 関数の戻り値型は、その関数が実際に返す値のみを表現しなければならない。呼び出し側が使えない
   ダミー値を含んではならない。
2. 失敗を表す値は、**取り得る失敗の種類を型として列挙**しなければならない。任意の文字列であってはならない。
3. ある判断を行う責務を持つ関数がその判断結果を返すとき、呼び出し側はその結果を**採用するか、
   または判断責務そのものをその関数から外す**かのいずれかでなければならない。返された判断を
   黙って破棄してはならない。
4. 同一の入力に対する状態遷移の適用は、単一の経路で行われなければならない。
5. もし状態遷移が複数の層に分かれざるを得ないならば、コードベースはその境界と適用順序の根拠を
   型または明示的な契約として表現しなければならない。コメントによる注意喚起のみに依存してはならない。

### ユーザーストーリー4 — 規則が 1 箇所にあり、全ての経路がそこを通る（優先度: P2）

このコードベースを保守する者として、規則を変更するとき**1 箇所を直せば全ての経路に反映される**状態にしたい。
なぜなら、同じ規則が複数箇所にあると「片方だけ直す」事故が必ず起き、しかもテストが緑のまま通過するからだ
（Issue #22 の G8 で実際に起きた）。

**受け入れ基準（EARS）:**

1. コードベースは、同一の判定規則を複数の箇所で独立に実装してはならない。
2. 利用者に提示される文言は、単一の箇所で定義されなければならない。
3. あるコマンドの処理に共通して必要な前処理は、コマンドごとに複製されてはならない。
4. ある概念について共通の実装が用意されているとき、その概念を扱う全ての箇所はその実装を経由しなければならない。
5. もし同じ役割を果たす画面部品が複数存在するならば、コードベースはそれらを単一の部品に統合するか、
   共通の規則を両者が経由することを保証しなければならない。

### ユーザーストーリー5 — 構造が責務を表している（優先度: P2）

このコードベースを保守する者として、**変更したい対象がどのファイルにあるかを推測ではなく構造から知りたい**。
なぜなら、単一の巨大なモジュールに複数の責務が同居していると、変更のたびに全体を読み直す必要があり、
また状態が共有されているために分割そのものが着手できなくなるからだ。

**受け入れ基準（EARS）:**

1. 単一のモジュールは、独立して変更される複数の責務を同時に担ってはならない。
2. データの定義とそれを操作するロジックは、同一のモジュールに置かれてはならない。
3. 共有されるパッケージは、**外部に提供する契約と内部の実装詳細を区別**して公開しなければならない。
4. ディレクトリ構成は、実在しない構造を示唆してはならない。
5. 設計文書が複数の体系に分かれている場合、コードベースはどれが正本であるかを記録しなければならない。

### エッジケースと想定される失敗

- **撤去したコードが実は必要だった。** 参照の走査は静的なものであり、文字列によるモジュール解決や
  設定ファイル経由の参照は捕捉できない。→ FR-090 で走査方法を定める
- **テストの書き換えでテスト自体を壊した。** テストにはテストが無い。名前と構造だけを変えたつもりが
  検証内容を変えてしまっても、テストは緑のまま通る。→ FR-098 で検出手段を定める
- **リファクタリング中に本体の欠陥を「直してしまう」。** 挙動を変えない作業のはずが挙動が変わり、
  どちらの変更が原因か切り分けられなくなる。→ **FR-115**
- **作業が長期化し、機能開発と衝突する。** 本仕様の作業単位は独立してマージ可能でなければならない
  → **FR-113・FR-116**
- **安全ネットに指定したテスト自身が、書き換えの対象になる。** `permissions-differential.test.ts` は
  全工程で緑を維持すると定めているが、US2 の対象でもある。→ 後述「非機能要件」で扱いを定める
- **共通化しすぎて、かえって読めなくなる。** 「規則を 1 箇所に」は、無関係な処理を 1 つの抽象に
  押し込む理由にはならない。→ US4 の受け入れ基準はいずれも「同一の規則」に限定している

## 要件 *(必須)*

### 機能要件

既存の FR-001〜FR-086 に続く番号を用いる。本仕様は既存 FR を書き換えない（**外部から観測可能な
振る舞いを変えないため**）。

**撤去（US1）**

- **FR-087**: コードベースは、**各パッケージの `src` 配下**において、製品コードから到達しないモジュールを
  保持してはならない。保持を正当化する例外を設けてはならない。
  **`test/` 配下は本要件の対象外である**（テスト用の共有ヘルパは製品コードから到達しないことが正常であり、
  対象に含めると FR-097 が新設を求めるものを本要件が撤去することになる）。
- **FR-088**: コードベースは、到達しないモジュールに対応するテストを、そのモジュールと同時に撤去しなければならない。
- **FR-089**: コードベースは、外部との取り決めに属する定義については、内部の到達不能な処理のみを撤去し、
  受理側の後方互換を維持しなければならない。
- **FR-090**: 撤去の判断は、製品コードの入口から辿った参照関係にもとづかなければならない。
  テストからの参照は根拠に含めてはならない。
- **FR-119**: コードベースは、**生きたモジュールの内部にある到達不能な要素**を撤去しなければならない。
  対象は**分岐・データ・エクスポート**を含む（当初は「分岐」に限定していたが、
  同じ場所にある死んだデータを取りこぼしたため一般化した。後述）。

  **判定は「そのモジュールが属する層の公開面から到達できるか」で行う。**
  - `apps/` のモジュールは、**受理されるコマンドの集合**が公開面である。
    受理されないコマンドによってのみ成立する分岐は到達不能である
  - `packages/` の**公開関数（引数を取り、呼び出し側が値を決められるもの）の分岐は対象外**。
    利用者が任意の引数で呼べるため、本リポジトリ内の特定の経路から到達しないことは
    到達不能を意味しない
  - **`packages/` の公開データ（定数・テーブル）は対象である。** 引数がなく、
    参照するか否かしかないため、「製品コードから一度も参照されない」ことが到達不能を意味する
  - 撤去が当該モジュール単体の振る舞いを変える場合、その撤去は FR-115（挙動を変える変更）として
    扱い、単独の変更単位に分離しなければならない

  > **この区別が必要な理由（当初この要件は誤った実例を根拠にしていた）。**
  > 当初は `packages/core` の `evolveConfigSet` の members 分岐を実例に挙げていたが、
  > これは誤りだった。同分岐は公開 API `evolve()` から到達可能であり、
  > `packages/core/test/coverage-supplement.test.ts` が実際に呼んでいる。
  > 「共有ルームの経路からは到達しない」ことと「到達不能」は別である。

  > **「分岐」から「要素」へ一般化した理由（レビュー 2 巡目）。**
  > 当初の FR-119 は分岐のみを対象としたため、**同じ「生きたモジュールの中の死んだもの」でありながら
  > データが対象外**になっていた。実例が見つかった: `packages/core/src/i18n/`（`ja.ts` 162 行 /
  > `en.ts` 151 行）は**製品コードから一度も参照されていない**（画面の文言は各コンポーネントに
  > 直接書かれている）。参照しているのはテスト 2 ファイルのみで、うち
  > `apps/web/test/ui/i18n-coverage.test.ts` は**キーが存在することだけを検証するテスト**である。
  > これは本仕様が US1 で名指しして否定した循環（テストがあるからコードを残す）そのものである。
  > **一度見つけた欠陥の型を一般化しきらないと、同じ形の別の実例が残る。**

  **正しい実例:**
  | 対象 | 種別 | 判定 |
  |---|---|---|
  | `apps/sync/src/application/handlers.ts:97` の `!room.onBreak` | 分岐 | **到達不能**（`break.start` は `buildDomainCommand` に分岐が無く `UNKNOWN_COMMAND` になる） |
  | `packages/core/src/i18n/ja.ts` ・ `en.ts` | データ | **到達不能**（製品コードからの参照がゼロ） |
  | `packages/core/src/evolve.ts` の `evolveConfigSet` members 分岐 | 公開関数の分岐 | **対象外**（公開 API から到達可能） |

**テスト（US2）**

- **FR-091**: テストは、前提・操作・検証を識別できる構造で記述されなければならない。
- **FR-092**: テストの名前は、観測可能な振る舞いを述べなければならない。
- **FR-093**: テストの名前は、仕様の識別番号・内部の関数名・呼び出しの発生を含んではならない。
  **例外は次の 1 ファイルに限る。**

  | 例外を認めるファイル | 認める内容 | 根拠 |
  |---|---|---|
  | `packages/core/test/permissions-differential.test.ts` | 入力の組み合わせ（コマンド名 / 役割 / 自己対象か）を名前に含めてよい | 参照実装との一致を検証する差分テストであり、述べるべき振る舞いは「オラクルと一致する」ことそのもの。個々の組み合わせは振る舞いではなく入力である |

  > **例外をファイル名で閉じる理由。** 「差分テストは対象外」という**種類による例外**にすると、
  > 「これは差分テストだ」と主張することで要件を回避できる。
  > 本仕様は US1 で同じ理由により「記録すれば残してよい」という例外を撤去した。
  > **同じ弱さを別の要件に持ち込まないため、例外は列挙して閉じる。**
  > 例外を追加する場合は、この表に行を足す変更として明示的に行う。
- **FR-094**: テストは、仕様への追跡情報を名前以外の手段で保持しなければならない。
- **FR-095**: 1 つのテストは 1 つの振る舞いのみを検証しなければならない。
- **FR-096**: 検証を表す記述は、前提の構築段階に置かれてはならない。前提の構築が失敗した場合は、
  検証の失敗と区別できる形で報告されなければならない。
- **FR-097**: テスト用の代替実装は、単一の箇所で定義され、各テストから共有されなければならない。
- **FR-098**: テストの書き換えにあたっては、書き換えの前後で**検出できる欠陥の集合が変わっていないことを
  確認しなければならない**。確認の手段を用意するだけでは足りず、各段階で実際に実行し、
  結果を変更単位の記述に残さなければならない。
- **FR-099**: テストの構造を変える変更と、検証内容を変える変更は、同一の変更単位に含めてはならない。
- **FR-123**: 既に要件を満たしているテストは、**書き換えてはならない**。
  本仕様は要件違反の是正であり、記述の統一そのものを目的としない。

  **適用の範囲を明確にする。** 本要件が守るのは次の 3 つである。
  - **テスト名**（FR-092・FR-093）— 既に振る舞いを述べている名前は言い回しを変えない
  - **関心の分割**（FR-095）— 既に 1 テスト 1 振る舞いなら分割も統合もしない
  - **検証の内容** — 既に意図で取り出しているなら書き換えない

  **構造の付与（FR-091 / SC-032）は本要件の対象外である。** 区切りが無いテストは
  FR-091 を満たしていないため、良い名前を持つテストであっても区切りの付与は行う。
  （この限定が無いと、SC-032 がほぼ全ファイルを「未達」と判定するため本要件が空文になる）

  > 対象の規模: `it` 名の 89% は仕様 ID を含まず、81% は検証が 1〜2 件で既に良好である。
  > **これらの名前と分割に手を入れることは、改善ではなく改悪の危険だけを持ち込む。**

**契約（US3）**

### 非機能要件

- **保守性（本仕様の主目的）**: 上記 FR がその内容である。
- **安全性**: 本仕様の作業中、いかなる時点においても**その時点で存在するテストがすべて緑**であること。
  「既存の」ではなく「その時点で存在する」とするのは、FR-088 により撤去されるテストがあるためである
  （撤去されたテストは存在しないので緑たり得ない）。
  **ただし「落ちるテストを削除して緑にする」ことを禁じる。** テストの削除が許されるのは
  FR-088（撤去されたモジュールに対応するテスト）に該当する場合のみであり、
  それ以外の削除は検証内容の減少として FR-098 の対象になる。
- **安全ネット自身の書き換え（上のエッジケースへの回答）**:
  `packages/core/test/permissions-differential.test.ts` は権限仕様の実行可能な表現であり、
  全工程を通じて緑でなければならない。同時に US2 の対象でもあるため、次の制約を課す。
  1. **このファイルの書き換えは単独の変更単位で行い、他の変更と混ぜない**
  2. 書き換えは**名前の付け方と構造の表現に限る**。オラクル（参照実装）と検証の組み合わせは変えない
  3. 書き換えの前後で**検証される組み合わせの総数が一致すること**を確認する（現状: 開始前 150 通り + 開始後）
  4. FR-093 の例外に該当するため、組み合わせを名前に含めることは許される
- **検証可能性**: 本仕様の達成度は、人の目視ではなく**機械的に走査可能な指標**で測れなければならない
  （SC-027〜 を参照）。
- **性能**: テストスイートの実行時間を現状より悪化させてはならない。
  （現状 `apps/web` の単体テストは 14 分前後を要しており、これ自体は本仕様の対象外だが、悪化させない）
- **可観測性**: 本仕様は実行時の可観測性に影響を与えない。

### 安全ネットの循環という構造的な弱点（明記する）

本仕様は「リファクタリングの安全ネットはテストである」を前提に置きながら、
**その安全ネット自身が不十分であること**を US2 の動機にしている。したがって
**P3（テストの一括書き換え）は、弱い安全ネットの上で安全ネット自身を大改修する**という、
本仕様で最も危険な作業である。この弱点は消せないため、次の多層で緩和する。

| 層 | 何を守るか | 限界 |
|---|---|---|
| **製品コードを 1 行も変えない**（P2・P3） | テストが同じものを検証し続けていることを、製品コード不変という事実が裏づける | 検証内容を**減らした**ことは検出できない |
| **変異検査**（FR-098） | 検出できる欠陥の集合が変わっていないこと | **抜き取り検査であり網羅ではない。**十数件の変異で 1,104 テストの検証能力を代表させている |
| **1 ファイル単位のコミット**（FR-116） | 問題が起きた範囲を 1 ファイルに限定する | — |
| **段階の分離**（FR-117） | 機械的な差し替えと判断を要する変更を混ぜない | — |

> **変異検査は十分ではない。** これは限界として受け入れる判断であり、見落としが無いという主張ではない。
> 変異は「過去に実際に起きた欠陥の型」から選ぶこととし、**網羅性ではなく的中率で価値を出す**。
> 変異検査を通っても、それは「代表的な欠陥は今も検出できる」ことしか意味しない。

### 主要エンティティ

本仕様が対象とするのはコードベースそのものであり、実行時のデータではない。判断の対象となる構成要素を挙げる。

- **到達可能なモジュール** — 製品コードの入口から参照関係を辿って到達できるモジュール。撤去対象の判定基準
- **契約** — 関数が呼び出し側に約束する入出力と失敗の種類。型として表現される
- **判定規則** — ある入力に対する可否や分類の決定。**単一の箇所に存在すべきもの**
- **状態遷移** — イベントを適用して状態を更新する操作。単一の経路で行われるべきもの
- **テスト** — 前提・操作・検証の 3 要素からなる、振る舞いの実行可能な記述
- **テスト用代替実装** — テストにおいて本物の依存を置き換えるもの。共有されるべきもの
- **公開契約** — 共有パッケージが外部に提供すると宣言した記号の集合

### レビュー時のチェック項目（機械的には判定できない）

次の 3 点は達成すべき性質だが、走査で 0/1 を判定できない。**各段階のレビューで人が確認する**ものとし、
成功基準（SC）には数えない。SC の前提「走査で判定できるものだけを置く」を守るためである。

> **自己申告で合格にできる項目にしないため、各項目に「誰が・何を見て・何をもって不合格とするか」を定める。**
> これを書かない限り、RC は「レビューしたことにすれば通る要件」になり、
> 本仕様が US1 で撤去した「記録すれば残してよい」と同じ弱さを持つ。

| ID | 確認すること | 何を見るか | 不合格の条件 |
|---|---|---|---|
| **RC-001**<br>（旧 SC-033） | 呼び出し側が使用しないダミー値を含む戻り値が無い | 変更したハンドラの戻り値型と、その**全呼び出し箇所** | 呼び出し側が参照しないフィールドが戻り値型に 1 つでも残っている |
| **RC-002**<br>（旧 SC-034） | 同一の判定規則が 2 箇所以上で実装されていない | 段階で触れた判定ロジックと、同じ入力を扱う他の箇所 | 同じ入力に対して同じ結論を出すコードが 2 箇所以上ある |
| **RC-003**<br>（旧 SC-037） | 外部から観測可能な振る舞いに差分が無い | 後述の定義表の「含む」列の各項目 | 定義表の「含む」項目に、FR-115 で分離されていない差分が 1 つでもある |

**RC-001 / RC-002 の補助的な機械判定**（網羅ではないが、見落としを減らす）:
`hostToken: ""` 等の空文字リテラル充填の件数（現状 10 箇所）を計測し、減少していることを確認する。

**RC-003 の確認手順**（最も見落としやすいため手順を固定する）:
1. WebSocket 層 — 既存の統合テストが緑であること
2. 画面 — **`vite` を再起動してから**実機で確認する（この環境は HMR を取りこぼし旧バンドルを配信する）
3. 確認した画面と操作を、変更単位の記述に列挙する（「確認した」だけでは不合格）

### 「外部から観測可能な振る舞い」の定義

FR-114・FR-115・SC-037 が指す範囲を次に固定する。**これを定義しないと「振る舞いを変えていない」が
検証できない主張になる。**

| 含む | 含まない |
|---|---|
| WebSocket で受理されるコマンドの形式と、拒否されるコマンドの形式 | 内部関数の戻り値・シグネチャ |
| 配信されるメッセージ（`snapshot` / `error` / `signal`）の**種類・順序・内容** | ログ出力の文言 |
| エラーコードと、利用者に表示される文言 | ファイル構成・モジュール名 |
| 画面に表示される文言・操作可能な要素・その有効/無効 | DOM の構造（テストで参照していない部分） |
| 記録（`CompletionRecord`）の内容 | 実行時の計算量（悪化させない範囲で） |

**検証方法:** WebSocket 層は既存の統合テストで担保する。画面は**実機での目視確認**による。
自動化された E2E は存在しないため、**SC-037 は「機械的に測定できる」とは主張しない**
（この点で SC-037 は他の SC と性質が異なる。RC に落とさないのは、実機確認という明確な手順が
定義できるためである）。

### 達成条件としない指標

- **行数の削減** — 結果として減るが、目的ではない。分割によって増える箇所もある
- **テストカバレッジの向上** — 現状で閾値を満たしている。本仕様はカバレッジを目的としない
  （むしろ「カバレッジのために書かれたテスト」の解体を含む）
- **ファイル数の削減** — 責務の分離は通常ファイル数を増やす

3. **後方互換の範囲**: 通信プロトコル（クライアント・サーバー間で受理される形式）は維持する。

## 決定事項（レビューで確定）

- **決定 1 — 休眠コードは単純に削除する。** 退避用のタグは打たない。git 履歴に残るため復元は可能であり、
  「いつでも戻せる」という余地を残すこと自体が撤去の判断を鈍らせるため。
- **決定 2 — 本仕様を Issue #26 より先に実施する。** 本仕様は **Tidy First の整理整頓**であり、
  #26（`handlers.ts` の二重ルート統合）という**設計変更を安全に行うための地ならし**として位置づける。
  順序が逆だと、荒れた土台の上で構造変更を行うことになり、#26 自体の難度と危険度が上がる。
  したがって US3（契約）・US4（規則の一元化）も #26 の前に行う。
  ただし、**本仕様は二重ルートそのものには手を付けない**（それは #26 の仕事である）。
  本仕様が行うのは「二重ルートの両側に散らばっている重複・ダミー値・文言を整理し、
  #26 が統合すべき対象を見えるようにする」ところまでである。
- **決定 3 — テストの書き換えは一括で行う。** 「触ったファイルのみ」の段階適用は、実際には
  最後まで着手されないまま残ることが見込まれるため採らない。全 1,155 件を対象とし、
  SC-029〜SC-032 は**一括での達成**を条件とする。

  **決定 3 と FR-116（任意の時点で停止可能）が競合した場合、FR-116 を優先する。**
  「一括」は着手範囲を全 1,155 件とすることを意味し、「途中で止められない」ことを意味しない。
  P3 の途中で停止した場合、SC-029〜SC-032 は未達のまま残る。
  **未達のまま停止することは許容し、そのとき達成済みの範囲を記録する**
  （停止できない計画は、停止すべき事態が起きたときに必ず破綻するため）。

### 決定 2・3 に伴う制約（**最重要**）

本仕様は**リファクタリングであり、振る舞いを変えない**。一括での書き換えを選んだことにより、
次の制約を要件に加える（FR-116〜FR-118）。

> **後から変えられなくなる直し方をしない。**
> 一括であることは「大きな 1 つの変更」を意味しない。**小さく・可逆な変更を数多く積む**ことを意味する。

この制約は **FR-116（任意の時点で停止できること）・FR-117（機械的な変更と判断を要する変更の分離）・
FR-118（抽象は現存する重複から導き、元に戻せる形にすること）** として機能要件に定義した。
要件の本文は「機能要件」節を参照する（ここでは重複して書かない）。
