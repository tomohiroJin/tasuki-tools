### SC-039② の判定方法（推移的な生存性。ここが最も間違えやすい）

生存性は次の手順で判定する（`sc039bUnusedPublicData` の実装）。

1. **生きた根** = `packages/*/src` の公開記号のうち、**自ファイル以外の製品コード**
   （`apps/*/src` と、宣言ファイル自身を除く `packages/*/src`）から識別子として参照されているもの。
2. ある記号は、生きた根から**同一ファイル内の参照関係を推移的に辿って**到達できるなら生きている
   （固定点に達するまで繰り返し伝播する。非公開のトップレベル宣言を経由する多段の連鎖にも対応する）。
3. SC-039② はこの意味で**生きていない** `export const`（公開データ）の行数合計。
4. **テストからの参照は根拠に含めない**（FR-090）。

この定義では `ja`/`en` は死ぬ（参照元は同じく死んでいる型 `JaMessages`/`EnMessages` のみ）が、
`FALLBACK_PROBLEMS`（生きた関数 `pickFallback` から参照）や `schemas.ts` の各スキーマ
（最終的に他ファイルから参照されるスキーマへ合成される）は生きている。

## 3. 走査スクリプトの既知の限界（実装のバグではなく設計上の制約）

- **SC-039① は既知パターン（`!room.onBreak`）のみを検出する。** 一般の「受理コマンド集合から到達しない
  条件」を機械的に網羅する実装は行っていない（spec/plan の指示どおり）。
- **SC-028 は同一識別子名での重複のみを検出する。** 名前が異なる構造的重複（`FakeAudio` と
  `FakeAudioContext` 等）は検出できない。
- **型情報を使わない。** import 解決・参照判定はすべて正規表現ベースであり、TypeScript の型システムは
  見ていない。パスエイリアス（`@tdd-mob/core` 等）はパッケージ境界として意図的に追わない設計。
  今回確認した範囲では `apps/web/tsconfig.json` にそのようなエイリアスは無かった。
  再エクスポート文（`export { x } from "..."`）は「消費ではなく通過点」として明示的に除外している。
- **短い識別子名の誤検出リスク。** 2〜3文字の識別子は「名前一致」方式では偽陽性・偽陰性のリスクが残る
  （文字列リテラル・コメントの除去で軽減しているが、完全な字句解析ではない）。
- **SC-039② の推移的生存性判定は1ファイル内に閉じる。** ファイルをまたいだ「実は生きている根から
  複数ファイルを経由して間接的に到達する」ような連鎖までは追わない（同一ファイル内の参照連鎖のみ辿る）。

- **SC-039②③ の参照元からは、SC-027 が到達不能と判定したファイルを除いている。**
  死んだファイルからの参照を生存の根拠にすると、「撤去予定のファイルからしか参照されていない記号」が
  生きているように見え、**G1 で撤去した瞬間に SC-039 の値が跳ね上がる**（計測器が撤去を検知できない）。
  この除外を入れた結果、SC-039③ は 48 件から **50 件**へ増えた（2 件は死んだファイルからのみ参照されていた）。
  逆に言えば、**SC-027 の判定が誤ると SC-039 も連鎖して誤る。**SC-027 は最も慎重に扱うこと。

**欠陥1（SC-028 過小計上）:** 「同名が2ファイル以上」を「同名が2**箇所**以上（ファイル境界を問わず出現回数で判定）」に修正。
`apps/web/test/platform/sound.test.ts` 内の同一ファイル内複数回定義（`FakeAudio`5回等）を正しく捕捉できるようにした。

**欠陥2（誤り→再修正）:** 当初「自ファイル内でも参照されないものだけを②に数える」（＝②と③を排他にする）よう
修正したが、これは `packages/core/src/i18n/ja.ts` の `ja` が同一ファイルの `export type JaMessages = typeof ja;`
から参照されていることを「生存の根拠」にしてしまい、`JaMessages` 自体がどの製品コードからも使われていない
**死んだ型**であるにもかかわらず `ja` を生存扱いにする誤りを生んだ（SC-039② が期待313行に対し実測0行になった）。
**正しい定義は「推移的な生存性」**（1章参照）であり、死んだ記号からの参照を生存の根拠にしないよう
`computeTransitivelyAliveExportedSymbols` を実装し直した。この過程で、`packages/core/src/schemas.ts` の
`ServerMsgSchema`（生きた根 `ServerMsg` から参照される）が、**非公開の中間宣言**（`SnapshotMsg` 等、
`export` されていないトップレベル定数）を経由して公開スキーマ（`RoomSchema` 等）を参照している連鎖も
正しく辿れるよう、参照グラフのノードを「公開シンボルのみ」から「公開・非公開を問わない全トップレベル宣言」に
拡張した（生きた根の判定自体は公開シンボルに限定したまま）。

**欠陥3（SC-039③ の宣言抽出漏れ）:** `export function`/`export class` を正規表現に追加し、
`participants.ts` の `countManagers` 等を捕捉できるようにした。

**欠陥4（文字列リテラルへの誤一致）:** `stripStringsAndComments`（文字列リテラル・コメントを除去する
簡易字句スキャン、エスケープ考慮済み）を新設し、`isReferencedElsewhere` の照合対象をこの除去後の
ソースにした。これにより `ja` が他ファイルの `"ja-JP"` のような文字列リテラルの中身に一致して
誤って「参照されている」と判定される問題を解消した。同じ理由で `events.ts` の24個のイベント
インターフェースと `errors.ts` の3型が、判別用文字列リテラル（`type: "SessionStarted"` 等）への
一致によって誤って「参照されている」とみなされていた問題も解消し、これらが正しく③の対象に加わった
（19件→48件）。

**宣言スパン境界のバグ修正（欠陥2の再修正に必須だった前提修正）:** 以前の実装は「次の `export` 宣言まで」を
現在の宣言の本体とみなしていたが、`schemas.ts` のように export された宣言の間に非公開の補助宣言が
挟まる実際のソースでは、この補助宣言の中身が手前の export 宣言の本体に誤って取り込まれ、
(a) 行数の過大計上、(b) 自ファイル内参照判定の誤り、を引き起こしていた。宣言の境界を
「次のトップレベル宣言（export の有無を問わない）の開始位置まで」に修正した。

**全過程を通じて製品コード（`*/src/*`）は一切変更していない。**
