## 概要

`Lobby.tsx`（開始前・ロビー画面）と `RosterPanel.tsx`（開始後・セッション画面）が、
参加者一覧の各行について**同じ種類の操作**（ドライバー加入/離脱・ホスト移譲・退出）を
**別々の JSX 実装**として持っている。判定ロジック（誰にどの操作を出すか）は
`participant-label.ts` にすでに1箇所へ統合済み（PR #31・Issue #28 C-3 相当）だが、
その判定結果を使って実際に行を描画するコードは今も2系統のままである。

この構造は**すでに Issue #22 の G8 で実際の事故を起こしている**。同名参加者を区別する
`participantLabel` を作ったにもかかわらず Lobby 側の描画コードへ行き渡らず、
同名参加者を見分けられないまま出荷しかけた。**抽象（判定関数）を作っても、
それを呼び出す描画コードが2系統ある限り、次の抽象も同じ理由で片方に行き渡らない**
——これが本仕様の是正動機である。

### なぜ「判定の統合」だけでは足りないのか

`participant-label.ts` の統合（C-3）は「何をしてよいか」を1箇所にした。しかし
「その判定結果をどう画面に描画するか」は Lobby と RosterPanel がそれぞれ独立に書いている。
本仕様はこの描画コードのうち、**実装が実際に一致している部分だけ**を共有部品として
切り出す（「一本化の単位」節を参照）。

### 一本化の単位（要件レビューで確定した設計方針）

旧 Draft は `RosterRow.tsx` を新設し `variant: "compact" | "detailed"` で行全体を分岐する
設計だった。**この設計は不採用**とする。理由: `RosterRowProps` が 17 props に達し、
`compact` では約半数が未使用になる。DRY のために単一責任を犠牲にしており、
二重実装より保守しにくくなる懸念がある（詳細な検討経緯は plan.md「意思決定」節）。

★採用する方針: **行全体ではなく、Lobby と RosterPanel の双方に実在し、かつ実装まで
一致している「部品」だけを共有コンポーネント化する。** リスト構造（Lobby=フラット・
参加順／RosterPanel=ドライバー/見学のセクション分割・ターン順ソート）と行のレイアウト・
バッジ構成・ボタン部品の見た目は**各ファイルに残す**（バッジとボタンを共有化しない理由は
plan.md「コンポーネントとインターフェース」節に根拠つきで記録する）。

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 — 実装が一致する部品が単一の実装から生まれる（優先度: P1）

このコードベースを保守する者として、Lobby とセッション画面の双方に実在し実装まで
一致している部品（在席ドット・退出確認ダイアログの生成）については、**1箇所を直せば
両方に反映されたい**。なぜなら、2箇所を手で同期する構造は、同期を忘れる事故を構造的に
誘発するからだ（Issue #22 G8 で実証済み）。一方で、実装が一致していない部分（バッジ構成・
ボタン部品の見た目）まで無理に共通化すると、単一責任を犠牲にした props 分岐が生まれ、
二重実装より保守しにくくなる。

**受け入れ基準（EARS）:**

1. コードベースは、Lobby と RosterPanel の双方に実在し実装が一致している部品
   （在席ドット表示・退出確認ダイアログの生成）を、共有コンポーネントとして1箇所にのみ
   実装しなければならない。
2. コードベースは、実装が一致していない部品（役割/代理/一時離脱/現ドライバーのバッジ構成、
   `RowIconButton`/`MiniButton` のボタン部品）を、無理に単一の共有コンポーネントへ統合
   してはならない。各画面固有の実装として維持する。
3. `participantLabel`（同名参加者の区別）は、共有部品・各画面固有の実装のいずれを
   経由する場合も、参加者行が描画されるすべての経路で例外なく適用されなければならない。
4. リスト構造（フラット一覧 or ドライバー/見学のセクション分割＋ターン順ソート）は、
   Lobby.tsx / RosterPanel.tsx にそれぞれ残り、共有部品側へ移動してはならない。
5. 一本化後の Lobby とセッション画面は、`baseline.md` が記録した**現状の可否**
   （どの操作がどちらの画面で可能か）をそのまま維持しなければならない。例外は無い
   （旧 Draft にあった FR-013 の意図的差分は撤回済み。「振る舞いの変更の扱い」は本仕様には
   存在しない＝一切変更しない）。

### ユーザーストーリー2 — 部品共通化によって表示・操作が変わらないことを検証できる（優先度: P1）

このコードベースを保守する者として、部品共通化の作業が**利用者から見える振る舞いを
一切変えていないこと**を、テストと実画面の両方で確認したい。なぜなら、型が変わらない
意味変更は静的検査もテストも検出できず、実際に Issue #22 で 1,412 テスト緑・
typecheck 通過の状態から実機検証が退行を2件検出した実績があるためだ。

**受け入れ基準（EARS）:**

1. 一本化の完了条件は、既存の全テストゲート（`packages/core` ・ `apps/sync` ・
   `apps/web` の単体テスト、typecheck、lint、build）がすべて緑であることを含まなければ
   ならない。
2. 一本化の完了条件は、テスト件数が作業開始時点（1,538件）を下回らないことを含まなければ
   ならない。
3. 一本化の完了条件は、**実画面での目視確認**（ロビー画面・セッション画面の双方で、
   同名参加者を含む参加者一覧を表示し、加入/離脱・ホスト移譲・退出・並べ替えの各操作を
   実際に操作して確認すること）を含まなければならない。
4. もし単体テストが全緑であっても実画面確認が未実施であれば、システムは一本化を
   完了とみなしてはならない。
5. 実画面確認において、変更前（本ブランチの開始コミット）と変更後で、画面の表示・操作・
   外観・並び順・文言に差分が無いことを確認しなければならない（本仕様の中核制約）。

### エッジケースと想定される失敗

- **共有部品化した在席ドット・退出確認ダイアログに、意図せず新しい情報や文言を混入させて
  しまう。** → FR-176・FR-177 で、両画面の現状の出力を合算した仕様として固定し、
  差分が出ないことを回帰テストで担保する。
- **バッジ・ボタンを「ついでに」共通化してしまい、片方の見た目がもう片方へ寄る。** →
  FR-179 で明示的に禁止する。レビューのチェック項目（RC-002）で検出する。
- **同名参加者が3名以上いる場面で、共有部品を経由しない画面固有の実装にだけラベルの
  識別子が付かない。** → ユーザーストーリー1の受け入れ基準3（`participantLabel` の全経路
  適用）および FR-187 で全経路への適用を明示している。回帰テストで3名同名のケースを
  扱う（tasks.md 参照）。
- **共通化の途中でテストが一時的に赤くなる段階を経由してしまう。** → 段階分け（plan.md の
  「段階分け」節）で、各段階の終了時点で緑を維持することを条件にする。

## 機能要件 *(必須)*

**部品共通化の対象と非対象**

- **FR-176**: コードベースは、参加者行のうち「在席ドット表示」を、Lobby と RosterPanel の
  双方が呼び出す単一の共有コンポーネントから生成しなければならない。
- **FR-177**: コードベースは、参加者行のうち「退出確認ダイアログの生成」（対象参加者の
  特定・確認ダイアログのタイトル/説明文/確定・取消ハンドラ）を、Lobby と RosterPanel の
  双方が呼び出す単一の共有コンポーネントから生成しなければならない。ダイアログを開く
  トリガとなる状態（`pendingRemovalId` 等）の保持は呼び出し側（Lobby / RosterPanel）に
  残してよい（既存の「オブジェクトを capture したままにしない」設計を変えないため）。
- **FR-178**: 共有コンポーネントは、判定規則（`canTransferHostTo` / `canRemoveParticipant` /
  `canReorderRotation` / `participantLabel`）を `participant-label.ts` からそのまま利用
  しなければならない。判定規則を共有コンポーネントの内部に再実装してはならない。
- **FR-179**: 役割/代理/一時離脱/現ドライバーのバッジ構成（`ParticipantBadges` 相当）、
  および行内アクションボタンの見た目（`RowIconButton` vs `MiniButton`）は、Lobby と
  RosterPanel で実装が一致していないため、共有コンポーネントへ統合してはならない。
  各画面は現状のバッジ・ボタン実装をそれぞれ独立に維持しなければならない。
  （判断根拠: plan.md「コンポーネントとインターフェース」節の「不採用にした共通化案」）
- **FR-180**: 参加者一覧の表示構造（フラット一覧 or ドライバー/見学のセクション分割＋
  ターン順ソート）は、Lobby.tsx / RosterPanel.tsx にそれぞれ残し、共有コンポーネント側へ
  移動してはならない。

**baseline.md の `[要確認]` を受けた決定（本仕様が確定させる）**

  について、**追加しない**ことを決定する。理由は FR-181 と同じ。

**安全ネット**

- **FR-184**: 一本化の作業は、各段階の終了時点で `packages/core` ・ `apps/sync` ・

## 前提

明示的な指示が無かった事項について、次を仮定した。**誤っていれば指摘してほしい。**

1. 一本化する範囲は「Lobby と RosterPanel の間で実装まで一致している部品」のみであり、
   `Session.tsx` 内の2つの `RosterPanel` 呼び出し（セッションタブ／ルームタブ）は
   同一コンポーネントの再利用であるため対象に含めない。
2. 実画面確認は開発環境（`vite` 再起動後・`bun run src/server.ts`）で行う想定とする。
3. 「利用者に見える変更ゼロ」の判定基準は、本仕様の「外部から観測可能な振る舞いの定義」表に
   従う。この表に載っていない差分（ファイル分割・関数名等）は振る舞いの変更に数えない。
