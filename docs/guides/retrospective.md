# 振り返りガイド

## このガイドの位置づけ

**振り返りの型と書き方の正本はこのガイドです。** 「epic・大きめの Issue の完了時には
振り返りを記録する（MUST）」という決定そのものは
[`docs/adr/0003`](../adr/0003-agile-operations.md)（決定 4）が定めており、型・書き方の
追加や更新は ADR の改版を経ずにこのガイドの更新のみで行います（`docs/adr/0002` の
三層構造・書き分け規則）。振り返りは教訓の正本であり、決定は ADR に、要求は
Issue（EARS 記法）に、教訓は振り返りに記録するという分担です（憲法 原則 VIII
「記録が正本」）。

## いつ書くか

epic または大きめの Issue の完了時に書きます。小さな PR 1 件ごとには書きません
（積み上げ PR の 1 コミットごとに書くと粒度が細かすぎて教訓が埋もれます）。

## どこへ書くか

`docs/retrospectives/YYYY-MM-DD-<topic>.md` に置きます。`YYYY-MM-DD` は振り返りを
書いた日付、`<topic>` は epic 番号または内容が分かる短い識別子（例:
`2026-08-10-issue68-governance-and-docs`）です。

## 型（3 部構成）

振り返りは次の 3 部構成で書きます。感想文にせず、次に同じ罠を踏まないために
使える形で残すことが目的です。

1. **踏んだ罠（事実と再発条件）**
   何が起きたかを事実として書きます。「なぜ気づけなかったか」ではなく
   「どんな条件が揃うとまた起きるか」（再発条件）まで書きます。再発条件が
   書けない罠は、まだ原因の特定が終わっていません。

2. **検査の穴（緑のまま壊れていたものは何か・なぜ緑だったか）**
   テスト・型検査・lint が通っていたにもかかわらず問題が発生した箇所を書きます。
   「何が壊れていたのに緑だったか」と「なぜ検査がそれを検出できなかったか」の
   両方を書きます（憲法 原則 VII「検査は壊して確かめる」の裏返し。検査そのものの
   欠陥を記録する）。壊れていたのに検査に引っかからなかった実例が無ければ、
   このセクションは「該当なし」と明記します。

3. **次への申し送り（どの文書・Issue に反映したか）**
   教訓をどこに反映したかを書きます。設計判断が変わったなら ADR、手順・書き方が
   変わったならガイド、未対応の作業が残るなら Issue番号、というように反映先を
   具体的に書きます（DoD 項目 7「文書への影響を反映した」との対応）。反映先が
   無い教訓は、まだ次に活かせる形になっていません。

## 書き方

**事実 → 原因 → 対処の順で書きます。** 感想（「大変だった」「気をつけたい」）で
終わらせず、次にこの文書を読む人（自分自身を含む）が再発を防げる具体的な記述に
します。

- 事実は日時・箇所・現象を特定できる粒度で書く（「テストが落ちた」ではなく
  「`decide.test.ts` の〈どの〉ケースが〈どんな入力〉で失敗した」）
- 原因は「なぜそれが起きたか」の機序を書く。表面的な直接原因だけでなく、
  それを許した設計・運用上の条件まで掘る
- 対処は実際に行った修正と、再発を防ぐために変えた仕組み（検査・文書・手順）を
  分けて書く
