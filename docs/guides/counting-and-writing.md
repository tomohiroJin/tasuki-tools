# 数える・書く規律

## このガイドの位置づけ

**件数を言うとき、文書を書くときに繰り返し踏んだ誤りの型をまとめた、書き方のガイドである。**
新しい義務は作らない。正本は憲法 原則 VIII（記録が正本・二重正本を作らない）と
[`AGENTS.md`](../../AGENTS.md)「AI 運用規則」で、ここはその使い方を示す
（[`docs/adr/0002`](../adr/0002-document-system-three-layers.md) の三層構造のうち、ガイドの層）。

## 数える

- **件数は実行して数える。** 文字列検索の件数は、行数であって項目数ではない（`grep -n | wc -l` は行を数え、`grep -c` は 1 行に複数あっても 1 と数える）。
  テーブルの結果を grep で数えるとヘッダ行も数える。**機構が申告する件数の行**（実行の最初に出る件数・`--plan` の件数行など）を読む
- 数えたコマンドを、数の隣に残す。後から同じ手順で数え直せる
- **出力を切って数えない。** `head`・`tail` で切った出力は、眺めるためのもので、数えるためのものではない。数えるなら切らずに集計へ渡す
- 数える対象が**古い台帳**でないかを疑う。リモート追跡の参照・キャッシュ・生成済みの一覧は、現物とずれる
  （枝の有無は `git ls-remote`、PR は `gh pr list` で現物に聞く）
- 測る場所が正しいかを先に見る。フィルタの名前が workspace に無いと 0 件一致で成功扱いになる（偽の緑）。置き場の測り方は [`development.md`](./development.md)「9p 越しで実行するとき」
- 緑も件数も、まず測り方を疑う。対照（壊さない状態で緑・壊した状態で赤）を取ってから、結果を信じる
- 道具が使えないと言う前に、経路を 1 つずつ実測する。報告は「揃っているもの」と「足りないもの」に分けて書く
- ISSUE 本文の件数・「無い」という主張・仮説は、ほぼ毎回どこかが誤っている（規則は [`AGENTS.md`](../../AGENTS.md)「作業の始めに」）。
  自分の計画も同じ。ISSUE が指定した解法も疑う。ADR は決定の節だけでなく「影響」の節まで読む

## 書く

### 数え上げでなく、性質で指す

- 「N 箇所」「この 4 形だけ」「どちらも」は、項目が増えると嘘になる。**数える鍵（何を数えたか）を明示するか、機構や性質で指す。**
  項目を足したら、数え上げの言い回し（「N つ」「どちらも」）と分類名を引いて追う
- テストや検査の件数を文書に直書きしない。数えたいなら、実行して出る件数を指す
- 切り詰めた観測から「これだけ」と断定しない。主張は**射程つき**で書く（「この基準で走査した範囲では 0 件」）

### 同じ数を二度書かない

- 数値（件数・時間・閾値）は、**正本を 1 か所に決め、ほかは参照する**。同じ数を spec・plan・tasks のように自分の成果物の間で転記すると食い違う
- 手元にしか無い数値（セッションの記憶・作業メモ）を公開文書へ書くときは、**途中の値であること**と**最終値の出典**を添える
- 同じ主張を複数の文書に書かない。書き換えるときは、同じ主張の言い換えを全域で引く（片側だけ直る）。名指しする側（例外表・検査の対象宣言・散文・テスト名）も引く

### 識別子を記憶で書かない

- コミットの SHA・PR 番号・ISSUE 番号・ファイル名・関数名は、**出力から写す**（`git log`・`gh` の出力）。記憶で書くと、存在しない SHA を書く
- 文書にコマンドやファイル名を書く前に、いまの現物で確かめる。古い名前は、検査が落ちるまで気づかれない

### 決定と現況を分ける

- **決定の段（ADR・設計・計画）に、完了形で現況を書かない。** 規範の文書が現況について嘘をつくようになる。
  現況は記録（振り返り・ISSUE・PR）に書く。書いた後で、完了形の語（「済」「導入した」「いまは」）を最後に走査する
- 「節が無い」と言う前に、履歴を引く。参照が壊れて見えるときは、別の日付の設計を指している場合がある（`git log` で差し戻しを探す）。
  「設計正本」と書かれた参照は、文書ごとに指す設計が違う（例: `docs/adr/0011`・`docs/adr/0012` の裸の「設計正本」は
  `docs/superpowers/specs/2026-08-13-security-norms-design.md`、`scripts/audit-ui-components.mjs` のは #320 の UI の設計）。その文書の冒頭か近くの参照で、どの設計かを確かめる

### 節の追記は末尾へ

- 文書へ `##` を途中に差し込むと、**直後の `###` が新しい節の子になり、帰属が変わる。** 追記は末尾へ足す。
  途中へ足すなら、直後が `###` でないかを `grep -n '^##\|^###' <ファイル>` で見る。足した `###` の親が意図した `##` かも、足した後に同じ grep で確かめる
  （設計文書の改定の決まりは [`design-doc-revision.md`](./design-doc-revision.md)）

### 規範と食い違う教訓は、両方の条件を書く

- 既存の規範と食い違う教訓を足すときは、片方を上書きせず、**それぞれが当てはまる条件**を並べて書く。
  例: 「範囲外の作業は別の Issue / PR に切り出す」と「範囲内の作業を先送りの連鎖にしない」は、対象が違う
  （[`pr-granularity.md`](./pr-granularity.md) の「派生した作業の扱い」）
- 条件を揃えても解けない食い違いは、書かずに人へ聞く

## 検査と対策を書くとき

- 欠陥を塞ぐ対策は、同じ欠陥を持ちやすい（件数 0 のときの扱い・規範を破る手順書・閉じた数え上げ）。**新しい検査に、同じ検査を当てる**
- 全称・否定・「唯一」の主張は、反例を作って確かめる。判定はヘルパへ寄せ、複数の場所へ写さない
- 単純な検査（状態を持たず、許可の一覧が閉じているもの）は、賢い検査より穴が少ない。ただし倒す条件は
  [敵対的レビュー](./procedures/adversarial-review.md)の「往復の終わり方」を見る
- 規範に強制の実装が無いときの考え方は [`security.md`](./security.md) の「規範に強制の実装が無いとき」
- 期限つきの約束（例外の解除など）は、専用の ISSUE に置く（[`development.md`](./development.md)「緊急の脆弱性修正を待機期間中に取り込む例外手順」）
- 指標の未達を潰す前に、内訳を出し、その数を作っている規範を確かめる。別の決定が「残す」と定めたものを、別の指標が未達と数えることがある。
  合否の無い行は、基準値と比べない限り、後退しても緑のままである
