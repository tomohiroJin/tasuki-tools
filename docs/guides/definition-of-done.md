# DoD（Definition of Done）ガイド

## このガイドの位置づけ

**DoD 項目の正本はこのガイドです。** 「DoD を運用する」という決定そのものは
[`docs/adr/0003`](../adr/0003-agile-operations.md) が定めており、項目の追加・削除は
ADR の改版を経ずにこのガイドの更新のみで行います（`docs/adr/0002` の三層構造・
書き分け規則）。すべての Issue / PR はここに挙げる 8 項目を満たしてからマージします
（憲法 原則 IX「小さく回す」）。

## チェックリスト

以下は PR テンプレートに転記して使うチェックリストです。各項目の補足は
「何をもって満たしたとするか」を示します。**文書のみの変更などその項目が
そもそも該当しない場合は、チェックを付ける代わりに「該当なし」と明記してよい**
（テストを伴わない ADR・ガイド・README の更新等が典型例）。

1. [ ] **テストを先に書き、ユニットテストが揃って全緑（`pnpm test`）**
   Red → Green の順を守り、`pnpm test` がすべてのパッケージで通ることを確認する
   （憲法 原則 I「テスト駆動開発」）。文書のみの変更など該当しない場合は
   「該当なし」と明記してよい。

2. [ ] **利用者の通る経路が変わる変更では、必要な E2E テストを作成した（`pnpm e2e`）**
   実画面・実プロトコルを通る振る舞いが変わったときに対象範囲の `pnpm e2e` を実行し、
   結果を報告する（憲法 原則 V「実画面検証」）。API 内部実装のみの変更など
   利用者の経路が変わらない場合は「該当なし」と明記してよい。

3. [ ] **新しく足した検査は、わざと壊して赤くなることを確認した**
   実装側を意図的に壊し、追加した検査が失敗することを確認してから元に戻す
   （憲法 原則 VII「検査は壊して確かめる」）。新しい検査を追加していない変更
   （リファクタリングのみ等）では「該当なし」と明記してよい。

4. [ ] **実装を書き換えた場合、既存テストが恒真化していないか変異で確認した**
   既存実装を書き換えたときは、対象箇所を意図的に壊して既存テストが赤くなるか
   確かめる（変異検査。憲法 原則 VII）。新規追加のみで既存実装を書き換えていない
   場合や文書のみの変更は「該当なし」と明記してよい。

5. [ ] **実経路で動作を確認した（実画面または実プロトコル）**
   テストが緑・型検査が通るだけで完了とせず、実際の画面操作または実際の
   WebSocket プロトコル越しに動作を確かめる（憲法 原則 V「実画面検証」）。
   挙動に影響しない変更（文書のみ・コメントのみ等）では「該当なし」と
   明記してよい。

6. [ ] **リファクタリングを実施した（Tidy First: 実装に先立つ整地、または実装後の
       後片づけ。大きな整理は別出しの Issue / PR として明示した）**
   実装の前後どちらでも構わないが、この PR の範囲を超える大きな整理が
   必要だと分かった場合は、この PR に混ぜず別の Issue / PR として切り出す
   （憲法 原則 IX「小さく回す」）。整地・後片づけの必要が生じなかった場合は
   「該当なし」と明記してよい。

7. [ ] **文書（README / ADR / ガイド）への影響を反映した**
   決定を変えたら ADR、書き方を変えたらガイド、使い方を変えたら README、
   というように影響が及ぶ文書を更新する。どの文書にも影響しない変更
   （内部リファクタリングのみ等）では「該当なし」と明記してよい。

8. [ ] **Issue の完了条件を満たした**
   Issue 本文に書かれた完了条件（EARS で書かれた振る舞いを含む）を満たしたことを
   確認する。完了条件が明文化されていない Issue（chore 等）では、代わりに
   作業内容が Issue の目的を満たしていることを確認し「該当なし」ではなく
   その旨を記す。

## 新しい画面・部品を足すときの作法

画面（アプリの主な画面・状態）や部品（`packages/ui` の部品）を足す・大きく変える PR は、上の 8 項目に加えて次を満たします
（決定は [`docs/adr/0035`](../adr/0035-spacing-owner-and-stack-components.md) 決定 5。洗い出し（#479）の崩れは、どれも既存の検査を緑のまま通った。
測っていたのは押せる操作の大きさ・当たりの重なり・横のはみ出しだけで、**ブロックどうしの間と重なり**は誰も測っていなかった）。
PR 本文の「確かめたこと」に、各項目を満たした根拠を 1 行ずつ書きます。該当しない項目は「該当なし」と理由を書きます。

1. [ ] **部品と余白のトークンを使った。** 縦に並ぶブロックの間は親が `gap` で持つ（`.ui-stack`・画面の容器の `gap`）。子へ外側の縦の余白（`margin-block`・`margin-top`・`margin-bottom`）を足さない。
   見出し＋操作の行は `.ui-section-head` を使う。間の値はトークン（`--space-1`〜`--space-6`）で書き、値の直書きをしない（`audit-ui-components` が落とす）。部品の一覧と使い方は `packages/ui/README.md`。
2. [ ] **5 つの幅（320・390・768・1280・1920）で撮影して目で見た。** 憲法 原則 V の実画面検証。40rem 未満（320・390）と 64rem 以上（1280・1920）は並びが変わるので、768 だけで済ませない。
   長い名前（全角 28 字）と、人数が多い状態でも見る。
3. [ ] **重なりと間の検査を呼んだ。** `e2e/specs/block-gaps.spec.ts` に、足した画面の状態を 1 つ足し、`expectBlocksSeparated`（`e2e/support/block-gaps.ts`）を呼ぶ。
   隣り合うブロックが重ならず、縦の間が `--space-2`（8px。字と箱の組は `--space-1`＝4px）以上あることを、5 つの幅と文字 200% で測る。
   赤になったら、偽陽性を規則で除く前にまず本当の崩れを疑う。除く規則を足すときは、要素の名前ではなく**性質**（位置・表示・変形・字だけか）で書き、理由をコメントに書く（許可リストは最小に）。
4. [ ] **文字を 200% にしても確かめた。** `<html>` の字を 200% にして、5 つの幅で崩れない（上の検査が 1 倍と 200% の両方で測る）。
   #555・#556 のレビューで見つかった崩れの多くは、文字 200% の折り返しで出た（名前と操作が次の行へ回って詰まる・列が中身の幅まで縮まず隣と重なる）。
   この検査自身も、4 か所の崩れを見つけた（agenda の延長のボタンの重なり・roulette の行の 2 段・timer の共有メモの印は文字 200%、timer のロビーの行の詰まりは 1 倍）。
   幅の下限やはみ出しの量（320 の 200% に残る記録。`docs/superpowers/specs/2026-11-06-layout-audit.md` の補遺）は、この検査が測らない。足した画面で目でも見る。

検査は構造（同じ親の隣り合う子）で測る。画面ごとの座標を決め打ちしないので、新しい画面も状態を足すだけで同じ規則に入る。
スクリーンショットの比較は入れない（ADR 0035 決定 4）。撮影は人とエージェントが目で見るために行う。

## 完了条件と検査を書くときの補足

- **段組みは、実際の中身の量で決める。** 読む物は、行の長さが取れる区画に置く。検査が緑でも、釣り合いは誰も測っていないので、
  撮影（上の作法の 2）を自分で目で見る。
- **値を足したときは、wire（メッセージ）までの全ホップを 1 本のテストで通す。** 途中の段だけのテストは、どこかのホップで値が落ちても緑になる。
- **検査を足したら、利用者が叩くコマンドで一度発火させる。** 個別のスクリプトが緑でも、包んだ側（スクリプト化・別名・ランナー）が元の検証を引き継ぐとは限らない。
  依存の宣言を確かめる検査は、ランナーが解決を補った緑を信じない（`docs/guides/development.md`「検査スクリプトを新しく足すとき」）。
- **完了条件は、EARS の振る舞いと検査の対応表で、手段まで突き合わせる。** 設計の正本が検査の手段（何を・どの層で確かめるか）まで指定しているなら、
  主張が一致するだけでなく、指定された手段で検査されているかを見る（上のチェックリストの 8）。
- **対照が取れたことと、原因が分かったことは別。** 壊さずに緑・壊して赤が取れても、原因が説明できるまで「直った」と書かない。
