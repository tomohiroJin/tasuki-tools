# 設計文書の改定のしかた

設計文書（`docs/superpowers/specs/` の設計・`docs/superpowers/plans/` の実装計画）を
**決定したあとで直すときの手引き**です。**決まりそのものは [`docs/adr/0002`](../adr/0002-document-system-three-layers.md)
の追記（2026-11-03・#506）が定めています。** ここは手順・雛形・例で、育ててよい（同 決定 2）。

**ADR の本文をどう直すかは別の決まりです**（同 追記（2026-09-09・#258））。ここは設計文書の話です。

## 使い方

決まりの要点は「決定した節（マージ後の節）は書き換えず、改定は新しい節に書く」です。細部（意味を変えない直しの範囲・
決定した節とは何か・#258 の作法を採らない理由）は ADR の追記を読んでください。ここに写しません。

- 実装で外れた・見直した・実装に任せた答えは、**文書の末尾に足した節**（補遺・改定の節）に、どの節をどう置き換えるかを名指しして書く
- 古い節を置き換える新しい節を足したら、**置き換えられる古い節の末尾に印を 1 行だけ**足す。本文は変えない

  ```markdown
  > 改定: §N（2026-11-03・#506）
  ```

- 古い節の本文が現況と違って見えても直さない。置き換えは新しい節の側に「§N の○○は、この形に置き換わった」と書く

## 見落とさないために

この決まりは、文書ごとの冒頭や末尾の節にしか書かれていないことが多く、**離れた節を読んでいる最中は目に入りません**。
次のようにします。

- 設計文書を直す前に、**その文書の末尾の補遺・改定の節と冒頭を先に読む**
- Issue に「設計 §N の見直し」とあっても、**§N を直すことを求めているとは読まない**。見直しの結果は
  新しい節に書く。Issue の書き方があいまいなら、書き換えてよいか人に聞く
- 新しい設計文書を書くときは、冒頭に次の 1 行を置く（置く範囲と、いつの日付以降の文書に要求するかは `scripts/audit-plan-gate.mjs` の `DECLARATION_WINDOW_LINES` と `DECLARATION_BOUNDARY_DATE` が正本）。節の番号は書かない（書き始めには決まらない）。
  折り返して続く引用行にしてもよく、ガイドへはバッククォートのパスでも相対リンクでも指せる。
  読み手がどの節から入っても決まりに当たるようにする

  ```markdown
  > マージ後の節は書き換えない。後から分かったことは末尾の補遺の節に書き、置き換えた古い節の末尾に改定の印を足す（`docs/guides/design-doc-revision.md`）。
  ```
- 文書の中で他の節を指すときは、**行番号で指さない**。「すべて」「どちらも」のような量化語を書いたら、反例を作って確かめる
- 範囲を切り出すときは、その時点で既に決まっていないかを確かめる。案内を足すときは、誤って当てはまる場合を先に探す
- 節を足すときは末尾へ足す。途中へ足すと、直後の `###` が新しい節の子になる（[`counting-and-writing.md`](./counting-and-writing.md)）

## 実例

`docs/superpowers/specs/2026-10-28-checkin-checkout-design.md` は §12 の冒頭で「§1〜§11 は書き換えない」と
宣言し、§5 の札の名前の読み上げが手札では変わった分を §14.2 の 5 に書いている（§12.1 は別の外れを扱う）。
#491 の試し（`docs/retrospectives/2026-11-02-issue-491-two-place-trial.md` の罠 2）では、決まりが §12 にしか無く、
§5 側に印も無かったため、§5 を読んで直した AI が決まりに気づかず書き換えた。

## 機械で守れるか（`docs/adr/0030` 決定 2）

決まりには 2 つの面があります。守れる形が違うので分けて書きます。

**差分の検査（古い節の書き換えの禁止）は、足していません。** 基準の版は
`git merge-base origin/main HEAD` で取れ（`scripts/local-check.mjs` と `scripts/mutation-check.mjs` が同じ取り方をしている）、
宣言の無い古い文書は `scripts/audit-plan-gate.mjs` の境界日の型で外せます。それでも守れないのは、
**何を書き換えと数えるかが機械で引けない**からです。

- 許す直し（誤字・壊れたリンク・`- [x]` の印・改定の印の 1 行）と、意味を変える書き換えは、差分の形が同じです。
  誤字の直しと数値の差し替えは、どちらも 1 行の置換です
- 「決定した節」の範囲は文書ごとに違い、節の見出しは途中に足せば番号がずれます。範囲を機械に渡すには
  文書ごとの宣言の書式を固定する必要があり、既存の文書へは遡れません
- 許可リストに倒すと、リストに無い正当な直しで止まり、検査が外されがちです

**存在の検査のうち、冒頭の 1 行は足しました。** `scripts/audit-plan-gate.mjs`（CI の docs ジョブで流れる既存の監査）が、
境界日（同ファイルの `DECLARATION_BOUNDARY_DATE`）以降の日付を持つ設計（`docs/superpowers/specs/`）と実装計画（`docs/superpowers/plans/`）について、
冒頭（`DECLARATION_WINDOW_LINES` 行）の引用に「書き換えない」とこのガイドのパスがあるかを見ます。ガイドのパスが実在することも見ます
（設計文書の置き場はリンク検査の外なので、ガイドの改名・削除を宣言の側では捕まえられないため）。見るのは**存在だけ**で、節が書き換えられたかは見ません。
境界日より前の文書へは遡らず、除外の表も持ちません（実装計画のゲートと同じ型）。
対象は置き場の**直下**の `*.md` だけで、`README.md` と、日付つきディレクトリの下の付属ファイル（例: `specs/2026-11-01-x/notes.md`）は
設計文書ではないので見ません。付属ファイルを数えると、以前から許された置き方が日付の無いファイルとして落ちるためです。
コードフェンスと 4 字以上の字下げ（コードブロック）の中の引用では満たせません。

**残る穴（存在しか見ないことの帰結）:** HTML のコメントの中の宣言、「書き換えない」を否定する文面、
冒頭の宣言にもかかわらず後で節を書き換えること、文書の日付を偽って境界日より前に見せることは、検査では拾えません。
宣言は決まりへの入口であって、守られたことの証明ではありません。差分の検査を足していない理由（上）と同じで、レビューで見ます。

**改定の印（`> 改定: §N`）の検査は足していません。** 印が要るかどうかは「置き換える新しい節を足したか」で決まり、
その判断は節の意味を読まないと下せません（補遺の節が古い節を置き換えているのか、足しているだけなのかは、見出しの形では分かりません）。
印の書式だけを見ても、印があるべき所に無いことは拾えず、印を付け忘れた文書が素通りします。印は決まりとして残し、
レビューで見ます。

加えて、人と AI が**目にする場所に決まりを置いています**。`docs/superpowers/README.md`・`docs/README.md`・
新しい設計文書の冒頭の 1 行です。
