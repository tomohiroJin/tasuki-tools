# 設計文書の改定のしかた

設計文書（`docs/superpowers/specs/` の設計・`docs/superpowers/plans/` の実装計画）を
**決定したあとで直すときの作法**です。置き場を定める [`docs/adr/0002`](../adr/0002-document-system-three-layers.md)
決定 4 と、その追記（2026-08-16・#71）の「どちらも追記のみ」を、書き方まで下ろしたものです。
様式や例の追加はこのガイドの更新のみで行います（同 決定 2）。

**ADR の本文をどう直すかは別の決まりです**（同 追記（2026-09-09・#258））。ここは設計文書の話です。

## 決まり

**決定した節は書き換えません。改定は新しい節か追記に書きます。**

設計文書は「その時点で何を考え、なぜそう決めたか」の記録です。後から直すと、実装やレビューが
何を根拠に動いたかが辿れなくなります。実装で外れた箇所、設計が実装に任せた箇所、見直した決定は、
**文書の末尾に足した節**（実装後の補遺・改定の節）に、**どの節をどう置き換えるか**を名指しして書きます。

- 古い節には手を入れない。誤字や壊れたリンクの修正のような、意味を変えない直しだけは可
- 古い節の本文が現況と違って見えても、直さない。読み手が古い節で迷わないよう、**新しい節の側**に
  「§N の○○は、この形に置き換わった」と書く
- 新しい節は古い節を指す。古い節から新しい節への印は付けなくてよい（付けるなら、末尾への追記だけにする）
- 日付つきの記録（振り返り・追記）に引用された文面も同じ。書かれた時点の記録として残す

## 見落とさないために

この決まりは、文書ごとの冒頭や末尾の節にしか書かれていないことが多く、**離れた節を読んでいる最中は目に入りません**。
次のようにします。

- 設計文書を直す前に、**その文書の末尾の補遺・改定の節と冒頭を先に読む**。その文書に「書き換えない節」の
  宣言があれば従う
- Issue に「設計 §N の見直し」とあっても、**§N を直すことを求めているとは読まない**。見直しの結果は
  新しい節に書く。Issue の書き方があいまいなら、書き換えてよいか人に聞く
- 新しい設計文書を書くときは、冒頭に次の 1 行を置く。読み手がどの節から入っても決まりに当たるようにする

  ```markdown
  > 決定した節（§1〜§N）は書き換えない。後から分かったことは末尾の補遺の節に書く（`docs/guides/design-doc-revision.md`）。
  ```

  補遺の節を足したあとも、冒頭の 1 行はそのまま残す

## 実例

`docs/superpowers/specs/2026-10-28-checkin-checkout-design.md` は §12 の冒頭で「§1〜§11 は書き換えない」と
宣言し、§5 の札の読み上げの扱いが実装で変わった分を §12 に書いている。#491 の試し
（`docs/retrospectives/2026-11-02-issue-491-two-place-trial.md` の罠 2）では、決まりが §12 にしか無かったため、
§5 を読んで直した AI が決まりに気づかず書き換えた。

## 機械で守れるか（`docs/adr/0030` 決定 2）

**検査は足していません。** 検討した形と、足さない理由は次のとおりです。

- 「設計文書の頭に書き換えない節を宣言し、差分で検査する」形は、**基準の版との比較が要り、手元の
  `check:fast` と CI の両方で基準の取り方が割れます**（base の取り方・squash 後の履歴）
- 古い設計文書の大半は宣言を持たず、宣言を一斉に足すと「決定当時の記録」に手を入れることになります。
  宣言の無い文書は検査の対象外になり、**守りたい文書ほど守れない**（宣言を忘れた文書が素通りする）
- 「意味を変えない直しは可」の線は機械で引けず、許可リストか人の判断に倒れます。誤検知で止まる検査は
  外されがちです

代わりに、人と AI が**目にする場所に決まりを置いています**。`docs/superpowers/README.md`・`docs/README.md`・
新しい設計文書の冒頭の 1 行です。同じ型の見落としが重なったら、宣言と差分を見る検査を改めて検討します。
