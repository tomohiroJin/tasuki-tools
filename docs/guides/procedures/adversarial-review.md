# 敵対的レビュー

## いつ使うか・拠り所

実装を終えた PR を、**壊れているところを探すつもりで**確かめるときに使います。#468〜#472 で行った手順を起こしたものです。

- 敵対的なレビューは、**実装したのとは別のエージェント（か人）が、実装した側の結論ではなく差分とコードを渡されて行う**
  （MUST。[`docs/adr/0030`](../../adr/0030-ai-driven-development-operations.md) 決定 5）。結論を渡すと、レビューはそれを追認しやすい
- 指摘は検査（テスト・変異・実画面の計測）で再現してから直す。再現できない指摘は、再現できなかったと記録する（同 決定 5）
- 「完了」の根拠は機械的な検査の結果と実経路での確認であって、レビューの印象ではない（同 決定 2・憲法 原則 V・VII）

## 頼む側（実装した側）がすること

1. レビューする側に渡すのは **ISSUE の番号・PR かブランチ・基準のブランチ（ふつうは `main`）だけ**にする。
   「何を確かめたか」「どこが怪しくないか」は渡さない（PR 本文の「テスト方法」も、先に読ませない）
2. 作業ツリーを分ける。レビューする側は実装した側の作業ツリーを触らない（同 決定 5。同じ作業ツリーでの衝突は変異検査で実際に起きた）

```bash
git fetch origin <ブランチ>
git worktree add ../review-<ISSUE 番号> origin/<ブランチ>
```

3. 返ってきた指摘は、下の「指摘を受けた後」のとおりに扱う

## レビューする側の手順

### 1. 求められていることを先に読む

差分より先に、**何が求められているか**を読みます。差分から読むと、差分が正しいことを前提に読んでしまう。

- ISSUE の背景・振る舞い（EARS）・完了条件・スコープ外
- 関係する ADR と、触っている層のガイド（例: [`docs/guides/architecture.md`](../architecture.md)）
- 完了条件の 1 つずつについて、**それを守るテストか検査がどこにあるはずか**を先に書き出す

### 2. 差分を読む

```bash
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
git log --oneline origin/main..HEAD
```

見るところ:

- 手順 1 で書き出した「あるはずのテスト」が、実際にあるか。完了条件に対応するテストが無いものを挙げる
- **テストの差分**。リファクタリングなのに既存のテストの期待値が変わっていたら、振る舞いが変わった疑いがある
  （`git diff origin/main...HEAD -- '*.test.*' '*.spec.*'`）
- 恒真のテスト（何をしても通る形。`expect` が無い・同じ値どうしを比べている・モックの戻り値をそのまま確かめている）
- 境界での検証・エラーの扱い・依存の向き（憲法 原則 IV・VI）。監査が見ない書き方で規則を抜けていないか
- 消えたコード。消した振る舞いを誰も頼っていないか（`git grep` で呼び手を探す）
- 文書。決定を変えたのに ADR が古いまま、使い方を変えたのに README が古いまま、になっていないか

### 3. 振る舞いの同値性を機械的に比べる（振る舞いを変えないはずの変更）

リファクタリング・部品への寄せ替えは「振る舞いを変えない」と主張しています。**読んで同じだと判断せず、比べます。**

- **既存のテストを変えずに流す。** 基準のブランチのテストを、変更後のコードへ当てる

```bash
git checkout origin/main -- <テストのファイル>   # レビュー用の作業ツリーでだけ行う
pnpm --filter <パッケージ> test
git checkout HEAD -- <テストのファイル>
```

- **出力を並べて比べる。** 純粋な関数なら、基準のブランチと変更後の両方を import して、生成した入力で出力の差を数える
  （差 0 件を件数つきで報告する。例: #284 では生成した 30 万件で差 0 件を実測し、変異 48 が等価だと示した。
  記録は `scripts/lib/mutation-declarations.mjs` の id 48 のコメント）
- **DOM と見た目を比べる。** 同じ操作をした後の DOM（`locator.ariaSnapshot()`・`page.content()`）・計算済みのスタイル
  （`getComputedStyle`）・要素の位置と大きさ（`boundingBox()`）を、基準のブランチと変更後で取って差を見る。
  取り方は [実画面で確かめる](./live-check.md)。片方ずつ起動するので、ポートを空けてから入れ替える
- **公開面を比べる。** パッケージのエントリが export する名前の差（消えた名前・増えた名前）

差が出たら、それが意図した差かを ISSUE と照らす。意図していない差は指摘にする。

### 4. 実画面で測る

画面・同期に触る変更は、[実画面で確かめる](./live-check.md) のとおり実際に起動して測ります（憲法 原則 V）。

- 印象ではなく数で言う（はみ出しの有無・要素の幅・重なり・コントラスト比・フォーカスが見えるか）
- 幅は少なくとも 320px と 1280px。段の境目（`40rem`・`64rem`・`90rem`。`docs/adr/0025` 決定 1）の前後も見る
- 同期は 2 つのブラウザのコンテキストで、片方の操作がもう片方に届くかを見る
- `prefers-reduced-motion: reduce` でも見る（動きを伴う画面）

### 5. 壊して確かめる

テストが緑であることは、テストが何かを守っている証拠になりません（憲法 原則 VII）。

- **足された検査とテストは、実装をわざと壊して赤くなるかを見る。** 壊すのはレビュー用の作業ツリーでだけ行い、見たら戻す
- 変異検査を流す。宣言を足していれば、その変異が検出されることも見る

```bash
node scripts/mutation-check.mjs --changed
```

- 検査を足したのに変異の宣言が無い・実装を書き換えたのに変異で確かめていない、は DoD 3・4 の欠けとして指摘する
  （変異の足し方は [変異の足し方・作り直し方](./mutations.md)）
- 検査を飛ばす・弱める変更（skip・変異の宣言の削除・走査対象の除外）が入っていたら、人の承認があるかを確かめる（`AGENTS.md`「AI 運用規則」）

### 6. 報告する

報告は、指摘の一覧と、確かめたこと・確かめられなかったことに分けて書きます（`docs/adr/0030` 決定 4）。

```markdown
## 指摘

### 1. <一行の要約>
- 重さ: 直す / 直すか検討 / 記録のみ
- 場所: `path/to/file.ts:42`
- 再現: <流したコマンド・足したテスト・測った値>
- 期待: <ISSUE・ADR・テストが求めていること>
- 実際: <起きたこと>

## 確かめたこと
- <流したコマンドと結果。比べた件数・測った幅>

## 確かめられなかったこと
- <流せなかった検査とその理由。無ければ「なし」>
```

- **再現できたものだけを「直す」にする。** 再現できない懸念は「記録のみ」にして、再現を試みた方法を書く
- 指摘が無ければ「指摘なし」と書き、確かめたことを同じ書式で書く。何も見ずに「問題なし」と書かない

## 指摘を受けた後（実装した側）

1. 指摘ごとに、**先に再現する**。テストを足す（Red）か、変異を足して未検出を確かめるか、実画面で測る
2. 直す（Green）。直した性質を守るテストに対して変異を足し、検出されることを確かめる（変異の `note` に「#<番号> のレビュー」と書く）
3. 直さない指摘は、PR 本文の「レビューで挙がったが今回やらないもの」に理由つきで残す。別の作業にするなら ISSUE を起こす
   （起こすのは依頼に含まれる範囲で。含まれないなら人に聞く）
4. 再現できなかった指摘は、再現できなかったことと試した方法を PR 本文に残す
5. 直した後、もう一度レビューを頼むときは、手順 1 に戻って差分だけを渡す
