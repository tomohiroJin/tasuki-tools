# 変異の足し方・作り直し方

## いつ使うか・拠り所

- **検査やテストを足したとき**: 実装をわざと壊して赤くなることを確かめ、その壊し方を変異として残す（DoD 3・憲法 原則 VII）
- **実装を書き換えたとき**: 既存のテストが恒真になっていないかを変異で確かめる（DoD 4・`docs/adr/0006` 決定 4）
- **変異のパッチが当たらなくなったとき**: 作り直す（下の「作り直す」）

変異検査の仕組み・選び方の指定（`--changed`・`--id`・`--pkg`・`--jobs`・`--shard`）・段ごとの使い分けの正本は
[`docs/guides/development.md`](../development.md) の「検査系」です。ここは変異を足す・作り直すときの手順です。

置き場:

- 宣言の表: `scripts/lib/mutation-declarations.mjs` の `MUTATIONS`
- パッチ: `scripts/mutations/m<ID>-<短い名前>.patch`
- 宣言とパッチは 1 対 1（`scripts/mutation-check.mjs` の `assertMutationPatchesBijective` が実行の初めに見る）

## 足す

### 1. 守りたい性質を 1 つ決める

「このテストは何を守っているか」を 1 文で書きます。それが `label` になります。

- 1 つの変異で壊すのは 1 つの性質だけ。2 つ壊すと、どちらのテストが拾ったのか分からない
- **本当に起こりそうな壊れ方を選ぶ**（境界の 1 つずれ・条件の反転・段の飛ばし・検証の外し・順序の入れ替え）。
  `throw` を差し込むような、どのテストでも落ちる壊し方は何も確かめない
- **等価な変異にしない。** 壊しても出力が変わらないなら、テストが足りないのではなく変異が意味を持たない。
  怪しいときは入力を生成して元と変異後の出力を比べ、差 0 件なら変異にしない（`MUTATIONS` の id 48 のコメントが例）

### 2. 番号を決める

```bash
grep -o 'id: [0-9]*' scripts/lib/mutation-declarations.mjs | awk '{print $2}' | sort -n | tail -1
```

いまの最大に 1 を足します。**番号は詰めない・使い回さない**（過去の記録が番号で変異を指している）。
複数の作業を並行に進めるときは、ISSUE で範囲を割り当ててから使います（表の頭の `RESERVED_*` が例）。
同じ番号が別のブランチで使われていたら、後から merge する側が付け直します。

### 3. パッチを作る

製品コード（かテストされる検査の本体）を最小限だけ壊し、その差分をパッチにして、すぐ戻します。

```bash
# 1. 壊す（エディタで 1 か所だけ直す）
# 2. 差分をパッチにする（リポジトリ直下から。パスは a/… b/… のリポジトリ相対になる）
git diff -- <壊したファイル> > scripts/mutations/m<ID>-<短い名前>.patch
# 3. 戻す
git checkout -- <壊したファイル>
# 4. 当たることを確かめる（作業ツリーは変わらない）
git apply --check scripts/mutations/m<ID>-<短い名前>.patch
```

- パッチは 1 ファイルにする。2 ファイルに跨るなら、性質が 1 つかを見直す
- 壊した行の周りにコメントを足さない（パッチの文脈の行が増え、周りを触ったときに当たらなくなりやすい）

### 4. 宣言を足す

`MUTATIONS` の末尾に足します。

```js
{
  id: <ID>,
  label: "<何をどう壊すか。label だけで壊し方が分かるように>",
  patch: "m<ID>-<短い名前>.patch",
  pkg: "<対象のディレクトリ。例: packages/room-core・apps/tasuki-sync・scripts>",
  tests: ["<pkg からの相対パス。検出を期待するテスト>"],
  note: "<ISSUE 番号。壊れると何が起きるか（利用者から見て）>",
},
```

- `tests` には**その性質を守るテストのファイルだけ**を書く。パッケージの全テストを並べると、どのテストが守っているかが記録に残らない
- `note` は必ず書く。「#<番号>。<壊れると何が起きるか>」。レビューで見つかった欠けを塞いだ変異は「#<番号> のレビュー。」と書く

### 5. 検出されることを確かめる

```bash
node scripts/mutation-check.mjs --id <ID>
```

- 作業ツリーは、宣言の表・パッチ・入口（`DIRTY_CHECK_EXCLUDES`）のほかは綺麗にしておく。それ以外の変更は先にコミットする
- **「検出」なら終わり。** 宣言とパッチを同じコミットに入れる
- **「未検出」なら、テストが性質を守っていない。** テストを足すか直して（TDD の Red から）、もう一度流す。
  **変異を弱めたり消したりして通さない**（検査を弱める変更。`AGENTS.md`「AI 運用規則」）
- 対照実行（変異を当てる前の実行）が落ちたら、変異ではなくテストかランナーが壊れている。先にそちらを直す

最後に、関係する変異をまとめて流します（PR を出す前の段。`docs/guides/development.md` の段の表）。

```bash
node scripts/mutation-check.mjs --changed
```

宣言の表を書き足した枝は「機構の変更」に当たり、`--changed` は全件に倒れます。時間が掛かるときは `--jobs <コアの数>` を足します。

## 作り直す

周りのコードを変えると、パッチの文脈（直前・直後の行）が合わなくなり、`git apply` が失敗します。そうなった変異は
**結果の表に「未検出」として現れないまま死にます**（検査ごと異常終了するため）。`scripts/mutation-check.test.mjs` の
「宣言した変異が当たること」が `git apply --check` で全件を見て、落ちたものを名指しします。

```bash
git apply --check scripts/mutations/m<ID>-*.patch
```

1. 宣言の `label` と古いパッチを読み、**何をどう壊していたか**を確かめる
2. いまのコードで、**同じ壊し方**を手で再現する（壊す場所が移っていれば、移った先で）
3. 「足す」の手順 3 のとおり、`git diff` で同じファイル名のパッチを上書きし、戻し、`git apply --check` で確かめる
4. `node scripts/mutation-check.mjs --id <ID>` で検出されることを確かめる

- **変異そのものは変えない。** `label`（壊し方）は同じまま、パッチの文脈だけを合わせる
- 守っていたテストが別のファイルへ移った・対象が別のパッケージへ移ったときは、`pkg`・`tests` を直し、`note` に理由を足す
- 作り直した変異の番号は、PR 本文の「変更内容」に書く（例: 「m608・m612 を作り直し」）

## 消す

**変異は原則として消しません。** 消してよいのは、守っていた性質が**概念ごと無くなった**とき（例: 役割とホストを廃止して、
権限の確認そのものが消えた）と、等価な変異だと分かったときだけです。

- 消すのは検査を弱める変更に当たるので、**人の承認を得てから**消す（`AGENTS.md`「AI 運用規則」・`docs/adr/0030` 決定 1）
- 宣言を消した場所に、消した理由と番号をコメントで残す。**番号は詰めない**（`MUTATIONS` の id 2・5・48 のコメントが例）
- パッチのファイルも消す（宣言とパッチは 1 対 1）
