# 変異の足し方・作り直し方

## いつ使うか・拠り所

- **検査やテストを足したとき**: 実装をわざと壊して赤くなることを確かめ、その壊し方を変異として残す（DoD 3・憲法 原則 VII）
- **実装を書き換えたとき**: 既存のテストが恒真になっていないかを変異で確かめる（DoD 4・`docs/adr/0006` 決定 4）
- **変異のパッチが当たらなくなったとき**: 作り直す（下の「作り直す」）

変異検査の仕組み・選び方の指定（`--changed`・`--id`・`--pkg`・`--jobs`・`--shard`）・段ごとの使い分けの正本は
[`docs/guides/development.md`](../development.md) の「検査系」です。ここは変異を足す・作り直すときの手順です。

置き場:

- 宣言の表: `scripts/lib/mutation-declarations.mjs` の `MUTATIONS`
- パッチ: `scripts/mutations/m<ID>-<短い名前>.patch`
- 宣言とパッチは 1 対 1（`scripts/mutation-check.mjs` の `assertMutationPatchesBijective` が実行の初めに見る）

## 足す

### 1. 守りたい性質を 1 つ決める

「このテストは何を守っているか」を 1 文で書きます。それが `label` になります。

- 1 つの変異で壊すのは 1 つの性質だけ。2 つ壊すと、どちらのテストが拾ったのか分からない
- **本当に起こりそうな壊れ方を選ぶ**（境界の 1 つずれ・条件の反転・段の飛ばし・検証の外し・順序の入れ替え）。
  `throw` を差し込むような、どのテストでも落ちる壊し方は何も確かめない
- **等価な変異にしない。** 壊しても出力が変わらないなら、テストが足りないのではなく変異が意味を持たない。
  怪しいときは入力を生成して元と変異後の出力を比べ、差 0 件なら変異にしない（`MUTATIONS` の id 48 のコメントが例）

### 2. 番号を決める

```bash
grep -o 'id: [0-9]*' scripts/lib/mutation-declarations.mjs | awk '{print $2}' | sort -n | tail -1
```

いまの最大に 1 を足します。**番号は詰めない・使い回さない**（過去の記録が番号で変異を指している）。
複数の作業を並行に進めるときは、ISSUE で範囲を割り当ててから使います（表の頭の `RESERVED_*` が例）。
範囲は最初から**多めに**予約します。並行の作業は、思ったより変異を足します（[並行実装のまとめ役](./orchestration.md)）。
同じ番号が別のブランチで使われていたら、後から merge する側が付け直します。

### 3. パッチを作る

製品コード（かテストされる検査の本体）を最小限だけ壊し、その差分をパッチにして、すぐ戻します。

```bash
# 1. 壊す（エディタで 1 か所だけ直す）
# 2. 差分をパッチにする（リポジトリ直下から。パスは a/… b/… のリポジトリ相対になる）
git diff -- <壊したファイル> > scripts/mutations/m<ID>-<短い名前>.patch
# 3. 戻す
git checkout -- <壊したファイル>
# 4. 当たることを確かめる（作業ツリーは変わらない）
git apply --check scripts/mutations/m<ID>-<短い名前>.patch
```

- パッチは 1 ファイルにする。2 ファイルに跨るなら、性質が 1 つかを見直す
- 壊した行の周りにコメントを足さない（パッチの文脈の行が増え、周りを触ったときに当たらなくなりやすい）

### 4. 宣言を足す

`MUTATIONS` の末尾に足します。

```js
{
  id: <ID>,
  label: "<何をどう壊すか。label だけで壊し方が分かるように>",
  patch: "m<ID>-<短い名前>.patch",
  pkg: "<対象のディレクトリ。例: packages/room-core・apps/tasuki-sync・scripts>",
  tests: ["<pkg からの相対パス。検出を期待するテスト>"],
  note: "<ISSUE 番号。壊れると何が起きるか（利用者から見て）>",
},
```

- `tests` には**その性質を守るテストのファイルだけ**を書く。パッケージの全テストを並べると、どのテストが守っているかが記録に残らない
- **重いファイル（子プロセスを何十回も走らせるもの）を `tests` に置かない**（#544）。対照実行は `tests` の組ごとに使い回す（`groupByControl`、#387）が、
  検出の実行は変異ごとに 1 回流れる。同じ重いファイルを指す変異が同じワーカーに寄ると、そのシャードだけが長くなる。
  重いファイルは検査スクリプトごとに分け（`scripts/wiring-*.test.mjs`）、関係するファイルだけを指す。
  それでも重い組を指すときは、下の「重い組の実測の表」に載せる（載せないと見積もりが軽く数えて、また寄る。#546）
- `note` は必ず書く。「#<番号>。<壊れると何が起きるか>」。レビューで見つかった欠けを塞いだ変異は「#<番号> のレビュー。」と書く

### 5. 検出されることを確かめる

```bash
node scripts/mutation-check.mjs --id <ID>
```

- 作業ツリーは、宣言の表・パッチ・入口（`DIRTY_CHECK_EXCLUDES`）のほかは綺麗にしておく。それ以外の変更は先にコミットする
- 別の作業ツリー（`git worktree add`）で流すときは、**別の作業ツリーの `node_modules` を symlink で共有しない。**
  `.gitignore` の `node_modules/` はディレクトリにしか当たらないので、symlink は未追跡（`?? node_modules`）に見え、
  `mutation-check` が「未コミットの変更があります」で起動を拒む（#491 の振り返りの罠 7）。
  その作業ツリーで `pnpm install --frozen-lockfile --offline --store-dir "$(pnpm -C <元の作業ツリー> store path)"` を流す（別のファイルシステムの一時ディレクトリでも本体のストアを使うため。#535）。**ストアの場所は元の（本体の）作業ツリーで引く。** 新しい作業ツリーの中で `pnpm store path` を展開すると、そこのファイルシステムのストアを指して元の失敗に戻る。その作業ツリーで後から pnpm を流すときも、同じ `--store-dir` を渡す（渡さないと `ERR_PNPM_UNEXPECTED_STORE` になる）。元の作業ツリーで install 済みなら pnpm の store を使うので取得はせず、数秒で済む（#509 で 3 秒）。
  store に無いと言われたら（`ERR_PNPM_NO_OFFLINE_TARBALL`）、`--offline` を外して流す
- **「検出」なら終わり。** 宣言とパッチを同じコミットに入れる
- **「未検出」なら、テストが性質を守っていない。** テストを足すか直して（TDD の Red から）、もう一度流す。
  **変異を弱めたり消したりして通さない**（検査を弱める変更。`AGENTS.md`「AI 運用規則」）
- 対照実行（変異を当てる前の実行）が落ちたら、変異ではなくテストかランナーが壊れている。先にそちらを直す

最後に、関係する変異をまとめて流します（PR を出す前の段。`docs/guides/development.md` の段の表）。

```bash
node scripts/mutation-check.mjs --changed
```

宣言の表を書き足した枝は「機構の変更」に当たり、`--changed` は全件に倒れます。流し始める前に件数・見込みの時間と、
手元で絞る `--id` の候補が出ます（`--plan` を足すと見込みだけを出して終わる）。手元はその `--id` で絞り、全件は CI に任せます。

## 途中で止める

まず `ps -eo pid,ppid,pgid,args` で、自分が起動した `mutation-check` の親・子と実行の形を確かめます。
子のテストプロセスや、呼び出したシェルだけを止めないでください。
**逐次実行と並列実行では、止め方が違います**（#505 のレビューで実測された制約）。

### 逐次実行（`--jobs` なし・`--jobs 1`）

現行のランナーは同期処理でテストを待つため、親に `SIGINT`・`SIGTERM` を送ってもシグナルのハンドラが動かず、
中断できないまま全件を流し切ることがあります。Ctrl-C も中断を保証しません。
`pnpm check:fast` の変異の段（`--changed`）もこの形です。待てる場合は完走を待ちます。

待てず強制停止する場合は、**起動時に `setsid` などでほかの作業から分離した専用プロセスグループだけ**を対象にします。
`ps` の PID・PPID・PGID とコマンドを照合し、シェルや別の検査・人のプロセスが同じグループにいないことを確かめます。
分離できていないグループに下のコマンドを使わないでください。

```bash
kill -KILL -- -<自分の変異検査専用の PGID>
```

`SIGKILL` では終了の処理が動きません。親だけを殺すと子が残るため、専用グループ全体を止めます。
適用中なら変異・復旧用のマーカー（`.applied`）・ロック（`.lock`）が残るので、下の「停止後の確認と復旧」へ進みます。

### 並列実行（`--jobs 2` 以上）

全体を起動した親の Node プロセスに `SIGINT` か `SIGTERM` を送ります。親は子へも終了を伝え、終了時に
並列用の作業ツリーを片付けます。親だけでなく子の終了も `ps` で確認してから、停止後の確認へ進みます。

```bash
kill -TERM <mutation-check 全体を起動した親の PID>
```

### 停止後の確認と復旧

実行前の変更はコミットしておきます。停止後、親と子の終了を確認してから次を実行します。

```bash
git status --porcelain
ls scripts/mutations/.lock scripts/mutations/.applied
```

- `git status --porcelain` の出力が空か確かめます。出力が残っていたら、そのままコミット・push せず、
  `git diff` と実行のログで変異とほかの変更を区別します。一括の `git reset --hard` や `git checkout -- .` で戻しません
- `.lock` と `.applied` は無視対象なので、`git status` が空でも存在することがあります。
  `ls` の「そのようなファイルやディレクトリはありません」は、そのファイルが残っていないことを表します
- 残っていたら、前の親と子が終了したことを確認して、同じ変異検査のコマンドを起動し直します。
  ランナーは死んだ PID のロックを引き取り、`.applied` に記録されたファイルを復元します。
  ロックやマーカーは手で消しません。再実行は復旧だけでなく検査も行うので、最後まで待ちます
- 復旧後にも、作業ツリーが空で、`.lock`・`.applied` が残っていないことを上の 2 コマンドで確かめます。
  復元するファイルが無いときは復元のログが出ないので、ログが出るまで待つ手順にはしません。
  並列用の作業ツリーが残った場合は、次の並列実行の起動時に、死んだ親のものをランナーが片付けます

復元に失敗したらログと差分を残します。中断して流し切れなかった範囲と理由は、
復元できた場合も「確かめられなかったこと」に書きます（`docs/adr/0030` 決定 4）。

## 作り直す

周りのコードを変えると、パッチの文脈（直前・直後の行）が合わなくなり、`git apply` が失敗します。そうなった変異は
**結果の表に「未検出」として現れないまま死にます**（検査ごと異常終了するため）。`scripts/mutation-check.test.mjs` の
「宣言した変異が当たること」が `git apply --check` で全件を見て、落ちたものを名指しします。

```bash
git apply --check scripts/mutations/m<ID>-*.patch
```

1. 宣言の `label` と古いパッチを読み、**何をどう壊していたか**を確かめる
2. いまのコードで、**同じ壊し方**を手で再現する（壊す場所が移っていれば、移った先で）
3. 「足す」の手順 3 のとおり、`git diff` で同じファイル名のパッチを上書きし、戻し、`git apply --check` で確かめる
4. `node scripts/mutation-check.mjs --id <ID>` で検出されることを確かめる

- **変異そのものは変えない。** `label`（壊し方）は同じまま、パッチの文脈だけを合わせる
- 守っていたテストが別のファイルへ移った・対象が別のパッケージへ移ったときは、`pkg`・`tests` を直し、`note` に理由を足す
- 作り直した変異の番号は、PR 本文の「変更内容」に書く（例: 「m608・m612 を作り直し」）

## 消す

**変異は原則として消しません。** 消してよいのは、守っていた性質が**概念ごと無くなった**とき（例: 役割とホストを廃止して、
権限の確認そのものが消えた）と、等価な変異だと分かったときだけです。

- 消すのは検査を弱める変更に当たるので、**人の承認を得てから**消す（`AGENTS.md`「AI 運用規則」・`docs/adr/0030` 決定 1）
- 宣言を消した場所に、消した理由と番号をコメントで残す。**番号は詰めない**（`MUTATIONS` の id 2・5・48 のコメントが例）
- パッチのファイルも消す（宣言とパッチは 1 対 1）

## 重い組の実測の表（#546・#550。ランナーごとの既定値も同じ手順）

変異をシャード（`--shard`）・ワーカー（`--jobs`）へ分けるときの重さは、2 つの値で決まります。どちらも **CI の実測の秒数**に合わせて持ちます
（手元の値で決めない。2026-11-05 の測り直しでは、手元の値の見積もりは、bun は組ごとの実測 ÷ 見積もりの中央値が 0.12（約 8 倍の過大）でも合計はほぼ合い、node は合計が約 0.6 倍の過小だった）。

- **ランナーごとの既定値**（`scripts/lib/mutation-weights.mjs` の `RUNNER_COST_SECONDS`。対照 1 回と検出 1 回の秒数。vitest 3/2.7・bun 0.6/1.7・node 1/0.6）。
  表に無い組はこれで見積もります
- **重い組の表**（`scripts/lib/mutation-weights.mjs` の `MEASURED_GROUPS`。行は `pkg`・`tests`・`control`・`mutation`。鍵は対照の組の鍵 `controlGroupKey` と同じで、表の下で作る）。
  組（`pkg` と `tests` の並びが同じ変異の束。対照実行を使い回す単位）によって 1 回 0.1 秒から 60 秒まで開くので、**重い組だけ**を実測で載せます。
  `weightOfGroup` が表を優先し、`isHeavyGroup` が表の行を重い組の印にします（軽い組まで持つと、テストを足すたびに腐るため）

分け方（`scripts/lib/mutation-partition.mjs`）は、**表に載った組**を重い印として、置き場を問わず
重い順に「いま最も軽い分け前」へ入れ（LPT）、残りの軽い組を置き場ごとに散らします（見積もりだけが大きい組は印にしません。
実測では軽いことがあるため）。散らすときは、重い組で埋まった分け前に
少なく配ります（重い組の分け前にも軽い組が 1/n ずつ入ると、最も長い分け前が短くならない）。

### 測り方（既定値も表も、同じ手順）

1. **run を選ぶ。** main の CI の run を、離れた 2 つ以上（できれば 5 つほど。同じ組でも run ごとに最大 2 倍揺れる）。`mutation (1)〜(3)` が全部あるもの
   （文書だけの変更の run は変異を流さない）。`gh api "repos/<owner>/<repo>/actions/runs?branch=main&event=push"` で一覧できる
2. **ログを取る。** run ごとに `mutation (k)` の job の id を引き、ログを保存する。
   ```bash
   gh api repos/<owner>/<repo>/actions/runs/<run>/jobs --jq '.jobs[] | select(.name | test("^mutation \\(")) | "\(.id) \(.name)"'
   gh api repos/<owner>/<repo>/actions/jobs/<job id>/logs > <run>-<k>.log
   ```
3. **数える。** 1 つの run のログ 3 つを `,` でつなぎ、run ごとに引数に並べる。
   ```bash
   node scripts/measure-mutation-costs.mjs a-1.log,a-2.log,a-3.log b-1.log,b-2.log,b-3.log
   ```
   `scripts/measure-mutation-costs.mjs` は、ワーカー（`[w番号]`）ごとに `--- 変異 #n` の行 → `対照:` の行 → `検出:` の行の時刻の差から、
   対照（`使い回し` でないもの。「変異」の行から「対照:」の行まで）と検出（「対照:」の行から「検出:」の行まで）の秒数を組ごとに数え、
   run をまたいで平均する。出すもの: ランナーごとの実測と、いまの既定値との差（実測 ÷ 見積もり）・組ごとの実測と、いまの重さとの比（run ごとの値も並ぶ）・
   **案**（既定値と表の行）。**いまの宣言に無い組**（消した・並びを変えた組）は数えない。テストは `scripts/measure-mutation-costs.test.mjs`
4. **既定値は「合計を合わせる平均」で決める。** 表の行を除いた組について、ランナーごとに、対照 = 組ごとの対照の平均・検出 = 検出の合計 ÷ 変異の件数（0.1 秒単位）。
   中央値にしないのは、分け方が均すのがワーカー・シャードごとの**合計**で、分布の裾が長い（少数の組が桁違いに重い）ため。中央値だと表に無い組の合計が
   何倍も過小になる（bun は実測 185 秒に 24 秒・node は 138 秒に 56 秒）。直した値は 188 秒・132 秒・vitest 1516 秒に 1499 秒で合う。
   **直した後は、ランナーごとの「表に無い組の実測の合計と見積もりの合計」が合うこと**を出力で確かめ、JSDoc（`RUNNER_COST_SECONDS`）に前後を書く
5. **表の行は「載せる目安」で決める。** 変異のある組で、組の合計（対照 1 回＋検出 1 回 × 件数）が約 30 秒以上、かつ**実測が既定値の見積もりの 2 倍以上**、かつ対照 1 回＋検出 1 回が `HEAVY_RUN_SECONDS`（7 秒。自己テストが行ごとに見る下限）以上。道具もこの下限を知っているので、案をそのまま写せる。
   値は run の平均を半秒単位に丸める。目安に当たらなくなった行は消す。**変異の無い組は載せない**（原則 X）。
   重いテストを指す変異を足すときに、その run の CI のログで測って足す（例: `scripts/wiring-audit-structure-sc039.test.mjs` は約 60 秒と #544 で測られているが、いま指す変異が無いので載せていない）。
   案は、表の行と既定値が互いに依るので、変わらなくなるまで繰り返した結果が出る
6. **効果を確かめてから直す。** `--simulate` は、各 run の変異の集合を `--shard k/3`・`--jobs 4` で分けたときの各ワーカーの実測の秒数
   （シャードの最長・ワーカー全体の最長と最短・差）を、**基準の重み**と**測り直した案の重み**で並べる（`--shards`・`--jobs` で形を変えられる）。
   案を測った run そのものでは良く見えすぎるので、`--leave-one-out`（他の run から測った案で残した run を分ける）も見る。
   「基準」は既定ではいまのコードの重みで、直した後は直す前の値を再現できないので、`--baseline <json>` で明示できる（下の「直す前」の JSON）。
   run ごとの揺れが大きく（同じ組が 2 倍違う）、割れない大きな組（test-shuffled は 1 組で約 4 分）が最長を決めるので、
   差は run ごとに数十秒動く。**「縮む」と言い切らず、run ごとの数字と、悪化した run を書く。** 2026-11-05 の 5 run（最長/差、秒）:

   | run（commit） | 直す前 | 案（同じ run） | 他の 4 run の案 |
   |---|---|---|---|
   | 42040543527（f48d2f9） | 285/127 | 276/108 | 272/100 |
   | 42038371106（e802805） | 333/193 | 306/149 | 306/151 |
   | 42027659444（f94c52b） | 257/119 | 226/74 | 224/79 |
   | 41981719850（4cdca8c） | 217/66 | 214/62 | **245/96（悪化）** |
