# ADR-0002: 文書体系の三層構造

- **ステータス**: Accepted（2026-08-09）
- **関連**: [#68](https://github.com/tomohiroJin/tasuki-tools/issues/68)（規範とアーキテクチャの確立、
  親 epic [#67](https://github.com/tomohiroJin/tasuki-tools/issues/67)）/
  [#78](https://github.com/tomohiroJin/tasuki-tools/issues/78)（ADR 0001、横断 ADR の先行新設）/
  `docs/adr/README.md`（採番規約の申し送り元）/
  `docs/timer/adr/0010-design-doc-source.md`（本 ADR が置換する宣言）

## 背景

Tasuki には判断の拠りどころが揃っていない。ADR は timer の 10 件
（`docs/timer/adr/0001`〜`0010`）と横断の 1 件（`docs/adr/0001`、#78 で先行新設）に
分かれており、どちらを見ればよいかは `docs/adr/README.md` の申し送りでしか分からない。
同ファイルは #78 の時点で自ら次のように申し送っている。

> ADR のテンプレートと採番規約の統一は #68 の宿題です。

規範文書 `docs/constitution.md` にも、現状と矛盾する条項が残っている。
`constitution.md:97` には「既存の timer（`packages/timer-core` / `apps/timer-*`）には
手を入れない（MUST NOT）」という条項が実在するが、これは #78 で timer 側のデザインを
作り直した現状と矛盾する。

設計文書（spec / plan）の置き場も、宣言と実態が乖離している。timer ADR 0010
（`docs/timer/adr/0010-design-doc-source.md`）は「正本は `docs/plans/`、
`docs/superpowers/` は移行前の履歴アーカイブ」と宣言し、`docs/superpowers/` 側は
「以降更新されていない」と述べている。しかし #73 の E2E 設計
（`docs/superpowers/specs/2026-08-07-e2e-foundation-design.md`、main に収録済み）や、
本 Issue #68 自身のスペック（`docs/superpowers/specs/2026-08-09-governance-and-docs-design.md`、
PR #99）も `docs/superpowers/specs/` に新規作成しており、この前提はもう事実でない。
`docs/superpowers/` への新規作成は現に続いている。

`docs/` 全体も `plans/` `superpowers/` `adr/` `experiments/` 等が混在し、どれが
現行の正本か文書構造だけからは読み取れない状態にある。

## 決定

### 1. 三層構造を採る

文書を変更頻度で 3 つの層に分ける。

| 層 | 役割 | 変更の重さ |
|---|---|---|
| **憲法**（`docs/constitution.md`） | 「何を守るか」の宣言。原則は各数行 | めったに変えない。改版は ADR を伴う |
| **ADR**（`docs/adr/` ほか） | 「なぜそう決めたか」の不変の記録 | 追記のみ。覆すときは Superseded（**本文の事実訂正は改定節つきで可**。下の「追記（2026-09-09・#258）」を併せて読むこと） |
| **ガイド**（`docs/guides/`） | 「今日どう書くか」の手引き | 育ち続ける。ADR の改版なしに更新してよい |

> 改定: 採択しなかった ADR の扱いは 追記（2026-11-07・#561）

### 2. 書き分けの規則

- **決定の中身と根拠は ADR に書く。手順・例・チェックリストはガイドに書く。**
- 両方に跨る内容は、片方に書き、もう片方からは参照する。**二重正本を作らない。**
- ガイドの中身（例: DoD の項目）は ADR の改版なしに育ててよい。**「DoD を運用する」という
  決定自体**を覆すときだけ ADR を書く。DoD の項目の追加・削除自体はガイドの更新のみで行う。

### 3. 採番規約

- 横断的な判断は `docs/adr/` に置き、`0001` からの連番で採番する。
- アプリ固有の判断は `docs/<app>/adr/`（例: `docs/timer/adr/`）に置き、置き場ごとに
  独立して採番する。
- 参照するときは必ず置き場つきで書く（例: `docs/adr/0005`）。置き場を省いた
  「ADR 5」のような参照は行わない。

これは `docs/adr/README.md` が #78 の時点ですでに実践していた規約の追認である。
同ファイルの「ADR のテンプレートと採番規約の統一は #68 の宿題」という申し送りを、
本 ADR とテンプレート（`docs/adr/template.md`）の追加で解消する。

### 4. 設計文書（spec / plan）の置き場

新規の機能設計文書（spec / plan）は `docs/superpowers/` に日付つきのファイル名
（例: `2026-08-09-<topic>.md`）で置く。これは現行のスキル運用（`superpowers:*`）の
出力先を追認するものであり、新しい規則を課すものではない。

`docs/plans/`（`spec-plan-tasks` スキルによる SDD: Specification-Driven Development の
成果物一式）は、今後は SDD 期の記録として扱う。新規の設計文書をここへ追加することは
規定しない。

**本 ADR は timer ADR 0010（`docs/timer/adr/0010-design-doc-source.md`）の
全体向け宣言を置換する。** 0010 は「正本は `docs/plans/`」と全体に向けて宣言していたが、
これは横断 ADR の置き場がまだ無かった時期に、アプリ固有の置き場（`docs/timer/adr/`）で
書かれた宣言であり、背景で述べたとおり現行運用（`docs/superpowers/` への新規作成が
続いている実態）と乖離していた。横断 ADR の置き場ができた今、本 0002 がその宣言の
後継となる。**0010 の本文は削除しない。**先頭に本 ADR への昇格注記を足すのみとする
（注記の追加は本 ADR の後続タスクで行う）。

### 5. 憲法改版時のチェック項目

憲法（`docs/constitution.md`）を改版する際のチェック項目に、
**AGENTS.md の憲法見出しの同期確認**を含めることを MUST とする。AGENTS.md は
憲法の見出しのみを転記した薄い複製を持つ設計であるため、憲法側の見出しが変わった
ときにドリフトしないよう、改版のたびに両者を突き合わせる。

## 影響

- 既存の `docs/plans/` `docs/superpowers/` `docs/poker/` `docs/timer/experiments/` は
  **移動しない**（物理的な整理は #71 の領分）。本 ADR は位置づけの宣言に留める。
- アプリケーションコード（`apps/` `packages/` `e2e/` `scripts/`）への変更は無い。
- timer ADR 0010 は本 ADR（0002）へ置換されるが、本文に昇格注記を足す作業自体は
  #68 の後続タスクで行う。timer ADR 0006・0009 も同様に横断 ADR（0005・0006、
  #68 の後続タスクで新設）へ昇格する予定だが、その内容・注記の追加は本 ADR の対象外。
- `docs/README.md`（文書地図）は、本 ADR が定めた三層構造と置き場の宣言を踏まえて
  新設する（#68 の別タスク）。

## この ADR で決めないこと

- ADR 0003〜0007 の内容そのもの（アジャイル運用の形式化・同期サーバーのポート/アダプタ
  構成・境界の型安全・テスト規約・抽象の導入基準）→ #68 の後続タスク（PR-3）
- 憲法本体の書き直し → #68 の後続タスク（PR-2）
- `docs/plans/` `docs/superpowers/` の物理的な整理・統合 → #71

## 追記（2026-08-16・#71）

### 憲法の正本を `docs/constitution.md` へ移した

決定 1 の三層表・背景・決定 5 のパス表記は更新済み。**三層構造そのもの、書き分けの規則、
採番規約、改版時の AGENTS.md 見出し同期の MUST は変えていない。**

**2026-08-16 以前の文書は憲法を `.specify/memory/constitution.md` として参照している。**
これは当時の正本のパスであり、記録として正しい。**現在の正本は `docs/constitution.md`。**
休眠文書（`docs/superpowers/` `docs/retrospectives/` ほか）のバッククォート表記は
リンク検査の対象外であり、意図的に当時のまま残している（25 箇所）。

### 設計文書の追記規約（決定 4 の運用を明文化する）

決定 4 は置き場を定めたが、**完了した文書をどう扱うか**を宣言していなかった。#71 で
明文化する。

- `docs/plans/` は SDD 期の記録一式、`docs/superpowers/` は現行の設計文書
- **どちらも追記のみ。完了しても移動しない。ディレクトリ名も当時のまま改名しない**
- `docs/plans/archive/` は実装前の最終設計書の置き場（1 本）。隣接する spec / plan / tasks とは
  種類が違うため分かれている。廃止しない

理由: 記録の所在が動くと、そこを指す過去の文書が一斉に壊れる。実際 #71 で
`docs/plans/archive/` の廃止を検討した際、`docs/adr/0011` のリンクのほか、**リンク検査が
捕まえない**休眠文書からのバッククォート参照 2 系統が壊れることが分かったため撤回した。

> 改定: 節の単位の扱いは 追記（2026-11-03・#506）

## 追記（2026-09-09・#258）

### ADR の改版作法 —— 本文の事実訂正は「改定節つき」で許す

決定 1 の表は ADR を「追記のみ。覆すときは Superseded」と定めているが、
[#95](https://github.com/tomohiroJin/tasuki-tools/issues/95) S3
（[#244](https://github.com/tomohiroJin/tasuki-tools/issues/244)）の作業の中で**作法が 2 通りに割れた**。

**起票時（#258）は「2 通りに割れた」と書かれていたが、実測すると 3 通りだった。**

| ADR | S3 での扱い |
|---|---|
| [`docs/adr/0015`](./0015-web-layer-structure.md) | 古い表を残し、**追記だけ**を足した |
| [`docs/timer/adr/0007`](../timer/adr/0007-volatile-in-memory-state.md) | **改定節**を付けたうえで、決定の本文を直接書き換えた |
| [`docs/timer/adr/0008`](../timer/adr/0008-server-resident-ai-generation.md) | 本文を書き換え、**丸括弧で当初の文面を本文内に残した**。ただし追記の末尾は「追記のみ」と自称しており、実体と食い違っていた（#258 で訂正を足した） |

**後者を正とする。** 次のように読み分ける（**MUST**）。

- **決定そのものを覆す**ときは、従来どおり Superseded を立てる。本文は書き換えない
- **決定は変えず、本文が記述している現況が事実でなくなった**ときは、
  **改定節（`**改定（日付・Issue 番号）**`）で差分を明記したうえで、本文の該当箇所を直してよい**
- **当時の観測・引用・根拠として書かれた記述は書き換えない**（追記のみ）。
  日付つきの追記が引用している文面は、その追記が書かれた時点の記録だからである

理由は 2 つある。

1. **本文が現況を語る ADR で、追記のみを貫くと本文が嘘をつく。** `docs/timer/adr/0007` の本文は
   「主催者が猶予 30 秒を超えて不在なら最古のオンライン編集者へ自動委譲する」と書いていた。
   委譲する対象そのものが無くなった以上、この文は決定の記録ではなく**誤った現況の説明**になる。
   読んだ人が実装を探して見つからない、という壊れ方をする
2. **どちらが正かを決めないと、次の作業でまた割れる。** 割れたまま置くと、同じ ADR の
   隣り合う節が別の作法で書かれ、読み手は「なぜここだけ違うのか」を毎回考えることになる

**S3 の 3 本とも、本文を書き戻す必要は無い。**

- `docs/adr/0015` が残したのは「背景の表が挙げる純粋ロジック 9 本」という**当時の実測**であり、
  上の 3 つ目（書き換えない）にそのまま当たる
- `docs/timer/adr/0007` は改定節つきの本文訂正であり、上の 2 つ目に当たる
- `docs/timer/adr/0008` も本文訂正だが、**当初の文面を丸括弧で本文内に残す形**を採った。
  これは上の 2 つ目の一変種であり禁じない（旧文面が本文から読める分だけ親切である）。
  ただし**同じ追記が「追記のみ」と自称していたのは誤り**なので、#258 で訂正を足した

割れていたのは規範の側だけだった。

**この追記自体が新しい作法の実例である。** 決定 1 の三層表の ADR 行に「本文の事実訂正は
改定節つきで可」を書き足した —— 表だけを読んだ人が古い規範のまま作業するのを防ぐためで、
決定 1 そのもの（三層に分ける）は変えていない。

## 追記（2026-11-03・#506）

### 設計文書の「追記のみ」を節の単位で定める —— 古い節は書き換えず、改定の印を求める

追記（2026-08-16・#71）は設計文書（`docs/superpowers/` の spec / plan）を「追記のみ」とした。
だが**何の単位で追記のみか**を定めていなかったため、文書ごとの冒頭や補遺（例: checkin の設計の §12 の冒頭）にしか
決まりが無く、離れた節を読んだ AI が古い節を書き換えた（#491 の試し。振り返り
`docs/retrospectives/2026-11-02-issue-491-two-place-trial.md` の罠 2）。一般の決まりとして次のように定める。
**#71 の追記の「追記のみ」を節の単位まで下ろす。そのとき、意味を変えない直し（誤字・壊れたリンク・`- [x]` の印付け）と古い節の末尾の改定の印だけは書き足してよいと広げる。**
#71 の行は、この追記の側に印を足して指す（本文は変えない）。

- **決定した節**とは、その文書が main にマージされた時点で存在する節である。マージ前の自分のブランチでは自由に直してよい
- 決定した節の**本文は書き換えない**。実装で外れた箇所・実装に任せた箇所・見直した決定は、**文書の末尾に足した節**
  （補遺・改定の節）に、どの節をどう置き換えるかを名指しして書く
- 本文に手を入れてよいのは、**意味を変えない直し**だけである: 誤字、壊れたリンクの修正、実装計画の `- [x]` の印付けと進み具合の追記
- **改定の印を求める。** 古い節を置き換える新しい節を足したら、置き換えられる古い節の末尾に
  `> 改定: §N（日付・#Issue）` の 1 行を足す。この 1 行だけは古い節への書き足しとして許す。
  理由: 古い節だけを読む人は文書の末尾を見ない。古い節の側に印が無いと、置き換わったことも決まりも目に入らない。
  既存の文書へは遡らない
- 日付つきの記録（振り返り・追記）の中の引用は、書かれた時点の記録として書き換えない

**追記（2026-09-09・#258）の作法 —— 改定節つきで本文の事実訂正を許す —— は、設計文書には採らない。**
ADR の本文は、いま有効な決定として読まれる規範なので、現況と食い違えば嘘をつく。だから改定節つきで直してよい。
設計文書は決定当時の考えの記録であり、現況を語るのは ADR・ガイド・コードである。記録を直すと、後から
「なぜそう考えたか」を辿れなくなるため、直さずに新しい節で置き換える。

**決定 2 の書き分けに従い、手順・雛形・例はガイド `docs/guides/design-doc-revision.md` が持つ。** 機械で守れる部分は
`scripts/audit-plan-gate.mjs` が見る（境界日以降の設計文書に、冒頭の宣言があること）。守れない部分（節が書き換えられたか、
改定の印が要るか）を検査にしない理由は、ガイドの「機械で守れるか」に書いた（`docs/adr/0030` 決定 2）。

## 追記（2026-11-07・#561）

### 採択しなかった ADR は `Rejected` にし、本文を案の記録として残す

決定 1 は ADR を「追記のみ。覆すときは Superseded」と定めたが、**Proposed のまま採択しなかった ADR の扱い**を決めていなかった。
雛形（`docs/adr/template.md`）のステータスの値も Proposed・Accepted・Superseded の 3 つだけだった。
[ADR-0034](./0034-scheduled-mutation-survey.md) を利用者が却下したとき（#561）、Proposed のままでは「まだ決めていない」のか「採らなかった」のかが
読めないため、その ADR だけ `Rejected` と書いた。同じことは今後も起こるので、一般の決まりとして次のように定める（**MUST**）。

- **人が採択しないと決めた Proposed の ADR は、ステータスを `Rejected（日付・誰がどこで判断したか）` にする。**
  却下も採択と同じく人が判断する（`docs/adr/0030` 決定 1）
- **ADR は消さず、起草した時点の案（「背景」以降）は書き換えない。** 案の記録として残す。ステータスの直後に
  **「却下の理由」の節**を足し、なぜ採らなかったか・残したもの（案が拾おうとした穴をどう扱うか）・決め直す条件を書く。
  ステータスと「却下の理由」の節は、却下の後の現況を語るので、追記（2026-09-09・#258）の作法（改定節つき）で直してよい
- **一覧（その置き場の `README.md`）のステータスも `Rejected` にする。** 番号はその ADR に割り当てたまま残し、ほかに使わない
- 却下した案を後で採り直すときは、**新しい ADR を起こす**（却下した ADR を Accepted に戻さない）。新しい ADR は却下した ADR を下敷きにしてよく、関連にその番号を書く。
  却下した ADR の側には、ステータスの後ろに `採り直し: NNNN` を書き足す（Superseded の `by NNNN` と同じく、古い側から新しい側を辿れるようにする）
- **Superseded との違い**: Superseded は採択した決定を別の決定で置き換えるときに使う。Rejected は、一度も採択されなかった案に使う

理由: 却下した案を消すと、同じ案が後でまた起草されたとき、なぜ前に採らなかったかを辿れない。
Proposed のまま残すと、決まっていない案と採らなかった案が見分けられない。

値の一覧は雛形（`docs/adr/template.md`）が持つ。この追記に合わせて `Rejected` を足した。
