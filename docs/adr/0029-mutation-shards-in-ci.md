# ADR-0029: 変異検査は全件のまま、ジョブと作業ツリーの 2 段に分けて並行に流す

- **ステータス**: Accepted（2026-10-31）
- **関連**: [#481](https://github.com/tomohiroJin/tasuki-tools/issues/481) /
  [ADR-0009](./0009-ci-scope-and-checks.md)（CI が守る範囲と検査の配置） /
  [ADR-0014](./0014-scan-target-integrity.md)（走査対象の健全性） /
  設計正本 [`2026-10-31-ci-wait-design.md`](../superpowers/specs/2026-10-31-ci-wait-design.md)

## 背景

PR に push してから CI が緑になるまで 15〜23 分かかり、開発に支障が出ていた（2026-10-31 の利用者のフィードバック）。
4 つのジョブは並行に走るので、いちばん長い `quality` が全体を決めていた。その `quality` の 8 割以上が
変異検査（`node scripts/mutation-check.mjs`。440 件・13〜19 分）だった。変異は機能を足すたびに増え、
2026-10-14 の 153 件から 17 日で約 2.9 倍になっていた。実測と内訳は設計正本 §2。

変異検査は 1 つの作業ツリーの上で「当てる → 流す → `git checkout --` で戻す」を繰り返す。同じ作業ツリーで
2 つを同時に流すと互いの復元が潰し合い、変異が当たったまま残る（2026-09-08 に起きた）。そのため
同じ作業ツリーではロックで拒んでおり、**1 つの作業ツリーの中では直列にしか流せない。**

#387（設計正本 [`2026-10-14-test-weight-design.md`](../superpowers/specs/2026-10-14-test-weight-design.md)）では
手元の待ちだけを縮め、「CI は全件のまま安全網として残す」と決めていた。今回はその決まりを守ったまま CI の待ちを縮める。

## 決定

### 1. 変異は全件を、PR でも main でも毎回流す（変えない）

- **MUST**: CI は変異の全件を、PR への push と main への push のたびに流す
- **MUST NOT**: CI で差分による絞り込み（`--changed`）をしない。速さのために検査の強さ（全件を流す機会）を落とさない
- 理由: #387 で利用者が選んだ「CI は全件」を守る。差分で絞ると、選び方の正しさが品質の要になり、
  全件で落ちたことに気づくのが merge の後になる。分けて並行に流せば、強さを落とさずに目標の時間（10 分以内）に届く

### 2. 2 段に分けて並行に流す

1. **ジョブを分ける**（`--shard k/n`）: CI の matrix の行の数だけジョブを起こし、全件を n 個に分けた k 番目をそれぞれが流す
2. **ジョブの中で作業ツリーを分ける**（`--jobs m`）: 各ジョブが HEAD の写しの作業ツリー（`git worktree`）を m 個作り、
   runner のコアで並列に流す

- **MUST**: どちらの段も、分け方は 1 つの純粋関数（`scripts/lib/mutation-partition.mjs`）を使う。
  **n 個の分け前を合わせると全件になり、重ならない**ことを自己テストと変異で固定する
- **MUST**: 対照の組（`pkg` と `tests` が同じ変異）を分けない。#387 の対照実行の使い回しを、分けた先でも効かせるため
- **MUST**: 空の分け前を作らない（0 件の緑にしない）。組の数より多くは分けられない（エラー）。ワーカーの数は組の数で抑える
- **MUST**: 作業ツリーを分けるときも、**ロック・復元・マーカー・未コミット変更の検査は作り直さない。** 各作業ツリーで、
  普段の 1 回の実行（`--id …`）をそのまま子として起こす。本体の作業ツリーには変異を当てない
- **MUST**: `--jobs` は HEAD の写しで流すので、本体に未コミットの変更（宣言の表・パッチの置き場を含む）があれば止める
- 重さ（分け前を偏らせないための目安）はランナーごとの起動の秒数で持つ。**ずれても正しさは崩れない**（偏るだけ）
- 分け方は**置き場（`pkg`）ごとに散らす**。同じランナーでも置き場によって速さが 2〜3 倍違い、全体の重さだけで配ると
  CI のシャードが偏った（設計正本 §8.3）。置き場の名前で速さを決め打ちしない

### 3. CI の形

- **MUST**: `--shard` の番号と数は、matrix の値ではなく `strategy.job-index` と `strategy.job-total` から取る。
  matrix の値を渡すと、`[1, 2, 4]` のような書き間違いで 1 つのシャードが黙って流れなくなる。
  GitHub が数える値なら、matrix の行の数を変えるだけで割り当てが必ず全件を覆う
- **MUST**: 集約のジョブ `mutation-all` を置き、シャードが 1 つでも success でなければ（失敗・取り消し・飛ばし）赤くする。
  必須チェックにするときはこれを指す（シャードの数を変えても名前が変わらない）
- **MUST**: 絞り込み（`ci-scope.mjs` の `code`）はステップ単位の `if` で行う（ADR-0009 D4 のとおり）
- `fail-fast: false`。1 つのシャードが落ちても他を止めず、検出されなかった変異を一度にすべて見る
- 上の 3 つ（呼び出しは 1 か所で `--shard` つき・番号の出どころ・集約の判定）は `scripts/mutation-check.test.mjs` の
  「CI への配線」が ci.yml を読んで見る

### 4. 増やし方

- 変異が増えて遅くなったら、**matrix の行を足す**（スクリプトは変えない）。目安は設計正本 §6
- `--jobs` は runner のコアの数に合わせる。コアの数を超えて増やしても速くならない

### 退けた案

| 案 | 退けた理由 |
|---|---|
| PR は差分だけ、全件は main と夜間 | 決定 1。検査の強さが落ちる |
| ジョブを分けるだけ（作業ツリーは分けない） | 1 ジョブが 1 コアしか使わず、同じ速さに届くのにジョブの数（準備の重複）が 3〜4 倍要る |
| 作業ツリーを分けるだけ（ジョブは分けない） | 伸びしろが runner のコアの数で頭打ちになり、変異が増え続けると追いつけない |
| 1 件あたりを速くする（vitest の起動の使い回し） | 変異のたびにモジュールが読み直されることを自前で保証することになる。強さを落としうる |
| 分け前を前回の所要時間から決める | 記録の置き場が要り、記録が消えたときの振る舞いを別に決めることになる。偏りは所要時間に出るので固定の重さで足りる（原則 X） |

## 影響

- CI の全体時間は、変異検査ではなく `ci`・`e2e` ジョブの長さで決まるようになる（実測は設計正本 §8）
- ジョブが `ci` / `e2e` / `docs` / `quality` / `mutation`（n 本）/ `mutation-all` になる。`quality` は変異検査を持たない
- ジョブの準備（checkout・install・作業ツリー）が n 倍かかる。公開リポジトリなので Actions の分は数えないが、
  非公開に変えるときは見積もり直す
- 手元でも `--jobs` で並列に流せる（全件の待ちが縮む）。`--changed` などの選び方とも組める
- `scripts/lib/` の lib が lib を import するようになったので、`--changed` が全件に倒れる「機構のファイル」の導出を再帰にした
- 新しい変異 620〜627 が、分け方・`--shard` の範囲・ワーカーの数の抑え・残骸の扱い・終了コードの扱い・緑の文言を守る
