# ADR-0014: 検査の走査対象は宣言と実体の照合で決める

- **ステータス**: Accepted（2026-08-16）
- **関連**: [Issue #135](https://github.com/tomohiroJin/tasuki-tools/issues/135) /

## 背景

リポジトリの検査は走査対象をそれぞれの流儀で決めていた。ハードコードの配列、
非再帰のグロブ、実行時に静かに空になる走査。#70 の最終レビューで 4 経路、
その後 #116・#119・#103・#126 から 8 経路の申し送りが入り、うち**同一機序（宣言と
実体がずれても誰も言わない）だったもの 6 件**（①②③④⑧⑪）を本 ADR の対象とした。
**残る 1 件（⑬・`node --test` の対象がハードコードで新設テストが対象に入らない）は
申し送りには無く、#135 の作業そのものが新たに見つけたもの**であり、同じ機序を
持つと判明したため合わせて対象に含めた（計 7 件）。

構造監査が走査対象を失って全指標 PASS の表を出す穴は、#72 が
パッケージを移設した瞬間に踏む。ログ衛生が新設パッケージを見ない穴は、
packages/rate-limit で**一度実際に踏んでいる**（人が気づくまで緑だった）。

## 決定

*本 ADR の決定番号は、設計正本の D 番号と対応しない。*

1. **走査対象は宣言し、実体と全単射で照合する。** 「宣言にあるが実在しない」
   「実在するが宣言に無い」のどちらでも落とす（MUST）。片方向では、
   移設と新設のどちらかが必ず素通りする。
2. **除外には理由を書く**（MUST）。除外に書いた対象が実在しなくなったら落とす。
3. **実体の権威はツール自身。** workspace は `pnpm -r list --depth -1 --json`、
   ファイルは `git ls-files`。`pnpm-workspace.yaml` の手解析も、
   `git ls-files '*package.json'` による代替も禁ずる（MUST NOT）。
   どちらも pnpm の解決規則の自作再実装であり、glob が変われば黙ってずれる。
4. **リンク検査は追跡下の全 `*.md` を全分割する**（MUST）。
   「各エントリが 1 件以上に一致すること」では塞げない。エントリを削除すれば
   照合対象ごと消えるため、対策のつもりで同じ穴を再生産することになる。
5. **走査対象の拡大と存在判定の拡大を混同しない**（MUST NOT）。
   存在判定を未追跡ファイルへ広げると、ローカル緑・CI 赤の食い違いを生む。
6. **走査量を常に出力する**（MUST）。緑のときも「何を何件見たか」を出す。
7. **計測器の健全性は合否を持つ。** ADR-0009 D2 の「構造監査は値を出すだけ」は
   **測定値**についての決定であり、走査対象を失ったまま全指標 PASS の表を
   出すことまでは許していない。測定値は落ちない、計測器は落ちる。
8. **件数の下限を直書きしない**（MUST NOT）。ファイルが減るたびに下限を
   下げるのが赤を消す最短経路になり、対応表から項目を消すのと同じ穴になる。
   **ただし 0 件（空振り）の検出は下限の直書きではなく、必ず落とす**（MUST）。
   対象が 1 件も無い検査は「何も検証していない」状態そのものであり、
   これを見逃すと決定 6 の走査量の出力自体が空欄のまま緑になる。
   **書いてよい下限は「非空（1 件以上）」の判定のみ**であり、`if (n < 2)` の
   ような 2 以上の下限は維持コストが要る閾値として MUST NOT の対象に含む。
   **数えるのは宣言の行数ではなく、決定 6 で出力する走査量そのもの**（MUST）。
   宣言の各要素の中身（走査するディレクトリ名）を空にすれば走査は 0 件になるのに
   宣言の行数は変わらないため、行数を見るガードは「走査 0 件・全指標 PASS」の表を
   素通しにする。走査量に内訳があるなら、**内訳のどれか 1 つでも 0 件なら落とす**。
9. **走査量の算出と実走査を、同じ 1 か所から導出する**（MUST）。
   走査対象かどうかの判定は**述語を 1 本に固定**し、数えるときと読むときで
   書き分けない（MUST NOT）。書き分けると条件が割れ、**ガードが「走査した」と
   数えた集合を実走査が見ない**状態が作れる。実際に、数え上げが `!== null`・
   読み込みが真偽値評価という書き分けのせいで、空文字列を宣言すると
   「166 件走査した」と出しながら実際の走査は 0 件・指標は PASS になった。
   宣言の値の妥当性（空文字列・書き忘れ）も検査する — 1 件だけ対象を失った状態は
   件数のガードでは検知できない。

## 塞げていないこと

**変異検査の対応表を丸ごと空にする（`MUTATIONS = []`）経路は、決定 8 の 0 件ガードで
落ちる。塞げていないのは、対応表の項目と patch ファイルを 1 件以上「対で」消す経路
である。** 全単射の照合は宣言と実体の対応が取れているかしか見ないため、項目と
それに対応する patch を両方消せば、残った対応表は依然として全単射のまま通る。
patch ファイルの削除が diff に現れることをレビューの拠り所とする。**この限界は
既知であり、緑は「対応表が健全である」ことを証明しない。**

`scripts/` は `package.json` を持たないため、`mutation-check` の
`detectRunner` で走者を決められず、共有モジュール自身を変異検査で守れない。

## 影響

**数値の正本は設計正本
[`docs/superpowers/specs/2026-08-16-scan-target-integrity-design.md`](../superpowers/specs/2026-08-16-scan-target-integrity-design.md)
（§3.9・§3.4・§3.5・§3.7・§3.10）に置く。本節は転記せず、起きたことの質だけを書く。**

- 構造監査の走査対象が、宣言と理由つき除外で全パッケージを覆う形へ広がった結果、
  **SC031（前提の段の検証）が「0 件＝PASS」から未達へ変わった。** 走査対象を
  失ったままでは表に出なかった違反が、走査対象を広げたことで可視化されたのであり、
  規範そのものの悪化ではない。他の指標も値が動いたものと動かなかったものがあるが、
  動かなかった指標は新しい走査対象に該当が無かったためであり断線ではない
  （レビューで指標の定義と実体を突き合わせて確認済み）。露出した未達の是正は
  #72 または別 Issue へ送る（本 ADR の範囲外）。
- ログ衛生の走査対象も、宣言と理由つき除外で全パッケージを覆う形へ広がった。
  違反は増えていない。走査していない `.tsx` の件数を出力に明示するようにした
  （射程の判断は別 Issue へ送った）。
- リンク検査の**走査対象**は「追跡下 ∪（未追跡かつ gitignore 対象外）」へ広げた。
  **存在判定は追跡下のみに据え置いた**（決定 5。広げるとローカル緑・CI 赤になる）。
  **全分割の照合**は決定 4 のとおり追跡下の `*.md` に対して行う。`LIVE_DOCS` に
  `SECURITY.md` を追加し（それまで検査対象外だった）、`DORMANT_DOCS` を新設した。
- shellcheck は宣言から `git ls-files` を用いた導出へ変えた。対象本数そのものは
  変わらなかった（移行費用ゼロ）が、宣言だと見えなかった「サブディレクトリに置いた
  `.sh` も対象に入る」ことを、CI 上で意図的に SC2045 を仕込んで実証した（検証後に
  削除済み）。自己テスト（`node --test`）の対象も同様の導出に変え、共有モジュールの
  自己テストが自動で対象に加わることを確認した。
- 決定 6・7 により、これらの走査量は成否によらず出力される。
- **ログ衛生の走査ディレクトリの実在確認は当初入っていなかった**（決定 1 の未達。
  Issue #158 で 2026-08-16 に解消）。宣言から導出した `src` ディレクトリが改名・
  消失しても、全単射照合はパッケージ名しか見ないため素通りし、走査だけが静かに
  空になっていた。実測では 9 パッケージのうち 1 つを失っても「120 → 118 ファイル」と
  減るだけで緑だった。実在確認は決定 10 に従い共有モジュールの 1 関数に置き、
  構造監査とログ衛生の両方がそれを使う。あわせてログ衛生の走査量を、宣言の行数では
  なく**実在確認を通った対象**の件数へ変えた（決定 8 の「数えるのは走査量そのもの」）。

## 追記（2026-08-28・#180）

**SC-039②③ の走査は `packages/timer-core` 1 パッケージに限定されたままだった。**
本 ADR の決定 1・決定 9 は構造監査の走査対象全体には適用されたが、SC-039②③ が使う
2 つの集合（照合先・参照元）を組み立てる関数だけが、パッケージ名を名指しで取り出す
書き方で残っていた。指標は「公開記号 0 件」と報告していたが、それは timer-core に
ついてのみ 0 で、`packages/` 配下の残り 3 つは一度も測られていなかった
（実測: 照合先 14 ファイル・1 パッケージ / 参照元 137 ファイル・3 パッケージ）。

### 決めたこと

**走査を `packages/` 層の全体へ広げる。** 根拠は要求そのものの文言である。
FR-119（設計正本 [`docs/plans/codebase-refactoring/spec.md`](../plans/codebase-refactoring/spec.md)）は
対象を**層の言葉**で定めており（「`packages/` の公開データ（定数・テーブル）は対象である」）、
特定のパッケージ名を 1 つも挙げていない。**要求の射程を広げたのではなく、実装が要求より
狭かったのを直した。** したがって FR 側の文書に追随は要らない。

FR-119 が挙げる実例が timer 由来（`i18n/ja.ts`・`handlers.ts`）である点は、要求が
書かれた当時 `packages/` に timer-core しか無かったことの反映であり、射程の限定ではない。

走査対象は宣言（`SCANNED_PACKAGES`）から導く。**パッケージ名の名指しを別の名指しへ
置き換えない。** 層の判定は述語 1 本（`isPackageLayer`）に固定し（決定 9）、
組み立てた結果は「実際に集合へ入ったパッケージ」を名乗って、宣言から導いた一覧と
全単射で照合する（決定 1）。走査量は照合先・参照元それぞれについて
**パッケージ数とファイル件数の両方**を出す（決定 6）。ファイル件数だけでは
「照合先 14 ファイル」が 1 パッケージ分でしかないことが読み手に伝わらない。

**照合の粒度はファイルとする（決定 1 の適用単位）。** パッケージ単位の名乗りだけでは、
**すでに照合先へ入っているパッケージの中で特定ファイルだけを部分的に除外する**
狭め方を捕まえられない。そのパッケージは他のファイルで寄与し続けるので名乗りは残り、
走査量も 0 件にならず、例外表も腐らない。実測（2026-08-29）では、組み立ての中へ
`packages/poker-core` の `stats.ts` だけを外す 1 行を差し込むと
「照合先 4 パッケージ / 28 ファイル」（正規は 29）で **exit 0** のまま素通りした。
照合先・参照元それぞれについて、宣言から導いた**ファイル集合**と実際に集合へ入った
**ファイル集合**を両方向で照合する（`diffTargets` を粒度だけ変えて再利用する）。

### 広げた結果（実測・2026-08-28）

照合先 4 パッケージ / 29 ファイル、参照元 9 パッケージ / 186 ファイル。
新たに 16 件の公開記号が検出された。うち 3 件（`normalizeClientAddress` /
`DEFAULT_SWEEP_THRESHOLD` / `MAX_SWEEP_THRESHOLD`）は既存の基準
（その公開を失うと検査そのものが弱くなる）に当てはまるので理由つき例外表へ載せた。
**残り 13 件は例外表へ入れず、指標に見えたまま残した。** 「まだ決めていない」は
理由ではなく、例外へ入れると指標が 0 に戻って [Issue #182](https://github.com/tomohiroJin/tasuki-tools/issues/182)
が読むべき信号を消すためである。測定値は落ちない（ADR-0009 D2。実測で exit 0）。
#135 で走査を広げた結果 SC-031 が未達へ変わったときと同じ扱いである（「影響」節を参照）。

### 塞げていないこと（2026-08-29 に実測して書き直し）

**当初この節は「落ちるのは述語の後段の絞り込み（組み立ての中や `main()` での再フィルタ）
だけである」と書いていたが、これは誤りだった。** 後段の絞り込みのうち、パッケージ単位で
丸ごと外す形は落ちるが、**すでに照合先へ入っているパッケージの中で特定ファイルだけを
外す形は落ちなかった**（上記「決めたこと」の実測を参照）。照合の粒度をファイルへ
上げてこの穴を塞いだうえで、残りを実測で確かめ直した内容が以下である。

**落ちる**（いずれも実測で赤・抜けたファイルを名指しする）:

- 組み立ての中でパッケージを丸ごと外す（#180 以前の「timer-core だけ」の形）
- 組み立ての中でパッケージ内の特定ファイルだけを外す（照合先・参照元とも）
- 宣言に無いファイルを集合へ混ぜる（全単射のもう一方の向き）
- `main()` の照合より**手前**で集合から間引く

**落ちない**（すべて実測。共通する形は「宣言側と実体側が同じ上流を通るので揃って
狭まる」か「照合より後段にある」かのどちらか）:

1. **層の述語（`isPackageLayer`）そのものの書き換え。** 宣言側も実体側も同じ述語を
   通る。走査対象の判定を 1 本の述語に固定する（決定 9）ことの裏返しであり、両立しない。
   実測: `packages/` を timer-core と rate-limit の 2 つへ狭めると
   「照合先 2 パッケージ / 19 ファイル」で exit 0。timer-core だけへ狭めると赤になるが、
   それは**例外表 `SC039C_EXCEPTIONS` が rate-limit のファイルを名指ししているため**
   であって、例外表の中身に依存した偶然であり構造的な歯止めではない。
2. **読み込みそのものの書き換え**（走査ディレクトリを読む関数・拾う拡張子）。
   宣言側も実体側も同じ読み込み結果から導くので揃って狭まる。
   実測: 読み込み時に 1 ファイルを落とすと「照合先 28 / 参照元 185」で exit 0。
3. **照合より後段での間引き**（指標を測る側の中）。照合は既に終わっている。
   実測: 指標側で組み立て直した集合から 1 件消すと、走査量の表示すら
   「照合先 29 / 参照元 186」のまま変わらず exit 0。**この中で唯一、数字に痕跡が残らない。**
   ここを守るのは走査範囲の検査ではなく、指標関数自身のテストと `scripts/mutation-check.mjs`
   である（走査範囲の全単射照合で塞げる種類の欠陥ではない）。
4. **宣言の `entry` を別ファイルへ差し替えて到達性を痩せさせる。** 参照元の唯一の
   絞り込みは到達性であり、宣言側も同じ到達性を通る。
   実測: poker-core の `entry` を `index.ts` → `deck.ts` にすると参照元 186 → 179 で exit 0。

1・2・4 の歯止めは、出力する走査量の数字が変わることと、それが 1 行の差分として
diff に現れることの 2 つに限られる。3 にはその歯止めも無い。**緑は「走査範囲が
正しい」ことを証明しない**（原則 VII）。

**SC-035 と SC-039① は広げていない。** どちらも timer の特定の文言テーブル・
特定の既知パターン 1 つを見る指標であり、層へ一般化する意味を持たない。
代わりに、①の値には測った範囲の名札を添えた（`分岐 0（apps/timer-sync の既知パターンのみ）`）。
広げないなら、どこを測った 0 なのかを出す。
