# ADR-0009: CI が守る範囲と検査の配置

- **ステータス**: Accepted（2026-08-12）
- **関連**: [Issue #70](https://github.com/tomohiroJin/tasuki-tools/issues/70) / `.github/workflows/ci.yml`

## 背景

Tasuki は「検査が静かに効かなくなる」失敗を繰り返し踏んできた。CI そのものが
機能していなかった期間（#50）、eslint の対象がアプリ名を固定していたためパッケージの
移設のたびに検査対象から外れて死んだことが 2 回、構造監査が存在しないパスを
走査して全指標 0 のまま PASS 表示を出していたこと（#69 の破壊検証で発覚）。
いずれも「検査はある。しかし対象・実行経路のどちらかが壊れていて、誰も気づけない」
という同型の事故だった。

#70 では、リンク検査（`node scripts/check-links.mjs`）・構造監査
（`node scripts/audit-structure.mjs`）・変異検査（`node scripts/mutation-check.mjs`）・
shellcheck を CI へ載せ、変更内容に応じた絞り込み（`scripts/ci-scope.mjs`）を入れた。
CI のジョブは `ci` の 1 本から `ci` / `quality`（新設）/ `docs`（新設）/ `audit` /
`e2e` の 5 本へ増えた。本 ADR はその過程で下した決定を記録する。

実装作業中、決定そのものではないが決定の一部として残す必要がある事実が 2 つ判明した。

1. `scripts/ci-scope.mjs` の `main()` は判定処理（`changedFiles()` と
   `decideScope()`）だけを `try` で囲み、fail-open するのは「判定の失敗」
   （未知のイベント・`base` が空・`git diff` の失敗・イベント JSON の不正・
   `before` が全 0・差分が空）に限る。仮に `main()` 全体を `try` で囲むと、
   判定スクリプト自体が異常終了したときも「全部走らせる」側に倒れて CI は
   緑のままになり、**絞り込みが死んだこと自体に誰も気づけなくなる。** そのため
   判定スクリプトの異常終了は素通しし、ジョブを赤くする。
2. `scripts/mutation-check.mjs` は、vitest が「No test files found」（exit 1）を
   返した場合を「変異を検出した」（`result.status !== 0`）と誤判定していた。
   対応表（`MUTATIONS`）が指すテストファイルが消えると、変異検査は全件
   「検出」と報告して緑になる。守るべき「検査が静かに効かなくなる」を、
   検査自身が起こしていたことになる。CI へ載せる前提として、実行前に
   対応表のテストファイルの実在を確かめる `assertMutationTestsExist()` を足した。

## 決定

- **D1**: リポジトリが持つ検査はすべて CI で走らせる。手動専用の検査を残さない
  （**MUST**）。
  理由: 「検査が静かに効かなくなる」失敗を繰り返し踏んでいる（#50 の CI 未実行、
  eslint の対象がアプリ名固定で移設のたびに死んだ 2 回、構造監査が存在しないパスを
  走査して全指標 0 で PASS 表示）。手動運用は「実行し忘れる」経路をそのまま残す。

- **D2**: 構造監査（`scripts/audit-structure.mjs`）は値を出すだけとし、合否の
  判定は持たせない。合否は自己テスト（`scripts/audit-structure.test.mjs`）と
  変異検査で取る（**MUST**）。
  但し書き: この形では指標の退行そのものは止まらない。自己テストが守るのは
  「計測器が壊れていないこと」だけである。閾値を設けるかどうかは未達指標
  （SC029=7 / SC030=3 / SC032 の未付与 28 件 / SC039 の公開記号 34 件）の
  解消とセットで判断すべきで、それは #72 の領分とする。

- **D3**: カバレッジは `timer-core` の lines / branches 90% のみを gate とし、
  他パッケージでは測らない（**MUST**）。
  理由: テストランナーが 3 種（vitest 8 / bun test 1 / node --test 1）に分かれ、
  カバレッジの出力形式も閾値の指定方法もランナーごとに異なる。全パッケージを
  横断して統合した見方を作る作業は本決定の範囲外であり、別途必要になる。

- **D4**: ジョブの絞り込みは「常に起動し、ステップ単位の `if` で判定して
  早期成功させる」形（**MUST**）。paths フィルタでジョブそのものを止める形は
  **MUST NOT**。
  理由: paths フィルタでジョブごと止めると、必須チェックに指定した瞬間に
  対象外のパスしか触らない PR が「未報告」のまま永久待ちになる。main は
  現在ブランチ保護が無いが（2026-08-11 に 404 Branch not protected を確認済み）、
  将来かけた時点でこの穴を踏む。
  補足（fail-open の範囲）: `scripts/ci-scope.mjs` の fail-open は「判定の失敗」
  （未知のイベント・base が空・`git diff` の失敗・イベント JSON の不正・`before` が
  全 0・差分が空）だけを拾う。**判定スクリプト自体の異常終了では拾わず、ジョブを
  赤くする。** `main()` 全体を `try` で囲むと、判定スクリプトが壊れても全ジョブが
  走って CI は緑になり、絞り込みが死んでいることに誰も気づけないため。CI 上で
  実証済み: fail-open が働いた実行では `audit` が本体まで実行して 19 秒、通常時は
  早期成功で 7 秒だった。

- **D5**: デプロイは自動化しない。ローカルからの手作業を正とする（**MUST NOT**
  自動デプロイを CI に組み込まない）。
  理由: 再起動で稼働中のルームが全消滅するため、タイミングの判断は利用状況を
  知っている人にしかできない。

- **D6**: shellcheck を導入し、`deploy/**` と `scripts/**` の対象 6 本
  （`deploy/*.sh` / `deploy/lib/*.sh` / `scripts/*.sh`）を CI で走らせる
  （**MUST**）。`.specify/scripts/**` は vendor のため対象外（**MUST NOT**）。
  info は合否の対象にしない（`--severity=warning`）。
  理由: 抑制ディレクティブ（`deploy/deploy.sh:75` / `deploy/lib/common.sh:58`）
  だけが存在し、検査そのものが無かった。抑制だけが残って検査が無いのは
  「検査が静かに効かなくなる」の最終形である。

## 影響

- CI のジョブが `ci` の 1 本から `ci` / `quality`（新設）/ `docs`（新設）/
  `audit` / `e2e` の 5 本へ増える。実測の所要時間は `ci` 121〜133 秒 /
  `e2e` 51〜69 秒 / `quality` 22〜34 秒 / `audit` 7〜10 秒（早期成功時）/
  `docs` 4〜9 秒。`quality` は臨界経路の `ci` に完全に隠れるため、体感の
  待ち時間は増えない。
- コードを変える PR は検査が 4 種（リンク検査・構造監査・変異検査・shellcheck）
  増えるぶん遅くなる。
- 文書だけの PR は `code` フラグが立たず大半のステップが早期成功するため、
  大幅に速くなる。
- `docs/adr/0003` と `docs/adr/0008` の `docs/BACKLOG.md` への言及は、
  リンク検査の例外表（`scripts/check-links.mjs` の `MISSING_PATH_EXCEPTIONS`）で
  扱う。`docs/BACKLOG.md` は不在であることが正しいため、リンクは直さない。
- D4 の fail-open が「判定の失敗」に限定されたことで、判定スクリプト自体が
  壊れた場合は CI が赤くなり気づける形になった。裏を返すと、`scripts/ci-scope.mjs`
  の保守（新しいイベント種別への対応など）を怠ると、絞り込みが機能する PR の
  種類が狭まっていく。変更時は `scripts/ci-scope.test.mjs` で退行を確かめる
  運用とする。
- D1 の「変異検査自身が検査の欠落を隠していた」不具合を塞いだことで、対応表
  （`MUTATIONS`）とテストファイルの実ファイル構成がずれた場合、変異検査は
  「検出」ではなく明示的な失敗（exit 1・対応表の不整合を指す出力）で止まる
  ようになった。これにより、テストファイルの移動・削除を伴うリファクタリングでは
  対応表の追随が必須になる。
