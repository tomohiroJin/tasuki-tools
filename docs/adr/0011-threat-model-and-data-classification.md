## 背景

脅威モデルは archive 配下の設計文書（`docs/plans/archive/tdd-mob-pro-timer-spec-v3.0-final.md`
§7）に S1〜S11 として実在していた。しかし (a) 横断的な決定が個別アプリの archive 文書に
埋もれており見つからない、(b) 実装と食い違ったまま放置されていた。既定 role（S1）は
`viewer` から `editor` へ変わり、Markdown 描画は DOMPurify を使わない設計に変わり（S4）、
サーバーは秘密ゼロの原則を放棄している（S6、`docs/timer/adr/0008`）。

timer 側にはセキュリティを扱う ADR が 2 本ある。`docs/timer/adr/0005`（秘密ゼロ + BYOK）は
`docs/timer/adr/0008`（サーバー常駐 `claude -p` + 合言葉解錠）により Superseded されており、
0008 は 0005 の中心的な原則（秘密ゼロ）を明示的に放棄している。この転換は記録済みだが、
横断の脅威モデルには反映されていなかった。

**本 ADR は新規制定ではない。** archive の脅威モデルを横断 ADR へ昇格し、現在の実装に
合わせて更新するものである。データ分類・脅威モデルの内容の出所は設計正本
`docs/superpowers/specs/2026-08-13-security-norms-design.md` の 3.3 節・3.4 節・3.4.1 節・
3.5 節 D11 である。実測の数値の正本は 2 本に分かれる（**MUST**）:
**レート制限の設定値（容量・補充速度・バースト容量・掃除しきい値など）の正本は
`docs/superpowers/specs/2026-08-14-ip-rate-limit-design.md`（以下「#103 設計正本」）
D2・D4**。この文書は「#103 実装前」の仮定値であった `connId` 単位・10 秒あたり 30 回
のレート制限を #103 が置き換えた後の値を反映していない旧版であり、レート制限の設定値に
関しては正本ではなくなった。**探索空間（ルームコードの総当たりに要する時間）の正本は
引き続き同設計正本 2.3 節**。本 ADR は決定 4 の目標値・前提レートを除き、数値を転記しない。

憲法 原則 XI（秘密と個人情報を持ち込まない）は「新しい入力・保持・出力を足すときは、
本 ADR のデータ分類のどれに当たるかを決めてから実装する」ことを MUST とする。本 ADR は
その参照先を提供する。

## 決定

### 決定1: データは 4 段に分類する

「個人情報かどうか」の 2 値ではルームコードを分類できない（個人情報ではないが漏れては
いけない）。分類は次の 4 段とする（**MUST**）。値の一覧・件数は設計正本 2.2 節を参照する。

| 分類 | 定義 | 該当 | 扱い |
|---|---|---|---|
| **秘密** | 漏れると運営者の資産・アカウントが侵害される | 設計正本 2.2 節の 3 つ | env のみ。コード・argv・ログ・snapshot・エラー・永続化へ出さない。比較は定数時間 |
| **資格情報** | 知っているだけで入室・操作できる | ルームコード / パスフレーズ / `resumeToken` / poker の participant token | ログへ出さない。利用者へは自分の分だけ返す。比較は定数時間 |
| **個人に紐づく** | 個人を識別しうる | 表示名 / IP アドレス／**クライアント鍵**（IP の HMAC 値。#103 で導入） | 揮発のみ。ログへ出さない。保持期間は `docs/adr/0012` 決定 D3 を参照（レート制限器のエントリと生成元接続の長い方まで） |
| **公開可** | 出しても害が無い | 参加者数 / ルーム数 / フェーズ / 経過時間 / エラーコード | 制約なし |

新しい入力・保持・出力を設計するときは、この表のどれに当たるかを最初に決める（**MUST**、
憲法 原則 XI）。どれにも明確に当てはまらない値は、より厳しい分類（秘密に近い側）を仮に
割り当て、疑わしきは厳格運用とする（**MUST**）。

**クライアント鍵（IP の HMAC 値）を「個人に紐づく」に置く理由（#103・2026-08-14）**:
ソルト付きハッシュであり生の IP を逆算できないが、同一の起動プロセス内では同じ正規化 IP が
常に同じ鍵へ写る。したがって値そのものは読めなくても、**同一の送信元由来であることを
相関できる**という性質は生の IP と変わらない。この相関可能性のために「公開可」ではなく
「個人に紐づく」の扱い（ログへ出さない・揮発のみ）を適用する。

**ソルト（クライアント鍵の導出に使う `randomBytes(32)`）の位置づけ（2026-08-15追記・#103
最終レビュー）**: ソルト自体は上記 4 分類のどれにも明確には当てはまらない。

- **秘密ではない**: 漏れても運営者の資産・アカウントは侵害されない。漏洩の影響は
  「同一プロセスの生存期間中に生成されたクライアント鍵を、既知の正規形（IP）と突き合わせて
  逆算しやすくなる」という間接的なものにとどまり、しかもプロセス再起動でソルトごと失効する
- **資格情報ではない**: それ自体で入室・操作はできない
- **個人に紐づくではない**: 値そのものが個人を識別するのではなく、他の値（クライアント鍵）を
  導出するための定数である
- **公開可でもない**: 漏れると「個人に紐づく」に分類したクライアント鍵の非可逆性（生の IP へ
  逆算できない性質）を弱める

このため、ソルトは上記 4 分類（データの分類）とは別に、**「鍵導出材料」として独立に位置づける
（MUST）**。**env 化・永続化しない**（`docs/adr/0012` 決定 D3・**MUST NOT**）。プロセス起動時に
メモリ上でのみ 1 回生成し、再起動をまたいで保持しない。

**直前の MUST（「どれにも明確に当てはまらない値は秘密に近い側へ仮に割り当てる」）と衝突しない
理由**: その MUST を字義どおりソルトへ適用すると env only を仮採用することになるが、これは
`docs/adr/0012` 決定 D3 が明示的に定める「ソルトを env 化・永続化することは MUST NOT」
（プロセスごとに変わることで、再起動をまたいだ相関・辞書攻撃を防ぐ設計上の要）と正面から
衝突する。本 ADR はこの衝突を放置せず、ソルトを「鍵導出材料」という独立の扱いとして本決定で
明示的に位置づけることで、直前の MUST（4 分類のどれにも当たらない値のデフォルト扱い）の
対象から明示的に外す。憲法 原則 XI の「分類『秘密』の値は env のみに置く（MUST）」も、
分類が「秘密」である値を対象とした規定であり、ソルトは上記のとおり「秘密」に分類しないため、
この MUST とも矛盾しない。

### 決定2: 脅威モデルは S1〜S13 とする

archive §7 の S1〜S11 を現行化し、S12・S13 を新設する（**MUST**）。

|---|---|---|

| **S13** | **CI の供給網**（新設） | `permissions: contents: read` の最小宣言と GitHub Actions の SHA ピン（`docs/adr/0010` の trustPolicy の思想を Actions へ拡張する）。実装は `docs/adr/0012` に委ねる |

**S12 でルームコードをマスクしない理由**: ログは journal に残り、貼り付け・転送で
持ち出される。管理面はトークンと bind で意図的に開けた運用者向けの窓であり、ここで
コードを隠すと「特定のルームで何が起きているか」という運用者の問いに答えられなくなる。
露出の相手（bind とトークンで閉じられた運用者のみ）と持続性（journal に残り続けるログとは
異なる）が違うため、規律を分ける。

### 決定3: 表示名は「ログへ出さない」が「配信はする」

分類は保持と出力の規律であって、機能の否定ではない（**MUST**）。表示名は「個人に紐づく」
分類だが、全参加者へ snapshot として配信する設計はそのまま維持する。ログへ出さない
という制約と、参加者間で共有する機能は両立する。

### 決定4: ルームコードのエントロピー下限

下限は「**想定される総当たり速度で全探索に要する時間**」で定義する（**MUST**）。

**目標値**: 全探索に要する時間が **1 年以上**であること。理由は次のとおり。ルームは
アイドル 30 分で回収される揮発設計だが、個々のルームの寿命の短さは脅威の抑止にならない。
ルーム名・slug は繰り返し推測でき、攻撃者は特定のルームの生存に依存せず、緩やかに・
検知されにくい速度で長期間試行を続けられる。1 年は、四半期規模の間欠的な調査キャンペーン
（数週間〜数か月）に対して 1 桁以上の余裕を持たせ、かつ暗号鍵のような非現実的に大きい
基準（2^128 相当）を求めない、現実的だが十分保守的な水準として本 ADR が新たに置く。

**前提レート**:

- **#103 実装前**: **600 回/秒**。設計正本 2.3 節が実測した現行の上限（同時接続上限 200 ×
  接続単位のレート制限 10 秒あたり 30 回。接続単位のため再接続で窓がリセットされる）を
  そのまま用いる。
- **#103 実装後**: **実装済み（2026-08-14）**。IP 単位のレート制限はトークンバケツ
  （容量・補充速度の値の正本は #103 設計正本 D2）であり、持続レートは前倒しの仮定どおり
  **単一 IP あたり 1 回/秒**になった。実装はこれに加えてバースト容量（一斉再接続時に
  正規利用者を締め出さないための設計。値の正本は同節。#103 設計正本 D2・§3.5）を持つが、
  判定は下記「バーストの扱い」のとおりバーストを無視した持続レートで行ってよい。この前提は
  **攻撃者が単一 IP から
  試行する場合のみ有効であり、複数 IP へ分散する攻撃者を防ぐものではない**（下記
  「#103 実装後も…」を参照）。

**バーストの扱い（判定のやり直し）**: 数値を仮定から実装値へ差し替えるだけでなく、
バースト 60 を含めて判定をやり直した。バーストは**最初の 60 回ぶんの前倒し**でしかなく、
全探索という長時間の試行では最終的に持続レートへ償却される（60 回ぶんの時間短縮は、
探索に要する総時間が数分〜数十年の桁である経路のいずれに対しても無視できる大きさである。
根拠となる探索空間は設計正本 2.3 節、#103 実装後の所要時間は
#103 設計正本 §3.3・§3.4 を参照）。**バーストの有無で下表の判定（充足/不足）は変わらない。** バーストは攻撃者に有利な方向（時間を短縮する方向）にしか働かないため、
判定の向きを覆すとすれば「バーストを含めると充足が不足に転じる」経路だけが危ういが、
両経路とも該当しないことを確認した。

**判定**: 探索空間（設計正本 2.3 節）を上記のレートで割った時間を、目標値（1 年 =
31,536,000 秒）と比較する。

**行は「経路と桁数」、列は「前提レート」である。** 桁数を変えると同じ経路でも判定が動くため、
`slug-????` は #144 の前後で行を分けて示す。

| 経路 | #103 実装前のレート（600 回/秒） | #103 実装後のレート（持続 1 回/秒。バースト 60 込みでも結論は不変） |
|---|---|---|
| ルーム名なし | **不足** | **充足** |
| ルーム名あり（`slug-????`）・**#144 実装前の桁数** | **不足** | **不足** |
| ルーム名あり（`slug-????`）・**#144 実装後の桁数（現行）** | **充足** | **充足** |

**改訂（2026-08-30・#144）**: 接尾辞の桁数を伸ばしたことで、`slug-????` はどちらのレートでも
「充足」へ変わった。桁数は本 ADR に書かない（下記「転記しない」の理由がそのまま当てはまる）。
現行の桁数と、そこから算出される所要時間の正本は設計正本 2.3 節である。
**#103 設計正本 §3.4 が置く分散攻撃（1,000 回/秒）に対しても目標を満たす**ことを
#144 で確認した（本決定の目標値は単一 IP の持続レートで定義しているため、分散への充足は
目標の要求を超える余裕であって、決定4 が分散を射程に入れたことを意味しない）。

**探索空間と、そこから算出される所要時間は本 ADR へ転記しない。** 正本は設計正本 2.3 節
であり、ここには判定の結論だけを置く。理由は本決定自身にある — 下記の対応の選択肢には
**接尾辞の桁数を増やす**が含まれており、実施されれば探索空間も所要時間も変わる。転記すると
追随更新を怠った時点で誤った記述になる（`docs/adr/0002` の二重正本の禁止。
`docs/adr/0012` 決定 D2 も同じ理由で桁数を転記していない）。表の `slug-????` は
設計正本 2.3 節が使う**経路の呼び名**であって、桁数の宣言ではない。

**結論**: `slug-????` 経路は、**#144 実装前の桁数では**#103 実装前・実装後のどちらのレートでも
目標値（1 年）を満たしていなかった。**#144 で接尾辞を伸ばして解消済み**（2026-08-30。現行の
桁数ではどちらのレートでも充足する）。**判定の結論は既に出ている。** ルーム名なしの経路は #103 実装後は満たすが、#103 実装前は
満たさない。この結論は前倒しの仮定の時点から変わっていない — **仮定と実装値が一致した
（持続 1 回/秒）ため、判定を実測でやり直しても結論は動かなかった。** 動かなかったことは
「見直さなくてよかった」ことを意味せず、バーストという仮定に無かった要素を含めて
再確認した結果である。

**#103 実装後も、複数 IP へ分散する攻撃者は防げない**（実装済み・2026-08-14）。
単一 IP からの総当たりは 600 分の 1 に落ちるが、総レートは攻撃者が持つ IP 数に
比例する。ルームコードのエントロピー引き上げ（本決定が別 Issue へ送った対応）が
無ければ、S1 は解決しない。

対応の選択肢は「接尾辞の桁数を増やす」「ルーム名つきルームでパスフレーズを必須化する」
「#103 のレート低減に委ねる」のいずれかである。**いずれも利用者から見える振る舞い
（共有 URL・ルームコードの見た目）を変えるため、本 ADR では実装を決定しない。** 実装は
別 Issue を起票して行う。

**実施（2026-08-30・#144）**: 1 つ目の「接尾辞の桁数を増やす」を採った。2 つ目は
合言葉のエントロピー規範（[#145](https://github.com/tomohiroJin/tasuki-tools/issues/145)）が
未定で「目標を満たした」と言う根拠を持てないため、3 つ目は本決定が「レートをどう絞っても
届かない」と判定済みのため採らなかった。桁数の値は設計正本 2.3 節を参照する。

### 決定5: 合言葉のエントロピー下限

`AI_UNLOCK_KEY`（AI 解錠キー）とルームパスフレーズにも、決定4 と同じ方法でエントロピーの
下限を置く（**MUST**）。下限は「**想定される総当たり速度で全探索に要する時間**」で定義し、
**目標値は決定4 と同じ「1 年以上」**とする。

**射程は timer のみ。** poker には合言葉が無い（`packages/poker-core/src/protocol.ts` の
`join-room` は `roomId` / `name` / `token` だけを受け付ける）。

**前提レートは対象ごとに分ける（MUST）。**

| 対象 | 前提レート | 分ける根拠 |
|---|---|---|
| `AI_UNLOCK_KEY` | **1,000 回/秒**（#103 設計正本 §3.4 の分散モデル） | サーバー全体で 1 本・運用者が変えるまで不変・漏れれば全ルームに及ぶ |
| ルームパスフレーズ | **1 回/秒**（単一 IP の持続レート。決定4 と同じ） | 1 ルームだけを守り、アイドル 30 分で消滅する |

決定4 は「ルームの寿命の短さは脅威の抑止にならない」として揮発性を退けたが、**この論法は
ルームコードには成立し、パスフレーズには成立しない。** ルーム名・slug は繰り返し推測できるため
攻撃者は特定ルームの生存に依存しないが、パスフレーズは特定の 1 ルームだけを守るので、
その攻撃は当該ルームの生存に依存する。逆に `AI_UNLOCK_KEY` は決定4 が射程外とした分散攻撃を
前提に置くべき性質（全ルーム共通・長寿命）を持つ。

#### 規範

**`AI_UNLOCK_KEY`（運用者が env で決める）**

- **一様乱数で生成しなければならない**（**MUST**）。人が考えた文字列は、長さから算出される
  エントロピーを持たない。下限は乱数生成を前提としてのみ意味を持つ
- **ASCII の印字可能文字（空白を除く）だけで構成しなければならない**（**MUST**）。
  env ファイル・systemd の `EnvironmentFile=`・シェルの引用規則で曖昧さを生まないため
- **32 文字以上でなければならない**（**MUST**）
- **`MAX_AI_UNLOCK_KEY`（`packages/timer-core`）を超えてはならない**（**MUST**）。
  **上限はプロトコル側の制約**であって総当たりの話ではない。超える鍵は env に設定できてしまうが、
  `ai.unlock` の受信スキーマが長さを弾くため**解錠が永久に失敗する**（実測で確認）。
  **上限の値は本決定へ転記しない。正本は当該定数である**

**ルームパスフレーズ（ホストが会議中に決める）**

- **8 文字以上でなければならない**（**MUST**）
- **ルーム名・チーム名・日付や、`daily` `mob` `sprint` のような slug と同じ語を使っては
  ならない**（**MUST**）。単一 IP 1 回/秒という前提では、持続的な総当たりよりも
  「一発で当てられる語」のほうが現実的な脅威である
- **規則で生成できる並びを使ってはならない**（**MUST**）。同じ文字の繰り返し（`aaaaaaaa`）・
  連番（`12345678`）・キーボード配列は、長さの下限を満たしていても最初の数十回で当たる
- **文字種の下限は置かない。** 会議中に口頭で共有される値であり、文字種を強いると可用性を
  損なう。推測の容易さは、語と並びについての MUST が直接に禁じている

**回転**（**MUST**）—— 鍵の漏洩を疑ったときと、鍵を共有した相手の範囲が変わったときに回転する。
**定期回転は求めない。** 下記の検算のとおり、下限を満たす鍵の全探索には総当たりでは届かない。

#### 下限の根拠

目標（1 年 = 31,536,000 秒）を満たす**最低線**は `AI_UNLOCK_KEY` が 35 bit（英数 6 文字）、
パスフレーズが 25 bit（小文字 6 文字）である。**最低線は採らない。** #144 がルームコードで
目標の 35 倍の余裕を持つ桁数を採ったのと同じ姿勢で、**推奨する生成方法が自然に満たす値**から採る。
最低線を採ると、全ルーム共通・長寿命の秘密が使い捨てのルームコードより薄い余裕になる。

採った値の検算（探索空間 ÷ 前提レート）:

| 対象 | 最悪の構成 | 探索空間 | 全探索に要する時間 |
|---|---|---|---|
| `AI_UNLOCK_KEY` 32 文字 | 16 進（16 種） | 16^32（＝2^128） | 1.08×10^28 年 |
| `AI_UNLOCK_KEY` 32 文字 | 小文字のみ（26 種） | 26^32 | 6.03×10^34 年 |
| パスフレーズ 8 文字 | 数字のみ（10 種） | 10^8 | 3.2 年 |
| パスフレーズ 8 文字 | 小文字のみ（26 種） | 26^8 | 6,622 年 |

**この表は一様乱数を前提とする。** 人が決めるパスフレーズの実効エントロピーはこれを下回るため、
長さの下限は**最低条件であって十分条件ではない**。上の「規則で生成できる並びを使わない」が
その差を埋める役割を負う。`AI_UNLOCK_KEY` は一様乱数生成が MUST なので、この差は生じない。

**バーストは判定に用いない。** 決定4 が確認したとおり、バーストは最初の 60 回の前倒しでしかなく、
全探索という長時間の試行では持続レートへ償却される。

#### 本決定が持つ数値について

本 ADR は「決定 4 の目標値・前提レートを除き、数値を転記しない」と背景節で宣言している。
これは**正本が他所にある数値**を転記しないという意味であり、**本決定が自ら決めた下限と、
その検算は本決定が正本である**。`docs/guides/security.md` はこれを参照し、転記しない。

#### 本決定は機械検査を伴わない

本決定は規範であり、起動時検査などの機械的な強制は置かない。合言葉は運用で守る。

## 影響

- **#103（IP 単位のレート制限）は S1 の主防御であり、実装済みである（2026-08-14）。**
  接続単位のレート制限は再接続で回避できたが、#103 によりこの回避経路は塞がれた。
  ただしこの防御は `X-Forwarded-For` の内容が信頼できることに依存しており、その信頼は
  起動時 fail-closed（`HOST` をループバック限定にし Caddy 経由を強制する）と Caddy と
  ufw の組み合わせが支えている（#103 設計正本 D6）。**複数 IP へ分散する攻撃者への防御は
  なお持たない**（決定4）。
- 提案 #91（timer のお題機能の共通資産化）へ、**AI 子プロセスの権限の明示的な指定**と
  **`language`/`difficulty` の列挙検証**（S3・S6）を送る。設計正本 3.4.1 節が示す
  持ち出し経路（editor 権限での参加 → `config.set` への注入 → `claude -p` の Read 権限で
  秘密ファイルを読む → `problem.request` の応答として全参加者へ配信）はリスクとして
  受容し、実装は本 Issue（#136）では行わない。受容の根拠（解錠しない限り経路が
  存在しないこと・トークンは失効させれば回復できること等）は設計正本 3.4.1 節を参照する。
  この判断は「危険がない」ではなく「窓を運用で閉じられ、失効で回復できる」ことに基づく
  ものであり、AI を常時解錠する運用へ変える、または秘密の種類が増える場合は前提が崩れる
  ため再評価が必要である。
- 決定4により、`slug-????` を含むルームコード生成の実装は下限を満たさないことが
  確定していた。対応（コード生成の変更）は本 ADR の範囲外とし別 Issue で扱い、
  **[#144](https://github.com/tomohiroJin/tasuki-tools/issues/144) で接尾辞を伸ばして解消した**（2026-08-30）。
- 決定1〜3は `docs/adr/0012`（ログ・秘密・開示の取り扱い）とセキュリティガイド
  （docs/guides/security.md、後続タスクで新設）が実装・運用手順を担うための土台になる。

## この ADR で決めないこと

- ログの具体的な扱い（ロガの実装・整形・検査の設計）→ `docs/adr/0012`
- 認証・認可の作り込み（憲法 原則 III の単純運用の範囲を超えるもの）
- 脆弱性検査の方式 → [#69](https://github.com/tomohiroJin/tasuki-tools/issues/69)（`pnpm audit` の CI 化で対応済み）
- ルームコードの生成方式そのものの変更（決定4の判定結果を受けた対応）→ 別 Issue
  （[#144](https://github.com/tomohiroJin/tasuki-tools/issues/144) で対応済み・2026-08-30）
