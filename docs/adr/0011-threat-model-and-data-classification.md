# ADR-0011: 脅威モデルとデータ分類

- **ステータス**: Accepted（2026-08-13）

## 背景

脅威モデルは archive 配下の設計文書（`docs/plans/archive/tdd-mob-pro-timer-spec-v3.0-final.md`
§7）に S1〜S11 として実在していた。しかし (a) 横断的な決定が個別アプリの archive 文書に
埋もれており見つからない、(b) 実装と食い違ったまま放置されていた。既定 role（S1）は
`viewer` から `editor` へ変わり、Markdown 描画は DOMPurify を使わない設計に変わり（S4）、
サーバーは秘密ゼロの原則を放棄している（S6、`docs/timer/adr/0008`）。

timer 側にはセキュリティを扱う ADR が 2 本ある。`docs/timer/adr/0005`（秘密ゼロ + BYOK）は
`docs/timer/adr/0008`（サーバー常駐 `claude -p` + 合言葉解錠）により Superseded されており、
0008 は 0005 の中心的な原則（秘密ゼロ）を明示的に放棄している。この転換は記録済みだが、
横断の脅威モデルには反映されていなかった。

**本 ADR は新規制定ではない。** archive の脅威モデルを横断 ADR へ昇格し、現在の実装に
合わせて更新するものである。データ分類・脅威モデルの内容の出所は設計正本
`docs/superpowers/specs/2026-08-13-security-norms-design.md` の 3.3 節・3.4 節・3.4.1 節・
3.5 節 D11 であり、実測の数値（探索空間・レート制限の設定値など）は同設計正本 2 節を
正本とする。本 ADR は決定 4 の目標値・前提レートを除き、数値を転記しない。

憲法 原則 XI（秘密と個人情報を持ち込まない）は「新しい入力・保持・出力を足すときは、
本 ADR のデータ分類のどれに当たるかを決めてから実装する」ことを MUST とする。本 ADR は
その参照先を提供する。

## 決定

### 決定1: データは 4 段に分類する

「個人情報かどうか」の 2 値ではルームコードを分類できない（個人情報ではないが漏れては
いけない）。分類は次の 4 段とする（**MUST**）。値の一覧・件数は設計正本 2.2 節を参照する。

| 分類 | 定義 | 該当 | 扱い |
|---|---|---|---|
| **秘密** | 漏れると運営者の資産・アカウントが侵害される | 設計正本 2.2 節の 3 つ | env のみ。コード・argv・ログ・snapshot・エラー・永続化へ出さない。比較は定数時間 |
| **資格情報** | 知っているだけで入室・操作できる | ルームコード / パスフレーズ / `resumeToken` / poker の participant token | ログへ出さない。利用者へは自分の分だけ返す。比較は定数時間 |
| **個人に紐づく** | 個人を識別しうる | 表示名 / IP アドレス（#103 で導入） | 揮発のみ。ログへ出さない。IP はハッシュ化して窓の間だけ保持 |
| **公開可** | 出しても害が無い | 参加者数 / ルーム数 / フェーズ / 経過時間 / エラーコード | 制約なし |

新しい入力・保持・出力を設計するときは、この表のどれに当たるかを最初に決める（**MUST**、
憲法 原則 XI）。どれにも明確に当てはまらない値は、より厳しい分類（秘密に近い側）を仮に
割り当て、疑わしきは厳格運用とする（**MUST**）。

### 決定2: 脅威モデルは S1〜S13 とする

archive §7 の S1〜S11 を現行化し、S12・S13 を新設する（**MUST**）。

| # | 脅威 | 対策（現行） |
|---|---|---|
| S1 | 見知らぬ第三者の入室 | 高エントロピーのルームコード（`nanoid`）。**新規参加者の既定 role は editor**（2 層モデル。`viewer`/`editor` の呼称はクライアント側で rotation 加入の有無を表すのに使う設計であり、archive 時点からの単純な後退ではない）。任意で合言葉/入室承認。失敗 join のレート制限（接続単位）。ルームコードのエントロピー下限（決定4）を新設する。**主防御は #103（IP 単位のレート制限）**であり、接続単位の窓は再接続で回避できるため単独では総当たりを止められない |
| S2 | Cross-Site WebSocket Hijacking | `Origin` を許可ドメインのみ検証。認可は Cookie でなく最初のメッセージのトークン。WSS 必須（Caddy）。現行が規範に一致し、変更なし |
| S3 | 不正・巨大メッセージ・構造インジェクション | 境界で 1 度だけ Valibot 検証。未知 type・余剰フィールド・サイズ超過は即拒否。メッセージ最大長を設定。**AI へ補間される利用者由来の値（`language`/`difficulty`）の列挙検証**を規範として追加する。実装は提案 #91 に委ねる（3.4.1 参照） |
| S4 | XSS（メンバー名・お題の描画） | React 既定エスケープ。AI/利用者由来テキストに `dangerouslySetInnerHTML` を使わない。**DOMPurify は不採用と明記する**（`Markdown.tsx` は文字列 HTML を生成せず `innerHTML` を使わない設計であるため不要。依存は削除する）。**CSP を追加する** |
| S5 | AI 出力の取り違え（マークダウン誤読） | AI 応答は信頼しないデータとして `Problem` 形へ Valibot 構造検証してから使用する。生テキストを実行・レンダリング可能な形へ流さない。現行が規範に一致し、変更なし |
| S6 | 秘密の漏洩 | **秘密ゼロの原則は放棄済み**（`docs/timer/adr/0008`）。サーバーは秘密を 3 つ保持する。中身をトークン衛生（env のみ・非ログ・argv 非混入）へ差し替える。**AI 子プロセスの権限を明示的に閉じる**規範を追加する。実装は `docs/adr/0012` の決定と提案 #91 に委ねる（3.4.1 参照） |
| S7 | DoS（接続・ルーム濫造） | IP 単位のレート制限は **#103** が実装する。本 ADR はその前提（IP はハッシュ化・窓限定で保持し永続化しない）を先に固定する |
| S8 | AI コスト濫用 | サーバー常駐生成（`docs/timer/adr/0008`）が同時 1・クールダウン・日次上限で運営者クレジットを保護する。現行が規範に一致し、変更なし |
| S9 | 権限のなりすまし | サーバーがコマンドごとに role と段階（開始前 / 開始後）を再検証する。**権限規則の正本は `packages/timer-core/src/permissions.ts` であり、本 ADR はコマンド名を列挙しない**（列挙すると `docs/adr/0002` の二重正本の禁止に触れ、コマンドの増減のたびに ADR が腐る）。性質として、host 限定は段階に依存する（開始前のみ host 限定のコマンド群があり、開始後は編集者以上に開放される）。対象が自分自身かどうかでも扱いが分かれ、開始後に自分自身のみへ限定されるコマンドもある。host 操作の認可基盤（`hostToken` の発行・検証）自体は `apps/timer-sync/src/application/token-store.ts` に現存する。**archive 時点の「host 操作は一律 `hostToken` 必須」という記述は、開始後に編集者以上へ開放される現行の段階依存の権限規則と食い違っており、本 ADR で現行化する（「変更なし」ではない）** |
| S10 | 状態汚染 | クライアントは状態を直接書けない。必ず `decide` を通す。現行が規範に一致し、変更なし |
| S11 | ログ漏洩・PII | **決定1のデータ分類表へ置換する。** ルームコードのログ出力（3 箇所）を塞ぎ、制御されたロガ 1 本へ集約し、機械的に検査する。実装は `docs/adr/0012` に委ねる |
| **S12** | **管理面の露出**（新設） | `/status` `/admin/rooms`。127.0.0.1 bind・定数時間トークン・未設定時は存在秘匿で守る。**`/admin/rooms` によるルームコードの返却は意図的な露出であり、マスクしない。** |
| **S13** | **CI の供給網**（新設） | `permissions: contents: read` の最小宣言と GitHub Actions の SHA ピン（`docs/adr/0010` の trustPolicy の思想を Actions へ拡張する）。実装は `docs/adr/0012` に委ねる |

**S12 でルームコードをマスクしない理由**: ログは journal に残り、貼り付け・転送で
持ち出される。管理面はトークンと bind で意図的に開けた運用者向けの窓であり、ここで
コードを隠すと「特定のルームで何が起きているか」という運用者の問いに答えられなくなる。
露出の相手（bind とトークンで閉じられた運用者のみ）と持続性（journal に残り続けるログとは
異なる）が違うため、規律を分ける。

### 決定3: 表示名は「ログへ出さない」が「配信はする」

分類は保持と出力の規律であって、機能の否定ではない（**MUST**）。表示名は「個人に紐づく」
分類だが、全参加者へ snapshot として配信する設計はそのまま維持する。ログへ出さない
という制約と、参加者間で共有する機能は両立する。

### 決定4: ルームコードのエントロピー下限

下限は「**想定される総当たり速度で全探索に要する時間**」で定義する（**MUST**）。

**目標値**: 全探索に要する時間が **1 年以上**であること。理由は次のとおり。ルームは
アイドル 30 分で回収される揮発設計だが、個々のルームの寿命の短さは脅威の抑止にならない。
ルーム名・slug は繰り返し推測でき、攻撃者は特定のルームの生存に依存せず、緩やかに・
検知されにくい速度で長期間試行を続けられる。1 年は、四半期規模の間欠的な調査キャンペーン
（数週間〜数か月）に対して 1 桁以上の余裕を持たせ、かつ暗号鍵のような非現実的に大きい
基準（2^128 相当）を求めない、現実的だが十分保守的な水準として本 ADR が新たに置く。

**前提レート**:

- **#103 実装前**: **600 回/秒**。設計正本 2.3 節が実測した現行の上限（同時接続上限 200 ×
  接続単位のレート制限 10 秒あたり 30 回。接続単位のため再接続で窓がリセットされる）を
  そのまま用いる。
- **#103 実装後**: #103 が導入する IP 単位のレート制限の具体的な閾値は #103 自身が決める
  ため、本 ADR の時点では確定していない。本 ADR は前倒しの目安として、**単一 IP あたり
  1 回/秒**を仮定する（総当たり対策として一般的な水準の丸めた値）。この仮定は攻撃者が
  単一 IP から試行する場合のみ有効であり、複数 IP へ分散する攻撃者を防ぐものではない。
  **#103 が実装され次第、この仮定を実測値で置き換えて本決定を見直す。**

**判定**: 探索空間（設計正本 2.3 節）を上記のレートで割った時間を、目標値（1 年 =
31,536,000 秒）と比較する。

| 経路 | #103 実装前（600 回/秒） | #103 実装後の仮定（1 回/秒） |
|---|---|---|
| ルーム名なし | **不足** | **充足** |
| **ルーム名あり（`slug-????`）** | **不足** | **不足** |

**探索空間と、そこから算出される所要時間は本 ADR へ転記しない。** 正本は設計正本 2.3 節
であり、ここには判定の結論だけを置く。理由は本決定自身にある — 下記の対応の選択肢には
**接尾辞の桁数を増やす**が含まれており、実施されれば探索空間も所要時間も変わる。転記すると
追随更新を怠った時点で誤った記述になる（`docs/adr/0002` の二重正本の禁止。
`docs/adr/0012` 決定 D2 も同じ理由で桁数を転記していない）。表の `slug-????` は
設計正本 2.3 節が使う**経路の呼び名**であって、桁数の宣言ではない。

**結論**: `slug-????` 経路は、#103 実装前・実装後のどちらの前提でも目標値（1 年）を
満たさない。**判定の結論は既に出ている。** ルーム名なしの経路は #103 実装後の
仮定では満たすが、#103 実装前は満たさない。

対応の選択肢は「接尾辞の桁数を増やす」「ルーム名つきルームでパスフレーズを必須化する」
「#103 のレート低減に委ねる」のいずれかである。**いずれも利用者から見える振る舞い
（共有 URL・ルームコードの見た目）を変えるため、本 ADR では実装を決定しない。** 実装は
別 Issue を起票して行う。

## 影響

- **#103（IP 単位のレート制限）は S1 の主防御である。** 接続単位のレート制限は再接続で
  回避できるため、#103 が実装されるまで S1 の防御は実質的に手薄なままである。
- 提案 #91（timer のお題機能の共通資産化）へ、**AI 子プロセスの権限の明示的な指定**と
  **`language`/`difficulty` の列挙検証**（S3・S6）を送る。設計正本 3.4.1 節が示す
  持ち出し経路（editor 権限での参加 → `config.set` への注入 → `claude -p` の Read 権限で
  秘密ファイルを読む → `problem.request` の応答として全参加者へ配信）はリスクとして
  受容し、実装は本 Issue（#136）では行わない。受容の根拠（解錠しない限り経路が
  存在しないこと・トークンは失効させれば回復できること等）は設計正本 3.4.1 節を参照する。
  この判断は「危険がない」ではなく「窓を運用で閉じられ、失効で回復できる」ことに基づく
  ものであり、AI を常時解錠する運用へ変える、または秘密の種類が増える場合は前提が崩れる
  ため再評価が必要である。
- 決定4により、`slug-????` を含むルームコード生成の現行実装は下限を満たさないことが
  確定した。対応（コード生成の変更）は本 ADR の範囲外とし、別 Issue で扱う。
- 決定1〜3は `docs/adr/0012`（ログ・秘密・開示の取り扱い）とセキュリティガイド
  （docs/guides/security.md、後続タスクで新設）が実装・運用手順を担うための土台になる。

## この ADR で決めないこと

- ログの具体的な扱い（ロガの実装・整形・検査の設計）→ `docs/adr/0012`
- 認証・認可の作り込み（憲法 原則 III の単純運用の範囲を超えるもの）
- 脆弱性検査の方式 → [#69](https://github.com/tomohiroJin/tasuki-tools/issues/69)（`pnpm audit` の CI 化で対応済み）
- ルームコードの生成方式そのものの変更（決定4の判定結果を受けた対応）→ 別 Issue
