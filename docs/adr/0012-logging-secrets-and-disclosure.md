## 背景

[`docs/adr/0011`](./0011-threat-model-and-data-classification.md) は「何を守るか」
（データ 4 分類・脅威モデル S1〜S13）を定めた。本 ADR はその続きとして、ログの経路・
秘密の配り方・エラー開示・クライアント保存・CSP・CI の供給網・公開窓口・AI 子プロセスの
扱いという「どう守るか」を決める。0011 決定1（データ 4 分類：秘密 / 資格情報 / 個人に
紐づく / 公開可）を前提とする。

実装の現状の実測（`console.*` の件数・ルームコードのログ出力箇所・保持する秘密の数・
定数時間比較の適用箇所・CSP の不在・CI の `permissions:` 宣言の不在・本番の Caddy 設定の
実態など）は設計正本 2 節（実測は数値の正本）にあり、本 ADR はそこから数値を転記しない
（`docs/adr/0002` の二重正本の禁止）。

計画段階で新たに判明した事実が 1 つある。`requestId` の境界スキーマ
（`packages/timer-core/src/schemas.ts`）は文字列であることと 1 文字以上であることしか
制約しておらず、最大長も文字種の制限も持たない。利用者由来の値をログのフィールドへ
生のまま渡す設計のままでは、改行を含む `requestId` 1 つで journal に偽の行を作れる。
この事実を D12 として追加する。

## 決定

### 決定 D1: ログ経路の一本化（対象は `apps/timer-sync`）

**`apps/timer-sync` の出力は、制御されたロガ 1 本を通す（MUST）。** ロガは分類
「秘密・資格情報・個人に紐づく」（ADR 0011 決定1）の値を受け取らない設計とする。
`process.stdout` への直接書き込み、および未捕捉例外・未処理 rejection のハンドラも
同じ規律の対象に含める（**MUST**）。ハンドラは分類名（`err.name`）だけを出し、
`uncaughtException` と `unhandledRejection` のどちらも `process.exit(1)` で終える
（**MUST**）。ハンドラを置く目的は「何が起きたかを出さないこと」であって
「プロセスを生かすこと」ではない。ログを出すだけのハンドラを置くと、ハンドラが無ければ
落ちていたプロセスが落ちなくなり、systemd の再起動による復旧が働かなくなる。

直接の `console.*` 呼び出しは、行単位で明示した例外を除き禁止する（**MUST NOT**）。
本 ADR に基づく実装後に残っている直接呼び出しは、次の 2 箇所だけである。

| 箇所 | 理由 |
|---|---|
| `apps/timer-sync/src/adapters/console-log-sink.ts` | ロガの**唯一の実出力口**。ここだけが `console` を呼ぶ |
| `apps/poker-sync/src/server.ts` の `listening` 行 | **テストハーネスとの契約**（下記の繰り越しを参照） |

timer-sync の起動ログと設定エラーは、当初この例外に数えていたが、実装ではいずれも
ロガ経由になった。例外として数える必要はない。

**`apps/poker-sync` は繰り越しとする。** poker-sync の直接出力は
`{"event":"listening","port":...}` の 1 行だけで、これは
`apps/poker-sync/tests/helpers.ts` が `JSON.parse` して実ポートを受け取るテスト
ハーネスとの契約である。形式を変えると poker-sync のテストが全滅する。ロガ経路を
導入しても、この 1 行だけは同じ形式で出し続けなければならず、いま移行しても得られる
ものが無い。したがって poker-sync へのロガ導入は本 ADR では求めない（繰り越し先は、
poker 側のログ出力が `listening` 以外にも増えるときとする）。

ただし**規律の対象からは外さない**。`scripts/audit-log-hygiene.mjs` は
`apps/poker-sync/src` も走査対象に含み、許可マーカーの無い直接出力は増やせない
（**MUST NOT**）。分類「秘密・資格情報・個人に紐づく」の値をログへ出さないという
規範（憲法 原則 XI・ADR 0011 決定1）は、ロガの有無にかかわらず poker-sync にも効く。

ブラウザの `console` は本決定の対象外とする。journal は運用者とサーバーへ侵入した者の
双方が読みうるが、ブラウザの `console` は利用者本人しか見ない。脅威が異なるため規律を
分ける。ただし分類「秘密」の値をクライアントへ渡さないという制約は、ADR 0011 の分類表で
引き続き効く。

### 決定 D2: マスキングは部分表示を採らない

ルームコードそのものをログへ部分的にでも出力しない（**MUST NOT**）。追跡には別に発行した
相関 ID（`roomRef`）を用いる（**MUST**）。

**理由**: 部分表示は残りの探索空間を縮める。ADR 0011 決定4（探索空間の実測は設計正本
2.3 節が正本）が示すとおり、ルーム名つきの経路は推測困難な部分がもともと狭い。数文字が
漏れるだけで、残りの探索空間が実用的な総当たり範囲まで落ちる。ルームコードを一切含まない
相関 ID に置き換えれば、この縮小そのものが起きない。**推測困難な部分の具体的な桁数は本
ADR には転記しない**（ADR 0011 決定4は対応の選択肢として桁数の拡張を挙げており、実施
されれば値が変わる。転記すると追随更新を怠った時点で誤った記述になる）。

相関 ID はプロセス起動ごとのランダムなソルトから導出する。そのため**再起動をまたぐと
同じルームの相関が切れる**。揮発インメモリ設計（憲法 原則 III。ルームはプロセス再起動で
消える）と整合するため、この制約は受け入れる。

**この決定を覆す条件**: ADR 0011 決定4の対応（接尾辞の桁数拡張など）でルームコードの
探索空間が十分に広がり、数文字の露出が総当たりを実用的な範囲まで縮めなくなった場合は、
部分表示の採用を再検討できる。ただし本 ADR の時点ではその対応の実施可否・桁数は未定
（ADR 0011 決定4に委ねられている）ため、今は採らない。

### 決定 D3: IP アドレス

保持するのは、起動ごとのランダムソルトで HMAC-SHA256 したハッシュ値（以下「相関キー」）
のみとする（**MUST**）。生の IP アドレスは、それを必要とする処理の変数スコープを越えて
保持しない（**MUST NOT**）。相関キーの保持期間は下記「相関キーの保持期間」の改訂を
参照する。ログ・snapshot・永続化のいずれにも出さない（**MUST NOT**）。

**相関キーの保持期間（2026-08-14 改訂・[#103](https://github.com/tomohiroJin/tasuki-tools/issues/103)）**:
相関キー（IP の HMAC 値）は、レート制限器のエントリと、それを生成した接続の、
**長い方**まで保持し、どちらも失われた時点で破棄する（**MUST**）。

本 ADR の初版は「レート制限の窓が閉じたら、ハッシュ値も破棄する」と書いていたが、
これは #103 の実装形が未定のまま書かれたものである（`docs/adr/0011` 決定4 が
「閾値は #103 自身が決める」と明記している）。長寿命の WebSocket 接続を IP 単位で
縛るには、接続の生存期間ぶん相関キーを覚える以外に方法がない。代案は 2 つとも
成立しなかった（IP を接続の受け入れだけに使う案は目標レートに 30 倍届かず、
バケツへの参照だけを接続に持たせる案は接続を多数張れば回避できる）。詳細は
設計正本 `docs/superpowers/specs/2026-08-14-ip-rate-limit-design.md` D7 を参照。

**緩めた範囲と、変わらず禁じたままの範囲**: 緩めたのは**保持期間の長さ**だけである
（「窓が閉じたら破棄」→「レート制限器のエントリと生成元接続の、長い方まで保持し、
両方が失われたら破棄」）。次は初版から変わらず禁じたままである（**MUST NOT**）。

- 生の IP アドレスを、それを必要とする処理の変数スコープを越えて保持すること
  （相関キーへ変換した後は生の IP を持ち回さない。生の IP は adapter の変数スコープを
  出ない。#103 設計正本 5.3 節）
- 相関キーをログ・snapshot・永続化へ出すこと（保持先はプロセスのメモリ上のみ）
- 保持期間を「レート制限器のエントリと生成元接続の、長い方」より延ばすこと
  （例: プロセス再起動をまたいで保持する、両方が失われた後も居残らせる）
- ソルトを env 化・永続化すること。ソルトはプロセス起動時にメモリ上でのみ 1 回だけ
  生成する（決定は変更していない）

**Caddy のアクセスログは出さない（MUST NOT）。**

**理由**: 本番環境を実測した結果（設計正本 2.6 節）、稼働中の Caddy 設定は tasuki の
サイトブロックにもグローバルオプションブロックにも `log` ディレクティブを持たず、
`/var/log/caddy/` に tasuki 関連のログファイルは 1 件も存在しない。IP アドレスは現在
どの経路にも記録されていない。この状態を単なる「未設定」のまま扱うと、将来 Caddy 設定に
手を入れる誰かが「アクセスログは足すのが普通」という理由だけで有効化しうる。本 ADR は
この不在を明示的な決定へ格上げし、Caddy のアクセスログを出さないことを MUST NOT として
固定する。アプリ側で IP をハッシュ化し、上記「相関キーの保持期間」の範囲に限って保持する
設計は、Caddy 側で生 IP を別経路に残さない運用と対になって初めて成立するため、片方だけを
規範化すると漏れる。

**この決定を覆す条件**: 運用上どうしても生 IP を伴うアクセスログが必要になった場合
（法的要請や、アプリ側のハッシュ値だけでは足りない障害調査が生じた場合）。その場合も
生 IP をそのまま出す方向へは戻さず、Caddy 側でもハッシュ化・マスクしたうえで出力する
設計を新たに起こし、本 ADR を改めることを条件とする。「あると便利」という理由だけでは
覆さない（個人に紐づく情報の保持を最小化するという ADR 0011 決定1の分類そのものに
反するため）。

### 決定 D4: 秘密の置き場と配り方

分類「秘密」の値（管理トークン・AI 解錠キー・OAuth トークン。ADR 0011 決定1）は
env のみに置く（**MUST**）。利用者が決めるルームの合言葉（パスフレーズ）は分類
「資格情報」であり本決定の対象ではない（憲法 原則 XI と同じ切り分け）。サーバー上のファイル
パーミッションは 600 とする（**MUST**）。配り方と失効手順を `deploy/README.md` に明記する
（**MUST**）。子プロセスへは env 経由で渡し、argv には載せない（**MUST NOT**）。
現行の実装をそのまま規範として固定する。

### 決定 D5: エラー開示

利用者へ返すエラーは、**エラーコードと、決定1の「公開可」に収まる情報だけ**で構成する
（**MUST**）。例外メッセージ・スタックトレース・スキーマ検証の詳細を返さない（**MUST NOT**）。

**内部識別子の扱い**（何を返してよいか）は決定1の分類で決まる。

| 値 | 分類 | 利用者へ返してよいか |
|---|---|---|
| エラーコード（`UNAUTHORIZED` 等） | 公開可 | ✅ よい |
| **要求した本人が送った命令名**（`cmd.command`） | 公開可 | ✅ よい。本人が送った値なので開示にならない |
| ルームコード / パスフレーズ / `resumeToken` | 資格情報 | ❌ 自分の分以外は返さない |
| 他の参加者の `participantId` / 表示名 | 資格情報・個人に紐づく | ❌ エラーへは載せない |
| `connId` / 内部のエラー型名 | 公開可（実装の内部名） | ⚠️ **返してよいが、増やさない**。利用者の役に立たず、実装の形を外へ晒す |

> **⚠️ この節は 2026-08-13 に訂正した。** 当初は「エラーコードと固定文言のみ（MUST）」と
> 書き、あわせて「現行の timer・poker はいずれもこの規律を満たしている」と述べていた。
> **後者は事実誤認だった。** #136 の完了確認で `sendError` の全 42 箇所を調べたところ、
> 固定文言でない箇所が実在した（`packages/timer-core/src/permissions.ts` の `denied()`
> 5 箇所と `apps/timer-sync/src/application/handlers.ts` の 2 箇所。いずれも命令名か
> 内部のエラー型名を埋め込む）。
>
> 埋め込まれているのは**要求した本人の命令名**と**内部のエラー型名**だけで、秘密・資格情報・
> 個人に紐づく情報は含まれない。**情報開示は起きていない。** 誤っていたのは実装ではなく、
> 実態より強く書いた規範のほうだった。そこで「固定文言のみ」を「決定1の公開可に収まる
> 情報だけ」へ改め、内部識別子の扱いを上表で明示した。
>
> **実装は変更しない。** epic #67 の「利用者から見える振る舞いを変えない」制約に加え、
> 命令名を含むメッセージは利用者が原因を理解する助けになっており、変える理由がない。

**この決定に対応する機械的な検査は、現時点では持たない（規範のみ）。** 返却されるのが
公開可の情報だけかを静的に判定するには、エラー値がクライアントへ届くまでの経路を追う必要が
あり、`scripts/audit-log-hygiene.mjs` のような行単位の検査では扱えない。守られていることの
確認は、`docs/guides/security.md` のレビューチェックリスト（項目 4）が担う。検査を足すなら
別途設計する。

**この訂正が示すこと**: 規範を書くときに「現行は満たしている」と書き添えるなら、**書く前に
実際に数えること**。数えずに書くと、規範のほうが嘘になる。

### 決定 D6: クライアント保存（考え方のみ）

資格情報のクライアント保存先は、復帰の要件（同一タブで足りるか、端末をまたぐ必要が
あるか）と、共有端末上で漏れるリスクから選ぶ。timer が sessionStorage、poker が
localStorage である現状は、いずれもこの基準から説明できる。一本化は提案 #95
（参加者・ルームの共通化）の際に行う。本 ADR は判断基準のみを決定として記録し、実装は
変更しない。

### 決定 D7: CSP

次の Content-Security-Policy を追加する（**MUST**）。

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'
```

`connect-src` は `'self'` で足りる（**MUST**）。WebSocket は同一オリジンへ接続する
（`buildSyncUrl` が `location.host` を使う）ため、公開ドメインを列挙する必要はない。
列挙してもプレースホルダのドリフト源が増えるだけである。

**理由**: フレッシュビルドの資産を実測した結果（設計正本 2.2 節・7 節）、timer-web /
timer-sync / poker-sync の 3 アプリいずれもインラインの `<script>` を持たず、外部の
module script と外部 CSS のみで構成されている。`img-src 'self' data:` が必要なのは、
favicon が `data:` URI で埋め込まれているため。

`style-src 'unsafe-inline'` を残すのは、React の `style={{}}` によるインラインスタイルが
パッケージ横断で 10 箇所（設計正本 2.2 節）残っているためである。これを今外すと画面が壊れる
おそれがあるため、実測で確かめるまでは残す。

**`style-src 'unsafe-inline'` を外す条件（2026-08-13 Task 17 実測により訂正）**: 当初は
「該当箇所を CSS 変数（または CSS クラス）へ寄せる」ことを条件として記録したが、これは
正確ではなかった。**決定を覆すのではなく、事実誤認を訂正する。** 実測の結果、React の
`style` prop は `react-dom` の内部実装上 CSS プロパティを 1 つずつ代入する経路
（`setValueForStyle` 関数）で適用しており、この経路は Chromium の CSP `style-src` の
inline 判定に掛からない（`element.style.cssText = ...`・`setAttribute('style', ...)`・
`<style>` 要素の動的挿入・`innerHTML` 経由の `style=""` 属性は判定に掛かることを実測で
確認済み）。加えてリポジトリ全体を検索した結果、`cssText` と `setAttribute('style', ...)`
の使用は 0 件であり、`style={{}}` の 10 箇所はすべて React の `style` prop 経由である。
したがって「CSS 変数へ寄せる」書き換えは外す条件として必須ではない可能性が高い。

**外すために実際に確かめる必要があること**: `style={{}}` を使う画面（timer-web の
Session / Summary とその配下のコンポーネント）まで実際に到達し、`unsafe-inline` を
外した CSP のもとで違反が 0 件であることを確認する（**MUST**）。ロビー画面は
これらのコンポーネントを経由しないため検証にならない。到達には稼働中の timer-sync
サーバーとルーム作成が要り、e2e の領分である。

**外したあとに維持すべき条件**: 生の DOM スタイル操作（`element.style.cssText`・
`setAttribute('style', ...)`・`<style>` 要素の動的挿入・`innerHTML` 経由の `style=""`
属性）を持ち込まないこと（**MUST NOT**）。持ち込むと `unsafe-inline` が再び必要になる。

`frame-ancestors 'none'` は既存の `X-Frame-Options` の上位互換にあたる。移行期間として
両方を置く（**MUST**）。

### 決定 D8: CI の供給網

GitHub Actions のワークフローに `permissions: contents: read` を最小で宣言する
（**MUST**）。Actions の参照は SHA ピンとする（**MUST**）。ADR 0010 が定めた
trustPolicy（信頼証跡の降格を拒否する考え方）を、依存パッケージから GitHub Actions へ
拡張したものである。Renovate の digest 更新が動作することを確認するまでは、SHA ピン と
定期的な手動確認を組み合わせる（**MUST**）。

### 決定 D9: 公開窓口

脆弱性の報告を受け付ける `SECURITY.md` をリポジトリ直下に新設する（**MUST**）。

### 決定 D10: AI 子プロセス

`claude -p` へ渡す権限は、既定の挙動に依存せず明示的に閉じる（**MUST**）。プロンプトへ
補間する利用者由来の値（`language` / `difficulty`）は、境界で許可リストに対する
列挙検証を行う（**MUST**）。実装は提案 #91 へ送る（ADR 0011 決定2 S3・S6 を参照）。

### 決定 D12: ログ行への注入を防ぐ（2026-08-13 の計画時に判明）

利用者由来の文字列を、ロガのフィールドへ生のまま渡さない（**MUST NOT**）。整形の側で
制御文字（CR・LF・タブ）を必ず除去する（**MUST**）。

`requestId` の境界スキーマ（`packages/timer-core/src/schemas.ts`）は、文字列であることと
1 文字以上であることしか制約しておらず、最大長も文字種の制限も無い。そのままログへ渡すと、
`requestId` に改行を含めるだけで journal に偽の行を作れる。呼び出し側が善意で
`requestId` を組み立てることに規律の実効性を委ねず、**整形関数の側が必ず制御文字を
落とす**形にする（**MUST**）。

## 影響

- D2 の相関 ID 導入により、ログからルームコードそのものを追える経路が失われる。運用者が
  特定のルームコードを知る必要がある場合は、ADR 0011 S12 が定める意図的な露出経路
  （`/admin/rooms`）を使う。両者は露出の相手（bind とトークンで閉じられた運用者のみ）と
  持続性（journal に残り続けるログとは異なる）が違うため、規律を分けたままにする。
- D3 により、Caddy のアクセスログを追加する変更は本 ADR に反する。将来の Caddy 設定変更を
  レビューする際の明示的な根拠になる。
- D7 は、`style-src 'unsafe-inline'` を外す条件を満たすまでの間、CSP による XSS 対策の
  効果が部分的にとどまることを既知のギャップとして受け入れる。CSP の本番への到達性は
  `deploy/caddy/tasuki.conf` を変更しても届かず、#66 の設置作業まで持ち越しである
  （設計正本 2.6 節）。
- D12 により、ログ整形関数（後続タスク）は制御文字除去を持たない実装を許容しない。
  境界スキーマ自体（文字種・最大長の制限追加）を変更するかどうかは本 ADR の範囲外とし、
  別途判断する。
- D1 の対象を `apps/timer-sync` に絞ったことで、`apps/poker-sync` はロガ経路を持たない
  まま残る。これは既知の繰り越しであり、`docs/guides/security.md` の記述もこの切り分けに
  揃える。ログ衛生の検査は poker-sync も走査し続けるため、規律の穴にはならない。
- D5 に対応する機械的な検査は存在しない。守られていることの確認はレビュー
  （`docs/guides/security.md` のチェックリスト）に依存する。ここは検査で守られている
  他の決定より弱い。
- D1・D4・D5・D9 の多くは現行の実装を MUST 化するだけで、振る舞いを変えない。実装は
  後続タスクが本 ADR を根拠に行う。

## この ADR で決めないこと

- **ルームコードのエントロピー下限**（設計正本 3.5 節 D11）→ 既に
  [`docs/adr/0011`](./0011-threat-model-and-data-classification.md) 決定4が扱っている。
  本 ADR には転記しない
- ロガの型・語彙・整形関数・検査スクリプトの実装 → セキュリティガイド（後続タスクで新設）
  と、それに続く実装タスクが担う
- CSP の本番到達性の確認（Caddy 設定の設置） → #66
- 認証・認可の作り込み（憲法 原則 III の単純運用の範囲を超えるもの）
