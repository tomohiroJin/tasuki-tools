## 背景

### 用語

このリポジトリで「変異検査」と呼んできたものは、**手書きの変異**（`scripts/lib/mutation-declarations.mjs` の宣言と
`scripts/mutations/*.patch`。`node scripts/mutation-check.mjs`。2026-11-06 の main で `MUTATIONS` は 696 件）である。
狙った 1 つの性質を守る。CI は毎回全件を流す（ADR-0029 決定 1）。
本 ADR の**自動の変異**は、道具（Stryker）がソースから機械的に作る変異で、手書きの変異とは別のものである。

### 調査の数字

#496 は、Stryker（`@stryker-mutator/core` 9.6.1 ＋ `vitest-runner` 9.6.1）を**依存に足さず**、一時ディレクトリへ入れて、
使い捨ての作業ツリーで一度だけ流した（調査 2 節。道具の比較は 2.1）。

| 項目 | 結果（調査の節） |
|---|---|
| core 9 パッケージ（`packages/*-core`・`rate-limit`・`protocol`） | 4,452 件、生存と未到達 478 件。生存率 0〜23.3%。4 並列で計 12.1 分（2.3） |
| `apps/tasuki-sync`（境界の 3 ファイル） | 127 件中 6 件（4.7%）。9.6 分（2.3）。`bun test` を変異ごとに丸ごと流す |
| 生き残りの分類 | 条件・境界・演算 240 件（**振る舞いが変わる。本題**）・文字列と表 158 件・スキーマ 58 件・文言 22 件（2.4） |
| 製品のテストでも流し直した 100 件 | 83 件は製品でも生き残り、15 件は tasuki-sync が落とし、2 件は Stryker の誤り（2.5） |

調査の生き残りから起こした ISSUE は #521（rate-limit の境界と上限ちょうどのフレーム）と
#522（core の境界値の性質テスト）で、どちらも閉じている。
**#533（poker-core の捨て札の切り直し）と #534（timer-core の `member.add` の上限）は調査の生き残りから起こしたものではない。**
#522 の作業の PR #530 の敵対的レビュー、PR #528 の `/code-review` で、範囲の外の穴として偶然見つかったものである。
**#533 は「どのテストも守っていない」穴**（捨て札の切り直しを壊しても、どのテストも落ちない）で、自動の変異なら生き残りとして拾える種類である。
それがレビューという**偶然の経路**でしか見つからなかったことが、定期の調査の動機の裏づけになる。
**#534 は裏づけに数えない。** `member.add` の上限は、`>=` を `>` にすると既存のテストが落ちる（いまテストは守っている）。手書きの変異の宣言が無いだけで、
自動の変異では生き残りとして拾えない種類である。手書きの変異の偏りの話であり、本 ADR の仕組みの守備範囲ではない。
手書きの変異は 1 件ずつ狙って書くので、**変異が 1 つも無い箇所は誰も見ていない**（調査 1.3）。自動の変異はそこを広く拾う。

### 一度きりでは足りない

調査はある日の main の写真である。テストを足した後、コードが変わった後に穴が開いても、**誰も気づけない**。
手書きの変異は 2026-10-14 の 153 件から 17 日で約 2.9 倍に増えた（ADR-0029）。main へのコミットも、2 週あたり 46 件（2026-10-09〜10-23）・65 件（10-23〜11-06）と入り続けている
（GitHub の REST で数えた。この作業ツリーは浅い clone で `git log` は件数に使えない）。穴が戻るのを週のうちに見つける仕組みが要る。
調査の 6.1・6.2 は、これを「採る」「CI の合否でなく、定期の調査として。導入は ADR を通す（原則 II）」と決めた（案 F）。

### 2.1 で踏んだこと

| 踏んだこと | 本 ADR の扱い |
|---|---|
| TypeScript を Stryker から解決できないと `ERR_MODULE_NOT_FOUND` で止まる | 決定 1・4 |
| 隔離した写し（sandbox）では、パッケージの外を相対パスで読むテストが `ENOENT` で落ち、最初の実行で止まる（checkin-core・agenda-core・roulette-core。`../../ui/src/tokens/fonts.css` など） | 決定 4 |
| bun は `command` runner になり、変異ごとに `bun test` を丸ごと流す（絞り込みが効かない） | 決定 3・4 |
| Stryker の `perTest` が殺すテストを外し、丸ごと流すと落ちるもの（100 件中 2 件） | 決定 5 |

## 決定

### 1. 道具: Stryker をルートの devDependency に入れる

- **MUST**: `@stryker-mutator/core` と `@stryker-mutator/vitest-runner` を、ルートの `package.json` の `devDependencies` に入れる。
  eslint・typescript・turbo と同じ置き場・同じ書き方（`^` の範囲と lockfile）にする。**pnpm と Renovate の経路だけで入れる**
- **MUST NOT**: ワークフローの中で `npm i`・`npx`・`pnpm dlx` により一時に入れない。lockfile が無く、推移依存の版が実行のたびに動き、
  ADR-0008 の待機期間（`minimumReleaseAge`）・降格拒否（`trustPolicy`）・`--frozen-lockfile` の検証が効かない
  （調査はこの形だったが、「一度きり・手元の使い捨て」だから許した。**定期の実行は、無人で外部のコードを毎週実行する**）
- **MUST NOT**: `@stryker-mutator/*` の `allowBuilds`（インストール時のビルド許可）を足さない。下の測定でビルドが要る依存は 0 件だった。要るようになったら採否を決め直す

| 案 | 判断 |
|---|---|
| **A. ルートの devDependency** | **採る**。供給網の設定・検証・自動更新・脆弱性の通知が既存のまま 1 か所で当たる。vitest は既存の版に解かれ、新しい版を持ち込まない（下の測定） |
| B. 定期の実行の中だけで、npm で一時に入れる（調査と同じ形） | 退ける。上の MUST NOT。版を固定しても推移依存は固定できず、ADR-0008 の防御を自分で迂回する |
| C. `tools/` などの別ディレクトリに、固定した lockfile を持つ（`pnpm install --ignore-workspace`） | 退ける（今は）。供給網の設定は `pnpm-workspace.yaml` にしか書かない決まり（ADR-0008）で、`--ignore-workspace` はそれを読まない。写せば 2 か所になる。別のワークスペース内の package にすると、構造監査の走査対象の宣言（ADR-0014）が増える。**A が重すぎると分かったときの逃げ道として残す**（見直す条件） |
| D. 入れない（手元で手で入れる手順だけを置く） | 退ける。決定 2 のとおり、手動専用は ADR-0009 D1 の趣旨に反し、誰も流さなくなる |

**ADR-0008 との関係（起草側の測定）。** この repo の全 `package.json`・`pnpm-workspace.yaml`・`pnpm-lock.yaml` を別ディレクトリへ写し
（本 repo の供給網の方針をそのまま持つ）、ルートの `devDependencies` へ `@stryker-mutator/core` と `vitest-runner` を `^9.6.1` で足して、
pnpm 11.28.9 で `pnpm install --lockfile-only` を流した（2026-11-06）:

| 項目 | 結果 |
|---|---|
| `pnpm-lock.yaml` の `packages` のエントリ | **405 → 514（+109 件・+27%）** |
| 既存の行の変更 | 0 件（追加だけ） |
| `requiresBuild` | 0 件（`allowBuilds` の追加は要らない） |
| 供給網の方針（`minimumReleaseAge: 10080`・`trustPolicy: no-downgrade`） | 失敗なし |
| `vitest-runner` の peer の `vitest` | **既存の 4.1.12 に解かれた**（新しい `vitest` は入らない） |

起草の初めに、この repo の外の単独のディレクトリで解いたときは、エントリは約 218・peer の `vitest` は 5.0.5 だった。
**その値は本 repo の lockfile では起きない**（既存の `vitest` に重ねて解かれる）ので、使わない。
依存を入れ直す時間とストアの大きさは、起草側では測っていない（レビューの手元の測定は 6.09→6.24 秒・294M→330M だが、こちらでは再現していない参考値）。

**代償と、実装で確かめること**（採択後の PR の完了条件にする）:

- **全ジョブの `pnpm install` が少し重くなりうる。** 基準を決める: 実装の PR で、`mutation (k)` の最長の所要が、main の直近 5 回の run の
  最小〜最大の範囲に収まること。`mutation (k)` の最長は、各 run の job の開始・終了時刻（`gh api repos/<owner>/<repo>/actions/runs/<run>/jobs`）から取る。
  あわせて `pnpm install` のステップの秒数を、前後の run のログのステップ時刻から**直接並べて**書く
  （`scripts/measure-mutation-costs.mjs` は組ごとの変異の秒を測る道具で、install の時間は測らないので、判定には使わない）。**同じ組でも run ごとに最大 2 倍揺れる**（同書）ので、
  1 回の比較で「増えていない」と言い切らず、範囲を超えたときだけ増えたと扱う。範囲を超え、install のステップの増えが原因と分かれば、案 C へ移る
- **推移依存の勧告の手間が増える。** Stryker の推移依存に Dependabot alerts が上がると、ADR-0024 決定 4 とその追記（#444）のとおり、
  直接の依存ではないので Renovate の PR では届かず、lockfile の解き直しの PR が要る。開発時だけの依存で配布されないので、
  却下するなら理由をアラートに書く（0024 決定 4）。この作業が、週次の調査を読む仕事に加わる
- **`vitest-runner` が使う `vitest` は、流すパッケージ側のもの。** 配布物の `vitest-wrapper.js` は `createRequire(path.join(process.cwd(), 'package.json'))` で
  `vitest` を読む（起草側で配布物を確認した）。パッケージのディレクトリで流せば、そのパッケージの `vitest` が使われる。`packages/protocol` で流して確かめられた、というレビューの報告もあるが、起草側では流していない
- **`plugins` に絶対パスが要る見込み。** pnpm の配置では、Stryker 本体が `@stryker-mutator/*` を同じ階層から自動で見つけられない、というレビューの指摘がある
  （起草側では未確認）。調査の設定が `plugins` に `vitest-runner` の絶対パスを書いていたのと同じ形になる見込みで、実装で確かめて設定に書く
- **TypeScript の解決。** ルートの `typescript` が隠れた持ち上げで解決できる、というレビューの観察がある（未確認）。
  調査の `ERR_MODULE_NOT_FOUND` が出ないことを実装で確かめる。出るなら設定でパスを明示する（`typescript` を別に入れる形には戻さない）

### 2. 置き場: 定期の GitHub Actions のワークフロー（週 1 回＋手動起動）

- **MUST**: 新しいワークフローファイル（例: `mutation-survey.yml`。置き場は `.github/workflows/` の下）に置き、`on: schedule`（週 1 回）と `workflow_dispatch`（手動）で起動する。
  **`ci.yml` には何も足さない**。PR にも main への push にも載せない
- **MUST**: 自動の変異の結果で、CI の合否を決めない。生存率の下限（`thresholds.break` など）を置かない（決定 5）
- **MUST**: 実行の中身は `scripts/` の 1 つのコマンドにし、ワークフローはそれを呼ぶだけにする。**手元でも同じコマンドを、使い捨ての作業ツリーで 1 パッケージだけ流せる**
  （再現・直した後の確認のため）
- **MUST**: Stryker を流すジョブは `permissions: contents: read` だけを持つ。結果を知らせるジョブ（決定 5）は別のジョブにし、そこにだけ `issues: write` を足す
- **MUST**: 版は `toolchain.json` から読み（`scripts/audit-toolchain.mjs` の規則。ADR-0031 決定 3）、アクションは他のワークフローと同じくコミットの SHA で固定する
- 頻度は週 1 回（決定 6）。上限の時間（`timeout-minutes`）を付け、固まった実行を放置しない

| 案 | 判断 |
|---|---|
| **定期のワークフロー（週 1 回＋手動）** | **採る**。人が走らせ忘れない（ADR-0009 D1 の趣旨）。CI の時間・合否に触れない |
| 手元のコマンドだけ | 退ける。定期に流す主体がいなくなり、一度きりの調査と同じ結果になる。ADR-0009 D1「手動専用の検査を残さない」に反する |
| `ci.yml` に非必須のジョブとして足す（`continue-on-error`） | 退ける。PR のたびに約 30 分の runner を使い、結果が誰にも読まれない。`continue-on-error` は**道具が壊れた**ことも隠す（ADR-0009 の「検査が静かに効かなくなる」）。ADR-0029 の変異のシャードの時間（#544・#546・#550 で整えた）と同じ枠に入れることになる |
| 毎晩 | 退ける。1 回約 30 分 × 7 で、週に読む結果が増えるだけ。1 週間分の変更でも生き残りは読める量にしかならない |
| 月 1 回 | 退ける。理由は 2 つ。①1 回に溜まる変更が 4 倍になり（main のコミットは 2 週で 46〜65 件、月 1 回なら 1 回に約 100 件）、新しい生き残りがどの変更で出たかを辿れない。②費用は公開リポジトリでは無料で、減るのは**読む仕事**だけだが、それは間隔を後から伸ばせば済む。**週で始め、読まれなければ伸ばす**（見直す条件） |

起動の時刻は 0 分・30 分を避ける（例: 日曜 18:17 UTC ＝ 月曜 3:17 JST。月曜の朝に結果がある）。
`schedule` は既定のブランチ（main）でしか走らず、GitHub の負荷で遅れうる。遅れても困らない調査なので許す。

**CI の時間を増やさないこと。** 別のワークフローなので、`ci.yml` の `mutation (k)`・`mutation-all` の所要時間と必須チェックには触れない。
手書きの変異のシャード（ADR-0029・#544・#546・#550）の重みの表と matrix は変えない。
ただし決定 1 のとおり、ルートの依存が増えるので、`pnpm install` を通じた間接の影響の有無は、決定 1 の基準で判定する。
**後で手書きの変異を足す**（決定 5）ときの時間は、それぞれの ISSUE が既存の規則（`docs/guides/procedures/mutations.md`「重い組の実測の表」）で見積もる。

**ADR-0009 D1 との関係。** D1 は「リポジトリが持つ検査はすべて CI で走らせる。手動専用の検査を残さない」である。
この調査は結果に**合否を持たない**ので、D1 の対象の検査ではない。D1 の趣旨（走らせ忘れる経路を残さない）は、定期の自動実行で守る。
**合否を持つ部分（設定の宣言と実体の照合）は CI に置く**（決定 5）。ADR-0009 の本文は不変の記録なので直さない。実装の PR で、必要なら本 ADR を指す追記を足す。

**ADR-0024 との関係（逆の前例として引く）。** ADR-0024 は、`pnpm audit` を**定期実行（`schedule`）へ移す案を退けた**。理由は
「直る版が無い間は毎回落ち続け、同じ通知が繰り返し届く。却下や待機の記録を持てない」である。本案は定期の実行を採るので、この 3 点が当たるかを確かめる。

| 0024 の退けた理由 | 本案に当たるか |
|---|---|
| 毎回落ち続ける | **当たらない。** 生き残りがあっても緑で、赤になるのは道具が壊れたときだけ（決定 5） |
| 同じ通知が繰り返し届く | **一部当たる。** 処置されない生き残りは翌週も「未対応」として残る。繰り返しを畳むため、知らせは件数と変化を主にし、同じ未対応の一覧は貼り直さない（決定 5）。未対応が溜まり続けたら範囲を狭める（見直す条件） |
| 却下や待機の記録を持てない | **持てる形にする。** 処置（ISSUE にした・等価・受容）を、repo のファイルに鍵ごとに記録する（決定 5。Dependabot のアラートの却下のコメントに当たる） |

### 3. 範囲: core と小さい純粋なパッケージは全体、tasuki-sync は境界のファイルだけ、web は今は外す

| 対象 | 範囲 | 実行 |
|---|---|---|
| `packages/*-core`（agenda・checkin・poker・roulette・room・timer・topic）・`packages/rate-limit`・`packages/protocol` | **全体**（`src/**/*.ts`。`*.d.ts` と `index.ts` を除く。調査と同じ。件数と生存率を調査と比べられるように） | `testRunner: "vitest"`・`coverageAnalysis: "perTest"` |
| `packages/sync-client`（565 行）・`packages/dev-hub-redirect`（71 行）・`packages/markdown`（225 行） | **全体**。調査では測っていない。合わせて約 860 行で、core の約 8,800 行の約 1 割。**初回で測り、この ADR の追記で件数と所要を書く** | 同上（`sync-client` は jsdom のテスト） |
| `apps/tasuki-sync` | **境界の 3 ファイル**: `src/adapters/ws/connection-gate.ts`・`src/adapters/ws/tool-channel.ts`・`src/application/connection-errors.ts`（調査と同じ） | `testRunner: "command"`・`bun test --timeout 15000 --bail`・`coverageAnalysis: "off"` |
| `apps/*-web`・`apps/landing` | **外す**（今は） | — |
| `packages/invite-ui`・`packages/web-kit` | 外す（フックと部品で `.tsx` を含み、文言・JSX・見た目の等価に近い変異が多い。web を外す理由 3 が当たる。jsdom で重い・測っていないは、範囲に入れた `sync-client` にも当たり、行数も小さいので外す理由にしない） | — |
| `packages/ui` | 外す（TypeScript のソースが無い。CSS と `node --test`） | — |

**sync-client・dev-hub-redirect・markdown を入れる理由。** 調査 1.2・1.3 が、再接続と復帰の処理を持つ `sync-client`（手書きの変異の宣言が少ない）・
`dev-hub-redirect`（宣言 0 件）を、変異が薄い穴として名指しした。`.tsx` を含まない純粋な TypeScript で、行数も小さく、
core と同じ道具・同じ設定で流せる。外す理由が無い。`invite-ui`・`web-kit` は、実際の違いである「`.tsx` の部品とフックで、文言・JSX が大半」（web を外す理由 3）で外す。測れば入れてよい（見直す条件）。

**tasuki-sync を境界に絞る理由。** 全体は約 10,700 行で、境界の 3 ファイル（332 行）の約 32 倍である。調査では 127 件が 574 秒かかった
（実効約 4.5 秒/件）。変異の数が行数に比例すると仮定すると全体は約 4,000 件で、同じ速さなら約 5 時間である（**概算**）。
この速さが全体に当てはまるかは分からない。境界の 3 ファイルは変異が殺される割合が高く（生存 4.7%）、
殺された変異は `--bail` により途中で止まるので、生き残りが多い他のファイルは 1 件あたり長くなる側に外れうる（これも推論で、調査には無い）。
いずれにせよ週 1 回の枠（決定 6）には収まらない。**境界のファイルを足すときは、そのファイルの変異数 × 約 4.5 秒を見積もって、枠に収まることを確かめる**
（ファイルの一覧は設定の 1 か所に置き、足す・外すは PR で行い、決定 5 の照合が見る）。tasuki-sync の全体は、Stryker に bun の runner が出るか、
変異ごとに当てるテストを絞れるようになってから決め直す（見直す条件）。

**web を外す理由。**

1. **測っていない。** 調査は web にかけていない（調査 7 節）。生存率も、意味のある生き残りの割合も分からないまま、定期の実行に載せる根拠が無い
2. **重い。** web のソースは約 22,000 行で core の約 8,800 行の 2.5 倍。vitest でも jsdom のテストは `packages/*` の約 2 倍かかる（`docs/guides/procedures/mutations.md` の 2026-11-05 の測り直し）。
   core の 12 分を、概算で 1 時間以上に押し上げる
3. **等価に近い変異が多い。** 画面は文言・クラス名・JSX が大半で、調査 2.4 は core でも文字列と表が生き残りの約 3 分の 1（158/478）で、半分ほどは等価に近い。
   web ではこの割合が上がり、読む側が等価の判定に時間を取られる
4. **規則の置き場が core にある。** web 層は「純粋関数・同期フック・画面」に分け（ADR-0015）、ドメインの規則は core が持つ。
   穴を拾うべき規則（上限・境界・演算）は、core と同期サーバーの境界で拾える

web の純粋関数（`*-copy.ts` ではなく計算を持つもの）を後から足すときは、そのファイルだけを 1 回測って判断する（見直す条件）。

### 4. 調査で踏んだことの扱い（2.1）

- **TypeScript の解決**: 決定 1 のとおり、ルートに置く案 A で解決できる見込み。実装で、調査の `ERR_MODULE_NOT_FOUND` が出ないことを確かめる。出るなら設定でパスを明示する
- **sandbox で落ちるテスト**: `inPlace: true`（作業ツリーを直接書き換えて戻す）で流す。
  **ワークフローでは checkout した runner が使い捨てなので安全**。**手元では、手元の作業ツリーで流さない**（`git worktree` の使い捨てで流す。`mutation-check.mjs` の `--jobs` が作る作業ツリーと同じ考え方）。
  実装はこれを守らない呼び出しを止める（本体の作業ツリーに未コミットの変更があれば止める、など。`mutation-check.mjs` が既に持つ規則に合わせる）
  - **退けた案**: パッケージの外を読む 3 パッケージのテストを直す・sandbox から外す。直すのは別の ISSUE の範囲（core のテストが `ui` の資産を相対パスで読む形は、依存の向き〔原則 VI〕の観点でも見る価値がある。本 ADR では直さず、実装の PR で報告する）。
    sandbox から外すと、そのテストが守る変異まで「生き残り」に倒れて数字が歪む
- **bun**: `command` runner の `bun test --timeout 15000 --bail`・`coverageAnalysis: "off"`・`mutate` を境界のファイルへ絞る（決定 3）。
  `perTest` が使えないので変異ごとに全体が流れる。この遅さが、範囲を絞る理由である
- **bun の版**: ワークフローは `toolchain.json` の版で `setup-bun` する（ADR-0031）。手元は `check-toolchain` が止める

### 5. 結果の扱い: 記録し、前回と比べ、確かめ直し、知らせ、人がテストと手書きの変異に起こす

流れは「流す → 記録する → 前回からの新しい生き残りを抜く → 確かめ直す → 知らせる → 読む → ISSUE → テストと手書きの変異」である。
**自動の変異の結果は、CI の合否に触れない。**

1. **記録する**。パッケージごとに、変異の数・殺した・時間切れ・生存・未到達・生存率（調査 2.3 と同じ式）・所要時間を、
   **ジョブの要約**（`$GITHUB_STEP_SUMMARY`）に表で出し、Stryker の JSON と `summary.json`（生き残りの一覧と状態）を **artifact** に残す（保持は既定の 90 日）
2. **生き残りを識別する鍵と、前回の基準**。
   - 鍵は**行番号を使わない**: ファイル・変異の種類・置き換え後のコード・元のコードの正規化した 1 行、に**同じ鍵の中での出現の順番**（ファイル内の順）を足す。
     同じ行が 1 ファイルに複数あっても衝突しない
   - 前回の基準は、**main の `schedule` と、main で起動した `workflow_dispatch` の成功した実行だけ**。main 以外の枝で手動起動した結果は、artifact の名前に枝を入れ、基準に数えない
     （試しの実行が基準を書き換えて、次の週の「新しい」を狂わせない）
   - 前回が無い・読めないとき（初回・artifact の期限切れ）は、**「比べられなかった」と要約に出し、すべてを新しいものとして扱う**（0 件の緑にしない。ADR-0009 の「検査が静かに効かなくなる」）
3. **確かめ直す**。新しい生き残りのうち、**振る舞いが変わる種類**（条件・境界・論理・算術の演算。調査 2.4 の本題）だけを、
   1 件ずつ使い捨ての作業ツリーに入れ、**そのパッケージのテストを丸ごと**（`vitest run`。`perTest` の絞り込みなし）と、
   **製品のテスト**（`apps/tasuki-sync` の `bun test`・その core を使う web のテスト）で流し直す（調査 2.5 と同じ手順。`recheck-run.mjs`）。
   丸ごと流して落ちたものは Stryker の誤りとして外し、製品のテストで落ちたものは「製品が守っている」として別に数える。
   **どれでも落ちずに残ったものを `confirmed`（確かめ済み・未対応）にする**。
   - **MUST**: 作業ツリー **3 本を並列**に流す（調査の形。`--jobs 3`）。調査の実測は、3 本並列で 100 件が 2,308 秒（実効 約 23 秒/件）。
     直列なら約 69 秒/件で、同じ 100 件に約 115 分かかる（概算。調査の数字を 3 倍した値）
   - **MUST**: 件数ではなく**時間枠**で区切る。確かめ直しの段は 40 分の枠を持ち、枠を過ぎたら新しい 1 件を始めない。残りは `unchecked` のまま `summary.json` に持ち越し、
     次の実行が先に確かめる（3 本並列で枠に入る件数は約 100 件の見積もり）
   - 流す先の web の一覧は、各 core の `package.json` が持つワークスペースの依存から導く（調査の `CONSUMERS` の表を別に持たない。二重の正本にしない。原則 VIII）
   - 文字列・スキーマ・文言の表（調査 2.4 の残り）は確かめ直さず、数だけ記録する。調査 2.4 が「等価に近い」「境界のテストが守る」と読んだ種類のため
   - **初回の扱い**: 初回は生き残り 478 件（うち振る舞いが変わる種類は調査で 240 件）がすべて新しい。確かめ直しの枠は 1 回で約 100 件なので、
     **約 3 回の実行で消化する**。初回に ISSUE の洪水を起こさない
4. **知らせる。処置を記録する**。
   - **知らせる経路**: 決まった追跡用の ISSUE 1 件に、実行ごとに**要約のコメントを 1 件**書く（実行の日付・実行の URL・パッケージごとの生存率・新しい生き残りの件数・
     `confirmed` で未対応の件数と、新しく `confirmed` になったものの一覧）。同じ未対応の一覧は毎週貼り直さず、件数と変化にとどめる（全件は artifact）。
     追跡用の ISSUE は実装の PR で作り、その番号をワークフローの設定に置く
   - **権限**: コメントを書くジョブは Stryker を流すジョブとは別にし、そこだけが `issues: write` を持つ。ただし `issues: write` は全 ISSUE に書ける権限なので、
     **書き先が 1 件であることは権限ではなく、コードで強制する**（MUST）: 書き込みは `scripts/` の 1 つのコマンドだけが行い、書き先の番号はそのコード（または 1 か所の設定）に固定して、
     外から引数・環境変数で渡せない。番号の変更は PR で行う。自己テストが、書き込みの呼び出しが固定の番号 1 件のコメントだけであること、ワークフローにそれ以外の書き込み
     （`gh issue`・`gh pr`・書き込みの `gh api`）が無いことを見る（手書きの変異で壊して確かめる）
   - **コメントの書き方**: 変異のコード片は**コードブロックに入れる**（MUST）。`@名前` はメンションに、`#123` は ISSUE への参照になるため、そのまま貼ると無関係な人へ通知する。
     ブロックの囲みは、中身に現れるバッククォートの連なりより長くする。中身は変異のコード片と数字で、公開リポジトリのソースの一部であり、秘密・個人に紐づく値を含まない（原則 XI）
   - **いつ書くか**: コメントのジョブは `if: always()` で走り、Stryker のジョブが失敗・時間切れ・取り消しになった週も「失敗」「時間切れ」と実行の URL を書く
     （黙って何も届かない週にしない。ワークフロー自体が起動しなかった週は書けないので、コメントが来ないことで気づく）。
     書くのは**main の `schedule` と main で起動した `workflow_dispatch` だけ**。main 以外の枝で手動起動した結果は要約と artifact にだけ残し、コメントしない
   - **ADR-0030 決定 1 との関係**: 決定 1 は「依頼に含まれない ISSUE・コメントの投稿は人の指示を待つ」と置く。**本 ADR の採択をもって、書き先（追跡用の 1 件）・中身（数字と変異のコード片）・頻度（実行ごとに 1 件）に限り、
     人の明示の承認とする。** この範囲を超える投稿（他の ISSUE・PR への書き込み、生き残りごとの ISSUE の起票、中身や頻度の拡張）は含まず、そのたびに人の指示を待つ
   - **処置の記録**: `confirmed` の生き残りに、人が処置（ISSUE にした〔番号〕・等価・受容）を決めたら、**鍵ごとに repo のファイルへ記録する**。
     処置済みの鍵は次の週から「未対応」に数えない。**処置が無い `confirmed` は、新しくなくなっても毎週「未対応」に数え続ける**（翌週に落ちない）。
     等価と受容の処置は、実質的に**走査対象の除外の表**である。そのため次を守る（ADR-0014 決定 2・`AGENTS.md` の「走査対象の除外の追加は人の承認」）:
     - **MUST**: 処置には理由を必須にする（等価なら比べた入力と差が 0 件だった根拠、受容ならなぜ放置してよいか、ISSUE なら番号）。理由が空の行は読み込みで落とす
     - **MUST**: 処置の追加は PR で行い、人の承認を得る。AI は追加を提案するだけで、人の承認なしに等価・受容の処置を足さない
     - **MUST**: 鍵が実在しなくなった処置（コードが変わって対象の変異が無い）は、週次の実行が要約とコメントに「実在しない処置」として数えて報告する。
       **その処置は無効とし、何も免除しない**（古い除外が、同じ場所に生まれた新しい穴を黙って免除するのを防ぐ）。整理は PR で行う
     - 鍵の「出現の順番」は、同じ行が増減するとずれる。ずれた処置は上のとおり実在しないものになり、生き残りは未対応に戻る。**安全な側に倒れる**代わりに、再度の判断が要る
     - **置き場**: リポジトリのルート直下に置かない（`mutation-check.mjs` の `--changed` は、ルート直下の `.md` 以外のファイルの差分で全件に倒れる。`docs/guides/development.md`）。
       `docs/` か `scripts/` の下の、`mutation-check.mjs` が import しない場所に置く。**処置の記録と範囲の宣言は `.md` にしない**（例: `.json`）。`.md` だけの PR は上の自己テストが走らず、理由が空の処置や壊れた宣言を足しても PR の CI で止まらないため
   - **ISSUE にする**のは人の指示で行う。ワークフローは生き残りごとの ISSUE を作らない
5. **読んで起こす**。`confirmed` を人（または人に頼まれた AI）が読み、**等価かを判断する**（出力を元と変異後で比べ、差が無ければ等価。`docs/guides/procedures/mutations.md`「等価な変異にしない」と同じ）。
   等価でないものを、パッケージ・性質ごとにまとめて ISSUE にする（#521・#522 の形。1 つの ISSUE は 1 つの PR に収まる大きさ。`docs/adr/0013`）。
   ISSUE は TDD で進める（原則 I）。生き残った変異が落ちるテストを先に足し（Red）、その壊し方を**手書きの変異**として宣言する（`mutation-declarations.mjs`・原則 VII）。
   **手書きの変異にするのは、穴が戻ったときに週 1 回の調査を待たず CI で止めたいものだけ**にする。テストを足せば、定期の調査が次の週に同じ穴を拾い直すので、
   生き残りの 1 件ごとに手書きの変異を足す必要は無い（手書きの変異は CI の時間を増やす。ADR-0029・#546）。手順は `docs/guides/procedures/mutations.md` に足す（実装の PR）

**赤にするもの・しないもの。**

- **MUST NOT**: 生存率の下限・生き残りの件数で、ジョブを赤くしない
- **MUST**: 道具が壊れたことは赤にする。パッケージごとの変異の数が 0（`mutate` の対象が空・JSON が無い・Stryker が異常終了した）ときは失敗にする。
  ADR-0014 決定 8 のとおり、数えるのは宣言の行数ではなく走査量そのもので、**内訳（パッケージ・境界のファイル）のどれか 1 つでも 0 件なら落とす**。
  「調査の結果として生き残りがある」は緑、「調査ができていない」は赤である
- **MUST（CI で流す照合）**: 上の赤は週 1 回の実行でしか出ない。PR で境界のファイルを改名・削除しても、その PR の CI は緑のまま、翌週に初めて赤になる、という遅れが生じる。
  合否を持つ部分はそれを待たず、**PR の CI で流す**: 設定の宣言（対象のパッケージ・境界のファイル）と実体を、ADR-0014 決定 1・3 の形で**両方向に照合する自己テスト**を `scripts/` に置く。
  次を見る: 宣言のパッケージ・ファイルがすべて実在する（実体の権威は `pnpm -r list --depth -1 --json` と `git ls-files`）／
  **母集団はワークスペースの全パッケージ**（`pnpm -r list --depth -1 --json`。apps・bun のアプリ・`e2e` を含む。vitest に限らない）で、
  それぞれが「範囲に入れた（方式つき）」か「範囲に入れない（理由つきの除外）」のどちらか一方に宣言されていて全単射になる
  （新しいパッケージを足して宣言し忘れると落ちる。除外の対象が実在しなくなっても落ちる。ADR-0014 決定 1・2）／
  内訳に空が無い（決定 8）／ワークフローに `schedule` と `workflow_dispatch` があり、`ci.yml` が Stryker を呼ばない。
  この自己テストは `scripts/` の既存の `node --test` の経路で、CI の **`quality` ジョブ**の「scripts の自己テスト」のステップに載り、手書きの変異で壊して確かめる（原則 VII）。
  そのステップは `steps.scope.outputs.code == 'true'` のときだけ走る。範囲の判定（`scripts/lib/ci-scope.mjs` の `decideScope`）は、変わったファイルがすべて `.md` のときだけ `code: false` にする（差分が空なら `true`）。
  つまり **`.md` 以外のファイルを 1 つでも変える PR では走り**、`.md` だけの PR では走らない
  これで、PR の時点で宣言と実体のずれが赤になり、週次の実行が静かに何も見なくなる経路を塞ぐ
- 比較・確かめ直し・要約を作る自前のコードは `scripts/` に置き、自己テストと手書きの変異で守る（原則 I・VII。`scripts/` 配下は変異検査の対象。`docs/guides/development.md`）。
  調査のスクリプト（`2026-11-01-test-gap-survey/` の `stryker-run.sh`・`stryker-summary.mjs`・`recheck-*.mjs`）は検査ではなく測り直し用の記録で、
  実装ではそれを下敷きに書き直す（記録の側は変えない）

**知らせる経路の比較。**

| 案 | 得 | 失 | 判断 |
|---|---|---|---|
| 要約と artifact だけ | 権限が `contents: read` で済む | 通知が無く読まれない。`schedule` が止まっても気づけない。記録は 90 日で消える | 退ける |
| **追跡用の ISSUE 1 件に要約をコメント** | 購読者へ通知が届く。履歴が残る。コメントが来ない週で、止まったことに気づける | `issues: write` を 1 つのジョブに持つ（別ジョブ・書き先 1 件に限る） | **採る** |
| 新しい生き残りごとに ISSUE を自動で起票 | 取りこぼさない | 初回に数百件。等価なものが溜まる。依頼に無い投稿を大量に行う（ADR-0030 決定 1）。ADR-0024 が退けた「同じ通知の反復」になる | 退ける |

### 6. 費用: 1 回約 30 分＋確かめ直しの枠 40 分、週 1 回

**数字は見積もり**で、調査の数字（2.3。4 並列）からの計算である。runner（`ubuntu-latest`）は 4 vCPU（`ci.yml` の記述）で、調査の環境と同じとは限らない。

| 段 | 見積もり | 根拠 |
|---|---|---|
| core 9 パッケージ | 約 12 分（726 秒） | 2.3 の合計。room-core 281 秒・timer-core 126 秒が大きい |
| sync-client・dev-hub-redirect・markdown | 約 1〜3 分 | 行数が core の約 1 割、`sync-client` は jsdom（調査では測っていない。**初回で測る**） |
| tasuki-sync の境界 3 ファイル | 約 10 分（574 秒） | 2.3 |
| 準備（checkout・`pnpm install`・bun） | 3〜5 分 | 他のジョブの実測の概算 |
| **Stryker の段の合計（準備を含む）** | **約 30 分** | 12 + 2 + 10 + 3〜5 |
| 確かめ直しの段 | **40 分の枠**（3 本並列で約 100 件の見積もり） | 調査 2.5 の 100 件・2,308 秒 |
| 最悪の合計 | 約 70 分 | `timeout-minutes` は 120 分とする |

- **「所要」の意味を決める。** 見直す条件の「50 分」は、**確かめ直しの段を含まない Stryker の段（準備を含む）の所要**を指す。
  確かめ直しは 40 分の枠を持つ固定の段で、所要の基準に含めない。初回も同じ基準で数える（初回は Stryker の段が約 30 分、確かめ直しが枠いっぱいで、合計約 70 分。基準の 50 分は踏まない）
- 調査と同じ条件（`concurrency: 4`・`timeoutMS: 10000`）で流す。**実装の 1 回目で測り、この表を ADR の追記で直す**
- 週 1 回 ≒ 年 52 回 × 約 30 分（確かめ直しを除く）≒ 年約 26 時間。公開リポジトリでは Actions の分を数えない（ADR-0029 の影響）。非公開に変えるときは見積もり直す
- Stryker の段が 50 分に近づいたら、パッケージごとに分ける（`matrix`）。手書きの変異のシャードと同じ考え方で、`timeout-minutes` を上げて済ませない
- 変異の数は、コードが増えるほど増える。核のパッケージの行数は約 8,800 行で、手書きの変異ほどの勢いでは増えない見込みだが、**測っていない**。実装の 1 回目からの推移で見る

## 影響

- ルートの `package.json` と `pnpm-lock.yaml` に Stryker の 2 つ（と推移依存）が入る（`packages` のエントリは 405 → 514 の見込み。実測は決定 1）。Renovate の更新は既存の規則に乗る
  （minor・patch は束ね、major は承認制）。推移依存の勧告の手間が増える（決定 1）
- **新しいワークフロー（`mutation-survey.yml`）と、`scripts/` の定期の調査の実体、Stryker の設定、設定の照合の自己テスト、追跡用の ISSUE、処置の記録のファイルを足す**。
  `ci.yml` は変えない。CI の必須チェックと変異のシャードは変わらない。`quality` ジョブに足す自己テストは、`scripts/` の既存の経路で流れ、実行は軽い。ただしコストは別にある: **ワークスペースにパッケージを足す PR は、範囲に入れるか理由つきで除外するかの宣言の更新を必ず求められる**（宣言し忘れると `quality` が赤になる）
- 毎週 1 回、人が結果を読む仕事が増える。**読まれなければ価値が無い**。見直す条件に、読まれなかったときの外し方を置いた
- 定期の実行が緑でも、生き残りがあるとは限らないし、無いとも限らない。「要約のコメントを読む」ことが規則であって、緑の色は規則を守った証拠ではない

## やらないこと

- **自動の変異の結果で、CI の合否にしない**。生存率の下限・PR のたびの実行・必須チェックへの追加をしない（決定 2・5）
- **生き残りをすべて潰さない**。等価なもの・境界のテストが守るもの・文言は潰さない。確かめ直して残った等価でないものを、ISSUE ごとに扱う（#561 のスコープ外）
- **生き残りごとの ISSUE を自動で作らない**。ワークフローが書くのは追跡用の 1 件の ISSUE への要約のコメントだけ（決定 5）
- **apps の web と、tasuki-sync の全体にはかけない**（決定 3）
- **Stryker を `pnpm test`・`pnpm check:fast`・`pnpm check:full` に入れない**。速い段にも全件の段にも載せない（`docs/guides/development.md` の段の表）
- **sandbox で落ちるテストを直さない**（決定 4。別の ISSUE）
- E2E の `--repeat-each` の測り直しと、保留の候補（axe・状態遷移のテスト）は #561 のスコープ外

## 見直す条件

次のどれかに当たったら、本 ADR を Superseded にして書き直す（または追記で直す）。

- **読まれなかったとき**: 定期の実行が 13 回（約 3 か月）続いて、結果から起こした ISSUE・テスト・手書きの変異が 1 件も無いとき。まず間隔を伸ばし（月 1 回など）、それでも無ければ依存を外す
  （外すのは検査を弱める変更に当たらない。調査は検査でなく、合否を持たない。それでも人の承認を待つ）
- **未対応が溜まり続けたとき**: 処置の無い `confirmed` が 4 週続けて増え、減る週が無いとき。範囲を狭めるか間隔を伸ばす（ADR-0024 の「同じ通知の反復」に当たる状態）。
  **初回の消化の間は数えない**: 初回の `unchecked`（決定 5 の約 3 回の実行）が 0 になるまでは `confirmed` が増えるのが正常なので、数える起点は `unchecked` が 0 になった最初の実行とする
- **Stryker の段の所要が 50 分を超えたとき**（確かめ直しを含まない。決定 6）: パッケージごとに分ける（`matrix`）か、範囲を絞る
- **Stryker の依存が重いと分かったとき**: 決定 1 の基準（`mutation (k)` の最長が直近 5 回の範囲を超え、install の増えが原因）を満たすとき、`trustPolicy` や `minimumReleaseAge` で更新が詰まり続けるとき、Stryker の勧告の手間が続くとき。決定 1 の案 C（別ディレクトリの固定 lockfile）へ移す
- **web に価値があると分かったとき**: web の計算を持つファイルを 1 回測って、等価でない生き残りが多いと分かったとき。そのファイルだけ範囲に足す
- **`invite-ui`・`web-kit` を測ったとき**: 1 回測って、等価でない生き残りが多いと分かったら範囲に足す（決定 3）
- **bun の runner が出たとき・テストを絞れるようになったとき**: tasuki-sync の範囲を広げる
- 定期の実行が 2 回続けて走っていない（ワークフローが無効になった・`schedule` が止まった。追跡用 ISSUE にコメントが来ない）とき
- リポジトリを非公開に変えるとき（Actions の分の見積もり。決定 6）
