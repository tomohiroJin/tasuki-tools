## 背景

ファシリテーター・ルーレットは、お題に対する進行役を、誰かの遠慮や押し付けではなくその場で決める道具である。
ルームの全員の画面で同じ円盤が回り、同じ人のところで止まる。全員が一周するまで同じ人は選ばれない。

共通ルーム（#95）で、ルーム・参加者・在席・参加の入口・合言葉の関門・レート制限は共有できる状態にある。
お題（#91）が同じ形で足され、新しいサーバーを立てずに接続の種類（`?tool=`）だけで機能を足せることが分かっている。

実測と経緯の正本は設計正本に置く。ここには決定だけを書く。

## 決定

### 決定 1（R1・R3）: 共通ルームの一機能として足し、規則は 5 つ目の文脈 `packages/roulette-core` に置く

新しいサーバーは立てない。接続の種類 `?tool=roulette` を足し、お題と同じ形の専用のメッセージ層を持つ。
`roulette-core` は **`room-core` を含むどの `@tasuki/*` にも依存しない（MUST NOT）**。参加者 ID は不透明な文字列で、
名簿の断片はアプリ層が引数で渡す（`docs/adr/0017` 決定 1・2）。依存の向きの正本は
`scripts/audit-dependency-direction.mjs` の `ALLOWED` とする。

### 決定 2（R4）: 乱数の権威はサーバーである

回す要求を受けたサーバーが当たりを決め、円盤の並び・当たりの位置・止まる位置の揺らぎを全接続へ同じフレームで配る。
web は乱数を引かない。乱数源は `node:crypto` の `randomInt`（偏りが無い）をポート越しに渡し、
ドメインは環境から値を読まない（`scripts/audit-domain-side-effects.mjs`）。

### 決定 3（R5）: 配るのは絶対時刻ではなく「経過」である

フレームは `durationMs` と、**送る時点で計った** `elapsedMs` を持つ。端末の時計は数秒ずれうるので、
絶対時刻を配ると止まる時刻がずれる。経過で配れば、ずれは配送の遅れだけになる。途中で入った人・再接続した人にも
送る時点の経過が届くので、同じ場所から合流できる。回した時刻（`startedAt`）は単調時計の値で、**wire に載せない（MUST NOT）**。

### 決定 4（R6）: 公平性の既定は「一周するまで同じ人を選ばない」

当たりは「この一周でまだ選ばれていない人」から一様に引く。全員が選ばれたら一周を閉じ、**新しい一周の最初には
直前の当たりを入れない**（入る人が 2 人以上のとき）。周の境目で同じ人が 2 回続くのを防ぐ。

### 決定 5（R14）: 名簿をルーレットの接続にも配る。ルーレットの状態に名簿を埋め込まない

入る人の計算に在室が要る。名簿の配信は `saveRoster` に 1 本化されているので、宛先を足すだけで接続の着脱・退出の
すべてが届く。ルーレットのフレームに名簿を写すと経路が 2 本になる。お題の `topic` フレームもルーレットの接続に配る（R15）。

### 決定 6（R16）: 表現は直接遷移関数 ＋ `Result` を採る

`docs/adr/0016` 決定 1 が MUST とする「どちらを採ったかと理由の記録」がこれである。状態は小さく
（外した人・足した名前・この一周で選ばれた人・最後の 1 回）、イベントの履歴・再生・段階適用の要求が無い。
Decider を採る根拠が無い（`docs/adr/0007` 基準 3）。`room-core`・`topic-core` と同じ。

### 決定 7（R11）: ルーレットを操作できるのはルーレットの接続だけである

ルーレットのコマンドはハブ・timer・poker・お題のスキーマに含めない。さらに、ハンドラは
「**ルーレットとして**在席しているか」を名簿で確かめる（2 段目の守り）。**ルーレットの接続の受理は `onConnect` を通す（MUST）**
—— `ws-adapter.ts` の poker の早期 return に足すと、参加の失敗の積算が接続 ID に落ち、総当たりが張り直しで枠を回避できる。
共通の処理（`handlers.ts`）にツール別の可否判定を戻さない（MUST NOT）。

### 決定 8（R13）: 足した名前の同名判定は参加と同じ関数を引数で受け、後から来た在室者を勝たせる

足した名前（ゲスト）が同じ名前かどうかは、参加・改名・代理追加の重複拒否と**同じ関数・同じキー**
（`room-core` の `conflictsWithExisting`）で決める（MUST）。`roulette-core` は `room-core` に依存しない（決定 1）ので、
判定を写さず、型 `NameConflict` の関数として引数で受ける（乱数を引数で受けるのと同じ形）。同期サーバーと web が
同じ関数を渡す。見え方の骨格（`nameSkeleton`）では拒まない（`room-core` の「拒否は厳格に」）。

足した後で同じ名前の人が参加・改名したら、参加や改名は拒まず（他のツールへ波及する）、**入る人の段（`poolOf`）で
ゲストを外す（在室者が勝つ）**。状態からゲストは消さない。外れている印はルーレットのフレームに載せず、web が名簿と
同じ `poolOf` から導く（決定 5 と同じ理由）。退けた案と細部は設計正本 §5.1「R13 の判定」にある。

## 却下した案

| 案 | 退けた理由 |
|---|---|
| X2 各画面が乱数を引き、最初に引いた人の結果を配る | 「誰の結果を正とするか」の調停が要り、同時に 2 人が押すと割れる。役割（ホスト）は #95 で廃止した |
| X3 後から検証できる抽選（種のハッシュを先に配る） | 守る相手が居ない。コード・wire・テストが倍になる割に、利用者が得るものが無い。揮発インメモリなので検証の記録も残らない |
| X4 止まる絶対時刻（`stopsAt`）を配る | 決定 3。ルーレットの接続にも往復の測定が要る |
| X5 一様乱数（毎回全員から引く） | 「同じ人ばかり当たり続けない」を確率でしか守れない。4 人で同じ人が 3 回続く確率は 1/16 |
| X6 重み付け（選ばれた回数が少ない人ほど当たりやすい） | 回数の帳簿がルームの寿命いっぱい要り、途中で入った人の扱いを決める必要がある。一周の規則のほうが説明が 1 文で済む |

## 影響

- ルームの持ち物に、お題に続いてルーレットの状態が加わる。ルームの破棄（`destroy-room.ts`）が一緒に消す。
  状態は揮発インメモリで、再起動で一周の記録も最後の結果も消える（`docs/timer/adr/0007`）
- 名簿の配信先が「ハブ」から「ハブ ＋ ルーレット」に広がる。`hubRecipientsOf` の意味（ハブ）は変えず、
  `rosterRecipientsOf` として名前で分けた
- お題の配信先（`TOPIC_RECIPIENT_TOOLS`）にルーレットが加わる
- **配布の順序**: PR 1 だけを本番へ配っても、ルーレットの接続を張る web が無いので利用者に見える変化は無い。
  配布は PR 3 まで入れてから 1 回で行う（設計正本 §7）
