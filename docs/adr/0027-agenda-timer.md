## 背景

進行タイマーは、会の進行表（名前と長さを持つステップの並び）をルームの全員で同じ盤に映し、
いまのステップの残りと、会全体が予定より押しているか巻いているかを見せる道具である。最初に使う場面は
KPT のふりかえりで、約束の 1 時間に収まっているかを、会の最中に全員が同じ数字で確かめられることを目指す。

共通ルーム（#95）・お題（#91）・ルーレット（#94）で、新しいサーバーを立てずに接続の種類（`?tool=`）だけで
ツールを足せることが分かっている。一方で、進行タイマーは「時間が来たら次へ移る」をルームの側で決める必要があり、
既存の timer の期限の予約（`apps/tasuki-sync/src/application/schedule.ts` の `Scheduler`）は timer 専用の形をしている。

実測と経緯の正本は設計正本に置く。ここには決定だけを書く。

## 決定

### 決定 1（J1）: 独立したツールとして足し、規則は 6 つ目の文脈 `packages/agenda-core` に置く

timer のモードにはしない。timer はモブプロの交代の輪が中心で、ステップの並びとは形が違う。
新しいサーバーは立てず、接続の種類 `?tool=agenda` を足す（PR 2 で入れた。綴りの正本は
`apps/tasuki-sync/src/application/tool-id.ts`）。

`agenda-core` は **`room-core` を含むどの `@tasuki/*` にも依存しない（MUST NOT）**（`docs/adr/0026` 決定 1 と同じ）。
依存は `valibot` と `neverthrow` だけで、依存の向きの正本は `scripts/audit-dependency-direction.mjs` の `ALLOWED` とする
（PR 1 で `packages/agenda-core` を空の許可で登録した）。

### 決定 2（設計正本 §4.4・§5.2）: 自動で次へ移す判断はサーバーが行い、期限は agenda 専用の予約と単調時計で測る

「自動で次へ」のステップが時間切れになったときに次へ移す判断は、**サーバーが行う（MUST）**。画面ごとに判断すると、
閉じている画面・遅れている画面で割れる。

- **ドメインが持つもの（PR 1 で入れた）**: 期限は `deadlineOf`（計時が持ち時間に達する時刻。動いているときだけ値を持つ）、
  移す処理は `advanceIfDue`。移った次のステップは**期限の時刻ちょうどに始まったものとして記録する**（発火の遅れを持ち込まない）。
  次も期限を過ぎていれば続けて移す。時計は引数で受け、ドメインは環境から値を読まない
- **サーバーが持つもの（PR 2 で入れた）**: 期限の予約は **agenda 専用に持つ（MUST）**。`Scheduler` はサーバー全体で
  1 つのインスタンスがルームのコードを鍵に予約を上書きするので、共有すると同じルームの timer と agenda が互いの予約を消す。
  `Scheduler` の「長い単発の待ちを短く区切り、毎回残りを計算し直す」自己補正の考え方は写す
- **サーバーでの経過・期限はすべて `MonotonicClock` で測る（MUST）。** `WallClock` は NTP の調整で戻りうるので、
  agenda の計測に使わない（MUST NOT）
- 予約は一時停止・再開・延長・次へ・飛ばす・最初から・ルームの破棄で張り直す／消す。**ルームの破棄
  （`application/destroy-room.ts`）へ渡す agenda の状態と予約は必須の依存にする（MUST）**（省略可にすると、
  配線から落ちてもテストが緑のまま残る）
- **操作を当てる前にも `advanceIfDue` を通す（MUST・PR #431 のレビューで足した）。** 予約の発火は遅れうるので、
  期限を過ぎてから発火するまでの隙に届いた操作は、自動で次へ移した後の状態に当てる（古い区切りに当てると、所要が
  持ち時間を超えて確定し、一時停止なら終わったはずの区切りで止まる）。操作が拒まれても、移した分は保管して配る
  （変異 m451）

### 決定 3（J9）: 画面へは絶対時刻ではなく「経過」を配る

ルーレットの決定 3（`docs/adr/0026`）と同じ形を採る。フレームは**送る時点で計った**経過を持つ
—— 実時間の経過（`runElapsedMs`）・いまのステップの計時（`stepTimerMs`）・いまのステップの所要（`stepSpentMs`）。
開始の瞬間・`runningSince` などの**単調時計の値は wire に載せない（MUST NOT）**。写しを作るのは `toView`（`now` を受けて経過を計る）で、
画面は受け取ってからの経過を足して描く（`advanceView`）。終了見込みの時刻は端末の時計に足して出し、数秒のずれは表示上受容する。
**フレームの時間切れの振る舞い（`onTimeout`）は開いた文字列で受け、知らない値は「押すまで待つ」として読む**（後方互換のため。コマンドとシナリオの入力は列挙のまま。2026-10-21 の最終レビュー M-2・設計正本 §12.5）。

### 決定 4（設計正本 §4.6）: 進行の操作はステップの ID で指し、いまのステップと違う ID の操作は何もしない

次へ・延長・飛ばす／戻すは、**どのステップに対する操作かをステップの ID で持つ（MUST）**。位置（添字）では指さない。
いまのステップと違う ID の「次へ」「延長」は**何もせず成功として扱う**（`next`・`extend` は同じ参照を `ok` で返す）。
2 人がほぼ同時に「次へ」を押しても、自動で次へ移った直後に古い画面の「次へ」が届いても、進むのは 1 つだけになる。
状態が変わらないときは同じ参照を返すので、サーバーは参照の比較で「全員へ配るか、送り主にだけ返すか」を決められる
（送り主にだけいまの全体を返す配線は PR 2 で入れた）。

ID は置き換えの時点の並び順で採番する（`expand`）。後続の段で進行中にステップを足しても、既存の ID と操作は壊れない。

### 決定 5（設計正本 §5.1）: 長さは秒の整数で持ち、定義（シナリオ）と展開済みの並びを分ける

- **長さは core・wire・保存のすべてで秒の整数で持つ（MUST）。** 第 1 段の入力は分の整数に絞るが、その絞りは境界の検証
  （`StepInputSchema`）にだけ置く。後続の段で刻みを細かくしても、検証を緩めるだけで wire と保存の形は変わらない
- **シナリオ（`ScenarioInput`）と展開済みの並び（`PlannedStep[]`）を分け、進行の遷移はすべて後者の上で行う。**
  展開は `expand` が担う。第 1 段では写すだけだが、後続の段で繰り返しの組を足すときは `expand` と検証だけが変わる。
  繰り返しの型そのものは先取りしない（`docs/adr/0007`）
- 上限の値の正本は `packages/agenda-core/src/limits.ts` とする。ここへ数値を写さない

### 決定 6（J5）: 一時停止の間も実時間の経過は進み、一時停止はそのステップの所要に含める

一時停止で止まるのはステップの計時（残り）だけで、実時間の経過は進む。したがって**止めている間も押しは増える**。
約束しているのは実際の時計の 1 時間なので、隠さない。一時停止の時間はそのステップの所要に含める。

不変条件「終えたステップの所要の合計 ＋ いまのステップの所要 ＝ 実時間の経過」をドメインが守り、
性質テスト（`packages/agenda-core/tests/agenda-invariant.test.ts`）が固定している。終了の一覧（`summaryOf`）は
この等式が成り立つ数字だけを出す。一時停止中に「次へ」を押すと、次のステップは動いている状態で始まる（J19）。

### 決定 7: 表現は直接遷移関数 ＋ `Result` を採る

`docs/adr/0016` 決定 1 が MUST とする「どちらを採ったかと理由の記録」がこれである。状態は小さく
（展開済みの並び・いまのステップ・計時の基準）、イベントの履歴・再生・段階適用の要求が無い。Decider を採る根拠が無い
（`docs/adr/0007` 基準 3）。`room-core`・`topic-core`・`roulette-core` と同じ。遷移（`replaceScenario`・`start`・`next`・
`pause`・`resume`・`extend`・`setSkipped`・`reset`）は `Result` を返し、エラー値は判別子 `code` だけを持つ
（`AgendaError`。`scripts/audit-domain-error-shape.mjs` に登録した）。期限による遷移（`advanceIfDue`）は拒む場合が無いので状態をそのまま返す。

### 決定 8: 進行タイマーを操作できるのは agenda の接続だけである

`docs/adr/0026` 決定 7 と同じ。**agenda のコマンドは agenda の接続のスキーマ（`AgendaCommandSchema`）にだけ置く（MUST）。**
ハブ・timer・poker・お題・ルーレットのスキーマに含めない。コマンドは `v.strictObject` で余剰フィールドを拒む。
受けるフレーム（`AgendaFrameSchema`）は非 strict にする（後続の段で項目を足しても古い画面がフレームごと捨てない）。

**PR 2 で入れた**: ハンドラは「agenda として在席しているか」を名簿で確かめる（2 段目の守り）。**agenda の接続の受理は
`onConnect` を通す（MUST）**（通さないと参加の失敗の積算が接続 ID に落ち、総当たりが張り直しで枠を回避できる）。
共通の処理にツール別の可否判定を戻さない（MUST NOT）。

### 決定 9: お題のフレームを agenda の接続にも配る

`docs/adr/0021` 決定 2（宛先はツールを問わない）に従う。**PR 2 で** お題の配信先（`application/topic-broadcast.ts` の
`TOPIC_RECIPIENT_TOOLS`）に agenda を足した。agenda の画面は agenda 固有のスキーマより先に `TopicFrameSchema` で見分ける（同決定の MUST。PR 3 で
`apps/agenda-web/src/server-message.ts` に入れた）。第 1 段の画面はお題を受けて保持するが、表示はしない（実装の判断。設計正本 §12）。

### 決定 10（#429 第 2 段・設計 §5.5）: 繰り返しは「シナリオ全体 × 回数」で表し、展開の段で平らに並べる

- **繰り返しは、シナリオ全体に回数を掛ける形で表す（MUST）。** 回数は `ScenarioInput` の任意の項目で、展開（`expand`）がステップの並びを回数ぶん平らに並べる。
  決定 5 の継ぎ目（定義と展開済みの並びを分け、後続の段では `expand` と検証だけが変わる）をそのとおりに使う
- **進行の遷移は展開済みの並びの上でだけ動く（MUST）。** 遷移・計時・期限・終了の一覧は回数を知らない。回の見出しは展開済みの各ステップが持つ回の番号から画面が組む
- **回数の省略は 1 とみなす（MUST）。回数 1 のときは回数のキーを送らない（MUST）。** コマンドもフレームも同じ。
  回数 1 の送信形は第 1 段と同一なので、古い同期サーバー（strict）が拒むのは回数 2 以上のときだけになる。配布の順は同期サーバー（`deploy.sh timer`）が先、画面（`deploy.sh agenda`）が後
- 回数の上限・展開後の区切り・予定の合計の上限の値の正本は `packages/agenda-core/src/limits.ts` とする。ここへ数値を写さない（決定 5 と同じ）

## 却下した案

| 案 | 退けた理由 |
|---|---|
| timer のモードとして足す | timer はモブプロの交代の輪が中心で、ステップの並びとは形が違う。モードの分岐が timer の集約に入り込む（決定 1） |
| timer の `Scheduler` を共有する | サーバー全体で 1 つのインスタンスが、ルームのコードを鍵に予約を上書きする。同じルームの timer と agenda が互いの予約を消す。期限も `WallClock` で測っている（決定 2） |
| 期限を `WallClock` で測る | NTP の調整で時計が戻りうる。間隔の計測に使うと、期限が伸び縮みする（決定 2） |
| 絶対時刻（`endsAt`）を配る | 端末の時計は数秒ずれうるので、終わる時刻がずれる。往復の測定も要る。経過を配れば、ずれは配送の遅れだけになる（決定 3） |
| 位置（添字）で操作を指す | 自動で次へ移った直後に古い画面の「次へ」が届くと、意図しない 2 つ目が進む。後続の段で進行中にステップを足すと位置がずれる（決定 4） |
| 延長したぶんを後ろのステップ（予備など）から自動で削る（J17） | 削るかどうかはチームが「飛ばす」で決める。道具は進み具合とオーバーを見せることに徹する |
| 部分の繰り返し（ステップの一部だけを回す入れ子の組） | 型と画面が入れ子になり、進行表の見せ方・押し巻きの数え方・終了の一覧の組み方が増える。朝会と LT 会は「シナリオ全体 × 回数」で足りる（決定 10） |
| 回ごとの担当者 | 人の名前の持ち方（データ分類・名簿との関係）を新しく決めることになる。利用者の要望は一定の繰り返しで、担当の割り当ては範囲外（決定 10） |

## 影響

- ルームの持ち物に、お題・ルーレットに続いて進行の状態が加わる（PR 2）。状態は揮発インメモリで、再起動・デプロイ・アイドルの破棄で
  進行も終了の一覧も消える（`docs/timer/adr/0007`）。シナリオは保存した端末から読み直せる（画面の保存は PR 3 で入れた。`apps/agenda-web/src/storage/saved-scenarios.ts`）
- **データ分類**: ステップの名前・会の名前は利用者由来のテキストで、人の名前が入りうる。`docs/adr/0011` 決定 1 の
  「個人に紐づく」に置いた（J18。同 ADR の 2026-10-20 の追記）。ハンドラはログを書かず、名前をログの語彙に載せない
- **コマンドの頻度の上限は設けない**（J16）。お題の `topic.set`・ルーレットと同じ扱いで、効くのはメッセージの大きさの上限と
  定義の上限（`limits.ts`）である。経緯は `docs/adr/0011` の 2026-10-20 の追記
- **配布の順序**: PR 1 だけを本番へ配っても、agenda の接続を張るサーバーの経路も画面も無いので利用者に見える変化は無い。
  配布は PR 4 まで入れてから 1 回で行う（設計正本 §9）
