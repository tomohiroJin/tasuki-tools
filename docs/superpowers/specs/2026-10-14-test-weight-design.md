## 1. 目的

**実装中の手元の待ちを短くする。** 1 つのタスクを直すたびに、触っていない所の変異まで全件流し直す待ちをやめる。

利用者の判断（2026-10-14 の対話）:

- 一番つらいのは**実装中の手元の待ち**（PR 後の CI の待ちより優先）
- **CI は全件のまま安全網として残す**。手元は触った所だけを流し、漏れは CI が拾う
- E2E の同期サーバーのルーム枠は**E2E のときだけ広げる**（本番の値は変えない）

## 2. 実測した事実（Issue 本文の前提との差）

| 本文の前提 | 2026-10-14 の実態 | 確かめた方法 |
|---|---|---|
| 手元の E2E 全件が約 10 分 | **手元は 128 件で 1.3 分**（16 workers・turbo 経由の `pnpm e2e` で 86 秒・ビルドはキャッシュに当たった） | `playwright test --reporter=list,json` と `pnpm e2e` を素の main で実行 |

## 3. 範囲

### この設計で行うこと

1. `mutation-check.mjs` に**選んで流す指定**（`--changed` / `--id` / `--pkg`）を足す
2. **対照実行の重複を省く**（全件の実行にも効く）
3. 実行の最後に**所要時間と件数**を出す（計画の見積もりの根拠にする）
4. E2E の同期サーバーにだけ**ルーム枠を広げて渡す**
5. 開発の手引きに**段ごとに何を流すか**を書く

### やらないこと

- **CI の流し方は変えない**（変異も E2E も全件のまま）。CI の `quality` の約 10 分はこの設計では縮める対象ではない（対照実行の重複を省いた分だけは縮む）
- **変異の並列化**（一時 worktree で当てる形）は行わない。worktree ごとに依存の入れ直しが要り（9p の罠）、復元・ロック・残骸回収の機構を作り直すことになる。手元の「触った所だけ」は §4 の選び方で足りる
- **パッケージ間の依存をたどる選び方**は作らない（例: `room-core` を変えたときに `tasuki-sync` の変異を選ぶ）。漏れは CI の全件が拾う（原則 X）
- **E2E の選んで流す仕組み**は作らない。手元の全件が 1.3 分で、絞りたいときは Playwright にファイルを渡せば足りる
- **E2E の長い 2 件の分割**はしない。1.3 分を 1 分にする効き目は小さい
- `ci-scope.mjs` は触らない

## 4. 決定

### 4.1 変異検査の指定

```bash
node scripts/mutation-check.mjs                     # 全件（今と同じ。CI はこれ）
node scripts/mutation-check.mjs --changed           # origin/main との差分から選ぶ
node scripts/mutation-check.mjs --id 150,151        # 番号で選ぶ
node scripts/mutation-check.mjs --pkg apps/roulette-web
node scripts/mutation-check.mjs --changed --base HEAD~1   # 基準を変える（--changed と一緒にだけ）
```

- 選び方の指定（`--changed` / `--id` / `--pkg`）は **1 回に 1 つ**。2 つ以上を混ぜたらエラーで止める（組み合わせの意味を決めない）
- 既存の `--full` とは組み合わせられる（選んだ変異を、パッケージ全体のテストで流す）
- `--id` に存在しない番号が入っていたらエラーで止める（打ち間違いで 0 件の緑にしない）
- `--pkg` に該当する変異が 0 件なら、エラーで止める（同じ理由。`--pkg` は「このパッケージの変異を流したい」という意図なので、0 件は打ち間違いである）
- `--base <ref>` で `--changed` の基準を変えられる（既定は `origin/main`）。変異検査の機構そのものを変える枝は、`origin/main` を基準にすると常に全件へ倒れるため（2026-10-14 の計画で追補）
- **知らない指定はエラーで止める**（`--help` を含む）。以前は `--full` 以外を黙って無視し、打ち間違いで全件が走った（2026-10-14 の計画で追補）

### 4.2 `--changed` の選び方

**差分**: `git merge-base <基準> HEAD`（基準の既定は `origin/main`）から `HEAD` までのコミット済みの変更ファイル。`--no-renames` で改名の両側を拾う。
作業ツリーが汚れていれば今でも実行を拒むので、未コミット分を考える必要はない。

**変異を選ぶ条件**（いずれか 1 つに当たれば選ぶ）:

1. 差分に、その変異の `pkg` 配下のファイルがある（**パッケージ単位で多めに選ぶ**）
2. 差分に、そのパッチが触るファイルがある（`pkg` の外を変異させる場合への備え）
3. 差分に、そのパッチのファイル自体がある

**全件に倒す条件**（迷ったら多く流す。`ci-scope.mjs` と同じ fail-open の向き）:

- 差分に**変異検査の機構**が入っている。機構とは `scripts/mutation-check.mjs` と、それが import する `scripts/lib/*.mjs` である
  - 機構のファイルの一覧はコードに列挙せず、`mutation-check.mjs` の import 文から導く（列挙は腐る）
- 差分が取れない（`origin/main` が無い・merge-base が無い・git が失敗した）

**0 件のとき**: 「0 件。この差分に該当する変異はありません」と出して**終了コード 0** で終わる。
`--changed` の 0 件は正常な結果である（docs だけの枝など）。

**選び方の性質（設計として受け入れる漏れ）**: 条件 1〜3 は「その変異の検出力が変わりうる変更」を
**同じパッケージの中でだけ**拾う。別パッケージの変更（共有パッケージの型・依存の更新・設定）で
検出力が変わる場合は拾わない。これは CI の全件が拾う。

### 4.3 対照実行の重複を省く

1 回の実行の中で、**cwd とコマンドが同じ対照実行**は最初の 1 回の結果を使い回す。

- 根拠: 各変異の後に、作業ツリーが HEAD に戻ったことを `isRestoredToHead` で確かめている。
  確かめられなければ実行は止まる。したがって 2 回目以降の対照実行は、同じ木の上で同じコマンドを流すことになる
- 失うもの: 対照実行は、テストのフレーキーさを変異ごとに浴びる機会でもあった。使い回すと、
  変異を当てた後の実行だけがフレーキーに落ちて「検出」と数えられる余地が、わずかに増える。
  ただし今の形でも、対照が通った直後の本番の実行がフレーキーに落ちれば「検出」になるので、
  この穴は今もある。新しく開くものではない
- 見込み: vitest の対照実行は全件で約 220 秒あり、その大半が重複である。CI の全件で 3〜4 分縮む見込み（推測。PR 1 で実測する）

### 4.4 結果の表示

- 表題に**絞り込み実行であること**を出す: `絞り込み実行（--changed）: 153 件中 18 件`。全件の緑と取り違えないため
- `--changed` では、選んだ理由を変異ごとに 1 行で出す（どの条件に当たったか）
- 最後に**所要時間**（全体・対照実行の合計・使い回した回数）を出す

### 4.5 E2E のルーム枠

- `e2e/harness/sync.ts` が同期サーバーを起動するときに、`MAX_ROOMS` を env で渡す（値は 1000 を想定。PR 2 で決める）
- **本番の既定（`apps/tasuki-sync/src/config.ts` の 100）と、単体テストの `TEST_MAX_ROOMS` は変えない**
- 枠いっぱいの挙動を E2E で確かめている spec は無い（`e2e/` を `MAX_ROOMS` / `maxRooms` / `ルーム枠` で検索した。
  ヒットは「枠が逼迫しているので 1 室にまとめた」という注釈だけ）
- spec の「枠 100 ぎりぎり」の注釈（`layout` / `roulette` / `topic` / `timer-a11y`）を直す。
  **畳んだ検査をほどき直すことはしない**（動いている検査を触る理由が無い）
- `timer.spec.ts` の「`maxRooms`（既定 50）」という古い記述も、この機会に直す

### 4.6 進め方（開発の手引き）

`docs/guides/development.md` に、段ごとに何を流すかの表を足す。

| 段 | 変異検査 | E2E |
|---|---|---|
| 実装中（タスクごと） | `--changed`、または `--pkg <触ったパッケージ>` | 触った画面の spec だけ（Playwright にファイルを渡す） |
| PR を出す前 | `--changed` | 全件 |
| CI（変えない） | 全件 | 全件 |

- **手引きに実測の秒数は書かない**（腐る）。計画の見積もりは、直前の実行が §4.4 で出した所要時間を根拠にする
- `AGENTS.md` のコマンド一覧の `mutation-check` の行に、絞り込みの指定を書き足す
- Issue #387 の本文の「手元の E2E が約 10 分」は、§2 の実測をコメントで残して正す

### 退けた案

| 案 | 退けた理由 |
|---|---|
| CI も差分で絞る | 選び方の正しさが品質の要になり、選び方自体に検査が要る。このリポジトリは「検査自身の抜け穴」を繰り返し踏んでいる。利用者は「CI は全件のまま」を選んだ |
| 一時 worktree で並列に当てる | §3「やらないこと」のとおり。費用（依存の入れ直し・復元機構の作り直し）が手元の効き目に見合わない |
| `--id` / `--pkg` だけ足す（選び方を作らない） | 何を流すかを人が毎回書くことになり、選び忘れが起きやすい。`--changed` の費用は純粋関数 1 つで小さい |
| E2E にも「アプリ → spec」の対応表を作る | 手元の全件が 1.3 分で、困っていない（原則 X） |

## 5. 設計

### 5.1 `scripts/lib/mutation-select.mjs`（新設・純粋関数）

入出力は git にも fs にも触らない。呼び出し側が材料を渡す。

```js
/**
 * @param {object[]} mutations   MUTATIONS（id・pkg・patch を読む）
 * @param {object}   selector    { kind: "all" } | { kind: "id", ids } | { kind: "pkg", pkg }
 *                               | { kind: "changed", changedFiles, mechanismFiles, affectedFilesOf }
 * @returns {{ selected: { mutation, reason }[], fallbackToAll: string | null }}
 */
export function selectMutations(mutations, selector) { … }

/** argv から selector を組む。指定が 2 つ以上・不正な値ならエラー。 */
export function parseSelector(argv) { … }
```

- `affectedFilesOf` は関数で受け取る（パッチの読み込みは呼び出し側。テストでは表で渡す）
- パスはすべて**リポジトリのルートからの相対パス**で比べる（`git diff --name-only` とパッチの `+++ b/` が同じ形）。
  `pkg` は WORKSPACE_ROOT からの相対だが、Tasuki ではリポジトリのルートと一致する（`git rev-parse --show-toplevel` で確かめた）
- `pkg` 配下かどうかは `file.startsWith(pkg + "/")` で判定する（`apps/timer-web` が `apps/timer-web-x` に当たらないように）

### 5.2 `scripts/mutation-check.mjs` の変更

触るのは次の 4 か所だけにする（#380 との衝突の面を小さくするため）:

1. `main()` の冒頭: `parseSelector(process.argv)`。`--changed` なら差分と機構のファイルを集めて渡す
2. ループの対象: `MUTATIONS` ではなく `selectMutations(...)` の結果
3. 対照実行: `Map<cwd + コマンド, 結果>` で使い回す
4. 結果の表示: §4.4

`assertMutationTestsExist` と `assertMutationPatchesBijective` は**選んだかどうかにかかわらず全件に対して**流す（宣言の健全性は絞り込みと無関係）。

### 5.3 自己テスト

- `scripts/mutation-select.test.mjs`（新設）: 条件 1〜3 のそれぞれで選ばれること、どれにも当たらなければ選ばれないこと、
  機構の変更で全件に倒れること、`pkg` の前方一致の誤判定（`apps/timer-web-x`）、`parseSelector` のエラー
- **アサーションは値が分岐する所に置く**: 条件 1 だけに当たる変異・条件 2 だけに当たる変異・条件 3 だけに当たる変異を
  別々に用意する（1 つの変異が 3 条件すべてに当たる造作では、どの条件を外しても緑のまま）
- `mutation-check.test.mjs`: 対照実行の使い回しを、ランナーの呼び出し回数で確かめる（関数を分けて注入できる形にする）

### 5.4 選び方そのものへの変異（原則 VII）

## 7. 検証と見積もり

| 検証 | 1 回 | 回数 | 小計 |
|---|---|---|---|
| scripts の自己テスト | 約 2 分 | 4〜5 回 | 約 10 分 |
| `--changed` の実地確認（手元で枝を作り、選ばれる件数と理由を見る） | 1〜3 分 | 3 回 | 約 10 分 |
| 全件（使い回しを入れた形が全件で緑になること・所要時間の比較） | 手元 10〜15 分（推測）／CI 約 6〜7 分（推測） | 2 回 | 約 30 分 |
| 選び方への変異 2 件の検出（`--id` で流す） | 1 分 | 2 回 | 約 2 分 |
| E2E 全件（PR 2） | 約 1.5 分 | 2 回 | 約 3 分 |

**機械の待ちは合計約 1 時間**。実作業は 3〜4 時間（推測）。**合計が 2 倍を超えたら、続ける前に利用者へ報告する。**

**完了の条件**:

- `--changed` で、実装中のパッケージの変異だけが選ばれ、選んだ理由が出る
- 全件の実行が今と同じ 153 件＋新設 2 件で緑、かつ所要時間が出る
- CI の `quality` が緑（全件のまま）
- E2E 全件が、ルーム枠を広げた同期サーバーで緑
