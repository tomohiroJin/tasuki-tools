## 1. 範囲

**ルームを離れる 3 つの経路を、1 つの考え方で揃える。**

#249 でルームの入口を玄関 1 つへ寄せたとき、**入る側**は作り直されたが、**離れる側**は
旧世界の形が残った。Issue 本文の 3 症状はすべてこの取り残しから出ている ——
退出が成立しない（①）、離れ方で行き先が変わる（②）、終了すると押した本人だけが
ルームから出される（③）。

個別に直すこともできるが、**同じ取り残しの別々の顔**なので、行き先の考え方を
1 本決めてから 3 つとも閉じる。

### 本 Issue で扱わないもの

- **拒否理由を操作地点へ届ける根治。** 押した操作と返事を結ぶ `requestId` が wire に要る。
  #291 / #292 が申し送った未着手の課題であり、射程が倍増する（§8 に残余として記す）
- **`member.remove`（列から外れる）のガード。** ドメイン層（`decide.ts`）で守られ、
  UI もボタンを無効化して理由を出している。穴が開いているのは `participant.remove` 側だけである（§3.2）
- **poker 側の同種の導線。** 本 Issue の症状はすべて timer で報告された
- **「新しいセッション」というボタンの文言。** 意味は「同じルームで新しいセッション」へ変わるが、
  実際に新しいセッションが始まる以上、文言は現状のままでよい

## 2. Issue #290 本文との差異

着手前に本文の主張を 1 つずつ実測した。**4 件が事実と食い違っていた。**

### 2.1 行き先判定の正本のパスが違う

本文は `apps/timer-web/src/sync/error-action.ts` を名指しするが、そのパスに実体は無い。
正本は **`apps/timer-web/src/ui/error-action.ts`** である。

### 2.2 症状 ① は「導線が無い」ではない

本文は「セッション開始前の画面で退出も追い出しもできない」と書くが、`Lobby.tsx` の
既定タブ「ルーム」の名簿行に**両方とも実在する**（`:266-274` の「ルームから抜ける」と
`:310-316` の「◯◯ を退出させる」）。`App.tsx:151` で `onRemoveParticipant` も渡っている。

**実体は「押しても成立しない」である**（§3.1）。利用者の報告「押しても動かなかった」が正確だった。

### 2.3 「残った人が外された扱いになる」は成立しない

本文は「片方が抜けてルームが消えると、残った人は『外された』側の扱いになり、もう存在しない
ルームの参加画面に着く」と説明するが、この経路は無い。

- `removalNotificationFor()` の結果は**退出させられた本人の接続にだけ**送られる
  （`participant-remove.ts:122-130`）。残った人へ `REMOVED_FROM_ROOM` が飛ぶ経路は存在しない
- ルーム破棄は**名簿が空になったときだけ**である（同 `:158-169`）。1 人でも残ればルームは消えない

**非対称そのものは実在する**（自分で抜ける → `/`、外される → `/?room=CODE`）。ただしそれは
「残された人」の差ではなく、**「外された人」と「自分で抜けた人」の差**である。
本文の因果の物語の上に設計を建ててはならない。

### 2.4 「もう存在しないルームの参加画面」は既に無い

本文が問題視したこの帰結は、**#274 が先に塞いでいる**。玄関は `?room=CODE` を受けると
接続と同時にルームの生死をサーバーへ尋ね、見つからなければ**名乗らせずに不在を知らせる**
（`hub/hub-state.ts` の `screenFor`・§3.5）。#290 の起票（実画面フィードバックは 2026-09-19）
より後に #274 が main へ入ったため、本文はこの変化を知らない。

**この 1 件が本設計の形を決めた。** 行き先の正しさを tool 側が知る必要は無く、
**玄関が実際に確かめた答え**に委ねられる（D3）。

## 3. 実測した事実（2026-09-22・main `e75df3e`）

### 3.1 招待した瞬間に、作成者は抜けられなくなる

ルームは `rotation = [作成者]`（長さ 1）で始まり（`initial-timer-state.ts:65-66`）、
`room.join` した人は輪に入らない（「見学」。輪へ入るのは「ドライバーに加わる」を押したときだけ）。

`participant-remove.ts:183-192` は「対象が輪の席を持つ」かつ「`rotation.length <= 1`」を
`BelowMinMembers` で拒む。したがって:

| 場面 | 結果 |
|---|---|
| 作成者が 1 人（ソロ） | 名簿が空になる経路へ落ちる → **抜けられる**（#79） |
| **作成者＋参加者 1 人（招待した直後の普通の状態）** | 作成者は輪の唯一の席 → **拒否される** |
| その参加者（見学）が抜ける | 輪に触らない → **抜けられる** |

**2 人になった瞬間、作成者は自分で抜けることも、他の人から外されることもできなくなる。**

### 3.2 同じ不変条件が、片側だけ守られていない

輪を空にしない不変条件は 2 経路にある。

| 経路 | ガード | 利用者から見た拒否 |
|---|---|---|
| `member.remove`（列から外れる） | `decide.ts:308-310`（ドメイン層） | ボタンが**無効**・理由が隣に出る |
| `participant.remove`（ルームから抜ける） | `participant-remove.ts:189`（アプリ層） | **何も起きないように見える** |

### 3.3 輪が空になると `currentIndex` が `NaN` になる

`evolveMemberRemoved`（`evolve.ts:327-348`）は `newIndex % newRotation.length` を計算する。
輪が空なら `% 0` で `NaN` となり、`Math.max(0, Math.min(NaN, -1))` も `NaN` のままになる。
**ガードが守っている危険は実在する。** 輪を空にする解法は採れない（D1 の根拠）。

### 3.4 拒否は、押した場所から見えない位置に出て消える

`BelowMinMembers` は `errorAction()` の列挙に無く、既定の `transient` に落ちる。
`transient` は `showBanner(friendlyError(code), "warn")` を呼び（`use-timer-sync.ts:582-590`）、
バナーは `App.tsx:257` で **`renderBody()` より手前＝ページ最上部**に描かれ、`warn` なので
自動で消える。名簿の行はタブとカードの奥にある。

**通知は出ていたが、操作地点からは見えない位置にあり、数秒で消えていた。**
#291 / #292 とまったく同じ型である。

### 3.5 玄関は 5 画面に分岐し、不在を実際に確かめている

`hub/hub-state.ts` の `screenFor` は `create` / `join` / `choice` / `resuming` / `gone` を返す。
`gone` は推測ではなく**サーバーへ尋ねた答え**である（#274）。`RoomGone.tsx` は戻る道
（「新しいルームを作る」）と履歴リンクを持ち、行き止まりにならない。

### 3.6 不在の知らせは、退出の告知を意図的に捨てている

`App.tsx:88-92` は `gone` のとき `departure` を渡さない。根拠はコメントに残されている ——
「退出の告知と不在の告知を並べない」「そのルームはもう無く、退出したことより不在のほうが
利用者に必要な報せだからである」（`:73-77`）。

**この判断は「死んだ招待 URL で来た人」を想定している。** `?left=` を持つ人は文脈が違う（D4）。

### 3.7 終了後の遷移は、旧 `Setup` の直訳である

`newSession()`（`use-timer-sync.ts:770-773`）は `setPhase("setup")` と `redirectTo("/")` を
両方行う。`git log -L` で出自が分かれる:

- `redirectTo("/")` —— #249 以前の `setMode("setup")`（＝旧 `Setup` ＝ルーム作成画面へ戻る）の
  機械的な置き換え。当時の `newSession` は「**まっさらな新しいルームを作る**」操作で、
  全状態を捨てていた
- `setPhase("setup")` —— #249 で**新たに足された**もの。`celebration` のまま閉じ込められる
  閉路を塞ぐためである

いまは 2 行の意味が矛盾している。**押した本人だけがルームから出され、他の全員はロビーへ戻る。**

## 4. 決定

### D1. 最後のドライバーの退出は、拒まずに「繰り上げてから」成立させる

`participant-remove.ts` の拒否の手前で繰り上げ候補を探し、居れば
`MemberAdded`（繰り上げ）→ `MemberRemoved`（退出者の席を外す）の順に適用する。
**輪は一瞬も空にならない**ので §3.3 の `% 0` に触れず、`evolve` も `decide.ts` も変更しない。

候補が居ない場合は従来どおり `BelowMinMembers` で拒む（防御として残す）。
ただし**この経路に到達する時点で候補は必ず存在する** —— 退出者が席を持ち、輪の席がその 1 つだけで、
退出後も名簿が空でないなら、残る名簿の全員が見学だからである。代理は名簿に居ないが席は持つので、
代理が居れば `rotation.length >= 2` となりガードに到達しない。

**走行中の帰結を明示する。** セッション実行中に唯一のドライバーが抜けると、繰り上がった人が
そのまま現ドライバーになり、タイマーは継続する（`MemberRemoved` の `currentIndex` 調整の既存挙動）。
「抜ける操作は常に成立する」という決定の当然の帰結として受け入れる。

### D2. 繰り上げ先は「在席を優先し、同条件なら `joinedAt` の早い順」

名簿から退出者を除き、まだ輪の席を持たない人のうち、`Participant.connections` が
空でない人を優先する。**離席中の人を唯一のドライバーに据えない** —— #276 が扱った
「席は在るのに誰も居ない」状態を自分で作ることになる。

### D3. 行き先は離れ方で分けない。常に `/?room=CODE&left=<reason>` へ送る

`?room=` を落とす分岐（`hubRoomPath(null, "self")`）を無くす。行き先を決めるのは
「どう離れたか」ではなく、**玄関が実際に確かめたルームの生死**である（§2.4・§3.5）。
`?left=` は文言のためだけに残る。

これは EARS「離れ方によらず同じ考え方で行き先を決めること」に正面から応える —— 行き先は
全員同一で、違うのは見える言葉だけになる。

**コードを失っている場合だけは `?room=` が付かない。** 退出時のコードは
`room?.code ?? roomCodeRef.current` で引くが、どちらも無い状態は起こりうる。
そのときは `/?left=<reason>`（玄関そのもの＋告知）へ送る —— 存在しないコードを
載せると、玄関が不在の知らせを出して**退出の告知より不在のほうが前に出てしまう**。
これは「離れ方による分岐」ではなく「運ぶものが無い」という別の理由である。

**wire は変えない。** 配布の窓（#276）を増やさず、推測も競合も持ち込まない。

### D4. 玄関は「不在」かつ「退出の告知あり」を、作成画面＋告知にする

`App.tsx` の `gone` 分岐を次のように分ける。

| `?left=` | ルーム | 画面 | 出る言葉 |
|---|---|---|---|
| あり | 在る | 参加 / 選択 | 「ルームから抜けました。」等（現状どおり） |
| **あり** | **無い** | **作成画面＋退出の告知** | 「ルームから抜けました。」 |
| なし | 無い | 不在の知らせ（現状どおり） | 「ルームが見つかりません」 |

**#274 の判断（§3.6）を狭く見直す。** あの判断は死んだ招待 URL で来た人を想定していた。
`?left=` を持つ人は「**たったいま自分が抜けて、その結果この部屋が消えた**」人であり、
この人に「ルームが見つかりません／URL が正しくない可能性があります」とだけ見せるのは
**誤解を招く**（自分で押した操作の結果なのに、何かが壊れたように読める）。
退出の告知こそがその不在の説明になっている。

**根拠はコメントにしか無く、固定しているテストは無い。** コメント（`App.tsx:73-77` / `:88-91`）は
同じ変更の中で判断の更新を書き残す。

### D5. 終了後は、ルームが生きているなら遷移しない

D3 の帰結である。`newSession()` から `redirectTo("/")` を落とし、ルームを失っているときだけ
玄関へ送る。押した本人も他の全員と同じく snapshot でロビーへ戻る。

ルームから出たい人はロビーの「ルームから抜ける」（D1 で成立するようになる経路）を使える。
導線は失われない。

### D6. `ErrorAction` の `destination` を畳む

行き先が 1 本になるので `destination: "join" | "setup"` は決定を運ばなくなる。
**残してはならない** —— 使われない「行き先を決める値」が居座ると、次に読む人が
生きている分岐だと誤解する。`packages/room-core/src/departure.ts` の
「`destination` と 1 対 1 に対応する」という docstring も同時に直す。

**`docs/plans/` 配下の 2 つの計画書も `destination` を名指ししているが、書き換えない。**
当時の記録であり、「記録は移動・改名しない」という既存の決定に従う。

## 5. EARS と検査の対応

完了条件の突合は、主張ではなく**検査の手段**で行う。

| EARS（Issue #290） | 検査 |
|---|---|
| 利用者がルームを離れるとき、離れ方によらず同じ考え方で行き先を決めること | `use-timer-sync` のテスト: 自己退出・他者による退出の**どちらも** `/?room=CODE&left=...` へ行く |
| 利用者がセッションを終えたとき、ルームの扱いが玄関にあるという前提と矛盾しない場所へ送ること | `newSession` のテスト: ルームが生きていれば**遷移しない**／`sessionLost` なら `/` へ |
| セッション開始前の画面に、開始後と同じ退出・追い出しの導線を出すこと | `participant-remove` のテスト: 2 人ルーム（輪は作成者 1 人）で作成者の退出が**成立する** |
| 出せない理由があるなら、その理由が分かる形にすること | D1 により `participant.remove` 経路からこの拒否が消える。**残余は §8** |

## 7. 退けた代案

| 代案 | 退けた理由 |
|---|---|
| **常に玄関そのもの（`/`）へ送る** | 完全に対称で最小だが、外された人が再参加にコードを入れ直すことになり、`ARCHITECTURE.md` が明記した「運ぶ（再参加しやすくする）」意図を捨てる |
| **常に `?room=CODE` を運び、玄関は変えない** | D4 を伴わないと、自分で抜けた最後の 1 人が**説明の無い「ルームが見つかりません」**に着く（§3.6）。最も普通の「1 人で作って気が変わる」場面で誤解を招く |
| **クライアントが「自分が最後の 1 人か」を名簿から導出する** | サーバーの `hasNoParticipants` を写すことになり、#276 で学んだ「素朴な再計算はサーバーとずれる」を自ら招く。snapshot が古いと、塞ぎたい欠陥をそのまま再現する |
| **wire に「部屋は残るか」を載せる（サーバー権威）** | 精度は出るが、#274 の仕組みで同じ精度が wire を変えずに得られる（§2.4）。#276 と同じ配布の窓を増やす費用に見合わない |
| **輪を空のまま許し、「開始」を押せなくする** | `evolveMemberRemoved` が `currentIndex` を `NaN` にする（§3.3）。`evolve` の作り直しを伴い、射程が倍増する |
| **拒否は維持し、ボタンを無効化して理由を出す** | 最小だが、利用者から見て「抜ける」が成立しない状態が残る。輪の維持はシステム側の都合であり、退出を妨げる理由にならない（利用者の判断） |

## 8. 残余（この Issue では閉じない）

- **拒否理由が操作地点に届かない構造。** D1 により `participant.remove` 経路の拒否は消えるが、
  他の拒否（`INVALID` / `PARTICIPANT_NOT_FOUND` 等）が**最上部の自動消去バナー頼り**である
  構造自体は残る。根治には押した操作と返事を結ぶ `requestId` が wire に要る。

### 9.3 変異検査に新しい失敗様式が見つかった（この PR で塞いだ）

`scripts/mutation-check.mjs` は変異を適用したあと `git checkout --` で復元するが、
**`.git/index.lock` の競合で復元が失敗しても「知らせるだけ」で、再試行も検証もせず終了コードも
変えなかった。** 本 Issue の作業中に **3 回**発生し、製品コードに変異が残った
（`m29`＝合言葉チェックの短絡・`m54`＝不可視文字の除去を消す、ほか）。
自動セキュリティレビューがその状態を検知した。

**「変異検査が止まって以降が無検査になる」より危険である** —— 残るのは検査の不足ではなく
**製品コードの改変**であり、気づかずにコミットすれば認証バイパスが本番へ出る。

塞いだ内容: 再試行 ＋ **復元されたことの実検証**（コマンドの成功と実際に戻ったことは別） ＋
非ゼロ終了。異常終了からの復旧経路（`recoverFromCrashedRun`）にも同じ手当てを広げ、
そちらでは**復元を検証できてからマーカーを消す**ようにした（検証前に消すと、復元失敗時に
「変異が残っている」という唯一の記録を失う）。

### 9.4 繰り上げ候補は必ず存在する（防御の枝は到達不能）

D1 が「候補が居なければ従来どおり拒む」と書いた枝は、**実装上到達しない**ことが確認された。
枝は防御として残し、理由をコメントに明記してある。

**到達しない理由は 2 つの重なりである。片方だけを挙げると誤読される。**

1. あの枝は **`if (idx >= 0)`（対象が輪の席を持つ）の中**にある。席を持たない見学者が抜けるときは
   輪に触らないので、そこへ入らない
2. 入ったうえで候補が空になるのは、**名簿が空になる場合と同値**である（退出者が唯一の席を持つなら、
   残る名簿の全員が見学だからである）。名簿が空になる経路は `hasNoParticipants` の早期 return が
   その手前で捌いている。代理は名簿に居ないが席は持つので、代理が居れば `rotation.length >= 2` となり
   ガードに到達しない

⚠ **理由 1 を落とすと「見学者が自分を退出させたときに到達する」という誤った結論が出る。**
実際に、この PR のレビューで**採点者が理由 1 を見落として「到達可能」と判定した**
（`if (idx >= 0)` を見ずに `pickPromotionTarget` の候補計算だけを追った）。
規範文書側（`docs/timer/ARCHITECTURE.md`）にも同じ 2 点を書いてある。

### 9.5 E2E は画面種別を固定していない

`e2e/specs/leave-room.spec.ts` は、退出後に落ちる画面の種別（作成画面か参加画面か）を固定せず、
**契約そのもの**（行き先のパスと `room=` / `left=` のクエリ、告知の文言、繰り上げの結果）を固定した。
画面種別はルームの生死から導かれる結果であり、そちらを固定すると脆くなるためである。

### 9.6 繰り上げの「在席」は timer の在席で見る（D2 の訂正）

D2 は「在席を優先する」と決めたが、**その「在席」の判定を誤っていた。** 当初 `presenceOf`
（接続が 1 本でもあれば `online`）を使ったため、ハブ（選択画面）や poker のタブを開いている
だけの人も「在席」になった。

`apps/tasuki-sync/src/application/timer-snapshot-dto.ts` の D21 が、まさにこの用途に
`presenceOf` を使うなという結論を既に出していた —— 「その人は `online` なのにタイマーの前には
居ないので、タイマーを見ていない人にドライバーが回る。判定材料を timer の在席
（`isPresentIn(p, TOOL_TIMER)`）へ替えてある」。

**壊れ方**: 走行中に唯一のドライバーが抜けると、ハブだけを開いている見学者が繰り上がり、
`seatSkipReason` がその席を `"away"` と判定し、輪の席は 1 つだけなので全席が不適格になり、
`advanceDriver` が「現状維持＋再アンカー」へ縮退して誰も居ないドライバーのままタイマーが
永久に張り直され続ける。

**この誤りの経路を記録する**（同じ間違いを繰り返さないため）。

1. 計画に `p.connections.size > 0` と場当たりに書いた
2. レビューが「共有パッケージの `presenceOf` と同じ述語だからそちらへ寄せろ」と指摘した
   （重複した presence 導出は過去の不具合原因という、正しい根拠つき）
3. 述語が同一であることを確認して受け入れた
4. **確認したものが誤っていた。** 問うべきは「ドライバー適格の判定にどちらが正しいか」で、
   その答えは別の場所（D21）に既にあった

**2 つの規範が食い違っていた**（「presence 導出を重複させるな」対「ドライバー適格に presence を
使うな」）。指摘も検証もそれぞれ真で、結論だけが誤った。指標や規範が食い違うときは、
その数を作っている規範を先に見る。

### 9.7 走行中の繰り上げは前任者の残り時間を引き継ぐ

D1 は「タイマーは継続する」と決めたが、その具体を書いていなかった。`evolveMemberRemoved` は

### 9.9 `?left=removed` とルーム消滅が重なると、文言と画面が噛み合わない

`departureNoticeFor('removed')` は「ルームから退出しました。再参加するには名前を入力して

D4 の表（§4）は「あり／無い」の行に self の文言しか書いておらず、removed の組み合わせを
検討していなかった。頻度は低い（外された直後に残りの全員も抜ける等）ため、承知で受け入れる。

### 9.10 `?left=` を持つ人にも、名乗りフォームが一瞬出る

`?room=CODE&left=self` で玄関に着いた人は復帰の組を捨てられているので、`room.check` の答えが
届くまで `screenFor` は `'join'` を返す。たったいま抜けた部屋の「◯◯ に参加します」が出てから
作成画面（部屋が消えた場合）へ切り替わる。#274 の判断は「名乗る前に不在を知らせる」だった。

ちらつき自体は #274 からの既存性質だが、自己退出は D3 まで `/` へ即着していたので、
この経路で見えるのは今回が初めてである。

**素朴な修正は採れない。** `departed && !joined && !gone` で `'resuming'` を返すと、
ルームが生きている場合に永久に読み込み中になる（`gone` も `joined` も立たないため）。
正しく直すには「照会の答えが届いたか」を `screenFor` の入力に足す必要があり、#290 の射程を超える。
承知で受け入れる。
