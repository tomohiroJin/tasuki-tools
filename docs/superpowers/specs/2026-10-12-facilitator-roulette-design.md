## 1. 目的

**次の進行役（ファシリテーター）を、誰かの遠慮や押し付けではなく、その場で決める。**
ルームの全員の画面で同じ円盤が回り、同じ人のところで止まる。全員が一周するまで同じ人は選ばれない。

利用者の言葉:

- 「ファシリテーター・ルーレットでは、お題に対するファシリが誰かを決める」（2026-09-23・#91 の対話）
- **見た目の良さにこだわりたい**（2026-10-12・統括経由）

本文に書かれていないが、設計に効く事実:

- **名簿（`roster`）はハブの接続にしか配られていない**（`create-sync-server.ts` の `hubRecipientsOf` は `connectionsIn(room, null)`）。
  ルーレットは「いまルームに居る人」を描くので、名簿を受け取る経路が要る
- **在室（online / offline）は導出である**（`room-core` の `presenceOf`）。切断しても名簿からは消えず、`offline` になるだけ。
  明示的な退出だけが名簿から消す
- 1 ルームの参加者数に**上限が無い**（`maxParticipants` に当たる値は無い。grep 0 件）。円盤の席数の上限は設計で決める（§5.6）
- **書体の base 層に無い字**: 「抽」「選」の「抽」・「当」・「巡」・「候」「補」・「誰」・「足」・「以」・「字」「文」・「円」「盤」・「札」・「転」・「目」・「減」・「司」・「顔」（2026-10-12 に `fonts.css` の 3 つの太さの base の `unicode-range` へ 1 字ずつ当てた）。
  画面の言葉は「選ばれる」「一周」「名前を追加」で書く（§6.6）

## 3. 範囲

### この設計で行うこと（#94）

1. ルーレットを 5 つ目の文脈（`packages/roulette-core`）にし、**ルームの持ち物**にする（状態は揮発インメモリ）
2. ルーレットのツール `apps/roulette-web`（公開パス `/roulette/`）を新設し、玄関に **4 枚目の札**を足す
3. 抽選は**同期サーバーが引き**、結果と「止まるまでの残り時間」を全接続へ配る
4. 抽選に入る人は**ルームの在室者**から取り、その場で外す・戻す、ルームに居ない人の名前を足す・消すができる
5. **全員が一周するまで同じ人は選ばれない**（一周の記録はルームの揮発メモリの中）
6. いまのお題があれば、そのタイトルを「お題「○○」の進行役を決めます」と添える（読むだけ）
7. 動きを減らす設定（`prefers-reduced-motion`）では回さず、結果をすぐ出す。結果は読み上げる

### 後続に回すこと（この設計では行わない）

- 選ばれた進行役を timer や poker の画面に出す（「いまの進行役」をほかのツールが読む）。**需要が出てから**（原則 X）
- 履歴（過去の何回分か）を残す・書き出す
- 円盤の音（tick 音）。timer の音の資産（`countdown-tick-sound`）を流用する案はあるが、音は「見た目」の範囲の外で、同時に鳴ると煩い

### やらないこと

- **抽選結果のサーバー永続化**（`docs/timer/adr/0007`）。再起動で一周の記録も最後の結果も消える
- **後から検証できる抽選**（コミット・リビール方式の乱数）。§4 の退けた案 X3
- timer の rotation の持ち上げ（§4 R12）

## 4. 決定

番号は `R`（Roulette）で振る（`docs/adr/0012` の `D10`、#91 の `T1` などと字面で混ざらないように）。

| # | 決定 | 理由 |
|---|---|---|
| R1 | **共通ルーム（#95）の一機能として足し、新しいサーバーは立てない。** 接続の種類 `?tool=roulette` を足し、お題（`?tool=topic`）と同じ形の専用のメッセージ層を持つ | 参加・復帰・合言葉・レート制限・在席・破棄をすべて共有できる（§2）。お題ツールが同じ形で足されて動いている |
| R2 | **独立したアプリ `apps/roulette-web`（公開パス `/roulette/`）として玄関の 4 枚目の札にする**（ツール ID `roulette`） | 円盤は画面の主役で、選択画面に押し込むと札の列と参加者の一覧を押し出す。札にすれば「その場で決める道具」として玄関に並ぶ（利用者が #91 で並べた 3 つの用途のひとつ）。配備資材は静的サイト 1 本ぶん（`STATIC_ONLY=1`）で、サーバーは増えない |
| R3 | ルーレットの規則は 5 つ目の文脈 **`packages/roulette-core`** に置く。**`room-core` に依存しない**（参加者 ID は不透明な文字列）。ほかのツールのドメインもこれに依存しない | `docs/adr/0017` 決定 1・2（ツールのドメインは参加者エンティティを持たず、名簿の断片を引数で受ける）。wire のスキーマを同期サーバーと web の両方が読むので、置き場は共有のパッケージになる |
| R4 | **乱数の権威はサーバー。** 回す要求を受けたサーバーが当たりを決め、円盤の並び・当たりの位置・止まる位置の揺らぎ（`settle`）を全接続へ同じフレームで配る。web は乱数を引かない | 画面ごとに引くと画面ごとに違う人が当たる（Issue 本文）。乱数源は `node:crypto` の `randomInt`（偏りが無い）をポート越しに渡す（ドメインは環境から値を読まない・`scripts/audit-domain-side-effects.mjs`） |
| R5 | **配るのは絶対時刻ではなく「経過」**。フレームは `durationMs` と、**送る時点で計った** `elapsedMs` を持つ。web は受け取った時点を起点に残り（`durationMs - elapsedMs`）を回して止める | 端末の時計は数秒ずれうる。絶対時刻（「〇時〇分〇秒に止まる」）を配ると、ずれた端末だけ早く・遅く止まる。経過で配れば、ずれは配送の遅れ（数十〜数百 ms）だけになる。途中で入ってきた人・再接続した人にも、送る時点の経過が届くので同じ場所から合流できる |
| R6 | **公平性の既定は「一周するまで同じ人を選ばない」**。当たりは「この一周でまだ選ばれていない人」から一様に引く。全員が選ばれたら一周を閉じて新しい一周を始め、**新しい一周の最初には直前の当たりを入れない**（入る人が 2 人以上のとき） | 利用者の「同じ人ばかりが当たり続けない」（Issue のあるべき姿）。直前の当たりを外さないと、周の境目で同じ人が 2 回続く（一周の規則だけでは防げない） |
| R7 | **抽選に入る人 = 在室（online）の参加者 − 外した人 ＋ 足した名前 − 外した名前**。離席中（offline）の参加者は自動で入らない。この計算は `roulette-core` の純粋関数 1 つにし、**サーバーと web が同じ関数を使う** | 「ルームの参加者一覧から取る」（Issue の決めること 3）と「その場で外す・足す」を両立する。ルームに居ても画面を閉じた人を当てない。web が円盤の下書き（回す前の並び）を描くのにも同じ計算が要り、写しを持つと片方だけ直る |
| R8 | **ルーレットの状態**は「外した人の ID」「足した名前」「この一周で選ばれた人（選ばれた順）」「最後に回した 1 回（円盤の並び・当たり・揺らぎ・回した人の名前・開始の単調時刻）」の 4 つだけ。**履歴は持たない** | 揮発方針（`docs/timer/adr/0007`）。「結果を残すか」（Issue の決めること 6）への答えは「最後の 1 回と、いまの一周だけを残す」。これだけで「この一周で選ばれた人」の表示と、途中参加者への合流ができる |
| R9 | **回っている間（`durationMs`）は次の回す要求を拒む**（`ROULETTE_SPINNING`）。外す・戻す・足す・消すは回っている間も受けるが、**回っている円盤は凍結した並びのまま**で変わらない。web は回っている間それらの操作を押せなくする | 回転中に 2 回目が来ると、画面ごとにどちらの回転を見ているかがずれる。編集を拒むと「押したのに何も起きない」になるので、サーバーは受けて、凍結で整合を保つ（並びは回す時点のものをフレームに載せている） |
| R10 | 入る人が **2 人未満なら回せない**（`ROULETTE_TOO_FEW`） | 1 人のルーレットは決める意味が無い |
| R11 | ルーレットを操作できるのは**ルーレットの接続だけ**（お題の T4 と同じ）。ルーレットのコマンドはハブ・timer・poker・お題のスキーマに含めない。**ルームの在室者なら誰でも回せる**（役割は #95 で廃止済み） | お題と同じ線引き。共通の処理（`handlers.ts`）にツール別の可否判定を戻さない |
| R12 | **timer の rotation とは持ち上げ（共通化）をしない** | rotation は「席の並びを順に回す」もので、代理の席・見送り・交代回数と結びつく timer の帳簿である。ルーレットは「並びの無い集まりから 1 人を無作為に選ぶ」もので、一周の記録の意味（選ばれた順）以外に重なりが無い。共通化すると timer のドメインが新しい文脈に依存するか、`room-core` にツールの語彙が入る（`docs/adr/0017` 決定 1・2 に反する）。**同じ型の重複は「一周で外す」の数行だけ**で、原則 X（抽象は実需で）の閾値に届かない |
| R13 | **足した名前（ゲスト）は表示名の規約（`display-name-rule.ts`）を通す**。上限は 1 ルーム 12 件。名簿の参加者（在室を問わない）・ほかのゲストと同じ名前（正規化後）は拒む。**同じ名前かどうかは参加の重複拒否と同じ関数・同じキー（`room-core` の `conflictsWithExisting`。大文字小文字を畳む）で決め、`roulette-core` へは関数として渡す**（`NameConflict`）。**足した後で同じ名前の人が参加・改名したら、入る人の段（`poolOf`）でゲストを外す（在室者が勝つ）。状態にはゲストを残す**。**ゲストの名前はログへ出さない** | 足した名前は利用者の入力で、全接続へ配られる。表示名と同じ扱い（`docs/adr/0011` 決定 3・#284 のなりすまし対策）を写しではなく同じ関数で受ける。同名を許すと円盤の上で区別できない。判定の詳細と退けた案は下の「R13 の判定（PR #355 のレビューで決めたこと）」 |
| R14 | **名簿（`roster`）をルーレットの接続にも配る**（今はハブだけ）。ルーレットの状態に名簿を埋め込まない | 入る人の計算（R7）に在室が要る。名簿の配信は `saveRoster` に 1 本化されており（`test/save-roster.wiring.test.ts`）、宛先を足すだけで接続の着脱・退出のすべてが届く。ルーレットのフレームに名簿を写すと、名簿が変わるたびにルーレットの配信も要り、経路が 2 本になる |
| R15 | **お題の `topic` フレームもルーレットの接続に配る**（`TOPIC_RECIPIENT_TOOLS` に足す） | 「お題に対するファシリを決める」（§1）。お題はタイトルだけを 1 行で添える。web は `topic` フレームを先に見分ける（#91 と同じ規律。知らないフレームを捨てて通知すると利用者に誤報が出る） |
| R16 | `roulette-core` の表現は **直接遷移関数＋`Result`**（`docs/adr/0016` 決定 1） | 状態は小さく、イベントの履歴・再生・段階適用が要らない。`room-core`・`topic-core` と同じ |
| R17 | 表示部品（円盤・結果の札）は**アプリに置く**。`packages/ui` に足すのはトークン（必要なら）だけ | `packages/ui` は CSS と書体だけのパッケージ（#91 T13 と同じ理由）。円盤は 1 画面でしか使わない（`docs/adr/0022` 決定 2 の「2 画面以上」に当たらない） |

### 退けた案

| # | 案 | 退けた理由 |
|---|---|---|
| X1 | 玄関（ハブ）の選択画面の中にルーレットを置く（新しいアプリを作らない） | 配備資材は減るが、ハブのコマンド（`room-core` の `HubCommandSchema`）にルーレットの語彙が入り、メンバーシップの文脈にツールの言葉を持ち込む（`docs/adr/0017`）。画面としても、道具を選ぶ札の列と円盤が場所を奪い合う。利用者は #91 でルーレットを timer・poker と並ぶ用途として挙げている |
| X2 | 各画面が乱数を引き、最初に引いた人の結果を配る（ホストが引く） | 「誰の結果を正とするか」の調停が要り、同時に 2 人が押すと割れる。役割（ホスト）は #95 で廃止した。サーバーが引けば調停は要らない |
| X3 | 後から検証できる抽選（サーバーが種のハッシュを先に配り、後で種を明かす） | 守る相手が居ない。サーバーは運用者自身が動かしており、参加者同士は同じルームの仲間である。コード・wire・テストが倍になる割に、利用者が得るものが無い。**揮発インメモリなので検証の記録も残らない** |
| X4 | 止まる絶対時刻（`stopsAt`）を配り、端末の時計で止める | R5。timer は `time.ping` で時計のずれを測っているが、それを持ち込むとルーレットの接続にも往復の測定が要る。ずれの許容（配送の遅れ程度）なら経過で足りる |
| X5 | 一様乱数（毎回全員から引く） | 「同じ人ばかり当たり続けない」を確率でしか守れない（4 人で同じ人が 3 回続く確率は 1/16）。会議の現場では 1 回の偏りが不公平に見える |
| X6 | 重み付け（選ばれた回数が少ない人ほど当たりやすい） | 回数の帳簿がルームの寿命いっぱい要り、途中で入った人の扱い（回数 0 で始めると連続で当たる）を決める必要がある。一周の規則のほうが説明が 1 文で済む（「全員が一周するまで、同じ人は選ばれません」） |
| X7 | 名簿をルーレットのフレームに埋め込む | R14 |
| X8 | 離席中の人も既定で入れ、手で外させる | 画面を閉じて会議を抜けた人が当たり、毎回手で外すことになる。逆に「画面を開いていないが会議に居る人」は名前を足せば入れられる（R7） |
| X9 | 足した名前をルームの参加者（名簿）として作る | ゲストは接続を持たず、名簿に載ると玄関・timer・poker の参加者一覧にも出てしまう。ゲストはルーレットの中だけの存在にする |

## 5. 設計

### 5.1 `packages/roulette-core`（純粋なドメイン）

```ts
/** 抽選に入りうる 1 人。参加者 ID か、ゲストの ID（`g-` で始まる）。この文脈は中身を解釈しない */
type EntryId = string;

interface Entry { id: EntryId; name: string }

/** 名簿の断片（アプリ層が room-core の Room / 玄関の RosterRoom から作って渡す） */
interface Member { id: EntryId; name: string; present: boolean }

interface Spin {
  seq: number;              // 回した通し番号（ルームごと・1 から）。web はこれで「新しい回転か」を見分ける
  wheel: Entry[];           // 回す時点の並び（凍結）。2〜MAX_WHEEL 件
  winnerIndex: number;      // wheel の添字
  settle: number;           // 当たりの席の中のどこで止まるか（0.2〜0.8）。全画面で同じ
  spunBy: string;           // 回した人の表示名（表示名は配信してよい・docs/adr/0011 決定 3）
  startedAt: number;        // サーバーの単調時計（ms）。**wire には載せない**（R5）
}

interface RouletteState {    // ルームごとに 1 つ
  excluded: EntryId[];      // 外した人（参加者もゲストも）
  guests: Entry[];          // 足した名前。最大 MAX_GUESTS = 12
  drawn: EntryId[];         // この一周で選ばれた人（選ばれた順）
  lastSpin: Spin | null;
  nextGuestSeq: number;     // ゲスト ID の採番（`g-1`, `g-2`, …）
}
```

純粋関数（すべて `Result` を返すか、全域関数）:

| 関数 | 役目 |
|---|---|
| `poolOf(members, state, conflicts)` | 入る人の並び（R7）。**並びは決定的**: 在室の参加者（名簿の順）→ ゲスト（足した順）。外した人を除く。**在室者（外したかを問わない）と同じ名前のゲストを除く**（R13。`conflicts` は `room-core` の `conflictsWithExisting`） |
| `drawWinner(pool, state, randomInt)` | 一周の規則（R6）で当たりを引く。`randomInt(n)` は `[0, n)` の整数を返す注入された関数。戻り値は `{ winnerIndex, drawn }`（周を閉じたら `drawn` は新しい周の 1 件目だけになる） |
| `startSpin(state, input)` | 回転中なら `ROULETTE_SPINNING`、入る人が 2 人未満なら `ROULETTE_TOO_FEW`、`MAX_WHEEL` を超えるなら `ROULETTE_TOO_MANY`。通れば `lastSpin` と `drawn` を更新した状態を返す。`now`・`randomInt`・`randomSettle` は引数で受ける |
| `isSpinning(state, now)` | `lastSpin !== null && now - startedAt < SPIN_DURATION_MS` |
| `setIncluded(state, id, included)` | 外す・戻す（冪等。トグルにしない —— 2 人がほぼ同時に押すと打ち消し合う） |
| `addGuest(state, name, members, conflicts)` | 名前は**正規化済みで受ける**（正規化は同期サーバーが表示名の規約で行う・R13）。上限・同名を見る。同名の相手は `members`（在室を問わない）とゲストで、判定は `conflicts` だけで決める（ここで文字列を比べない） |
| `removeGuest(state, id)` | ゲストを消し、`excluded`・`drawn` からも落とす |
| `resetCycle(state)` | `drawn` を空にする（「一周をやり直す」） |
| `prune(state, knownIds)` | 名簿から消えた参加者の ID を `excluded` / `drawn` から落とす（退出を繰り返しても配列が膨らまない） |
| `toView(state, now)` | wire へ載せる形（§5.3）。`elapsedMs` を**この時点で**計る |

**PR 1 の実装で決めたこと**（2026-10-12）:

- **公開契約（`src/index.ts`）に `drawWinner` と `isSpinning` を載せない。** どちらも `startSpin` の内側でだけ使い、製品コードの使い手が居ない（公開契約の指標 SC-039 を後退させない）。テストはモジュールから直接読む。web が「回っているか」を知るのは wire の `elapsedMs < durationMs` から（§5.3）
- **`startSpin` は `settle` が `SETTLE_MIN`〜`SETTLE_MAX` の外なら `INVALID_SETTLE` を返す**（ドメインのエラーコード `RouletteDomainErrorCode`）。乱数源（`adapters/crypto-random-source.ts`）が契約を破ったときだけ起きる内部の誤りで、利用者の操作では起きない。**wire の `ROULETTE_ERROR_CODES` には載せず、同期サーバーが `INTERNAL_ERROR` に畳んで返す**（`application/roulette-handlers.ts`）。**畳むときはログを 1 行残す**（#382）: イベント名 `roulette-random-violation`・`reason=invalid-settle`（`randomInt` の契約違反は `reason=invalid-random`。こちらは例外だった頃の `on-message-error name=RangeError` の行も保つ）・水準 error。`reason` は語彙（`application/log/vocabulary.ts` の `RANDOM_VIOLATION_REASONS`）から引き、自由文・値は載せない
- **遷移関数のエラーの型は、その関数が返しうるコードへ絞る**（`RouletteError<C>`）。`addGuest` は `TOO_MANY_GUESTS` / `GUEST_NAME_TAKEN` だけを返す型にし、呼び出し側に到達しない `INVALID_SETTLE` の分岐を書かせない（PR #355 のレビュー）
- **変わらない操作は同じ参照を返す**（`setIncluded`・`removeGuest`・`resetCycle`・`prune`）。同期サーバーが参照で「変わっていないので保管も配信もしない」を判定する（§5.2）
- **`INITIAL_ROULETTE_STATE` は凍結する（配列も）。** 全ルームで同じ参照を共有するので、書き換えると状態の無いすべてのルームへ漏れる。状態の配列は `readonly` にした（遷移関数は新しい配列を作る）

定数: `SPIN_DURATION_MS = 4000`（§6.4）・`MAX_GUESTS = 12`・`MAX_WHEEL = 24`（§5.6）・`SETTLE_MIN = 0.2`・`SETTLE_MAX = 0.8`。

**R13 の判定（PR #355 のレビューで決めたこと・2026-10-12）**

- **同じ名前の判定は `room-core` の `conflictsWithExisting`（`trim().toLowerCase()` の比較）をそのまま使う。** 参加・改名・代理追加の重複拒否と同じ関数・同じキーで、`"Alice"` と `"alice"` は同じ名前として拒む。全角（`ＡＬＩＣＥ`）・ゼロ幅文字・合成の違いなど #284 で潰した紛らわしい書き方は、先に表示名の規約（`normalizeDisplayName`）が正規形に寄せるので、同じ判定で拒まれる。PR 1 の最初の実装は大文字小文字を区別する完全一致を写しており、参加の拒否と食い違っていた
- **見え方の骨格（`nameSkeleton`・キリル文字の `В` と Latin の `B` など）では拒まない。** `room-core` の線引き（「検出は寛容に、拒否は厳格に」・`display-name.ts` の冒頭）に従う。骨格で拒むと `Вова` のような正当な名前が弾かれる。円盤の上で見分けが付かない組は、web が骨格で見分けて識別子を添える（timer・玄関の `participant-label` と同じ）余地を残す
- **関数の渡し方は「ポート（関数の引数）」を採る。** `roulette-core` は `room-core` に依存できない（`docs/adr/0017` 決定 1・2・`docs/adr/0026` 決定 1）。型 `NameConflict` を `roulette-core` に置き、同期サーバーと web が `conflictsWithExisting` を渡す。乱数（`randomInt`）を引数で受けるのと同じ形
  - 退けた案: **共有パッケージへ移す** —— 表示名の規約は `room-core` の持ち物で、`roulette-core` のためだけに切り出すと文脈の境界（ADR 0017）を動かすことになる。**`roulette-core` で写す** —— 写しは片方だけ直る（この指摘そのもの）。**名前の比較をアプリ層だけで行い、`addGuest` に「衝突しているか」の真偽を渡す** —— `poolOf` は web も使うので、web 側にも同じ組み立てが要り、写しが 2 つになる
- **足した後で同じ名前の人が参加・改名したら、入る人の段（`poolOf`）でゲストを外す（在室者が勝つ）。** ゲストの追加だけで拒むと、後から同じ名前で参加・改名した人とゲストが円盤に 2 席並ぶ
  - 比べる相手は**在室者（外したかを問わない）**。外した在室者と同じ名前のゲストも外す（外した人がゲストの席で戻ってこない）。離席中の参加者とは比べない（離席中の参加者は円盤に居ないので 2 席にならない）
  - **状態からゲストを消さない。** 在室者が抜ければまた入る。足した人の操作を、別の人の参加が黙って取り消さない
  - 退けた案: **参加・改名を拒む** —— 参加と改名は全ツールの共通の入口で、ルーレットのゲストのためにハブ・timer・poker の参加を拒むと他のツールへ波及する。**参加・改名のときにゲストを消す** —— 名簿の変化がルーレットの状態を書き換える経路が増え、保管と配信の対（§5.2）が名簿の配信の側にも要る
- **外れているゲストの印は、ルーレットのフレームに載せない。** web は名簿（`roster`）とルーレットの状態から同じ `poolOf` を呼び、「ゲストのうち外しておらず、入る人に居ない人」を「同じ名前の人がいるため外れています」として出す（PR 2）。フレームに載せると名簿が変わるたびにルーレットの配信も要り、経路が 2 本になる（R14 と同じ理由）。印の判定のための関数を公開契約に足すと、製品コードの使い手が居ないまま SC-039 が後退する

**一周の規則の細部（R6）**

- `eligible = pool − drawn`。空なら周を閉じる: `drawn = []`、`eligible = pool − {直前の当たり}`（pool が 2 人以上のとき）
- 周の途中で入ってきた人は `drawn` に居ないので、その周の残りに入る
- 周の途中で外された人・居なくなった人は、`eligible` から自然に落ちる（`drawn` に残っていても害は無いが、`prune` で落とす）
- **pool が 2 人のときは当たりが必ず交互になる**（A → B → A …）。E2E はこの性質で「サーバーが一周の規則で引いている」ことを決定的に確かめる（§8）

### 5.3 wire

**コマンド（ルーレットの接続だけ・すべて `v.strictObject`）**

| コマンド | 形 | 失敗 |
|---|---|---|
| `roulette.spin` | `{}` | `ROULETTE_SPINNING` / `ROULETTE_TOO_FEW` / `ROULETTE_TOO_MANY` / `NOT_IN_ROOM` |
| `roulette.include` | `{ id: string(1〜64), included: boolean }` | `NOT_IN_ROOM`（知らない ID は黙って無視する —— 退出と同時に押されることがある） |
| `roulette.guest.add` | `{ name: string }`（`room.join` の `displayName` と同じく境界で長さを縛らない。正規化と上限 `MAX_DISPLAY_NAME` は表示名の規約が正規化の前後で課す。巨大入力は接続層のメッセージの大きさの上限が落とす） | `INVALID_GUEST_NAME` / `GUEST_NAME_TAKEN` / `TOO_MANY_GUESTS` |
| `roulette.guest.remove` | `{ id: string(1〜64) }` | （知らない ID は無視） |
| `roulette.cycle.reset` | `{}` | — |

`strictObject` にするのは `docs/adr/0011` 決定 2 の S3（余剰フィールドを拒む）。新しいコマンドには古いクライアントが居ないので、厳しい側から始める（`room-core` の `room.check` と同じ理由）。

**フレーム（サーバー → ルーレットの接続）**

```ts
{ type: "roulette", state: RouletteView }

interface RouletteView {
  excluded: string[];
  guests: { id: string; name: string }[];
  drawn: string[];
  spin: null | {
    seq: number;
    wheel: { id: string; name: string }[];
    winnerIndex: number;
    settle: number;
    spunBy: string;
    durationMs: number;     // SPIN_DURATION_MS
    elapsedMs: number;      // 送る時点の経過（0〜durationMs に丸める）。R5
  };
}
```

- 受けるフレームは非 strict の `v.object`（サーバーが項目を足しても古い web がフレームごと捨てない。`room-core/src/wire.ts` の規律）
- エラーは `{ type: "error", code, message }`（ハブの形）。コードは `roulette-core` の `ROULETTE_ERROR_CODES`、文言は `roulette-core` の文言表（書体の base 層の検査を当てる）。`ROULETTE_ERROR_CODES` は上の表のコードに加えて、境界と接続層のコード（`INVALID_JSON`・`INVALID_COMMAND`・`MESSAGE_TOO_LARGE`・`INTERNAL_ERROR`）を持つ。**ルーレットのメッセージ層の `fail` と接続層の `sendRouletteFrame` が返すものだけ**で、どちらも型でこの列挙に縛られている。ドメインの `INVALID_SETTLE` は載せない（§5.1・`INTERNAL_ERROR` に畳む）。使わない `RATE_LIMITED` は PR #355 のレビューで外した
- **参加の失敗（`ROOM_NOT_FOUND`・`JOIN_RATE_LIMITED`・合言葉の誤りなど）は `ROULETTE_ERROR_CODES` に載せない。** `join-room.ts` が返すハブのコード体系で、ハブと同じ形（`HubServerMsg` の `error`）で届く。お題（#91）の `TOPIC_ERROR_CODES` と同じ線引きで、web は下の順で `roulette` に合わなければハブの形として受け取り、`@tasuki/sync-client` の `planForJoinError` で扱う（PR 2 のレビューで写しを寄せた・§5.6「写しの扱い」）。web がルーレットのエラーのスキーマ（`RouletteErrorFrameSchema`）で参加の失敗を検めてはならない（落ちる）。`RouletteErrorFrameSchema` はサーバー側の狭い型（`RouletteOwnFrame`）のためにある
- ルーレットの接続が受け取るのはこれに加えて、ハブと同じ形の `room.joined`・`roster`・参加の失敗と、お題の `topic` フレーム

**web の見分ける順**: `topic` → `roulette` → ハブの形（`HubServerMsgSchema`）。どれにも合わなければ捨てる（`apps/topic-web/src/server-message.ts` と同じ形）。

### 5.4 揮発と寿命

- 状態はルームの寿命と同じ。ルームが破棄されたら消える（`destroy-room.ts`）。サーバーの再起動ですべて消える（ADR 0007）
- 最初のルーレットの接続が参加した時点で既定の状態（空）を置く。ルーレットを開いていないルームには状態を作らない
- `lastSpin.startedAt` は単調時計の値で、wire に出さない（プロセスの外では意味を持たない）

### 5.5 守り（憲法 XI・`docs/adr/0011`・`docs/adr/0012`）

| 脅威（ADR 0011） | 守り |
|---|---|
| S1 見知らぬ第三者の入室 | 参加は共有の入口（`join-room.ts`）を通す。合言葉の関門・ルームコードのエントロピー・IP 単位のレート制限をそのまま受ける |
| S3 不正・巨大メッセージ | コマンドは `strictObject`・文字列は長さの上限つき。フレームのサイズ上限は接続層（`maxMessageBytes`）が掛ける |
| S4 XSS（名前の描画） | 名前は React の既定のエスケープで描く。円盤の SVG も `<text>` の子に文字列で入れ、`innerHTML` を使わない |
| S7 DoS | ゲストは 12 件まで・円盤は 24 席まで・回転中は次の回転を拒む（約 4 秒に 1 回が上限）。外す・戻すは冪等で、状態の大きさは名簿＋ゲストで頭打ち（`prune`）。**メッセージ単位の新しいレート制限は足さない**（お題の `topic.set` と同じ扱い。足すなら別 Issue） |
| S9 権限のなりすまし | 在室者なら誰でも操作できる（役割は無い）。ルーレットのコマンドはルーレットの接続のスキーマにしか無い（R11） |
| S11 ログ漏洩 | ゲストの名前・表示名・ルームコードをログへ出さない。ルーレットのハンドラはログを書かない |

**データ分類（ADR 0011 決定 1）**: ゲストの名前は表示名と同じ「配信はするがログへ出さない」段。乱数の値・`settle` は分類の外（公開してよい）。

### 5.6 画面 `apps/roulette-web`（見た目は §6）

- 入り方・戻り方・接続の告知・抜けたときの扱いは**お題ツール（`apps/topic-web`）に揃える**（`router.ts`・同期フック・`InviteLink`・`LoadingView`）。名乗りは玄関だけ（`docs/adr/0018`）。純粋な規則は写さず共有から引く（下の「写しの扱い」）
- **知らない下位パスでも `?room=` は落とさない**（`/roulette/x?room=R1` → 玄関の `/?room=R1`）。PR 2 のレビューで、コードを落として玄関の入口へ戻していたのを直した。お題ツールの `router.ts` も同じ形だったので揃えて直した（poker の旧リンクの救済と同じ考え方）
- **同名で外れたゲストの行はチェックを押せない**（`disabled`）。チェックを入れても `poolOf` が外すので押しても何も起きない。押せない理由は印「同じ名前の人がいます」を `aria-describedby` でチェックの説明に結び付けて読み上げる（PR 2 のレビュー）

## 6. 見た目（`frontend-design` の指針に沿って決めた）

### 6.1 方向

**卓の上のルーレット。** Tasuki の世界観「夜のカードテーブル」（深緑のフェルト・象牙の札・真鍮）に、カジノの卓に置かれる真鍮縁のルーレットを 1 台据える。
**大胆にするのは 1 か所だけ —— 円盤と、止まった瞬間に札がめくれる 1 回の演出。** 周りの区画（入る人の一覧・招待）は既存の部品のまま静かに置く。

避けたもの（よくある既定の見た目）:

- **虹色の扇形の円盤**（抽選ツールの定番）。色で席を分けると卓の配色が壊れ、色だけで人を区別することにもなる。席は**フェルトの濃淡の交互**（700 / 900。奇数のときだけ最後の席を 800・§6.2）と、真鍮の細い仕切り・縁の鋲で分ける
- 当選者を紙吹雪や大きな絵文字で祝う演出。進行役は「罰ゲーム」でも「景品」でもない。**卓に札が 1 枚配られ、めくれる**だけにとどめる
- 数字の大きな見出し＋小さなラベル＋グラデーションの帯（KPI 風）。結果は名前そのものを主役にする

### 6.3 円盤（SVG）

- `viewBox="-122 -122 244 244"`（正方形。指し針が下にも右にも出られる余白を取る）。縁 r=106（真鍮）・席 r=21〜93・中心 r=21・鋲 r=101.5 の円周上
- 0° は真上・時計回り。席 i は回転子の座標で `[i·s, (i+1)·s)`（`s = 360/n`）
- **指し針は円盤の外にあり、並び（§6.7）で位置が変わる**: 縦積みでは真下（180°）、横並びでは右（90°）。どちらも札の側を向き、**当たりの席 → 指し針 → 札** が一続きに見える。指し針は台座を支点に弾む
- **席の名前の向き**（4 版・**利用者の決定 案 2「いまの方式（半径に沿わせる＋字の傾きの上限）を磨く」**・2026-10-13）。`labelPlacement(mid, rotorDeg, kind)` が席ごと・フレームごとに 3 つの書き方から選ぶ（回っている間も毎フレーム決め直す。n ≤ 24 個の transform を書くだけ）:
  - **半径に沿う横書き**（`radial`）: 字の傾きが上限以内なら常にこれ。上限は名前の性質（`labelKindOf`）で変える —— **長い名前（全角主体で 4 字以上）は 45°、欧文（半角が空白を除いて半分以上。半角はラテン 1 までと半角カナ・半角の句読点 U+FF61〜FF9F —— 「ﾔﾏﾀﾞ」は欧文と同じ扱い）と短い名前（全角主体で 3 字まで）は 60°**。行が外へ進むなら行の終わりを縁（r=84）に、内へ進むなら行の始まりを縁に置く
  - **半径に沿う縦書き**（`vertical`・`writing-mode: vertical-rl`）: 上限を超える席（半径が画面の縦に近い席）の、全角主体の名前。字の傾きは長い名前で 45°・短い名前で 30° 以内。**空白は詰める**（縦書きでは 1 字ぶん空いて「佐藤　花子」が間延びした）。混じった欧文の字は立てる（`text-orientation: upright`）
  - **半径を横切る横書き**（`across`）: 上限を超える席の欧文。行は半径に直交し、字の傾きは縦書きと同じ（30° 以内）。中心 r=78 に中央揃えで置き、字の内側の端（r=73）での席の弦から 2 ずつ空けた幅に収まるよう切る（`acrossMaxEm`。切ったら `…` のぶんも空ける）。12 席で「O'B…」になる
  - **選んだ理由**: (1) **欧文を縦に積むと読めない**（3 版の追補で立てて積んだ「M／i／k／a」を統括が読みにくいと指摘）。欧文は横書きで読ませ、縦の半径の席では半径を横切らせる。(2) **2 字の名前の縦書きが 30° を超えて傾くと、2 字が画面の左右に並んで逆順に読める**（「山田」が「田山」・2026-10-13 の 1280・1440・1920 の撮影。字は倒立していなかった —— 画素で約 +30°・`getScreenCTM` で +32°）。短い名前は 60° までの横書き（左から右へ読める）を優先し、縦書きは 30° 以内の立った列にだけ使う。(3) **長い名前は 45° のまま**: 4 字以上の列は斜めでも列として読め、横書きを 60° まで寝かせるほうが読みにくい
  - **退けた細部**: 縦中横（名前全体を横に組むので半径を横切る横書きと同じ見た目になり、行の幅が席の弦を超える）／欧文を縦書きの席で横倒しにして字の傾きを 90° まで許す（統括の撮影で読めないと判断）／全部の名前の上限を 60° にする（長い名前が斜めに寝て、3 版より読みにくい）／欧文だけ字を小さくする（書体スケールの外の値が増える）
  - 2 版の「右半分は中心→縁」は真下に近い席で字が 60° 前後まで寝た（2026-10-12 の 1440 の撮影の「山田」）。3 版は「字の傾き ±45°」に揃えた
- **縦書きの欧文の字は立てる**（`text-orientation: upright`）。既定の `mixed` では、ブラウザは縦書きの欧文・数字・記号を **90° 回して横倒しに組む**（Chromium の `getRotationOfChar` で実測: 「Mika」の各字が 90・「山田」は 0）。3 版の `labelPlacement` は「縦書きなら字は立つ」を前提にしていたので、縦書きの席に入った欧文の名前は画面上で 90° ± 傾きだけ倒れた（2026-10-13 の 768 の撮影の「Mika」・E2E の実測で 106.4°）。**単体の「全組で ±45°」は関数の戻り値（`rotate + 回転子`）だけを測り、字の組み方を見ていなかったので緑だった**（物差しが実装と同じ前提）。4 版では欧文が主の名前を縦書きにしないので、立てる字は全角主体の名前に混じった欧文だけ。立てた字は 1 字が 1em を取るので、縦書きでは `fitLabel(name, maxEm, true)` が半角も 1 で数える
- **当たりの席の名前の太さは変えない**（色だけで示す）。書体の 700 は base 層しか無く、**名前の漢字を 700 で引くとシステムの書体に落ちる**。落ちた先（この環境では WenQuanYi Zen Hei・CDP の `CSS.getPlatformFontsForNode` で実測）は縦書きの字の送りが 0 で、幅 320 の当たりの席（真下＝縦書き）の「健太」が 1 字に重なり、行の長さも 0 と数えられて `text-anchor: end` の行が縁の外（r=104〜106.5）へ伸びて指し針に掛かった（`getExtentOfChar` の高さ 0）。ext 層の 700 を足すと 1 太さで約 210KB 増えるので、太さを 500 に揃える。**一度は「Chromium が縦書きの `end` を効かせない」と診断して基準点を置き直したが、書体を測り直して誤りと分かり戻した**
- 物差し（**描かれた結果を測る**）:
  - **E2E**（`e2e/specs/roulette.spec.ts`・既存の 1 ルームに相乗り）が正。`expectWheelGlyphsUpright` —— 全 `<text>` の全部の字について、`getScreenCTM()` の回転成分 `atan2(b, a)`（回転子と名前の `rotate` をブラウザが合成したもの）に `getRotationOfChar(i)`（ブラウザがその字を回して組んだ角度）を足して画面上の字の傾きを出し ±60° 以内、計算値の `writing-mode` が縦の名前に欧文が主のものが無い、半径を横切る欧文の名前（行の向きと「円盤の中心 → 名前の箱の中心」の成す角が 60° 以上）がある。`expectWheelLabelsInsideSeats` —— 描かれた箱（`getBoundingClientRect`）の四隅の中心からの距離が 95 以内（下半分の縦書きの席があることを先に見る）。`expectWheelLabelsUseWebFonts` —— 名前ごとに描くのに使われた書体が全部 web フォント（CDP）。**欧文だけで 6 席・3 席にすると、どの角度で止まっても縦から 30° 以内の半径の席が必ずできる**（半径の向きは 180° の剰余で 60° おき）。漢字 2 字だけで 6 席にすると、幅 320 では当たりの席が真下の縦書きになる。乱数の止まり方に頼らず局面が成立する
  - **単体**（`tests/wheel-glyphs.test.tsx`）は描かれた `<Wheel>` の DOM の transform の文字列（回転子と名前）を読んで足し、縦書きの席では `index.css` の `text-orientation` を読んで `mixed` なら欧文を 90° 回す（上の実測の規則の写し）。ほかに、縦書きの席に欧文が主の名前が無いこと、横切る名前の幅が席の弦以内、`.wheel-label` 系の太さが `fonts.css` の ext 層の太さにあることを見る。jsdom は CSS を当てず字も組まないので、**単体はブラウザの組み方の写しを持つ限界がある**。全角度・全席数を速く回せる側で、正は E2E
  - 関数の性質（`wheel-motion.test.ts`）は全組で「字の傾きが上限以内・欧文は縦書きにしない・行（横切るなら行に直交する向き）が半径に沿う」を見る。これは関数の戻り値の検査で、描かれた姿は上の 2 つが見る
- **入る字の幅は `fitLabel(name, maxEm)` の純粋関数で切る**（全角 1・半角 0.6 で数え、溢れたら `…`。半角の範囲は `labelKindOf` と同じ `isHalfWidth` —— PR #383 のレビューで、半角カナを全角と数えて「ﾔﾏﾀﾞ」が長い名前として縦に積まれ 5 字で切られるのを直した）。12 席までは 5.5 字ぶん、13 席以上は 4 字ぶん。縦書きの席でも同じ `fitLabel` で切る。切った名前の全体は脇の一覧で読める
- 円盤は `aria-hidden`。読み上げは結果の一言（§6.8）が持つ
- **描く席**（`wheelSeatsOf`・PR #383 のレビュー）: 回転があれば、**次に回すまで回したときの並び（`spin.wheel`）を描き続ける**（回っている間も、止まった後も）。当たりの席は止まってから示す。回したことが無ければ、いまの入る人を描く。
  - **理由**: 止まる角度は `spin.wheel` の席数と当たりの添字で計算する。初版は止まった後に「いまの入る人」と回したときの席が同じなら当たりの席を示し、違えばいまの入る人を当たり無しで描いた。止まった後にゲストを足す（席数が変わる）と、角度は 2 席で計算したまま 3 席を描き、**針は別の人を指し、札は本当の当たりを見せた**。名簿の順だけが変わる（再接続）と、順込みの比較で「違う」と判定され、当たりの席の強調が消えた
  - **退けた案**: 止まった後はいまの入る人を描き、当たりの席を指すよう角度を組み直す —— 当たりの人が入る人から外れていると指す席が無く、組み直すたびに円盤が跳ぶ。止まった後の円盤は「その回の結果」として、結果の一言（発表した結果は次の回転まで消さない・§6.8）と同じく次の回転まで保つ。いまの入る人は脇の一覧が持つ
  - 単体（`tests/wheel.test.tsx`「止まった後に入る人が変わる」）は、描かれた DOM（回転子と指し針の角度・席の数・席の順の名前）から針の下の名前を引き、札の名前と比べる
- **席ごとの計算は回転のたびにしない**: 名前の性質（`labelKindOf`）・3 つの書き方それぞれで切った名前（`fitLabel`）・扇形と鋲の位置は席の並びだけで決まるので、並びが替わったときだけ組む（`useMemo`）。毎フレーム決めるのは向き（`labelPlacement`）だけ

### 6.4 回して止める（1 回の演出）

- **長さは `SPIN_DURATION_MS = 4000`・余分の周回 `TURNS = 4`・減速は 3 次（`easeOutCubic`）**（2 版。初版の 4800ms・5 周・4 次の減速は、最後の 1 秒以上がほとんど動かず、利用者側では 8 秒以上に感じられた）。3〜4 秒は「誰になるか」の間が持ち、待たされた感じが出ない長さとして選んだ。4 次の減速は終わり際が長すぎるので 3 次にした
- **止まる角度**は純粋関数 `finalAngle(n, winnerIndex, settle, pointerDeg, startDeg) = startDeg + 360·TURNS + ((pointerDeg − (winnerIndex + settle)·s − startDeg) mod 360)`。**360° の剰余は `startDeg` に依らない**ので、どの画面も同じ席で止まる。`startDeg` は回し始めにその画面が見せている角度で、**0° へ戻さない**（戻すと、前の回転の止まった位置から一瞬で跳ぶ）。途中から合流した画面は `startDeg = 0` から始めてよい（見え始めが途中なので跳びは見えない）
- **角度の時間変化**は `angleAt(elapsedMs) = startDeg + (finalAngle − startDeg) · easeOutCubic(elapsed / duration)`。どちらも `apps/roulette-web/src/wheel-motion.ts` に置く
- **止まったかの判定は画面の 1 か所**（PR #383 のレビュー）: 画面（`RouletteRoom`）の局面 `phaseOf`（時計は `useNowMs` の 1 つ・経過は `elapsedOf`）が決め、円盤（`Stage` → `useWheelRotation`）は局面を受けて止まる。札・当たりの席・結果の一言・一覧の「選ばれた」は**同じ瞬間に**切り替わる。初版は円盤が自前の時計（rAF ＋自前の終わりの timer）で止まり、終わり際に札と当たりの席は止まった姿、一言と一覧はまだ回転中、と食い違った（画面の timer は終わりの 30ms 後に描き直す）。円盤の角度は同じ `elapsedOf` で出し、`durationMs` で頭打ちになるので、局面が切り替わる瞬間に跳ばない。単体は終わりの時刻の前後を 10ms ずつ刻み、4 つが毎回同じ局面であることを見る
- 描画は `requestAnimationFrame` で回転子（`<g>`。席・名前・鋲を含む）の `transform` と名前の向きを書く。**終わりは rAF に頼らない**: 回し始めに残り時間ぶんの `setTimeout` を置き（画面の `useNowMs`）、時刻が来たら必ず止まった状態にする（裏のタブやヘッドレスのブラウザでは rAF が止まる・間引かれる。2026-10-12 のヘッドレスの撮影で、4 秒の回転が 14 秒後まで止まって見えなかった）。止める処理は二重に呼ばれても 1 回だけ効き、前の回転の timer や rAF は今の回転を止めない。**途中から合流した画面は `elapsedMs` から始める**
- 席の境目を指し針が通るたびに、指し針を 120ms だけ 12° 弾ませる（減速すると間隔が開き、止まる直前に「カチ、…カチ」と緩む）
- 止まったら:
  1. 当たりの席が真鍮の地に変わり、名前の向きが整う（320ms の `fill` の移り変わり）
  2. 指し針の先に伏せて置いてあった象牙の札が**めくれる**（`rotateY(180deg)`・640ms・少し跳ねる曲線）。表は「次の進行役」と名前・「さん」だけ
  3. 札の下の一言が「次の進行役は ○○ さんです」に変わる（読み上げ）
  4. 札が画面に見えていなければ、札を見える位置へ寄せる（`scrollIntoView({ block: 'nearest' })`。見えていれば動かさない。動きを減らす設定では滑らかにしない）。下端の帯の分は要素層の `scroll-padding-block-end` が空ける。**他の人が回したときも同じ**（2026-10-12 利用者が推奨のまま承認）
- **同じ `seq` の再描画では回し直さない**（外す・戻すで状態が配り直されても、回転は続く）。新しい `seq` を受けたときだけ回し始める
- **同じ `seq` のフレームでは、回転の基準（受け取った時刻 `receivedAt` と経過 `elapsedMs` の組）を前のまま保つ**。回転以外（外した人・ゲスト・一周の記録）は新しいフレームのものを採る。PR 2 のレビューで、古い `receivedAt` に新しい `elapsedMs` を足して経過を二重に数え、回転中の外す・戻すや再接続のたびに止まる時刻が前へずれる（画面ごとに当たりの出る時刻が違う）のを直した
- 回し始めたら札は伏せ直す（裏に戻る）
- **回っている間は並び（縦積み／横並び）を変えない**。止まっている間に並びが変わったら、新しい指し針の位置で止まった角度を置き直す。**凍結は「測った値」を保つ**: 舞台が付いたら、回っている最中でも必ず 1 回測る（§6.7）

### 6.5 動きを減らす設定

- `matchMedia('(prefers-reduced-motion: reduce)')` が真なら、**回さずに最終の角度へ置き**、当たりの席と札の表をその場で出す。指し針は弾ませない
- CSS の移り変わり（札のめくり・席の色）は要素層の一括の手当て（`elements/reset.css` の `transition-duration: 0.01ms`）に乗る。**rAF の回転はその手当ての外なので、JS で止める**（ここを忘れると設定を無視して 4 秒回る）
- 回転中もサーバーは次の回転を拒む（R9）。動きを減らした画面にも「回しています…」は約 4 秒出る（他の画面がまだ回っているため）

### 6.7 段組み（320px〜1920px）

器は `.ui-page .ui-page--wide`（道具の部屋）。区画は `.ui-workspace .ui-workspace--side-end`（脇を右・既定 22rem）。
**操作の面（円盤）が主役、脇（入る人）は操作の合間に横目で見るもの**なので右へ置く（`packages/ui/README.md`「選び方」）。

DOM の順（狭い幅で見せたい順・読み上げの順）: 見出し（h1 と戻る）→ お題の添え書き → 円盤 → 札 → 一言（`role="status"`）と回す → 入る人の一覧 → 名前を追加 → 一周の行 → 仲間を招く（招待）。

**入る人の一覧の行は名前を先に読ませる**（2026-10-13）: 名前（ラベル）は中身の幅より縮まず、印（離席中・選ばれた）と「名前を消す」の塊が入らない幅では塊ごと次の行の右へ回る（`flex-wrap`）。名前は行の幅を超えるときだけ `…` で切る。幅 320 の撮影で、2 つの印に幅を取られて「山田」が「山…」に切れていた。E2E は `expectRouletteNamesNotCut`（`.roulette-name` の `scrollWidth` と `clientWidth`）で、印と名前を消すを持つ行があることを先に見てから測る。退けた細部: 印を 1 字に縮める（「選」は意味が取れない）／印を名前の下に常に置く（広い幅でも行が 2 段になり一覧が長くなる）

**操作の面（舞台）の中の並びは 2 つ**（2 版）。**舞台の幅**で決める（画面の幅ではない —— 脇の有無で舞台の幅が変わる）。
判定は純粋関数 `stageLayoutFor(widthPx)`（720px 以上で横並び）にし、`ResizeObserver` のフックが `data-layout` に書く。
**舞台が付いたら凍っていても必ず 1 回測り、測るのは描く前（`useLayoutEffect`）**（PR #383 のレビュー）。初版は最初の測りも凍結に従わせ、`useEffect`（描いた後）で測っていた。回転中にマウントした画面（再読み込み・途中入室）は、広い舞台でも回っている間ずっと縦積み（指し針が下）のまま凍り、止まった瞬間に横並びへ跳んで止まる角度が 90° 変わり、円盤が一瞬で回った。回っていなくても、広い舞台で 1 フレームだけ縦積みが描かれてから横並びへちらついた。**守りは単体**（`tests/wheel.test.tsx`「回転中にマウントした広い舞台」・m183）。E2E で回転中に再読み込みする形も試したが、実際のブラウザでは参加の返事（`room.joined`）が回転の状態より先の描画に届き、舞台は回転の前に一度測られるので、m183 を当てても緑だった（恒真なので足していない）。凍結の前に測れない局面は、参加の返事と回転の状態が同じ描画に入るときだけ起きる
**指し針の位置（§6.3）も同じ値から決まる**ので、CSS のコンテナクエリと JS の判定を二重に持たない。

- **入る人の一覧の 1 行は [チェック][名前][印][名前を消す] を横に並べる**（2 版）。⚠ **要素層の `label` は `display: flex; flex-direction: column` で縦に積む**（`elements/controls.css`）。行の中のラベルは画面のクラスで `flex-direction: row` に戻す（初版はこれを書かず、チェックボックスが名前の上に単独で載った）。行全体が `<label>` で、高さは 44px

### 6.8 a11y

- 結果の一言は `role="status"`（`aria-live="polite"`）。**止まってから**文言を入れる（回し始めた時点で当たりの名前を入れると、読み上げが演出より先に結果を言う）。回し始めは「{名前} さんが回しました」
- **止まった結果は「2 人から回せます」より先に言う**。発表の後で入る人が 1 人に減っても、発表した「次の進行役は ○○ さんです」を消さない（PR 2 のレビュー）
- 回っている間、脇の一覧の「選ばれた」印と一周の数、円盤の「選ばれた人」の沈んだ席は**今回の当たりを除いて**出す（見た目でも先に結果が分からないように。§6.4 の 3 と揃える）
- 円盤は `aria-hidden`・`focusable="false"`
- フォーカスの輪は要素層が持つ（roulette-web は 3 層とも読む）。画面で `outline` を書かない
- 色だけで状態を示さない: 選ばれた人は印（「選ばれた」）・離席中は印（「離席中」）・外した人はチェックの有無

モックの JS（`stageLayoutFor` / `pointerDegFor` / `finalAngle` / `angleAt` / `toneOf` / `labelPlacement` / `fitLabel` / 一周の引き方）は実装の純粋関数の下書きでもある。名前の向きは毎フレーム `orientLabels(rotorDeg)` で決め直す。
`finalAngle` と `labelPlacement` は、モックの値を別の計算（指し針の点を回転子の座標へ戻して `atan2` で席を引く・画面上の字の向きを角度から出す）に当て、n = 2〜24・全席・`settle` 3 点・回し始めの角度 4 点・指し針 2 か所で食い違いが 0、`labelPlacement`（3 版）は回転子の角度と席の位置の全組で字の傾きが最大 45°・半径からずれた行 0 であることを確かめた（node で計算しただけ。**画面で撮って確かめてはいない** —— この担当は Playwright を動かさない）。

## 8. 検証

### 8.1 EARS

**状態と抽選**

- E1 システムは、常にルームごとに高々 1 つのルーレットの状態を持ち、ルーレットの接続が初めて参加するまで持たないこと
- E2 利用者がルーレットを回したとき、システムは入る人のうち、この一周でまだ選ばれていない人から 1 人を選び、その結果をそのルームのすべてのルーレットの接続へ同じ形で配ること
- E3 この一周で全員が選ばれていた場合、システムは新しい一周を始め、入る人が 2 人以上なら直前に選ばれた人を新しい一周の最初の抽選から除くこと
- E4 入る人は、在室の参加者のうち外されていない人と、外されていない追加の名前であること。離席中の参加者は入らないこと
- E5 回っている間に回す要求を受けた場合、システムはその要求を拒否し、回っている結果を変えないこと
- E6 入る人が 2 人未満、または 24 人を超える場合、システムは回す要求を拒否すること
- E7 システムは、ルーレットの状態を配るとき、回した時点からの経過を送る時点で計って載せ、絶対時刻を載せないこと
- E8 接続がルーレットへ参加・復帰したとき、システムはその接続へいまのルーレットの状態（回っている途中なら経過を含む）と名簿を送ること
- E9 ルーレット以外の接続からルーレットのコマンドを受信した場合、システムはそれを不正なメッセージとして拒否し、状態を変えないこと
- E10 ルームが破棄されたとき、システムはそのルームのルーレットの状態を破棄すること
- E11 名簿が変わったとき（参加・退出・接続の着脱）、システムはそのルームのルーレットの接続へ新しい名簿を配ること
- E12 お題の状態が変わったとき、システムはそのルームのルーレットの接続へもお題の状態を配ること

**名前の追加**

- E13 利用者が名前を追加したとき、システムは表示名の規約で正規化し、規約を満たさない名前・既に居る名前・13 件目を拒否すること
- E14 システムは、常に追加の名前と表示名をログへ出力しないこと
- E15 境界で余剰の項目や形の不正なルーレットのコマンドを受信した場合、システムは検証エラーとして拒否すること

**画面**

- E16 新しい回転を受け取ったとき、画面は受け取った経過から回し始め、残りの時間の後に、全画面で同じ席（当たりの席の `settle` の位置）で止めること
- E17 同じ回転の状態を再び受け取ったとき、画面は回し直さないこと
- E18 動きを減らす設定が有効な間、画面は回さずに結果をすぐに出すこと
- E19 円盤が止まったとき、画面は結果を読み上げの領域に出すこと。止まる前に当たりの名前を読み上げの領域・一覧の印・一周の数に出さないこと
- E20 ルームにお題がある間、画面はお題のタイトルを添えて出すこと
- E21 画面は 320・768・1280・1920px の幅で横に溢れず、押せるものは 44px 以上で重ならないこと
- E22 円盤が止まったとき、札が画面に見えていなければ、画面は札を見える位置へ寄せること（他の人が回したときも）

## 12. 実装で実測して外したこと（2026-10-13・#94 PR 3）

§11.2 の「実装時に確かめること」のうち、円盤と見た目に関わるものの答え。

- **円盤の SVG の `<text>` はコントラストの走査に入らない。** `scanContrast` の対象は `button` / `a` / `h1`〜`h3` / `label` / `p` / `span` だけで、2026-10-13 の探索（止まった後の 1280px の画面）で円盤の席の名前は 0 件だった（測った 20 件は札・見出し・ボタン・脇の字）。そこで `e2e/support/roulette.ts` の `expectWheelLabelsReadable` が、席の名前の塗りと同じ席の地の塗りの比（AA 4.5:1）を測る。地の上の光沢（`--ivory-inset` → `--felt-grain`）は測っていない（席の明度を数 % 動かすだけ）。**止まった席（真鍮の地 + `--on-gold`）も同じ測り方に入る**
- **`scripts/audit-ui-components.mjs` は TSX の `style` の中の生の色を拾わない。** `style={{ stopColor: '#ff0000' }}` も `rgb(255 0 0)` も「違反 0 件」だった（実測）。CSS の `stop-color: #ff0000` は拾う。そこで `<stop>` の色は CSS のクラス（`.wheel-stop--brass-lift` など）で当てた。**同じ穴は `style` 属性を使う他の画面にもある**（この PR では塞いでいない）
- **縦書きの席（`writing-mode: vertical-rl`）の字の中央合わせ。** 単体では傾き・向きを全組で測った（`labelPlacement`）が、描いたときの縁の点との位置は 2 席と 6 席の撮影で見ていない。実画面検証（統括）の観点に残す
- **名前の向きの切り替え（45° の境目）のちらつき。** ヒステリシスは入れていない。回転は 4 秒で減速するため境目を通る回数は少ない見込み。実画面で気になれば足す
- **モックから外したもの**: モックの `.roulette-stage` は `grid-template-columns: var(--wheel-size) …` と書いていたが、`--wheel-size` は `cqi`（舞台の幅）で書いてあり、舞台**自身**のこのプロパティでは `cqi` が舞台の外の容器を指して画面の幅で解かれる。1280px で列が舞台より 40px 広がり、円盤と札が左右へはみ出した（モックの 1440px では舞台が広く出なかった）。列は `auto`（円盤の幅に任せる）にした。脇のパネルの列も `minmax(0, 1fr)` にした（名前が 1 行で切れない幅だと、既定の `auto` が名前の長さで列を広げ、320px で右へはみ出した）
- **止まったら札を寄せる処理の検査は、先頭にいると空振りする。** 320×640 で先頭から回すと札が最初から見え、寄せる処理を外しても E2E が緑のままだった（対照実験で確認）。下までスクロールしてから DOM の `click()` で回す形にして、寄せる処理を外すと赤になることを確かめた（`click()` は押す前にボタンを自分で見える位置へ寄せ、札も一緒に見えてしまう）
- **同期フックの基準の組**: 円盤の回転フックは `receivedAt` と `spin.elapsedMs` の組から経過を出す。同じ `seq` の再配布で `receivedAt` が前のままで `elapsedMs` だけ新しくなる形（PR 2 のレビュー前）では、経過が二重に足されて円盤が先へ進む。レビュー後の「同じ `seq` では組ごと前のまま」で正しく動く
