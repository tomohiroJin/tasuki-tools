### 2.3 ルームコードのエントロピーと総当たりコスト

`apps/timer-sync/src/adapters/nanoid-code-gen.ts:26-27` にコード生成の経路が **2 つ**ある。

| 経路 | 形 | 推測困難な部分 | 探索空間 |
|---|---|---|---|
| ルーム名なし | `A7K2M9` | 6 文字 / 31 種 | 31⁶ = 887,503,681 |
| **ルーム名あり** | `morning-mob-7f3k` | **4 文字 / 32 種**（`slug` はルーム名から機械的に導ける） | **32⁴ = 1,048,576** |

`room.join` の失敗レート制限は **`connId` 単位で 10 秒あたり 30 回**
（`handlers.ts:142,148`）。**キーが接続なので、再接続すれば窓はリセットされる。**
同時接続の上限は 200（`MAX_CONNECTIONS`、`deploy/timer/env.example`）。

上限まで使った場合の総当たり速度は 200 × 30 / 10 秒 = **600 回/秒**。

| 経路 | 総当たりに要する時間（上式・平均ではなく全探索） |
|---|---|
| ルーム名なし | 約 17 日 |
| **ルーム名あり** | 約 **29 分** |

**パスフレーズ未設定でルーム名を付けたルームは、slug を推測できれば約 30 分で開く。**
`daily` `mob` `sprint-planning` のような slug は推測の対象になる。

> これは Issue #136 の「ルームコードは実質的な入室資格情報である」という主張を、
> Issue 本文より強く裏づける。同時に **#103（IP 単位のレート制限）が S1 の主防御である**
> ことを意味する。接続単位の窓は再接続で回避できるため、単独では総当たりを止められない。

### 3.2 憲法 原則 XI（案）

```
### XI. 秘密と個人情報を持ち込まない

預かる値は分類したうえで、必要な場所にだけ置く。

- サーバーが保持する秘密（トークン・鍵・合言葉）は環境変数のみに置く（MUST）
- 秘密・資格情報・個人に紐づく情報をログへ出してはならない（MUST NOT）
- ログ出力の経路は 1 本に集約し、規範が守られていることを機械的に検査する（MUST）
- 個人を識別しうる値を、目的に必要な期間を超えて保持してはならない（MUST NOT）
- 新しい入力・保持・出力を足すときは、`docs/adr/0011` のデータ分類の
  どれに当たるかを決めてから実装する（MUST）
```

### 3.3 ADR 0011 — データ分類

**分類は 4 段とする。**「個人情報かどうか」の 2 値ではルームコードを分類できない
（個人情報ではないが漏れてはいけない）。現にそれがログに出ている。

| 分類 | 定義 | 該当 | 扱い |
|---|---|---|---|
| **秘密** | 漏れると運営者の資産・アカウントが侵害される | §2.2 の 3 つ | env のみ。コード・argv・ログ・snapshot・エラー・永続化へ出さない。比較は定数時間 |
| **資格情報** | 知っているだけで入室・操作できる | ルームコード / パスフレーズ / `resumeToken` / poker の participant token | ログへ出さない。利用者へは自分の分だけ返す。比較は定数時間 |
| **個人に紐づく** | 個人を識別しうる | 表示名 / IP アドレス（#103 で導入） | 揮発のみ。ログへ出さない。IP はハッシュ化して窓の間だけ保持 |
| **公開可** | 出しても害が無い | 参加者数 / ルーム数 / フェーズ / 経過時間 / エラーコード | 制約なし |

**表示名は「ログへ出さない」が「配信はする」。** 全参加者へ snapshot で配る設計であり、
分類は保持と出力の規律であって、機能の否定ではない。

### 3.4.1 AI お題生成の持ち出し経路と、受容した判断

§2.5・§2.6 の実測から、**本番で次の経路が成立している**。

1. AI が解錠されたルームへ参加する（**新規参加者は自動的に editor**。`config.set` と
   `problem.request` はいずれも editor 以上で通る）
2. `config.set` の `language`（40 字）へ注入文を入れる
3. `problem.request` → サーバーが `claude -p` を `tomohiro` として起動する
4. **Read ツールは許可されている**ので `/opt/tasuki/tasuki-sync.env`（600・所有者 tomohiro）を読める
5. `description`（4000 字）等の自由文字列へ埋めて返す。Valibot の `Problem` 検証は通る
6. ルームの全参加者へ配信される

得られるのは `CLAUDE_CODE_OAUTH_TOKEN` / `AI_UNLOCK_KEY` / `ADMIN_TOKEN` の 3 つ。
入室に必要なのはルームコードのみで（パスフレーズは任意）、§2.3 のとおりルーム名つきの
ルームは総当たりの射程にある。**攻撃者は `AI_UNLOCK_KEY` を事前に知る必要がない。**

**実証していないこと**: 本番に対して注入は行っていない。検証したのは CLI のツール権限の挙動
（手元・CLI 2.1.228・おとりファイル）と前提条件の実測のみである。**40 字で成立する注入文が
書けるかは未検証**であり、ここが崩れれば連鎖は成立しない。本番の CLI は 2.1.178 で版差もある。

**判断（2026-08-13・利用者）: リスクを受容し、実装は先送りする。** 根拠は次のとおり。

- **解錠しなければ経路そのものが存在しない。** `problem-delegation.ts:94` が `room.aiUnlocked` を
  要求するため、解錠されていないルームでは `claude -p` が起動しない。**運用で前提を外せる。**
- AI お題生成の利用は一時的であり、常時解錠しているわけではない
- ルームには寿命があり（アイドル 30 分で回収）、総当たりが成立する窓は限られる
- 万一漏れても**トークンを失効させれば回復できる**（`AI_UNLOCK_KEY` / `ADMIN_TOKEN` も差し替え可能）

**したがって本 Issue では規範のみを定め、実装は #91 の機会に行う**（§4.3）。
規範（§3.5 D10）は先に置くので、次に AI 経路へ触る作業は既定に依存しない形で入る。

> **この判断は「危険がない」ではなく「窓を運用で閉じられ、失効で回復できる」ことに基づく。**
> AI を常時解錠する運用へ変えるとき、あるいは秘密の種類が増えるときは、
> **この判断の前提が崩れる**ため再評価すること。

### 3.5 ADR 0012 — どう守るか

- **D1 ログ経路の一本化（対象は同期サーバー）**: `apps/timer-sync` / `apps/poker-sync` の出力は
  制御されたロガ 1 本を通す。ロガは分類「秘密・資格情報・個人」の値を受け取らない。
  直接の `console.*` は行単位で明示した例外（起動ログ・設定エラー）以外は禁止。
  `process.stdout` への直接書き込みと**未捕捉例外・未処理 rejection のハンドラ**も同じ規律に含める。
  - **ブラウザの `console` は本決定の対象外とする。** 脅威が違う（journal は運用者と
    サーバーに入れる者が読むが、ブラウザの console は利用者本人しか見ない）。
    ただし**分類「秘密」の値をクライアントへ渡さない**という制約は分類表（§3.3）で
    引き続き効く。timer-web の 6 件（§2.2）は例外メッセージのみで、
    資格情報・秘密を含まないことを確認済み。
- **D2 マスキングは部分表示を採らない**: 追跡には**別に発行した相関 ID（`roomRef`）**を使う。
  部分表示は残りの探索空間を縮める（§2.3 のとおり、片方の経路はもともと狭い）。
  相関 ID はプロセス起動ごとのソルトで導出するため、**再起動をまたぐと相関が切れる**。
  揮発インメモリ設計（憲法 III）と整合するので、これは受け入れる。
- **D3 IP アドレス**: 起動ごとのランダムソルトで HMAC-SHA256 した値のみを保持する。
  レート制限の窓が閉じたら破棄する。生の IP は変数を越えて残さない。ログ・snapshot・
  永続化へ出さない。**Caddy のアクセスログは引き続き出さない**（「不在」を「決定」へ格上げする）。
- **D4 秘密の置き場と配り方**: env のみ。サーバー上は 600。配り方・**失効手順**を
  `deploy/README.md` に明記する。子プロセスへは env で渡し argv には載せない（現行維持の規範化）。
- **D5 エラー開示**: 利用者へ返すのはエラーコードと固定文言のみ。例外メッセージ・スタック・
  スキーマ検証の詳細は返さない。**現行の timer / poker はいずれもこれを満たしている**ため、
  実装変更ではなく規範化と検査の対象とする。
- **D6 クライアント保存（考え方のみ）**: 資格情報の保存先は、復帰の要件（同一タブか、端末を
  またぐか）と共有端末のリスクで選ぶ。timer が sessionStorage、poker が localStorage である
  現状はどちらも要件から説明できる。**一本化は参加者・ルームの共通化（提案 #95）の際に行う。**
  本設計では判断基準のみを記録し、実装は変更しない。
- **D7 CSP**: 次を追加する。
  `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`
  - `connect-src` は `'self'` で足りる（WS は同一オリジン。`buildSyncUrl` が `location.host` を使う）。
    公開ドメインを書かないことで、プレースホルダのドリフト源を増やさない。
  - `style-src 'unsafe-inline'` は React の `style={{}}`（§2.2）のため。
    **これを外す条件を ADR に書く**（該当箇所を CSS 変数へ寄せたら外せる）。
  - `frame-ancestors 'none'` は既存の `X-Frame-Options` の上位互換。両方置く。
- **D8 CI の供給網**: `permissions: contents: read` を最小で宣言する。Actions は SHA ピンとする
  （ADR 0010 の trustPolicy の思想を Actions へ拡張）。**Renovate の digest 更新が動くことを
  確認するまでは、ピン＋定期の手動確認とする**（Renovate は GitHub App 有効化済みだが
  「スキャンのみ」で導入されており、PR 作成は未実証）。
- **D9 公開窓口**: `SECURITY.md` を新設する。
- **D10 AI 子プロセス**: 権限を明示的に閉じる（既定に依存しない）。プロンプトへ補間する
  利用者由来の値は境界で**列挙検証**する。
- **D12 ログ行への注入を防ぐ**（**2026-08-13 の計画中に判明**）: 利用者由来の文字列を
  ロガのフィールドへ生のまま渡さない。**整形の側で制御文字（CR・LF・タブ）を必ず除去する。**
  - `requestId` の境界スキーマは `v.pipe(v.string(), v.minLength(1))` で、
    **最大長も文字種の制限も無い**（`packages/timer-core/src/schemas.ts`）。
    そのままログへ出すと改行で journal に偽の行を作れる
  - 呼び出し側の善意に頼らない。**整形関数が必ず落とす**形にする
- **D11 ルームコードのエントロピー下限**: 下限は「**想定される総当たり速度で全探索に要する時間**」で
  定義する。ADR ではその時間の目標値と、前提とする速度（#103 実装前 / 実装後）を明記する。
  - §2.3 のとおり、**現行レート（600 回/秒）では `slug-????` 経路が約 29 分**であり、
    どの妥当な目標値を置いても下限を満たさない。**判定の結論は既に出ている。**
  - 対応の選択肢は「接尾辞の桁数を増やす」「ルーム名つきルームでパスフレーズを必須化する」
    「#103 のレート低減に委ねる」。**いずれも利用者から見える振る舞いが変わるため、
    本 Issue では実装せず §5 に従って別 Issue とする。**

## 6. 検査

**規範は、守られているかを機械が見ないと必ず腐る**（憲法 VII）。

### 6.1 `scripts/audit-log-hygiene.mjs`（新設）

- 制御されたロガ以外からの `console.*` / `process.stdout` への直接出力を検出する
- 許可は**行単位**で明示する
- **最初から fail-closed に作る**: 走査対象の既知の必須ファイルが実在しないとき赤にする。
  許可リストの項目が実在しなくなったときも赤にする

> **数値の下限を直書きしない。** 「走査ファイル数が N を割ったら赤」という形は、
> ファイルが減るたびに「N を下げる」のが赤を消す最短経路になり、
> #70 で踏んだ罠（対応表から項目を消すのが最短経路になる）と同型である。
> **既知の必須ファイルを名前で固定する。**

### 6.2 既存の検査への追加

- ロガの単体テスト: 分類ごとの値を渡して拒否されること
- `scripts/mutation-check.mjs` に「ルームコードをログへ戻す」変異を追加する
- CI の `quality` ジョブへ組み込む

### 6.3 破壊検証（憲法 VII）

**次のすべてで赤になることを確認する。**

| # | 壊し方 | 期待 |
|---|---|---|
| 1 | ログへルームコードを戻す | 赤 |
| 2 | 許可リストを空にする | 赤 |
| 3 | 走査対象の必須ファイルを消す | 赤 |
| 4 | ロガを迂回して直接 `console` を呼ぶ | 赤 |

> 効いておらず、緑を「守れている証拠」と誤読しかけた。

## 8. 受け入れ基準（EARS）

- システムは、常に資格情報・個人に紐づく情報をログへ出力しないこと
- システムは、常にルーム識別のためのログ出力に相関 ID を用いること
- **ルームコードをログ出力へ渡す変更が入った場合**、CI はその変更を検出して失敗すること
- **制御されたロガを迂回して `console` を直接呼ぶ変更が入った場合**、CI はその変更を検出して失敗すること
- **検査の走査対象または許可リストの項目が実在しなくなった場合**、CI は失敗すること
- システムは、常にルームパスフレーズの照合を定数時間で行うこと
- システムは、常に利用者へ返すエラーをエラーコードと固定文言のみで構成すること

### 提案 #91 へ送る受け入れ基準（§3.4.1 の判断による）

本 Issue の完了条件には含めない。規範（§3.5 D10）だけを先に置く。

- **AI お題生成を備える場合**、システムは子プロセスへ渡す権限を明示的に指定すること
- **境界で列挙に含まれない言語・難易度を受信した場合**、システムは検証エラーとして拒否すること

## 11. 最終レビューによる訂正（2026-08-13・実装後）

**3 節の決定案のうち 4 点は、実装と最終レビューを経て変更された。**
規範として効くのは憲法と ADR の側であり、以下は「案がどう変わったか」の記録である。
数値の正本が 2 節である点は変わらない。

| 節 | 案の記述 | 確定した規範 | 理由 |
|---|---|---|---|
| 3.2 | 「秘密（トークン・鍵・**合言葉**）は環境変数のみ」 | 分類「秘密」に限定し、ルームの合言葉（分類「資格情報」）を対象外と明記 | 字義どおり読むと、in-memory Map に保持するルームパスフレーズが憲法の MUST に反する（憲法 2.1.1） |
| 3.5 D1 | 対象は `apps/timer-sync` と `apps/poker-sync` | **対象は `apps/timer-sync` のみ。** poker-sync は明示的な繰り越し | poker-sync の直接出力は `listening` 行 1 本で、テストハーネスとの契約。いま移行しても得るものが無い（ADR 0012 D1） |
| 3.5 D1 | 例外は「起動ログ・設定エラー」 | 実装後に残った直接 `console` は 2 箇所（唯一の実出力口・poker の `listening` 行） | timer-sync の起動ログ・設定エラーはロガ経由になった |
| 3.5 D5 | 「規範化と**検査**の対象とする」 | 「今は規範のみ」。対応する検査は持たない | 返却されるエラーが固定文言かを行単位の検査で判定できない（ADR 0012 D5） |

**6 節の検査に 1 つ足りなかった。** ロガの `fields` は型で守られていたが、**第 1 引数
（`event`）は生の `string`** であり、`` logger.info(`reclaimed ${code}`, { idleMs }) ``
と書くだけで 8 節の受け入れ基準（ルームコードをログへ渡す変更を CI が検出すること）を
すり抜けられた。`scripts/audit-log-hygiene.mjs` に「第 1 引数はその場に書いた文字列
リテラルだけ」という規則を足して塞いだ。あわせて、型の壁（`LogField`）そのものが
消えたときに型検査が落ちるテスト（`apps/timer-sync/test/log/log-safe-type-wall.test.ts`）
を足した。**壁を守る検査が無ければ、壁を広げるのが型エラーを消す最短経路になる。**

**4.1 の 2 番目は振る舞いを変えていた。** `unhandledRejection` のハンドラがログを出す
だけで `process.exit` を呼んでおらず、ハンドラが無ければ exit 1 で落ちていたプロセスが
落ちなくなっていた（Bun で実測）。`uncaughtException` と揃えて `process.exit(1)` を
呼ぶよう戻した。
