## 1. 目的と方針

### 1.1 利用者の言葉（2026-09-27）

> 今の修正の仕方だとプルダウンという共通するデザインを別々に画面毎に作成してしまうことになり、デザインシステムの構築として思わしくない。また、他の部品についてもあわせて新しい画面が作られても統一感のある画面にしていかなければならない。

設計の対話で、利用者は方針を次のように述べた。

> もともと、各機能毎に画面はそれぞれのものとして、別々に考えるがデザインシステムとしての基礎部品は共通の利用できる状態のものを用意していけるように考えていた。あくまで使うかどうかは機能側の表現しだい。
> 最初から全ての部品を使うのではなく、DRY にする必要がある共通部品は一緒にする方針。
> 各機能は別々とはいえ、基本的には同じデザインシステムをベースとして統一感がある画面にしたい。

> 共有部品があっても機能側の見た目が大事なので必ずしも共通部品を使いなさいにしなくても良い。あくまで複数の画面で共通される部品として考えられる場合だけで、できる限り共有していく方針が良い。

### 1.2 方針

- **画面は機能ごとに別々に考える。** どう表現するかは機能側が決める
- **統一感は 2 段で支える。**
  1. **全画面が必ず従う土台**: トークン（色・余白・角丸・影・書体・文字の大きさ 5 段）
  2. **使ってよい共通部品**: 見た目の語彙を CSS のクラスとして `@tasuki/ui` に置く
- **共有するのは、複数の画面で共通する部品だけ。** 条件は ADR 0007 の基準（利用者 2 つ以上・同じ知識の重複）に従う
- **既定は「共有部品を使う」。ただし強制しない。** 機能側が独自の見た目にしたい場合は、**理由を申告すれば外れてよい**（§5）
- **まず CSS の部品を共有する。** 構造まで同じ React の部品を共有パッケージへ上げるかは、実需が出た部品ごとに判断する（Markdown の描画は #315 で判断する。§7）

## 3. 実測した事実（main `7d4a203`）

- `@tasuki/ui` は `tokens/`（4 アプリ）と `elements/`（timer 以外）の 2 層。`exports` は `.`・`./tokens.css`・`./elements.css`・`./base.css`・`./controls.css`・`./card.css`（`packages/ui/package.json`）
- poker・玄関・お題ツールは CSS の先頭で `@import '@tasuki/ui';` を書く。timer は `main.tsx` で `import "@tasuki/ui/tokens.css";` を `./index.css` より先に読む。CSS から `@import` すると Tailwind が展開して書体の `url()` が壊れるため（#297）
- timer の Tailwind 4 のユーティリティは `@layer` の中にある。**レイヤーの外の規則は、詳細度によらずユーティリティに勝つ**
- **poker とお題ツールの `Markdown.tsx` は注釈 1 行を除いて同一**（`diff` の差は 5 行目の「poker-web では」と「topic-web では」だけ）。timer の `Markdown.tsx` は別実装
- 要素層の `:focus-visible` は `outline: 2px solid var(--gold); outline-offset: 3px;`（`packages/ui/src/elements/reset.css`）。お題ツールの入力欄は `offset: 2px`、timer は `var(--signal)`（`--gold-bright`）
- エラーの色: 玄関 `--rose-bright`・お題ツール `--rose-pale`・poker `#f0b5a4`（生の色）。お題ツールの注釈によれば `--rose-bright` は felt-700 上で約 3.55:1、`--rose-pale` は約 5.91:1
- 生の色の禁止を検査しているのは timer の `.tsx` だけ（`apps/timer-web/test/ui/design-tokens.test.ts`）。CSS は見ていない
- `scripts/` の検査はルートから素の `node` で走る。**ルートの `package.json` は CSS の解析器を依存に持たない**（postcss は stylelint と timer の依存木にだけある）

## 4. 部品層の形

### D1. `packages/ui/src/components/` を新設する

```
packages/ui/src/
  tokens/      ← 全アプリ（変更なし）
  elements/    ← timer 以外（変更なし。素の要素）
  components/  ← 新設。全アプリが読める。`.ui-` で始まるクラスだけを定義する
    index.css  ← まとめ読み
    field.css  ← 入力欄の系（PR 1）
    …          ← 後続の PR で部品ごとに 1 ファイル
```

- `exports` に `"./components.css": "./src/components/index.css"` を足す
- `src/index.css`（`@import '@tasuki/ui'` の入口）に `components/index.css` を足す。poker・玄関・お題ツールは読み込みを変えずに部品を使える
- timer は `main.tsx` で `tokens.css` の次・`./index.css` の前に `import "@tasuki/ui/components.css";` を置く（#321 までの暫定。#297 と同じ理由）

### D2. 部品は接頭辞 `ui-` のクラスで表す

- 例: `.ui-field`・`.ui-input`・`.ui-textarea`・`.ui-select`・`.ui-banner`・`.ui-note`・`.ui-panel`・`.ui-page-header`・`.ui-invite`（名前は各 PR で確定する）
- アプリ固有のクラス（`.hub-*`・`.topic-*`・`.invite`）と衝突しない。マークアップを見ただけで共有部品かどうかが分かる
- 変化形は修飾クラスで表す（例: `.ui-banner.is-unreachable`・`.ui-note.is-error`）。既存の `.connection-banner.unreachable` の書き方に倣う
- **クラスを当てたときだけ効く。** 当てなければ何も起きない（使うかどうかは機能側が決める）
- 要素層（`button`・`.card`・`.badge`）の名前と中身は #320 では変えない

### D3. 部品層は `@layer` を使わない

- Tailwind のレイヤー構造に合わせた仕掛けを入れない（#321 で Tailwind が消えても同じ定義のまま使える）
- 上書きは既存の要素層と同じく「**同じ詳細度なら後勝ち**」。画面側の CSS を部品層より後に読めば、機能側の表現が勝つ
- **Tailwind が残っている間の制約**: 部品の規則はレイヤーの外にあるので、timer のユーティリティより必ず勝つ。timer で部品を当てる要素からは、同じ性質を持つユーティリティを外す。#320 で timer に当てるのは**プルダウンだけ**（#319 の写しの解消）とし、ほかの部品は #321 で組み直すときに使う

### D4. 部品と画面の役割分担

- **部品が持つもの**: 見た目と、見た目に関わる知識（16px の下限・`base-select`・AA のための不透明な地・フォーカスのリング）
- **画面が持つもの**: 配置（幅・並び・外側の余白）と、画面固有の上書き

### D5. 画面ごとの値の差は「規則」を 1 つにし、変えてよい値だけをつまみで出す

差のほとんどは、どちらが正しいかではなく**置かれる面が違う**ことから来ている。そこで値ではなく規則を 1 つに決め、機能側が変えてよい値だけをカスタムプロパティ（つまみ）として出す。

**入力欄の系**

| 項目 | いまの差 | 決定 |
|---|---|---|
| 欄の地 | 玄関・お題ツール `--felt-950`（面より沈める）／timer `--panel-2` = `--felt-700`（面より浮かせる） | 規則は「欄は面より沈める」。既定は `--felt-950`。つまみ `--ui-field-bg` を出す。timer は #321 まで `--panel-2` を当て、同じ画面のほかの入力欄（Tailwind）と揃える |
| 一覧（`::picker(select)`）の地 | お題ツール `--felt-950`／timer `--panel-2` | 欄の地と同じつまみを使う（欄と一覧は必ず同じ色） |
| 字の大きさ | 玄関・お題ツール `1rem`／timer `text-sm` | `1rem` に固定する。**つまみは出さない**（iOS の自動拡大を避ける知識なので機能側に変えさせない） |
| フォーカスのリング | 要素層 `--gold`・3px／お題ツール `--gold`・2px／timer `--signal` | 要素層の `:focus-visible` に揃え、部品では書かない。timer は自前の `:focus-visible` が勝つので見た目は変わらない |
| 選択肢のホバー・余白・スクロールバー | 画面ごとに少しずつ違う | お題ツールの値（ホバー `--felt-700`・余白 `--space-*`・つまみ `--gold-edge` と溝 `--felt-900`）を正にする。つまみは出さない |

**告知・一言**

| 項目 | いまの差 | 決定 |
|---|---|---|
| エラーの色 | 玄関 `--rose-bright`／お題ツール `--rose-pale`／poker `#f0b5a4` | `--rose-pale` に揃える（`--rose-bright` は felt-700 上で AA を割る） |
| 接続の帯の地 | poker は半透明の生の色＋`backdrop-filter`／お題ツールは不透明の `--felt-950` | お題ツールの形を正にする（半透明の地は AA を割ることが実測で分かっている） |

**見た目が変わる画面**: 玄関のエラーの文字（少し淡くなる）、poker の接続の帯とエラー（地が不透明になる）。timer は変えない。

## 5. 写しを止める検査と例外表

### D6. 検査 1: アプリの CSS が、共有部品のある要素の見た目を直接書いたら落とす

- 置き場: `scripts/audit-ui-components.mjs` と自己テスト `scripts/audit-ui-components.test.mjs`。CI では既存の `audit-*` と同じ段で流す
- 対象の web アプリは、`scripts/audit-web-sync-boundary.mjs` と同じく**実体から導出して宣言と突き合わせる**（新しい画面が無検査で素通りしない。ADR 0014 決定 1）
- 対象は各アプリの `src` 配下の `.css`
- **検出する規則**: セレクタの対象の要素（最後の複合セレクタの型）が `select`・`input`・`textarea`・`option` のいずれかであるもの、または `::picker(select)` を含むもの
  - 例: `.topic-panel select`・`select::picker(select)`・`option:hover` は落ちる
  - `.hub-input` のように `<input>` に当てるクラスは、CSS だけからは要素が分からないので**落ちない**。クラス名で表す役割の写しは、レビューと README（§6）で担う
- **セレクタは正規表現ではなく CSS の構文解析器で読む。** 一覧（`a, b`）を分けて 1 つずつ判定する（#280 で「1 行に 2 つ書くと片方を見逃す」穴を踏んだ）
- **例外表**: 検査のスクリプトに `{ file, selector, reason }` の配列で持つ。申告した規則は通す
- **例外表の行が実在しなければ落とす**（直したのに行だけ残る腐り方を防ぐ）
- **残る穴**: timer が Tailwind のクラスで `<select>` などを飾る分は CSS に現れないので見えない。#321 で Tailwind が消えれば閉じる

**計画で決めること**: 解析器はルートの依存に無い（§3）。依存木に既にある postcss（と postcss-selector-parser）を直接の依存として宣言するか、stylelint の規則として各アプリに置くかを、計画の段で実測して決める。どちらを選んでも**新しい技術は足さない**（憲法 原則 II）。供給網の検査（ADR 0008）を通すこと。

### D7. 検査 2: 部品層の規則（`packages/ui` の stylelint に足す）

- `src/components/**` のセレクタは `.ui-` のクラスから始める。素の要素は子孫の位置にだけ置ける（`.ui-select option` は可、`select` は不可）。timer へ素の要素の規則が漏れない
- `src/components/**` では生の色（6 桁と 3 桁の `#`・`rgb(` / `rgba(`）を禁じる。値はトークンだけ

### D8. 検査 3: 生の色の禁止をアプリの CSS と要素層へ広げる（epic の最後の PR）

- 先に、残った生の色を 3 つに仕分ける: 部品へ寄せて消えるもの・トークンへ置き換えるもの・パレットの外で正当なもの（影の `rgba(0, 0, 0, …)` など）
- 正当なものは検査 1 と同じ形の例外表に理由を書く
- 部品を寄せる PR ごとに生の色は減るので、仕分けは最後に残った分だけで済む
