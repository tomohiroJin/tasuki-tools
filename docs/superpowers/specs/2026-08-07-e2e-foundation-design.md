# E2E テストの土台（#73）

作成日: 2026-08-07 / 改訂: 2026-08-08（第 2 段・第 3 段の実測を反映）/ 対象 Issue: #73

## 目的

**常にリリース可能な状態を、外から見た振る舞いで確認できるようにする。**

ユニット・結合テストは **1,836 件**（実測 2026-08-07）が CI で緑になっているが、
**外部から通しで確かめる試験が無い**。そのため次が検出できていない。

- リバースプロキシを含む経路（Caddy 断片・base パス・WS の rewrite）
- 複数ブラウザ間の同期（「相手の画面にどう見えるか」）
- 3 系統（`/`・`/timer/`・`/poker/`）の並存

S4（#65）でローカルに Caddy を立てて手で確かめたが、**その検証は CI に残っていない**。
#76（ローカル動作確認）で手作業した手順も、毎回やり直すことになっている。
本設計はそれらを資産化する。

## 決めたこと

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| 1 | 本番に対する試験の深さ | **ルームを 1 つ作って最小の通し確認をする** | スモークだけでは不安が残る。正常性確認の最低限を定める意味も持たせる |
| 2 | ローカルの検証経路 | **Caddy を立てた本番同等のみ。dev サーバー経路は対象外** | #73 が挙げる検出漏れは dev 経路では原理的に検証できない。#76 F-1 は `:5173` 直結だと Vite の base リダイレクトで偶然通り、玄関経由でしか死ななかった |
| 3 | 選択子のために実装へ手を入れるか | **原則は触らない。掴めない箇所だけ `aria` を補う。`data-testid` は使わない** | `aria` は読み上げという実益を持ち製品の一部として残るが、`data-testid` はテスト専用の死荷重で腐る |
| 4 | CI での実行 | **全 PR で必須。既存 CI と並列の別ジョブ** | 「常にリリース可能」がそのまま成立する。main 限定は #50（CI が一度も走っていなかった）と同じ後悔の形 |
| 5 | timer のルームの片付け | **1 ルーム作り、30 分の自然回収に委ねる** | timer には退出手段が無い（実測。#79 として別 Issue 化） |
| 6 | 第 1 弾の範囲 | **ハッピーパスと回帰の要に絞る。異常系は第 2 弾** | 異常系はハーネスに停止・再開の能力が要り、遅く揺れやすい（**根拠のうち「停止・再開の能力が要る」は誤りだった。**#142 で訂正。下記）|
| 7 | ハーネスのポート | **Caddy は 18080 に固定** | 動的確保にすると値を `playwright.config.ts` へ渡す経路が要る。固定なら `baseURL` が定数になり、占有検査がそのまま二重起動の排他になる |
| 8 | テストファイルの拡張子 | **`*.spec.ts`（Playwright の既定）** | 規約は `*.test.ts` だが、それだと vitest / bun test が拾って `pnpm test` に混ざる事故が起きる。**安全性を優先する明示的な例外**として記録する |

## 全体の形 — シナリオ集は 1 つ、ターゲットを差し替える

**「ローカル用」と「本番用」で別のテストを書かない。** 別々に書くと必ず片方だけが腐り、
しかもそれに気づけない。

### ターゲット（どこへ流すか）

| 名前 | 何を起動するか | 入口 |
|---|---|---|
| `local` | ハーネスが Caddy + timer-sync + poker-sync + 3 つの dist を**自分で起動し、自分で止める** | `http://127.0.0.1:18080`（固定） |
| `production` | **何も起動しない。** 既に動いているサーバーに外から当てるだけ | `TASUKI_E2E_BASE_URL` |

#### ターゲットの取り違えを防ぐ

環境変数の消し忘れで「ローカルのつもりが本番へ全シナリオを流す」事故が起きうる。
**両方向を fail-fast で塞ぐ。**

| コマンド | 検証 | 違反したら |
|---|---|---|
| `pnpm e2e` | `TASUKI_E2E_BASE_URL` が**設定されていない**こと | 起動前に落とす（「本番向けの変数が残っています」と表示） |
| `pnpm e2e:prod` | 設定されていること／`https://` で始まること／ホストが `localhost`・`127.0.0.1`・プライベート IP でないこと | 起動前に落とす |

### プロファイル（何を流すか）

Playwright のタグで分ける。**本番で走るコードはローカルで走るコードとまったく同じ実体**で、
違うのは向き先だけ。

| タグ | 内容 | `local` | `production` |
|---|---|:-:|:-:|
| `@smoke` | 経路・リダイレクト・ヘッダ・WS ハンドシェイク（ブラウザを使わない HTTP 確認） | ✓ | ✓ |
| `@core` | 最小の通し。**LP の描画**、poker 1 ルーム（投票 → 自動公開）、timer 1 ルーム（参加 → 交代） | ✓ | ✓ |
| （タグ無し） | 残り全部 | ✓ | — |

### 置き場所

**新規トップレベル `e2e/`**（パッケージ名 `@tasuki/e2e`）。`pnpm-workspace.yaml` に glob を 1 行足す。

`apps/` に置かないのは、そこが**配信されるアプリの場所**だから。E2E は配信されない。

```
e2e/
├── package.json             @tasuki/e2e（下記の依存宣言が必須）
├── playwright.config.ts     ターゲットを解決する（default export はここだけの例外）
├── harness/                 local ターゲットの起動と停止
│   ├── caddy.ts               断片を /etc/caddy/tasuki/apps/ へ設置し、Caddy を起こす
│   ├── www.ts                 /var/www/* を dist へ向ける
│   ├── sync.ts                timer-sync / poker-sync を起こす
│   ├── browsers.ts            要求 revision が導入済みかを検査する
│   └── preflight.ts           ポート占有・残骸・環境変数の検査
├── specs/                   シナリオ（*.spec.ts・Given/When/Then をコメントで明示）
├── fixtures/                共通フィクスチャ（コンソールエラー収集など）
└── support/                 選択子ヘルパ・ルーム作成の共通手順
```

**`e2e/package.json` は 3 つの web アプリを `workspace:*` 依存として宣言する。**

```json
"dependencies": {
  "@tasuki/timer-web": "workspace:*",
  "@tasuki/poker-web": "workspace:*",
  "@tasuki/landing": "workspace:*"
}
```

turbo の `dependsOn: ["^build"]` は **`package.json` の依存宣言を根拠に依存グラフを組む**。
同じワークスペースに居るだけ・実行時に dist を読むだけでは解決されない
（最小再現で実証済み）。この宣言が無いと `pnpm e2e` を単独実行したとき、
**古いか存在しない dist を黙って使う**。

### 実行の入口

```bash
pnpm e2e                    # local / 全シナリオ（3 アプリの build が先に走る）
pnpm e2e --grep @smoke      # local / 経路だけ手早く
TASUKI_E2E_BASE_URL=https://<公開ドメイン> pnpm e2e:prod    # production / @smoke + @core
```

`turbo.json` に `"e2e": { "dependsOn": ["^build"], "cache": false }` を追加する。
**`pnpm test` には混ぜない。** 混ぜると既存の 1,836 件が毎回 E2E の所要時間を背負う。

## ハーネス（`local` ターゲット）

肝は 1 点。**何を書き換えず、何を書き換えるかを明示し、それを機械で固定すること。**

### 断片の扱い — 「書き換えない」と「設置しない」は違う

| ファイル | 扱い | 理由 |
|---|---|---|
| `deploy/*/caddy/*.conf`（経路の本体 5 本） | **内容を 1 バイトも書き換えない。ただし所定の絶対パスへ設置する** | ここが検証対象そのもの |
| `deploy/caddy/tasuki.conf`（サイトブロック） | **アドレス行 1 行だけ**を `http://127.0.0.1:18080` に差し替えて設置する | ドメインと TLS（ACME）はローカルで再現できない。`header {}` と `import` はそのまま活かす |

**設置が必要な理由（初版で見落としていた点）。** `tasuki.conf:40` の import は
**絶対パス固定**である。

```
import /etc/caddy/tasuki/apps/*.conf
```

Caddyfile 側にこれを相対パスや CLI 引数で読み替える手段は無い。したがってハーネスは
**断片 5 本を `/etc/caddy/tasuki/apps/` へ内容不変のままコピーする**（`sudo` が要る）。
「書き換えない」のは内容であって、配置は行う。

### 起動前の検査（preflight）

**1 つでも該当したら起動せず、理由を示して落とす。**

| 検査 | 落とす理由 |
|---|---|
| 8787 / 3311 / 18080 のいずれかが使用中 | `pnpm dev` か前回の残骸。**誰が掴んでいるかを表示する** |
| `/etc/caddy/tasuki` が既に存在する | 前回の残骸か、このマシンの本物の Caddy 設定か区別できない。**本物を壊さない** |
| Chromium の要求 revision が `/opt/playwright-browsers` に無い | Playwright が root 所有のディレクトリへ書こうとして、原因の分からないエラーになる |
| `TASUKI_E2E_BASE_URL` が設定されている | ターゲットの取り違え |
| 3 つの dist に `index.html` が無い | ビルドされていない |

**ポートの占有検査が、そのまま二重起動の排他になる。** 別途ロックファイルは持たない
（TOCTOU のある自作ロックより、OS が保証する bind の排他のほうが確実）。

### root の解決

断片は `root * /var/www/tasuki` を絶対値で宣言している。環境側を断片に合わせる。

| symlink | 向き先 |
|---|---|
| `/var/www/tasuki` | `apps/timer-web/dist` |
| `/var/www/tasuki-poker` | `apps/poker-web/dist` |
| `/var/www/tasuki-home` | `apps/landing/dist` |

**`/var/www` は CI（ubuntu-latest）には存在しない。** `sudo mkdir -p /var/www` を先に行う
（初版の「CI では自明に通る」は根拠のない断定だった）。

### 起動と後始末

- **Caddy は 2.11.4 に版を固定**して取得し、`~/.cache/` にキャッシュする
- **`caddy validate` の成否を起動ゲートにしない。** import のグロブが 0 件マッチでも
  `Valid configuration` を返すことを実測した。**設置した断片が 5 本あることを数え、
  そのうえで実リクエストで確かめる**
- timer-sync / poker-sync は Bun で起動する。`ALLOWED_ORIGINS` にはローカルの入口 URL を渡す。
  なお**両サーバーとも起動を拒否するのは `NODE_ENV=production` かつ空のときだけ**で、
  poker-sync 固有の仕様ではない（初版の記述は誤り。`poker-sync/src/config.ts:65`・
  `timer-sync/src/config.ts:51`）

**後始末:**

- **正常終了・テスト失敗・`SIGINT`・`SIGTERM` では必ず**、Caddy と 2 つの sync を止め、
  `/etc/caddy/tasuki` を削除し、`/var/www` の symlink を外す
- **`SIGKILL` では保証できない**（プロセスがハンドラを実行できないため）。
  そのため上記 preflight で**残骸を必ず検出して落とす**設計にしてある。
  「次回起動時に気づける」ことで保証の穴を埋める
- 終了後の確認コマンドを README に置く: `ss -tlnp | grep -E ':(8787|3311|18080)'` が無出力であること

## シナリオ

### `@smoke` — ブラウザを使わない経路確認（`local` / `production` 共通）

| # | 確認すること | 落ちると分かること |
|---|---|---|
| 1 | `/`・`/timer/`・`/poker/` がすべて 200 | 3 系統の並存 |
| 2 | 各 HTML が参照する資材 URL に**実際に GET して 200**。かつ接頭辞が `/assets/`・`/timer/assets/`・`/poker/assets/` | base パスの崩れ（**#76 F-1 と同じ壊れ方**）と、**参照先が実在しない配信事故** |
| 3 | `/timer`・`/poker` が 301。**`Location` の値を厳密に固定** | 末尾スラッシュの救済 |
| 4 | `/?room=ABC123` が 301 で `Location: /timer/?room=ABC123`（**クエリを含めて厳密に**）／`/` 単体は 200 で LP | 旧共有リンクの救済と玄関の役割の両立 |
| 5 | `/timer/ws` が 426、`/poker/ws` が 400 | **WS が SPA に吸われていない**こと |
| 6 | `Strict-Transport-Security` を含む**ヘッダ 5 種すべて** | サイトブロックが効いていること |

**#2 は「参照文字列を見るだけ」にしない。** HTML から `src` / `href` を抜き出し、
実際に取得して 200 を確認する。文字列比較だけだと、資材が 404 でも緑になる。

**接頭辞の判定は `startsWith` でなければならない。** `toContain` にすると、
`/timer/assets/...` も `/assets/` を含むため `/` についての判定が恒真になり、
玄関 LP が別アプリの SPA に化けても検出できない（実測で確認済み）。

**status だけを見てはいけない。** 断片は `try_files {path} /index.html` を持つため、
資材が消えていても SPA フォールバックが `index.html` を 200 で返す（実測）。
`Content-Type` で「JS/CSS が返ったか、HTML へ縮退したか」を見分ける。

**#3・#4 は `maxRedirects: 0` を明示したうえで `Location` の値まで固定する。**
`maxRedirects: 0` は「301 という事実を掴む」ためのもので、行き先の正しさとは無関係。
`redir @legacy-room /timer/ permanent`（クエリを落とす）に改変しても 301 のままなので、
コードだけ見ていると #76 J-1 と同じ壊れ方が素通りする。

**#5 の注意（timer では経路の正しさを保証しない）。** poker-sync は
`url.pathname === '/ws'` を厳密に検査するが、**timer-sync（ws-adapter）はパスを見ずに
無条件で upgrade を試みる**（断片のコメントにも「剥がさなくても現状は通る」とある）。
そのため `10-timer-ws.conf` から `rewrite * /ws` を削っても 426 は返り続ける。
**timer 側の経路の正しさは `@core` の実接続成立に委ねる。**

**#6 は 5 種すべてを対象にする。** `Strict-Transport-Security` は `tasuki.conf` の
`header {}` で明示指定しているため、**TLS の有無に関係なく http でも付与される**
（実測。初版の「HTTPS のときのみ付与」は誤りで、検査網を不必要に狭めていた）。

#### #8 の判定 — DOM だけでは不十分

**DOM の範囲限定に加えて、WebSocket フレームを検査する。**

1. 参加者一覧の行と結果セクションに範囲を限定し、他人の値が見えないこと
2. 結果セクションがまだ存在しないこと
3. **`page.on('websocket')` で受信フレームを収集し、公開前に自分以外の票の値が
   一度も届いていないこと**

3 が要る理由: サーバーが投票中に他人の票を余剰フィールドで配信しても、
**UI がそれを参照しないので DOM には絶対に現れない**。DOM だけの判定では、
本設計自身が「落ちるべき」と挙げている壊し方を検出できない。
Playwright の WebSocket 監視はブラウザ標準の経路を使うので、製品コードの変更は要らない。

#### #9 の判定 — 名前を見ると恒真になる

`RosterPanel.tsx` は参加者名を**役割に関係なく全員常時表示**する。
「新ドライバー名が見えること」で判定すると、
**交代がまったく起きていなくても最初から真**になる。

**訂正（2026-08-08）:** 初版は「現ドライバーの視覚差分は `RosterPanel.tsx:251-252` の
`▶ 今` チップだけ」と書いていたが誤り。**同じ文字列が `RotationLineup.tsx:23`
（本文側）にも出る**ため、可視テキストでは一意に掴めない。名簿行には背景色・枠線の
差もある。判定は**名簿（`<ul aria-label="ドライバー一覧">`）の中に限定**し、
`aria` を足すのもそちらだけにした。

判定は次の 3 点に限定する。

1. **`▶ 今` の目印が新ドライバーの行に移動していること**
2. **旧ドライバーの行から消えていること**（2 人が同時にドライバー表示になる分裂を排除）
3. 上記が**両方の文脈で同じように見えていること**

現状 `▶ 今` はアクセシブル名を持たない `<span>` なので、**ここには `aria` の追加が要る**
（下記「追加した `aria` の一覧」に記録する）。

#### 2 人目をどうやって同じルームに入れるか

**poker にはルームコードの手入力欄が無い**（`router.ts` は `/poker/room/<roomId>` の
パス形式のみ解釈）。timer も招待は URL 表示・コピー・QR のみ。したがって経路は
**1 人目の URL を 2 人目の文脈で開く**の一択。

ただし **#11（招待 URL の回帰）だけは `page.url()` を使ってはいけない。**
検証対象が「招待パネルが生成する URL 文字列」そのものなので、
**画面に表示された URL を読み取って開く**。`page.url()` を使うと、URL 生成が壊れていても
緑になる（これが #76 F-1 の壊れ方そのもの）。

**「タグ無しは `local` 専用」を機械的に固定する**（2026-08-08・第 3 段で追加）。
この取り決めを支えているのは `e2e/package.json` の `e2e:prod` に書かれた
`--grep "@smoke|@core"` という**文字列ひとつだけ**で、第 2 段まではタグ無しの
シナリオが 1 本も無かったため、絞り込みが実際に何かを除外したことは一度も無かった。

| 固定するもの | 崩れると何が起きるか |
|---|---|

（`App.tsx:819`）、**それが見えていること自体が「参加画面ではない」の肯定形**になる。

### 第 2 弾（本設計では作らない）

### 禁じ手

| 禁じ手 | 理由 |
|---|---|
| **固定時間の待機**（`waitForTimeout`） | 遅いマシンで揺れ、速いマシンで見逃す。**待つのは常に「相手の画面にそれが出ること」そのもの** |
| **ページ全体への文字列一致** | poker の秘匿判定がこれで必ず緑になる。**否定の判定は範囲を限定する** |
| **常時表示される要素での状態判定** | timer の交代がこれで恒真になる。**状態の変化そのものを掴む** |
| **同一 `BrowserContext` で 2 人を演じる** | 同一人物になる（下記） |
| **`301` だけを見て `Location` を見ない** | 行き先が壊れても緑になる |
| **揺れたテストの無効化（quarantine）** | 揺れたらその場で原因を潰す |

#### なぜ 2 人には別の `BrowserContext` が要るか

- poker は `localStorage` の `poker:participant:<roomId>` に参加トークンを保存する
  （`apps/poker-web/src/storage.ts`）
- timer は `sessionStorage` に復帰情報（#24）、`localStorage` に環境設定を保存する

同じ文脈でタブを 2 枚開くと、2 人目が 1 人目として復帰し、
**「2 人居るつもりで 1 人」のまま緑になる。** 本題に入る前に
**2 人が別人として名簿に並んでいることを必ず確認する。**

なお #12（再読込での復帰）は `sessionStorage` に依存するため、
**同じ page の `reload()` で検証する**。新しい文脈を作ると意味が変わる。

### コンソールエラーの収集

**`page` を生成した直後、最初の `goto()` より前**にリスナーを登録する。
`goto()` の後に登録すると初期ロード中のエラーを見逃す。

全シナリオに一律で効かせるため、**カスタムフィクスチャで強制**する
（`test.beforeEach` では page 生成のタイミングを取り逃す経路が残る）。
`production` にも適用する。

**収集は全シナリオ、`0 件` の判定は `@core` #7（LP）だけ**（2026-08-08 に決定）。
他のシナリオでも収集はして、**落ちたときだけ**証跡に添付する。スクリーンショット
だけでは「JS が例外で止まったのか、要素が出るのが遅いだけなのか」が分からないため。
全シナリオで 0 件を強制しないのは、`production` で外部要因（フォント配信の一時障害など）
が混ざると本題と無関係に赤くなるから。

**2 人目の文脈にも必ず効かせる。** `browser.newContext()` を直接呼ぶと監視の付け忘れが

（下記）と監視の付け忘れを、1 つの入口で同時に塞ぐ。

## CI・証跡

### CI

既存の `ci` ジョブと**並列の別ジョブ**として追加する。

```
e2e ジョブ:
  checkout → Node 22 → corepack → Bun
  → pnpm install --frozen-lockfile
  → sudo mkdir -p /var/www          ← ubuntu-latest には存在しない
  → pnpm build
  → Caddy 2.11.4 を取得（版でキャッシュ）
  → npx playwright install --with-deps chromium（版でキャッシュ）
  → pnpm e2e
  → 失敗時のみ証跡を upload-artifact
```

- **並列度**: ハーネスは Caddy + sync 1 組だけ起動し、シナリオ側は複数ワーカーで流す。
  各シナリオが自分のルームを作るので干渉しない
  （`maxConnections` 既定 200・`maxRooms` 既定 50 に対し、ワーカー数は 1 桁）
- **再試行**: CI でのみ 1 回
- **目標 10 分**

### 落ちたときに残すもの

出力先は **`e2e/test-results/`**（`.gitignore` に追加）。

| 証跡 | 設定 | 出力先 |
|---|---|---|
| トレース | 再試行時に取得 | `test-results/` |
| スクリーンショット | 失敗時のみ | `test-results/` |
| 動画 | 失敗時のみ保持 | `test-results/` |
| **Caddy・timer-sync・poker-sync の標準出力／エラー** | 常に | `test-results/logs/*.log`（`spawn` の `stdio` を capture してファイルへ） |

CI では `actions/upload-artifact` で **失敗時のみ**アップロードし、保持は 7 日。
画面が赤いだけでは、Caddy が断片を読めていないのか sync が落ちたのか分からない。

## 本番実行

```bash
TASUKI_E2E_BASE_URL=https://<公開ドメイン> pnpm e2e:prod
```

- **`deploy.sh` には統合しない。** `deploy.sh` はアプリ単位だが、本番の通し確認は
  **3 系統が揃って初めて意味を持つ**。粒度が違うものを結合すると、1 アプリだけ出したときに
  必ず落ちる確認が走る。代わりに **`deploy.sh` 末尾の「確認:」ブロックに案内を追記**する
- 参加者名に **`e2e` を含める。** 人がルームを見たとき確認用だと分かるように
- **逐次実行（ワーカー 1）。再試行は 0 回**（本番の枠を無用に消費しない）
- **ルーム作成に失敗したら再試行せず落とす。** `maxRooms` 到達や sync の不調が原因なので、
  再試行は状況を悪くする。終了コードで判別できるようにする
- poker のルームは最後の接続が切れた瞬間に消える。**timer のルームは 30 分残る**（#79）。
  1 回の実行で 1 部屋。`maxRooms` 既定 50 に対し、**30 分以内に 50 回実行しない限り
  枠は圧迫しない**

### #11 が pathname を見る理由（第 3 段の最大の発見）

**「表示された URL を開いて参加できた」だけでは、F-1 の再発を検出できない。**

`40-timer-legacy-room.conf` が `/?room=CODE` を 301 で `/timer/?room=CODE` へ救済する
ため、招待 URL が壊れた形に戻っても**参加は成立してしまう**。

実測でこれを証明した。`room-url.ts` を F-1 の形に戻したうえで、**pathname の判定
1 行だけをコメントアウトすると、21 件すべてが緑に戻った**。「2 人目が実際に参加でき、
2 人が別人として輪に並ぶ」ところまで通る。つまり**この 1 行だけが F-1 を捕まえている**。

救済の 301 は古いリンクのための保険であって、いま配る招待 URL が頼るものではない
（`apps/timer-web/src/ui/room-url.ts` の冒頭コメントが同じことを述べている）。
**保険が効く経路では、保険が隠す壊れ方を別の手段で見なければならない。**

### 壊し方を選び直した経緯（#8）

**初手の「`room-state` に余剰フィールドを足す」は成立しない。** クライアントの境界検証は
`v.strictObject`（`protocol.ts`）で、余剰フィールドを持つフレームは丸ごと捨てられる
（`useSync.ts:106`「境界検証に失敗したフレームは無視」）。結果、**画面が固まって
ルーム作成の時点で落ちる**。赤くはなるが「秘匿の検査が働いた証拠」にはならない。

設計が述べた「UI が参照しないので DOM に出ない」を再現する壊し方は、
**クライアントが黙って捨てる別メッセージとして余分に配る**形（`vote-peek` を
`rooms.ts` の `broadcast` から追加送信）。これなら画面は正常に動き、
DOM には何も出ず、ワイヤーにだけ票が乗る。

**そしてこの変異は、最初の実装では素通りした。** 検査側が受信フレームを
`type === 'room-state'` で絞ってから走査していたため、自分でふるい落としていた。
**届いたフレームは全部走査する**形に直して検出できるようになった
（`e2e/specs/poker.spec.ts`）。変異検査をしなければ、この穴は見つからないまま
「WS まで見ているから安心」と書かれていた。

**この表の「実施結果」を書くときは、赤くなった理由まで確かめること。**
型エラーやビルド失敗で偶然赤くなっただけでは、検出できた証拠にならない。

### turbo の strict env が落とす変数、3 つ目（2026-08-08・第 3 段）

**`pnpm e2e` だけが落ち、`playwright test` を直接叩くと通る**、という形で現れた。

```

  - locator resolved to <a href="/timer/" data-label="交代" class="card tool-card">…</a>
```

### #4 の顛末（2026-08-08・第 2 段）

**ローカルで、ブラウザが 1 つも起動できなかった。**

```
Error: browserType.launch: Executable doesn't exist at
  /home/vscode/.cache/ms-playwright/chromium_headless_shell-1234/...
```

原因は `TASUKI_E2E_BASE_URL` のときとまったく同じ型で、
**turbo 2.x の strict env モードが `PLAYWRIGHT_BROWSERS_PATH` を落としていた**。
devcontainer はこの変数で `/opt/playwright-browsers` の導入済みブラウザを使う。
届かないと Playwright は自分の既定（`~/.cache/ms-playwright`）を探して落ちる。

**さらに悪いことに、起動前の検査は素通りしていた。** `harness/browsers.ts` の
`assertChromiumInstalled` は変数が未設定なら何もしない設計で（CI では Playwright
自身がブラウザを入れるため、そちらは正しい）、**変数が落ちている状態と
CI の正常な状態を区別できない**。preflight は通り、ブラウザ起動の瞬間に初めて落ちる。

対応: `turbo.json` の `e2e` / `e2e:prod` の `passThroughEnv` に
`PLAYWRIGHT_BROWSERS_PATH` を追加し、`e2e/tests/turbo-env.test.ts` に宣言を固定する
テストを足した（`TASUKI_E2E_BASE_URL` と同じ形）。

**この穴は第 1 段では原理的に見えなかった。** 13 件が 1 つもブラウザを起動して
いなかったため。PR #81 の CI で Chromium 151.0.7922.34 / revision 1234 の取得自体は
成功していたが、起動して使う経路は通っていなかった。
