# E2E テストの土台（#73）

作成日: 2026-08-07 / 対象 Issue: #73

## 目的

**常にリリース可能な状態を、外から見た振る舞いで確認できるようにする。**

ユニット・結合テストは 1,792 件が CI で緑になっているが、**外部から通しで確かめる試験が無い**。
そのため次が検出できていない。

- リバースプロキシを含む経路（Caddy 断片・base パス・WS の rewrite）
- 複数ブラウザ間の同期（「相手の画面にどう見えるか」）
- 3 系統（`/`・`/timer/`・`/poker/`）の並存

S4（#65）でローカルに Caddy を立てて手で確かめたが、**その検証は CI に残っていない**。
#76（ローカル動作確認）で手作業した手順も、毎回やり直すことになっている。
本設計はそれらを資産化する。

## 決めたこと

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| 1 | 本番に対する試験の深さ | **ルームを 1 つ作って最小の通し確認をする（中間案）** | スモークだけでは不安が残る。正常性確認の最低限を定める意味も持たせる |
| 2 | ローカルの検証経路 | **Caddy を立てた本番同等のみ。dev サーバー経路は対象外** | #73 が挙げる検出漏れは dev 経路では原理的に検証できない。#76 F-1 は `:5173` 直結だと Vite の base リダイレクトで偶然通り、玄関経由でしか死ななかった |
| 3 | 選択子のために実装へ手を入れるか | **原則は触らない。掴めない箇所だけ `aria` を補う。`data-testid` は使わない** | `aria` は読み上げという実益を持ち製品の一部として残るが、`data-testid` はテスト専用の死荷重で腐る |
| 4 | CI での実行 | **全 PR で必須。既存 CI と並列の別ジョブ** | 「常にリリース可能」がそのまま成立する。main 限定は #50（CI が一度も走っていなかった）と同じ後悔の形 |
| 5 | timer のルームの片付け | **1 ルーム作り、30 分の自然回収に委ねる** | timer には退出手段が無い（実測。#79 として別 Issue 化）。デプロイでどのみち全ルームが消える揮発設計 |
| 6 | 第 1 弾の範囲 | **ハッピーパスと回帰の要に絞る。異常系は第 2 弾** | 異常系はハーネスに停止・再開の能力が要り、遅く揺れやすい。土台を固めてから積む |

## 全体の形 — シナリオ集は 1 つ、ターゲットを差し替える

**「ローカル用」と「本番用」で別のテストを書かない。** 別々に書くと必ず片方だけが腐り、
しかもそれに気づけない。

### ターゲット（どこへ流すか）

| 名前 | 何を起動するか | 入口 |
|---|---|---|
| `local` | ハーネスが Caddy + timer-sync + poker-sync + 3 つの dist を**自分で起動し、自分で止める** | `http://127.0.0.1:<確保したポート>` |
| `production` | **何も起動しない。** 既に動いているサーバーに外から当てるだけ | `TASUKI_E2E_BASE_URL` |

### プロファイル（何を流すか）

Playwright のタグで分ける。**本番で走るコードはローカルで走るコードとまったく同じ実体**で、
違うのは向き先だけ。

| タグ | 内容 | `local` | `production` |
|---|---|:-:|:-:|
| `@smoke` | 経路・リダイレクト・ヘッダ・WS ハンドシェイク（ブラウザを使わない HTTP 確認） | ✓ | ✓ |
| `@core` | 最小の通し。poker 1 ルーム（投票 → 自動公開）、timer 1 ルーム（参加 → 交代） | ✓ | ✓ |
| （タグ無し） | 残り全部 | ✓ | — |

### 置き場所

**新規トップレベル `e2e/`**（パッケージ名 `@tasuki/e2e`）。`pnpm-workspace.yaml` に glob を 1 行足す。

`apps/` に置かないのは、そこが**配信されるアプリの場所**だから。E2E は配信されない。
`deploy/*/app.env` が実際のデプロイ対象を列挙している構造とも整合する。

```
e2e/
├── package.json             @tasuki/e2e
├── playwright.config.ts     ターゲットを環境変数で解決する
├── harness/                 local ターゲットの起動と停止
│   ├── caddy.ts               本番と同一の断片を集め、root を dist へ向ける
│   ├── sync.ts                timer-sync / poker-sync を起こす
│   ├── browsers.ts            要求 revision が導入済みかを検査する
│   └── lock.ts                二重起動の防止
├── specs/                   シナリオ（Given/When/Then をコメントで明示）
└── support/                 選択子ヘルパ・ルーム作成の共通手順
```

### 実行の入口

```bash
pnpm e2e                    # local / 全シナリオ
pnpm e2e --grep @smoke      # local / 経路だけ手早く
TASUKI_E2E_BASE_URL=https://<公開ドメイン> pnpm e2e:prod    # production / @smoke + @core
```

**`pnpm test` には混ぜない。** turbo のタスクを `e2e` として独立させる。混ぜると既存の
1,792 件が毎回 E2E の所要時間を背負い、ユニットテストを気軽に回せなくなる。

## ハーネス（`local` ターゲット）

肝は 1 点。**何を書き換えず、何を書き換えるかを明示し、それを機械で固定すること。**

### 断片の扱い

| ファイル | ローカルでの扱い | 理由 |
|---|---|---|
| `deploy/*/caddy/*.conf`（経路の本体 5 本） | **1 バイトも書き換えない** | ここが検証対象そのもの |
| `deploy/caddy/tasuki.conf`（サイトブロック） | **アドレス行 1 行だけ**を `http://127.0.0.1:<port>` に差し替える | ドメインと TLS（ACME）はローカルで再現できない。`header {}` と `import` はそのまま活かす |

**「書き換えたのはアドレス行 1 行だけである」ことをテストで機械的に固定する。**
ここが緩むと、いつの間にか「ローカルだけ通る設定」で緑になる。#65 で踏んだ
「誤った前提の上にテストを積み上げる」の再発を先回りして塞ぐ。

このテストは `e2e/` 配下に置き、`e2e` タスクではなく **`test` タスクで走らせる**
（Caddy もブラウザも要らない純粋な文字列比較なので、E2E の実行を待たずに落ちるべき）。

### root とポートの解決

断片は `root * /var/www/tasuki` と `reverse_proxy 127.0.0.1:8787` を**絶対値で宣言**している。
Caddy 側に読み替える手段は無いので、環境側を断片に合わせる。

| symlink | 向き先 |
|---|---|
| `/var/www/tasuki` | `apps/timer-web/dist` |
| `/var/www/tasuki-poker` | `apps/poker-web/dist` |
| `/var/www/tasuki-home` | `apps/landing/dist` |

ハーネスが起動時に `sudo ln -sfn` で張り直す（既存の残骸に依存しない）。
sync は**本番と同じ 8787 / 3311** で起動する。

**この選択の代償（承知のうえで受け入れる）:**

1. `/var/www` はマシン全体で 1 つなので、**同一マシンで E2E を 2 つ同時に走らせられない**。
   ロックを取り、二重起動は黙って混ざる前に即座に落とす
2. 8787 / 3311 が固定なので、**`pnpm dev` を起動したまま E2E を走らせられない**。
   起動前に占有を検査し、使われていたら誰が掴んでいるかを示して落とす
3. `sudo` が要る（CI では自明に通る。この devcontainer でも実測で確認済み）

断片のポートと `deploy/*/app.env` の `PORT` の一致は、E2E ではなく**静的なテストで押さえる**。
安く、確実で、壊れたとき原因が一目で分かる。置き場所は
`apps/landing/tests/caddy-fragment-order.test.ts`（既に断片の衝突を機械的に固定している）の隣とし、
**同じ観点のテストを 2 箇所に散らさない**。

### 起動と後始末

- **Caddy は 2.11.4 に版を固定**して取得し、`~/.cache/` にキャッシュする。
  「最新」を取ると、ある日突然赤くなって原因が分からない
- timer-sync / poker-sync は Bun で起動し、`ALLOWED_ORIGINS` にローカルの入口 URL を渡す
  （poker-sync は空だと起動を拒否する仕様）
- dist は `pnpm build` の成果物を使う。E2E 自身はビルドしない（turbo の依存で解決）

**後始末は必須要件とする。**

- 成功・失敗・中断（Ctrl-C）・強制終了のいずれでも、**Caddy・timer-sync・poker-sync を必ず止め、
  8787 / 3311 を解放し、symlink を元に戻す**
- 終了後にポートが空いていることを確認する手順をコマンドとして用意する
  （`ss -tlnp | grep -E ':(8787|3311)'` が無出力であること）
- 起動しっぱなしは過去に実害を出している（放置された dev サーバー 4 本で `pnpm dev` が全滅した）

### ブラウザ

**実測により `playwright@1.62.1` に完全固定する**（`^` を付けない）。

| Playwright | chromium revision | ブラウザ版 | 導入済みと一致 |
|---|---|---|:-:|
| **1.62.1 / 1.62.0** | **1234** | **151.0.7922.34** | **✓** |
| 1.61.1 / 1.61.0 | 1228 | 149.0.7827.55 | — |
| 1.60.0 | 1223 | 148.0.7778.96 | — |

`ffmpeg` は 1.60〜1.62 すべて revision 1011 で導入済みと一致（**失敗時の動画記録が使える**）。
revision は版に 1 対 1 で紐づくため、キャレットを付けると `pnpm update` の副作用で
突然ブラウザを取りに行く。

- ローカル: `PLAYWRIGHT_BROWSERS_PATH=/opt/playwright-browsers`（この環境では設定済み）
  ＋ `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`
- CI: `/opt/playwright-browsers` が無いので `npx playwright install --with-deps chromium` を、
  版を固定したキャッシュ鍵で `actions/cache` に載せる
- **ハーネス起動時に「要求 revision が導入済みか」を検査し、ずれていたら明示して落とす。**
  検査しないと Playwright が root 所有のディレクトリへ書こうとして、原因の分からない
  エラーになる。devcontainer のイメージが更新されたら、この検査が最初に教えてくれる

## 「通っていないのに緑」を作らないための規律

E2E は放っておくと必ずこの状態になる。禁じ手を設計時点で決めておく。

### 選択子は 3 段階で、上から順に

1. **ロール + アクセシブル名**（`getByRole('button', { name: 'ルームを作成' })`）
2. **可視テキスト**（範囲を限定したうえで）
3. **`aria` を足す** — ここに来たものだけ、本文書の「追加した `aria` の一覧」に列挙する

`data-testid` は使わない。

実測した現状（2026-08-07）:

| アプリ | `data-testid` | `aria-label` | `role` |
|---|---|---|---|
| timer-web | 0 | 73 | 30 |
| poker-web | 0 | 2 | 4 |
| landing | 0 | 1 | 0 |

timer-web はそのまま掴める。poker-web / landing は薄いが、可視テキストとロール
（`ルームを作成` ボタン、カード面の数字、`投票済み` の `aria-label`、`結果` の見出し）でほぼ足りる。

### 追加した `aria` の一覧

実装時に記入する。**空のまま実装を終えないこと**（＝1 つも足さずに済んだ場合は「なし」と書く）。

| ファイル | 足したもの | なぜ既存の手段で掴めなかったか |
|---|---|---|
| （実装時に記入） | | |

### 禁じ手

| 禁じ手 | 理由 |
|---|---|
| **固定時間の待機**（`waitForTimeout`） | 遅いマシンで揺れ、速いマシンで見逃す。**待つのは常に「相手の画面にそれが出ること」そのもの** |
| **ページ全体への文字列一致** | poker の秘匿判定がこれで必ず緑になる（下記）。**否定の判定は範囲を限定する** |
| **同一 `BrowserContext` で 2 人を演じる** | 同一人物になる（下記）。文脈を分けたうえで、**2 人が別人として名簿に並んでいることを先に確認**してから本題に入る |
| **リダイレクトの追跡を任せたまま `301` を確認したつもりになる** | `maxRedirects: 0` を明示する |
| **揺れたテストの無効化（quarantine）** | 揺れたらその場で原因を潰す。無効化を許した瞬間に E2E は形骸化する |

#### なぜ秘匿の判定は範囲を限定しなければならないか

**カード手札に同じ数字のボタンが常時並んでいる。** 「画面に `5` が出ていないこと」で
判定すると絶対に一致してしまい、秘匿が破れていても緑になる。判定は
**参加者一覧の行と結果セクションに範囲を限定**し、かつ「結果セクションがまだ存在しないこと」を
併せて確認する。

#### なぜ 2 人には別の `BrowserContext` が要るか

実測（2026-08-07）:

- poker は `localStorage` の `poker:participant:<roomId>` に参加トークンを保存する
  （`apps/poker-web/src/storage.ts`）
- timer は `sessionStorage` に復帰情報（#24）、`localStorage` に環境設定を保存する

同じ文脈でタブを 2 枚開くと、2 人目が 1 人目として復帰し、
**「2 人居るつもりで 1 人」のまま緑になる。**

なお #11（再読込での復帰）は `sessionStorage` に依存するため、
**同じ page の `reload()` で検証する**。新しい文脈を作ると復帰情報が無く、意味が変わる。

### 併せて固定するもの

- **コンソールエラーが 0 件**であること（S4 の手動検証で見ていた項目を自動化して残す）
- Given / When / Then をコメントで明示する。既存の SC-032 の規約に合わせる。
  ただし `audit-structure.mjs` は `packages/timer-core`・`apps/timer-sync`・`apps/timer-web` を
  名指しで走査しており **`e2e/` は測定対象外**。ここは人が守る規約とする

## CI・証跡

### CI

既存の `ci` ジョブと**並列の別ジョブ**として追加する。

```
e2e ジョブ:
  checkout → Node 22 → corepack → Bun
  → pnpm install --frozen-lockfile
  → pnpm build
  → Caddy 2.11.4 を取得（版でキャッシュ）
  → npx playwright install --with-deps chromium（版でキャッシュ）
  → pnpm e2e
```

- **並列度**: ハーネスは Caddy + sync 1 組だけ起動し、シナリオ側は複数ワーカーで流す。
  各シナリオが自分のルームを作るので干渉しない
- **再試行**: CI でのみ 1 回。それ以上は隠蔽
- **目標 10 分**。超えたら見直す

### 落ちたときに残すもの

| 証跡 | 設定 |
|---|---|
| トレース | 再試行時に取得 |
| スクリーンショット | 失敗時のみ |
| 動画 | 失敗時のみ保持 |
| **Caddy・timer-sync・poker-sync の標準出力／エラー** | 常に保存 |

最後の 1 つが重要。画面が赤いだけでは、Caddy が断片を読めていないのか sync が落ちたのか
分からない。

## 本番実行

```bash
TASUKI_E2E_BASE_URL=https://<公開ドメイン> pnpm e2e:prod
```

- **`deploy.sh` には統合しない。** `deploy.sh` はアプリ単位（timer / poker / landing を個別に出す）
  だが、本番の通し確認は**3 系統が揃って初めて意味を持つ**。粒度が違うものを結合すると、
  1 アプリだけ出したときに必ず落ちる確認が走る
- 代わりに **`deploy.sh` 末尾の「確認:」ブロックに、このコマンドを案内として追記**する
  （既にそこは確認手順を印字する作りになっている）
- 参加者名に **`e2e` を含める。** 人がルームを見たとき、確認用だと分かるように
- **逐次実行（ワーカー 1）。** 実サーバーの枠を無用に消費しない
- poker のルームは最後の接続が切れた瞬間に消える。**timer のルームは 30 分残る**（#79）。
  デプロイは元々「最後に 1 回」の運用であり、`MAX_ROOMS=50` を圧迫しない

## 「わざと壊すと落ちる」の確認

Issue #73 の完了条件。**自動化せず、手順として本文書に残し、実装時に 1 回実施して結果を記入する。**

| 壊し方 | 落ちるべきもの | 実施結果 |
|---|---|---|
| `10-timer-ws.conf` の受けパスを変える | `@smoke` #5 | （実装時に記入） |
| `20-poker.conf` を外す | `@smoke` #1・#2 | （実装時に記入） |
| poker-sync が公開前に他人の票を配信するよう変える | `@core` #7 | （実装時に記入） |
| timer の交代を自分の画面だけに反映するよう変える | `@core` #8 | （実装時に記入） |

自動化しないのは、E2E での変異検査が遅すぎるため。既存の `mutation-check.mjs` は
ユニットテスト向けで、そちらは維持する。

## スコープ外
