## 1. 目的

**PR に push してから CI が緑になるまでの待ちを、検査の強さを落とさずに短くする。**

- PR でも main でも、変異は**全件**を流し続ける（変異を減らさない・PR で絞らない）
- 変異が増えても、CI の時間が件数に比例して伸びない形にする（並行の数を 1 か所で増やせる）

#387 では「CI は全件のまま」を守り、手元の待ちだけを縮めた。今回はその決まりを守ったまま、CI の待ちを縮める。

### 2.4 並列化の制約

- 変異検査は 1 つの作業ツリーの上で「当てる → 流す → `git checkout --` で戻す」を繰り返す。
  **同じ作業ツリーで 2 つを同時に流すとロックで拒む**（2026-09-08 に変異が残る事故があった。`scripts/mutation-check.mjs` のヘッダ）
- したがって 1 つの作業ツリーの中では直列にしか流せない。並行にするには、**作業ツリーそのものを分ける**必要がある。
  分け方は 2 通り: 別の runner（ジョブ）に分ける（案 A）／1 つの runner の中で `git worktree` を複数作る（案 B）
- GitHub の `ubuntu-latest`（公開リポジトリ）は 4 vCPU・16 GB。手元のコンテナも 4 コア

## 3. 案の比較

| 案 | 中身 | 見込み | 検査の強さ | 費用・危うさ |
|---|---|---|---|---|
| **A. ジョブを分ける** | matrix で n 個のジョブに分け、各ジョブが自分の割り当て分だけを流す | 変異の段 ÷ n ＋ジョブの準備 約 30 秒 | 変わらない（全件・毎回） | 準備がジョブごとにかかる。分け方の偏り |
| **B. 1 ジョブの中で並列** | HEAD の写しの作業ツリーを m 個作り、同時に流す | runner のコア数（4）倍まで | 変わらない | 作業ツリーごとに依存の取得が要る（§2.3 で実測 1.9 秒）。**伸びしろがコア数で頭打ち** |
| C. PR は差分だけ | PR は `--changed`、main と夜間に全件 | PR の待ちが大きく減る | **弱まる**（全件で落ちるのが merge の後になる） | 選び方の正しさが品質の要になる。#387 で利用者は「CI は全件」を選んだ |
| D. 1 件あたりを速くする | vitest の起動の使い回しなど | 未知 | 弱まりうる | 1 件の大半は起動の時間で、使い回すと変異のたびのモジュールの読み直しを自前で保証することになる |
| E. 変異以外の段 | 自己テストの並列化・turbo のキャッシュ | 数分 | 変わらない | 変異を外したあとの quality は約 2〜3 分で臨界経路に乗らない。ci（約 5.5 分）を縮める話は別にする |

**A と B を組み合わせる**（2026-10-31 の利用者の判断）。

- A だけでは 1 ジョブが 1 コアしか使わない。同じ速さに届くのに、ジョブの数（準備の重複）が 3〜4 倍要る
- B だけでは伸びしろが runner のコア数で頭打ちになり、変異が増え続けると追いつけない
- 組み合わせると、**コアは B で使い切り、件数の伸びは A の行を足して吸収する**（完了条件の「比例して伸びない形」）

#387 は B を「作業ツリーごとに依存の入れ直しが要り、復元・ロック・残骸回収の機構を作り直すことになる」として退けた。
今回は次の 2 点でその費用が消えたので採る:

1. **依存の入れ直しは 1.9 秒で済む**（pnpm のストアから `--offline` で引く。§2.3）
2. **安全機構を作り直さない形がある。** 親は作業ツリーを作って、それぞれで**普段の 1 回の実行**（`--id …`）を子として起こすだけにする。
   ロック・復元・マーカー・未コミット変更の検査は、子が自分の作業ツリーで今までどおり行う。本体の作業ツリーには変異を当てない

## 4. 決定

### 4.1 変異検査に `--shard <k>/<n>` を足す

```bash
node scripts/mutation-check.mjs --shard 2/4    # 全件を 4 つに分けた 2 つ目だけを流す
```

- `k` と `n` は正の整数で `1 ≤ k ≤ n`。外れたらロックより前にエラーで止める（打ち間違いで 0 件の緑にしない）
- `--changed` / `--id` / `--pkg` とは混ぜられない（選び方の指定は 1 回に 1 つ、のまま）。`--full`・`--jobs` とは組める
- 分け方は**宣言の表 `MUTATIONS` だけから決まる**（§4.3）。同じ表と同じ `n` からは、どの機械でも同じ割り当てになる
- **n 個の割り当てを合わせると全件になり、重ならない**（自己テストで固定する）
- 割り当てが 0 件になる `n`（対照の組の数より大きい）はエラーで止める
- 表題: `分割実行（--shard 2/4）: 440 件中 110 件`。最後の 1 行:
  「シャード 2/4 の 110 件の変異がすべて検出されました（全件ではありません。全件は 4 個のシャードの合計です）」。全件の緑と取り違えないため

### 4.2 変異検査に `--jobs <m>` を足す

```bash
node scripts/mutation-check.mjs --jobs 4                  # 全件を 4 つの作業ツリーで並列に
node scripts/mutation-check.mjs --shard 1/2 --jobs 4      # CI の形
node scripts/mutation-check.mjs --changed --jobs 2        # 選び方とも組める
```

- 指定が無ければ 1（今までどおり、この作業ツリーで直列）
- 親は次の順に進む:
  1. 今までと同じ前段（ロック・前回の異常終了の復元・宣言の健全性・未コミット変更の検査・選び方）
  2. **除外なしの未コミット変更の検査**。写しは HEAD なので、宣言の表とパッチの置き場（普段の検査は除外する）の未コミットの変更も写しに入らない。流したつもりの変異が流れないので止める
  3. 前回の並列の実行が残した作業ツリーを消す（名前に親の PID を入れ、**親が死んでいるものだけ**消す）
  4. 選んだ変異を m 個に分ける（§4.3 と同じ分け方。**ワーカーの数は対照の組の数で抑える**）
  5. 一時ディレクトリに `git worktree add --detach <dir> HEAD` を m 個作り、それぞれで `pnpm install --frozen-lockfile --offline`
  6. それぞれの作業ツリーで `node scripts/mutation-check.mjs --id <割り当て> [--full]` を子として起こす
  7. 子の出力は終わった順にまとめて出す（混ぜない）。最後にワーカーごとの件数・所要時間・終了コードの表
  8. 終わり（緑・赤・シグナル）に作業ツリーを消す。シグナルのときは子にも SIGTERM を送る（子は自分の作業ツリーで復元する）
- 子が 1 つでも 0 以外（**シグナルで止まった null を含む**）で終われば、親は赤で終わる

### 4.3 分け方

- **対照の組**（`pkg` と `tests` が同じ変異の集まり）を分けない単位にする。同じ組は同じ分け前に入るので、
  #387 の対照実行の使い回しが分けた先でもそのまま効く
- 組の重さは「対照 1 回の秒数＋変異 1 件の秒数 × 件数」。秒数はランナーごとの目安（§2.3 の実測）で、入口の `RUNNER_COST_SECONDS` に置く
- 重い組から順に、その時点でいちばん軽い分け前へ入れる（貪欲法・LPT）。同点は組の鍵の辞書順・分け前の番号の若い順
- 分け前の中の流す順は宣言の順のまま（ログが読みやすいように）
- **重さの値がずれても、正しさは崩れない**（偏るだけ）。偏りは各シャード・各ワーカーの所要時間で見える
- シャード（ジョブの段）とワーカー（作業ツリーの段）は**同じ 1 つの関数**を使う（`scripts/lib/mutation-partition.mjs`）

### 4.4 CI の形

```yaml
  mutation:
    name: mutation (${{ matrix.shard }})
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2]
    steps:
      # checkout・setup-node・ci-scope・corepack・setup-bun・pnpm install
      - run: node scripts/mutation-check.mjs --shard "$((SHARD_INDEX + 1))/$SHARD_TOTAL" --jobs 4
        env:
          SHARD_INDEX: ${{ strategy.job-index }}
          SHARD_TOTAL: ${{ strategy.job-total }}

  mutation-all:
    needs: mutation
    if: always()
    steps:
      - run: test "$RESULT" = success
        env:
          RESULT: ${{ needs.mutation.result }}
```

- **シャードの番号と数は matrix の値から取らず、`strategy.job-index` と `strategy.job-total` から取る。**
  `matrix.shard` を `--shard` に渡すと、`[1, 2, 4]` のような書き間違い（3 が抜ける）で 1 つのシャードが黙って流れなくなる。
  job-index と job-total は GitHub が数えるので、matrix の行の数を変えるだけで割り当てが必ず全件を覆う。`matrix.shard` はジョブ名の表示にだけ使う
- **n = 2・m = 4 で始める。** CI の直列は 13〜19 分（§2.2）。`--jobs 4` が手元と同じく約 2.8 倍なら 1 ジョブで 4.6〜6.8 分、2 つに分けて 2.3〜3.4 分＋準備で、ci（約 5.5 分）の内側に収まる。m は `ubuntu-latest`（公開リポジトリは 4 vCPU）のコアの数
- `fail-fast: false`。1 つのシャードが落ちても他を止めない（検出されなかった変異を一度にすべて見るため）
- **集約のジョブ `mutation-all` を置く。** シャードが 1 つでも success でなければ（失敗・取り消し・飛ばし）赤くなる。
  いま main にブランチ保護は無いが、将来の必須チェックはこの 1 つを指せばよく、n を変えても名前が変わらない
- ADR 0009 D4 のとおり、絞り込み（`ci-scope.mjs` の `code`）は**ステップ単位の `if`** で行い、各シャードは常に起動して success を報告する
- quality からは変異検査の段を外す。setup-bun は残す（scripts の自己テストが `apps/tasuki-sync` の変異の実行コマンドを組むときに bun の実行体を探す）
- シャードの install は素の `pnpm install --frozen-lockfile` でよい（供給網の検証の目撃者は quality の 1 ジョブだけ。ci.yml のコメント・設計正本 D5）

### 退けた案

| 案 | 退けた理由 |
|---|---|
| C（PR は差分だけ） | 検査の強さが落ちる。A＋B で目標に届くので、引き換えにする理由が無い |
| `pkg` ごとに 1 ジョブ | 22 か所あり、1 件しか無い所もある。ジョブの数が件数でなく置き場の数で決まり、偏りが大きい（`apps/tasuki-sync` 93 件・`packages/topic-core` 1 件） |
| 番号の範囲で分ける（`id` の 1〜150 など） | 対照の組が範囲の境目で割れて使い回しが減る。番号は足した順なので、重いアプリの変異が 1 つの範囲に固まる |
| 割り当てを実行時の記録（前回の所要時間）から決める | 記録の置き場（キャッシュ・成果物）が要り、記録が消えたときの振る舞いを別に決めることになる。偏りは見えるので、まずは固定の重さで足りる（原則 X） |
| 作業ツリーの依存を本体の `node_modules` への symlink で済ませる | パッケージ間の symlink が本体のソースを指し、写しの中の変異ではなく本体のコードを試すことがある。`--offline` の install は 1.9 秒で済む |
| 1 つのプロセスの中でワーカーを回す（子を起こさない） | ロック・復元・マーカーがモジュールの変数と作業ツリーに 1 つずつ結びついており、作り直しになる |

| 626 | シグナルで止まったワーカーを成功に数える | null も失敗 |
| 627 | シャードの緑を「全変異」と言う | 緑の文言 |

## 6. 今後（変異が増えたとき）

- **増やすのは matrix の行だけ**（`shard: [1, 2]` → `[1, 2, 3]`）。スクリプトの側は何も変えない
- 目安: いちばん長いシャードの変異の段が ci ジョブ（約 5.5 分）を超えたら 1 つ増やす。所要時間は各シャードの最後の行に出る
- シャード・ワーカーが偏ってきたら（最長と最短の差が 1.5 倍を超えるなど）、`RUNNER_COST_SECONDS` を測り直す
- ジョブの準備（約 30 秒）が n 倍かかるので、n を大きくしすぎると準備の割合が増える。n が 8 を超えそうなら、1 件あたりを速くする案（D）をそのときに比べる
- `--jobs` は runner のコアの数に合わせる。GitHub が runner の大きさを変えたら合わせる（`nproc` はログの準備の段で見える）
- このリポジトリは公開なので Actions の分は数えない。非公開に変えるときは、準備 × n の分が増えることを見積もる
- ci ジョブ（`pnpm test` 約 3.5 分）が次の律速になる。縮めるなら案 E を別の Issue で扱う

## 7. 検証

**完了の条件**:

- PR の CI の全体時間が 10 分以内に、3 回以上続けて収まる
- シャードの件数の合計が全件（448 件）で、すべて検出される（入れる前の全件と同じ集合）
- `mutation-all` が、シャードが 1 つでも落ちたら赤になる（わざと 1 つ落として確かめる）
- ADR 0029 と ADR 0009 の追記、`docs/guides/development.md` の段ごとの表が新しい形になっている
