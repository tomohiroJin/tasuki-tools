# 機能仕様: メジャー依存の更新

**Issue:** [#113](https://github.com/tomohiroJin/tasuki-tools/issues/113)（親エピック #67・段階 B、#69 から切り出し）
**ブランチ:** `docs/113-pr0-spec-and-plan` ・ **ステータス:** Draft ・ **フロー:** 要件優先

## 概要

#69「依存の最新化と供給網対策」は、待機期間（`minimumReleaseAge`）・`pnpm audit` の CI 組み込み・
Renovate の設定という**仕組み**を整え、非メジャー更新までを済ませた。破壊的変更を伴う
メジャー更新は憲法 原則 IX「小さく回す」に反するため #113 へ切り出されている。

本件は、そのメジャー更新を**1 単位ずつ・回帰を検出できる形で**取り込む作業である。
対象はビルド・テスト基盤（型検査・テストランナー・バンドラ・CSS 基盤・lint）に集中しており、
**利用者から見える振る舞いを変えないまま、開発基盤の土台を入れ替える**ことが本質である。
土台が古いまま後続の #70（CI/CD 整備）・#72（ADR に沿ったリファクタリング）を進めると、
新しい版で書き方が変わる箇所を二度書くことになるため、本件はそれらより先に置かれる。

一方で、対象のすべてが「今すぐ上げられる」わけではない。**上げると別の道具が壊れる依存**が
実在することを前提に、「上げる」と同じ重みで「**上げない判断を根拠つきで記録する**」ことを
成果物に含める。

## ユーザーシナリオとテスト

### ユーザーストーリー1 — 回帰を出さずに 1 単位ずつ取り込む（優先度: P1）

開発者として、メジャー更新を 1 単位ずつ取り込みたい。なぜなら、複数の破壊的変更を同時に
入れると、赤くなったときにどれが原因か切り分けられなくなるからだ。

**受け入れ基準（EARS）:**

1. メジャー更新を取り込むとき、システムは 1 つの PR で 1 つの更新単位のみを変更すること。
2. 相互に peer 依存で版が束縛された複数パッケージを更新するとき、システムはそれらを
   同一の更新単位として 1 つの PR で更新すること。
3. 開発時にのみ使われ、失敗の現れ方が互いに区別でき、実画面・実プロトコルの確認を
   要しない更新が複数あるとき、システムはそれらを 1 つの更新単位にまとめてよい。
4. 実行時に読み込まれる更新・画面の描画に関わる更新・設定の移行作業を伴う更新・
   ワークスペース全体の宣言を動かす更新のとき、システムはその更新を単独の更新単位とすること。
5. もしまとめた更新単位が検査で赤くなった場合、システムは原因となった対象のみを当該
   更新単位から外して別の更新単位とし、残りの対象は取り込むこと。
6. 更新単位の PR を作成したとき、システムは `pnpm typecheck`・`pnpm lint`・`pnpm test`・
   `pnpm build` のすべてが緑であることを確認できる状態にすること。
7. もし更新によって既存のテストが赤くなった場合、システムは当該更新を取り込まず、
   原因と対処（追随・不採用）を記録すること。
8. 更新単位の作業を始めるとき、システムは対象パッケージの取り得る版を作業当日に
   再実測すること。
9. 対象パッケージに、依存する道具が対応している範囲内の上位メジャー版が存在するとき、
   システムは最新版ではなくその範囲内の最大の版を取り込む候補とすること。

### ユーザーストーリー2 — 利用者の振る舞いが変わらない（優先度: P1）

timer / poker の利用者として、依存の更新後も画面と操作が今までどおりであってほしい。
なぜなら、この作業は自分にとって何の機能追加でもなく、壊れることだけがリスクだからだ。

**受け入れ基準（EARS）:**

10. 依存の更新を取り込んだとき、システムは利用者が通る画面・操作・表示を更新前と同一に
   保つこと。
11. 画面の描画に関わる依存を更新したとき、システムは実際の画面で表示崩れが無いことを
   確認してから完了とすること。
12. 実行時に読み込まれる依存を更新したとき、システムは実際のプロトコル越しに当該機能が
   動作することを確認してから完了とすること。
13. もし更新によって利用者から見える振る舞いが変わる場合、システムは当該更新を本件では
   取り込まず、別の Issue として切り出すこと。

### ユーザーストーリー3 — 取れなかった版について、判断材料が事実として残る（優先度: P2）

保守者として、取り込まなかった版について「なぜ取れないのか」を**実測した事実**として
残してほしい。なぜなら、伝聞や peer 宣言の読みだけで「対応していない」と書かれた記録は、
次に見た人が信用できず、同じ調査をやり直すことになるからだ。

**受け入れ基準（EARS）:**

14. 依存する道具の対応範囲外であることを理由に版を取り込まないと判断したとき、システムは
    その判断を実際に検査を実行した結果（どの検査が、どう失敗したか）を根拠として記録すること。
15. 取り込まない版があるとき、システムは何が変われば取り込めるようになるかを観測可能な形
    （対応版の公開など）で記録すること。
16. 取り込まない版について記録するとき、システムはその版を将来どう扱うかの決定を本件では
    下さず、記録した事実のみを残すこと。
17. すべての更新単位の処理が終わったとき、システムは取り込んだものと取り込まなかったものの
    区別が一覧で分かる状態にすること。

### ユーザーストーリー4 — 供給網の防御が効いたまま残る（優先度: P3）

保守者として、更新作業のあとも #69 で入れた防御が効いたままであってほしい。なぜなら、
更新を急ぐと防御を一時的に外したまま戻し忘れるからだ。

**受け入れ基準（EARS）:**

18. 更新のために待機期間の例外を追加したとき、システムは当該例外に解除予定日を併記すること。
19. 更新単位の作業が完了したとき、システムは解除予定日を過ぎた待機期間の例外を残さないこと。
20. もし更新によって脆弱性検査が新たに検出を出した場合、システムは当該更新を完了とせず、
    検出の解消または不採用の判断を記録すること。

## 機能要件

- **FR-001**: 更新は「更新単位」ごとに 1 PR で扱い、1 PR に複数の更新単位を混在させない。
  更新単位は対象パッケージ 1 つとは限らず、下記 FR-002 の規則で決まる。
- **FR-002**: 更新単位は次の規則で決める。
  - (a) **束縛**: peer 依存によって互いの版が束縛されるパッケージ群は、1 つの更新単位とする
        （分離すると install が成立しないため）。
  - (b) **同梱してよい**: 開発時にのみ使われ、失敗の現れ方が互いに区別でき、実画面・
        実プロトコルの確認を要しない更新は、1 つの更新単位にまとめてよい。
  - (c) **単独にする**: 実行時に読み込まれるもの・画面の描画に関わるもの・設定の移行作業を
        伴うもの・ワークスペース全体の宣言（実行環境の下限など）を動かすものは、単独の
        更新単位とする。
- **FR-003**: まとめた更新単位が検査で赤くなったときは、原因となった対象のみを外して
  別の更新単位とし、残りは取り込む（まとめたことで全体が止まらないようにするため）。
- **FR-004**: 対象パッケージに、依存する道具が公式に対応している範囲内で最新版より
  低い上位メジャー版が存在する場合は、最新版ではなくその範囲内の最大の版を取り込みの
  候補とする（対応範囲外の版を掴んで検査の保証を落とさないため）。
- **FR-005**: 各更新単位の PR は、`pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build`
  の 4 つがすべて緑であること。
- **FR-006**: 各更新単位の PR は、更新前後でテストの実行件数が減っていないことを示すこと
  （更新に伴ってテストが黙って実行されなくなる事故を検出するため）。
- **FR-007**: 画面描画に関わる更新単位は、実画面での確認結果を PR に記すこと。
- **FR-008**: 実行時依存の更新単位は、実プロトコル越しの動作確認結果を PR に記すこと。
- **FR-009**: 版を取り込まないと判断した場合は、理由・再開条件・判断日を Issue #113 に
  記録すること。理由には、実際に検査を実行して観測した失敗の内容を含めること
  （peer 宣言の読みだけを根拠にしない）。
- **FR-010**: 取り込まなかった版の**将来の扱いは本件では決定しない**。記録するのは観測した
  事実と再開条件までとし、方針の決定は #113 の完了時に改めて行う。
- **FR-011**: 更新対象の版は作業当日に再実測し、記録した実測値には実測日を併記すること。
- **FR-012**: 更新によって実行環境の下限（Node の版など）が上がる場合は、その下限を
  リポジトリの宣言（`engines`）と CI の設定の両方へ反映すること。
- **FR-013**: 待機期間の例外を追加する場合は、解除予定日を併記し、作業完了時に期限切れの
  例外を残さないこと。
- **FR-014**: 更新の結果、設定ファイルの記法や構成が変わる場合は、変更の理由が読み取れる
  形で該当ファイルに残すこと。
- **FR-015**: すべての更新単位を処理し終えた時点で、取り込み・不採用の別が一覧で
  判別できること。

## 非機能要件

- **回帰検出**: 既存のユニットテスト・E2E テスト・型検査・lint・ビルドを回帰検出の
  主たる手段とする。更新のために検査を弱める（除外の追加、しきい値の引き下げ、
  テストの skip）ことをしない。**検査の層そのものが実行不能になる更新**は、
  検査を弱める行為より重いものとして扱い、取り込まない。この判断は宣言の読みではなく、
  実際に検査を実行した結果に基づくこと。
- **セキュリティ**: 更新後も `pnpm audit` が high 以上を検出しない状態を保つ。待機期間の
  防御を恒久的に無効化しない。
- **アクセシビリティ**: デザイントークン層が保証している配色のコントラスト等の契約を、
  更新の前後で維持する。
- **可観測性**: 各更新単位の判断（取り込み／不採用）と根拠が、後から Issue と PR だけで
  追跡できる。
- **可逆性**: いずれの更新単位も、単独の revert で更新前の状態へ戻せる。

## 主要エンティティ

- **更新単位** — 1 つの PR で扱う更新のまとまり。対象パッケージ（1 つ以上）、更新前後の版、
  影響を受けるワークスペース内パッケージ、必要な確認手段（テスト／実画面／実プロトコル）を持つ。
  peer 依存で束縛される複数パッケージは 1 つの更新単位になる。
- **不採用の記録** — 取り込まないと判断した版について、理由・再開条件・判断日を持つ記録。
  理由は実際に検査を実行して観測した失敗の内容であり、再開条件は観測可能であること
  （「対応版が公開されたら」など）。
- **実測ログ** — 版・公開日・peer 依存・実行環境の下限といった、判断の前提となる測定値。
  測定日を必ず伴い、測定日が古くなった値は再測定の対象になる。

## 成功基準

- **SC-001**: Issue #113 が挙げるすべての対象について、取り込み済みか不採用（実測した理由つき）
  かのいずれかに分類されており、未処理が 0 件である。
- **SC-002**: すべての更新単位の PR が、4 つの検査（型検査・lint・テスト・ビルド）を
  緑で通過してマージされている。
- **SC-003**: 全作業の完了時点で、テストの実行件数が作業開始時点を下回っていない。
- **SC-004**: 全作業の完了時点で、脆弱性検査が high 以上を 0 件で維持している。
- **SC-005**: 利用者から見える振る舞いの変更を目的とした差分が 0 件である。
- **SC-006**: 待機期間の例外に、解除予定日を過ぎたまま残っている項目が 0 件である。
- **SC-007**: 取り込まなかった対象それぞれについて、実測した失敗の内容と再開条件が
  記録されている。

## スコープ外 / 非目標

- **非メジャー（minor / patch）更新はしない。** #69 で完了済み。本件で偶発的に上がる
  推移依存は妨げないが、目的にはしない。
- **`trustPolicy` の採否は決めない。** #116 の担当。
- **Renovate の運用設定は変えない。**「スキャンのみ」から自動 PR への切り替えは本件で行わない。
- **未使用依存の削除・不要ファイルの整理はしない。** #71 の担当。
- **CI へ新しい検査を足さない。** #70 の担当。既存の検査を通すことのみ行う。
- **利用者から見える振る舞いを変えない。** エピック #67 の全体制約。更新に伴って挙動を
  変えたくなった場合は、本件に混ぜず別 Issue へ切り出す。
- **性能改善を目的としない。** 新しい版が速い／遅いは受け入れ基準にしない。
- **lint・型検査の基盤そのものを置き換えない。** 更新を阻む依存が見つかっても、
  基盤の置き換えは技術選定の変更であり ADR を要する（憲法 原則 II）。本件では扱わない。
- **取り込めなかった版の将来の方針を決めない。** 本件が残すのは観測した事実と再開条件まで。
  方針は #113 の完了時に、揃った事実をもとに改めて決める。
- **依存を新規に追加・削除しない。** ただし、更新対象そのものが構成の変更（同一エコシステム内で
  提供パッケージが分割された等）を要求する場合はこの限りではない。

## 前提

- **対象の一覧と版の正本は Issue #113 とする。** 本仕様・実装計画・タスクのいずれにも
  版番号の一覧表を転記しない（同じ表を複数の文書に持つと必ず食い違うため。憲法 原則 VIII
  「記録が正本」の SOT）。実装計画には、判断の根拠として使った実測値を**測定日つきで**残す。
- 実測はすべて 2026-08-11 時点のものであり、**着手時に再実測する**ことを前提とする。
  公開日・最新版・peer 依存の宣言はいずれも日が進めば変わる。
- 対象の中には、**上げると別の道具が壊れるもの・実行環境の下限を押し上げるものが含まれる**。
  本仕様は「全件を上げること」ではなく「全件について判断を下し、記録すること」を完了と定義する。
- **「最新版へ上げる」ことは目的ではない。** 依存する道具の対応範囲内で最も新しい版を取り、
  範囲外の版は取り込まない（FR-004）。`pnpm outdated` が示す最新版は候補の 1 つにすぎない。
- **危険度の低い更新をまとめることは、この repository の前例に沿う**（#69 PR-4 が非メジャー
  6 件を 1 PR で扱った）。憲法 原則 IX「1 PR は 1 つの論理的変更」との整合は、「開発時の
  検査ツール群を最新へ揃える」を 1 つの論理的変更と見なすことで取る。
- EARS 記法は本来 `docs/guides/ears-writing.md` により機能系 Issue に対して必須とされ、
  chore 系には強制されない。本件は chore だが、受け入れ基準を検証可能にするため EARS で書く。
- 作業は overlay 側のクローンで行う（`docs/guides/development.md` および AI 運用規則）。
