## 1. 何のために作るか

プランニングポーカーに、**知っている人だけが入れる遊び**を 1 つ置く（イースターエッグ）。目的は遊び心だけで、
見積もりの機能には一切影響させない。

## 2. 目標・目標にしないもの・失敗とみなすもの

**目標**

- 隠しの入口から、同じルームの仲間とトランプのポーカーを遊べる
- 自分の手札は他の人の画面（と、他の人の手元の JS）に届かない
- 普段の利用者には見えない。見積もりの画面と初回の読み込みは変わらない

**目標にしないもの**

- チップ・賭け・ベットの回（勝ち負けの記録も持たない）
- テキサスホールデム・手札の交換（§9 D1）
- 入口を秘密にすること（**隠しは入口が見えないだけで、アクセス制御ではない**。配布された JS を読めば誰でも見つけられる）
- timer・roulette への持ち込み

**失敗とみなすもの**

- 配った手札が、配られた本人以外へ見せる前に届く（wire のどのフィールドにも載る）
- テーブルの操作で、見積もりの状態（投票・公開・記録）が動く
- テーブルに着いていない人の画面に、テーブルが出る
- 古いサーバーにつながった新しい画面、新しいサーバーにつながった古い画面が `room-state` を捨てる

## 3. 用語

| 語 | 意味 |
|---|---|
| テーブル | ルームごとに 1 つの、トランプのポーカーの状態。見積もりのラウンド（`Round`）が持つ別の部分 |
| 席に着く | テーブルに加わること。着いている人だけに手札が配られ、テーブルが見える |
| 手 | 配られた 5 枚のカード。見せるまでは本人にしか届かない |
| 役 | 5 枚の強さの分類（ハイカード〜ロイヤルストレートフラッシュ） |

## 4. 振る舞い（EARS）

- **T-1** 参加者が隠しの入口を開いたとき、サーバーはその参加者をテーブルの席に着け、ルームへ配信する
- **T-2** 席に着いている参加者の画面だけが、テーブルを出す。着いていない参加者の画面は何も変わらない
- **T-3** 席に着いている参加者が「カードを引く」を押したとき、サーバーは 52 枚をよく切り、席の全員へ 5 枚ずつ配る
- **T-4** 手が配られている間、サーバーは各受信者へ**その人の手だけ**を送る。他の人について届くのは「席に着いている」ことだけである
- **T-5** 席に着いている参加者が「見せる」を押したとき、サーバーは全員の手と役、いちばん強い手の持ち主（同点なら全員）を配信する
- **T-6** 手が配られている間に「カードを引く」が届いたとき、サーバーは状態を変えず `table-in-play` を返す
- **T-7** 手が配られていないのに「見せる」が届いたとき、サーバーは状態を変えず `table-no-hand` を返す
- **T-8** 席に着いていない参加者から「カードを引く」「見せる」が届いたとき、サーバーは状態を変えず `table-not-seated` を返す
- **T-9** 席が 10 人で埋まっているときに席に着こうとしたとき、サーバーは `table-full` を返す（52 枚で 5 枚ずつ配れるのは 10 人まで）
- **T-10** 参加者が「閉じる」を押したとき、サーバーはその参加者を席から外し、その人の手を捨てる。席が空になったらテーブルを最初の状態へ戻す
- **T-11** 参加者がルームから外れたとき（退出・片付け）、サーバーは票と一緒にその人の席と手を捨てる
- **T-12** テーブルの操作は、投票・公開・記録・見学のどれも変えない。見積もりの操作もテーブルを変えない

## 5. 画面

### 5.1 入口（§9 D3）

2 つ置く。どちらも「席に着く」を送るだけで、画面の状態は持たない（テーブルを出すかは配信された席で決める）。

- **キーボード**: 入力欄の外で `↑ ↑ ↓ ↓ ← → ← → B A`（コナミコマンド）
- **タッチ・マウス**: 参加者の見出し（`参加者（N人）`）を 2 秒以内に 5 回押す

見出しを押しても、見出しは何も起こさないように見える（ボタンにはしない —— ボタンにすると入口が見えてしまう）。
キーボードの利用者はコマンドで入れるので、見出しにフォーカスを足さない。

### 5.2 テーブル

席に着いている間だけ、操作の面（`.room-main`）の先頭にテーブルの札を出す。

- 見出し `トランプのポーカー`
- 自分の手（`あなたの手`）。配られる前は `カードを引くと、テーブルの全員に 5 つずつ回ります。`、配ったあとに着いた人には `次の手から加わります。`
- 見せたあとは、席ごとに名前・5 枚・役。いちばん強い手には `いちばん強い手` の印
- 帯: 配る前・見せたあとは `カードを引く`、配られている間は `見せる`。右端に `閉じる`
- カードは `A♠` の形の文字で描く。♥ ♦ は赤、♠ ♣ は本文色（デザインシステムのトークン）。読み上げは `スペードのA` の形

### 5.3 書体

スートの記号 ♠（U+2660）♣（U+2663）♥ ♦（U+2665–2666）は書体の base 層に入っている（`packages/ui/src/tokens/fonts.css` で実測）。
役の名前はカタカナだけで書けるので base 層に収まる。文言の漢字は検査（`apps/poker-web/tests/card-table-copy-fits-font-base.test.ts`）で確かめ、外れる字（配・札・枚・着・届・勝 など）を避けた。

### 5.4 普段の利用者の負担（§9 D6）

テーブルの部品と役の名前は `React.lazy` で別の塊へ分け、席に着いたときにだけ読み込む。
初回の読み込みに増えるのは、入口の検出（数十行）とスキーマの数行だけである。役の判定はサーバーだけが呼ぶ（画面へは役の分類だけが届く）。

実測（`vite build`・2026-10-28）: 初回の JS は 274.78 kB → 275.97 kB（gzip 85.99 → 86.44 kB・+0.45 kB）、初回の CSS は 57.78 kB のまま。
テーブルは別の塊（JS 2.47 kB・CSS 1.00 kB）で、入口を開くまで取りに行かない（実ブラウザで要求が 0 件であることを確かめた）。

## 6. 状態とプロトコル

### 6.1 状態（§9 D5）

テーブルは見積もりの集約ルート `Round` の `table` に持つ。保管（`RoundStore`）・配信・破棄の経路は見積もりと同じ 1 本を通る
（ルームが消えればテーブルも消える。新しい保管は足さない）。

```ts
interface CardTable {
  seats: readonly string[];                       // 着いた順
  status: 'idle' | 'dealt' | 'shown';
  hands: ReadonlyMap<string, readonly PlayingCard[]>;
}
```

乱数は `dealHands(round, actorId, randomInt)` へ注入する（憲法 原則 VI）。本番は timer のシャッフル・ルーレットと同じ
`RandomSource`（`node:crypto`）を使う。

### 6.2 C→S（すべて `v.strictObject`）

| type | 形 | エラー |
|---|---|---|
| `table-seat` | `{ "seated": boolean }` | `table-full` |
| `table-deal` | `{}` | `table-not-seated` / `table-in-play` |
| `table-show` | `{}` | `table-not-seated` / `table-no-hand` |

### 6.3 S→C（`room-state.table`）

**席が空のときは載せない**（普段のルームの wire は 1 バイトも変わらない）。受信側は `v.optional`。

```json
{
  "status": "dealt",
  "seats": ["p1", "p2"],
  "yourHand": [{ "suit": "S", "rank": 14 }],
  "hands": [],
  "winners": []
}
```

- `yourHand`: 受信者が席に着いていて手を持つときだけ値。それ以外は `null`
- `hands` / `winners`: `shown` のときだけ中身がある。`hands[]` は `{ participantId, cards, category }`
- `rank` は 2〜14（11=J, 12=Q, 13=K, 14=A）。`suit` は `S` `H` `D` `C`

## 7. データ分類（憲法 原則 XI）

手札と席は**ゲームの状態**で、個人を識別しない。ただし「どの参加者が席に着いているか」は見学と同じく参加者に結びつくので、
決定1 の「当てはまらない値は厳しい側」により**個人に紐づく**の段に置く（揮発のみ・ログへ出さない・配信はする）。
ハンドラはテーブルの状態も参加者 ID もログへ書かない。

## 8. 試験

- ドメイン: 役の判定（10 分類・同点の比べ方・A を 1 として使うストレート）、配る・見せる・席の出入りの状態遷移、秘匿の投影
- 境界: 3 つのコマンドの受理と拒否（余分なキー・範囲外）、`table` の省略と受理
- サーバー: 配った手が本人にしか届かない（実プロトコル越し）、見積もりが動かない
- 画面: 入口 2 つ、席に着いた人だけにテーブル、帯の出し分け、文言の書体
- E2E: 2 人のブラウザで入口 → 引く → 互いの手が見えない → 見せる

## 9. 判断の一覧（Issue の「実装時に決めること」への回答）

| # | 問い | 決定 | 理由 |
|---|---|---|---|
| D1 | どのポーカーか | **5 枚の「せーので見せる」**（交換なし） | プランニングポーカーの「伏せて出す → 一斉に開く」にそのまま重なる。交換を入れるとコマンド・山札の残り・10 人で山が尽きる場合の規則が増える。足すのは遊ばれた実績が出てから（原則 X） |
| D2 | 賭けの扱い | **チップなし**。役の強さだけを比べる | 状態が手札だけで済む。勝ち負けを持ち越さない |
| D3 | 入口 | **コナミコマンド（キーボード）と参加者の見出しを 5 回押す（タッチ・マウス）** | 両方の端末で開ける。既存の操作（投票など）に副作用を持たない場所を選んだ |
| D4 | ひとりか全員か | **ルームの全員**（着いた人だけ）。配るのはサーバー | Issue の「あるべき姿」が仲間と遊ぶことを求めている。クライアントが引くと他人の札が手元の JS に届く |
| D5 | 見積もりとの関係 | **混ぜない**。`Round.table` に別の部分として持ち、互いに変えない | 遊んでいる最中も見積もりは続けられる。保管・破棄の経路を増やさない |
| D6 | 普段の利用者の負担 | **テーブルの部品は遅延読み込み**。`room-state.table` は席が空なら載せない | 初回の読み込みも wire も、普段のルームでは変わらない |
| D7 | 書体 | **文字で描く**（スートは base 層に入っている） | 図形を描く部品を足さずに済む。文言は外れる字を避けた |

### 見送らなかった理由（Issue の「見送る判断材料」への回答）

同期サーバーに 3 つのコマンドを足す重さはある。それでも全員で遊ぶ形を選んだのは、**手札を隠す仕組みが既存の受信者別の投影にそのまま乗る**からで、
新しく作るのはドメインの関数と投影の数行に留まる。「壊れても気付かない」には E2E を 1 本置いて答える（隠しモードも CI が毎回通る）。
