## 3. 実測した事実

### 3.1 Caddy の `X-Forwarded-For` の扱い（2026-08-14 実測・Caddy 2.11.4）

`reverse_proxy` の背後にプレーンな HTTP サーバーを置き、ヘッダを偽装して測った。Caddy は
`:19900`（ポート番号のみ指定＝Go の dual-stack listener）で待ち受けており、下表は
`127.0.0.1`（IPv4）から接続した計測である。同じ dual-stack listener に IPv6 から接続した
計測は本節後半（「多要素・重複ヘッダ・IPv6 での追加実測」）を参照。

| クライアントが送るヘッダ | バックエンドに届く値 |
|---|---|
| （何も送らない） | `X-Forwarded-For: 127.0.0.1` |
| `X-Forwarded-For: 9.9.9.9` | `X-Forwarded-For: 127.0.0.1`（**偽装値は消える**） |
| `X-Forwarded-For: 1.1.1.1, 2.2.2.2` | `X-Forwarded-For: 127.0.0.1`（**上書き。追記ではない**） |
| `X-Real-IP: 9.9.9.9` | `X-Real-IP: 9.9.9.9`（**そのまま素通し**） |

WebSocket upgrade 要求（`Connection: Upgrade` ＋ `Sec-WebSocket-Key`）でも同じ挙動だった。

**帰結**: `X-Real-IP` は攻撃者が自由に書けるため**使わない**。`X-Forwarded-For` は信頼できるが、
本設計は**最後のカンマ区切り要素**を取る。Caddy が上書きでも追記でも正しく、本番の Caddy の版・
設定に依存しないため（§7 の未確認事項を参照）。

**実断片での再測定（2026-08-14・Caddy 2.11.4）**: 上記は手書きの Caddyfile での実測だった。
リポジトリの実断片（`deploy/timer/caddy/10-timer-ws.conf` と `deploy/poker/caddy/20-poker.conf` を
1 バイトも変えずコピーし、`import` で読み込んだもの）を通しても同じ結果になるかを実装タスク 1 で
測り直した。バックエンドはプレーンな Node HTTP サーバー（ポート 8787＝timer、3311＝poker）。

| 経路 | 送ったヘッダ | 実際に届いた応答 |
|---|---|---|
| `/timer/ws`（`handle` ＋ `rewrite * /ws` ＋ `reverse_proxy 127.0.0.1:8787`） | `X-Forwarded-For: 9.9.9.9` ＋ `X-Real-IP: 9.9.9.9` | `{"url":"/ws","xff":"127.0.0.1","xrealip":"9.9.9.9"}` |
| `/poker/ws`（`handle` ＋ `rewrite * /ws` ＋ `reverse_proxy 127.0.0.1:3311`） | `X-Forwarded-For: 9.9.9.9` | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |

`handle` と `rewrite` を挟んでも、`X-Forwarded-For` の偽装値（`9.9.9.9`）は手書き版と同じく
`127.0.0.1` に上書きされ、`rewrite * /ws` によって sync 側が受け取るパスは想定どおり `/ws` になった。
timer 側では `X-Real-IP` が `9.9.9.9` のまま素通しされることも再確認した（**使ってはいけない証拠**）。
これで §3.1 の実測は実断片経路でも成立していると確認できた。実装の以降のタスクはこの事実に依存してよい。

**実断片での upgrade 経路再測定（2026-08-14・Caddy 2.11.4）**: 上記の実断片再測定はプレーンな GET
だった。本番の実経路は WebSocket upgrade 要求そのものなので、同じ実断片環境に対して
`Connection: Upgrade` ／ `Upgrade: websocket` ／ `Sec-WebSocket-Version: 13` ／
`Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==` を付け、`X-Forwarded-For: 9.9.9.9` を偽装して測り直した。

| 経路 | 送ったヘッダ | 実際に届いた応答 |
|---|---|---|
| `/timer/ws`（upgrade ヘッダ付き） | `X-Forwarded-For: 9.9.9.9` ＋ upgrade 4 ヘッダ | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |
| `/poker/ws`（upgrade ヘッダ付き） | `X-Forwarded-For: 9.9.9.9` ＋ upgrade 4 ヘッダ | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |

（バックエンドの echo サーバーはプレーンな HTTP サーバーで `101 Switching Protocols` を返さないため、
Caddy は upgrade を確立できず通常の `200 OK` を返した。それでも `reverse_proxy` がバックエンドへ
転送する `X-Forwarded-For` と `rewrite` 後のパスはプレーン GET のときと同じであり、ヘッダ書き換え
自体は upgrade 要求か否かに左右されないことが確認できた。）

**帰結**: upgrade ヘッダを足しても `X-Forwarded-For` の偽装値は同じく `127.0.0.1` に上書きされ、
`url` は `/ws` になった。プレーン GET の実測と一致しており、**ヘッダ書き換え（XFF の上書き・
`rewrite` によるパス変換）が upgrade 要求か否かに左右されないこと**が確認できた。ただし今回の
実測はハンドシェイク要求（HTTP リクエスト行とヘッダ）の段階までであり、`101 Switching Protocols`
後の WebSocket 接続確立そのものは測っていない（バックエンドの echo サーバーが 101 を返さないため）。
レート制限はハンドシェイク要求時のヘッダで判定するため、この範囲の確認で本設計の前提としては
十分である。

**多要素・重複ヘッダ・IPv6 での追加実測（2026-08-14・Caddy 2.11.4）**: 上記は XFF を 1 本だけ
送ったケースしか測っていなかった。`e2e/harness` がキャッシュしている実バイナリで、素の
`reverse_proxy` 構成に対し、複数要素・重複ヘッダ・IPv6 ループバックを追加で測った。

| 送ったもの | バックエンドに届いた `X-Forwarded-For` |
|---|---|
| XFF なし | `127.0.0.1`（実ピア）・1 本 |
| `X-Forwarded-For: 9.9.9.9`（偽装 1 本） | `127.0.0.1`・1 本 |
| `X-Forwarded-For` を 2 本（`9.9.9.9` と `8.8.8.8`） | `127.0.0.1`・**1 本**（重複ヘッダは畳まれる） |
| `X-Forwarded-For: 9.9.9.9, 8.8.8.8`（カンマ 2 要素） | `127.0.0.1`・1 本 |
| `X-Forwarded-For: 9.9.9.9,`（末尾カンマ） | `127.0.0.1`・1 本 |
| IPv6 ループバック `[::1]` から接続 | `::1`（**射影形 `::ffff:` ではない**）・1 本 |

**この実測から言えること**:

- 攻撃者は XFF の内容を一切制御できない。重複ヘッダによる「最後の要素の乗っ取り」は
  素の `reverse_proxy` では成立しない
- Caddy は dual-stack ソケットで受けた IPv4 接続にも点付き 10 進を書く。**射影形は書かない**ので、
  F1 の欠陥（IPv4 射影アドレスが `v6:0:0:0:0` に丸め崩壊する）は現構成では本番到達しない
  潜在欠陥だった。とはいえ `@tasuki/rate-limit` は Caddy 経由に限定されない汎用パッケージであり、
  将来別の前段プロキシや直接呼び出しで射影形が現れる可能性は残るため、修正自体は行う
- 「最後の要素を採る」規則（D5）は、この構成では常に要素数 1 を見ることになる。多要素の扱いは
  前段プロキシが増えたときのための防御

### 3.2 `net.isIP` による妥当性判定（Bun で実測）

| 入力 | `net.isIP` | 意味 |
|---|---|---|
| `1.2.3.4` | 4 | — |
| `01.2.3.4` | **0（拒否）** | IPv4 は先行ゼロが弾かれる → **表記が一意**。文字列のまま鍵にしてよい |
| `2001:db8::1` | 6 | — |
| `2001:DB8::1` | **6（通る）** | 同一アドレスの別表記 |
| `2001:0db8::1` | **6（通る）** | 同一アドレスの別表記 |
| `2001:db8:0:0::1` | **6（通る）** | 同一アドレスの別表記 |
| `[2001:db8::1]` | 0 | 角括弧は事前に剥がす必要がある |
| `2001:db8::1%eth0` | 6 | ゾーン ID は通る。事前に剥がす |
| `unknown` / 空文字 | 0 | — |

**帰結**: IPv6 は**同一アドレスに複数の表記があり、すべて検証を通る**。文字列をそのまま鍵にすると、
表記を変えるだけで別の鍵になり、レート制限を回避できる。**必ず数値へ展開して正規化する。**

### 3.3 総当たりコストと探索空間

現行レートは **600 回/秒**（同時接続上限 200 × 接続単位 10 秒あたり 30 回。接続単位なので
再接続で窓がリセットされる。ADR 0011 決定4 の「#103 実装前」の前提レート）。

| 対象 | 生成方式 | 探索空間 | 600 回/秒 | 1 回/秒 |
|---|---|---|---|---|
| timer・ルーム名あり `slug-????` | 小文字英数 32 種 × 4 桁 | 1,048,576 | **約 29.1 分** | 約 12.1 日 |
| timer・ルーム名なし `A7K2M9` | 大文字英数 31 種 × 6 桁 | 887,503,681 | 約 17 日 | 約 28.1 年 |
| poker `roomId` | UUID 先頭 8 桁（32 bit） | 4,294,967,296 | 約 82.9 日 | 約 136 年 |

ADR 0011 決定4 の目標は「**全探索に 1 年以上**」である。**レートをどう絞っても
`slug-????` は目標に届かない**（§3.4）。

### 3.4 分散攻撃に対する効き目

| 攻撃者の持つ IP 数 | 総レート | `slug-????` の全探索 |
|---|---|---|
| 1 | 1 回/秒 | 12.1 日 |
| 100 | 100 回/秒 | 2.9 時間 |
| 1,000 | 1,000 回/秒 | **17 分** |

対してエントロピー側は次のとおり。

| 接尾辞の長さ | 探索空間 | 1,000 回/秒での全探索 |
|---|---|---|
| 4 文字（現行） | 1,048,576 | 17 分 |
| 8 文字 | 1,099,511,627,776 | **約 34.9 年** |

**てこはエントロピー側にある。** 本 Issue は単一 IP からの総当たりを 600 倍遅くするが、
**S1 を解決しない。** 完了条件にこれを明記する（§8）。

### 3.5 一斉再接続時のクライアントの振る舞い

`apps/timer-web` は指数バックオフ（初回 1 秒・上限 30 秒・上限回数なし）で自動再接続し、
再接続後に `resumeToken` つきで `room.join` を再送する（`sync/resume-identity.ts`）。

ルームがアイドル 30 分で回収済みの場合、この再送は `ROOM_NOT_FOUND` を受ける。ただし
`ui/error-action.ts` が `ROOM_NOT_FOUND` を `session-lost` に振り分け、`App.tsx` が
`clearResumeIdentity()` を呼ぶため、**各クライアントは 1 回だけ失敗し、以後 join を再送しない**。

**帰結**: 同一 NAT の N 人が一斉に復帰すると、失敗は瞬間的に N 件積まれるが、その後は増えない。
バースト容量が N を上回っていれば正規利用者は締め出されない（§4 決定 D2）。

## 4. 決定

### D1: 鍵は IP アドレスの HMAC。IPv6 は /64 に丸める

レート制限の鍵は、クライアント IP を正規化したうえで **HMAC-SHA256（起動ごとのランダムソルト）**
した値とする（**MUST**）。IPv6 は**上位 64 ビットのみ**を鍵に使う（**MUST**）。IPv4 は全 32 ビットを使う。

**理由**: VPS・ISP は 1 ホストに IPv6 /64 を割り当てるのが標準であり、アドレス単位で数えると
送信元を回すだけでレート制限が消える。/64 で丸めると、IPv4 で NAT 配下を 1 つと数えるのと
同じ粒度になり、両者の扱いが揃う。/48 まで丸めるとクラウド事業者の /48 に同居する
無関係なテナントを巻き込むため採らない。

正規化の誤りは 2 方向に壊れる。**過剰にまとめる**（別の /64 を同じ鍵に）と誤爆が増えるだけだが、
**細かく分けすぎる**（同じ /64 を別の鍵に）と**静かに回避できる**。後者を作らないことが要件であり、
§3.2 の表記ゆれをすべて同じ鍵へ落とすことで担保する。

### D2: 窓ではなくトークンバケツ。容量 60・毎秒 1 補充

失敗回数の制限は、**容量 60・毎秒 1 個補充のトークンバケツ**とする（**MUST**）。

**理由**: 持続レートとバースト耐性は分離できる。「10 回/10 秒」の窓は持続 1 回/秒を表現すると
同時に「10 回を超える瞬間的な集中を許さない」と言ってしまうため、§3.5 の一斉再接続で
正規利用者を締め出す。バケツなら持続レートを 1 回/秒に保ったままバースト 60 件を吸収できる。

- 持続レートは **1 回/秒**。ADR 0011 決定4 の仮定と一致する
- 攻撃者が 1 年に得る試行回数は 31,536,000 + 60。バーストの寄与は誤差
- 回復が滑らか。窓方式は「窓ぶん丸ごと拒否」だが、バケツは 1 秒ごとに 1 件通る
- 保持するのは鍵ごとに**残量と最終更新時刻の 2 値**のみ

### D3: 判定・照会・消費の 3 段を分離する

レート制限器は次の 3 つを別々の関数として公開する（**MUST**）。呼び出し側は
**「判定 → 照会 → 消費」の順で使う**（**MUST**）。

```
shouldReject(key, now): boolean   // 残量が無ければ true
consume(key, now): void           // 失敗が確定したときだけ呼ぶ
sweep(now): void                  // 満タンに戻ったエントリを捨てる
```

**理由**: 判定と消費を 1 関数にまとめると、実装が「照会してから判定する」順序を選べてしまう。
その順序ではバケツが空のときに `ROOM_NOT_FOUND` が返り、**攻撃者はトークンを消費せずに
存在確認を続けられる**。レート制限が意味を失う。バケツが空のときは**照会する前に**拒否し、
正しいコードで来ても同じ応答を返すことで、存在の有無を漏らさない。

現行の `room-join.ts` は既にこの順序である。本設計はその順序を API の形で固定する。

### D4: 掃除は最終掃除時刻で間隔を空ける

`sweep` は、Map のサイズが閾値を超え、**かつ**前回の掃除から容量ぶんの補充時間（60 秒）が
経過したときにだけ全走査する（**MUST**）。

**理由**: サイズ閾値だけを条件にすると、エントリが全部フレッシュな状況では何も消えず、
サイズが閾値以上のまま次の呼び出しでもまた全走査が走る。O(n) が毎回になる。
タイマー（`setInterval`）は使わない。テストが実時間に依存しなくなるため。

### D5: `X-Forwarded-For` の最後の要素だけを使う

クライアント IP は `X-Forwarded-For` の**最後のカンマ区切り要素**から取る（**MUST**）。
`X-Real-IP` は使わない（**MUST NOT**）。

**理由**: §3.1 のとおり `X-Real-IP` は偽装がそのまま素通しする。`X-Forwarded-For` の最後の要素は、
Caddy が上書きする場合も追記する場合も「Caddy が見た直接のピア」であり、本番の Caddy の版・
設定に依存しない。

### D6: 二段の fail-closed

```
起動時   NODE_ENV=production かつ HOST がループバック以外   → 起動を拒否する
接続時   NODE_ENV=production かつ クライアント IP が不明   → close(1008) で拒否する
```

いずれも **MUST**。`ALLOWED_ORIGINS` の既存の fail-closed（`config.ts`）と同じ型である。

**理由（起動時）**: Caddy を迂回して sync へ直接繋げば `X-Forwarded-For` を自由に偽装でき、
レート制限を無効化できるうえ、任意の他人の IP に濡れ衣を着せられる。ループバック限定を
強制すれば、**ufw の設定状態に依存せず**この経路が消える。検証できない前提への依存を切る。

**理由（接続時）**: フォールバックを黙って接続単位へ戻すと、本番で `X-Forwarded-For` が
届かなくなったときに**防御が静かに後退する**。壊れて気づく方を選ぶ。

**適用範囲**: 拒否するのは WebSocket 接続のみ。管理エンドポイント（`/status`・`/admin/rooms`）は
127.0.0.1 から直接叩く運用であり（ADR 0011 脅威 S12）、`X-Forwarded-For` を持たない。
ここを拒否すると管理面が使えなくなるため、対象外とする（**MUST NOT** 拒否する）。

**拒否の close reason**: Origin 拒否と**別の文字列**を使う（**MUST**）。どちらも close コードは
1008 であり、reason を分けないと「XFF 拒否のテスト」が実は Origin 拒否を見ているだけ、という
空振りが起きる。

**dev・単体テストでの挙動**: `NODE_ENV` が `production` でなく `X-Forwarded-For` も無い場合は、
接続 ID（`conn-<n>`）を鍵にフォールバックする。現行と同じ接続単位の挙動になる。

### D7: 相関キーは接続の生存期間まで保持する（ADR 0012 D3 の改訂）

相関キー（IP の HMAC 値）は、**レート制限器のエントリと、それを生成した接続の、長い方**まで
保持し、どちらも失われた時点で破棄する（**MUST**）。**ADR 0012 D3 を改訂する。**

**理由**: ADR 0012 D3 は「レート制限の窓が閉じたら、ハッシュ値も破棄する（MUST）」と書いているが、
これは #103 の実装形が未定のまま書かれた（ADR 0011 決定4 が「閾値は #103 自身が決める」と明記）。
長寿命の WebSocket 接続を IP 単位で縛るには、接続の生存期間ぶん相関キーを覚える以外に方法がない。

代案を 2 つ検討し、いずれも成立しなかった。

- **IP は接続の受け入れだけに使い、失敗の計数は接続単位に戻す**: 合成レートが
  「接続受け入れ 1 回/秒 × 接続あたり 30 回/10 秒」＝ 30 回/秒となり、目標の 1 回/秒に 30 倍届かない
- **バケツオブジェクトへの参照だけを接続に持たせ、Map からは満タンで落とす**: 以後その接続は
  自分専用のバケツを使うことになり、**接続を多数張れば制限を回避できる**

実害の評価: ハッシュは起動ごとのソルトで非可逆、ソルトはメモリのみに存在し、ログ・snapshot・
永続化のいずれにも出さず、プロセス再起動で消える。**同一 IP の複数接続を紐づけられること自体が、
レート制限の目的そのものである。**

## 5. 設計

### 5.1 新パッケージ `@tasuki/rate-limit`

`packages/rate-limit`。`@tasuki/protocol` と同じ形（`exports: { ".": "./src/index.ts" }`・
ビルド不要・TypeScript ソースを直接公開）。スクリプトは `test`（vitest）・`lint`・`typecheck`。
外部依存なし（`node:crypto`・`node:net` のみ）。

**なぜ新パッケージか**: timer-sync と poker-sync の双方から使う。両アプリに独立実装を置くと
閾値と正規化方式の正本が 2 本になり、`docs/adr/0002` の二重正本の禁止に触れる。
`@tasuki/protocol` への相乗りは、あちらが「境界のメッセージ定義」のパッケージであり、
防御ロジックを入れると責務がボケるため採らない。

公開する関数:

```
createClientKeyDeriver(salt: Uint8Array):
  (forwardedFor: string | undefined) => string | null

createTokenBucketLimiter({ capacity, refillPerSec }): {
  shouldReject(key: string, now: number): boolean
  consume(key: string, now: number): void
  sweep(now: number): void
  size(): number
}
```

戻り値の `null` は「クライアント IP を特定できなかった」を表す。`{ key, known }` の形は
採らない。**`fallback`（特定できなかったときにどの鍵を使うか）は呼び出し側（adapter）の
責務**とし、このパッケージには持たせない。D6 の接続時 fail-closed（本番は拒否・dev は
接続 ID を代替鍵にする、という分岐）は adapter 側の判断であり、`null` を受け取った adapter
がその分岐を行う。パッケージ側が `known: boolean` を返す設計にすると、この分岐ロジックが
パッケージへ漏れ出し、責務が曖昧になる（実装時に `string | null` へ変更。§5.2 も参照）。

### 5.2 クライアント鍵の導出

```
1. X-Forwarded-For を最後のカンマ区切り要素まで刈り込む（D5）
2. 前後空白・角括弧・ゾーン ID（%...）を除去する
3. net.isIP で判定する
     4 → 文字列をそのまま正規形にする（先行ゼロは isIP が弾く・§3.2）
     6 → 8 グループへ完全展開し、
           IPv4 射影アドレス（::ffff:0:0/96）なら下位 32 ビットを IPv4 の
             点付き 10 進へ復元し、v4: 名前空間の正規形にする（実測・F1）
           それ以外は上位 4 グループを整数化した正規形にする（= /64・D1）
     0 → 特定できない（呼び出し側は null を受け取り、fallback 鍵を自分で選ぶ）
4. HMAC-SHA256(salt, 正規形) を鍵にする（ソルトは 32 バイト未満を拒否する）
```

ソルトはプロセス起動時に `randomBytes(32)` で 1 回だけ生成し、env 化しない（ADR 0012 D3）。
32 バイト未満のソルトは `createClientKeyDeriver` が throw する。正規形（`v4:<IP>` 等）は
探索空間の狭い既知の文字列なので、ソルトが退化すると鍵から IP を総当たりで逆算できるため。

**IPv4 射影アドレスの扱いは実測で判断を訂正した経緯がある。** 当初は「埋め込み IPv4
（`::ffff:192.0.2.1`）は定義上つねに下位 32 ビットに来るため、上位 64 ビットの抽出には
影響しない」としていたが、これは前段の事実は正しく結論が逆だった。**下位 32 ビットに
あるからこそ**、/64（上位 4 グループ）だけを見る丸めでは IPv4 部が常に切り捨てられ、
`::ffff:203.0.113.7` も `::ffff:198.51.100.9` も同じ `v6:0:0:0:0` に落ちる（実測で確認、
F1）。全世界の IPv4 射影クライアントが単一の鍵バケツを共有する状態であり、識別情報が
丸めで完全に消える欠陥だった。対処として、6 判定後に 8 グループへ完全展開し、
IPv4 射影レンジ（`::ffff:0:0/96`）かどうかを数値で判定した上で、射影であれば
`v4:` 名前空間へ落とす（§5.1 の実装を参照）。射影ではない埋め込み IPv4
（`2001:db8::192.0.2.1` のように上位ビットが非ゼロのもの）は当初の記述どおり
/64 の抽出に影響しない。影響するのは射影アドレス特有の「上位 96 ビットが固定」という
性質による。

### 5.3 各アプリへの結線

**生 IP は adapter の変数スコープを出ない**（ADR 0012 D3）。両アプリとも、現在 `origin` を
読んでいるのと同じ場所で `X-Forwarded-For` を読み、**鍵へ変換してから** `ConnectionData` に
載せる。application 層は生 IP を見ない。

| | timer-sync | poker-sync |
|---|---|---|
| 鍵を作る場所 | `adapters/ws-adapter.ts` の `handleFetch` | `src/server.ts` の `Bun.serve` の `fetch` |
| 数える失敗 | `room.join` の `ROOM_NOT_FOUND` とパスフレーズ不一致、`ai.unlock` の失敗 | `join-room` と `check-room` の `room-not-found` |
| 拒否時のエラー | 既存の `JOIN_RATE_LIMITED` / `RATE_LIMITED`（コードを変えない） | 新設 `rate-limited` |

- timer-sync の `application/join-rate-limiter.ts` は `@tasuki/rate-limit` のバケツへ置き換える。
  接続クローズ時の `clear(connId)` は無くなる（鍵が接続に紐づかないため）。掃除は D4 が担う
- `room.join` と `ai.unlock` が**同一インスタンスのバケツを共有する**制約は維持する
  （現行の `join-rate-limiter.ts` が明記している。別インスタンスにすると合言葉の総当たり対策が
  黙って弱まる）
- poker の `rate-limited` は `packages/poker-core/src/protocol.ts` の `ERROR_CODES` へ追加する
  （サーバーとクライアントの共通正本。`deploy.sh` が web と sync を同時に配るため版ずれは起きない）

**poker の `check-room` の約束が変わる**: 現行は「無いときだけ応える。無音＝生きている」
（`server.ts` のコメント・#76 J-1）。レート制限に掛かると `rate-limited` が返るため、**無音の意味が
「生きている」から「生きている、または拒否された」へ変わる**。画面は「参加フォームを出しておき、
無いと分かったらエラー表示へ切り替える」形なので実害は小さいが、約束の変更として記録する。

## 6. 検証

### 6.1 EARS（機能系 Issue の「振る舞い」節へ転記する）

- 単一の送信元 IP からの入室失敗が毎秒 1 件を超えて続く場合、システムは超過分の要求を拒否すること
- 入室失敗が 60 件を超えて瞬間的に集中した場合、システムは 60 件目までを受け付けること
- レート制限に達している間に入室要求を受けたとき、システムは**ルームの存在を照会する前に**拒否し、
  ルームの有無によらず同じエラーコードを返すこと
- 同一の IPv6 /64 に属する複数のアドレスから要求を受けたとき、システムはそれらを 1 つの
  送信元として数えること
- 本番環境で `HOST` がループバック以外に設定されている場合、システムは起動を拒否すること
- 本番環境でクライアント IP を特定できない接続を受けたとき、システムは Origin 拒否とは異なる
  理由を付けて接続を閉じること
- 本番環境以外でクライアント IP を特定できない場合、システムは接続 ID を鍵として数えること

## 8. 残るリスクと申し送り

- **本 Issue は S1 を解決しない。** 単一 IP からの総当たりは 600 倍遅くなるが、複数 IP へ分散されると
  総レートは IP 数に比例する（§3.4）。ADR 0011 決定4 自身が「複数 IP へ分散する攻撃者を防ぐもの
  ではない」と明記している。**完了条件に明記する**
- **グローバルな失敗レート上限は採らない。** 上限が発火している間は正規利用者も入室できず、
  攻撃者が意図的に飽和させることで入室妨害 DoS へ転換できる。#103 の元の動機が可用性で
  あったことを踏まえると本末転倒である
- **`ai.unlock` の初回バーストが 30 → 60 に増える。** 持続レートは実質無制限から 1 回/秒へ
  劇的に改善するが、バーストだけを見ると増える。`AI_UNLOCK_KEY` は運用者が決める文字列であり、
  #136 が指摘したとおり**エントロピーの規範がない**。**合言葉のエントロピー規範を別途起こす**
- **poker は本番未公開**（`deploy/poker/app.env` に明記）。poker 側の起動時 fail-closed は
  #66 のデプロイ当日に本番で初めて走る。**#66 への申し送り**
- ADR 0011 決定4 の見直しで、仮定「1 回/秒」を本設計の実測値へ置き換える
