## 3. 実測した事実

### 3.1 Caddy の `X-Forwarded-For` の扱い（2026-08-14 実測・Caddy 2.11.4）

`reverse_proxy` の背後にプレーンな HTTP サーバーを置き、ヘッダを偽装して測った。Caddy は
`:19900`（ポート番号のみ指定＝Go の dual-stack listener）で待ち受けており、下表は
`127.0.0.1`（IPv4）から接続した計測である。同じ dual-stack listener に IPv6 から接続した
計測は本節後半（「多要素・重複ヘッダ・IPv6 での追加実測」）を参照。

| クライアントが送るヘッダ | バックエンドに届く値 |
|---|---|
| （何も送らない） | `X-Forwarded-For: 127.0.0.1` |
| `X-Forwarded-For: 9.9.9.9` | `X-Forwarded-For: 127.0.0.1`（**偽装値は消える**） |
| `X-Forwarded-For: 1.1.1.1, 2.2.2.2` | `X-Forwarded-For: 127.0.0.1`（**上書き。追記ではない**） |
| `X-Real-IP: 9.9.9.9` | `X-Real-IP: 9.9.9.9`（**そのまま素通し**） |

WebSocket upgrade 要求（`Connection: Upgrade` ＋ `Sec-WebSocket-Key`）でも同じ挙動だった。

**帰結**: `X-Real-IP` は攻撃者が自由に書けるため**使わない**。`X-Forwarded-For` は信頼できるが、
本設計は**最後のカンマ区切り要素**を取る。Caddy が上書きでも追記でも正しく、本番の Caddy の版・
設定に依存しないため（§7 の未確認事項を参照）。

**実断片での再測定（2026-08-14・Caddy 2.11.4）**: 上記は手書きの Caddyfile での実測だった。
リポジトリの実断片（`deploy/timer/caddy/10-timer-ws.conf` と `deploy/poker/caddy/20-poker.conf` を
1 バイトも変えずコピーし、`import` で読み込んだもの）を通しても同じ結果になるかを実装タスク 1 で
測り直した。バックエンドはプレーンな Node HTTP サーバー（ポート 8787＝timer、3311＝poker）。

| 経路 | 送ったヘッダ | 実際に届いた応答 |
|---|---|---|
| `/timer/ws`（`handle` ＋ `rewrite * /ws` ＋ `reverse_proxy 127.0.0.1:8787`） | `X-Forwarded-For: 9.9.9.9` ＋ `X-Real-IP: 9.9.9.9` | `{"url":"/ws","xff":"127.0.0.1","xrealip":"9.9.9.9"}` |
| `/poker/ws`（`handle` ＋ `rewrite * /ws` ＋ `reverse_proxy 127.0.0.1:3311`） | `X-Forwarded-For: 9.9.9.9` | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |

`handle` と `rewrite` を挟んでも、`X-Forwarded-For` の偽装値（`9.9.9.9`）は手書き版と同じく
`127.0.0.1` に上書きされ、`rewrite * /ws` によって sync 側が受け取るパスは想定どおり `/ws` になった。
timer 側では `X-Real-IP` が `9.9.9.9` のまま素通しされることも再確認した（**使ってはいけない証拠**）。
これで §3.1 の実測は実断片経路でも成立していると確認できた。実装の以降のタスクはこの事実に依存してよい。

**実断片での upgrade 経路再測定（2026-08-14・Caddy 2.11.4）**: 上記の実断片再測定はプレーンな GET
だった。本番の実経路は WebSocket upgrade 要求そのものなので、同じ実断片環境に対して
`Connection: Upgrade` ／ `Upgrade: websocket` ／ `Sec-WebSocket-Version: 13` ／
`Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==` を付け、`X-Forwarded-For: 9.9.9.9` を偽装して測り直した。

| 経路 | 送ったヘッダ | 実際に届いた応答 |
|---|---|---|
| `/timer/ws`（upgrade ヘッダ付き） | `X-Forwarded-For: 9.9.9.9` ＋ upgrade 4 ヘッダ | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |
| `/poker/ws`（upgrade ヘッダ付き） | `X-Forwarded-For: 9.9.9.9` ＋ upgrade 4 ヘッダ | `{"url":"/ws","xff":"127.0.0.1","xrealip":null}` |

（バックエンドの echo サーバーはプレーンな HTTP サーバーで `101 Switching Protocols` を返さないため、
Caddy は upgrade を確立できず通常の `200 OK` を返した。それでも `reverse_proxy` がバックエンドへ
転送する `X-Forwarded-For` と `rewrite` 後のパスはプレーン GET のときと同じであり、ヘッダ書き換え
自体は upgrade 要求か否かに左右されないことが確認できた。）

**帰結**: upgrade ヘッダを足しても `X-Forwarded-For` の偽装値は同じく `127.0.0.1` に上書きされ、
`url` は `/ws` になった。プレーン GET の実測と一致しており、**ヘッダ書き換え（XFF の上書き・
`rewrite` によるパス変換）が upgrade 要求か否かに左右されないこと**が確認できた。ただし今回の
実測はハンドシェイク要求（HTTP リクエスト行とヘッダ）の段階までであり、`101 Switching Protocols`
後の WebSocket 接続確立そのものは測っていない（バックエンドの echo サーバーが 101 を返さないため）。
レート制限はハンドシェイク要求時のヘッダで判定するため、この範囲の確認で本設計の前提としては
十分である。

**多要素・重複ヘッダ・IPv6 での追加実測（2026-08-14・Caddy 2.11.4）**: 上記は XFF を 1 本だけ
送ったケースしか測っていなかった。`e2e/harness` がキャッシュしている実バイナリで、素の
`reverse_proxy` 構成に対し、複数要素・重複ヘッダ・IPv6 ループバックを追加で測った。

| 送ったもの | バックエンドに届いた `X-Forwarded-For` |
|---|---|
| XFF なし | `127.0.0.1`（実ピア）・1 本 |
| `X-Forwarded-For: 9.9.9.9`（偽装 1 本） | `127.0.0.1`・1 本 |
| `X-Forwarded-For` を 2 本（`9.9.9.9` と `8.8.8.8`） | `127.0.0.1`・**1 本**（重複ヘッダは畳まれる） |
| `X-Forwarded-For: 9.9.9.9, 8.8.8.8`（カンマ 2 要素） | `127.0.0.1`・1 本 |
| `X-Forwarded-For: 9.9.9.9,`（末尾カンマ） | `127.0.0.1`・1 本 |
| IPv6 ループバック `[::1]` から接続 | `::1`（**射影形 `::ffff:` ではない**）・1 本 |

**この実測から言えること**:

- 攻撃者は XFF の内容を一切制御できない。重複ヘッダによる「最後の要素の乗っ取り」は
  素の `reverse_proxy` では成立しない
- Caddy は dual-stack ソケットで受けた IPv4 接続にも点付き 10 進を書く。**射影形は書かない**ので、
  F1 の欠陥（IPv4 射影アドレスが `v6:0:0:0:0` に丸め崩壊する）は現構成では本番到達しない
  潜在欠陥だった。とはいえ `@tasuki/rate-limit` は Caddy 経由に限定されない汎用パッケージであり、
  将来別の前段プロキシや直接呼び出しで射影形が現れる可能性は残るため、修正自体は行う
- 「最後の要素を採る」規則（D5）は、この構成では常に要素数 1 を見ることになる。多要素の扱いは
  前段プロキシが増えたときのための防御

### 3.2 `net.isIP` による妥当性判定（Bun で実測）

| 入力 | `net.isIP` | 意味 |
|---|---|---|
| `1.2.3.4` | 4 | — |
| `01.2.3.4` | **0（拒否）** | IPv4 は先行ゼロが弾かれる → **表記が一意**。文字列のまま鍵にしてよい |
| `2001:db8::1` | 6 | — |
| `2001:DB8::1` | **6（通る）** | 同一アドレスの別表記 |
| `2001:0db8::1` | **6（通る）** | 同一アドレスの別表記 |
| `2001:db8:0:0::1` | **6（通る）** | 同一アドレスの別表記 |
| `[2001:db8::1]` | 0 | 角括弧は事前に剥がす必要がある |
| `2001:db8::1%eth0` | 6 | ゾーン ID は通る。事前に剥がす |
| `unknown` / 空文字 | 0 | — |

**帰結**: IPv6 は**同一アドレスに複数の表記があり、すべて検証を通る**。文字列をそのまま鍵にすると、
表記を変えるだけで別の鍵になり、レート制限を回避できる。**必ず数値へ展開して正規化する。**

### 3.3 総当たりコストと探索空間

現行レートは **600 回/秒**（同時接続上限 200 × 接続単位 10 秒あたり 30 回。接続単位なので
再接続で窓がリセットされる。ADR 0011 決定4 の「#103 実装前」の前提レート）。

| 対象 | 生成方式 | 探索空間 | 600 回/秒 | 1 回/秒 |
|---|---|---|---|---|
| timer・ルーム名あり `slug-????` | 小文字英数 32 種 × 4 桁 | 1,048,576 | **約 29.1 分** | 約 12.1 日 |
| timer・ルーム名なし `A7K2M9` | 大文字英数 31 種 × 6 桁 | 887,503,681 | 約 17 日 | 約 28.1 年 |
| poker `roomId` | UUID 先頭 8 桁（32 bit） | 4,294,967,296 | 約 82.9 日 | 約 136 年 |

ADR 0011 決定4 の目標は「**全探索に 1 年以上**」である。**レートをどう絞っても
`slug-????` は目標に届かない**（§3.4）。

**てこはエントロピー側にある。** 本 Issue は単一 IP からの総当たりを 600 倍遅くするが、

### 3.5 一斉再接続時のクライアントの振る舞い

`apps/timer-web` は指数バックオフ（初回 1 秒・上限 30 秒・上限回数なし）で自動再接続し、
再接続後に `resumeToken` つきで `room.join` を再送する（`sync/resume-identity.ts`）。

ルームがアイドル 30 分で回収済みの場合、この再送は `ROOM_NOT_FOUND` を受ける。ただし
`ui/error-action.ts` が `ROOM_NOT_FOUND` を `session-lost` に振り分け、`App.tsx` が
`clearResumeIdentity()` を呼ぶため、**各クライアントは 1 回だけ失敗し、以後 join を再送しない**。

**帰結**: 同一 NAT の N 人が一斉に復帰すると、失敗は瞬間的に N 件積まれるが、その後は増えない。
バースト容量が N を上回っていれば正規利用者は締め出されない（§4 決定 D2）。

**#103 実装後の追記（このバケツ ID 単位ではなく NAT/IP 単位で共有されるようになったことによる
帰結。§8 にも申し送る）**: バースト容量（既定 60）を N が上回る場合、61 人目以降は
`ROOM_NOT_FOUND` ではなく `JOIN_RATE_LIMITED` を受ける（実測: N=100 で `ROOM_NOT_FOUND`
60 件 / `JOIN_RATE_LIMITED` 40 件）。**「各クライアントは 1 回だけ失敗し、以後 join を
再送しない」という上記の前提は `JOIN_RATE_LIMITED` には当てはまらない**
——`apps/timer-web/src/ui/error-action.ts` の `errorAction` は `JOIN_RATE_LIMITED` を
列挙しておらず、既定の `transient` に落ちる。`App.tsx` の `transient` 分岐はバナー表示と
自動消去（4 秒）のみで、`clearResumeIdentity()` も再送も行わない。**結果として、
バースト容量を超えた利用者は接続済み・未入室のまま滞留し、リロードするまで復帰しない。**
クライアント側の扱い（再送・指数バックオフでの再挑戦等）は本 Issue のスコープ外とし、
別 Issue へ送る。製品コード（`error-action.ts` / `App.tsx`）はこの Issue の範囲では
変更しない。

## 4. 決定

### D1: 鍵は IP アドレスの HMAC。IPv6 は /64 に丸める

レート制限の鍵は、クライアント IP を正規化したうえで **HMAC-SHA256（起動ごとのランダムソルト）**
した値とする（**MUST**）。IPv6 は**上位 64 ビットのみ**を鍵に使う（**MUST**）。IPv4 は全 32 ビットを使う。

**理由**: VPS・ISP は 1 ホストに IPv6 /64 を割り当てるのが標準であり、アドレス単位で数えると
送信元を回すだけでレート制限が消える。/64 で丸めると、IPv4 で NAT 配下を 1 つと数えるのと
同じ粒度になり、両者の扱いが揃う。/48 まで丸めるとクラウド事業者の /48 に同居する
無関係なテナントを巻き込むため採らない。

正規化の誤りは 2 方向に壊れる。**過剰にまとめる**（別の /64 を同じ鍵に）と誤爆が増えるだけだが、
**細かく分けすぎる**（同じ /64 を別の鍵に）と**静かに回避できる**。後者を作らないことが要件であり、
§3.2 の表記ゆれをすべて同じ鍵へ落とすことで担保する。

### D2: 窓ではなくトークンバケツ。容量 60・毎秒 1 補充

失敗回数の制限は、**容量 60・毎秒 1 個補充のトークンバケツ**とする（**MUST**）。

**理由**: 持続レートとバースト耐性は分離できる。「10 回/10 秒」の窓は持続 1 回/秒を表現すると
同時に「10 回を超える瞬間的な集中を許さない」と言ってしまうため、§3.5 の一斉再接続で
正規利用者を締め出す。バケツなら持続レートを 1 回/秒に保ったままバースト 60 件を吸収できる。

- 持続レートは **1 回/秒**。ADR 0011 決定4 の仮定と一致する
- 攻撃者が 1 年に得る試行回数は 31,536,000 + 60。バーストの寄与は誤差
- 回復が滑らか。窓方式は「窓ぶん丸ごと拒否」だが、バケツは 1 秒ごとに 1 件通る
- 保持するのは鍵ごとに**残量と最終更新時刻の 2 値**のみ

### D3: 判定・照会・消費の 3 段を分離する

レート制限器は次の 3 つを別々の関数として公開する（**MUST**）。呼び出し側は
**「判定 → 照会 → 消費」の順で使う**（**MUST**）。

```
shouldReject(key, now): boolean   // 残量が無ければ true。状態を書き換えない（純粋な照会）
consume(key, now): void           // 失敗が確定したときだけ呼ぶ
sweep(now): void                  // 満タンに戻ったエントリを捨てる
size(): number                    // 保持しているエントリ数（検査・運用観測用）
sweepRunCount(): number           // sweep が実際に全走査した回数（検査・運用観測用）
```

`size()` と `sweepRunCount()` は防御の挙動そのものではなく、**掃除が生きているかを外から
確かめるための観測点**である（**MUST**）。D4 の「全走査は最悪でも `refillFullMs` に 1 回」も
「しきい値が大きすぎて掃除が死んでいないか」も、この 2 つが無ければテストからも運用からも
確かめられない。実際 `sweepThreshold` の上限を設ける根拠になった「5 万件を保持したまま掃除が
0 回」は `sweepRunCount()` で観測した。

**`shouldReject` は純粋な照会であり、内部状態を一切書き換えない（MUST）。** これは呼び出し順
（D3）と直結した不変条件である。D3 の順序では `shouldReject(k, t)` と `consume(k, t)` が
**同じ `now` を 2 回観測する**ため、照会でも時刻の基準点を進める設計にすると、単発の異常な
`now` が自分自身を「2 回連続の裏付け」として認証してしまう（実測: そう実装したところ、
`consume` を単発で呼べば 10 万件通るのに、D3 の順では 59 件で凍結した）。

**理由**: 判定と消費を 1 関数にまとめると、実装が「照会してから判定する」順序を選べてしまう。
その順序ではバケツが空のときに `ROOM_NOT_FOUND` が返り、**攻撃者はトークンを消費せずに
存在確認を続けられる**。レート制限が意味を失う。バケツが空のときは**照会する前に**拒否し、
正しいコードで来ても同じ応答を返すことで、存在の有無を漏らさない。

現行の `room-join.ts` は既にこの順序である。本設計はその順序を API の形で固定する。

### D4: 掃除は最終掃除時刻で間隔を空ける。呼び出しは consume 駆動のまま、タイマーは使わない

`sweep` は、Map のサイズが**閾値（既定 `DEFAULT_SWEEP_THRESHOLD`。値の正本はここ。1,000 件）**を
超え、**かつ**前回の掃除から容量ぶんの補充時間（`refillFullMs`。60 秒）が経過したときにだけ
全走査する（**MUST**）。閾値・容量・補充速度はいずれもコンストラクタの引数で、非有限や
0 以下（`sweepThreshold` のみ 0 は許容）を渡すと起動時に `throw` する（**MUST**）。さらに、
`capacity` と `refillPerSec` の商である `refillFullMs` 自体が非有限・0 になる組み合わせ
（例: `capacity` が極端に大きい、`refillPerSec` が極端に小さい）も起動時に `throw` する
（**MUST**）。個々の入力が有限でも、商はオーバーフロー・アンダーフローしうるため。

**`refillFullMs` が有限かつ正でも、基準時刻の前進幅として意味を持たないほど小さい場合は
起動時に `throw` する（**MUST**。実装では M-1 ガードと呼ぶ）。** 基準時刻（`refTime`）は
1 回の呼び出しで最大 `refillFullMs` しか進めない設計だが、`refillFullMs` が
`Number.MAX_SAFE_INTEGER` 規模の加算で吸収されてしまう大きさだと、`clock + refillFullMs`
が丸め誤差で `clock` と等しくなり、基準時刻が実質的に一切前進しなくなる（実測:
`capacity: 1, refillPerSec: 1e7` は `capacity` も `refillPerSec` も有限かつ正で、
`refillFullMs`（≈0.0001ms）も有限の正数だが、`createTokenBucketLimiter` はこの組み合わせを
`throw` で拒否する。個々の入力・商のどちらも上記の非有限・0 以下チェックをすり抜ける値の
組であるため、別の検査として必要）。

`sweepThreshold` には**上限**もある。`MAX_SWEEP_THRESHOLD`（値の正本はここ。**1,000,000 件**）を
超える値を渡すと起動時に `throw` する（**MUST**）。有限であっても到達不能に大きい値
（例: `Number.MAX_VALUE`）は `buckets.size` が一生しきい値を超えず、**自動の掃除が完全に死ぬ**
（実測: `Number.MAX_VALUE` で 5 万件を保持したまま全走査が 0 回）。非有限を `throw` で弾いて
おきながら、同じ結末を「有限だが到達不能な値」という別の入口から素通しするのは筋が通らない。

**上限を 1,000,000 件にした根拠**は 2 つある。1 つは掃除の停止時間で、`sweep` は同期パスで走る
O(n) であり、本節の実測では 50 万件で 1 回 34.7 ms かかる。100 万件なら約 70 ms で、同期の
sync サーバーがイベントループを止めてよい実用上の限界がこのあたりにある。もう 1 つはメモリで、
1 エントリ約 473 バイトなので 100 万件は約 473 MB になる。**`sweepThreshold` は掃除を開始する
下限であり、Map サイズの上限ではない点に注意する。** 実際のピークは
`sweepThreshold +（掃除の間隔 1 窓ぶんで増える件数）`になり、この 473 MB を上回りうる。
本節で実測した最悪の攻撃ピーク（5,000 件/秒で約 305,000 件・約 144 MB）の 3 倍以上あり、
正常な運用値がこの上限に触れることはない。

`capacity` は **1 以上**を要求する（**MUST**）。`0 < capacity < 1` は「有限の正数」ではあるが、
満タンでも残量が 1 に届かないため、一度でも失敗した鍵は補充が終わっても「残量 < 1」が成立し
続け、その鍵の利用者が永久に拒否される（実測: `capacity: 0.5` で 1 回失敗した鍵は、その後
10,000 秒ぶんの補充を挟んでも 1 件も通らない）。これは `sweepThreshold` の上限（防御が死ぬ側）
とは逆に、**無実の利用者が締め出される側**の設定ミスであり、どちらも起動時に落とす。

**理由**: サイズ閾値だけを条件にすると、エントリが全部フレッシュな状況では何も消えず、
サイズが閾値以上のまま次の呼び出しでもまた全走査が走る。O(n) が毎回になる。

**間隔の判定は渡された `now` ではなく、内部基準時刻の目盛りで行う（MUST）。** `lastSweepAt`
には基準時刻 `t`（後述「時計の非単調性」）を記録し、条件も「`t - lastSweepAt >= refillFullMs`」
とする。基準時刻は**単調非減少**なので差が負になることが原理的に起きず、絶対値（`Math.abs`）も
「`lastSweepAt` が未来にある」という特別扱いも要らない。

**間隔の判定に絶対値（`Math.abs`）を使ってはいけない（MUST NOT）**。前方へ大きく飛んだ時刻で
1 度掃除すると基準点が未来の値になる。その後 `now` が現実的な値へ戻ると差が負のまま続き、
絶対値を取る間隔条件は「経過した」ときだけでなく常に成立してしまい、以後の呼び出し
（`consume` 経由の毎回）で O(n) の全走査が走り続ける。

基準時刻は 1 回の呼び出しで最大 `refillFullMs` しか進まないため、**`consume` 駆動の自動掃除に
限れば、全走査は最悪でも `refillFullMs` に 1 回**という不変条件が、前方への時計飛びが
混じっても保たれる（**MUST**）。

**この不変条件は `consume` 内部の間隔・閾値判定を経由する自動掃除にのみ適用され、公開
`sweep(now)` を直接呼ぶ経路には及ばない。** `sweep(now)` は呼ばれた回数だけ無条件に全走査
する（間隔・閾値の判定を一切経由しない。`sweepAt` を直接呼ぶだけの実装である）。したがって
`sweep(now)` を高頻度に呼べば全走査も同じ頻度で起きる。**呼び出し頻度の責任は呼び出し側に
ある。** 下記「誰が `sweep` を呼ぶか」が「定期バッチ・管理コマンドで `sweep(now)` を
明示的に呼ぶことは妨げない」と述べているのはこの前提のうえであり、手動呼び出しの頻度に
上限を設けないのは設計上の意図であって、本項の MUST と矛盾しない（実測:
`createTokenBucketLimiter({capacity:60, refillPerSec:1})` に同一時刻で `sweep(now)` を
100 回呼ぶと `sweepRunCount()` は 100 になる）。

**実測（`capacity` 2・`refillPerSec` 1・`refillFullMs` 2,000ms、`now` を上端 `T0`+1,000,000ms と
下端 `T0`+2,000ms の間で 5,000 回往復させたときの全走査回数）**:

| 実装 | 全走査回数 |
|---|---|
| `Math.abs` を使った誤った間隔判定 | **4,998 回**（往復回数とほぼ同数＝毎回全走査） |
| `now` を直に使い、未来判定で引き戻す旧方式 | **2,499 回**（前方向への遷移のたび） |
| 基準時刻の目盛りで判定する現行方式 | **499 回** |

499 は上限そのものである。往復の振幅 998,000ms を `refillFullMs` 2,000ms で割ると 499 で、
基準時刻がこの区間で進みうる幅を使い切ったところで全走査は止まる。

#### 誰が `sweep` を呼ぶか

**自動の掃除は `consume` の呼び出し駆動のままとし、タイマー（`setInterval`）は追加しない
（MUST）**。テストが実時間に依存しなくなるため（既存の理由を維持）。

**`sweep` 自体は `RateLimiter` の公開メソッドである。** 上記は「自動発火の仕組み」の話で
あって、`sweep` の可視性の話ではない。呼び出し側（adapter）が運用上の都合（例: 定期
バッチ・管理コマンド）で `sweep(now)` を明示的に呼ぶことは妨げない。むしろテスト自身が
`limiter.sweep(now)` を直接呼んでいる（`sweep` の掃除条件と、前方へ飛んだ `now` が
混じったときの挙動を検証するため）。

この設計には次のトレードオフがある。**正直に書く**:

- 自動の掃除は `consume` 駆動のみであるため、**手動で `sweep` を呼ばない運用では、攻撃が
  止むと保持数はその時点の値のまま残る**（次に誰かが失敗するまで回収されない）
- 保持数の上限は「直近の窓で失敗した相異なる IP の数」で決まる。これは IP 単位の
  レート制限では本質的なコストであり、タイマーを足しても消えない
- `sweep` は O(n) であり、`consume` の同期パス（または手動呼び出し自身の同期パス）で
  走るため、その間はイベントループが止まる

#### 実測値（2026-08-14・token-bucket 実装に対する敵対的レビューの一環で測定）

- 1 エントリあたりの占有メモリ: **約 473 バイト**（HMAC-SHA256 の鍵長 64 文字・30 万件で測定）
- 攻撃レート 600 件/秒: ピーク **36,599 件・約 17 MB**
- 攻撃レート 5,000 件/秒: ピーク **304,995 件・約 144 MB**
- `sweep` の所要時間: 50 万件のとき 1 回 **34.7 ms**

#### `now` の値域の契約

`shouldReject`・`consume`・`sweep` はいずれも `now` に**有限数**を要求する（**MUST**）。
`Number.isFinite(now)` が偽のときの挙動:

- `shouldReject`: **`true`（拒否）** を返す
- `consume`: 状態を一切書き換えずに戻る（`NaN` を状態へ焼き付けない）
- `sweep`: no-op（`lastSweepAt` も更新しない）

**理由**: `NaN` はすべての比較を false にするため、素朴な実装では判定も掃除も
「通す・消さない」側へ倒れる。レート制限は防御であり、例外で接続処理ごと落とすより、
判定不能な入力は弾く（拒否する）ほうが安全側である。

#### 時計の非単調性（会計は `now` ではなく内部基準時刻で行う）

`now` は後退しうる（NTP のステップ調整・VM スナップショットからの復帰で現実に起きる）し、
前方へ大きく飛ぶこともある（誤って 100 年先の値が渡る等）。**渡された `now` をそのまま
会計に使ってはいけない（MUST NOT）。** `now` を**単調非減少で、1 回の呼び出しで進める幅に
上限のある内部基準時刻**へ丸めてから、残量・`updatedAt`・`lastSweepAt` のすべてをその
目盛りで扱う（**MUST**）。

基準時刻を進める幅は、次の 3 つの上限の**最小**とする（負なら 0 に丸める＝進めない）:

| 上限 | 何を防ぐか |
|---|---|
| `now - 直近に観測した now` | 実時間が経っていない前進。時計が巻き戻れば負になり 0 に丸まるので、巻き戻り中は「時間が止まる」挙動になる（V4: 無実の利用者を締め出さない） |
| `now - 基準時刻` | 基準時刻が実時刻を追い越すこと。巻き戻った後の復路（元の時刻へ戻るまでの差分）を二重に加算しない（V3: バースト枠を還付しない） |
| `refillFullMs` | 1 度の前方飛びで満タン 1 杯を超えて進むこと。壊れた時計が 1 回だけ遠い未来を渡しても基準時刻はそこへ飛ばない（I-4: 永久凍結しない） |

**理由**: この 3 つを課すと基準時刻は単調非減少になり、かつ実時刻を追い越さない。
どのバケツの `updatedAt` も「過去のある時点の基準時刻」なので、**`updatedAt` が基準時刻より
未来になることが原理的に起きない**。したがって次のものが**すべて不要になる（MUST NOT: 残さない）**:

- 残量計算での `Math.max(0, now - updatedAt)`（経過時間が負にならない）
- `consume` が書き込む `updatedAt` の `Math.max(既存の updatedAt, now)`（時刻が後退しない）
- 掃除の間隔判定での未来判定・`Math.abs`（差が負にならない）
- 「時計リセットの検知」と「満タン扱いで再出発」（そういう状態にならない）

最後の 2 つが消えることが要点である。**許可側（レート制限が緩む側）への譲歩は
`refillFullMs` の上限 1 か所に集約される。**

**譲歩の粒度は「1 回の呼び出しにつき満タン 1 杯まで」であって、「生涯で 1 度だけ」ではない
（MUST 読み違えないこと）。** `refTime` は毎回の呼び出しで独立に `refillFullMs` で頭打ちする
だけで、これまでに何回還付したかを覚えていない。**壊れた時計のジャンプが間隔を空けて 2 回・
3 回と来れば、その都度あらためて満タン 1 杯ぶんが還付される**（実測: 暖機した制限器で使い切った
あと、遠い未来へのジャンプを 3 回繰り返すと、各回の直後に **60 件**＝容量ちょうどずつ通った）。

> **この節の 4 度目の訂正（2026-08-15）。** 直前の版は「各回 59 件」と書いていたが誤りだった。
> 計測スクリプトが `drain` の前に `consume` を 1 回呼んでおり、その 1 回を数え漏らしていた
> （controller の誤り。実装者はそれを転記した）。**同じ段落が「満タン 1 杯ぶん」と書いている
> 以上、容量 60 と一致しなければ自己矛盾する** — この矛盾は段落を自分自身と突き合わせるだけで
> 見つけられた。数値を書くときは、その数値が同じ段落の他の主張と整合するかを見ること。

総量に効く上限は別にある。基準時刻 `t` は構造上つねに「観測した `now` の最大値」以下なので、
**還付の累計は実時刻の進みを追い越せない**。旧方式との差は「誤検知のたび、実時刻と無関係に
無制限へ還付する」対「1 回の呼び出しにつき満タン 1 杯、累計は観測した `now` の最大値まで」で
あり、後者に絞り込めたこと自体が本方式の価値である。

（この節は 3 度書き直している。最初は「許可側へ倒れる分岐が 1 つも無い」、次は「還付の総量は
満タン 1 杯に固定」と書き、いずれも実測で反証された。**断定を書いたら、その断定を壊す
呼び出し列を実際に作ってみること。**）

**照会は基準時刻を動かしてはいけない（MUST NOT）。** `shouldReject` は丸めた値を読むだけで、
基準時刻も「直近に観測した `now`」も更新しない（D3 の純粋性の項を参照）。`consume` と
`sweep` は状態を書き換える操作なので更新する。

**残余（正直に書く）**: **ごく最初の 1 回目の呼び出しが壊れた時計だった場合**（比較する基準が
まだ存在しないコールドスタート）は、その値がそのまま基準時刻になる。この限定器インスタンスは
`clock`（内部基準時刻）を 1 個しか持たないため、**特定の鍵だけでなく全鍵が凍結する**
（実測: controller の実測で、無関係な鍵 `innocent` の通過が理想 100,000 件に対し 60 件まで
落ち込んだ）。以後の正常な `now` では基準時刻が進まないので、各バケツは残量を使い切った
ところで凍結する。凍結している間は誰も満タンに戻らないため、**`sweep` が 1 件も回収できず、
Map のエントリが際限なく増え続ける**（実測: コールドスタート後に 5,000 鍵を投入し `sweep` を
100 回呼んでも `size` は 5,001 のまま）。凍結期間は「壊れた時計が渡した値と実時刻との差」＝
**飛び幅ぶんの実時間**であり、実時刻がその差に追いつくまで解消しない。

この焼き付きは `consume` だけでなく、**`sweep` が最初の commit になった場合にも起きる**
（`sweep` も内部で `commit: true` で `refTime` を呼ぶため）。定期バッチ・管理コマンドから
`sweep` だけを繰り返し呼ぶ運用（D4 参照）を許しているため、コールドスタートの入口は
「ごく最初の 1 回目の `consume` 呼び出し」に限らず、`sweep` が先に呼ばれる経路も含む。

これは既知の残余であり、テストで明示している。**旧方式（`stableNow`）の残余とは包含関係に
ない（真部分集合ではない）。** 新旧のどちらが広いかは指標によって逆転する（実測、controller）:

| 指標 | 新方式 | 旧方式 |
|---|---|---|
| 稼働中に前方へ時計が飛んだ後の通過件数（理想 100,000） | **99,999**（ほぼ解消） | 59（凍結） |
| コールドスタート時、**無関係な鍵**の通過件数（理想 100,000） | **60**（鍵横断へ広がる） | 100,000（無傷） |
| コールドスタート後、5,000 鍵投入＋`sweep` 100 回後の `size` | **5,001**（回収されない） | 1 |

新方式は**稼働中の凍結を解消した一方、コールドスタート時の凍結は単一の鍵から鍵横断（全鍵）へ
広がった**。これはトレードオフであり、「旧方式の残余の真部分集合」という主張は撤回する。

**旧方式（`stableNow`）を採らなかった理由**: 「近い `now` が 2 回連続したら信用できる現在時刻
として前進させる基準点」を持つ案は、D3 の呼び出し順と両立しない。D3 は
`shouldReject(k, t)` → `consume(k, t)` を要求するので**同じ `now` が必ず 2 回観測され**、
`|now - 前回の now| < refillFullMs` が常に成立する。つまり単発の異常な `now` が
**自分自身を「2 回連続の裏付け」として認証**してしまう。実測: `consume` を単発で呼べば
10 万件通るのに、D3 の順では 59 件で凍結した（`Math.max` で `updatedAt` に焼き付くので
二度と戻らない）。既存テストが緑だったのは、テストが `shouldReject` を呼ばずに `consume` を
単発で呼んでおり、**実経路を通っていなかった**ためである。

### D5: `X-Forwarded-For` の最後の要素だけを使う

クライアント IP は `X-Forwarded-For` の**最後のカンマ区切り要素**から取る（**MUST**）。
`X-Real-IP` は使わない（**MUST NOT**）。

**理由**: §3.1 のとおり `X-Real-IP` は偽装がそのまま素通しする。`X-Forwarded-For` の最後の要素は、
Caddy が上書きする場合も追記する場合も「Caddy が見た直接のピア」であり、本番の Caddy の版・
設定に依存しない。

### D6: 二段の fail-closed

```
起動時   NODE_ENV=production かつ HOST がループバック以外   → 起動を拒否する
接続時   NODE_ENV=production かつ クライアント IP が不明   → close(1008) で拒否する
```

いずれも **MUST**。`ALLOWED_ORIGINS` の既存の fail-closed（`config.ts`）と同じ型である。

**理由（起動時）**: Caddy を迂回して sync へ直接繋げば `X-Forwarded-For` を自由に偽装でき、
レート制限を無効化できるうえ、任意の他人の IP に濡れ衣を着せられる。ループバック限定を
強制すれば、**ufw の設定状態に依存せず**この経路が消える。検証できない前提への依存を切る。

**理由（接続時）**: フォールバックを黙って接続単位へ戻すと、本番で `X-Forwarded-For` が
届かなくなったときに**防御が静かに後退する**。壊れて気づく方を選ぶ。

**適用範囲**: 拒否するのは WebSocket 接続のみ。管理エンドポイント（`/status`・`/admin/rooms`）は
127.0.0.1 から直接叩く運用であり（ADR 0011 脅威 S12）、`X-Forwarded-For` を持たない。
ここを拒否すると管理面が使えなくなるため、対象外とする（**MUST NOT** 拒否する）。

**拒否の close reason**: Origin 拒否と**別の文字列**を使う（**MUST**）。どちらも close コードは
1008 であり、reason を分けないと「XFF 拒否のテスト」が実は Origin 拒否を見ているだけ、という
空振りが起きる。

**dev・単体テストでの挙動**: `NODE_ENV` が `production` でなく `X-Forwarded-For` も無い場合は、
接続 ID（`conn-<n>`）を鍵にフォールバックする。現行と同じ接続単位の挙動になる。

**接続時 fail-closed の役目（P-4・敵対的レビューで確定）**: 接続時の検査は
「`X-Forwarded-For` が**ある**か」しか見ておらず、**その内容が信用できるかは一切見ていない**。
本番モードでも、ソケットに直接届きさえすれば偽装した `X-Forwarded-For` を配るだけで
Task 5 実測と同数（180 件）の枠稼ぎが通る（再レビューが実測）。したがって**接続時
fail-closed は Task 5 の穴（枠稼ぎ）を塞ぐ防御ではなく**、Caddy 経由で `X-Forwarded-For` が
届かなくなったことに運用者が気づける形にするための検査である。

**枠稼ぎを実際に止めているのは、起動時 fail-closed（`HOST` をループバック限定）と Caddy と
ufw の組み合わせである。** 接続時 fail-closed 単体には枠稼ぎを止める効力がない。

**ここで誤解しやすい点を訂正する。** 「`HOST` をループバック外へ変える変更は、レート制限を
丸ごと無効化する」という表現は誤りである。`HOST` を書き換えるだけでは無効化されない
——**`server-env.ts` の起動時 fail-closed が `NODE_ENV=production` かつ `HOST` が
ループバック以外のとき起動そのものを拒否する（D6・MUST）ため、本番でこれをやると
サービスが起動せず、すぐに気づける失敗になる。**

**実際に静かにレート制限を無効化しうるのは次の 2 つである**:

1. **起動時 fail-closed の検査そのものを外す・緩める変更**（`isLoopbackHost` の判定を
   緩める、`config.ts` の throw を削る等）。この場合だけ `HOST` をループバック外にしても
   起動が通ってしまう
2. **env から `NODE_ENV=production` が落ちる（未設定・書き間違いになる）変更。** これは
   `HOST` のループバック検査と `requireClientAddress`（接続時 fail-closed）を**同時に**
   無効化し、かつ `isProductionEnv` が false 側へ倒れるため、接続単位の鍵へ**静かに戻る**
   （`server-env.ts` は未知の値なら throw するが、空文字列や `development` は正規の値として
   通る）。3 箇所すべてが一度に緩む点で、`HOST` 単体の書き換えより深刻である

次にこのコードへ触る人が誤った方向（`HOST` さえ守れば安全、という誤解）へ誘導されないよう、
ここに明記する。

**検討したが採らなかった代案（二重化）**: 接続元ピアが 127.0.0.1 のときだけ
`X-Forwarded-For` を受け入れる、という二重化も可能である（レビュアー提案）。
**controller の裁定として今回は採らない。** `Bun.Server#requestIP` への依存が増え、
E2E・テストの構成にも影響するためである。

### D7: 相関キーは接続の生存期間まで保持する（ADR 0012 D3 の改訂）

相関キー（IP の HMAC 値）は、**レート制限器のエントリと、それを生成した接続の、長い方**まで
保持し、どちらも失われた時点で破棄する（**MUST**）。**ADR 0012 D3 を改訂する。**

**理由**: ADR 0012 D3 は「レート制限の窓が閉じたら、ハッシュ値も破棄する（MUST）」と書いているが、
これは #103 の実装形が未定のまま書かれた（ADR 0011 決定4 が「閾値は #103 自身が決める」と明記）。
長寿命の WebSocket 接続を IP 単位で縛るには、接続の生存期間ぶん相関キーを覚える以外に方法がない。

代案を 2 つ検討し、いずれも成立しなかった。

- **IP は接続の受け入れだけに使い、失敗の計数は接続単位に戻す**: 合成レートが
  「接続受け入れ 1 回/秒 × 接続あたり 30 回/10 秒」＝ 30 回/秒となり、目標の 1 回/秒に 30 倍届かない
- **バケツオブジェクトへの参照だけを接続に持たせ、Map からは満タンで落とす**: 以後その接続は
  自分専用のバケツを使うことになり、**接続を多数張れば制限を回避できる**

実害の評価: ハッシュは起動ごとのソルトで非可逆、ソルトはメモリのみに存在し、ログ・snapshot・
永続化のいずれにも出さず、プロセス再起動で消える。**同一 IP の複数接続を紐づけられること自体が、
レート制限の目的そのものである。**

### D8: `shouldReject` / `consume` / `sweep` に渡す `now` は単調時計（`performance.now()`）でなければならない

アダプタ（timer-sync・poker-sync）がレート制限器に渡す `now` は、**壁時計（epoch ms）ではなく
単調時計（`performance.now()`）を使うこと（MUST）。**

**背景（controller の裁定）**: D4 で明記したコールドスタートの残余は、「起動直後の 1 回目の
`consume`（または `sweep`）が壊れた時計を見る」と発生する。**VPS では systemd が NTP 同期の
完了より前にサービスを起動することが現実に起きる**ため、これは机上の空論ではない。起きた場合、
起動直後に接続してきた全利用者が入室できなくなり、実時刻がその壊れた値へ追いつくまで回復しない
（可用性の実害）。

**根本対処**: レート制限が必要とするのは**経過時間だけ**であり、絶対時刻（今日が何月何日か）を
一度も使わない。制限器はインメモリでプロセス寿命と一致するため、`performance.now()` の原点
（プロセス起動時刻 = 0）とちょうど重なる。単調時計を使えば、NTP のステップ調整・起動時の時計
補正・前方への飛び・巻き戻りは**供給元（OS の壁時計）そのものが供給しなくなる**ため、経路ごと
消える。

**内部ガードは廃止しない（多層防御）**: `refTime` の 3 つの上限（`now - lastNow` / `now - clock` /
`refillFullMs`）と `Number.isFinite` 検査は、単調時計を渡すという契約が**呼び出し側の実装ミスで
破られた場合**の保険として残す（**MUST**）。D4 の「時計の非単調性」の節はこの契約を前提に
書かれており、内部ガードの記述は変更しない。

**既存の `Clock` ポートとは別系統である（混同禁止）**: `apps/timer-sync/src/ports/clock.ts` の
`Clock.now()` は epoch ms を返す壁時計であり、ルームの会計（`joinedAt` などのアイドル回収の
基準）には**そのまま壁時計を使い続けてよい**。レート制限器に渡す `now` だけを単調時計へ
差し替えること。**同じ変数 `now` を両方に使い回さない（MUST NOT）** — 呼び出し側でこの 2 つを
混同すると、レート制限が単調時計の利点を失うか、ルームの会計が単調時計を誤って受け取るかの
どちらかで壊れる。

**残余は消えない**: 単調時計にしても、D4 のコールドスタート残余がゼロになるわけではない。
プロセス起動直後の 1 回目の呼び出しは、依然として「比較する基準がまだ存在しない」基準点に
なる。変わるのは、その基準点に**「壊れた値」が来る経路そのものが無くなる**ことである。
`performance.now()` は起動時刻を 0 として単調に増えるため、コールドスタートの基準点は
常に妥当な小さい値になり、本節が対処する「NTP 未同期による誤った巨大値」は発生しない。

## 5. 設計

### 5.1 新パッケージ `@tasuki/rate-limit`

`packages/rate-limit`。`@tasuki/protocol` と同じ形（`exports: { ".": "./src/index.ts" }`・
ビルド不要・TypeScript ソースを直接公開）。スクリプトは `test`（vitest）・`lint`・`typecheck`。
外部依存なし（`node:crypto`・`node:net` のみ）。

**なぜ新パッケージか**: timer-sync と poker-sync の双方から使う。両アプリに独立実装を置くと
閾値と正規化方式の正本が 2 本になり、`docs/adr/0002` の二重正本の禁止に触れる。
`@tasuki/protocol` への相乗りは、あちらが「境界のメッセージ定義」のパッケージであり、
防御ロジックを入れると責務がボケるため採らない。

公開する関数:

```
createClientKeyDeriver(salt: Uint8Array):
  (forwardedFor: string | undefined) => string | null

createTokenBucketLimiter({ capacity, refillPerSec, sweepThreshold? }): {
  shouldReject(key: string, now: number): boolean
  consume(key: string, now: number): void
  sweep(now: number): void
  size(): number
  sweepRunCount(): number
}
```

戻り値の `null` は「クライアント IP を特定できなかった」を表す。`{ key, known }` の形は
採らない。**`fallback`（特定できなかったときにどの鍵を使うか）は呼び出し側（adapter）の
責務**とし、このパッケージには持たせない。D6 の接続時 fail-closed（本番は拒否・dev は
接続 ID を代替鍵にする、という分岐）は adapter 側の判断であり、`null` を受け取った adapter
がその分岐を行う。パッケージ側が `known: boolean` を返す設計にすると、この分岐ロジックが
パッケージへ漏れ出し、責務が曖昧になる（実装時に `string | null` へ変更。§5.2 も参照）。

### 5.2 クライアント鍵の導出

```
1. X-Forwarded-For を最後のカンマ区切り要素まで刈り込む（D5）
2. 前後空白・角括弧・ゾーン ID（%...）を除去する
3. net.isIP で判定する
     4 → 文字列をそのまま正規形にする（先行ゼロは isIP が弾く・§3.2）
     6 → 8 グループへ完全展開し、
           IPv4 射影アドレス（::ffff:0:0/96）なら下位 32 ビットを IPv4 の
             点付き 10 進へ復元し、v4: 名前空間の正規形にする（実測・F1）
           それ以外は上位 4 グループを整数化した正規形にする（= /64・D1）
     0 → 特定できない（呼び出し側は null を受け取り、fallback 鍵を自分で選ぶ）
4. HMAC-SHA256(salt, 正規形) を鍵にする（ソルトは 32 バイト未満を拒否する）
```

ソルトはプロセス起動時に `randomBytes(32)` で 1 回だけ生成し、env 化しない（ADR 0012 D3）。
32 バイト未満のソルトは `createClientKeyDeriver` が throw する。正規形（`v4:<IP>` 等）は
探索空間の狭い既知の文字列なので、ソルトが退化すると鍵から IP を総当たりで逆算できるため。

**IPv4 射影アドレスの扱いは実測で判断を訂正した経緯がある。** 当初は「埋め込み IPv4
（`::ffff:192.0.2.1`）は定義上つねに下位 32 ビットに来るため、上位 64 ビットの抽出には
影響しない」としていたが、これは前段の事実は正しく結論が逆だった。**下位 32 ビットに
あるからこそ**、/64（上位 4 グループ）だけを見る丸めでは IPv4 部が常に切り捨てられ、
`::ffff:203.0.113.7` も `::ffff:198.51.100.9` も同じ `v6:0:0:0:0` に落ちる（実測で確認、
F1）。全世界の IPv4 射影クライアントが単一の鍵バケツを共有する状態であり、識別情報が
丸めで完全に消える欠陥だった。対処として、6 判定後に 8 グループへ完全展開し、
IPv4 射影レンジ（`::ffff:0:0/96`）かどうかを数値で判定した上で、射影であれば
`v4:` 名前空間へ落とす（§5.1 の実装を参照）。射影ではない埋め込み IPv4
（`2001:db8::192.0.2.1` のように上位ビットが非ゼロのもの）は当初の記述どおり
/64 の抽出に影響しない。影響するのは射影アドレス特有の「上位 96 ビットが固定」という
性質による。

### 5.3 各アプリへの結線

**生 IP は adapter の変数スコープを出ない**（ADR 0012 D3）。両アプリとも、現在 `origin` を
読んでいるのと同じ場所で `X-Forwarded-For` を読み、**鍵へ変換してから** `ConnectionData` に
載せる。application 層は生 IP を見ない。

| | timer-sync | poker-sync |
|---|---|---|
| 鍵を作る場所 | `adapters/ws-adapter.ts` の `handleFetch` | `src/server.ts` の `Bun.serve` の `fetch` |
| 数える失敗 | `room.join` の `ROOM_NOT_FOUND` とパスフレーズ不一致、`ai.unlock` の失敗 | `join-room` と `check-room` の `room-not-found` |
| 拒否時のエラー | 既存の `JOIN_RATE_LIMITED` / `RATE_LIMITED`（コードを変えない） | 新設 `rate-limited` |

- timer-sync の `application/join-rate-limiter.ts` は `@tasuki/rate-limit` のバケツへ置き換える。
  接続クローズ時の `clear(connId)` は無くなる（鍵が接続に紐づかないため）。掃除は D4 が担う
- `room.join` と `ai.unlock` が**同一インスタンスのバケツを共有する**制約は維持する
  （現行の `join-rate-limiter.ts` が明記している。別インスタンスにすると合言葉の総当たり対策が
  黙って弱まる）
- poker の `rate-limited` は `packages/poker-core/src/protocol.ts` の `ERROR_CODES` へ追加する
  （サーバーとクライアントの共通正本。`deploy.sh` が web と sync を同時に配るため版ずれは起きない）

**poker の `check-room` の約束が変わる**: 現行は「無いときだけ応える。無音＝生きている」
（`server.ts` のコメント・#76 J-1）。レート制限に掛かると `rate-limited` が返るため、**無音の意味が
「生きている」から「生きている、または拒否された」へ変わる**。画面は「参加フォームを出しておき、
無いと分かったらエラー表示へ切り替える」形なので実害は小さいが、約束の変更として記録する。

### 6.1 EARS（機能系 Issue の「振る舞い」節へ転記する）

- 単一の送信元 IP からの入室失敗が毎秒 1 件を超えて続く場合、システムは超過分の要求を拒否すること
- 入室失敗が 60 件を超えて瞬間的に集中した場合、システムは 60 件目までを受け付けること

- 本番環境でクライアント IP を特定できない接続を受けたとき、システムは Origin 拒否とは異なる
  理由を付けて接続を閉じること

## 8. 残るリスクと申し送り

- **接続時 fail-closed は Task 5 の穴（枠稼ぎ）を塞ぐ防御ではない**（D6・P-4 で詳述）。
  枠稼ぎを止めているのは起動時 fail-closed（`HOST` をループバック限定）と Caddy と ufw の
  組み合わせであり、接続時 fail-closed は「XFF が届かなくなったことに気づける形にする」
  ためのものである。**`HOST` を単体で書き換えても、本番では起動時 fail-closed が起動を
  拒否するため、レート制限は丸ごと無効化されない**（気づける側の失敗）。実際に静かに
  無効化しうるのは、起動時 fail-closed の検査そのものを外す・緩める変更と、env から
  `NODE_ENV=production` が落ちる変更（`HOST` 検査と `requireClientAddress` の両方が同時に
  緩み、接続単位へ静かに戻る）の 2 つである。次にこのコードへ触る人が「`HOST` さえ
  守れば安全」と誤解しないよう D6 に明記した
- **`NODE_ENV` が効く箇所は 3 つ（`ALLOWED_ORIGINS` の fail-closed・`HOST` のループバック
  限定・`requireClientAddress`）＋ `server-env.ts` の未知値 throw であり、`e2e/harness/sync.ts`
  のコメント（「2 箇所だけ」）は古い。** `e2e/` は本タスクの対象外のため直接は修正していない。
  次に `e2e/harness/sync.ts` に触る人（controller）へ申し送る
- **§3.5 の「各クライアントは 1 回だけ失敗し、以後 join を再送しない」は #103 実装後は
  成立しない。** バケツが NAT 単位（IP 単位）で共有されるため、N > 60（バースト容量）の
  一斉復帰では 61 人目以降が `ROOM_NOT_FOUND` ではなく `JOIN_RATE_LIMITED` を受ける
  （実測: N=100 で `ROOM_NOT_FOUND` 60 件 / `JOIN_RATE_LIMITED` 40 件）。`error-action.ts` は
  `JOIN_RATE_LIMITED` を既定の `transient` に振り分け、`App.tsx` の `transient` 分岐は
  バナー表示のみで再送・自動再試行を行わないため、**61 人目以降は接続済み・未入室のまま
  滞留し、リロードするまで復帰しない。** クライアント側の対応（再送・指数バックオフの
  再挑戦等）は本 Issue のスコープ外とし、別 Issue へ送る
- **本 Issue は S1 を解決しない。** 単一 IP からの総当たりは 600 倍遅くなるが、複数 IP へ分散されると
  総レートは IP 数に比例する（§3.4）。ADR 0011 決定4 自身が「複数 IP へ分散する攻撃者を防ぐもの
  ではない」と明記している。**完了条件に明記する**
- **グローバルな失敗レート上限は採らない。** 上限が発火している間は正規利用者も入室できず、
  攻撃者が意図的に飽和させることで入室妨害 DoS へ転換できる。#103 の元の動機が可用性で
  あったことを踏まえると本末転倒である
- **`ai.unlock` の初回バーストが 30 → 60 に増える。** 持続レートは実質無制限から 1 回/秒へ
  劇的に改善するが、バーストだけを見ると増える。`AI_UNLOCK_KEY` は運用者が決める文字列であり、
  #136 が指摘したとおり**エントロピーの規範がない**。**合言葉のエントロピー規範を別途起こす**
- **poker は本番未公開**（`deploy/poker/app.env` に明記）。poker 側の起動時 fail-closed は
  #66 のデプロイ当日に本番で初めて走る。**#66 への申し送り**
- ADR 0011 決定4 の見直しで、仮定「1 回/秒」を本設計の実測値へ置き換える
- **拒否ログの発生ペースが journald の既定レート制限に抵触しうる（再確認・実測）。**
  Origin 拒否は `maxConnections` の検査より前にあり、未認証ハンドシェイクの受け入れ自体に
  上限が無いため、単一クライアントから連投すると `conn-rejected` が約 1,300〜1,900 行/秒
  出ることが実測された。実装の欠陥ではないが、攻撃のピーク時に「気づくために足したログ」
  自体が journald 側で抑制されうる点は運用上の注意として残す
