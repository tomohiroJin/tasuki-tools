## 1. 何のために作るか

利用者が最初に使う場面は **KPT のふりかえり（1 時間）** である。

> K を出すのに 5 分、P を出すのに 7 分、投票に 1 分、Try に対する議論の時間をリーンコーヒーのように取りたい。
> タイマーを毎回セットしなおしたり、実行を忘れたり、入れ忘れたりして時間通りに進まない。そのうえ全体で 1 時間という約束が過ぎて困る。（利用者・要旨）

Try の議論では、ファシリテーターが時間をずるずると延長してしまうことがある（利用者の経験から作った例。特定の会の出来事ではない）。
これを止めやすくするのは**道具による強制ではなく見えること**だ、というのが利用者の考えである。

> 現在の時間の進捗とオーバーした時間の長さが見えていれば止めやすい。（利用者）

したがってこの道具の芯は次の 2 つ。

1. **組んでおけば、あとは迷わず進む。** 区切りの名前と長さを前もって並べておく。当日は「開始」を押すだけで、区切りごとにセットし直す手間・押し忘れが無くなる
2. **約束の 1 時間に対して、いまどこにいるかが全員に見える。** 押し・巻き・超過・終わる見込みを、隠さずに数字と形で出す

### あるべき姿（#429 から）

- **進行役**として、会議の前に区切りとその時間を組んでおき、当日はボタン 1 つで始めて、区切りごとに迷わず次へ進められる
- **参加者**として、いま何の時間で、あと何分で、この後に何が続き、会がいつ終わる見込みかが分かる
- **チーム**として、予定より押したときに気づき、どこを詰めるかをその場で決められる

## 2. 範囲

### 2.1 第 1 段で作るもの（利用者の決定）

利用者の言葉: 「LT や朝会の型は同じ型で使える仕様になるといい。が一気に全ては無理なので、シナリオ的にタイマーを利用できる（5, 7, 1 のように）部分が最初にほしい。リーンコーヒーも最初はオーバー」

- 名前と長さを持つ**区切り**を並べた**シナリオ**を組み、順に計って進める
- 区切りごとに**時間切れの振る舞い**を選べる（§4.4）
- 会の最中にできる組み替えは**延長**と**飛ばす**だけ（利用者: 「延長と飛ばすができれば十分」）
- 組んだシナリオを**端末に保存して使い回せる**
- 会全体の**進み・押し巻き・超過・終わる見込み**が全員に見える
- 見た目は**カードテーブルの世界観の中で磨き上げる**。モチーフは懐中時計（§7）

### 2.3 やらないこと（反目標）

- **延長を道具で止めない。** 延長の回数・合計に上限を設けて強制しない。判断はチームに任せ、道具は見せることに徹する（§1）。ただし入力の健全性のための数値の上限（§6）はこれとは別
- **上限の無い延長の道を作らない。** 延長は必ず「何分足すか」を決めて入れる。0 を過ぎたあとの超過は数字として見え続ける
- **役割を持ち込まない。** 進行役だけが押せる、のような段差は作らない（#95）。ルームにいる誰でも押せる
- **サーバーにシナリオや記録を残さない**（原則 III）
- **timer の交代の輪に混ぜない。** timer は改造しない

## 3. 使う場面（利用者の言葉から）

- **リモートで、各自が自分の画面で開く**のが基本。全員の画面で同じ時計が動く
- 集まっているときは、**代表の人の画面、または全員に見えるスクリーンに映す**。手元のノート PC でも、部屋の奥からスクリーンでも読めなければならない
- 利用者: 「できるだけスタイリッシュでカッコイイが求められる」
- シナリオを組むのは、**会の冒頭、みんながルームに入る前**（利用者）。進行役が先にルームを作って組んでおき、後から入った人は開始前に今日の進行表を見られる

## 4. 振る舞い

### 4.1 言葉

| 語 | 意味 |
|---|---|
| シナリオ | 区切りの並びと、会の名前。端末に保存して使い回す単位 |
| 区切り | 名前・長さ（分）・時間切れの振る舞いを持つ 1 行 |
| 進行 | ルームでシナリオを 1 回走らせている状態。区切りごとの実績を持つ |
| 予定 | 開始時点のシナリオの合計。「予定の終わり」は開始時刻 ＋ 予定の合計 |
| 終わる見込み | いまの区切りの残り（0 未満なら 0）＋ まだの区切り（飛ばしたものを除く）の長さの合計 ＋ いまの時刻 |
| 押し・巻き | 終わる見込み − 予定の終わり。正なら押し、負なら巻き |
| 超過 | いまの区切りの経過 − （長さ ＋ 延長）が正のときのその値 |

### 4.2 準備（開始前）

1. ルームでこのツールを開くと、ルームのシナリオが空なら**組む画面**が出る
2. 区切りを並べる。各区切りには**名前・長さ（分）・時間切れの振る舞い**がある。区切りの追加・削除・並べ替えは開始前ならできる
3. 組んでいる間、盤のプレビューに**合計時間と、いま開始したときの終わる見込みの時刻**が出る
4. 「この端末に保存」で名前を付けて保存する。保存済みの一覧から選ぶと、ルームのシナリオがそれに置き換わる
5. **見本として「KPT のふりかえり」を 1 つ同梱する**【判断】: K を出す 5 分 → P を出す 7 分 → 投票 1 分 → Try の議論 40 分 → 予備 7 分（合計 60 分・全区切り「押すまで待つ」）。K・P・投票の長さは利用者の言葉、Try と予備は 60 分に収まるよう設計者が置いた
6. シナリオは**ルームの共有状態**であり、後から入った人にも開始前の進行表として見える。組み替えはルームの誰でもでき、**シナリオ全体の置き換え 1 種のコマンド**で表す（後勝ち）【判断】

### 4.3 進行

- 誰かが「開始」を押すと、全員の盤が一斉に動き出す。1 つ目の区切りが始まる
- 「次へ」でいまの区切りを終え、次の（飛ばしていない）区切りへ移る。時間が来る前に押せば、そのぶん巻く
- 「一時停止」「再開」ができる。**一時停止の間も壁の時計は進むので、予定の終わりとの差（押し）は増える**【判断】（約束しているのは壁の時計の 1 時間なので、隠さない）
- 最後の区切りを終えると**終了**になり、区切りごとの予定・延長・実績・差の一覧と、合計の押し巻きが出る（Markdown のコピーは後続）
- 終了後と進行中に「最初から」で進行を捨ててシナリオだけ残す（確認を挟む）【判断】
- 進行中はシナリオの組み替えはできない（延長と飛ばすを除く）

### 4.4 時間切れ（利用者の決定）

利用者: 「両方をオプション選択できるとうれしい。きっと基本は押すまで超過を数えながらでしょうが、LT は流れ続けるのがうれしい」

区切りごとに次のどちらかを持つ。

| 振る舞い | 既定 | 0 になったとき |
|---|---|---|
| **押すまで待つ** | ○ | 音と画面の合図を 1 回出す。0 で止めず、超過を「+0:42」のように数え続ける。盤には赤銅色の超過の弧が伸びる。誰かが「次へ」を押すまで次へ移らない |
| **自動で次へ** | | 音と画面の合図を出し、次の区切りへ移る。最後の区切りなら終了する |

- **自動で次へ移す判断はサーバーが行う（MUST）。** 画面ごとに判断すると、閉じている画面・遅れている画面で割れる。サーバーは時計のポートで期限を張り、一時停止・延長・次へ・最初からで張り直す
- 合図の音は既存の timer の交代チャイム（`apps/timer-web/src/platform/sound.ts`）と同じ考え方で鳴らす（初回の操作で解錠した `AudioContext`）【判断】。段階的な合図・音の種類の選択は第 2 段

### 4.5 延長と飛ばす（利用者の決定）

- **延長**: いまの区切りに「+1 分」「+3 分」「+5 分」を足す【判断: 刻み】。何度でも押せる。延長は区切りの長さと**別に**記録し、盤・一覧では「予定 7 分 ＋ 延長 3 分」と分けて見せる。延長した瞬間に終わる見込みと押しが動く
  - 超過中に延長すると、残りが正に戻りうる（リーンコーヒーの「区切り直す」に近い使い方。第 3 段で本格的に扱う）
  - 「自動で次へ」の区切りでも延長できる。期限はサーバーが張り直す
- **飛ばす**: **まだ始まっていない**区切りを「やらない」にする。飛ばした区切りの長さは終わる見込みから引かれ、巻きとして表れる。始まる前なら「戻す」ができる【判断】。いまの区切りを早く終えるのは「次へ」で、飛ばすではない
- 順番の入れ替え・区切りの追加は第 1 段ではやらない

### 4.6 途中で入った人・再接続

- 途中で入った人・再接続した人には、その時点の進行の全体（シナリオ・いまの区切り・経過・実績）が届き、同じ盤から合流できる
- ルームは揮発で、再起動・デプロイ・アイドルの破棄で進行は消える（原則 III・受容）。シナリオは保存した端末から読み直せる

## 5. 設計

置き場所は**独立したツール**とする【判断】。timer のモードにはしない —— timer はモブプロの交代の輪が中心で、区切りの並びとは形が違う（#429 の「実装時に決めること」2 の見立てと同じ）。
新しい文脈を足すので **ADR を通す（原則 II）**。番号は `docs/adr/` の次（現時点で 0027）。ルーレット（`docs/adr/0026`）と同じ形で足す。

| 層 | 置き場所（仮名） | 中身 |
|---|---|---|
| ドメイン | `packages/agenda-core` | シナリオの検証・展開・進行の遷移・押し巻きの計算。純粋関数（原則 VI）。`room-core` を含むどの `@tasuki/*` にも依存しない（`docs/adr/0026` 決定 1 と同じ） |
| 同期サーバー | `apps/tasuki-sync` | 接続の種類 `?tool=agenda`（綴りの正本は `application/tool-id.ts`）。ストア・ハンドラ・配信・期限の時計。ルームの破棄で一緒に消す |
| 画面 | `apps/agenda-web` | 組む画面・進める画面・終了の一覧。端末の保存 |
| 玄関 | `apps/landing` | ツールの札を 1 枚足す |
| 配備 | `deploy/` | ルーレットと同じ形 |

名前（`agenda`・画面上の呼び名）は仮。**画面上の呼び名は「進行タイマー」を仮置きする**【判断】（書体の base 層に入ることは実測済み。§7.3）。

### 5.1 ドメイン（`packages/agenda-core`）

**シナリオ（定義）と進行の計画（展開済みの並び）を分ける。** これが第 2 段への継ぎ目である。

- `Scenario` = 会の名前 ＋ `items`。第 1 段の `items` の要素は区切り（`Step`）だけ
- `expand(scenario) → PlannedStep[]` が展開済みの平らな並びを返す。第 1 段では区切りをそのまま写すだけ
- **進行の遷移はすべて `PlannedStep[]` の上で行う**。第 2 段で `items` に「繰り返しの組」を足すときは `expand` と検証だけが変わり、進行の遷移・押し巻きの計算・wire の進行部分は変えずに済む
- 第 1 段で `items` を判別共用体（`kind: 'step'`）にしておくかは実装者の判断。ただし**抽象の先取りはしない**（原則 X）。「繰り返し」の型そのものは第 2 段で足す

進行の状態（案。名前は実装者が決めてよい）:

- 開始前 / 進行中 / 一時停止中 / 終了
- 展開済みの並び（各区切りの長さ・時間切れの振る舞い・飛ばしたか・延長の合計・実績の経過）
- いまの区切りの位置と、その区切りの経過（`runningSince`＋積算。timer-core の `accumulatedElapsedMs` と同じ考え方）
- 開始した時刻（壁の時計の押し巻きの基準）と、一時停止の累計

純粋関数で出すもの: 押し巻き・終わる見込み・超過・自動で次へ移る期限・終了の一覧。時計は引数で受ける（原則 VI）。
表現は `room-core`・`topic-core`・`roulette-core` と同じ**直接遷移関数 ＋ `Result`**（`docs/adr/0016` 決定 1 が求める記録は ADR に書く）。

### 5.2 時計の配り方

全員が同じ残り時間を見る必要がある。既存の手は 2 つある。

- timer: 端末が `time.ping` を繰り返してサーバーとの時計のずれ（`clockOffset`）を推定する（`apps/timer-web/src/sync/clock-offset.ts`）
- ルーレット: フレームに**送る時点で計った経過**を載せ、端末は受け取ってからの経過（単調時計）を足す（`docs/adr/0026` 決定 3）

**ルーレットの「経過を配る」を採るのを推奨する**【判断】。往復の測定が要らず、絶対時刻を wire に載せない。
ただし 1 時間を超える進行で、フレームが来ない間の端末の単調時計の進みのずれが問題にならないかは実装者が確かめる（数十 ppm なら 1 時間で数十 ms で問題にならない見込み・推測）。
終わる見込みの**時刻**（「15:02 終了見込み」）の表示には端末の壁の時計を使う。数秒のずれは表示上受容する【判断】。

### 5.3 wire

- 進行役の操作はすべて `agenda.*` のコマンド（シナリオの置き換え・開始・次へ・一時停止・再開・延長・飛ばす／戻す・最初から）
- サーバーは変化のたびに進行の全体を 1 本のフレームで配る（途中で入った人も同じフレームで合流できる）
- 境界は Valibot で検証する（原則 IV）。**agenda のコマンドは agenda の接続のスキーマにだけ置く**（`docs/adr/0026` 決定 7 と同じ。ハンドラでも「agenda として在席しているか」を確かめる。接続の受理は `onConnect` を通す）
- **お題のフレームは agenda の接続にも配る**（`docs/adr/0021` 決定 2「宛先はツールを問わない」・`application/topic-broadcast.ts` の `TOPIC_RECIPIENT_TOOLS` に足す）。agenda-web は agenda 固有のスキーマより先に `TopicFrameSchema` で見分ける（同決定の MUST）。第 1 段の画面がお題を表示するかは実装者の判断
- 名簿の配信先に agenda を足すかは実装者の判断（在席の表示に要るなら足す）

### 5.4 端末の保存

- 保存先は **localStorage**【判断】（timer の設定 `apps/timer-web/src/prefs/local-prefs.ts` と同じ考え方。シナリオは小さく、IndexedDB の非同期は要らない）
- 保存するのはシナリオ（会の名前・区切り）だけ。進行の実績は保存しない（第 1 段）
- 読むときは保存の中身も**境界として Valibot で検証する**。保存の形には版を持たせる（第 2 段で `items` が広がるため）
- **古い版は新しい形へ移して読む（MUST）。** 版が上がったときに、利用者が前の段で保存したシナリオを黙って消さない。読み飛ばすのは壊れている項目（どの版のスキーマにも合わない）だけ【判断】
- 保存は**ルームの誰でも、自分の端末に**できる

## 6. 守り（原則 XI・`docs/adr/0011`・`docs/adr/0012`）

区切りの名前・会の名前は**利用者由来のテキスト**である。

- 分類は `docs/adr/0011` 決定 1 の表で決めてから実装する（MUST）。近い前例は「個人に紐づく」に入れた poker の見積もりのアイテム名（#93）で、それに倣うのが筋（推測）。ADR 0027 に記録する
- 描画は既定のエスケープだけ。`dangerouslySetInnerHTML` を使わない
- サーバーのログに名前を出さない（ログの語彙 `application/log/vocabulary.ts` に載せない）
- 上限【判断】（数値は実装者が既存と突き合わせて確定してよい）:

| 項目 | 上限 | 根拠 |
|---|---|---|
| 区切りの数 | 20 | 1 時間の会で 7 前後。#429 の表 |
| 区切りの名前 | 40 字 | 表示名 `MAX_DISPLAY_NAME = 40` に揃える。盤の中央に収める |
| 会の名前 | 60 字 | ルーム名 `MAX_ROOM_NAME = 60` に揃える |
| 区切りの長さ | 1〜120 分（整数） | 投票 1 分が下限。秒の刻みは第 2 段（LT の入れ替え 30 秒など）で要るなら広げる |
| 合計 | 180 分 | 合計の健全性の上限。延長はこれとは別 |
| 延長を含めた 1 区切りの長さ | 240 分 | 数値の健全性の上限。運用の上限ではない（§2.3） |

- 名前の空文字・前後の空白・制御文字の扱いは、お題・表示名の既存の規則に揃える
- **コマンドの頻度の上限は設けない**【判断】。既存のレート制限が数えるのは入室・`ai.unlock` の失敗と poker の入口だけで、普通のコマンドの頻度を抑える仕組みはどのツールにも無い（効くのはメッセージの大きさの上限 `MAX_MESSAGE_BYTES` だけ）。agenda も他のツールと同じ扱いにし、そのことを ADR 0027 に書く。シナリオの置き換えは 20 区切りで小さい

## 7. 見た目（利用者: 「カードテーブルの世界観の中で磨き上げる」）

実装時は `frontend-design` の指針に沿い、**モックを先に作って利用者に見せる**（§10）。ここには方向だけを置く。

### 7.1 方向: 会議の懐中時計

利用者は「カッコイイと思ったのはオールドクラシックな懐中時計」と言い、カードテーブルとは合わせにくいと考えていた。
設計者の見立て【判断】: **合う。** Tasuki の強調色は真鍮（`--gold` 系）、数字はセリフ体の Fraunces で、どちらも懐中時計の素材そのものである。
timer はすでにクロノグラフの目盛り盤・計測弧・運針を持つ（`apps/timer-web/src/styles/circular-progress.css`・`base.css` の `chrono-hand`）。

- **文字盤 1 周 = 予定の合計**（KPT なら 60 分）。区切りの長さで盤を割り、真鍮の目盛りと区切りの名前の頭文字（または番号）を置く
- **二重の環**【判断】: 外の環が**予定**（開始時点の区切り）、内の環が**実際**（終えた区切りの実績 ＋ いまの経過）。内の環の先端と外の環の目盛りのずれが、そのまま押し・巻きとして目に入る
- 針は壁の時計の経過を指す。一時停止中は止めず、針を鈍く（`--ivory-faint` 程度に）して止まっていることを示す（§4.3 と整合）
- **超過は赤銅色（`--rose` 系）だけで描く。** 金と翡翠は落ち着いた状態、赤銅色は時間切れ・超過のときだけ。色の意味を混ぜない
- 盤の中央: いまの区切りの名前（Zen Kaku Gothic New）と残り時間（Fraunces・大きく）。超過中は「+0:42」を赤銅色で
- 盤の下（控えめに）: 次の区切りの名前・終わる見込みの時刻と押し巻き（例: 「15:02 終了見込み ・ +3 分」）

### 7.2 映す表示

- 手元の画面: 盤 ＋ 進行表（区切りの一覧。いま・済み・飛ばした・まだ を描き分ける）＋ 操作
- **映す表示**: 盤と数字だけを画面いっぱいに出す切り替え。部屋の奥から読めることを優先する。ブラウザの全画面表示 API と Wake Lock は第 2 段（§2.2）だが、**第 1 段でも CSS の段組みとしての「映す表示」は持つ**【判断】
- 320px〜1920px の段組みは `docs/adr/0025` に従う

### 7.3 色・字・動き

- 新しい生の色を足さない（デザインシステムの検査が止める）。足りない色は `packages/ui` のトークンとして足し、コントラストを測る
- 動きを減らす設定（`prefers-reduced-motion`）では、針と弧の連続した動きを止め、1 秒ごとの描き替えにする
- 区切りが変わったことは `aria-live` で読み上げる。残り時間の毎秒の更新は読み上げない
- **UI の固定文言は書体の base 層に入る字だけで作る（利用者の決定 U9）。** base 層は広げない。2026-10-19 に `packages/ui/src/tokens/fonts.css` の Zen Kaku Gothic New 400 base の unicode-range で実測した結果:
  - 入らない字: 区切り（区）・延長・超過（超）・巻き（巻）・飛ばす（飛）・実績（績）・足す（足）・早め（早）・遅れ（遅）・前倒し（倒）
  - 入る語: 押し・予定・次へ・一時停止・再開・終了見込み・最初から・保存・開始・残り・予備・投票・進行タイマー・スキップ・オーバー・ステップ
  - 言い換えの方針: 延長 →「+1 分」「+3 分」「+5 分」のボタンそのもの／飛ばす →「スキップ」／超過 →「オーバー」または「+0:42」の数字だけ／押し・巻き →「予定より +3 分」「予定より −2 分」／区切り →「ステップ」。最終の文言は実装者が決め、各アプリの `copy-fits-font-base` の検査（例: `apps/roulette-web/tests/copy-fits-font-base.test.ts`）と同じ検査を agenda-web にも置いて機械で守る
  - この設計書の本文の「区切り」「延長」「飛ばす」「超過」は設計上の語であり、画面の文言ではない
  - 利用者が入力する名前（区切りの名前・会の名前）と、同梱する見本の区切りの名前（「Try の議論」など）はこの制約の外（利用者由来のテキストと同じく ext 層で描く）

## 8. 検証

### 8.1 振る舞い（EARS の材料。計画で番号を振り、検査との対応表を作る）

- シナリオの区切りが 1 つ以上あり上限内のとき、システムは開始を受け付ける
- 「押すまで待つ」の区切りの経過が長さ＋延長に達したとき、システムは合図を出し、超過を数え続け、次へ移らない
- 「自動で次へ」の区切りの経過が長さ＋延長に達したとき、システムはサーバーの判断で次の飛ばしていない区切りへ移る（最後なら終了）
- 延長されたとき、システムは区切りの延長の合計を増やし、終わる見込みと押し巻きを更新する。自動で次へ移る期限を張り直す
- まだ始まっていない区切りを飛ばしたとき、システムはその長さを終わる見込みから外す
- 一時停止中、システムは区切りの経過を止め、押し巻きは壁の時計で増やし続ける
- 途中で入った・再接続した端末は、次のフレームを待たずに同じ進行を描く
- agenda 以外の接続から agenda のコマンドが来たとき、システムは拒む
- 保存の中身が古い版のとき、画面は新しい形へ移して読む。どの版にも合わない（壊れている）項目は、落ちずに読み飛ばす

### 8.2 実画面（原則 V）

- 2 つのブラウザで同じルームを開き、KPT の見本を走らせて、残り時間・超過・押し巻きが揃うこと
- 「自動で次へ」の区切りで、操作していない画面も同時に移ること
- 映す表示を 1920px で、手元を 375px で見ること
- 変異検査（原則 VII）の ID の帯は計画で台帳から予約する

### 8.3 検証の時間

計画（`superpowers:writing-plans`）で、各段の検証の実行時間の見積もりと Constitution Check の節を書く（利用者の方針）。
