# 検査の CI 組み込みとジョブ絞り込みの設計（#70）

> 親エピック: [#67](https://github.com/tomohiroJin/tasuki-tools/issues/67) ・ 段階: **C**
> 対象 Issue: [#70](https://github.com/tomohiroJin/tasuki-tools/issues/70)

## 背景と目的

リポジトリが持つ検査のうち、**構造監査・その自己テスト・変異検査の 3 種は手動でしか走りません**。
このリポジトリは「検査が静かに効かなくなる」失敗を繰り返し踏んでおり（#50 の CI 未実行、eslint
の対象がアプリ名固定で移設のたびに死んだ 2 回、構造監査が存在しないパスを走査して全指標 0 で
PASS 表示）、**手動でしか走らない検査はいずれ効かなくなる**という前提に立ちます。

同時に、#68 から「リンク検査を CI へ組み込むこと。ただしアンカーとバッククォート内のコードパスの
両方を対象に含めた実装へ書き直すこと」という申し送りを受けています。リンク検査はリポジトリに
存在せず、これまで作業のたびに使い捨てのスクリプトを scratchpad へ書いていました。

**目的は 2 つです。**

1. リポジトリが持つ検査を CI へ寄せ、手動専用の検査を無くす
2. 変更内容に対して走らせる検査を絞り、PR あたりの待ち時間を減らす

## 実測で確認した前提（2026-08-12・`34db348`）

**#70 本文の現状記述は 2026-08-05 時点のもので、9 項目のうち 7 項目が既に成立しません。**

| 5 | timer-core に coverage gate は無い | `lines: 90` / `branches: 90` が実在し CI で効いている | 訂正する |
| 6 | SC029=6 / SC030=3 / SC039=34 | **SC029=7** / SC030=3 / SC039=34 | 訂正する |

**CI へ足す検査の実費**（overlay 実測）:

```
node scripts/audit-structure.mjs            1.3 秒   ← ただし常に exit=0
node --test scripts/audit-structure.test.mjs 0.08 秒（36 件）
node scripts/mutation-check.mjs             9.6 秒（9 件すべて検出）
```

**ランナー時間の前提が変わりました。** `tomohiroJin/tasuki-tools` は PUBLIC リポジトリであり、
GitHub Actions は標準ランナー（`ubuntu-latest`）では無料です。**このリポジトリの実データで
確認しました。**

```
$ gh api repos/tomohiroJin/tasuki-tools/actions/runs/31484518697/timing
{"billable":{"UBUNTU":{"total_ms":0,"jobs":3,...}},"run_duration_ms":102000}
```

実時間 102 秒に対し、**GitHub 自身が課金対象を 0 ミリ秒と報告しています**。#70 のコメントが
根拠にしていた「消費したランナー時間の 43%（52.4 分）が無駄」は、**金銭的にはゼロ円の無駄**
です。したがって絞り込みの目的は費用削減ではなく、**待ち時間の短縮**に置き換わります。
直近の実測では文書のみの PR が 128〜141 秒かかっています。

**shellcheck は抑制ディレクティブだけが存在し、検査が存在しません。** `deploy/deploy.sh:75` と
`deploy/lib/common.sh:58` に抑制コメントがある一方、shellcheck を走らせる仕組みはリポジトリの
どこにもありません（plan 文書に「あれば」と書かれているだけ）。#70 本文はこれを挙げていません
（D6 で対応）。

## 決定の一覧

新規 ADR `docs/adr/0009` に記録します。ADR は不変の記録であり、判断が覆ったら削除せず新しい ADR で
`Superseded` する（`docs/adr/README.md`）という規約に従い、既存 ADR への追記ではなく新規に立てます。

| ID | 決定 |
|---|---|
| **D1** | リポジトリが持つ検査はすべて CI で走らせる（手動専用の検査を残さない） |
| **D2** | 構造監査は値を出すだけとし、合否は自己テストと変異検査で取る |
| **D3** | カバレッジは `timer-core` の `lines` / `branches` 90 のみを gate とし、他パッケージでは測らない |
| **D4** | ジョブの絞り込みは (a) 形（常に起動し、中で判定して早期成功）。必須チェックにしても壊れない |
| **D5** | デプロイは自動化しない。ローカルからの手作業を正とする |
| **D6** | shellcheck を導入し、`deploy/**` と `scripts/**` の 6 本を対象に CI で走らせる。`.specify/scripts/**` は vendor のため対象外。info は合否の対象にしない |

### D2 の但し書き

**この形では指標の退行そのものは止まりません。** 自己テストが守るのは「計測器が壊れていないこと」
だけです。数値は CI のログに毎回残るので、退行は後から追えます。閾値を設けるかどうかは、
未達の指標（SC029=7 / SC030=3 / SC032 の未付与 28 件 / SC039 の公開記号 34 件）の解消と
セットで判断すべきであり、それは #72 の領分です。

### D4 が (b) ではない理由

`on.push.paths` / `paths-ignore` でジョブ自体を起動させない形にすると、そのチェックを必須
（required status check）に指定した瞬間、対象外のパスしか触らない PR が「チェック待ち」で
永久にマージできなくなります。GitHub がスキップされたワークフローを「成功」ではなく
「未報告」として扱うためです。`main` に現在ブランチ保護は設定されていない（2026-08-11 に
`gh api .../branches/main/protection` が `404 Branch not protected`）ため今すぐ壊れることは
ありませんが、**将来保護をかけた時点で踏みます**。

## ジョブ構成 — 3 ジョブから 5 ジョブへ

| ジョブ | 中身 | 走らせる条件 | 時間 |
|---|---|---|---|
| `ci` | typecheck / lint / test / build（40 タスク） | `code` | 2 分 12 秒（実測） |
| **`quality`**（新設） | 構造監査・自己テスト 36 件・変異検査 9 件・**shellcheck**・新規スクリプトの自己テスト | `code` | 32〜34 秒（実測、2026-08-12） |
| **`docs`**（新設） | リンク検査 | **常時（判定しない）** | 7〜9 秒（実測、2026-08-12） |
| `audit` | `pnpm audit` | `deps` | 16 秒（実測） |
| `e2e` | E2E 25 シナリオ | `code` | 1 分 4 秒（実測） |

`quality` の中身は次のとおりです。**`setup-bun` は不要です** — `mutation-check.mjs` は
`apps/timer-sync` の変異も含めて `npx vitest run` で実行しており（`scripts/mutation-check.mjs:283`）、
パッケージの `test` スクリプト（`bun test`）を経由しないためです。

```
node scripts/audit-structure.mjs                 1.3 秒 ・値を出すだけ（落とさない）
node --test scripts/audit-structure.test.mjs     0.08 秒・36 件・落とす
node --test scripts/ci-scope.test.mjs            新規・落とす
node --test scripts/check-links.test.mjs         新規・落とす
node scripts/mutation-check.mjs                  9.6 秒 ・9 件・落とす
shellcheck -x --source-path=deploy --severity=warning deploy/*.sh deploy/lib/*.sh scripts/*.sh
                                                 0.19 秒・落とす
```

**`quality` の所要時間は `pnpm install` が支配します。** 検査そのものの合計は約 11 秒で、
ジョブ全体は 32〜34 秒（実測、2026-08-12・PR #132）。`checkout` / `setup-node` / `corepack enable` /
`pnpm install --frozen-lockfile` の合計が残り約 21〜23 秒を占める計算になります。

### shellcheck を新たに入れる

**リポジトリには shellcheck の抑制ディレクティブだけが存在し、検査は存在しません。**

```
deploy/deploy.sh:75      # shellcheck disable=SC2029
deploy/lib/common.sh:58  # shellcheck source=/dev/null
```

これは #70 が問題にしている「検査が静かに効かなくなる」の最終形（抑制だけが残り、検査が無い）
であり、D1 の対象です。追跡下の `.sh` は 11 本、うち `.specify/scripts/**` の 5 本は vendor
なので対象外とし、`deploy/**` と `scripts/**` の 6 本を対象にします。

**実測で現状は緑です**（`-x --source-path=deploy --severity=warning` で findings 0 件・0.19 秒）。
オプションの意味は次のとおりです。

| オプション | 理由 |
|---|---|
| `-x --source-path=deploy` | `source "$(dirname …)/lib/common.sh"` が動的パスのため、これが無いと SC1091 で落ちる |
| `--severity=warning` | `deploy/setup.sh:40` の SC2153（`ENV_FILE` の綴り誤り疑い）は、`app.env` から読む変数に対する偽陽性。info を合否の対象にしない |

`ubuntu-latest` に shellcheck がプリインストールされていることは**初回 PR で確認します**
（無ければ `apt-get install` の 1 ステップを足す）。

### `quality` を `ci` に混ぜない理由

変異検査は `node_modules` を要求するため `pnpm install` が要ります。`ci` に足すと臨界経路が
2 分 12 秒から 2 分 42 秒へ伸びます。別ジョブなら並列に隠れて 2 分 12 秒のままです。
落ちたときに「テストが赤いのか、変異が検出されないのか」が区別できる利点もあります。

### `docs` を絞らない理由

**リンク検査はコードを変えたときにこそ壊れます。** ファイルを移動・削除すると、文書の
バッククォート内パスが宙に浮くからです。「文書が変わったときだけ走らせる」と、
**この経路を取り逃がします**。`pnpm install` 不要の素の node なので、絞る利得がありません。

**効き目の範囲は正確に書きます。** コードパス検査の対象は現役の規範文書のみなので、
常時実行が捕まえるのは「**現役の規範文書が指すコードパスが、コード側の移動・削除で壊れる**」
場合です。#71 が `docs/timer/**` や `docs/poker/**` を整理しても、そこは対象外のままです。

### 同時実行の打ち切り

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

`main` への push は打ち切りません。マージ後の実行は「`main` が緑である」という記録そのもの
だからです。打ち切られるのは既に古いコミットに対する PR の実行だけなので、検査が静かに死ぬ
余地がありません。

### 見込みの効果

| | 現状（実測） | 変更後（実測・2026-08-12） |
|---|---|---|
| 文書のみの PR | 128〜141 秒 | **20 秒** |
| コードの PR | 128〜142 秒 | 2 分 11 秒 |

**文書のみの PR は実測できませんでした。** PR #132 は積み上げ PR の末端（base は
`chore/70-checks-to-ci`）で、`ci-scope.mjs` は base との三点差分（`origin/<base>...HEAD`）を見ます。
PR #132 自身の既存コミット（`scripts/ci-scope.mjs` と `.github/workflows/ci.yml` の追加）がすでに

**この行は PR-5（#133）で実測しました。** PR-5 は `docs/adr/0009`・`docs/adr/README.md`・
`docs/guides/development.md`・`deploy/README.md` の 4 ファイルだけで構成され、base は

**128〜141 秒が 20 秒になりました。** 見積りの 25 秒より速く、ジョブが 3 つから 5 つへ増えた

**コードの PR は遅くなります。** 検査が 4 種増えるので当然ですが、隠しません。

## `scripts/ci-scope.mjs` — 走らせる範囲の判定

判定を純関数に閉じ込め、自己テストで守ります。

```js
export function decideScope(changedFiles) // → { code: boolean, deps: boolean }
```

| フラグ | true になる条件 |
|---|---|
| `code` | 変更ファイルに **`.md` 以外が 1 つでもある** |
| `deps` | `pnpm-lock.yaml` / `pnpm-workspace.yaml` / `**/package.json` が含まれる |

**規則の向きが設計の要です。**「走らせる条件」を列挙するのではなく、**「走らせなくてよい条件」を
許可リストで書き、それ以外はすべて走らせます**。未知のパスは必ず「走らせる」側に倒れます。

### `deps` は待ち時間短縮のためではない

**`deps` フラグは待ち時間を 1 秒も減らしません。** `audit` は 16 秒で `ci` の 2 分 12 秒と
並列に走るため臨界経路に乗っておらず、文書のみの PR では `code=false` で全ジョブが早期成功
するため `deps` の出番がありません。

`deps` を残す理由は別にあります。**依存を変えていない PR が、新しく公開された脆弱性勧告で
赤くなるのを防ぐ**ためです。`pnpm audit` はレジストリの勧告を都度参照するので、依存が
同一でも結果が変わりえます。無関係な変更の PR がそれで止まると、赤の意味が薄れます。

継続的な勧告の検知は Renovate の担当です（#69・ADR 0008）。**この分担を明示しておかないと、
`deps` で絞ったことが「脆弱性を見逃す設計」に読めます。**

### `e2e` に独立したフラグを持たせない

#70 本文は「`e2e` は利用者の通る経路に関わる変更（`apps/**`・`packages/**`・`e2e/**`・Caddy 断片）
のときだけ走らせる」としていますが、**本設計は意図的にこれを採らず、`e2e` の条件を `code` と
同一にします。**

理由は、`turbo.json`・ルートの設定ファイル・`.github/workflows/**` はいずれも E2E の挙動を
変えうるためです。「利用者の通る経路」を狭く列挙すると、列挙から漏れた設定変更で E2E が
走らなくなります。狭める利得は、実行数の 45%（40 実行中 18 件）を占める文書のみの PR では
既にゼロです（`code=false` で全ジョブが早期成功するため）。

### 差分の取り方と fail-open

```
pull_request : git diff --name-only origin/<base_ref>...HEAD
               三点＝マージベース。積み上げ PR でも base が親ブランチになるので正しい
push         : git diff --name-only <before> <sha>
               before が全 0（新規ブランチ）なら fail-open
それ以外・例外・空 : すべて「全部 true」に倒す
```

`actions/checkout` は `fetch-depth: 0` にします（`.git` は 17MB / 713 コミットで数秒）。

#### fail-open が拾う範囲と、拾わない範囲

**fail-open は「判定の失敗」だけを拾います。判定スクリプト自体が異常終了したときは、
ジョブを赤くします。** この二段構えは意図したものです。

| 失敗の種類 | 挙動 |
|---|---|
| 未知のイベント・`base_ref` が空・`git diff` の失敗・イベント JSON の不正・`before` が全 0・差分が空 | **fail-open**（`code=true` / `deps=true` を書き出して全ジョブを走らせる） |
| 判定スクリプト自体の異常終了（構文エラー・想定外の実行時例外） | **`scope` ステップが落ち、そのジョブが赤くなる** |

**なぜ後者を fail-open にしないか。** `main()` 全体を `try` で囲むと、判定スクリプトが壊れても
全ジョブが走って CI は緑になります。**絞り込みが死んでいることに誰も気づけません。**
これはこのリポジトリが繰り返し踏んでいる「検査が静かに効かなくなる」そのものです。
赤くなるのはうるさいですが、**何も黙って飛ばされない**方を選びます。

前者（判定の失敗）は、`main()` の中で `changedFiles()` と `decideScope()` を囲む `try` が
捕まえます。この経路は 10 通りの入力で fail-open することを実測で確認しています。

### 早期成功の表現

ジョブ単位の `if:` ではなく、**ステップ単位の `if:`** を使います。ジョブは常に起動して常に
`success` を報告するため、必須チェックに指定しても「未報告」になりません。ジョブ単位の
`if:` でスキップした場合の必須チェックの扱いに依存しない形を選びます。

## `scripts/check-links.mjs` — リンク検査

### Markdown のコード領域を読まないことが土台

フェンス（<code>```</code> / `~~~`）内の行と、本文中のインラインコードは検査対象から外します。
これは正しさの問題であり、検出精度の問題ではありません。**この処理を入れるだけで検出が
12 件から 4 件へ減り、残った 4 件はすべて実害でした。** 落ちた 8 件は
`[x](no-such-file.md)` のような**検査手順の説明文**で、直したら記録が壊れるものです。

### 3 種の検査と対象範囲

| 検査 | 対象範囲 |
|---|---|
| 相対リンク | 全 `*.md` |
| アンカー（`#見出し`） | 全 `*.md`。GitHub 風 slug・日本語見出し対応 |
| バッククォート内のコードパス | **現役の規範文書のみ** |

現役の規範文書は次のとおりです。

```
README.md  AGENTS.md  CLAUDE.md  docs/README.md
docs/adr/**  docs/guides/**  deploy/**  .github/**  e2e/**  .specify/memory/**
```

コードパスの検査は、拡張子つきかつグロブや変数展開を含まないものに限り、`file.ts:12` /
`file.ts:5-6` の行番号は落として突き合わせます。

### 対象範囲を種類ごとに変える理由

全 `*.md` を全種類で検査すると、**バッククォート内のコードパスだけで 1301 件**が検出されます。
その大半は履歴文書です。`docs/poker/specs/…/tasks.md`（55 件）や `docs/timer/**`（18 件）は
**monorepo 統合前の `packages/core` / `apps/sync` 表記**で書かれた当時の記録であり、直すべき
ものではありません。`.claude/skills/speckit-*`（36 件）は spec-kit の vendor ファイルで、
`.specify/extensions.yml` という存在しないファイルを指しています（#71 が抱える
`.specify/feature.json` の件と同根）。

これらを例外表で凍結する形にすると、**例外表が 1200 行を超え、履歴文書を 1 行直すたびに
例外表の保守が発生します**。検査そのものが形骸化するため、範囲を種類ごとに分けます。

### 空振り防止

**ここが本スクリプトで最も重要な部分です。** 対象範囲はスクリプト内の定数として持ちます
（設定ファイルにすると「対象から外した」変更が差分で目立たなくなるため）。その上で 2 つの
自己防衛を組み込みます。

1. **定数に実在しないパスが混ざっていたら落とす。** #71 が抱える `.specify/feature.json` が
   実在しないディレクトリを指してスクリプトを全滅させた事故、および構造監査が存在しない
   パスを走査して全指標 0 で PASS した過去と、まったく同型です。**新しく作る検査に、同じ穴を
   最初から塞いだ形で入れます**
2. **走査対象が 0 件なら落とす。** 対象が消えたのに緑になる経路を断ちます
3. **使われなくなった例外は落とす。** 例外表の各エントリは、それが実際に検出を抑えている
   ことを検査します。抑える対象が消えたエントリは、次の作業者にとって嘘になるので落とします

### 意図的な不在 — 例外表を 1 エントリだけ持つ

**削除されたファイルへの言及は、記録として正しい場合があります。** `docs/adr/0003` は

```
3. バックログは GitHub Issues に一本化する（MUST）。
   `docs/BACKLOG.md` は廃止する。
```

と決定しており、**`docs/BACKLOG.md` が実在しないのはこの決定が実行された結果**です。
ADR は不変の記録なので、この言及を直すと決定の記録が壊れます。ADR 0008 の 1 件も同じです。

`no-such-file.md`（検査手順の説明文）と同型の「意図的な不在」ですが、そちらはコード領域の
除外で自動的に解決するのに対し、こちらは**記法で区別できません**。したがって例外表を持ちます。

```
例外: docs/BACKLOG.md   理由: ADR 0003 の決定により廃止済み。言及は記録として正しい
```

**エントリは 1 件です。**「例外表は形骸化の入口」という本設計自身の主張と両立させるため、
上記の空振り防止 3（使われなくなった例外は落とす）を必ず併設します。

## 検証方法 — 破壊検証 10 件

憲法 原則 VII（新しい検査はわざと壊して赤を見る）に従い、**10 個とも実際の PR で確かめます**。

|---|---|---|

## リスクと手当て

| リスク | 手当て |
|---|---|
| 判定が誤って「走らせない」に倒れる | 許可リストの向きを反転し、未知は必ず走らせる。fail-open を不変条件とし、破壊検証 #1 / #3 で確かめる |
| 将来ブランチ保護をかけたとき必須チェックが永久待ちになる | ステップ単位の `if:` を使い、ジョブは常に `success` を報告する（D4） |
| リンク検査の対象範囲が実在しないパスを指し、静かに空振りする | 定数の実在検査と、走査対象 0 件で落とす検査を組み込む |
| 変異検査が CI で実行できない（作業ツリーが汚れている前提） | `actions/checkout` 直後の作業ツリーは clean。`pnpm install --frozen-lockfile` は追跡ファイルを変更しない |
| コードの PR の待ち時間が伸びる | 隠さず記録する。`quality` を独立ジョブにして臨界経路への影響を約 10 秒に抑える |
| 「意図的な不在」を壊れと誤認して、正しい記録を書き換えてしまう | 例外表に理由を併記し、使われなくなった例外は落とす（破壊検証 #6）。本設計自身が ADR 0003 の `docs/BACKLOG.md` でこの誤りを一度犯している |
| shellcheck の導入で既存スクリプトが赤くなり作業が膨らむ | **実測済み**。`-x --source-path=deploy --severity=warning` で findings 0 件・0.19 秒 |
| `ubuntu-latest` に shellcheck が無い | 初回 PR で確認し、無ければ `apt-get install` の 1 ステップを足す |
