## 1. 目的と方針

### 1.1 利用者の言葉

> レスポンシブに考えたときに横が狭すぎる。（タブレットの縦とスマホ縦に対応しているが普通の PC 利用では小さく狭く使いにく）
>
> 全画面そうなのだが、ボタンなどのおさまりが悪く崩れて見えるのでデザインを何とかしたい
>
> （2026-09-26・Issue 本文）

> 見せ方は改めて考慮していただいてよいのでデザインシステムになるようにしてほしいのと、レスポンシブな対応をお願いします。
> PC の大きな画面で見る人やスマホで見る人等を考慮してください。
>
> （2026-10-08・設計の対話）

### 1.2 方針

- **見せ方は変えてよい。** #321 の「見た目を変えない」はこの Issue には掛からない。timer のボタンの形も変わる
- **幅・段組み・ボタンの語彙は部品層（`@tasuki/ui` の `components/`）が持つ。** 区画に何を置くかは各アプリが決める（#320 D4 の「配置は画面が持つ」を保つ）
- **大画面とスマホの両方を一級に扱う。** 大画面では横に並べて一度に見える量を増やし、スマホでは縦に積んで主の操作を親指の届く位置に置く
- 部品層の既存の規則（命名 `.ui-*`・`ui-exempt:`・2 アプリ以上が使う・`@layer` を使わない）にそのまま従う

## 2. 洗い出し（実測・main `f6ce549`）

各画面の主な状態を 320・768・1024・1280・1920px で撮り、操作要素の大きさ・行数・はみ出しを測った（使い捨ての Playwright の spec。E2E の起動の仕組みに相乗りした。成果物は残さない）。

### 2.1 器の幅（1920px の画面で、中身が使う幅）

| 画面 | 器の幅 | 1920px での使用率 |
|---|---|---|
| poker のルーム | 680px | 35% |
| 玄関の作成・参加 | 680px | 35% |
| 玄関の道具選び・お題ツールの部屋 | 1120px | 58% |
| timer のロビー・セッション | 1152px | 60% |
| timer のまとめ | 448px（中央の 1 列） | 23% |

**poker は 768px 以上のどの幅でも 680px のまま**で、1280px の画面でも両脇に 300px ずつ空く。Issue の「狭い」はここが最も強い。

### 2.2 幅の境目（メディアクエリ）

画面の CSS が使う幅の境目は **`40rem`・`48rem`・`64rem`・`420px`・`720px` の 5 種類**（コンテナクエリの `48rem` を除く）。単位も rem と px が混ざる。timer の JS は `innerWidth >= 1024`（px）で、CSS の `64rem` と既定の文字の大きさを変えた利用者で食い違う（#321 の申し送り）。

### 2.3 崩れ（画像で確かめたもの）

| # | 画面・幅 | 崩れ |
|---|---|---|
| B1 | timer のロビー・320px | **ページが横に約 70px 溢れる。** 1 人目の行の「前へ」「後へ」がカードの外へ押し出され、パスフレーズの「設定」ボタンがパネルからはみ出して「設／定」の 2 行に折れる |
| B2 | timer のセッション・1024px 以上 | 参加者のパネルが内側でスクロールし、3 人目の行の操作が途中で切れて見える。行の操作（改名・一時離脱・ドライバーにする・順番・外す）が 2 段に折れる |

### 2.4 ボタンの形の種類（1280px・計算後のスタイルで数えた）

| アプリ | 角丸 | 高さ・字の大きさの組み合わせ |
|---|---|---|

### 2.5 押せる大きさ（44px 未満・1280px）

- timer: **30 を超える操作が 44px 未満**。行の操作 32px・トグル 20px・通知の「閉じる」16px・ステータスの「通知」24px・「選択画面へ戻る」のリンク 16px。timer は 40rem 以上で `min-height: 44px` を外している（`.ghost-button`）
- poker: 招待リンクのコピー 34px・「選択画面へ戻る」26px・お題の「説明を見る」27px
- お題ツール: 「選択画面へ戻る」26px／玄関: 「記録を見る」43px

## 3. 決定

### D1. 幅の段を 4 つにし、境目を 3 つの rem に絞る

| 段 | 幅 | 想定する端末 |
|---|---|---|
| compact | `< 40rem` | スマホの縦持ち |
| medium | `40rem ≤ w < 64rem` | タブレットの縦持ち・小さい窓 |
| wide | `64rem ≤ w < 90rem` | ノート PC |
| ultra | `≥ 90rem` | 大きなモニター |

- 画面の CSS の `@media` の幅の条件は **`40rem`・`64rem`・`90rem` の 3 つだけ**を書ける。`48rem`・`420px`・`720px` は近い段へ寄せる（寄せた結果は §6 の実画面比較で確かめる）
- CSS のカスタムプロパティはメディアクエリに使えないので、値は直書きし、検査で守る（D9）
- **コンテナクエリは対象外。** 部品の内側の並び替え（お題ツールの `make` / `compose`）は器の幅で決まるべきで、画面の幅の段とは別物
- timer の `useIsWide` は `matchMedia('(width >= 64rem)')` に替え、CSS と同じ条件で判定する

### D2. 器の幅 `.ui-page` を 3 段にする

| 部品 | 最大幅 | 使う画面 |
|---|---|---|
| `.ui-page--prose` | `40rem` | 読む・入力する: 玄関の作成と参加・読み込み中・ルームが見つからない・timer のまとめ |
| `.ui-page` | `72rem` | 選ぶ・一覧する: 玄関の道具選び・timer の履歴 |
| `.ui-page--wide` | `96rem` | 道具の部屋: poker のルーム・timer のロビーとセッション・お題ツールの部屋 |

- 外の余白は `clamp(1rem, 4vw, 3rem)`。最大幅を超える画面では中央に寄せ、両脇は卓の地を見せる
- **要素層の `.page`（680px）は消す。** 同じ知識（器の幅）を 2 か所に置かない。`.page` を使う画面はすべて `.ui-page*` へ置き換える
- timer の `Stage` の `.stage-inner`（72rem）も `.ui-page*` へ置き換える

### D3. 段組み `.ui-workspace` は 3 つの区画を持つ

- 区画は **主（`.ui-workspace-main`）・右脇（`-aside`）・左脇（`-rail`）**
- compact・medium: 縦に積む（左脇 → 主 → 右脇）。medium で右脇が 2 つ以上の箱を持つときは 2 列にしてよい（画面が決める）
- wide: 主＋右脇（`22rem`）。左脇の中身は右脇の先頭へ回る
- ultra: 左脇（`18rem`）＋主＋右脇（`22rem`）
- **主の幅は `minmax(0, 1fr)` で取り、32rem 以上は `--wide` の器と段の境目の計算で保証する。** grid の `minmax(32rem, 1fr)` は、72rem の器の中で使われると横に溢れる。64rem の画面は器の内側が約 58.9rem で、主 32 + 右脇 22 + 間 2 に入る。90rem の画面は 84rem で、18 + 32 + 22 + 間 4 に入る。E2E が 1280px と 1920px で主の幅が 32rem 以上であることを測る
- **DOM は 左脇 → 主 → 右脇 の順に書く。** 狭い幅の見た目の順と読み上げの順を揃えるため（PR 1 で『主 → 脇』から改めた）
- 左脇へ回す中身を「右脇の先頭へ回す」動きは、wide では右の列に 左脇（上）・右脇（下）を積み、主が 2 行をまたぐ形で実現する（CSS だけで済み、DOM を 2 回描かない）。**左脇が無い画面では行を 1 本にし、主と右脇を 1 行目に置く**（下に gap だけの空きを残さない）。左脇も右脇も無ければ、主だけの 1 列になる
- **お題ツールの「作る」「書く」の並び替え（コンテナクエリ）は段の約束の外**で、境目を 48rem から **44rem** に下げた。道具の部屋の器を広げると、1280px の画面で右の列（22rem）の横の箱の内側が約 750px になる。常時表示のスクロールバー（約 17px）があっても並ぶ余裕を取るため。768px の画面では引き続き切り替わる（#313 D7 を保つ）
- **玄関の道具の札は 64rem 未満で縦に積む**（元は 720px）。640px で 3 枚を横に並べると名前が 2 行になったため。札の寸法も同じ境目で揃える
- **timer は PR 1 では `.ui-page`（72rem）の器で、左脇を置かないので段組みを使ってよい。** `--wide` へ広げるのは PR 3（E3 の timer の部分は PR 3 で満たす）

### D4. ボタン `.ui-button` は形 1 つ・役割 4 種・大きさ 3 段

- **形は真鍮のチップ（丸・999px）1 つ。** 要素層の `button` の見た目（金のグラデーション・押し込みの影）を部品へ移す
- 役割: `--primary`（既定。画面に 1 つ）／`--secondary`（枠のみ）／`--quiet`（下線の文字。戻る・閉じる・設定）／`--danger`（朱の枠。取り消せない操作）
- 大きさ: `--sm`（見た目 36px・字 xs）／既定（44px・字 sm）／`--lg`（52px・字 base）。字は 5 段のスケールから取り、直値を書かない
- **押せる高さは常に 44px 以上。** `--sm` は見た目だけ 36px で、当たりは擬似要素で 44px に広げる（`pointer: coarse` に限らず常に。マウスでも当てやすさは損をしない）
- 最小幅 `6rem`。アイコンだけのボタンは `.ui-button--icon`（正方形・44px）で、`aria-label` を必須にする（検査は既存の a11y の走査が担う）
- フォーカスのリングは部品が持たない（#320 D4）。要素層の `:focus-visible` と timer の自前のものがそのまま効く
- **ボタンの形をしない操作は部品にしない。** poker の札（手札）・timer のタブ・トグル・行の中の「前へ」「後へ」は各アプリの部品のまま（44px の当たりだけは揃える。D7）

### D5. 要素層の `button` は見た目を持たない

- 要素層の `button` の規則は `font: inherit` と `cursor` 程度の初期化だけに減らす。**見た目は `.ui-button` だけが持つ**（同じ知識を 2 か所に置かない・#320 D1）
- poker・お題ツール・玄関の素の `<button>` にはすべてクラスを付ける。付け忘れると素の灰色のボタンが出るので、E2E の走査で「`.ui-button` も画面固有のクラスも持たない `<button>`」を落とす（D9）
- **timer に要素層を読ませるかの判断（#321 の申し送り 2）は「読ませない」を維持する。** ボタンの見た目は部品層から来るので、要素層を読ませる理由が消える。要素層が持つ見出し・リンク・ラベルの見た目は timer の計器の意匠と別物で、読ませると打ち消しの規則が要る（ADR 0023 決定 4 の理由がそのまま残る）

### D6. 操作の並び `.ui-actions` は「主は常に最後」

- medium 以上: 横に並べて右寄せ。折り返すときも右から詰める。控え（`--quiet`）は左端に離す（`.ui-actions-start` に入れる）
- compact: 幅いっぱいに縦へ積む。**主が最後＝最下段で、親指に最も近い**
- `.ui-actions--dock`: compact でだけ、画面の下端に固定する帯になる。主の操作が画面の外へ流れる画面（poker の投票・timer のセッション）だけが使う。帯の高さぶん、器の下に余白を足す（帯が中身を隠さない）
  - iOS の画面下のバーに重ならないよう、`padding-bottom` に `env(safe-area-inset-bottom)` を足す（`index.html` の viewport に `viewport-fit=cover` が要るかを計画で確かめる）

### D7. 画面ごとの当て方

| 画面 | 器 | 段組み | 主な変化 |
|---|---|---|---|
| poker のルーム | `--wide` | 左脇=参加者・主=手札と操作と結果・右脇=お題 | 680px → 最大 1536px。「票を公開する」「再投票」を主に、招待リンクのコピーを副に（B5）。compact では主の操作を下端の帯へ |
| お題ツールの部屋 | `--wide` | 左脇=いまのお題・主=作る・書く（右脇なし） | 招待の行の余白（B3）・パネルの見出しの空き（B4） |
| 玄関の作成・参加 | `--prose` | なし | 680px → 640px（わずかに狭まる） |
| 玄関の道具選び | 既定（72rem） | 道具の札＋下に参加者・招待 | 1120px → 1152px（ほぼ同じ） |
| timer のロビー | `--wide` | 主=開始・設定・右脇=参加者と順番・招待 | 320px の横溢れ（B1）を直す |
| timer のセッション | `--wide` | 左脇=お題・主=計器と操作・右脇=順番・参加者・メモ・終える | 参加者の内側スクロールをやめて行の操作を 1 段に（B2）。「完成!」だけを主に、「途中で終える」「最初から」は危険の枠へ（B6）。compact は「セッション」「ルーム」のタブを保ち、主の操作を下端の帯へ |
| timer のまとめ | `--prose` | なし | 448px の 1 列 → 640px |

- **timer のボタンは丸くなり、大きさで付けたクラス（`session-button-sm` など）は消える**（#321 の申し送り）
- 44px 未満の操作（§2.5）は、ボタンは `.ui-button`、ボタンでない操作は各アプリで当たりを 44px に広げる。**行の中の小さな操作は見た目を保ち、当たりだけを広げる**（行が太るのを避ける）

### D9. 検査

- **幅の境目**: 画面の CSS と部品の CSS の `@media` の幅の条件が `40rem`・`64rem`・`90rem` 以外なら落とす（`scripts/audit-ui-components.mjs` に足す。`ui-exempt:` で外せる）。`max-width` / `min-width` の旧構文・px・`em` も同じ扱い
- **要素層の `.page` の消滅**: 画面の `.tsx` に `className="page"`（`.ui-page` 以外の `page`）が残れば落とす
- **素のボタン**: E2E で各画面を開き、`.ui-button` も画面固有のクラスも持たない `<button>` が 1 つでもあれば落とす（`landing-design.spec.ts` の幅ごとの測り方を広げる）
- **はみ出しと当たり**: E2E で各画面を 320・768・1280・1920px で開き、(1) ページが横に溢れない (2) 表示中の `button`・`a[href]`・`summary`・`[role=tab]` の当たりがすべて 44×44px 以上（行内のリンクは除く・除き方は計画で決める）を確かめる。**この E2E は最初は合否にしない**（網羅系の検査は、最初に件数を出してから合否にする）。PR ごとに直した画面を合否に入れていく
- 既存の検査（コントラストの走査・書体の base 層・文字の大きさ 5 段・部品層の D10 / D11・変異検査）はそのまま通す。**`.ui-*` が 2 つ以上のアプリで使われる（D11 の 6）**ので、`.ui-workspace` などは最初の PR で 2 アプリ以上に当てる

## 4. PR の刻み方

ADR 0013 の既定から分割する理由は、`docs/guides/pr-granularity.md` の理由 1（独立して revert したい単位が複数ある）と理由 3（危険度の異なる変更が混ざっている）。timer は見た目の変化が最も大きく、独立して戻せるようにする。

| PR | 中身 | 画面 |
|---|---|---|
| **1** | 幅の段（D1）・`.ui-page` の 3 段（D2）・`.ui-workspace`（D3）・幅の境目と `.page` の検査（D9）・はみ出しと当たりの E2E（合否にしない）。ADR 0025・README の「画面を組む」の節（幅・器・段組み）。timer の `Stage` と 2 列・`useIsWide`（死んだ部品の検査を満たすため）。timer の 48rem は PR 3 まで `ui-exempt:` | poker・お題ツール・玄関（timer は一部） |

### 7.1 方針をデザインシステムとして残す（利用者の依頼・2026-10-08）

> なお、ここで決めた方針は次回以降機能を追加されるときなどに利用できるようにデザインシステムとして残してください。

この設計正本は「なぜそう決めたか」の記録で、新しい画面を作る人が最初に読む場所ではない。次の 3 つに分けて残す。

| 置き場 | 残すもの | 書く PR |
|---|---|---|
| **`packages/ui/README.md`**（新しい画面を作る人が最初に読む場所・#320 で決めた） | 「画面を組む」の節: 幅の段と境目（D1）・器の選び方（D2 の表）・段組みの区画と並び替え（D3）・ボタンの役割と大きさの選び方（D4）・操作の並び（D6）・押せる大きさ・**新しい画面や機能を足すときの手順**（器を選ぶ → 区画に置く → ボタンの役割を決める → 主は 1 つ → compact で確かめる → 検査を流す） | 部品を足す PR が、その部品の分だけ書く（PR 1: 幅・器・段組み／PR 2: ボタン・操作の並び）。手順の節は PR 4 で全部が揃ってから書く |
| **ADR 0025**（`docs/adr/`） | 決定（D1〜D9）とその理由・#320 の ADR 0022 と ADR 0023 決定 4 との関係・要素層の `button` と `.page` を消したこと | PR 1 で決定を書く。PR 2〜4 で実施する決定は「決定した。実施は PR n」と書き、完了形で書かない |
| **検査**（`scripts/audit-ui-components.mjs`・E2E） | 文書が守られなくなったときに落ちる仕組み（D9） | 各 PR |

- **見た目の見本は README の表と部品の CSS が正本。** 方向性を決めたキャンバス（Claude の Artifact）は利用者の非公開の場所にあり、リポジトリから辿れないので正本にしない
- **README に数と画面の列挙を書かない**（「poker・timer・お題ツールは `--wide`」のような列挙は画面が増えると古くなる）。書くのは「どんな画面ならどの段か」という選び方。どの画面がどれを使っているかは `git grep ui-page` で引ける
- 新しい部品の段（たとえば 4 つ目の器の幅）が要るときは、README の選び方に当てはめて足りない理由を書き、ADR 0025 に追記する
