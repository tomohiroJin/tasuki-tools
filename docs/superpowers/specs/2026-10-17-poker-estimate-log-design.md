## 1. 何のために作るか

利用者のチームは PBR（プロダクトバックログリファインメント）で、Jira のバックログアイテムのうち見積もれる段まで精査したものを poker で見積もる。1 回の PBR で見積もるのは 3〜4 件、多いと 10 件ほどである。

いまの poker は `next-round` を打つと票が消え、**履歴がどこにも残らない**。1 件ずつ Jira と行き来するなら困らないが、**数件を続けて見積もると、直前に何を何点としたかを忘れる**。基準を思い出すために Jira へ戻ると、頭の切り替えに負担がかかる。

**やりたいことは「見積もりの最中に、その日に見積もった他のアイテムが同じ画面に並んでいること」**（利用者の言葉では「一つの画面で考えられるようにしたい」）。その日に見積もったアイテムは、常に用意している基準アイテムと同じく、相対見積もりの基準になる。

## 2. 目標・目標にしないもの・失敗とみなすもの

**目標**
- 開票 1 回ごとに、**時刻・何回目か・実施内容（アイテム名とカードの分布）**をルームの中で後ろへ積み、見積もり中の画面の横に出す
- **再見積もりを勧める**作りにする（割れたら話して、投票し直すのが基本の流れ）
- アイテム名を入れなくても、今までどおり使える

**目標にしないもの**
- **点数をアプリが決めること。** 「5 と 8 が出たが 8 にした」という判断は人が覚えておけばよい（利用者）。アプリは出た結果を残す道具に徹する
- 基準アイテム（「これが 3 点」）を画面に出すこと（利用者: 今は不要）
- 書き出し（Markdown・CSV・クリップボード）。**今回は作らない**（設計者の判断。Jira への転記は今までどおり人が行う。要望が出たら足す）
- ルームが消えた後まで記録を残すこと（端末への保存・IndexedDB）
- 見学者（投票しない参加者）。**別の Issue にする**（§10）

**失敗とみなすもの（動いていても失敗）**
- **誰が何を出したかが記録に残る。** 「変な軋轢があると困る」（利用者）。記録はカードの分布だけを持ち、参加者 ID も表示名も持たない
- アイテム名や点数の入力を**求める**こと（空欄に注意を促す表示・必須の検証）
- 記録のために手札・「票を公開する」が押しのけられる、または開票の瞬間に操作の面が跳ぶ

## 3. 用語

| 画面の語（案） | 意味 |
|---|---|
| **お題** | 今までどおり、ルームの共有資産（topic・ADR-0021）。**今回は触らない** |
| **いま見積もっているもの** | ラウンドに付ける任意の名前（アイテム名）。Jira のキーや短い題を想定 |
| **見積もりの記録** | 当日の開票の積み重ね。アイテムごとのまとまり（以下「束」）に分かれる |

Issue 本文の「お題（見積り対象）」は、画面でも型でも**「お題」と呼ばない**（topic と取り違えるため）。型の名前は実装役に任せるが、`topic` の語は使わない。

**画面の文言はすべて書体の base 層に収まるかを実測してから確定する**（base 層に無い字が 1 字でもあると ext 層の約 210KB が読まれる。「記録」「回め」「割」などは未測）。上の語は案であり、base 層に無い字があれば言い換える。

## 4. 振る舞い

### 4.1 アイテム名（「いま見積もっているもの」）

- 操作の面の手札のすぐ上に 1 行で出す。**在室者なら誰でも書き換えられ**、全員に同じ値が配られる（ホストは #95 で廃止済み）
- **空でよい。** 空のときは控えめな置き文字だけを出し、入力を促す表示は出さない
- 見た目は「ラウンドの題」として読める形にし、押すと編集になる（投票中にうっかり触って書き換わるのを防ぐ。デザイン批評の指摘）
- 投票中でも開票後でも書き換えられる。開票の瞬間の値を写す。開票後に書き換えたら、いま見ている開票の行（束の最後の行）にも写る（束の見出しが追う）。閉じた束は変えない
- 保存は確定時（Enter・フォーカスが外れたとき）に 1 回送る。打鍵ごとには送らない
- 前後の空白を削る。上限の長さを持つ（値は実装役が決める。topic の題の上限 `MAX_TOPIC_TITLE = 200` を超えない）

### 4.2 開票と記録

- 開票（手動の「票を公開する」・全員の投票による自動公開のどちらでも）の瞬間に、**記録へ 1 行を足す**（票が 1 枚以上あるときだけ。票の無い開票は公開だけ行い、行にしない）
- 1 行が持つもの: **開票の時刻**（サーバーの壁時計）／**束の中での N 回めか**（1 から）／**その時点のアイテム名**（空可）／**カードの分布**（カードごとの枚数。数字以外の「?」「☕」も数える）
- 1 行が**持たないもの**: 参加者 ID・表示名・誰がどのカードを出したか。開票前の秘匿（SC-004）とは別に、**記録は永久に匿名**とする
- 平均・最頻値（`computeStats`）を行に持たせるかは実装役に任せる（分布から導ける）

### 4.3 開票後の 2 つの操作（`next-round` を分ける）

いまの「次のラウンドへ」と「再投票」は、ラベルが違うだけで同じ `next-round` である（`RoomPage.tsx` の `RevealedSection`・FR-011）。これを**意味の違う 2 操作に分ける**。

| 操作 | 位置づけ | アイテム名 | 記録 |
|---|---|---|---|
| **再投票** | 主の操作（再見積もりを勧める） | そのまま残す | 同じ束が続き、次の開票は「2 回め」になる |
| **次のアイテムへ** | 副の操作 | **空に戻す** | 今の束を閉じる。横に**ポイントの欄（任意）**を出し、入れたらその束に添える |

- **ポイントの欄は入れても入れなくても進める。** 入れたポイントは束の見出しの右に出る。入れなければ「ポイントなし」とだけ出す
- ポイントの欄の形は**デッキの数字のカードから選ぶ（空を含む）**とする（設計者の判断。自由記述にすると検証と表示が増え、「5〜8」のような値は人が覚えておく領分とした §2）
- **ポイントは後から入れ直せる**（利用者・2026-10-17: 「誰でも入れなおせるので素敵」）。閉じた束のポイントは、記録の欄の束の見出しから**在室者なら誰でも**設定・変更・消去できる。入れ忘れ・入れ間違いの救済である
  - 束を指すために、束は**ルームの中で安定した ID** を持つ（行の上限で古い行が落ちても、残った束の ID は変わらない）
  - 同時に 2 人が入れたら**後に届いた方が勝つ**（サーバーが受けた順）。競合の通知はしない
  - 束がもう記録に無い（上限で落ちた）ときの設定は、画面の文言を伴うエラーで返す（コードの名前は実装役が決める）
  - まだ閉じていない束（「見積もり中」）には、見出しからポイントを入れられない（ポイントは「次のアイテムへ」の欄か、閉じた後に入れる）
- 束の区切りは「次のアイテムへ」だけが作る。**アイテム名が空でも束は分かれる**
- 再投票と次のアイテムへは、どちらも開票後にだけ押せる（今の `not-revealed` の事前条件を保つ）

### 4.4 束の表示

```
見積もりの記録
┌ PROJ-121 検索の絞り込み            見積もり中
│   1回め 14:20  5×2 8×2
├ PROJ-120 ログイン改修                     [5]
│   2回め 14:12  5×4
│   1回め 14:08  3×1 5×2 8×1
└ （名前なし）                         ポイントなし
    1回め 14:01  2×2 3×2
```

- **新しい束が上**、束の中も新しい回が上（直前の結果が目線に一番近い）
- 束の見出しは、その束の**最後の開票時点のアイテム名**。再投票の間に名前を変えたときの扱いはこれで決まる
  - **閉じた束の名前は後から直せる**（#427）。直すと束の中の全部の行の名前が書き換わり、見出しも新しい名前になる（見出しが最後の開票時点の名前から決まる規則と食い違わない）。操作は `set-group-item`（[`ws-protocol.md`](../../poker/specs/001-planning-poker-mvp/contracts/ws-protocol.md)）。経緯は [#427 の設計](./2026-10-18-release-check-and-feedback-design.md)（§4 E）
- まだ閉じていない束（今のアイテム）は「見積もり中」と出す
- 記録が 0 件のときは「開票すると、ここに残ります」程度の 1 行を出す（文言は base 層を実測して決める）
- 一番強く見せるのは添えたポイント、一番弱いのは時刻。分布の見せ方は `Results` のポイントの表し方と揃える

### 4.5 寿命と後から入った人

- 記録は**ルームの状態の一部としてサーバーのメモリに持つ**（揮発）。ルームが回収されれば消える（今の回収の仕組みのまま。`ROOM_IDLE_TTL_MS` 既定 30 分）。ADR-0007 の「サーバーは揮発」に沿うので ADR の補足は要らない
- 途中から入った人・再接続した人にも、**それまでの記録が全部見える**
- 記録の件数には上限を持つ（開票の行の数。値は実装役が決める。PBR の 10 件 × 数回の再投票が余裕で収まり、snapshot が膨れすぎない値）。上限を超えたら古い行から落とす
- 記録を消す操作は置かない（ルームを作り直せば空になる）

### 4.6 途中で抜けた人の票

今の振る舞い（退出した人の票は `discardVote` で捨てる・R8）を変えない。記録には**開票の瞬間に残っていた票**だけが入る。

## 5. 画面の配置（案 B・利用者が選んだ）

モックアップ: `.superpowers/brainstorm/65399-1792222574/content/layout-b-v2.html`（gitignore 対象。手元にだけある）。**配置の参考であり正本ではない**（ポイントの欄が自由入力で、手札の並びも実際のデッキ `0 1 2 3 5 8 13 21 ? ☕` と違う。食い違ったら本文に従う）

### 5.1 64rem 以上

- 左の脇（読む面）に、上から**お題の札**（あるときだけ）→**見積もりの記録**を縦に置く。右は今までどおりの操作の面（参加者 → いま見積もっているもの → 手札 → 下端の操作）
- **脇はルームに入った時点から出ている。** 記録が 0 件でも出しておく（1 件目の開票で脇が現れると、札がめくれる演出と重なって操作の面が滑るため）
  - **記録を切っている間は除く**（#427）。記録は既定で「しない」で、切っている間は記録の札を描かない。お題があれば、脇はお題の札だけで残る。お題が無い、またはお題を隠しているときは脇ごと描かず（または閉じた札だけ）、操作の面は中央に寄る（#348 D7〜D9 の規則）。経緯は [#427 の設計](./2026-10-18-release-check-and-feedback-design.md)（§4 D）
- **「お題を隠す」は、お題の札だけを畳む。** 記録は残り、上へ詰まる（利用者: 「お題があれば説明後に閉じて、記録は下にでいい」）
- これにより、**今の「脇を閉じる・お題が無い → 操作の面を 46rem で中央に寄せる」規則（`apps/poker-web/src/index.css` の `.room-main`・#348 D7〜D9）は、poker では成り立たなくなる。** 脇の列は常に開いたまま持つ。お題の札の開閉の移り変わり（#348 の不透明度・高さの段取り）は、札の単位へ移す
- 記録は脇の中でスクロールする（札が開いているときも記録の見出しが見える高さを残す）。脇の地はお題と同じ読む面の札（`.ui-reader` 系）に揃える

### 5.2 64rem 未満

- 縦に積む順は **お題 → 参加者 → いま見積もっているもの → 手札 → 結果 → 記録**（手札がカードの外へ押し出されないよう、記録は下へ）
- 記録は**直近の数束だけ**を出し、残りは既存の下からのシート（`.ui-drawer`・`useReaderDrawer`）で全文を出す（何束を出すかは実装役が決める）

## 6. 作りの制約（実装役が守ること）

- **記録・アイテム名・点数は poker の状態として持つ**（`RoundStore` の側か、それと対になる保管。`@tasuki/room-core` の名簿には持ち込まない）。topic（`@tasuki/topic-core`）は触らない
- **ドメインは `packages/poker-core` に純関数＋ `Result` で書く**（憲法 IV・`round.ts` と同じ形）。依存方向の許可表（`scripts/audit-dependency-direction.mjs`）で poker-core が引けるのは `@tasuki/protocol` だけ
- 時刻は**アプリ層が壁時計（`WallClock`）から渡す**。ドメインは時計を読まない
- wire（`packages/poker-core/src/protocol.ts`）にクライアント→サーバーの操作を足す: アイテム名の設定・再投票・次のアイテムへ（点数つき）・閉じた束の点数の設定（束 ID と点数または空）。**入力側は `v.strictObject`**、サーバー→クライアントの `room-state` に足す項目は `v.object`（前方互換・docs/poker/adr/0004）
- **古いバンドルとの互換**: `next-round` は**再投票として受ける**（決定済み。item も開いた束も残す。配布の途中で古い画面が残っていても壊れない）。wire のスキーマには残し、新しい画面は送らない
- **データ分類（ADR-0011 決定1 の MUST）**: アイテム名はバックログの題（業務上の情報）を含みうるが、4 段のどれにも明確には当たらない。決定1 の「当てはまらない値は厳しい側を仮に当てる」に従い、**「個人に紐づく」の扱い（揮発のみ・ログへ出さない）を当て、分類表の該当欄に書き足す**（5 段目は作らない。設計者の判断）。topic のお題の分類は今回の射程に入れない。ADR-0012 のログ衛生の射程に入る
- 表示は React の既定エスケープだけで描く。アイテム名を Markdown として描かない
- **部屋の中の操作にメッセージ単位のレート制限は無い**（poker のレート制限は入室失敗だけを数える `poker-rate-limit-gate.ts`）。新しい操作も足さない（ADR-0011 の「お題の `topic.set` と同じ扱い」）。守りはフレーム上限（`maxMessageBytes`）と長さの上限だけ
- **配布の途中の新旧の並び**: `deploy.sh` は web を先に配り、sync を後で差し替える。**新しい画面が古いサーバーにつながる短い窓は許す**（再起動でルームは全部消えるため。設計者の判断）。ただし新しい画面が古いサーバーのフレームを捨てないよう、`room-state` に足す項目は**受信側では省略可**にする

## 9. 実装役に任せること

- 型・メッセージ・モジュールの名前（`topic` の語を避けることだけ守る）
- アイテム名の上限の長さ、記録の行の上限、64rem 未満で出す束の数
- 行に平均・最頻値を持たせるか
- 分布の見せ方の細部（`Results` と揃える範囲）
- 画面の文言（base 層の実測が先）
- PR の分け方（ADR-0013 の粒度に従う）

## 10. 別の Issue にするもの

**見学者（投票しない参加者）**: 利用者の発案（2026-10-17）。ホストは無いが、見積もりに加わらず見ているだけの人は作れてよい。自動公開の判定（接続中の全員が投票済み）から外れる必要がある。**Issue の文案は利用者に見せてから立てる。**
