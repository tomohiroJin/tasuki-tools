### 2.1 本文に無い欠陥（計算による推定・E2E の対照実行で確かめる）

**320px の画面で、所要時間の数字が統計の札からはみ出している見込みが高い。** 札は常に 3 列で、内側の幅は次のとおり。

- 器の内側 = 320 − 16 × 2 = 288px。札 1 枚 = (288 − 12 × 2) ÷ 3 = 88px。`.meter-panel` の余白は 40rem 未満で 1.5rem（24px）× 2 と枠 1px × 2 → **内側は約 38px**
- 値の字は `--font-size-lg`（320px で 18.4px）・`white-space: nowrap`。「0分05秒」は数字 3 字（約 11px）＋漢字 2 字（18.4px）で**約 70px**

内側に収まらない行は先頭に寄せて右へ溢れる（CSS Text の規定）ので、所要時間の数字が隣の「交代回数」の札へ約 30px かぶる。ページの横溢れ（`scrollWidth`）は 3 枚目の札でも 320px を越えないので、既存の `buttons.spec.ts`（はみ出しと当たり）には掛からない。**これは推定である。** 計画の Task 1 で、札の中の字の矩形と札の内側を比べる物差しを書き、main の状態で赤になることを統括が確かめる。

## 3. 決定

### D1. まとめの器は部屋の器（`--wide`）を保つ

`pageOf` は、ルームのあるロビー・セッション・**まとめ**（`mode === "celebration"`）に `"wide"` を返す。読み込み中・喪失は `"prose"`、履歴は既定（72rem）のまま。

**理由**: まとめは別の画面ではなく、**同じ部屋の段階**（始める前 → 進行中 → 終えた後）である。上のステータスの帯は同じルームのコードと接続状態を出し続けるので、段階が変わっても同じ位置・同じ幅に居るべきである。器の段を段階ごとに変えると、帯ごと画面の幅が跳ねる（§2 の 3）。中身が少ないことは、器ではなく中身の側で読みやすい幅に寄せて扱う（README の「1 列のときの操作の面の幅は画面が決める（読みやすい幅で中央に寄せてよい）」と同じ考え方。poker はお題を隠したとき約 46rem で中央に寄せている）。

### D2. 中身（`.summary`）は段ごとに読みやすい幅で中央に寄せる

| 幅の段 | `.summary` の最大幅 | 並び |
|---|---|---|
| compact（`< 40rem`） | 器いっぱい（40rem に届かない） | 1 列。統計の札は縦に 3 枚積み、札の中はラベルを左・値を右の 1 行にする（計器の読み） |
| medium（`40rem ≤ w < 64rem`） | `40rem` | 1 列。統計の札は今と同じ 3 列（札の中はラベルの下に値） |
| wide・ultra（`≥ 64rem`） | `64rem` | 2 列。題と達成の帯は 2 列にまたがって上に、**左の列に統計の札 3 枚（縦に積む・計器の読み）、右の列にドライバー別の回数**。保存・新しいセッションは 2 列にまたがって下に |

- **64rem 未満の見た目は今と同じ**（compact の札の積み方だけが変わる）。40rem の上限は今の器（`--prose`）と同じ幅なので、タブレットの縦持ちでは中身の幅が変わらない。変わるのは帯の幅（器）だけである
- **64rem の上限の理由**: 2 列のそれぞれが約 31rem（496px）になり、ドライバー別の名前（6rem）・棒・回数が 1 行に収まり、計器の読みのラベルと値の間が開きすぎない。上限を置かないと 1920px の画面で 1 列が約 700px になり、ラベルと値が離れて読み取りにくい
- **ドライバー別の札が無いとき**（`driverCounts` を持たない旧記録・輪が空）: 64rem 以上でも統計の札を 2 列にまたがらせ、3 列（ラベルの下に値）で並べる。右の列を空のまま残さない
- **中断**（記録なし）: 題・一言・新しいセッションだけで、どの段でも 1 列・中央寄せ。器は D1 のとおり `--wide` で、帯は動かない
- **DOM の順は変えない**（題 → 達成の帯 → 統計 → ドライバー別 → 次の行動）。2 列でも左上から右下へ読む順と DOM の順・読み上げの順が揃う
- 並び替えは `summary.css` の `@media (width >= 40rem)` と `@media (width >= 64rem)` の 2 つだけで書く（ADR 0025 決定 1 の境目）。2 列の配置は `.summary` の直下の子に掛けるので、統計の札とドライバー別の札は `.summary` の直下に置いたままにする（今と同じ）。ドライバー別の有無は `:has(> .summary-drivers)` で見る（部品層の `.ui-workspace` と同じ書き方）
- 2 列の行は高さを揃える（grid の既定の `stretch`）。統計の札 3 枚は左の列の高さを分け合う

### D3. 字の段と札の大きさ

- **統計の値は 64rem 以上で `--font-size-xl`**（今は全幅で `--font-size-lg`）。広い画面ではまとめの主役は数字で、題（xl）より小さい lg のままだと、ロビー・セッションの区画の見出し（lg）と並ぶ程度にしか目立たない。64rem 未満は lg のまま（medium の 3 列の札に xl の「120分00秒」は 640px の画面で収まり切らない見込み）
- 題（`.summary-title` xl・900）・達成の帯の題（lg）・ラベル（xs の計器ラベル）・ドライバー別の行（sm）は変えない。いずれも README の「文字の段」の役割（画面の見出し xl・区画の見出し lg・添え書き xs・項目 sm）に既に合っている
- 札は今と同じ計器のパネル（`Card` / `.meter-panel`）で、余白はロビー・セッションの札と同じ（40rem 未満 1.5rem・以上 1.75rem）。札の新しい種類を作らない

### D4. 文書を揃える

| 文書 | 直すこと |
|---|---|
| `packages/ui/README.md`「器の選び方」 | 表の 1 行目の例から「まとめ」を外す。3 行目を「道具の部屋（区画を横に並べる）と、その部屋の段階（始める前・進行中・終えた後のまとめ）」にする。表の下に「**部屋の中で段階が移る画面は、段階が変わっても器を変えない。** 器を変えると上の帯ごと画面の幅が跳ねる。中身が少ない段階は、中身の側で読みやすい幅に寄せて中央に置く」を足す。「新しい画面や機能を足すときの手順」の 1 も同じ言い方に揃える |

## 4. 退けた案

| 案 | 退けた理由 |
|---|---|
| **A. `--prose`（40rem）のまま、字の段と札の大きさだけを上げる** | 帯ごと幅が跳ねる問題（§2 の 3）が残る。利用者の「バランスがおかしい」は 1920px の画面で 640px の中身が浮いて見えることで、字を上げても中身の幅は変わらない |
| **B. 既定の器（72rem）に上げる**（統括の見立ての片方） | 1920px の画面で帯が 1536px から 1152px へ縮み、跳ねは小さくなるが残る。README の「選ぶ・一覧する」画面の段で、まとめはそれに当たらない |
| **C. `--wide` にして、中身も器いっぱい（約 1440px）に広げる** | 1 列が約 700px になり、統計の札のラベルと値が離れ、ドライバー別の棒が長すぎて回数の差が読み取りにくい。題と達成の帯の 1 行も長い |
| **D. 統計の札を 64rem 以上でも横 3 枚のまま左の列に置く** | 64rem（1024px）の画面で左の列は約 455px、札 1 枚の内側は約 88px で、xl の「120分00秒」（約 130px）も lg の「0分05秒」（約 78px）も危うい。縦に積めば内側は約 400px あり、字の段を上げられる |
| **E. 統計とドライバー別の並べ替えをコンテナクエリで書く** | 統計の札の列の数を `.summary-stats` 自身の幅で変えるには、もう 1 つ包む要素が要る。幅の段（`@media`）で足りる（中身の幅が段ごとに決まっているため） |
| **F. ロビー・セッションの段組み（`.ui-workspace`）を使う** | 区画は操作の面と脇の 2 つで、脇は「参照するもの」（README）。まとめの 2 列は主従の無い 2 つの読み物で、脇は 22rem 固定か読む面の比（約 45%）になる。統計を脇にすると 22rem に詰まり、主従も逆に見える |

## 5. 4 つの幅での見え方（計算・撮影で確かめる）

| 幅 | 器（帯の幅） | `.summary` | 並び |
|---|---|---|---|
| 320 | 320px（今と同じ） | 288px | 1 列。統計の札は縦に 3 枚、各札は「所要時間 … 0分05秒」の 1 行。数字は札の内側（約 238px）に収まる |
| 768 | 768px（**今は 640px**） | 640px（今と同じ） | 1 列。統計の札は横に 3 枚（内側 約 147px） |
| 1280 | 1280px（**今は 640px**） | 1024px（64rem） | 2 列（各 約 500px）。左に統計の札 3 枚を縦に、右にドライバー別。題と帯は 1024px にまたがる |

## 6. アクセシビリティ

- **読む順**: DOM の順を変えない。2 列では上（題・達成の帯）→ 左の列（統計）→ 右の列（ドライバー別）→ 下（次の行動）と見え、DOM の順・読み上げの順・Tab の順と同じ
- **見出しの段**: 題の `h2` は変えない（まとめの画面の見出しの段は本 Issue の外）
- **押せる大きさ**: ボタンは 2 つのまま（`.ui-button` の既定と `--lg`）。並びは中央寄せのまま。`buttons.spec.ts` の「timer まとめ」が 4 つの幅で 44px と重なりを測り続ける
- **色**: 色を足さない・変えない（コントラストの走査の結果は変わらない）
- **動き**: 動きを足さない（`prefers-reduced-motion` の手当ては要らない）
- **書体の base 層**: **文言を足さない・変えない。** 今のまとめの文言 13 種（「セッション完了」「ナイスワーク！」「所要時間」「交代回数」「周回数」「ドライバー別の回数」「記録を保存」「保存しました」「新しいセッション」「お題をやり遂げました。お疲れさまでした。」「完了時に自動保存されています。手動で再保存もできます。」「記録は残りません。お疲れさまでした。」「セッション終了（中断）」）と単位（分・秒・回・周）を `packages/ui/src/tokens/fonts.css` の base の `unicode-range`（400・500・700 の 3 面）で 1 字ずつ測り、すべて収まることを確かめた（2026-10-12）。参考: 見出しの候補に考えた「振り返り」（返）・「統計」（統）・「担当」（担・当）は base に無く、使わない

## 7. 何で固定するか

### 7.1 E2E（`e2e/specs/layout.spec.ts`・**ルームを足さない**）

既存の「timer は 1 つのルームでロビー・セッション・お題・まとめの順に画面を見る」の末尾（まとめ）を広げる。まとめは完了のあと幅を変えても出続けるので、同じルームで 4 つの幅を測れる。

| # | 確かめること | 物差し（実装と前提を共有しない） | 正しい実装と誤実装で分かれる局面 |
|---|---|---|---|
| L1 | 完了の前後で器と帯が動かない（1920） | セッションの画面で器（`div.ui-page.stage-inner`）の外寸と `.app-status-strip` の `x`・幅を測り、完了後に同じ値か（±0.5px）を見る。**クラス名や 96rem の直値と比べない**（段の名前を変えても、跳ねないことだけを見る） | main（`--prose`）では 1536 → 640 で赤。B 案（72rem）でも 1536 → 1152 で赤 |
| L2 | 64rem 以上で 2 列（1920・1280） | 統計（`.summary-stats`）の右端 ≤ ドライバー別（`.summary-drivers`）の左端、上端の差 ≤ 1px。達成の帯の左端 ≤ 統計の左端・右端 ≥ ドライバー別の右端（帯は 2 列にまたがる） | main では縦に積まれて赤 |
| L3 | 64rem 以上で中身は中央の 64rem 以下（1920） | `.summary` の幅 ≤ 1024.5px、左右の余り（器の内側の左端・右端との差）の差 ≤ 1px | C 案（器いっぱい）で赤 |
| L4 | 統計の札の積み方（320・1920 は縦、768 は横） | 3 枚の札の上端を比べる。縦なら上端が狭義に増え左端が揃う、横なら上端が揃う（±1px） | D 案で 1920 が赤、medium の 3 列を壊すと 768 が赤 |
| L5 | 統計の数字が札に収まる（320・768・1280・1920） | 値の文字の `Range` の矩形が、札（`.meter-panel`）の矩形から枠と余白を引いた内側に収まる（±0.5px）。`scrollWidth` やクラスの値を読まない | §2.1 の推定どおりなら main の 320 で赤 |
| L6 | 320 で横に溢れない | 既存の `expectNoHorizontalOverflow` | — |

既存の `buttons.spec.ts`（390 から 4 つの幅でまとめの押せる大きさ・重なり・字の折れ・横溢れ）はそのまま通す。中断のまとめは E2E で測らない（§9）。

### 7.2 単体テスト（Vitest）と変異（ID 130〜139 のうち 2 つを使う）

`pageOf` は `App.tsx` の中の関数なので、`<App />` を FakeWS で動かし、`Stage` の器の `className` を見る（新しいテストファイル `apps/timer-web/test/ui/App.page-tier.test.tsx`）。

| テスト | 物差し | 捕まえる変異 |
|---|---|---|
| セッションの snapshot → 完了の snapshot で、器の `className` が変わらない | 2 つの時点の `className` を比べる（直値と比べない） | **m130** `pageOf` がまとめに `"prose"` を返す（今の main の形） |
| snapshot が届く前（読み込み中）の器は `--prose` | `className` に `ui-page--prose` を含む | **m131** `pageOf` の既定の枝を `"wide"` にする（「全部 wide にすれば跳ねない」という雑な直し方で、読み込み中・行き先の無い URL の画面まで 96rem になる） |

並びと字の大きさ（L2〜L5）は jsdom では測れないので変異にしない。E2E の破壊検証（計画の Task 4）で、`summary.css` の 64rem の規則と 40rem 未満の積み方をそれぞれ外して赤を見る。

## 9. 受け入れた限界

- **中断のまとめは E2E で測らない。** 中断にするとルームが戻れないので、既存のルームの流れ（完成で終える）と両立しない。ルームを 1 つ足す余裕が無い（E2E 全件がルーム枠 100 ぎりぎり）。中身は題・一言・ボタンの 1 列で、並び替えの規則に掛からない（`:has(> .summary-drivers)` も統計も無い）
- **参加者が少ないと、64rem 以上でドライバー別の札の下に空きが出る**（2 列の高さを揃えるため。2 人なら棒は 2 本）。統計の札 3 枚の側を縮めて揃えると数字の札が潰れるので、空きを受け入れる
- **64rem をまたいで幅を変えると、統計の札の並びが組み替わる**（縦 → 横 → 縦）。画面を作り直す操作として許す
- お題のタイトル（記録の `topicTitle`）はまとめに出していない。本 Issue の外（§10 の利用者に確かめたい点）
