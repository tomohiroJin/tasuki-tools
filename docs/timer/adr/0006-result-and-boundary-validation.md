# ADR-0006: Result 型のエラー処理と Valibot 境界検証

- **ステータス**: Accepted
- **関連要件**: FR-010, FR-017, FR-023, FR-084, NFR セキュリティ（境界検証・境界正規化）

> **昇格**: 全体標準としては [docs/adr/0005](../../adr/0005-result-and-boundary-validation.md) が後継。timer 固有の詳細は本文のまま有効。

## 背景

ドメインは多くの拒否条件（空名・重複名・人数上限/下限・無効な交代間隔・権限不足・フェーズ競合）を
持ちます。例外で表現すると、どのエラーが起こり得るかが型に現れず、握り漏れが起きます。また WebSocket
の受信メッセージは外部入力であり、未知 type・過大サイズ・不正形式を境界で確実に弾く必要があります。
AI 由来テキストも信頼しないデータです。

## 決定

- **エラー処理**: `neverthrow` の `Result<T, E>` を用い、`decide` は例外を投げず
  `Ok(events)` / `Err(DomainError)` を返す。アプリケーション層が `Err` を受けて送信者へ `error` を返す。
- **境界検証**: front/server で共有する **Valibot** スキーマ（`schemas.ts`）で、全 WS メッセージを
  境界で一度だけ検証する。未知 type・余剰や不正・サイズ超過を即拒否。`config.set` も必ず
  `decide` のドメイン検証を通す。
- **境界正規化**: 表示名は検証だけでなく、境界で**正規形へ変換**する（`v.transform`）。
  以後は正規形しか内側へ流れない。呼び出し側ごとに `trim()` する方式は必ずどこかが抜ける
  （実際に `room.join` だけ素通りし、見た目が同じで文字列が違う名前が並んだ）。
  最大長は正規化の**前後で二重に**課す。NFKC は文字数を増やしうるため（最大 18 倍）、
  前段だけでは保存・配信される値に上限が効かない。
- **AI 出力**: `validateProblem` でお題構造へ検証してから使用し、失敗時は定型へ縮退する。

## 影響

- **利点**: 起こり得るエラーが `DomainError` 合併型として型に現れ、握り漏れを防げる。境界検証の
  スキーマが契約そのものとなり、front/server で同一物を共有するためズレない。
- **代償**: `Result` の連鎖で記述がやや冗長になる。スキーマ定義の保守コストが増えるが、契約の
  単一情報源として価値が上回る。
- 実装上の注意: Valibot の `object` は未知キーを strip するため、現状は「未知キーで弾く」のではなく
  「無視する」挙動。厳密な reject はセキュリティ強化（M4）で検討する。


## 追記（2026-08-31・#209）: 契約に合わないフレームを捨てたことを利用者へ伝える

**背景**: [#181](https://github.com/tomohiroJin/tasuki-tools/issues/181)（`docs/adr/0005` の
追記が正本）で、`apps/timer-web` は受信フレームを `ServerMsgSchema` に通し、
落ちたものを捨てるようにした。**捨てること自体は正しいが、捨てたことが利用者に
一切伝わらなかった。** `snapshot` の棄却は継続しうるため、画面は生きて見えたまま
古い状態で固まり、再接続もエラー表示も起きない。

**決定**: `StatusStrip` に 4 つ目の接続状態「同期できていません (Out of Sync)」を足す。
ルームに入る前は表示する場所が無いので、その間だけ**消えないバナー**で補う。

1. **なぜ接続表示なのか。** 起きている異常は「接続は生きているのに画面だけが古い」で、
   利用者にとって「同期できているか」は接続の一部である。既に常設・色＋テキスト併記
   （FR-032）・`role="status"` を備えた場所がここしかない。バナーは枠が 1 つで、
   他の通知や再接続時の `clearBanner` に消される。**継続する異常を、消える面に載せない。**

2. **ルームに入る前だけバナーで補う。** `App.tsx` は `mode` が `setup` / `join` の間
   `StatusStrip` を描画せず、`mode` を動かすのは有効な `snapshot` だけである。したがって
   **壊れた値の残ったルームへ入ろうとすると、最初の `snapshot` から捨てるので表示する場所が
   無い**（実測: `StatusStrip` は描画されず、利用者には「ボタンが効かない」としか見えない）。
   ここは #209 が守りたかった本命の場面なので、`room` が無い間はバナーへ出す。

3. **一過性の棄却と継続的な棄却を、検証器の診断で区別する。** 立てるのは
   「画面が古くなる棄却」だけで、判定は `apps/timer-web/src/sync/stale-frame.ts` の
   `indicatesStaleRoom` が**落ちた項目の経路**から行う。**フレーム自身が名乗る `type` は
   使わない** —— それは契約検証に落ちた値であり信頼できない。経路はスキーマ自身の診断なので、
   送り手の意図で曲げられない。実測した対応:

   | 捨てたフレーム | 経路 | 画面は古くなるか |
   |---|---|---|
   | 壊れた `snapshot` | `room.config.members.0` | する |
   | `room` が数値／欠落 | `room` | する |
   | 素の数値・`null`・文字列・JSON として読めない | `<root>` | する（何だったか分からない） |
   | 配列・`type` 欠落・未知の `type` | `type` | する（同上） |
   | 壊れた `signal` / `error` / `room.joined` | `nextDriverName` / `message` / `resumeToken` | しない |

   **判別がつかないものは古い側へ倒す。** 画面が古いのに黙っているほうが、
   一時的に過剰へ倒れるより悪い。

4. **解除は有効な `snapshot` を受け取ったときだけ。** クライアントは 10 秒ごとに
   `time.ping` を送り `time.pong` が返る（`sync/client.ts` の `startPingLoop`）。
   「有効なフレームが届いたら解除」にすると、`snapshot` だけが落ち続ける状況で
   pong のたびに表示が消える。**そして `apps/timer-sync` に固定間隔の `snapshot` 配信は
   無い**（`broadcastSnapshot` の呼び出しはコマンド処理・presence 変化・お題委譲・
   自動交代のみ。2026-08-31 実測）ので、表示が戻るのは次に状態が動いたときになる。
   結果は「点滅」ではなく「消えて、しばらく戻らない」で、**そちらのほうが悪い**。
   3 の区別を入れたのは、この非対称のためでもある —— 一度立てると次の状態変化まで
   下りないので、画面が古くならない棄却では立ててはいけない。

5. **再読込の導線は置かない。** 継続する棄却の原因はサーバー側のルームに残った契約違反の
   値なので、**再読込しても直らない**。「再読み込みしてください」は嘘の導線になる。

6. **文言は自己ホスト書体の base 層に収まる字だけで書く。** 最初に選んだ「同期不整合」は
   「整」が base 層外で、この状態が出た瞬間に ext 層（約 210 KB）を追加取得していた
   （`packages/ui/src/tokens/fonts.css` の `unicode-range` を実測）。
   `packages/ui/README.md` が予告している劣化そのものなので、全字が base 層に収まる
   「同期できていません」へ改めた。

**検査**: `e2e/specs/timer.spec.ts` に `page.routeWebSocket()` で実際に壊れた `snapshot` を
流す `local` 専用シナリオを 2 本置いた（ルームに居る間の棄却／最初から捨てる場合）。
**製品コードにテスト用の経路は作らない。** どちらも配線を切って対照実行し、落ちることを
確かめた。変異 16・17（`scripts/mutations/`）が判定と解除点を守る。

**影響**: `dispatchServerMessage` は JSON として読めないフレームでも
`onInvalidFrame(["<root>"])` を呼ぶようになった（それまで無言で、**最も壊れている場面だけが
表出から外れていた**）。
